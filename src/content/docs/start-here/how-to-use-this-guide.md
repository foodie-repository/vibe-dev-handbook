처음부터 전체 흐름을 쌓는 방법과 지금 막힌 문제부터 찾는 방법은 같은 목적을 향하는 두 출발점입니다. 어느 쪽을 선택해도 한 문장 정의, 시스템에서의 위치, 판단 규칙과 검증 증거까지 확인해야 하며, 필요하면 언제든 다른 방법으로 전환할 수 있습니다.

## 처음부터 따라가기

[학습 경로의 Build Track](../learning-paths/#build-track-작은-서비스를-끝까지)은 핵심 개념에서 두 캡스톤까지 순서대로 연결합니다. 앞 장의 결정이 다음 장의 입력이 되는 흐름을 따라가며, 각 장을 읽은 뒤 다음 세 가지를 자신의 말로 기록하세요.

1. 이 개념의 한 문장 정의는 무엇인가
2. 내 시스템에서 어디에 있고 무엇과 연결되는가
3. 어떤 판단 규칙과 증거로 성공·실패를 구분하는가

순서대로 읽는 목적은 모든 문장을 외우는 것이 아니라 요구사항·설계·구현·테스트·배포·운영이 어떻게 이어지는지 설명할 수 있게 되는 것입니다.

## 필요한 내용만 찾기

작업 중 낯선 말이나 오류를 만났다면 사이트 검색과 참고편을 다음 순서로 사용하세요.

1. 먼저 `백엔드`, `인증`처럼 알고 있는 **한국어 용어**로 검색합니다.
2. 결과가 넓거나 없으면 `backend`, `authentication`, `API`, `SDD`처럼 **영문 또는 약어**로 다시 검색합니다.
3. 상황을 **문제 문장**으로 검색할 수도 있지만, 검색이 문장의 뜻을 해석해 관련 장을 찾는다고 보장하지는 않습니다. 예를 들어 `로그인은 됐는데 참가 신청이 거절됨`은 이 사용법의 예시만 찾을 수 있습니다. 결과가 없거나 예시만 나오면 `인증`, `인가`처럼 핵심어로 줄이세요. 또는 [API·데이터베이스·인증](../../04-backend-data/api-database-auth/)으로 직접 이동해 로그인 확인과 행동 권한, 모집 상태·정원 같은 업무 조건을 나누어 확인합니다.
4. [개발 용어집](../../reference/development-glossary/)과 [에이전트 출력 용어집](../../reference/agent-output-glossary/)에서 뜻, 비슷한 용어, 보장하지 않는 범위를 확인합니다.
5. 용어집이 연결한 관련 장으로 이동해 **한 문장 정의 → 시스템에서의 위치 → 판단 규칙** 순서로 읽고, 현재 문제에 필요한 검증 증거를 고릅니다.

검색 결과 한 문장만으로 결론을 내리지 마세요. 같은 단어도 제품과 문맥에 따라 뜻이 달라질 수 있으므로 관련 장의 경계와 실패 조건까지 확인해야 합니다.

## 용어보다 관계를 그리세요

새 용어를 만났을 때 정의만 메모하지 말고 다음 네 칸을 채웁니다.

| 질문 | 기록 예시 |
|---|---|
| 무엇인가 | API는 두 구성요소가 요청과 응답을 주고받는 약속입니다. |
| 어디에 있는가 | 브라우저와 백엔드 사이 또는 서비스와 서비스 사이에 있습니다. |
| 무엇이 실패하는가 | 형식 오류, 인증 실패, 시간 초과, 서버 오류가 생깁니다. |
| 무엇으로 확인하는가 | 요청 로그, 상태 코드, 응답 본문, 계약 테스트를 봅니다. |

## 비유의 한계를 확인하세요

비유는 이해의 발판이지 설계 규칙이 아닙니다. API를 식당 주문 창구에 비유할 수 있지만, 컴퓨터 시스템은 모호한 말을 사람처럼 보완하지 않습니다. 정해진 데이터 형식과 권한을 만족해야 합니다.

## 자신의 프로젝트 지도를 함께 만드세요

문서를 읽으면서 `PROJECT_CONTEXT.md` 또는 개인 노트에 다음을 누적합니다.

- 사용자와 해결하려는 문제
- 주요 구성요소와 책임
- 데이터의 출처와 이동 경로
- 중요한 제약과 금지 사항
- 결정한 내용과 이유
- 검증 명령과 배포 확인법

대화 기록만으로 프로젝트 맥락을 관리하면 세션이 바뀔 때 결정의 이유가 사라집니다.

## AI에게 한 번에 전부 맡기지 마세요

권장 작업 단위는 리뷰어가 독립적으로 승인하거나 거절할 수 있는 크기입니다.

- `/status`: 현재 사실과 불확실성을 보고합니다.
- `/goal`: 이번 작업의 목표와 비목표를 고정합니다.
- `/plan`: 변경 파일, 수용 기준, 위험, 검증 명령을 제시합니다.
- `/execute`: 승인된 한 단계만 변경합니다.
- `/verify`: 테스트·빌드·로그와 수용 기준을 대조합니다.
- `/review`: 구현 맥락을 보지 않은 관점으로 결함을 탐색합니다.
- `/update`: 결정, 진행 상태, 다음 작업을 저장소에 반영합니다.

도구마다 실제 명령 문법은 다를 수 있지만 이 사고 순서는 그대로 사용할 수 있습니다.

## 완료 상태를 섞지 마세요

에이전트가 “완료했습니다”라고 말하면 무엇이 완료됐는지 증거별로 나누어 확인하세요.

| 상태 | 확인할 직접 증거 | 아직 보장하지 않는 것 |
|---|---|---|
| 파일 변경 | `git status`, 대상 파일, diff | 테스트 통과와 요구 충족 |
| 자동 검증 | 실제 명령, 환경, 종료 코드, 통과·실패 수 | 브라우저·데이터·운영 성공 |
| 브라우저 확인 | 대상 URL, 뷰포트, 콘솔, 사용자 흐름 | 원격 배포와 다른 사용자 환경 |
| 로컬 커밋 | 커밋 SHA, 포함 파일, clean 여부 | 원격 push·검토·병합 |
| 원격 반영 | 원격 SHA, push·Pull Request·병합 결과 | 자동화 여부와 관계없이 배포가 실행·성공했는지, 기대한 버전이 배포됐는지 |
| 배포 | 배포 작업 결과, 배포된 SHA | 비로그인 공개 URL의 실제 동작 |
| 공개 확인 | 실제 URL, 배포 SHA, 검색·링크·자산 확인 | 이후 운영과 장애 복구 |

한 단계의 성공을 다음 단계의 성공으로 확대하지 마세요. 특히 로컬 빌드 성공과 실제 공개 배포 성공, 커밋과 push, 배포 작업 성공과 사용자 흐름 성공은 별도 상태입니다.

## 위험이 큰 영역은 전문가 경계를 세우세요

인증, 개인정보, 결제, 권한, 데이터 삭제, 법적 규제, 운영 마이그레이션은 작은 실수도 피해가 큽니다. AI가 코드를 생성할 수 있다는 이유만으로 독립 검토가 불필요해지지 않습니다.
