## 먼저 결론

AI가 “완료했습니다”라고 말한 것은 **주장**입니다. 계획은 아직 하지 않은 행동의 순서이고, diff는 실제 파일 변경이며, 테스트 출력은 특정 환경·명령·시점에 관찰한 **증거**입니다. 이 네 가지는 서로 대신할 수 없습니다.

리뷰의 목적은 AI의 문장을 더 그럴듯하게 고치는 데 있지 않습니다. 요구사항과 현재 상태를 기준으로 변경과 증거를 다시 대조하고, 발견한 의견까지 재현하거나 기각한 뒤 사람이 수용할 수 있는 상태인지 판정하는 데 있습니다.

## 한 문장 정의

**에이전트 결과 리뷰와 검증**은 구현자와 다른 관점에서 요구·설계·변경·증거·운영 위험을 검사하고, 각 지적을 재판정한 뒤 수용 기준별 결론과 미검증 범위를 기록하는 작업입니다.

## 비유와 비유의 한계

리뷰어는 영수증과 물건을 함께 확인하는 검수 담당자에 가깝습니다. “주문대로 보냈다”는 판매자의 말은 주장이고, 주문서는 요구이며, 상자 안 물건은 변경 결과이고, 수량·상태를 확인한 기록은 증거입니다. 주문서와 영수증만 맞아도 물건이 깨졌을 수 있고, 물건이 멀쩡해 보여도 주문과 다를 수 있습니다.

그러나 소프트웨어 리뷰는 상자 검수보다 어렵습니다. 같은 코드도 권한·데이터·브라우저·운영 환경에 따라 다르게 실패하고, 테스트 자체가 결과를 맞다고 판단하는 기준인 오라클을 잘못 정할 수 있으며, 리뷰어도 오탐을 낼 수 있습니다. 따라서 “두 번째 AI가 봤다”는 사실만으로 독립성이나 정확성이 보장되지는 않습니다.

## 먼저 네 종류를 분리합니다

| 종류 | 예 | 확인 질문 |
|---|---|---|
| 주장 | “중복 참가를 막았습니다.” | 누가 어떤 범위와 시점에 그렇게 말했나요? |
| 계획 | “통합 테스트를 추가하겠습니다.” | 아직 실행하지 않은 항목은 무엇인가요? |
| 변경 | `registrations` 제약과 참가 처리 코드의 diff | 어떤 파일·데이터·설정이 실제로 바뀌었나요? |
| 증거 | 동시 요청 테스트의 명령·종료 코드·최종 데이터 조회 | 그 주장을 직접 판정하며 현재 변경에서 다시 만든 결과인가요? |

설명이나 주석은 구현을 이해하는 단서지만 실제 동작의 증거는 아닙니다. 테스트 파일이 존재한다는 사실도 테스트 실행 성공과 다르고, 로컬 커밋은 원격 push·배포·공개 사용자 성공과 다릅니다.

## 독립 검토는 무엇을 분리하나요?

같은 대화에서 같은 에이전트에게 “다시 잘 봐”라고 하는 자체 검토도 작은 실수를 찾는 데 유용합니다. 다만 처음의 해석·생략·확증 편향을 그대로 공유할 가능성이 큽니다. 독립 검토에서는 적어도 다음 세 축을 의도적으로 분리합니다.

1. **역할**: 구현자는 고치지 않고, 리뷰어는 변경하지 않은 채 결함과 근거를 보고합니다.
2. **컨텍스트**: 리뷰어는 구현 대화의 결론보다 정본 요구·현재 파일·diff·실행 증거를 새로 읽습니다.
3. **권한**: 가능한 경우 리뷰어는 읽기와 비파괴 검증만 사용하고 write·network·외부 부작용 권한을 받지 않습니다.

이 분리는 검토의 관점을 개선하지만 통계적 독립성이나 정답을 보장하지 않습니다. 같은 모델 계열, 같은 잘못된 스펙, 같은 테스트 오라클, 같은 불완전한 fixture를 공유하면 두 에이전트가 같은 오류를 통과시킬 수 있습니다. 중요한 결정은 도메인 전문가와 사람이 최종 수용하며, AI 리뷰 PASS는 그 판단을 돕는 한 증거입니다.

## 리뷰의 다섯 층

### 1. 요구사항 적합성

- 수용 기준을 실제로 충족하나요?
- 비목표와 허용 파일을 침범하지 않았나요?
- 정상 경로뿐 아니라 예외·경계·실패 뒤 상태가 정의됐나요?
- 사용자·업무 규칙·제품 동작을 근거 없이 추측하지 않았나요?

### 2. 설계 적합성

- 책임·신뢰 경계·권위 상태가 기존 아키텍처와 맞나요?
- 새로운 중복·결합·숨은 외부 의존성을 만들지 않았나요?
- 데이터 흐름과 인증·인가·동시성 판단 위치가 명확한가요?
- 현재 문제에 필요하지 않은 일반화·새 패키지·구조 변경이 생기지 않았나요?

### 3. 구현과 diff

- 실제 변경 파일이 계획과 허용 범위에 정확히 일치하나요?
- 의도하지 않은 삭제·전체 포맷·생성물·비밀·개인정보가 포함됐나요?
- 오류 처리, 트랜잭션, 자원 정리와 되돌리기 경로가 있나요?
- 이름·주석·완료 보고가 실제 코드와 데이터 동작을 설명하나요?

### 4. 검증 증거

- 수정 전 실패를 확인했다면 요구와 관련된 올바른 이유로 실패했나요?
- 실행 명령·환경·대상 범위·테스트 수·종료 코드가 있나요?
- 필터 0건·건너뜀·예상 실패·오래된 캐시가 성공처럼 숨지 않았나요?
- mock보다 실제 계약·데이터·브라우저에서 확인해야 할 위험이 남았나요?

### 5. 운영 위험

- 환경 변수와 비밀이 소스·로그·브라우저에 노출되지 않나요?
- 스키마·데이터·API 호환성과 실패 시 중단·복구가 있나요?
- 로그와 지표로 실패를 발견하고 권위 상태를 재조회할 수 있나요?
- build·deploy·공개 사용·rollback·data recovery를 서로 다른 상태로 검증했나요?

## 위험마다 증거층이 다릅니다

증거를 많이 모으는 것보다 주장을 직접 판정하는 증거를 고르는 것이 중요합니다.

| 증거층 | 직접 확인하는 것 | 대신하지 못하는 것 |
|---|---|---|
| 요구·정본 | 목표·비목표·수용 기준·권한 | 실제 구현과 실행 성공 |
| diff·Git 상태 | 파일·설정·삭제·비밀 후보와 변경 범위 | 런타임 동작·원격 반영 |
| 정적 검사·test·build | 구문·타입·계약·선택한 오라클·아티팩트 생성 | 실제 데이터·브라우저·운영 사용자 성공 |
| data·권위 상태 | 제약·트랜잭션·최종 행·불변식 | 화면 표시·외부 전달 성공 |
| browser·접근성 | 실제 DOM·스타일·픽셀·키보드·요청·오류 | 서버 내부 불변식·다른 기기 전체 |
| security·권한 | 허용·거절·비밀 노출·부정 경로 | 취약점 부재와 미래 공격 방지 |
| human judgment | 도메인 의미·사용성·법률·운영 수용 | 실행하지 않은 자동·실제 검증 |

예를 들어 CSS diff와 스냅샷만으로 모바일 화면을 수용하지 않습니다. 실제 뷰포트에서 H1·상태 문구·overflow·콘솔 오류를 확인합니다. 데이터 변경은 화면 성공만 보지 않고 권위 있는 저장소의 최종 상태와 불변식을 재조회합니다. 권한 변경은 정상 동작만 보지 않고 미인증·타인 자원·범위 밖 대상이 거절되는 부정 테스트를 포함합니다.

## 한 작업을 검토하는 순서

1. **기준 상태를 고정합니다.** 저장소 경로·branch·HEAD·dirty 상태·규칙·실행 환경을 기록합니다.
2. **리뷰 계약을 만듭니다.** 정본 요구, 비목표, 허용 파일, 수용 기준, 위험, 실행 가능한 비파괴 검증을 제공합니다.
3. **주장을 목록으로 바꿉니다.** 완료 보고의 각 문장을 요구·변경·증거·미검증 중 하나로 분류합니다.
4. **범위부터 봅니다.** 전체 diff와 파일 목록에서 예상 밖 변경·생성물·비밀을 먼저 찾습니다.
5. **위험별 증거를 대조합니다.** 요구·설계·test·data·browser·security·운영 중 필요한 층만 선택합니다.
6. **finding을 심각도와 근거로 씁니다.** 파일·위치, 깨지는 시나리오, 영향, 요구 또는 증거를 포함합니다.
7. **재판정합니다.** 구현 담당자는 각 finding을 재현·기각·질문·별도 작업으로 분류하고 근거를 기록합니다.
8. **고친 뒤 같은 오라클을 다시 실행합니다.** 좁은 재현과 전체 회귀를 구분하고 새로운 diff도 다시 검토합니다.
9. **수용 여부를 결정합니다.** 수용 기준별 직접 증거, 미실행 검증, 남은 위험, 승인 주체를 남깁니다.

## 리뷰 에이전트 브리프 예시

```text wrap
당신은 구현자가 아니라 읽기 전용 독립 리뷰어다.
정본 요구와 현재 저장소 상태, base..HEAD diff, 새 검증 증거를 먼저 대조하라.
새 코드·설정·외부 상태를 바꾸지 말고 결함을 심각도 순으로 보고하라.
각 지적은 파일과 위치, 깨지는 시나리오, 영향, 요구 또는 직접 증거를 포함하라.
스타일 선호보다 정확성·데이터 무결성·권한·호환성·검증 누락을 우선하라.
근거 없는 가능성은 질문으로, 범위 밖 개선은 후속 후보로 분리하라.
PASS라면 무엇을 실제로 읽고 실행했는지와 미검증 범위를 함께 써라.
```

리뷰어에게 운영 자격 증명·배포 권한·write 권한을 기본 제공하지 않습니다. 동적 검증이 필요하면 가상 fixture와 격리된 환경, 허용된 명령, 정리 절차를 계약에 넣습니다. 리뷰 중 결함을 발견해도 리뷰어가 조용히 수정하면 발견 증거와 수정 diff가 섞이므로, 먼저 finding을 고정하고 변경 작업을 별도로 시작합니다.

## finding은 다시 판정해야 합니다

AI 리뷰 의견을 많이 적용했다고 품질이 높아지는 것은 아닙니다. 각 의견을 다음 상태 중 하나로 기록합니다.

- **confirmed defect**: 요구·재현·직접 증거가 결함을 지지합니다.
- **design decision**: 동작 오류가 아니라 장단점이 있는 선택이며 기존 결정과 변경 조건을 확인해야 합니다.
- **needs context**: 정본이나 사용자 결정이 없어서 판정할 수 없습니다.
- **out of scope**: 유용할 수 있지만 현재 수용 기준에 필요하지 않습니다.
- **false positive**: 현재 코드·문서·실행 증거가 지적의 전제를 반박합니다.

판정 기록에는 finding ID, 원래 주장, 확인한 파일·명령·결과, 판정, 조치와 재검증을 남깁니다. “리뷰어가 틀렸다”나 “수정했다”만 쓰면 다음 사람이 결정을 재현할 수 없습니다.

## 오탐·기각·재검증 예시

모임 웹앱 W-03에서 리뷰어가 “빠른 두 번 누르기가 활성 참가 두 건을 만든다”고 지적했다고 가정합니다.

1. 현재 스키마의 활성 `(event_id, participant_id)` 고유성, 참가 트랜잭션과 재시도 계약을 읽습니다.
2. 격리된 실제 데이터베이스에서 같은 가상 사용자의 독립 요청·연결로 시험합니다. 동시에 시작했다는 사실만으로 경쟁을 입증하지 않고, 선택한 보호 전략에 맞춰 경쟁 구간의 교차 실행을 통제하거나 관측합니다. 사전 조회만 하는 결함 구현이 시험에서 드러나는지도 확인합니다.
3. 두 행이 저장되면 `confirmed defect`이고, API 선검사만 믿지 말고 데이터 제약과 트랜잭션을 수정합니다.
4. 실제 보호 제약·트랜잭션과 경쟁 구간 증거를 대조하고, 한 건만 `commit`되며 다른 요청은 안전하게 거절되고 부분 저장 없이 최종 활성 행이 1건인지 확인합니다. 이 근거가 지적의 전제를 반박할 때만 확인한 구현·환경·시나리오 범위의 `false positive`로 기각합니다. 한 번의 성공이 모든 경쟁 조건의 부재를 증명하지는 않습니다.
5. mock 저장소만 썼거나 실제 제약·경쟁 구간·결함 검출 능력을 입증하지 못했다면 “현재 시험에서 미재현·동시성 검증 미완료”로 남깁니다. 우연히 순차 실행된 결과를 오탐 기각 근거로 쓰지 않습니다.
6. 수정했다면 같은 동시성 시험, 정상 참가·자기 취소, 미인증·타인 취소 부정 테스트와 전체 회귀를 다시 실행합니다.

이 예시는 요구와 오라클을 설명하는 교육 계약입니다. 이 저장소에 실제 모임 서비스·데이터베이스가 구현·배포됐거나 위 테스트가 실행됐다는 주장이 아닙니다. 구체적인 고유성·격리·재시도 방법은 선택한 데이터베이스와 런타임에서 다시 검증해야 합니다.

## 리뷰와 검증의 흔한 실패·복구

### 구현 대화를 그대로 넘겨 확증 편향을 공유함

복구는 fresh context에 정본·diff·증거만 제공하고 구현자의 결론은 검증 대상 주장으로 표시하는 것입니다. 모델 이름을 바꾸는 것만으로 독립성을 주장하지 않습니다.

### 성공 로그가 있지만 대상이 0건임

테스트 선택식·수집 수·건너뜀·예상 실패·종료 코드를 확인합니다. 올바른 실패 재현과 정상 범위 실행을 다시 수행하고 결과 수를 기록합니다.

### 스냅샷 기반 검토의 함정

스냅샷 diff를 요구와 실제 화면에 대조하고, 의도하지 않은 변화면 기준을 되돌린 뒤 원인을 수정합니다. 새 스냅샷은 정답 자동 생성물이 아니라 검토할 변경입니다.

### reviewer PASS를 인간 승인으로 바꿈

PASS가 판정한 base·HEAD·파일·증거·미검증 범위를 고정합니다. 그 뒤 생긴 변경은 다시 검토하며, 도메인·보안·법률·운영 수용은 지정된 사람이 별도로 결정합니다.

### 검증 과정이 상태를 바꿈

실제 write·network·database·배포가 필요한지 먼저 분리합니다. 격리된 fixture와 비파괴 검사를 우선하고, 외부 부작용은 명시적 승인·대상 확인·정리·복구 계약 뒤 실행합니다. 검증이 만든 상태도 결과에 포함합니다.

## 완료와 수용은 같은 말이 아닙니다

에이전트 작업의 가능한 상태를 분리해 기록하세요.

- 변경이 작업 트리에 있음
- staged diff가 검토됨
- 로컬 commit이 생성됨
- 독립 리뷰 finding이 재판정됨
- 수용 기준이 지정 증거로 통과함
- 원격 branch에 push됨
- PR이 승인·merge됨
- 아티팩트가 배포됨
- 공개 URL과 사용자 흐름이 검증됨

앞 단계가 뒤 단계를 자동 의미하지 않습니다. 특히 로컬 commit은 push가 아니고, build 성공은 배포가 아니며, 배포 작업 성공은 공개 사용자 흐름이나 데이터 복구 성공이 아닙니다.

- [ ] 전체 diff에서 예상 밖 삭제·생성물·비밀·개인정보를 확인했나요?
- [ ] 위험에 맞는 test·data·browser·security·human evidence를 선택했나요?
- [ ] 명령·환경·실행 수·종료 코드와 미실행 검증을 기록했나요?

- [ ] 수정 뒤 같은 오라클과 필요한 전체 회귀를 다시 실행했나요?
- [ ] 독립 AI 리뷰의 한계와 최종 인간 수용 주체를 남겼나요?
- [ ] local commit·push·merge·deploy·publication 상태를 분리했나요?

## 짧은 연습

다음 완료 보고를 검토해 보세요. “중복 참가 버그를 고쳤고 테스트도 통과했습니다. 커밋했으니 배포 준비가 끝났습니다.”

1. 이 문장을 주장·변경·증거·상태로 나눕니다.
2. W-03의 정상 참가·자기 취소·중복·미인증·타인 취소에서 필요한 오라클을 적습니다.
3. `test` 명령·실행 수·종료 코드 외에 권위 있는 데이터에서 재조회할 값을 적습니다.
4. 리뷰어의 중복 지적이 오탐일 때 기각에 필요한 증거를 적습니다.
5. 로컬 commit 뒤에도 push·배포·공개 사용에서 남는 검증을 적습니다.
