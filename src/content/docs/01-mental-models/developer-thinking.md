## 왜 필요한가

“참가 기능이 안 됩니다”라는 말만으로는 무엇을 고쳐야 할지 알 수 없습니다. 버튼을 누를 수 없는지, 요청이 전송되지 않았는지, 서버가 규칙에 따라 거절했는지, 참가 상태는 확정됐지만 응답이나 화면 갱신만 실패했는지에 따라 다음 행동이 달라집니다. 관찰한 증상을 곧바로 원인으로 바꾸어 코드를 수정하면 실제 문제를 가리거나 같은 참가 요청을 중복 실행할 수 있습니다.

“주가 차트가 비어 있습니다”라는 말도 마찬가지입니다. 이 사례의 fixture는 같은 결과를 반복 확인하려고 미리 정해 둔 교육용 가상 데이터 묶음입니다. 선택 기간에 이 데이터의 행이 없는 정상 빈 결과인지, 품질 규칙이 값을 차단했는지, 변환 결과와 화면 필터가 어긋났는지, 전달 파일을 읽지 못했는지를 먼저 구분해야 합니다. 차트 선을 억지로 이어 보이게 만들면 데이터 의미 문제를 화면 수정으로 숨길 수 있습니다.

AI는 모호한 요청에도 빠르게 구현안을 만듭니다. 그러나 파일과 코드가 늘어난 사실은 요구가 맞거나 원인을 찾았다는 증거가 아닙니다. 개발자 사고의 핵심은 기술 이름을 빨리 고르는 능력이 아니라, 불확실성을 감추지 않고 다음 결정을 바꿀 증거를 작고 안전하게 만드는 능력입니다.

## 한 문장 정의

**개발자처럼 문제를 나눈다는 것은 관찰된 현상을 사실·가정·제약·가설로 구분하고, 위험을 통제한 작은 작업과 실험으로 다음 결정을 내릴 증거를 만드는 것입니다.**

여기서 “개발자처럼”은 특정 직업의 타고난 직감을 뜻하지 않습니다. 누구나 기록하고 연습할 수 있는 문제 해결 방식이며, 경험이 많더라도 근거 없는 직감을 사실로 취급해서는 안 됩니다.

## 탐정의 사건 수첩으로 이해하기

이 사고법은 탐정이 사건 수첩을 정리하는 모습과 비슷합니다. 탐정은 현장에서 본 흔적과 그 흔적에 대한 해석을 구분하고, 여러 원인 후보를 세운 뒤 어떤 추가 증거가 나오면 후보가 맞거나 틀렸다고 볼 수 있는지 정합니다. 한 단서만 보고 결론 내리지 않고 새 증거가 나오면 앞선 설명을 수정합니다.

비유가 맞는 지점은 소프트웨어 문제도 관찰과 원인 설명을 분리해야 한다는 점입니다. 로그 한 줄, 화면 문구 하나, 테스트 실패 하나는 단서이지 전체 원인을 자동으로 증명하지 않습니다. 여러 가설이 같은 증상을 만들 수 있으므로 서로 다른 결과를 예측하는 검사를 골라 후보를 줄여야 합니다.

비유가 깨지는 지점은 조사 행동이 시스템 상태를 바꿀 수 있다는 사실입니다. 서버 재시작, 데이터 수정, 의존성 재설치, 요청 반복은 증거를 없애거나 사용자 상태를 더 바꿀 수 있습니다. 운영 중인 시스템에서는 원인 규명보다 사용자·데이터 보호와 영향 완화가 먼저일 수도 있고, 개인정보·비밀·권한이 얽힌 증거를 아무 곳에나 복사할 수도 없습니다. 그래서 소프트웨어 실험에는 관찰뿐 아니라 권한, 안전성, 되돌리기와 복구 조건이 필요합니다.

## 관찰 가능한 증상과 원인 해석을 분리한다

**증상(symptom)**: 특정 환경·입력·시점에서 직접 관찰한 결과입니다. **해석(interpretation)**: 그 결과가 왜 생겼는지에 대한 설명입니다. 해석은 다음 행동을 고르는 데 유용하지만 확인되기 전에는 사실이 아닙니다.

“참가 기능이 고장 났다” 대신 다음처럼 쓰면 검증 가능한 증상에 가까워집니다.

> 로컬 미리보기에서 가상 참가자 `user-participant-001`이 모집 중인 `event-example-001`의 참가 버튼을 한 번 눌렀습니다. 화면은 처리 중 상태 뒤 전달 실패 문구를 표시했습니다. 권위 있는 참가 관계를 다시 조회하지 않았으므로 신청이 확정됐는지는 아직 모릅니다.

이 문장에서 “전달 실패 문구가 보였다”는 관찰 사실이고, “데이터베이스가 느려서 실패했다”는 원인 해석입니다. 화면의 실패와 업무 상태의 실패도 같은 뜻이 아닙니다. 서버가 참가 상태를 확정한 뒤 응답 전달만 실패했다면 사용자는 실패를 보더라도 신청은 이미 완료됐을 수 있습니다.

증상을 기록할 때는 환경과 버전, 시작 상태, 입력, 수행한 행동, 기대한 결과, 실제 결과, 발생 시각과 반복 여부를 함께 적습니다. 어제 로컬에서 본 사실이 오늘 공개 배포의 상태를 자동으로 설명하지는 않습니다.

## 사실·가정·제약·가설·미확인·결정의 여섯 칸

모호한 문장을 다음 여섯 칸으로 나누면 AI가 빈칸을 임의의 사실로 채우는 일을 줄일 수 있습니다.

| 구분 | 뜻 | 모임 참가 사례 |
|---|---|---|
| 사실 | 특정 조건에서 직접 확인한 내용 | 버튼을 한 번 눌렀고 화면에 전달 실패 문구가 표시됨 |
| 가정 | 진행을 위해 임시로 받아들였지만 아직 확인하지 않은 내용 | 요청이 데이터 저장 전에 실패했을 것이라고 추정함 |
| 제약 | 반드시 지키거나 이번 작업에서 허용되지 않는 조건 | 실제 사용자 데이터 수정·외부 쓰기·승인 없는 설치 금지 |
| 가설 | 증상을 설명하며 다른 결과를 예측할 수 있는 원인 후보 | 참가 상태는 확정됐지만 응답 전달만 실패했을 수 있음 |
| 미확인 | 중요하지만 아직 증거가 없는 질문 | 권위 있는 참가 관계의 현재 상태를 재조회하지 않음 |
| 결정 | 현재 근거와 제약 안에서 선택한 다음 행동 | 요청을 반복하기 전에 참가 상태를 읽기 전용으로 재조회함 |

제약과 선호도 구분합니다. “개인정보를 복사하지 않는다”, “운영 데이터에 쓰지 않는다”, “외부 전송은 승인 전에 수행하지 않는다”는 안전 경계입니다. “이 프레임워크를 쓰고 싶다”, “한 페이지로 만들고 싶다”는 바뀔 수 있는 선호나 설계 후보일 수 있습니다. 선호를 제약처럼 다루면 더 단순하고 안전한 대안을 검토하지 못합니다.

## 하나의 실용 루프, 하나뿐인 절차는 아니다

다음 흐름은 디버깅과 불확실한 설계 판단에 사용할 수 있는 실용적인 출발점입니다.

`관찰 → 사실과 해석 분리 → 제약 확인 → 가설과 예상 증거 작성 → 가장 작은 안전한 실험 → 실제 결과 비교 → 다음 질문 또는 결정`

이 흐름은 모든 장애·조직·도메인에 맞는 보편적인 단일 절차가 아닙니다. 새 기능 설계, 운영 장애, 보안 사고, 데이터 손상은 위험과 시간 제약이 다르므로 안정화나 전문가 대응이 먼저일 수 있고, 숙련자는 다른 효과적인 순서를 사용할 수 있습니다. 중요한 원리는 순서를 외우는 것이 아니라 확인하지 않은 내용을 사실처럼 구현하지 않고, 각 행동이 어떤 질문에 답하는지 남기는 것입니다.

Google SRE의 문제 해결 장은 운영 신뢰성 문맥에서 관찰과 시스템 지식을 바탕으로 가설을 세우고, 확인하거나 반박할 증거를 찾으며, 통제된 변경 결과를 반복 관찰하는 접근을 설명합니다. 같은 자료도 숙련자가 다른 효과적인 방법을 사용할 수 있음을 밝힙니다. 이 장의 루프는 그 원칙을 초보자의 작업 질문으로 재구성한 편집 구조이지 공식 표준 절차가 아닙니다.

## 좋은 가설은 반대 증거를 포함한다

“서버 문제 같다”는 말은 범위가 너무 넓습니다. 가설은 다음 형식으로 씁니다.

> 같은 입력에서 원인이 `X`라면 경계 `Y`를 확인했을 때 결과 `Z`가 관찰될 것이다. `Z`가 관찰되지 않으면 이 가설의 가능성을 낮춘다.

모임 참가 요청 뒤 실패 문구가 보인 상황을 예로 들면 다음처럼 후보를 나눌 수 있습니다. 현재 참가 관계와 모임 상태를 읽는 목적은 안전한 다음 행동을 고르는 것이고, 이번 요청의 처리 결과를 밝히는 목적과는 다릅니다. 표의 처리 기록은 요청을 구분하는 식별 정보와 시각 등으로 바로 그 요청에 연결할 수 있는 기존 기록을 뜻합니다. 같은 사용자의 현재 상태나 비슷한 시각의 기록만으로 같은 요청이라고 단정하지 않습니다.

| 가설 | 가장 작은 확인 | 맞을 때 예상할 증거 | 반대 증거 |
|---|---|---|---|
| 요청이 애플리케이션 경계에 도달하지 않음 | 같은 요청의 기존 전달·수신 기록을 대조 | 해당 처리 기록이 없고 브라우저 전달 실패가 확인됨. 기록 누락 가능성은 남음 | 서버가 바로 그 요청을 받아 처리한 기록이 있음 |
| 모집 상태·정원·중복·권한 규칙이 거절함 | 같은 요청의 응답과 처리 기록을 대조 | 해당 요청을 거절한 업무 오류·처리 결과가 있음. 기존 참가 관계는 남을 수 있음 | 바로 그 요청의 성공 확정을 보여 주는 처리 기록이 있음 |
| 이번 요청은 확정됐지만 응답 또는 화면 갱신만 실패함 | 재전송 없이 같은 요청의 확정·전달 기록과 현재 참가 관계·모임 상태를 각각 확인 | 해당 요청의 성공 확정 기록과 그 뒤 응답 전달 또는 화면 갱신의 실패 증거가 있음 | 같은 요청이 확정되지 않고 거절됐음을 보여 주는 처리 기록이 있음 |

이미 참가한 사용자의 중복 요청이 거절된 경우와 이번 요청이 확정된 뒤 응답만 유실된 경우 모두 현재 참가 관계는 `confirmed`로 보일 수 있습니다. 반대로 이후 별도 취소가 있었다면 현재 관계가 없거나 취소 상태라고 해서 앞선 확정을 부정할 수 없습니다. 자기 상태를 조회할 때에는 모임 상태도 함께 읽고, 취소된 모임에 보존된 참가 이력을 현재 유효한 참가로 해석하지 않습니다.

요청 기록이 없다는 사실이 “요청이 오지 않았다”를 완전히 증명하지는 않습니다. 기록 수집 자체가 누락됐을 수 있기 때문입니다. 요청별 연결 증거가 없거나 조회가 실패했거나 관찰 사이에 다른 상태 변경이 있었다면 원인은 아직 판별 불가로 남깁니다. 현재 상태 조회는 POST 재전송 허가가 아닙니다. 따라서 “가설과 일치한다”와 “원인이 확정됐다”를 구분하고, 중요한 결정에는 서로 다른 경계의 증거를 더합니다.

## 가장 작은 안전한 실험을 고른다

작은 작업은 코드 줄이나 파일 수가 적다는 뜻이 아닙니다. 하나의 질문이나 사용자 결과를 독립적으로 판정할 수 있고, 실패했을 때 영향과 되돌릴 범위를 이해할 수 있는 단위입니다.

| 작업 종류 | 답할 질문 | 예시 |
|---|---|---|
| 조사 단위 | 어느 경계까지 정상이고 무엇이 아직 미확인인가? | 실패 응답 뒤 참가 관계를 읽기 전용으로 재조회함 |
| 구현 단위 | 어떤 최소 변경이 한 사용자 결과를 완성하는가? | 모집 중이고 자리가 있을 때 참가 관계를 한 번만 확정하고 결과를 다시 표시함 |
| 복구 단위 | 어떤 위험 하나를 통제하고 정상 상태를 다시 확인할 것인가? | 중복 재시도를 멈추고 권위 상태와 사용자 안내를 복구함 |

작은 실험은 다섯 조건을 갖춰야 합니다.

1. **판별 가능성**: 결과에 따라 원인 후보나 선택지를 실제로 줄일 수 있습니다.
2. **최소 범위**: 필요한 입력·구성요소·시간 범위만 다룹니다.
3. **안전성**: 실제 사용자·개인정보·운영 데이터·외부 상태를 해치지 않습니다.
4. **되돌리기 가능성**: 변경 실험이라면 원래 상태와 복구 방법을 먼저 압니다.
5. **기록 가능성**: 조건, 기대 결과, 실제 결과와 다음 결정을 남길 수 있습니다.

가능하면 기존 파일·로그·응답·테스트·데이터를 읽는 확인부터 시작합니다. 하지만 읽기 전용도 민감정보를 출력하거나 대량 조회로 부하를 만들 수 있으므로 범위와 출력 금지 항목을 제한해야 합니다. 한 번에 한 변수만 바꾸는 것이 해석에는 유리하지만, 시간·외부 서비스·동시성처럼 통제하기 어려운 요소가 있으면 고정할 수 없는 조건을 기록하고 fixture·반복·비교 증거로 불확실성을 줄입니다.

## 작업 단위의 계약을 먼저 적는다

| 항목 | 확인할 질문 |
|---|---|
| 목표 | 이번 단위가 해결할 사용자 결과나 불확실성은 무엇인가? |
| 비목표 | 이번에 바꾸거나 증명하지 않을 것은 무엇인가? |
| 시작 상태 | 어떤 환경·버전·입력·선행 상태에서 시작하는가? |
| 허용 범위 | 어떤 파일·구성요소·데이터를 읽거나 수정할 수 있는가? |
| 위험 | 사용자·데이터·보안·운영·기존 작업에 어떤 피해가 가능한가? |
| 수용 기준 | 어떤 관찰 가능한 출력·오류·상태가 나오면 통과인가? |
| 검증 | 어떤 테스트·로그·데이터 재조회·화면·diff가 필요한가? |
| 중단·복구 | 언제 멈추며 실패하면 어떤 상태로 돌아가는가? |

각 작업이 이 계약을 가지면 앞선 조사 결과가 필요한 작업, 같은 파일이나 상태를 바꾸어 동시에 실행하면 충돌하는 작업, 독립 검증할 수 있는 작업을 구분할 수 있습니다. “대시보드 전체 구현”처럼 큰 명사로 자르기보다 “고정 fixture의 기간 선택 결과가 표·차트·요약에서 같은 행 집합을 사용하고 빈 결과 상태를 표시한다”처럼 한 결과와 증거로 자릅니다.

## 구현부터 시작하면 무엇을 잃는가

모호한 요청 직후 코드를 바꾸면 다음 문제가 생깁니다.

- 수정 전 기대와 실제를 기록하지 않아 무엇이 개선됐는지 비교할 수 없습니다.
- 재시작·재설치·데이터 수정이 원래 실패 상태와 로그를 없앨 수 있습니다.
- 화면·서버·데이터·설정을 함께 바꾸면 어느 변경이 결과를 바꿨는지 알기 어렵습니다.
- 사용자의 결과보다 AI가 추측한 기능을 완성할 수 있습니다.
- 큰 diff에 진단용 임시 코드, 우회와 실제 수정이 섞여 되돌릴 경계를 잃습니다.
- 파일이 늘어난 활동을 사용자 문제 해결이라는 진척으로 과대평가합니다.

구현 자체가 작은 실험이 될 수는 있습니다. 버릴 수 있는 프로토타입을 격리된 환경에서 만들고 답할 질문·허용 범위·중단 조건을 미리 정했다면 설계 불확실성을 줄일 수 있습니다. 그래도 프로토타입 성공을 운영 가능한 제품이나 최종 설계의 증거로 확대하지 않습니다.

## 변경 전에 증거와 복구 지점을 보존한다

진단과 수정 권한은 현재 작업을 지우거나 덮어써도 된다는 뜻이 아닙니다. 변경 전에 다음을 확인합니다.

- 현재 작업 트리의 변경·새 파일·무시된 파일과 다른 사람이 진행 중인 작업
- 실패를 재현하는 최소 입력과 기대·실제 결과
- 현재 코드·설정·데이터·배포 버전
- 개인정보와 비밀을 제외한 필요한 로그·오류·화면 증거
- 변경이 영향을 줄 파일·프로세스·데이터와 외부 상태
- 실패했을 때 돌아갈 코드·데이터·서비스 상태
- 복구 뒤 다시 확인할 사용자 흐름과 데이터 불변식

버전 관리 이력이 있어도 커밋하지 않은 파일, ignored 산출물, 외부 데이터베이스와 실행 중인 프로세스가 자동으로 보호되는 것은 아닙니다. 반대로 증거를 보존한다는 이유로 개인정보·토큰·전체 운영 데이터를 복사해서도 안 됩니다. 필요한 필드와 시간 범위만 남기고 민감정보를 제거하며 보존 위치와 삭제 조건을 정합니다.

사용자 피해, 데이터 손상, 비밀 노출처럼 영향이 계속 커진다면 원인을 완전히 밝히기보다 승인된 범위에서 먼저 안정화합니다. 안정화 전에 사라질 증거를 안전하게 보존하고, 영향 완화와 원인 해결을 서로 다른 완료 상태로 기록합니다. 이전 버전으로 되돌려 사용자 흐름이 회복됐어도 원인과 재발 방지 검증은 남을 수 있습니다.

## 실험 결과를 피드백으로 바꾼다

실험은 통과 또는 실패 한 단어로 끝내지 않습니다. 어떤 가설을 확인했는지, 어떤 조건과 입력을 사용했는지, 예상과 실제가 어떻게 달랐는지, 이 결과로 어떤 후보를 낮추고 다음에 무엇을 확인할지를 기록합니다.

결과는 보통 세 가지 중 하나입니다.

- **가설과 일치함**: 다른 설명이 남는지 확인하고 필요하면 독립 증거를 더합니다.
- **가설과 일치하지 않음**: 가설을 폐기하거나 범위를 줄여 다음 후보로 이동합니다.
- **판별할 수 없음**: 관측 신호가 부족하거나 변수가 섞였는지 확인하고 실험을 다시 설계합니다.

같은 명령이나 요청을 이유 없이 반복하는 것은 피드백 루프가 아닙니다. 새로운 증거가 생기지 않으면 관찰 방법, 입력, 가설 또는 권한을 다시 검토해야 합니다.

## 중단 조건을 먼저 정한다

중단은 실패가 아니라 안전하고 검토 가능한 작업의 일부입니다. 다음 상황에서는 구현이나 실험을 계속하지 않고 상태를 보고합니다.

- 실제 사용자·개인정보·비밀·운영 데이터에 예상하지 못한 영향이 생길 수 있습니다.
- 허용되지 않은 파일 수정, 설치, 네트워크 접근, 외부 쓰기나 배포가 필요합니다.
- 다른 사람의 작업이나 실행 중인 세션을 안전하게 분리할 수 없습니다.
- 현재 상태를 보존하거나 되돌릴 방법을 확인하지 못했습니다.
- 같은 실험을 반복해도 새 정보가 생기지 않습니다.
- 가설을 구분할 관측 신호가 부족해 결과를 판정할 수 없습니다.
- 요구와 수용 기준이 충돌하거나 사용자 선택에 따라 결과가 크게 달라집니다.
- 영향 완화 뒤 추가 진단의 위험이 현재 이익보다 큽니다.

중단 보고에는 “막혔습니다”만 쓰지 않습니다. 확인한 사실, 시도한 안전한 방법, 남은 불확실성, 필요한 권한이나 결정, 재개 조건을 함께 적습니다.

## 증거로 완료를 판정한다

“코드를 작성했습니다”, “오류가 안 보입니다”, “AI가 수정됐다고 했습니다”는 활동이나 설명이지 완료 증거가 아닙니다. 수용 기준마다 직접 연결되는 증거가 필요합니다.

| 완료 주장 | 필요한 증거 | 그 증거만으로 말할 수 없는 것 |
|---|---|---|
| 원래 실패가 수정됨 | 수정 전 같은 조건의 실패와 수정 후 통과, 관련 회귀 확인 | 다른 환경·입력·운영 배포까지 모두 정상 |
| 모임 참가가 확정됨 | 권위 있는 참가 관계 재조회와 중복·정원·권한 조건 확인 | 응답 전달·화면·복구까지 모두 정상 |
| 화면이 정상임 | 목표 화면 폭과 사용자 행동에서 상태·텍스트·오류 확인 | 서버 내부 상태·데이터 의미·공개 배포 정상 |
| 자동 검사가 통과함 | 실제 명령, 실행 위치, 종료 코드, 실행·통과·실패·건너뜀 수 | 사용자 목적·운영 환경·미실행 범위 정상 |
| 작업 단위가 완료됨 | 수용 기준별 증거, 검토한 diff, 비목표 준수, 남은 위험 | 원격 공유·배포·사람 승인까지 완료 |

완료 전에는 원래 질문에 답했는지, 정상뿐 아니라 중요한 실패 조건을 확인했는지, 비목표를 지켰는지, 테스트 수·종료 코드·경고·건너뜀을 보았는지, 임시 코드와 무관한 diff가 없는지, 사용자·데이터·실행 환경이 안전한 상태인지 점검합니다. 남은 가정과 미확인 위험도 완료라는 말로 숨기지 않습니다.

“영향 완화 완료”, “로컬 검증 완료”, “독립 검토 대기”, “공개 배포 확인 완료”처럼 범위를 구체적으로 표현합니다. 한 단계의 성공을 더 큰 상태로 확대하지 않습니다.

## 두 사례에서 다음 행동이 달라지는 이유

같은 문제 분해 방법을 사용해도 시스템이 바꾸는 상태와 지켜야 할 의미에 따라 가장 안전한 실험과 완료 증거가 달라집니다.

| 비교 지점 | 모임 참가 웹앱 | 교육용 주가 fixture 대시보드 |
|---|---|---|
| 시스템 성격 | 권한이 필요한 요청으로 참가 관계와 정원을 바꿈 | 고정 fixture를 읽고 변환해 표·차트·요약으로 전달함 |
| 예시 증상 | 참가 요청 뒤 화면에 실패가 표시됨 | 선택한 기간의 차트가 비어 있음 |
| 먼저 피할 행동 | 현재 상태를 모른 채 참가 요청을 반복함 | 빈 구간을 임의의 값이나 선으로 채움 |
| 먼저 확인할 사실 | 권위 있는 참가 관계·모집 상태·정원과 처리 결과 | 선택 조건, fixture 행, 값 상태, 변환·데이터셋 버전과 표·차트 결과 |
| 작은 안전 확인 | 쓰기를 반복하지 않고 현재 참가 상태를 재조회함 | 고정 fixture에서 같은 선택 결과가 표·차트·요약에 전달되는지 비교함 |
| 완료 증거 | 참가 관계·중복 방지·정원·권한, 응답과 화면, 실패 뒤 재조회 | 데이터 계약·값/신선도 상태·버전·표/차트 일치·빈 결과와 차단 상태 표현 |

모임 앱에서는 사용자가 실패 문구를 보더라도 상태 변경이 이미 확정됐을 수 있으므로 재시도 전에 현재 상태를 확인해야 합니다. 교육용 fixture에서는 화면이 비었다는 이유만으로 오류라고 단정하지 않고 정상 빈 결과, 차단된 값, 필터 불일치와 전달 실패를 구분합니다. 주가 사례는 실제 상품·시세·거래일·조정 방식이나 투자 판단을 설명하지 않으며 저장소의 `EDU-FIXTURE` 계약 안에서만 사용합니다.

## AI와 작업할 때

AI에게 “원인을 찾아서 고쳐 주세요”라고 바로 요청하면 조사와 구현, 권한과 완료 기준이 섞입니다. 먼저 읽기 전용 진단으로 사실과 가설을 분리하고, 사람이 근거를 확인한 뒤 수정 계약을 새로 만듭니다.

```text
목표:
- 모임 참가 요청 뒤 실패 문구가 표시되는 현상을 읽기 전용으로 진단하고 다음에 할 가장 작은 안전한 검증을 제안하라.

현재 관찰:
- 로컬 미리보기에서 가상 참가자 user-participant-001이 event-example-001의 참가 버튼을 한 번 눌렀다.
- 화면은 처리 중 상태 뒤 전달 실패 문구를 표시했다.
- 권위 있는 참가 관계는 아직 재조회하지 않았다.

범위와 권한:
- 관련 화면·요청 처리·데이터 계약·테스트·안전한 로그 설정만 읽어라.
- 파일·데이터·프로세스·Git 상태를 수정하지 마라.
- 참가 요청을 다시 보내거나 서버를 재시작하지 마라.
- 패키지 설치, 네트워크 접근, 외부 쓰기와 배포를 하지 마라.
- 토큰·쿠키·개인정보·비공개 데이터를 출력하지 마라.

검토 방법:
- 관찰 사실, 해석, 가정, 제약과 미확인을 구분하라.
- 가능한 가설을 우선순위와 함께 최대 3개 제시하라.
- 각 가설의 예상 증거, 반대 증거, 가장 작은 읽기 전용 확인을 적어라.
- 파일 근거나 실행 증거가 없는 원인을 확정하지 마라.
- 추가 권한이나 상태 변경이 필요하면 실행하지 말고 중단 이유와 재개 조건을 보고하라.

산출물:
- 확인한 파일 경로와 관련 근거
- 가설·예상 증거·반대 증거·다음 확인 표
- 현재 말할 수 있는 범위와 말할 수 없는 범위
- 수정 전에 보존할 상태와 수용 기준 초안
```

AI가 구체적인 원인을 자신 있게 설명해도 실제 파일·명령·상태에 연결되지 않으면 가설입니다. 수정 계약에는 변경 가능한 파일, 재현 조건이나 실패 테스트, 수용 기준, 검증 명령, 중단 조건과 복구 방법을 포함합니다.

## 확인 체크리스트

- [ ] 문제를 사용자 결과 또는 관찰 가능한 증상으로 설명했나요?
- [ ] 환경·버전·입력·선행 상태·기대·실제를 기록했나요?
- [ ] 관찰 사실과 원인 해석을 분리했나요?
- [ ] 사실·가정·제약·가설·미확인·결정을 구분했나요?
- [ ] 사용자·데이터·보안·운영 영향과 먼저 완화할 위험을 확인했나요?
- [ ] 한 작업이 답할 질문이나 제공할 사용자 결과가 하나로 좁혀졌나요?
- [ ] 목표·비목표·허용 범위·금지 범위를 적었나요?
- [ ] 각 가설이 맞거나 틀릴 때 예상 증거가 다른가요?
- [ ] 기존 증거를 읽는 가장 작은 확인부터 검토했나요?
- [ ] 변경 전에 현재 작업·실패 입력·버전·로그·데이터 상태를 필요한 범위에서 보존했나요?
- [ ] 실험의 사용자 영향·권한·되돌리기와 복구 방법을 확인했나요?
- [ ] 결과를 일치·불일치·판별 불가로 기록하고 다음 결정을 연결했나요?
- [ ] 반복 한도와 중단·승인·재개 조건이 있나요?
- [ ] 수용 기준마다 테스트·데이터·화면·로그·diff 증거가 있나요?
- [ ] 자동 검사, 로컬 동작, 검토, 배포와 공개 사용자 성공을 구분했나요?
- [ ] 완화된 영향과 해결된 원인, 남은 가정과 미확인을 따로 보고했나요?

## 짧은 연습

다음 중 하나를 고릅니다.

- 모임 참가 버튼을 한 번 눌렀는데 실패 문구가 보였습니다.
- 교육용 주가 fixture에서 선택한 기간의 차트가 비어 있습니다.

아직 확인하지 않은 내용은 추측으로 채우지 말고 `미확인`이라고 적습니다.

| 항목 | 내 기록 |
|---|---|
| 환경·버전·입력·선행 상태 |  |
| 기대한 결과 |  |
| 직접 관찰한 실제 결과 |  |
| 사실 |  |
| 가정 |  |
| 제약과 금지선 |  |
| 가설 1과 예상·반대 증거 |  |
| 가설 2와 예상·반대 증거 |  |
| 가장 작은 안전한 확인 |  |
| 보존할 상태와 복구 지점 |  |

| 완료라고 말할 직접 증거 |  |

두 가설이 서로 다른 결과를 예측하는지 확인하세요. 같은 증거가 나와도 구분할 수 없다면 더 작은 경계나 다른 관측 신호를 고릅니다. 마지막으로 AI에게 보낼 읽기 전용 진단 지시를 쓰되, 확인하지 않은 원인을 확정하지 말라는 조건과 상태 변경 전 중단 조건을 포함합니다.
