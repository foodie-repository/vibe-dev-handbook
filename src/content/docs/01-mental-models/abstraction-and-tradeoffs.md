## 왜 필요한가

AI에게 기능을 요청하면 짧은 시간에 파일, 함수, API, 데이터 모델이 늘어납니다. 이때 모든 내부 세부를 한꺼번에 이해하려 하면 중요한 판단을 놓치고, 반대로 기술 이름만 믿으면 오류가 발생했을 때 어디를 확인해야 하는지 알기 어렵습니다. 추상화는 복잡성을 없애는 마법이 아니라, 지금 내릴 결정에 필요한 세부와 나중에 확인해도 되는 세부를 나누는 방법입니다.

예를 들어 모임 참가 화면에서 사용자는 `참가하기`라는 한 행동만 봅니다. 그러나 시스템 안에서는 현재 사용자 확인, 모집 상태와 정원 확인, 중복 참가 방지, 참가 기록 저장, 새 상태 응답이 이어질 수 있습니다. 화면 버튼은 이 세부를 모두 노출하지 않아도 되지만, “누가 어떤 조건에서 참가 상태를 바꿀 책임이 있는가”까지 숨겨서는 안 됩니다.

## 한 문장 정의

**추상화(abstraction)는 특정 목적에 필요한 속성과 동작을 드러내고 그 판단에 불필요한 세부를 경계 뒤로 숨기는 설계이며, 트레이드오프(trade-off)는 한 이점을 얻는 대신 생기는 비용과 제약을 함께 받아들이는 선택입니다.**

여기서 “숨긴다”는 “없앤다”는 뜻이 아닙니다. 숨은 세부도 누군가 구현하고 운영해야 하며, 성능·권한·데이터 일관성·장애 같은 조건이 경계를 넘어 보이면 다시 확인해야 합니다.

## 초보자를 위한 한 가지 비유

추상화는 식당의 메뉴와 비슷합니다. 손님은 주방의 모든 조리 순서를 몰라도 메뉴 이름, 가격, 알레르기 정보, 주문 가능 여부를 보고 선택할 수 있습니다. 주방은 정해진 주문을 받아 결과나 실패를 돌려줄 책임을 맡습니다. 메뉴가 적절한 인터페이스라면 손님과 주방은 서로의 모든 세부를 알지 않고도 협력할 수 있습니다.

이 비유가 맞는 지점은 역할과 경계를 분리한다는 점입니다. 그러나 비유는 식당 규칙이 소프트웨어의 정확한 동작을 설명하기 시작하는 순간 깨집니다. 소프트웨어 인터페이스에는 기계가 판정할 입력 형식, 권한, 상태 전이, 오류, 시간 제한과 버전 호환성까지 필요할 수 있고, 내부 구현의 지연이나 데이터 일관성 문제가 사용자에게 직접 드러날 수도 있습니다. “메뉴가 있으니 내부를 몰라도 된다”는 결론은 추상화의 한계를 지웁니다.

## 추상화는 어디에 놓이는가

추상화는 한 계층에만 존재하지 않습니다. 같은 시스템에서도 서로 다른 결정을 위해 여러 수준을 사용합니다.

| 수준 | 드러내는 것 | 주로 숨기는 것 | 경계가 새는 대표 신호 |
|---|---|---|---|
| 사용자 흐름 | 사용자가 할 수 있는 행동과 결과 | 내부 함수와 저장 방식 | 화면은 성공이라는데 새로고침하면 상태가 사라짐 |
| 업무 규칙 | 누가 어떤 조건에서 상태를 바꿀 수 있는지 | 화면 배치와 저장 쿼리 | 동시 요청에서 정원이나 중복 규칙이 깨짐 |
| 인터페이스 | 입력·출력·오류의 약속 | 내부 알고리즘과 데이터 배치 | 예상하지 못한 오류·지연·버전 불일치가 호출자에게 드러남 |
| 데이터 접근 | 읽고 쓰는 동작과 결과 | 파일·테이블·쿼리의 구체 형식 | 트랜잭션·인덱스·권한 특성이 결과나 속도에 영향을 줌 |
| 런타임·플랫폼 | 실행·배포에 사용할 기능과 제약 | 프로세스·네트워크·운영 세부 일부 | 지원 버전·제한·장애가 애플리케이션 동작을 바꿈 |

계층은 높을수록 좋거나 낮을수록 나쁜 것이 아닙니다. 사용자 요구를 논의할 때는 사용자 흐름 수준이 적절하고, 포트 충돌을 진단할 때는 프로세스와 운영체제 수준까지 내려가야 합니다. 좋은 설명은 현재 질문에 맞는 수준을 고르고, 더 아래로 내려가야 하는 신호도 함께 남깁니다.

## 책임과 경계를 먼저 적는다

기술 이름보다 먼저 추상화의 계약을 적으면 AI 결과를 검토하기 쉬워집니다.

| 질문 | 기록할 내용 |
|---|---|
| 목적 | 이 경계가 어떤 복잡성을 줄이는가? |
| 사용자 | 누가 이 경계를 호출하거나 의존하는가? |
| 책임 | 이 구성요소가 반드시 보장해야 하는 일은 무엇인가? |
| 입력·출력 | 어떤 값을 받고 무엇을 돌려주는가? |
| 실패 | 거절·시간 초과·부분 성공·오래된 값은 어떻게 보이는가? |
| 숨긴 세부 | 호출자가 몰라도 되는 구현 세부는 무엇인가? |
| 누수 신호 | 어떤 조건에서는 숨긴 세부를 다시 확인해야 하는가? |
| 교체 조건 | 어떤 증거가 쌓이면 경계를 나누거나 바꿀 것인가? |

모임 참가 기능이라면 “참가 상태 변경”이라는 책임은 정원·중복·모집 상태를 함께 판정해야 합니다. 이를 화면 버튼, API, 데이터베이스 중 어느 한 이름으로만 설명하면 책임이 빠집니다. 화면은 요청을 시작하고 결과를 보여 주지만, 사용자가 바꿀 수 있는 입력을 최종 규칙으로 신뢰해서는 안 됩니다. API는 규칙을 집행하고 데이터 변경을 조율하며, 데이터 저장소는 상태와 무결성 조건을 보존합니다. 구체적인 기술은 달라져도 이 책임 질문은 남습니다.

## 추상화에는 비용이 있다

추상화가 줄이는 복잡성과 새로 만드는 비용을 같은 표에서 비교해야 합니다.

| 얻는 것 | 함께 생길 수 있는 비용 |
|---|---|
| 호출 방식의 단순화 | 내부 동작을 추적하기 어려워짐 |
| 구현 교체 가능성 | 공통 인터페이스를 유지하는 변환 코드가 늘어남 |
| 중복 감소 | 서로 다른 요구를 한 규칙에 억지로 맞출 위험 |
| 일관된 오류 처리 | 원래 원인의 세부 정보가 사라질 위험 |
| 빠른 시작 | 프레임워크·플랫폼의 규칙과 버전에 묶이는 비용 |
| 성능 최적화의 은닉 | 캐시·배치·동시성 특성이 예상 밖으로 드러날 위험 |

트레이드오프는 “장점과 단점이 있습니다”로 끝내는 감상이 아닙니다. 현재 제약에서 무엇을 우선했고, 어떤 비용을 받아들였으며, 그 비용이 커졌음을 어떤 신호로 확인할지 남기는 결정 기록입니다. 같은 선택도 맥락에 따라 판정이 달라집니다.

예를 들어 같은 결과를 반복 확인하려고 미리 정해 둔 교육용 가상 데이터 묶음(fixture)을 읽어 변환한 정적 페이지는 값이 정해진 학습 자료를 반복 재현하는 데 단순하고 유리할 수 있습니다. 이 주가 사례에서 fixture는 고정된 데이터 묶음을 가리킵니다. 반면 모임 참가처럼 여러 사용자가 상태를 바꾸고 정원·권한을 즉시 판정해야 하는 기능을 같은 정적 파일 추상화에 억지로 넣으면 책임을 감출 뿐 해결하지 못합니다. 전자는 입력 버전과 변환 결과의 재현성이 핵심이고, 후자는 권위 있는 현재 상태와 동시 변경 규칙이 핵심입니다. 이 비교는 실제 시장 데이터의 정확성이나 이용 권리를 주장하지 않으며, 저장소의 `EDU-FIXTURE` 교육 범위에만 해당합니다.

## 추상화 누수는 실패가 아니라 진단 신호다

**추상화 누수(abstraction leak)**: 경계 뒤에 숨긴 내부 특성이 사용자의 판단이나 외부 동작에 영향을 주는 상황입니다. 모든 누수를 없애려 하기보다 다음과 같이 다룹니다.

1. 먼저 외부에서 관찰된 증상을 기록합니다. 예: “참가 요청이 8초 뒤 시간 초과됐지만 새로고침하면 참가 상태다.”
2. 어느 경계의 약속이 불충분한지 찾습니다. 시간 초과가 저장 실패를 뜻하는지, 결과 전달만 실패한 것인지 계약이 없을 수 있습니다.
3. 필요한 만큼만 한 단계 아래를 관찰합니다. 요청 식별자, 서버 로그, 데이터 상태처럼 판정을 바꿀 증거를 확인합니다.
4. 호출자에게 필요한 오류·상태를 경계에 추가할지, 내부 구현을 고칠지 결정합니다.
5. 정상·거절·시간 초과·재시도 경로를 다시 검증하고, 새 세부를 모든 호출자에게 무조건 노출하지 않습니다.

누수가 보였다는 이유로 모든 내부 코드를 공개하면 추상화의 목적이 사라집니다. 반대로 “원래 숨겨진 부분”이라며 조사하지 않으면 사용자는 성공과 실패를 구분할 수 없습니다. 필요한 관찰 가능성과 내부 캡슐화를 함께 유지하는 것이 핵심입니다.

## 추상화가 너무 적을 때와 너무 많을 때

추상화 부족과 과잉 추상화는 반대처럼 보이지만 둘 다 책임을 흐립니다.

### 과소 추상화, 즉 추상화가 너무 적은 신호

- 같은 규칙이나 오류 처리가 여러 파일에 복제돼 한 곳만 수정됩니다.
- 화면·업무 규칙·저장 코드가 섞여 작은 변경도 전체를 건드립니다.
- 호출자가 내부 파일명, 쿼리, 네트워크 재시도 방법까지 알아야 합니다.
- 동일한 개념이 위치마다 다른 이름과 형식으로 오갑니다.

이때는 반복 횟수만 보고 공통 함수를 만들기보다, 정말 같은 책임과 변경 이유를 가진 부분인지 먼저 확인합니다. 함께 바뀌어야 하는 규칙이라면 경계를 묶고, 표면만 비슷하지만 이유가 다르면 분리한 채 둡니다.

### 추상화가 너무 많은 신호

- 현재 하나뿐인 구현을 위해 범용 플러그인·팩토리·어댑터 계층이 여러 겹 생깁니다.
- 간단한 오류를 찾으려면 이름만 다른 파일을 계속 따라가야 합니다.
- 실제 요구보다 “언젠가 바뀔 수 있음”이 주된 도입 이유입니다.
- 공통 인터페이스 때문에 각 사례에 필요한 중요한 조건이 빠집니다.
- 새 계층을 통과시키는 코드와 테스트 비용이 줄어든 복잡성보다 큽니다.

과잉 추상화는 미래 변경을 예측했지만 변경 축을 틀리게 고른 경우가 많습니다. 아직 공통 책임이 확인되지 않았다면 작은 중복을 잠시 허용하고, 두 번째 실제 사례가 나타난 뒤 공통점과 차이를 다시 보는 편이 더 가역적일 수 있습니다.

## 가역성으로 선택을 비교한다

완벽한 미래 예측 대신 잘못 골랐을 때 되돌리는 비용을 비교합니다.

| 선택 질문 | 더 가역적인 시작의 예 |
|---|---|
| 경계를 지금 나눌 것인가? | 한 책임 안에서 명확한 함수·모듈 경계를 먼저 두고 실제 독립 배포 필요가 생길 때 분리 |
| 범용 인터페이스를 만들 것인가? | 현재 입력·출력·오류만 명시하고 확인되지 않은 확장 지점은 만들지 않음 |
| 도구 기능에 맡길 것인가? | 교체 시 가져갈 데이터 형식·검증 명령·내보내기 경로를 함께 보존 |
| 성능을 위해 캐시할 것인가? | 권위 원본과 만료·무효화 조건을 먼저 정하고 측정된 병목에만 도입 |

가역적이라는 말은 변경 비용이 0이라는 뜻이 아닙니다. 데이터를 외부에 저장하거나 공개 인터페이스를 배포한 뒤에는 호환성과 이전 책임이 생길 수 있습니다. 그래서 “지금 되돌릴 수 있다”는 판단도 파일 diff, 데이터 변환 시험, 호환 테스트와 운영 절차 같은 증거로 확인해야 합니다.

## 흔한 실패와 복구

### 기술 이름을 책임 대신 쓰기

“프레임워크가 처리합니다”라고만 적으면 입력 검증, 권한, 데이터 변경, 실패 복구의 담당자가 사라집니다. 복구할 때는 해당 기능의 입력·출력·오류·상태 원본을 다시 적고, 기술이 실제로 제공하는 범위와 애플리케이션이 구현할 범위를 나눕니다.

### 추상화 누수를 예외로 숨기기

내부 오류를 모두 `처리 실패` 하나로 바꾸면 사용자는 재시도해도 되는지 알 수 없고 운영자는 원인을 좁힐 수 없습니다. 사용자에게는 안전하고 행동 가능한 오류를, 내부에는 민감정보를 제외한 원인·요청 식별자·시점을 남기며 두 증거를 연결합니다.

### 미래를 위한 계층을 먼저 만들기

AI가 “확장 가능하게”라는 말에 플러그인 구조와 여러 인터페이스를 만들 수 있습니다. 실제 두 번째 구현, 독립 배포, 다른 변경 주기 같은 증거가 없다면 추가 계층을 제거하거나 한 모듈로 합치고, 다시 분리할 조건만 기록합니다.

### 추상화를 제거해 버리기

복잡한 계층을 줄이면서 업무 규칙까지 화면이나 쿼리에 흩어 놓으면 단순화가 아닙니다. 제거 전 책임·호출자·검증을 목록화하고, 변경 뒤에도 같은 정상·거절·경계 조건 테스트가 통과하는지 확인합니다. 데이터나 공개 인터페이스가 관련되면 먼저 백업·호환 경로·되돌리기 지점을 준비합니다.

## AI 결과를 검토하는 프롬프트

다음 프롬프트는 새 추상화를 자동 승인하기 위한 것이 아니라, 근거와 빠진 책임을 찾기 위한 읽기 전용 검토 요청입니다.

```text
이 변경에서 새로 만들거나 바꾼 추상화를 읽기 전용으로 검토해 주세요.

- 각 경계의 목적, 호출자, 책임, 입력, 출력, 오류를 표로 정리하세요.
- 숨긴 내부 세부와 외부로 새는 조건을 구분하세요.
- 현재 요구에서 실제로 확인된 변경 축과 추측한 미래 요구를 구분하세요.
- 추상화가 너무 적거나 너무 많은 신호를 파일과 코드 위치로 제시하세요.
- 단순성, 성능, 유연성, 비용, 운영 난이도 중 얻은 것과 잃은 것을 적으세요.
- 더 단순하고 가역적인 대안이 있다면 영향 범위와 되돌리기 방법을 비교하세요.
- 설명만으로 완료 판정하지 말고 필요한 테스트, 로그, 데이터 상태, 화면 증거를 제안하세요.
- 파일을 수정하거나 패키지를 설치하거나 외부 상태를 변경하지 마세요.
```

AI가 “깔끔하다”, “확장 가능하다”라고 평가한 문장은 증거가 아닙니다. 실제 diff에서 계층 수와 책임을 확인하고, 테스트가 경계의 정상·실패 조건을 다루는지, 빌드와 사용자 흐름이 유지되는지 따로 검증합니다.

## 확인 체크리스트

- [ ] 이 추상화가 필요한 현재 문제를 한 문장으로 설명할 수 있나요?
- [ ] 목적·호출자·책임·입력·출력·오류가 적혀 있나요?
- [ ] 숨기는 세부와 반드시 드러내야 하는 제약을 구분했나요?
- [ ] 경계가 새는 조건과 그때 볼 증거를 정했나요?
- [ ] 얻는 이점과 성능·유연성·비용·운영 측면의 대가를 함께 비교했나요?
- [ ] 추상화 부족과 과잉 추상화 신호를 실제 변경에서 확인했나요?
- [ ] 현재 확인된 요구와 추측한 미래 요구를 분리했나요?
- [ ] 더 단순한 대안과 되돌리기 비용을 비교했나요?
- [ ] 정상·거절·실패·복구 경로를 테스트나 관찰 증거로 확인했나요?
- [ ] 기술 이름이 책임과 검증 설명을 대신하지 않나요?

## 짧은 연습

현재 프로젝트의 함수, API, 라이브러리 또는 프레임워크 하나를 고릅니다. 다음 다섯 줄을 채워 보세요.

1. 이 경계가 숨기는 세부는 무엇인가?
2. 호출자가 반드시 알아야 하는 입력·출력·오류는 무엇인가?
3. 숨은 세부가 밖으로 새는 조건은 무엇인가?
4. 단순성을 얻는 대신 어떤 비용을 받아들였는가?
5. 실제 요구가 바뀌면 어떤 증거를 보고 유지·분리·제거할 것인가?

답을 쓴 뒤 AI에게 같은 항목을 독립적으로 찾게 하고, 서로 다른 부분을 실제 파일·테스트·로그에서 확인합니다.
