## 먼저 결론

ADR(Architecture Decision Record)은 중요한 아키텍처 결정을 **그때의 맥락, 검토한 대안, 선택, 받아들인 결과와 다시 볼 조건**까지 남기는 짧은 기록입니다. 기술 이름을 채택했다는 선언이나 회의 참석자·발언을 시간 순서로 적는 회의록이 아닙니다. 전체 시스템을 한 문서에 설명하는 설계 명세도 아닙니다.

좋은 ADR은 “왜 그때 이 선택이 합리적이었는가?”와 “지금 무엇이 달라지면 다시 판단해야 하는가?”에 답합니다. 결정 당시의 가정과 증거를 분리하면 미래의 팀이 결정을 무조건 지키거나 이유 없이 뒤집는 대신 현재 사실에 대조할 수 있습니다. ADR은 영원한 진리가 아니라 특정 맥락에서 승인된 결정의 역사입니다.

## 왜 필요한가

프로젝트가 몇 달 지나면 코드와 설정은 남아도 왜 그 구조를 선택했는지는 사라지기 쉽습니다. 새 구성원이 “왜 정적 전달인가?”, “왜 데이터베이스 하나인가?”, “왜 이 프레임워크인가?”라고 물을 때 제품 이름만 남아 있으면 원래 제약이 아직 유효한지 판단할 수 없습니다. 무작정 유지하면 바뀐 요구에 맞지 않을 수 있고, 무작정 교체하면 당시 지키려던 품질·권한·비용을 잃을 수 있습니다.

AI는 현재 저장소에서 보이는 기술을 그럴듯하게 사후 정당화할 수 있습니다. 실제 대안을 조사하지 않았는데 비교표를 채우거나, 측정하지 않은 트래픽·비용·성능을 사실처럼 쓰거나, 특정 공급자의 마케팅 문구를 아키텍처 원칙으로 바꿀 수 있습니다. ADR은 선택 이전의 질문·근거·미확인 범위와 선택 이후의 검증을 연결해 이런 사후 합리화를 줄입니다.

## 한 문장 정의

- **Architecture Decision Record(ADR)**: 한 개의 아키텍처적으로 중요한 결정을 당시 맥락·상태·선택·결과와 함께 남기는 짧은 기록입니다.
- **트레이드오프(trade-off)**: 한 이점을 얻는 대신 받아들이는 비용·제약·위험과 포기한 가치를 함께 보는 선택 관계입니다.
- **결정 맥락(context)**: 결정에 영향을 주는 사용자 문제, 품질 목표, 기술·조직·시간·비용 제약과 충돌하는 힘입니다.
- **결과(consequence)**: 결정을 적용해 새로 생기거나 달라지는 긍정·부정·중립 조건과 후속 책임입니다.
- **재검토 신호(revisit trigger)**: 가정·품질·비용·규모·지원 범위가 달라져 결정을 다시 평가해야 하는 관찰 가능한 조건입니다.

Michael Nygard의 ADR 원형은 제목·상태·맥락·결정·결과를 중심으로 하고, 뒤집힌 기록을 지우지 않고 `superseded` 같은 상태로 남기는 방식을 제안합니다. 이 장의 **대안·가정·증거·재검토 조건**은 그 핵심을 보존하면서 비개발자가 판단과 검증을 추적하기 위해 권장하는 확장 필드입니다. 모든 조직과 제품에 하나뿐인 ADR 양식이라고 주장하지 않습니다.

## 항해 일지로 이해하기

ADR을 항해 일지의 중요한 항로 선택에 비유할 수 있습니다. 선장은 출발지·목적지·날씨·연료·위험을 보고 여러 항로 중 하나를 선택하고, 예상 이점과 위험, 다시 판단할 기상 조건을 남깁니다. 나중에 다른 선장이 같은 기록을 보면 그 항로를 맹목적으로 따르기보다 현재 조건과 비교할 수 있습니다.

### 비유가 맞는 지점

- 선택은 당시 목표·제약·정보 안에서 평가해야 합니다.
- 선택하지 않은 경로와 제외 이유가 있어야 실제 트레이드오프를 이해할 수 있습니다.
- 결정 뒤 생긴 비용과 책임이 다음 결정의 맥락이 됩니다.
- 날씨가 달라지듯 가정과 환경이 바뀌면 재검토가 필요합니다.

### 비유가 깨지는 지점

소프트웨어 결정은 한 척의 배가 한 항로를 택하는 것보다 복잡합니다. 일부 구성요소에서 대안을 동시에 시험하거나 점진적으로 전환할 수 있고, 여러 팀·사용자·공급자와 법적 제약이 같은 결정에 영향을 줍니다. 코드·배포·데이터가 결정 문서와 다르게 움직일 수도 있습니다. 또한 과거 ADR은 현재 구현의 준수나 운영 성공을 자동으로 증명하지 않습니다. 이 비유만으로 성능·보안·접근성·복구 품질을 판정할 수는 없습니다.

## 시스템에서의 위치

ADR은 요구·설계·구현·검증 사이의 한 중요한 선택을 연결합니다.

```text
사용자 문제·품질 목표·제약
→ 아키텍처 대안과 가정
→ 비교 증거와 미확인 범위
→ 한 중요한 결정 승인
→ 구현·배포·운영 결과
→ 결과와 재검토 신호 관찰
→ 유지 / 수정 / 새 ADR로 대체
```

PRD는 어떤 사용자 문제와 결과가 필요한지, Software Design Description은 시스템이 책임·경계·인터페이스·데이터·상태를 어떻게 구성할지 넓게 설명합니다. ADR은 그 설계 안에서 구조·품질·의존성·인터페이스·배치·구축 방식에 의미 있는 영향을 주는 **한 결정**과 이유를 좁혀 기록합니다. 자세한 문서 구분은 [PRD·SDD·TDD](../prd-sdd-tdd/)에서 확인합니다.

작은 코드 스타일이나 쉽게 되돌릴 수 있는 지역 변수 이름을 모두 ADR로 만들 필요는 없습니다. 반대로 데이터 소유권, 신뢰 경계, 배포 단위, 동시성 전략, 대체 비용이 큰 프레임워크·런타임·플랫폼 선택처럼 여러 변경의 방향과 실패 범위를 바꾸는 결정은 기록 가치가 큽니다. 중요한 정도는 기술 유행보다 영향 범위·가역성·운영 책임으로 판단합니다.

## ADR의 핵심 필드

| 필드 | 답할 질문 | 좋은 증거 | 피할 내용 |
|---|---|---|---|
| 제목·ID | 한 결정은 무엇인가 | 안정적인 번호와 짧은 명사구 | 여러 결정을 한 제목에 묶음 |
| 상태 | 제안·승인·폐기·대체 중 무엇인가 | 승인 주체·날짜·대체 ADR 연결 | `final`, `영구` 같은 무기한 선언 |
| 맥락 | 어떤 문제·품질·제약·힘이 충돌하는가 | 요구 ID, 사용자 흐름, 현재 구조, 측정값 | 기술 이름을 먼저 정하고 배경을 끼워 맞춤 |
| 결정 | 정확히 무엇을 어떤 범위에서 선택하는가 | 책임·경계·적용/비적용 범위 | “현대적인 구조를 쓴다” 같은 모호한 문구 |
| 대안 | 무엇을 비교했고 왜 제외했는가 | 같은 요구·품질·제약 축의 비교 | 허수아비 대안이나 조사하지 않은 단정 |
| 결과 | 무엇을 얻고 어떤 비용·책임을 받는가 | 긍정·부정·중립 결과와 후속 작업 | 장점만 적거나 미래 문제를 숨김 |
| 가정 | 아직 사실이 아니지만 판단에 사용한 것은 무엇인가 | 예상 규모·팀 역량·지원 범위와 확인일 | 추정을 측정 사실처럼 표현 |
| 증거 | 어떤 사실과 실험이 선택을 지지하는가 | 공식 문서, 저장소 확인, 작은 실험, 측정 | 검색 요약·마케팅·AI 설명만 사용 |
| 재검토 조건 | 무엇이 달라지면 다시 보는가 | 수치·사건·지원 종료·반복 장애 같은 신호 | “필요하면 재검토”처럼 판정 불가 문구 |

필드 수를 채우는 것이 목적은 아닙니다. 맥락·결정·결과가 원형의 핵심이고, 이 장의 확장 필드는 결정의 불확실성과 수명을 드러낼 때 사용합니다. 짧게 유지하되 미래 독자가 선택과 한계를 다시 판정할 만큼 구체적이어야 합니다.

## 맥락에는 결론이 아니라 힘을 적으세요

맥락은 “React를 사용해야 한다” 같은 결론이 아닙니다. 사용자가 무엇을 해야 하는지, 어떤 품질과 제약이 충돌하는지, 현재 시스템이 무엇인지 적습니다. 예를 들어 교육용 주가 대시보드라면 다음과 같은 힘이 있을 수 있습니다.

- 현재 데이터는 작은 고정 `EDU-FIXTURE`이고 실제 시장 원천은 채택하지 않았습니다.
- 첫 공개 범위는 읽기 전용이며 로그인·주문·개인 포트폴리오는 비목표입니다.
- 표·차트·요약은 같은 버전과 선택 결과를 사용해야 합니다.
- 갱신 실패 때 마지막 정상 버전과 지연 이유를 보여 줘야 합니다.
- 실제 원천·권리·최신성 요구가 생기면 구조가 달라질 수 있습니다.

이 맥락에서 “초기에는 버전이 있는 정적 파일로 전달한다”는 결정이 나올 수 있습니다. 하지만 사용자가 실제 원천의 짧은 갱신 주기나 사용자별 비공개 데이터를 요구한다면 같은 결정의 전제가 달라집니다. 기술 선택을 맥락으로 쓰지 않으면 무엇이 바뀌었는지 비교할 수 없습니다.

## 결정은 범위와 비범위를 포함하세요

“단일 데이터베이스를 사용한다”보다 “첫 모임 참가 웹앱의 사용자·모임·참가 관계는 한 관계형 데이터베이스의 한 트랜잭션 경계에서 관리하고, 알림 큐·검색 인덱스·분석 저장소는 첫 범위에 추가하지 않는다”가 더 검증 가능합니다. 선택한 것과 선택하지 않은 범위, 적용 대상과 예외를 함께 적기 때문입니다.

결정 문장은 현재의 능동형으로 씁니다. “검토할 수 있다”, “향후 고려한다”는 결정이 아닙니다. 아직 승인되지 않았다면 상태를 `proposed`로 두고 필요한 증거와 승인 조건을 적으세요. 구현이 이미 시작됐다는 사실을 승인된 결정으로 바꾸지 않습니다.

## 대안은 같은 질문으로 비교하세요

대안을 나열할 때는 모두 같은 요구·품질·제약 축으로 비교합니다. 예를 들어 공개된 동일 버전의 검증 데이터셋을 로그인 없이 읽고, 실패하면 마지막 정상 버전을 보여 주는 대시보드를 비교한다고 가정합니다. 다음 세 열은 서로 다른 구성안입니다. A는 화면과 데이터 파일을 함께 정적으로 발행하고, B는 한 서버 애플리케이션이 검증된 데이터셋을 읽어 요청마다 화면을 만들며, C는 정적 화면과 별도로 배포한 읽기 전용 데이터 API를 조합합니다. 렌더링 위치와 API 유무 자체는 서로 배타적인 축이 아니며, API가 있다는 사실만으로 별도 서비스나 배포 단위를 뜻하지 않습니다.

| 비교 축 | A: 정적 화면·데이터 파일 | B: 한 서버의 화면 렌더링 | C: 정적 화면·별도 읽기 API |
|---|---|---|---|
| 현재 사용자 행동 | 공통 버전의 표·차트를 읽음 | 같은 버전의 표·차트를 서버가 구성 | 같은 버전의 데이터를 API로 받아 표시 |
| 신선도 | 검증·빌드·발행 주기에 의존 | 검증 데이터셋 교체 주기에 의존 | 검증 데이터셋 교체·캐시 계약에 의존 |
| 권한·비밀 | 공개 가능한 자산만 포함 | 서버 비밀은 응답에서 제외 | 공개 읽기 범위와 응답 필드를 제한하고 다른 출처 요청이면 CORS도 검토 |
| 실패·복구 | 실패 후보 미게시·이전 자산 복원 검증 | 같은 게시 게이트와 마지막 정상 버전 외에 서버 장애 대응 필요 | 같은 게시 게이트·정상 버전 외에 API 장애·화면과 데이터 버전 불일치 대응 필요 |
| 운영 비용 | 정적 발행·복구 경로 관리 | 런타임 관측·복구 경로 추가 | 이 구성에서는 화면/API의 별도 배포·호환·관측 추가 |
| 변경 신호 | 현재 발행 주기로 승인된 신선도 요구를 충족하지 못함 | 측정된 요청 부하·비용·장애 영향이 수용 범위를 넘음 | 실제 독립 소유·배포 이점보다 호환·운영 비용이 커짐 |

이 표의 문장은 제품별 보장이 아니라 결정 질문입니다. 실제 후보를 채택할 때는 공식 문서, 가격·지원 상태, 권한·배포·복구 범위를 확인일과 함께 다시 조사해야 합니다. 비교 축이 다르면 특정 대안을 이기게 만든 허수아비 비교가 됩니다.

## 결과는 장점과 단점보다 넓습니다

결과는 선택 뒤 새 맥락이 되는 사실입니다. 긍정과 부정뿐 아니라 중립적인 후속 변화도 기록합니다.

- 긍정: 초기 공개 경로와 운영 표면이 단순해집니다.
- 부정: 데이터 갱신은 빌드·발행 과정과 연결되고 사용자별 실시간 상태에는 맞지 않습니다.
- 중립: 데이터셋 버전·신선도·마지막 정상 버전을 정적 전달 계약에 포함해야 합니다.
- 후속 책임: 실패 후보가 정상 자산을 덮지 않는 발행 게이트와 이전 정상 버전 복구를 검증합니다.
- 새로운 위험: 실제 원천을 채택하면 이용 조건·재배포 권리와 정정 절차가 추가됩니다.

결과가 아직 관찰되지 않았다면 예상 결과라고 표시합니다. 구현 뒤 실제 결과를 ADR에 무한히 덧붙여 회의 일지로 만들기보다, 필요한 측정·인시던트·새 결정 문서를 연결하고 원래 가정이 맞았는지 재검토하세요.

## 가정과 증거를 분리하세요

“초기 사용자는 적다”는 가정이고 “교육용 fixture 6행, 공개 사용자 트래픽 측정 없음”은 현재 사실입니다. “팀이 이 데이터베이스에 익숙하다”도 누가 어떤 운영 경험과 권한을 갖는지 확인하지 않으면 가정입니다. 가정을 숨기지 않으면 틀렸을 때 결정을 실패로 낙인찍기보다 입력이 달라졌음을 알 수 있습니다.

증거에는 출처와 적용 범위를 적습니다.

- 표준·공식 문서: 어떤 정의·기능·지원 상태를 직접 뒷받침하는가?
- 저장소 증거: 현재 파일·설정·의존성·데이터·배포 경계가 실제로 무엇인가?
- 작은 실험: 어떤 후보와 실패 조건을 어느 환경에서 확인했는가?
- 측정: 입력·기간·단위·표본과 기대 기준은 무엇인가?
- 미확인: 제품별 가격·제한·운영 복구처럼 아직 직접 확인하지 않은 것은 무엇인가?

공식 문서가 기능을 설명해도 현재 프로젝트가 그 기능을 올바르게 채택했다는 증거는 아닙니다. 로컬 실험 성공도 운영 규모·권한·장애 복구를 자동으로 증명하지 않습니다. 각 증거가 닫는 주장과 남는 불확실성을 함께 씁니다.

## 재검토 조건을 관찰 가능하게 쓰세요

“나중에 필요하면 바꾼다”는 조건을 판정할 수 없습니다. 다음처럼 사건·수치·지원 상태·반복 실패에 연결하세요.

- 공개 데이터 갱신 허용 지연보다 실제 발행 지연이 반복해서 길어집니다.
- 사용자별 비공개 데이터나 쓰기 행동이 승인된 범위에 들어옵니다.
- 한 배포 단위의 장애가 서로 독립이어야 할 기능을 함께 중단시킵니다.
- 특정 후보의 공식 지원 종료나 보안 업데이트 중단이 발표됩니다.
- 데이터 크기·요청량·비용 측정이 현재 구조의 수용 기준을 넘습니다.
- 복원 시험이 정한 복구 목표를 충족하지 못합니다.
- 팀 소유권·운영 권한·규제가 바뀌어 기존 가정이 성립하지 않습니다.

신호가 발생했다고 자동으로 반대 대안을 채택하는 것은 아닙니다. 새 맥락과 현재 후보를 다시 조사하고, 기존 ADR을 `superseded`로 바꿀지, 범위만 수정할지, 결정을 유지할지 새 ADR에서 판단합니다.

## 상태와 역사 기록을 관리하세요

프로젝트에 맞는 상태 집합을 정하되 최소한 제안, 승인, 거절, 폐기·대체를 구분할 수 있어야 합니다. Nygard의 원형은 `proposed`, `accepted`, `deprecated`, `superseded` 예시를 제시합니다. 이름보다 상태의 의미·승인 주체·대체 연결을 일관되게 쓰는 것이 중요합니다.

결정이 바뀌어도 과거 ADR을 현재 결론처럼 고쳐 쓰거나 삭제하지 않습니다. 과거 기록에는 당시 맥락과 결정이 남아 있어야 합니다. 새 ADR이 무엇을 왜 바꿨는지 쓰고, 이전 ADR은 대체 상태와 새 기록 링크를 추가합니다. 잘못된 비밀·개인정보가 들어간 경우는 일반 역사 보존과 다른 보안 대응이 필요하므로 노출 범위·폐기·이력 정리 권한을 별도로 판단합니다.

## ADR은 회의록도 영원한 진리도 아닙니다

| 잘못된 사용 | 왜 문제인가 | 바꿀 질문 |
|---|---|---|
| 참석자와 발언을 시간 순서로 적음 | 결정의 맥락·대안·결과를 찾기 어려움 | 어떤 힘과 증거로 무엇을 선택했나 |
| 제품 이름과 버전 목록만 적음 | 구조·품질·책임과 선택 이유가 없음 | 어떤 책임·경계·실패를 바꾸는가 |
| 이미 구현한 기술을 정당화함 | 실제 대안과 미확인 범위가 사라짐 | 결정 시점에 무엇을 알았고 몰랐나 |
| 모든 작은 선택을 ADR로 만듦 | 중요한 결정이 소음에 묻힘 | 영향 범위·가역성·운영 책임이 큰가 |
| `accepted`를 영구 규칙으로 읽음 | 맥락과 가정 변화에 대응하지 못함 | 어떤 신호에서 다시 평가하나 |
| 과거 기록을 현재 구현 증거로 사용 | 문서와 코드·운영이 어긋날 수 있음 | 현재 diff·설정·테스트·브라우저·운영 증거는 무엇인가 |

## 두 사례의 ADR 후보

### 모임 참가 웹앱: 한 트랜잭션 경계에서 정원과 중복을 관리

- 맥락: 참가·취소는 인증된 자신의 행동이며 정원과 활성 중복 불변조건을 여러 요청에서 지켜야 합니다.
- 결정: 첫 범위의 사용자·모임·참가 관계는 한 관계형 데이터베이스의 일관된 트랜잭션·제약 경계에서 관리합니다.
- 대안: A는 한 애플리케이션 안의 참가 모듈이 모임·참가 데이터를 한 트랜잭션 경계에서 관리하고, B는 별도 배포하는 참가 서비스가 그 데이터를 독점 소유하며 API를 통해 처리하도록 설계합니다. 두 후보 모두 인증된 주체 확인·인가·정원·활성 중복 조건을 충족해야 하며, 같은 경쟁 요청과 실패·복구 시험으로 비교합니다. 코드 모듈 분리와 서비스의 별도 배포는 다른 결정입니다.
- 사전 탈락안: 화면 비활성화만으로는 서버의 동시 요청과 중복을 통제할 수 없으므로 필수 조건을 충족한 경쟁 후보로 세지 않습니다. A와 B 어느 쪽도 한 DB나 트랜잭션을 사용한다는 말만으로 동시성 보장이 완성되지는 않습니다.
- 결과: 서버·데이터 경계의 동시성 검증이 필요하고, 물리적 서비스 분리는 미룹니다.
- 가정: 첫 범위에서 독립 확장·배포가 필요한 팀·부하 증거가 없습니다.
- 증거: 모임 사례 불변조건, 데이터 제약·트랜잭션의 선택 제품 공식 문서, 동시 요청 테스트가 필요합니다.
- 재검토: 독립 소유·확장·장애 격리 요구가 실제로 생기거나 한 경계의 복구 목표를 충족하지 못합니다.

### 교육용 주가 대시보드: 첫 범위는 버전이 있는 정적 전달

- 맥락: 데이터는 작은 `EDU-FIXTURE`, 읽기 전용이며 실제 시장 원천·로그인·주문은 비목표입니다.
- 결정: 검증된 데이터셋과 화면을 정적 자산으로 함께 전달하고 버전·신선도·마지막 정상 버전을 표시합니다.
- 대안: 위 표의 A·B·C를 동일한 공개 읽기·버전 일치·신선도·실패 복구 조건으로 비교합니다. 노트북 공유는 계산 검토용 보조 자료일 수 있지만 브라우저에서 같은 표·차트를 제공한다는 조건을 충족하지 않으면 동등한 공개 구성안으로 세지 않습니다.
- 결과: 운영 표면은 작지만 갱신은 발행 주기와 연결되고 개인화·짧은 신선도 요구에는 맞지 않습니다.
- 가정: 현재 fixture 규모와 승인된 갱신 기대에서 정적 발행 지연이 허용됩니다.
- 증거: fixture 계약·빌드 산출물·화면 버전·실패 후보 미게시와 이전 정상 버전 복구를 확인합니다.
- 재검토: 실제 원천 채택, 더 짧은 신선도, 사용자별 권한, 데이터 크기·비용이 현재 수용 기준을 넘습니다.

이 예시는 완성된 제품 결정이 아니라 교육용 후보입니다. 실제 데이터베이스·런타임·호스팅·권리를 선택할 때 공식 문서와 현재 운영 증거를 다시 확인해야 합니다.

## 최소 ADR 템플릿

```text wrap

proposed / accepted / rejected / deprecated / superseded by ADR-NNN

- 결정·승인 날짜(미승인이면 미정):
- 관련 승인·대체 기록 링크(없으면 없음):

우리는 [적용 범위]에서 [선택]을 한다. [비적용 범위]는 포함하지 않는다.

## 검토한 대안
1. 대안 A: 같은 비교 축의 이점·비용·제외 이유
2. 대안 B: 같은 비교 축의 이점·비용·제외 이유

- 부정:

- 아직 미확인:
```

템플릿을 복사했다고 좋은 결정이 되는 것은 아닙니다. 한 ADR에 여러 독립 결정을 넣지 않았는지, 대안이 실제로 같은 질문에 답하는지, 결과와 재검토 신호가 검증 가능한지 검토하세요.

## AI와 작업할 때

다음처럼 사실·가정·대안·증거를 분리한 읽기 전용 초안을 요청하세요.

```text wrap
현재 저장소의 아키텍처적으로 중요한 결정 후보 하나를 읽기 전용으로 검토하라.
사용자 문제, 품질 목표, 제약, 현재 구조와 미확인 범위를 먼저 적고 기술 이름을 결론으로 선행하지 마라.
같은 요구·품질·비용·권한·실패·복구 축에서 현실적인 대안 2개 이상과 현 상태 유지 대안을 비교하라.
권장 결정의 적용·비적용 범위, 긍정·부정·중립 결과, 후속 운영 책임을 작성하라.
측정 사실, 공식 문서에서 직접 확인한 사실, 저장소 관찰, 추정을 구분하고 출처·확인일·적용 범위를 남겨라.
가정이 깨지는 수치·사건·지원 상태·반복 장애를 재검토 조건으로 제안하라.
회의 발언을 나열하거나 현재 구현을 사후 정당화하지 말고, 확인하지 못한 제품 기능·비용·성능은 미확인으로 남겨라.
파일을 수정하거나 결정을 accepted로 바꾸지 마라.
```

AI의 ADR 초안은 승인된 결정이 아닙니다. 실제 책임자와 영향을 받는 이해관계자가 맥락·대안·결과·증거를 검토하고 상태를 정해야 합니다. 공식 문서 인용도 현재 구현·배포·복구 성공을 대신하지 않습니다.

## 확인 체크리스트

- [ ] 한 ADR이 한 개의 아키텍처적으로 중요한 결정을 다룹니다.
- [ ] 제목·ID·상태·승인 주체와 날짜를 프로젝트 규칙에 맞게 기록했습니다.
- [ ] 맥락에 사용자 문제·품질·제약·충돌하는 힘이 있고 결론을 선행하지 않습니다.
- [ ] 결정의 적용·비적용 범위와 책임·경계를 구체적으로 썼습니다.
- [ ] 현 상태 유지와 현실적인 대안을 같은 축으로 비교했습니다.
- [ ] 선택하지 않은 이유를 허수아비 대안이나 기술 취향으로 쓰지 않았습니다.
- [ ] 긍정·부정·중립 결과와 후속 운영 책임을 모두 기록했습니다.
- [ ] 측정 사실·공식 자료·저장소 관찰·가정·미확인을 구분했습니다.
- [ ] 증거에 확인일·적용 범위·제품 일반화 금지선이 있습니다.
- [ ] 재검토 조건을 수치·사건·지원 상태·반복 실패처럼 관찰 가능하게 썼습니다.
- [ ] 과거 결정을 지우지 않고 새 ADR과 `superseded` 연결로 대체합니다.
- [ ] ADR을 회의록·전체 설계 명세·제품 목록·영원한 진리로 사용하지 않습니다.
- [ ] 현재 구현·테스트·브라우저·운영 증거를 ADR 작성 사실과 별도로 확인합니다.
- [ ] 비밀·개인정보·토큰·내부 접근 정보를 기록하지 않습니다.

- [ISO/IEC/IEEE 42010 conceptual model](https://www.iso-architecture.org/ieee-1471/cm/): 2026-08-13 확인 기록이 있는 보조 자료입니다. 2026-11-15 재확인은 접근 실패로 미확인(not-confirmed)이며, 이번에는 세부 관계를 뒷받침하는 새 직접 근거로 사용하지 않습니다.

Nygard의 글은 널리 쓰이는 ADR 원형의 1차 기록이지만 모든 조직의 유일한 표준은 아닙니다. ISO/IEC/IEEE 42010은 아키텍처 설명의 요구를 다루며 특정 ADR 파일 템플릿·방법·도구를 강제하지 않습니다. 이 장의 대안·가정·증거·재검토 필드는 판단 추적을 위한 핸드북의 권장 확장입니다.

출처의 확인일·문서 상태·적용 범위와 일반화 금지선은 저장소의 `research/source-map.md`에서 관리합니다. PBSG-003의 `confirmed` 전환은 당시 직접 자료 대조의 기록이며 모든 연결 페이지의 현재 접근 성공을 뜻하지 않습니다. 이번에는 Nygard 원형과 ISO 공개 소개의 범위를 확인했고, conceptual model의 과거 기록과 이번 접근 실패는 구분했습니다.
