## 먼저 결론

프런트엔드와 백엔드의 경계는 폴더 이름이나 사용하는 언어가 아니라 **누가 값을 바꿀 수 있고, 어느 쪽이 결과를 최종 보장해야 하는가**로 나눕니다. 프런트엔드는 사용자가 보고 조작하는 화면, 즉각적인 피드백과 아직 확정되지 않은 클라이언트 상태를 주로 맡습니다. 백엔드는 사용자가 우회해서는 안 되는 업무 규칙, 인증된 주체와 행동 권한, 비밀값, 영속 데이터와 동시 변경을 신뢰 가능한 서버 측 경계에서 판단합니다.

같은 입력 검사가 양쪽에 있어도 목적은 다를 수 있습니다. 브라우저의 “필수 입력” 안내는 사용자가 빨리 실수를 고치게 하지만 직접 요청을 만들어 우회할 수 있습니다. 서버의 입력·권한·업무 규칙 검사는 우회된 요청도 안전하게 거절해야 합니다. 따라서 중요한 검증의 완료 증거는 버튼 비활성화나 화면 오류 문구가 아니라 실제 서버 요청, 부정 테스트, 데이터 제약과 처리 뒤 권위 상태입니다.

## 왜 필요한가

AI에게 “프런트엔드와 백엔드를 만들어 주세요”라고 요청하면 양쪽 파일은 생겨도 책임 경계는 빠지기 쉽습니다. 브라우저가 보낸 `participantId`를 서버가 그대로 믿거나, 정원 초과를 버튼 비활성화만으로 막거나, 서버 전용 키가 빌드된 JavaScript에 포함되거나, 같은 상태 규칙이 양쪽에서 다른 버전으로 움직일 수 있습니다. 화면 데모는 정상처럼 보여도 직접 요청·여러 탭·동시 사용자·응답 유실 상황에서는 무너집니다.

반대로 “보안이 중요하니 모든 것을 백엔드에서 한다”도 충분한 답이 아닙니다. 이미 받은 공개 데이터를 정렬하거나 입력 형식을 안내하고 로딩·오류·재시도 상태를 표현하는 일은 프런트엔드의 책임입니다. 서버가 최종 규칙을 집행하더라도 사용자가 결과를 이해하고 다음 행동을 할 수 없다면 사용자 작업은 끝나지 않습니다. 경계의 목적은 한쪽을 없애는 것이 아니라 각 책임의 최종 보장 위치와 증거를 분명하게 만드는 것입니다.

## 한 문장 정의

- **프런트엔드(frontend)**: 사용자의 입력·표시·상호작용과 브라우저 안의 임시 상태를 담당하는 영역입니다.
- **백엔드(backend)**: 신뢰할 수 있는 업무 규칙·권한·비밀·영속 데이터 처리와 외부 연동을 담당하는 서버 측 영역입니다.
- **신뢰 경계(trust boundary)**: 서로 다른 신뢰 수준이나 권한 주체 사이에서 데이터와 제어가 오가는 경계입니다. 이 경계를 넘은 값은 신뢰 가능한 쪽에서 다시 확인해야 합니다.
- **클라이언트 측 검증(client-side validation)**: 입력 누락이나 형식 오류를 사용자 가까이에서 빠르게 안내하는 검사입니다. 사용자가 실행 코드와 요청을 바꿀 수 있으므로 보안 통제의 최종선이 아닙니다.
- **서버 측 검증(server-side validation)**: 요청의 입력·신원·권한·업무 규칙을 신뢰 가능한 처리 경계에서 확인하고 허용 또는 거절하는 검사입니다. 데이터베이스 제약이나 별도 인가 서비스가 최종 보장을 나누어 맡을 수도 있습니다.

프런트엔드와 백엔드는 클라이언트와 서버의 완전한 동의어가 아닙니다. 브라우저 프런트엔드는 보통 서버의 클라이언트지만, 백엔드도 데이터베이스나 외부 API를 호출할 때는 그 시스템의 클라이언트 역할을 합니다. 역할축과 책임축의 차이는 [클라이언트·서버·풀스택](../client-server-full-stack/)에서 더 넓게 다룹니다.

## 공연장 출입구로 이해하기

화면의 버튼과 입력 안내는 공연장 앞의 안내판과 줄 표시, 서버의 권한·업무 규칙은 실제 표를 확인하고 입장을 결정하는 검표대에 비유할 수 있습니다. 안내판은 잘못된 줄을 줄이고 관객이 준비할 정보를 알려 주지만, 안내판을 보지 않았다는 이유만으로 무표 입장을 허용하지는 않습니다.

### 비유가 맞는 지점

- 사용자 가까운 안내는 빠른 피드백을 주고 불필요한 실패를 줄입니다.
- 최종 입장 결정은 안내판이 아니라 신뢰 가능한 검표 절차가 맡습니다.
- 입장 가능 표시, 검표 완료, 실제 좌석 점유는 서로 다른 상태와 증거입니다.
- 규칙이 바뀌면 안내와 검표 기준이 같은 계약을 가리켜야 합니다.

### 비유가 깨지는 지점

웹 요청은 사람이 한 출입구를 지나가는 것보다 복제가 쉽고 여러 요청이 거의 동시에 도착할 수 있습니다. 사용자는 브라우저 개발자 도구나 별도 프로그램으로 화면 제약을 건너뛰고 요청을 만들 수 있고, 서버도 데이터베이스·캐시·외부 서비스와 여러 신뢰 경계를 가집니다. 또한 서버 한 프로세스가 모든 보장을 혼자 만드는 것이 아니라 API의 인가 검사와 데이터베이스의 고유성·트랜잭션 제약이 함께 결과를 보장할 수 있습니다. 그래서 “검표대에서 본다”는 비유만으로 동시성·데이터 무결성·응답 유실을 설명할 수는 없습니다.

## 시스템에서의 위치

모임 참가 웹앱의 참가 작업을 가장 단순한 책임 흐름으로 적으면 다음과 같습니다.

```text
사용자가 참가 버튼을 누름
→ 프런트엔드가 현재 화면 상태를 확인하고 로딩을 표시함
→ 참가 API 계약에 맞는 요청을 보냄
→ 백엔드가 입력과 인증된 주체를 확인함
→ 백엔드가 자신의 참가 행동인지, 모집 중인지, 중복인지, 정원이 남았는지 판단함
→ 데이터 경계가 참가 관계와 정원 불변조건을 함께 확정하거나 거절함
→ 백엔드가 안전한 성공·실패 응답을 보냄
→ 프런트엔드가 응답과 필요하면 재조회한 최신 상태를 화면에 표현함
```

이 흐름의 경계는 “브라우저 파일 대 서버 파일” 하나뿐이 아닙니다. 브라우저와 API 사이에는 사용자가 값을 바꿀 수 있는 신뢰 경계가 있고, API와 데이터베이스 사이에는 쿼리·트랜잭션·제약 계약이 있으며, 백엔드와 외부 서비스 사이에는 별도의 입력·출력·시간 초과·비밀 관리 경계가 있습니다. 하나의 저장소나 프레임워크 안에 코드가 함께 있어도 책임과 신뢰 수준이 같아지는 것은 아닙니다.

## 책임을 네 질문으로 나누세요

| 질문 | 프런트엔드의 주된 책임 | 백엔드·신뢰 가능한 데이터 경계의 주된 책임 | 직접 확인할 증거 |
|---|---|---|---|
| 사용자가 무엇을 보고 조작하는가? | 화면 구조, 입력, 포커스, 로딩·성공·빈 결과·오류 상태, 다음 행동 | 허용된 데이터와 가능한 행동을 계약에 맞게 제공 | 실제 DOM·화면·키보드 흐름과 응답 데이터 |
| 어떤 값은 아직 임시인가? | 입력 중 값, 선택 상태, 열림·닫힘, 보내는 중, 낙관적 표시 | 확정·거절·만료된 업무 상태와 그 판정 이유 | 새로고침·여러 탭·응답 유실 뒤 권위 상태 재조회 |
| 무엇을 사용자가 우회하면 안 되는가? | 숨김·비활성화로 의도를 안내하되 보안 보장으로 주장하지 않음 | 인증된 주체, 대상 소유권, 행동 권한, 모집 상태·정원·중복·가격 같은 중요 규칙을 매 요청 확인 | 직접 만든 요청과 다른 사용자의 대상에 대한 부정 테스트 |
| 무엇을 브라우저에 보내면 안 되는가? | 공개 가능한 코드·설정·데이터만 사용 | 외부 API 비밀, 서버 전용 설정, 전체 데이터베이스 연결 정보와 비공개 행 보호 | 빌드 산출물·응답·Sources·Network 검색과 비밀 스캔 |

프런트엔드는 허용되지 않은 버튼을 숨겨 사용자의 혼란을 줄일 수 있습니다. 그러나 버튼이 보이지 않는다는 사실은 서버가 요청을 거절한다는 증거가 아닙니다. 백엔드는 요청마다 “누가, 어느 대상을, 어떤 행동으로 바꾸려 하는가?”를 현재 정책과 데이터에 대조해야 합니다. 인증은 요청 주체를 확인하는 일이고, 인가는 그 주체가 이 행동을 해도 되는지 판단하는 일이므로 로그인 성공만으로 다른 사용자의 참가 취소가 허용되는 것은 아닙니다.

## 검증은 왜 서버 측 신뢰 경계에서 끝나야 하나요

브라우저로 전달된 HTML·CSS·JavaScript와 응답 데이터는 사용자가 열람하고 바꿔 실행할 수 있다고 가정해야 합니다. 화면의 `disabled` 속성을 제거하거나 JavaScript 함수를 건너뛰거나 별도 HTTP 클라이언트로 같은 endpoint를 호출할 수 있습니다. 따라서 클라이언트가 보낸 `userId`, `role`, `price`, `capacity`, `isOwner` 같은 값은 중요한 판단의 근거가 아니라 검증할 입력 후보입니다.

모임 참가 요청에서 서버는 화면이 보낸 참가자 ID를 최종 주체로 믿지 않고 서버가 검증한 세션·자격 증명에서 현재 주체를 얻어야 합니다. 이어 그 주체가 자신의 참가를 요청하는지, 대상 모임이 모집 중인지, 활성 중복이 없는지, 현재 확정 수가 정원을 넘지 않는지를 권위 상태에 대조해야 합니다. 여러 요청이 동시에 도착할 수 있으므로 “조회했을 때 자리가 있었다”와 “확정 시점에도 자리가 있었다”도 구분해야 합니다.

서버 검증은 API 코드 한 줄에서 끝난다는 뜻이 아닙니다. 입력 계약은 API 계층, 주체·행동 권한은 인가 계층, 활성 중복과 참조 관계는 데이터베이스 제약, 정원과 여러 변경의 원자성은 트랜잭션·동시성 전략처럼 나뉠 수 있습니다. 수용 기준은 특정 파일 위치가 아니라 우회 요청과 동시 요청에서도 불변조건이 유지되고 안전한 오류가 반환되는지로 씁니다.

## 같은 규칙을 양쪽에 둘 때 계약을 공유하세요

사용자 경험을 위해 같은 규칙의 일부가 양쪽에 보일 수 있습니다. 예를 들어 제목 길이를 프런트엔드가 입력 중 안내하고 서버가 저장 전에 다시 검사할 수 있습니다. 문제는 검사가 두 번 있다는 사실이 아니라 각 사본의 목적과 변경 규칙이 없다는 것입니다.

| 규칙 | 프런트엔드 사본의 목적 | 서버의 최종 책임 | 어긋났을 때 증상 |
|---|---|---|---|
| 제목 필수·길이 | 제출 전 빠른 안내 | 현재 API 계약에 맞지 않는 입력 거절 | 화면에서는 허용했지만 서버는 거절하거나 그 반대가 됨 |
| 참가 가능 표시 | 현재 받은 상태로 가능한 행동 안내 | 요청 시점의 모집 상태·정원·중복 재판정 | 버튼은 활성인데 마감·정원 충돌 응답이 옴 |
| 자신의 참가만 취소 | 다른 사용자의 취소 UI를 보여 주지 않음 | 인증된 주체와 대상 참가 관계의 소유권 확인 | URL·본문의 ID를 바꾸면 다른 사람의 상태가 바뀜 |
| 오류 문구 | 사용자가 다음 행동을 선택하도록 설명 | 안전한 오류 코드·분류·상관 식별자 제공 | 서버 내부 오류나 민감값이 화면에 노출되거나 모든 실패가 같은 문구가 됨 |

필드·타입·길이·오류 분류 같은 공유 가능한 계약은 스키마나 명세에서 양쪽 검증기를 생성할 수도 있지만, 생성 도구가 모든 업무 규칙과 권한을 자동으로 보장하지는 않습니다. 계약의 버전, 하위 호환 범위와 실제 요청·응답 검사를 함께 확인해야 합니다. 서버 규칙이 바뀌는 동안 이전 프런트엔드가 남아 있을 수 있으므로 한 번의 동시 배포를 항상 가정해서도 안 됩니다.

## 경계를 옮겨야 하는 신호

처음부터 모든 책임을 별도 서비스로 나눌 필요는 없습니다. 다음 신호가 실제로 생길 때 경계 이동을 검토하세요.

- 브라우저에 둘 수 없는 외부 API 비밀이나 서버 전용 설정이 필요합니다.
- 사용자별 비공개 데이터와 객체·기능별 권한 판단이 생깁니다.
- 여러 사용자·탭·기기가 같은 영속 상태를 함께 바꿉니다.
- 데이터 크기·비용 때문에 조회·필터·집계를 서버 가까이에서 제한해야 합니다.
- 오래 걸리는 작업이 요청 연결 수명보다 길어 별도 작업 상태나 큐가 필요합니다.
- 같은 서버 영역의 변경·확장·장애 영향이 너무 커서 독립 배치나 소유권 분리가 실제 이점을 줍니다.

경계를 옮기면 네트워크 실패, 인증·인가, 직렬화, 재시도, 배포 순서, 관측과 운영 책임이 늘어납니다. “백엔드답게 보이기 위해” 서버나 서비스를 추가하지 말고, 현재 요구·품질·실패 비용이 새 경계의 비용보다 큰지 ADR로 비교하세요. 반대로 비밀·권한·동시성 책임이 생겼는데 정적 파일이나 화면 제약으로 감추는 것도 안전한 단순화가 아닙니다.

## 대표 실패와 복구

### 화면에서만 권한을 막습니다

다른 사용자의 취소 버튼을 숨겼지만 서버가 본문의 `participantId`만 믿으면 직접 요청으로 우회할 수 있습니다. 인증된 현재 주체와 대상 참가 관계를 서버가 다시 대조하는 부정 테스트를 추가하고, 실패 뒤 다른 사용자의 데이터가 바뀌지 않았는지 재조회하세요.

### 서버 전용 비밀을 프런트엔드 환경 변수에 넣습니다

이름에 `SECRET`이 있어도 빌드 과정에서 브라우저 번들·정적 파일·응답에 포함되면 사용자가 볼 수 있습니다. 배포 자산과 Network 응답을 검색하고 노출된 비밀은 제거만 하지 말고 폐기·교체 범위까지 판단하세요. 공개 식별자와 비밀 자격 증명을 문서와 설정에서 구분하세요.

### 양쪽 규칙이 서로 다릅니다

프런트엔드는 100자를 허용하고 서버는 80자에서 거절하면 사용자는 제출 후에야 오류를 봅니다. 계약의 정본과 버전을 정하고 양쪽 계약 테스트를 실행하되 서버의 최종 거절을 제거하지 마세요. 이전 클라이언트와 새 서버 조합도 호환 범위에 포함하세요.

### 낙관적 화면을 확정 상태로 착각합니다

참가 버튼을 누르자마자 “참가 완료”로 바꾼 뒤 서버가 정원 충돌을 거절하면 화면과 권위 상태가 어긋납니다. 진행 중·확정·거절·결과 불명 상태를 구분하고, 응답이 끊겼다면 무조건 같은 쓰기를 반복하지 말고 자신의 현재 참가 상태를 재조회하세요.

### 백엔드가 응답했으니 사용자 작업도 끝났다고 봅니다

서버 성공과 데이터 확정 뒤에도 프런트엔드가 오래된 응답을 덮어쓰거나 오류 상태에 머물 수 있습니다. Network 응답, 데이터 재조회, UI 상태와 사용자가 다음 행동을 이해하는지를 각각 확인하세요.

### 경계를 너무 일찍 여러 서비스로 나눕니다

작은 모임 앱에서 책임·부하·배포 독립성 근거 없이 인증·참가·알림을 별도 서비스로 나누면 부분 실패와 운영 부담이 늘어납니다. 먼저 한 배포 단위 안에서 모듈·인터페이스 경계를 명확히 하고, 실제 변경·확장·장애 신호가 생길 때 물리적 분리를 검토하세요.

## AI와 작업할 때

“프런트엔드 검증과 백엔드 검증을 추가해 줘”보다 다음처럼 우회 가능성과 증거를 포함한 읽기 전용 검토를 먼저 요청하세요.

```text
모임 참가 웹앱의 참가·취소 흐름에서 프런트엔드와 백엔드의 책임·신뢰 경계를 검토하라.
표시·상호작용·클라이언트 임시 상태와 서버의 입력·인증·인가·업무 규칙·비밀·영속 데이터·동시성 책임을 분리하라.
사용자가 버튼 상태, URL, 요청 본문을 바꾸거나 같은 요청을 동시에 보낼 때 우회되는 규칙을 찾고, 각 규칙의 최종 집행 위치와 부정 테스트·데이터 재조회 증거를 표로 작성하라.
브라우저 번들·정적 파일·응답에 들어갈 수 없는 비밀 후보와 양쪽 계약이 어긋날 수 있는 필드·오류를 표시하라.
현재 저장소에서 직접 확인하지 못한 API·데이터베이스·배포 동작은 추정하지 말고 미확인으로 남겨라.
파일은 수정하지 말고 비밀·쿠키·토큰·개인정보의 실제 값을 출력하지 마라.
```

AI가 제안한 경계는 실제 구현이 아니라 검토 가설입니다. 요청을 우회해도 서버가 거절하는지, 거절 뒤 데이터가 그대로인지, 정상 흐름의 사용자 피드백이 유지되는지 직접 확인해야 합니다. 비밀 스캔 결과가 0건이어도 저장소 밖 배포 설정이나 이미 노출된 자격 증명의 안전을 자동으로 증명하지는 않습니다.

## 확인 체크리스트

- [ ] 프런트엔드의 표시·상호작용·임시 상태와 서버의 최종 보장 책임을 구분했습니다.
- [ ] 브라우저에서 사용자가 바꿀 수 있는 입력·코드·요청을 신뢰하지 않습니다.
- [ ] 인증과 인가를 구분하고 주체·대상·행동을 실제 요청마다 확인합니다.
- [ ] 권한·가격·소유권·정원·중복 같은 중요 규칙의 최종 집행 위치를 정했습니다.
- [ ] 데이터베이스 제약과 트랜잭션이 맡는 보장과 API 코드의 책임을 구분했습니다.
- [ ] 브라우저 번들·정적 파일·응답에 비밀·비공개 데이터가 포함되지 않는지 확인했습니다.
- [ ] 양쪽에 있는 입력 규칙의 정본·버전·호환 범위와 서버 최종 거절을 확인했습니다.
- [ ] 이전 프런트엔드와 새 서버가 잠시 함께 존재하는 배포 순서를 고려했습니다.
- [ ] 낙관적 표시와 권위 있는 확정 상태를 구분하고 실패·응답 유실 복구를 정했습니다.
- [ ] 정상 화면뿐 아니라 직접 만든 요청, 다른 사용자의 대상, 중복·동시 요청을 검사했습니다.
- [ ] 서버 응답, 데이터 재조회, UI 상태와 사용자 완료를 서로 다른 증거로 확인했습니다.
- [ ] 새 서버·서비스 경계의 필요 신호와 추가 운영 비용을 함께 기록했습니다.
