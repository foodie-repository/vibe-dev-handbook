## 왜 필요한가

AI가 “브랜치를 만들고 커밋했으니 PR까지 완료됐습니다”라고 보고해도 실제로는 로컬 브랜치만 있거나, 원격에 올렸지만 Pull Request를 만들지 않았거나, 리뷰 의견이 남아 있는데 병합됐을 수 있습니다. 반대로 한 파일만 바꾸면 항상 작은 작업이라고 생각해 테스트와 데이터 제약을 다른 브랜치로 떼어 놓으면 어느 시점에도 사용자 동작이 완전하지 않습니다.

안전한 협업은 명령의 개수가 아니라 변경이 놓인 상태와 다음 외부 행동의 권한을 구분하는 일입니다. 브랜치, 커밋, push, Pull Request, 리뷰, 승인은 각각 다음 단계의 입력일 뿐 자동으로 이어지는 완료 상태가 아닙니다.

## 한 문장 정의

**브랜치는 커밋을 가리키며 이동하는 작업선, 커밋은 선택한 변경과 부모 관계를 남긴 로컬 이력 단위, Pull Request는 한 브랜치의 변경을 다른 브랜치에 합치자고 원격 협업 서비스에서 제안하고 검토하는 단위입니다.**

## 공사 구역과 검수 요청에 비유하기

기준 브랜치를 사용 중인 본선, 작업 브랜치를 분리한 공사 구역, 커밋을 공정별 검사 기록, Pull Request를 본선에 반영하기 전 검수 요청에 비유할 수 있습니다. 공사 구역이 작고 검사 기록의 목적이 분명하면 검수자는 설계와 결과를 빠르게 대조할 수 있습니다.

### 비유가 깨지는 지점

Git 브랜치는 파일 전체를 복사한 별도 폴더가 아니라 커밋을 가리키는 참조입니다. 일반 작업 트리에서 브랜치를 바꾸면 같은 경로의 파일 상태가 달라지고, 여러 폴더가 필요하면 worktree 같은 별도 기능을 사용합니다. Pull Request도 Git 자체의 객체가 아니라 GitHub 같은 호스팅 서비스의 협업 기능이며, 승인 표시가 테스트·보안·제품 판단을 자동으로 보증하지 않습니다.

## 시스템에서 여섯 상태를 분리하세요

| 상태 | 일어난 일 | 직접 확인할 증거 | 아직 증명하지 못하는 것 |
|---|---|---|---|
| 작업 브랜치 | 로컬 참조가 별도 작업선을 가리킴 | 현재 브랜치·기준 커밋·작업 트리 | 커밋, 원격 공유, 리뷰 |
| 로컬 커밋 | 선택한 staged 변경이 로컬 이력에 기록됨 | commit ID·부모·staged diff·검증 결과 | push, PR, 승인, 병합 |
| 원격 공유 | push로 원격 브랜치가 갱신됨 | 정확한 remote·branch·원격 commit | PR 생성, 리뷰, 병합 |
| Pull Request | head와 base 사이의 변경 제안이 열림 | PR URL·head/base·diff·설명·검사 상태 | 승인, 병합, 배포 |
| 리뷰·승인 | 검토자가 의견·승인·변경 요청을 기록함 | 현재 diff에 대한 review 상태·미해결 대화·필수 검사 | 병합, 릴리스, 사용자 성공 |
| 병합 | 선택한 방법으로 변경이 base 브랜치 이력에 반영됨 | base의 commit·merge 방법·병합 시각 | 빌드, 배포, 운영 성공 |

GitHub의 review에는 comment, approve, request changes 같은 상태가 있지만 어떤 상태가 병합을 막는지는 저장소 ruleset이나 branch protection과 권한 설정에 따라 달라집니다. 승인 뒤 새 커밋이 추가되면 기존 승인이 유효한지도 설정과 현재 상태를 다시 확인해야 합니다.

## 브랜치에는 목표와 기준점을 함께 기록하세요

작업 브랜치를 만들기 전에 저장소 경계, 현재 브랜치와 작업 트리, 기준 브랜치가 가리키는 커밋을 확인합니다. 미커밋 사용자 변경이 있다면 새 작업과 섞기 전에 무엇을 보존할지 결정합니다.

브랜치 이름은 명령이 아니라 의사소통 표식입니다. `fix/duplicate-registration`처럼 목적을 드러낼 수 있지만 이름만으로 실제 범위나 안전성을 보증하지 않습니다. 다음 질문이 더 중요합니다.

- 어떤 사용자 결과 하나를 바꾸나요?
- 요구·코드·데이터·테스트·문서 중 함께 바뀌어야 하는 것은 무엇인가요?
- 기준 브랜치의 어느 커밋에서 시작했나요?
- 이 브랜치만 검증하고 되돌릴 수 있나요?
- 무관한 기존 변경이 작업 트리에 남아 있나요?

## upstream과 remote-tracking branch는 같은 브랜치가 아닙니다

`origin`은 흔한 remote 이름일 뿐 필수 이름이 아닙니다. `origin/main` 같은 remote-tracking branch는 마지막 fetch 때 관찰한 원격 브랜치 상태를 로컬에 기록한 참조이며, 네트워크의 원격 상태를 실시간으로 읽는 창이 아닙니다.

로컬 브랜치는 선택적으로 upstream을 가질 수 있습니다. upstream 설정은 인자 없는 pull이 어느 원격 브랜치를 통합할지, status가 어느 기준과 ahead·behind 관계를 보여 줄지 결정하는 데 쓰입니다. 로컬 브랜치와 upstream은 서로 다른 참조이고, tracking이라는 말이 파일 변경을 실시간 동기화한다는 뜻은 아닙니다.

```bash
git status --short --branch --untracked-files=all
git branch --show-current
git branch -vv
git remote -v
git log --oneline --decorate --graph -n 12
```

이 명령들은 대체로 읽기 전용 관찰에 유용하지만, 출력만으로 원격 최신성을 보증하지 않습니다. `fetch`는 네트워크에서 객체와 원격 추적 참조를 갱신하는 별도 행동이고, `pull`은 먼저 fetch한 뒤 현재 브랜치에 merge·rebase·fast-forward 같은 설정된 방식으로 통합합니다. 실행 전 네트워크 권한과 작업 트리 보존 상태, 통합 방식을 확인하세요.

## 커밋은 독립 검토 가능한 의미 단위입니다

좋은 커밋은 파일 수가 가장 적은 커밋이 아니라 한 가지 의도를 깨지지 않는 상태로 설명하고 검증할 수 있는 커밋입니다. 보통 다음을 함께 묶습니다.

- 하나의 관찰 가능한 동작 변경
- 그 동작을 확인하는 테스트 또는 직접 증거
- 필요한 데이터 제약·계약·문서 변경
- 실패했을 때 되돌릴 범위와 남는 외부 효과

무관한 리팩터링, 대규모 자동 포맷, 의존성 업그레이드, 개인 설정과 생성 산출물은 같은 의도가 아니라면 분리합니다. 반대로 데이터 제약만 먼저 바꿔 애플리케이션이 실행되지 않는 중간 상태나 테스트를 다른 커밋으로 미루는 방식은 작아 보여도 독립 검토 가능하지 않습니다.

커밋 전에는 전체 상태, unstaged diff, staged diff를 서로 다른 관찰값으로 읽습니다. untracked 파일은 일반 `git diff`에 나타나지 않을 수 있으므로 status와 파일 내용을 함께 확인합니다. 안전 점검에서는 `--untracked-files=all`을 명시합니다. 기본 status는 설정에 따라 새 파일을 숨기거나 디렉터리로 묶을 수 있으며, 이 옵션도 ignored 파일까지 보여 주지는 않습니다. 필요한 ignored 파일은 승인된 범위에서 별도로 확인합니다.

```bash
git status --short --untracked-files=all
git diff
git diff --staged
git diff HEAD
```

첫 커밋 전에는 비교할 HEAD 커밋이 없어 `git diff HEAD`가 실패합니다. 이때는 status·새 파일 내용·`git diff --staged`로 후보를 확인하며 기준 부재를 변경 없음으로 해석하지 않습니다.

기존 사용자 변경이 함께 있다면 경로나 변경 조각 단위로 stage 후보를 나누고, 안전하게 분리할 수 없는 파일은 커밋 후보에 넣지 않습니다. stage 뒤에는 staged diff와 의도적으로 남긴 unstaged·untracked 상태를 다시 확인합니다. 일부만 stage하거나 검증 뒤 수정했다면 커밋 후보인 index 스냅샷이 검증한 작업 트리와 다를 수 있습니다. 제외한 코드·설정·데이터 제약에 검증 결과가 의존하는지 대조하고, 필요하면 사용자 변경을 보존한 별도 환경에서 후보 스냅샷에 필요한 검증을 수행합니다. 작업 트리에만 있는 제약을 검증했다는 이유로 index의 후보도 성공했다고 보고하지 않습니다. 이를 위해 자동 stash나 사용자 변경 삭제를 하지 않습니다.

## Pull Request는 검토 계약입니다

Pull Request에는 변경 요약만이 아니라 검토자가 같은 판단을 재현할 정보를 남깁니다.

- 문제와 사용자 결과
- 범위와 명시적인 비목표
- head·base 브랜치와 기준 커밋
- 요구사항·설계·Issue와의 연결
- 테스트·정적 검사·빌드·브라우저·데이터 중 실제로 실행한 증거
- 실행하지 못했거나 권한이 없어 미검증인 범위
- 보안·데이터·호환성·운영 위험
- 롤아웃·중지·되돌리기 또는 수정 배포 조건
- 리뷰어가 집중해서 볼 질문

PR 생성은 GitHub의 협업 상태를 바꾸는 외부 쓰기입니다. 이미 존재하는 원격 브랜치에서도 PR을 만들 수 있으므로 PR 생성자가 push를 수행했다는 증거는 아니며, fork PR을 제안할 수 있다고 대상 저장소의 코드 push 권한이 있다는 뜻도 아닙니다. push 수행 여부·원격 브랜치 상태·권한은 별도 증거로 확인합니다. 로컬 변경 요청만 받았다면 설명 초안까지만 만들 수 있고, 승인 없이 push·PR 생성·리뷰 요청·GitHub PR 병합으로 넓히지 않습니다.

## 작은 브랜치와 PR은 사용자 결과로 나누세요

리뷰어의 주의력은 제한되어 있어 오래 사는 거대한 브랜치는 기준 브랜치와 멀어지고 충돌·회귀 범위가 커집니다. 작은 브랜치는 diff와 실패 원인을 좁혀 줍니다. 다만 한 파일·한 계층씩 자르는 가로 분할이 아니라 **독립적으로 검증할 수 있는 사용자 결과**가 기준입니다.

예를 들어 모임 웹앱의 “참가 기능 전체”를 한 PR로 묶기보다 공개 조회, 첫 참가, 중복 참가 거절, 자기 취소처럼 관찰 가능한 결과를 나눌 수 있습니다. 그중 중복 참가 거절은 서비스 검사만이 아니라 동시 요청에도 유지되는 데이터 제약과 테스트가 함께 있어야 완전한 한 조각입니다.

## 기준 브랜치와 최신화할 때의 판단

작업 중 기준 브랜치가 바뀌면 무조건 pull이나 rebase부터 실행하지 않습니다.

1. 현재 작업 트리와 로컬 커밋, upstream 관계를 기록합니다.
2. 네트워크와 원격 읽기가 허용되면 fetch로 원격 추적 참조를 갱신합니다.
3. 기준 브랜치와 내 브랜치의 고유 커밋·diff·충돌 가능성을 읽습니다.
4. 팀 정책과 공유 여부에 맞춰 merge, rebase 또는 새 기준에서의 재구성을 선택합니다.
5. 충돌이 나면 양쪽 요구를 읽고 의도를 통합합니다.
6. 전체 diff와 관련 회귀 검증을 다시 실행합니다.
7. 이미 받은 승인이 새 커밋 뒤에도 유효한지 확인합니다.

rebase는 커밋을 새 부모 위에 다시 만들므로 commit ID가 달라집니다. 이미 다른 사람이 사용하는 공유 이력을 임의로 재작성하지 않습니다. merge도 충돌을 자동으로 옳게 해결해 주지 않으며, 최신이라는 사실이 기능적으로 호환된다는 증거는 아닙니다.

## 개발 사례: 모임 참가 웹앱

### 중복 참가 방지를 하나의 검토 단위로 만든다면

W-03의 목표는 같은 사용자가 같은 모임에 활성 참가를 두 건 이상 만들지 못하게 하는 것입니다. 작업 브랜치에는 요구·참가 서비스·데이터 제약·정상 참가와 중복·동시 요청 테스트·관련 문서를 함께 포함하고, 무관한 UI 정리와 실제 계정·개인정보·운영 데이터는 제외합니다.

| 검토 경계 | 직접 증거 | 통과하지 못하면 |
|---|---|---|
| 범위 | W-03 수용 기준과 예상 변경 파일, 비목표 | 브랜치를 더 좁히거나 계약을 보완함 |
| 로컬 변경 | status·unstaged/staged diff·untracked 확인 | 기존 변경과 stage 후보를 다시 분리함 |
| 동작 | 첫 참가 성공, 중복·동시 요청 거절, 실패 뒤 활성 행 한 건 | 서비스·제약·트랜잭션 계약을 수정함 |
| 회귀 | 같은 사용자의 다른 모임 참가와 자기 취소 유지 | 관련 사용자 흐름까지 수정·재검증함 |
| 공유 | 정확한 remote·branch·원격 commit | 승인 없이 push하지 않고 로컬 상태로 남김 |
| PR·리뷰 | head/base, 현재 diff, 검사, 미해결 의견·승인 규칙 | 병합하지 않고 수정과 재검토를 반복함 |

로컬 커밋은 검토 가능한 기준점이지만 원격 공유·PR·승인·병합·배포를 증명하지 않습니다. 실제 외부 행동은 각각 대상과 권한을 다시 확인하고, 변경 커밋이 추가되면 stale approval 규칙과 검사를 다시 읽습니다.

## AI와 함께 작업하는 안전 순서

1. 저장소·브랜치·upstream·작업 트리와 보존할 변경을 읽기 전용으로 확인하게 합니다.
2. 한 사용자 결과, 비목표, 예상 파일, 수용 기준과 권한을 고정합니다.
3. 한 작업 브랜치에서 구현하고 실제 diff·테스트·빌드 결과를 받습니다.
4. 전체·unstaged·staged·untracked 상태를 직접 대조합니다.
5. 관련 변경만 로컬 커밋 후보로 선택하고 검증한 상태와 후보의 차이·의존성을 확인합니다. 필요한 후보 검증 뒤 커밋 메시지에 의도를 남깁니다.
6. 로컬 merge는 로컬 상태를, push·PR 생성·리뷰 요청·GitHub PR 병합·배포는 각각의 원격·외부 상태를 바꿉니다. 대상과 권한 및 직접 증거를 따로 판정합니다.
7. 리뷰 의견은 요구·코드·검증과 대조해 수용·부분 수용·기각한 뒤 재검증합니다.

승인 절차는 Git 명령의 내장 조건이 아니라 핸드북의 작업 안전 정책입니다. 명시적인 승인이나 상시 정책이 이미 있으면 그 범위에서 따르며, 로컬 통합 허용을 원격 쓰기 허용으로 확대하지 않습니다. 승인 범위를 벗어나는 행동만 별도로 확인합니다.

## 흔한 오해와 실패

### 브랜치를 만들면 변경이 안전하게 격리됐다고 봅니다

시작 전에 있던 미커밋 변경이 새 브랜치에도 남을 수 있습니다. 생성 전후 status와 diff를 비교하고 보존 대상을 먼저 확인하세요.

### `origin/main`을 실시간 원격 상태라고 봅니다

마지막 fetch 때 갱신된 로컬 참조일 수 있습니다. 원격 확인 권한과 시점을 기록하고, 원격을 읽지 않았다면 최신이라고 주장하지 마세요.

### 작은 PR을 파일 수로만 판단합니다

테스트와 데이터 제약을 빼면 한 파일이어도 불완전합니다. 사용자 결과·수용 기준·독립 검증·되돌리기 경계로 판단하세요.

### “update”, “fix” 같은 메시지만 남깁니다

나중에 이력만 보고 의도와 위험을 복원하기 어렵습니다. 한 줄에 변경 목적을, 필요한 경우 본문에 이유와 검증·호환성 정보를 남기세요.

### PR 설명이 AI의 긴 요약이면 충분하다고 봅니다

실제 diff와 검사·미검증 범위·위험·복구 질문이 없으면 검토 계약이 아닙니다. 요구와 직접 증거에 연결하세요.

### 승인 표시를 병합 가능성 전체로 봅니다

필수 검사, 최신화, 미해결 대화, CODEOWNERS, ruleset과 권한에 따라 결과가 달라질 수 있습니다. 현재 저장소 규칙과 현재 commit에 대한 승인을 확인하세요.

### 승인 전에 AI가 push·PR·병합합니다

로컬 구현 권한은 원격 쓰기나 다른 사람의 검토·기준 브랜치 변경 권한이 아닙니다. 각 외부 행동의 정확한 대상과 부작용을 확인하세요.

### 충돌을 한쪽 버전 선택으로 끝냅니다

문법 표시는 사라져도 요구가 사라질 수 있습니다. 양쪽 목적을 통합하고 diff와 사용자 흐름을 다시 검증하세요.

## 확인 체크리스트

- [ ] 저장소 경계·현재 브랜치·기준 commit·작업 트리를 확인했습니다.
- [ ] 보존할 기존 변경과 새 작업 범위를 분리했습니다.
- [ ] 로컬 브랜치·remote-tracking branch·upstream의 차이를 설명할 수 있습니다.
- [ ] 한 사용자 결과에 필요한 코드·데이터·테스트·문서를 함께 묶었습니다.
- [ ] 전체·unstaged·staged diff와 untracked 파일을 각각 확인했습니다.
- [ ] 커밋 후보 스냅샷과 검증한 상태의 차이·의존성을 확인하고 필요한 후보 검증을 수행했습니다.
- [ ] PR에 범위·비목표·실행 증거·미검증 범위·위험·복구 조건이 있습니다.
- [ ] 기준 브랜치 최신화 뒤 충돌 해결과 전체 회귀를 다시 확인했습니다.
- [ ] 현재 commit의 리뷰·검사·저장소 규칙을 확인했습니다.
- [ ] commit·push·PR·승인·merge·build·deploy를 서로 다른 상태로 보고합니다.

## 짧은 연습

“사용자 프로필 편집” 작업을 세 개 이하의 사용자 결과로 나누세요. 각 조각에 함께 바뀌어야 할 코드·데이터·테스트·문서, 기준 브랜치 최신화 시 충돌 위험, 로컬 커밋부터 병합까지 단계별 직접 증거와 승인자를 적으세요. 파일 수가 적지만 실행 불가능한 조각이 있다면 다시 합치거나 경계를 바꾸세요.
