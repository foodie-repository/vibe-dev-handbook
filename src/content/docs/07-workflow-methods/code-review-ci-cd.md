## 왜 필요한가

AI가 코드를 만들고 테스트가 초록색이 되면 변경이 안전해 보입니다. 그러나 자동 검사는 작성된 규칙만 실행하고, 코드 리뷰는 사람이 의도와 맥락을 판단하며, 배포 게이트는 사용자에게 영향을 줄 권한을 통제합니다. 이 책임을 한 덩어리의 “CI/CD 성공”으로 부르면 테스트가 실패했는데도 병합하거나, 리뷰 승인만으로 운영 배포까지 안전하다고 오해하기 쉽습니다.

이 장의 목표는 특정 서비스의 버튼을 외우는 것이 아닙니다. 변경이 어느 게이트를 통과했고, 누가 무엇을 확인했으며, 아직 어떤 위험이 남았는지를 증거로 설명하는 것입니다.

## 한 문장 정의

코드 리뷰는 저자 외의 사람이 변경의 의도·설계·정확성·위험을 검토하는 활동이고, 지속적 통합(Continuous Integration, CI)은 공유 코드에 자주 통합된 변경을 자동 빌드와 테스트로 확인하는 규율이며, 지속적 전달(Continuous Delivery)은 검증된 결과를 언제든 배포할 수 있는 상태로 유지하고, 지속적 배포(Continuous Deployment)는 정해진 자동 게이트를 통과한 변경을 운영 환경까지 자동으로 내보내는 방식입니다.

`CI/CD`라는 묶음 표현을 쓰더라도 네 책임을 다시 나눠야 합니다.

| 책임 | 핵심 질문 | 주된 판정 주체 | 대표 증거 |
|---|---|---|---|
| 코드 리뷰 | 이 변경의 의도와 구현이 현재 시스템에 적합한가? | 사람 리뷰어 | 변경 diff, 리뷰 의견, 해결 기록 |
| 승인 | 이 변경을 다음 단계로 보내도 되는가? | 권한 있는 사람 또는 정책 | 승인자, 시각, 대상 커밋, 예외 사유 |
| CI | 공유 코드와 합쳤을 때 정해 둔 자동 검증을 통과하는가? | 자동화된 작업 | 커밋에 연결된 빌드·검사·테스트 결과와 로그 |
| 지속적 전달 | 같은 아티팩트를 승인하면 배포할 수 있는가? | 파이프라인과 릴리스 결정권자 | 아티팩트 식별자, 환경별 검사, 배포 준비 상태 |
| 지속적 배포 | 자동 게이트를 통과한 변경을 운영에 자동 반영해도 되는가? | 사전에 승인된 정책과 자동화 | 배포 이력, 대상 환경·버전, 운영 확인과 복구 기록 |

## 공항 보안 검색대 비유와 한계

변경이 운영 환경으로 가는 흐름은 공항의 여러 검색대와 비슷합니다. 신분 확인, 수하물 검사, 탑승권 확인이 서로 다른 위험을 맡듯 코드 리뷰, CI, 배포 승인도 서로 다른 질문을 맡습니다. 한 검색대를 통과했다고 나머지 검사가 끝난 것은 아닙니다.

이 비유는 **각 게이트의 책임과 증거가 다르다**는 점에서만 맞습니다. 소프트웨어에서는 같은 변경을 다시 빌드하거나 자동 배포할 수 있고, 위험에 따라 게이트 순서를 바꾸거나 일부를 병렬로 실행합니다. 또한 사람의 판단과 자동 검사는 독립된 검색대처럼 완전히 분리되지 않고 서로의 결과를 입력으로 사용합니다. 따라서 이 비유로 고정된 파이프라인이나 무조건 많은 승인을 정당화해서는 안 됩니다.

## 전체 시스템에서의 위치

변경은 작업 트리에서 시작해 커밋과 Pull Request(PR) 같은 검토 묶음이 됩니다. 리뷰와 CI 결과가 병합 게이트의 입력이 되고, 병합된 커밋에서 추적 가능한 아티팩트를 만듭니다. 그 아티팩트가 환경별 검증과 배포 승인을 거쳐 운영에 반영되며, 마지막에는 실제 사용자 흐름과 운영 신호로 결과를 확인합니다.

```text
문제·수용 기준
  → 변경 diff와 로컬 검증
  → 사람 코드 리뷰
  → CI 상태 검사
  → 병합 결정
  → 식별 가능한 아티팩트
  → 배포 환경 검사와 필요 승인
  → 운영 반영
  → 사용자 흐름·로그·지표 확인
  → 유지 / 롤백 / 롤포워드
```

이 흐름은 선형 완료 목록이 아닙니다. 리뷰가 요구 누락을 찾으면 문제 정의로, CI가 회귀를 찾으면 구현으로, 운영 확인이 실패하면 완화와 원인 분석으로 돌아갑니다.

## 코드 리뷰와 승인은 같은 말이 아닙니다

코드 리뷰는 질문하고 읽고 검증하는 **활동**입니다. 승인은 그 결과를 바탕으로 다음 상태 전환을 허용하는 **결정**입니다. 리뷰 의견이 하나 달렸다는 사실, AI가 diff를 설명했다는 사실, 리뷰어가 일부 파일만 읽었다는 사실은 승인과 같지 않습니다. 반대로 승인 표시가 있어도 어떤 커밋을 어떤 범위로 검토했는지 연결되지 않으면 증거가 약합니다.

사람 리뷰는 자동화가 놓치기 쉬운 다음 질문을 맡습니다.

- 요구와 구현이 같은 문제를 풀고 있나요?
- 권한·개인정보·데이터 보존·접근성·운영 영향이 빠지지 않았나요?
- 테스트가 실제로 깨진 동작을 실패시키며, 잘못된 오라클을 보호하지 않나요?
- 변경 범위와 복잡성이 위험에 비해 적절한가요?
- 실패했을 때 관찰하고 복구할 경로가 있나요?

자동 검사는 리뷰어의 기억을 대신하는 것이 아니라 반복 가능한 사실을 빠르게 제공합니다. 리뷰어는 “검사 통과”를 다시 실행할 필요 없이 그 검사 범위가 현재 위험에 충분한지 판단할 수 있습니다.

## CI는 초록 체크를 만드는 서비스가 아닙니다

CI의 핵심은 팀원이 변경을 공유 코드에 자주 통합하고, 각 통합을 자동 빌드와 테스트로 빠르게 검증하며, 깨진 공유 상태를 즉시 복구하는 규율입니다. 브랜치에서 자동 검사를 한 번 실행했다는 사실만으로 팀이 지속적으로 통합하고 있다고 단정할 수 없습니다.

CI 결과를 증거로 쓰려면 최소한 다음 연결이 보여야 합니다.

1. **대상**: 어떤 커밋과 변경 묶음을 검사했는가?
2. **환경**: 런타임·의존성·설정·운영체제가 무엇인가?
3. **범위**: 정적 검사, 단위·통합 테스트, 빌드 중 무엇을 실행했는가?
4. **결과**: 실제 실행 수, 실패 수, 종료 코드와 로그는 무엇인가?
5. **재현성**: 잠금 파일과 명령이 기록돼 다시 실행할 수 있는가?
6. **후속 상태**: 실패 뒤 공유 브랜치를 복구했는가, 실패를 예외 처리했는가?

실제 실행 수·대상·환경·로그를 확인한 검사 통과는 그 범위의 좁은 증거입니다. 서비스의 초록 표시나 병합 허용만으로 실제 검사 실행을 단정하지 않습니다. GitHub에서는 `skipped`나 `neutral`도 필수 상태 검사 조건을 충족할 수 있으므로, 실행 0건·건너뜀·조건식을 로그와 함께 확인해야 합니다. 실행되지 않은 테스트, 실제 사용자 목적, 운영 데이터 마이그레이션, 접근성 전체, 배포 결과까지 증명하지 않습니다.

## 지속적 전달과 지속적 배포를 구분합니다

지속적 전달은 최신 검증 결과를 운영에 내보낼 수 있는 상태로 유지하되, 실제 릴리스 시점은 사업·안전·법적 판단에 따라 사람이 결정할 수 있습니다. 지속적 배포는 자동 게이트를 통과한 변경을 운영 환경까지 자동으로 반영합니다. 두 방식 모두 배포 자동화를 사용할 수 있으므로 “자동 스크립트가 있다”만으로 구분할 수 없습니다. 마지막 운영 반영에 별도 릴리스 결정이 필요한지를 확인해야 합니다.

배포 승인도 코드 리뷰의 재실행이 아닙니다. 보통 승인자는 다음을 봅니다.

- 지금 이 환경에 이 아티팩트를 내보낼 권한과 변경 시간이 적절한가?
- 데이터 변경, 외부 의존성, 규정 또는 사용자 영향에 추가 확인이 필요한가?
- 관측 기준과 중단 조건, 롤백 또는 롤포워드 경로가 준비됐는가?
- 승인 대상이 리뷰·CI를 통과한 바로 그 커밋과 아티팩트인가?

## 실패한 검사와 우회는 새로운 위험 기록입니다

필수 검사가 실패했으면 기본 행동은 병합이나 배포를 멈추고 원인을 확인하는 것입니다. 단순 재실행으로 통과할 때까지 누르는 행동은 flaky test, 공유 자원 충돌, 실제 결함을 구분하지 못합니다. 먼저 같은 커밋과 환경에서 실패가 재현되는지, 실패가 제품 코드·테스트·인프라 중 어디에서 왔는지 기록합니다.

긴급한 완화 때문에 우회가 정말 필요할 수 있습니다. 하지만 우회는 실패가 사라졌다는 뜻이 아니라 **통제를 잠시 건너뛴 별도의 위험 결정**입니다. 다음 항목이 없으면 조용한 예외가 됩니다.

- 우회한 검사·리뷰·배포 보호 규칙과 정확한 대상
- 사용자·데이터·보안 영향과 우회가 더 안전하다고 판단한 이유
- 승인 권한자와 시각
- 제한된 배포 범위와 관찰할 신호
- 되돌리기 또는 후속 수정 방법
- 만료 시점과 다시 원래 보호 규칙을 적용할 담당자

브랜치 보호와 배포 환경 보호는 이런 규칙을 기술적으로 강제할 수 있습니다. 다만 GitHub 같은 제품에서도 관리자 우회, 특정 역할의 bypass, 필수 리뷰·상태 검사·배포 조건은 저장소와 플랜 설정에 따라 달라집니다. “보호 브랜치”라는 이름만 보지 말고 현재 규칙과 우회 권한을 직접 확인해야 합니다.

## 반복 사례: 모임 참가 변경을 전달하기

모임 참가 기능에서 “같은 사용자는 한 모임에 한 번만 참가하고, 정원을 넘지 않는다”는 변경을 예로 들겠습니다.

### 1. 변경과 리뷰

PR은 문제, 수용 기준, 스키마·트랜잭션 변경, 정상·중복·정원 마감·동시 요청 테스트, 배포 위험을 설명합니다. 리뷰어는 버튼 모양뿐 아니라 서버가 권위 상태에서 중복과 정원을 함께 판정하는지, 실패 응답 뒤 화면이 잘못 성공으로 남지 않는지 확인합니다.

### 2. CI와 병합 게이트

CI는 정적 검사, 단위 테스트, 실제 데이터베이스 경계를 포함한 통합 테스트, 빌드를 실행합니다. 동시 요청 테스트가 실패하면 병합은 멈춥니다. 테스트를 삭제해 초록색으로 만드는 대신 원래 실패한 커밋·환경·재현 조건을 보존합니다. 결함을 수정한 뒤에는 새 커밋 또는 미커밋 diff까지 포함한 정확한 작업 트리 상태를 기록하고 같은 불변식과 오라클로 다시 확인합니다.

### 3. 전달과 배포 승인

파이프라인은 검증한 커밋에서 아티팩트를 만들고 스테이징 환경에 배포합니다. 스키마 변경이 이전 애플리케이션 버전과 호환되지 않거나 복구 경로가 없다면 배포 승인자는 보류할 수 있습니다. 코드 리뷰 승인이 있다는 사실은 이 운영 위험을 자동 승인하지 않습니다.

### 4. 운영 확인과 복구

운영 반영 뒤에는 승인된 범위의 안전한 읽기 확인을 우선합니다. 정상 참가·중복 거절·정원 마감·자기 취소의 쓰기 시험은 별도로 승인된 전용 모임·계정·가상 데이터에서 영향 범위·중지 기준·정리 절차를 정한 경우에만 수행합니다. 배포 승인이나 읽기 권한이 쓰기 시험 권한을 뜻하지 않으며, 조건이 없으면 해당 흐름은 미검증으로 남깁니다. 정원 경쟁이나 장애 주입을 일반 사용자의 운영 데이터에서 시험하지 않습니다.

허용된 확인 범위에서 오류율과 데이터 불변식을 관찰하고 오류가 증가하면 사용자 영향부터 줄입니다. 이전 아티팩트로 돌리는 롤백이 새 스키마와 호환되지 않으면, 호환 수정으로 롤포워드하거나 기능 플래그를 꺼야 할 수 있습니다. “배포 작업 성공”은 이 확인 전까지 사용자 성공의 증거가 아닙니다.

## 판단 규칙

### 규칙 1. 게이트마다 한 문장의 질문을 붙입니다

같은 테스트를 여러 단계에서 반복하기보다 코드 리뷰, CI, 병합, 배포 승인, 운영 확인이 각각 어떤 위험을 맡는지 씁니다. 답할 질문이 없는 게이트는 관성적인 대기 단계일 수 있습니다.

### 규칙 2. 증거를 대상 커밋과 아티팩트에 연결합니다

리뷰 뒤 코드가 바뀌었거나 CI 뒤 다시 빌드했다면 이전 증거가 현재 대상에 그대로 적용되는지 확인합니다. 배포할 아티팩트를 승인 뒤 다시 만들지 않고, 가능하면 검증한 동일 아티팩트를 환경 사이에서 승격합니다.

### 규칙 3. 자동화와 사람 판단의 빈틈을 서로 채웁니다

반복 가능하고 명확한 규칙은 자동화하고, 의도·맥락·트레이드오프·예외 승인은 사람이 맡습니다. 자동화가 사람을 없애거나, 사람이 실패한 자동 검사를 근거 없이 덮는 구조를 만들지 않습니다.

### 규칙 4. 보호 규칙보다 우회 경로를 먼저 감사합니다

필수 검사 이름만 보지 말고 누가 어떤 조건에서 건너뛸 수 있는지, 우회가 기록되고 만료되는지 확인합니다. 보호 규칙이 강해 보여도 넓은 bypass 권한이 있으면 실제 통제는 약할 수 있습니다.

### 규칙 5. 배포 성공 뒤 사용자 결과를 확인합니다

파이프라인 종료 코드, 배포 URL, 컨테이너 실행은 전달 증거입니다. 핵심 사용자 흐름, 권위 데이터, 오류·지연 신호와 복구 가능성은 별도로 확인합니다.

## 흔한 오해와 실패

- **“리뷰 의견이 있으니 리뷰 완료다”**: 미해결 의견, 대상 커밋 변경, 승인 권한을 확인하지 않습니다.
- **“CI가 초록색이면 안전하다”**: 검사하지 않은 요구·보안·데이터·운영 위험을 초록 체크에 포함시킵니다.
- **“CD는 곧 자동 운영 배포다”**: 지속적 전달과 지속적 배포를 구분하지 않아 사람 승인과 실제 반영 상태를 혼동합니다.
- **“관리자는 보호 규칙을 항상 지킨다”**: 제품 설정의 bypass 권한과 예외 기록을 확인하지 않습니다.
- **“실패한 검사는 다시 돌리면 된다”**: 불안정성의 원인과 실패 증거를 지우고 우연한 통과를 채택합니다.
- **“배포 승인자는 코드 전체를 다시 읽어야 한다”**: 코드 리뷰와 배포 위험 판단을 중복시켜 중요한 환경·데이터·복구 질문을 놓칩니다.
- **“파이프라인 성공이 릴리스 성공이다”**: 운영의 실제 사용자 흐름과 데이터 상태를 확인하지 않습니다.

## AI와 작업할 때의 요청 계약

```text wrap
이 변경의 코드 리뷰·CI·전달·배포 게이트를 설계해 주세요.

- 문제와 수용 기준:
- 변경한 파일과 위험한 경계:
- 사람 리뷰가 판단할 항목:
- 자동화할 검사와 각 검사의 실패 의미:
- 필수 검사 실패 시 기본 행동:
- 우회가 필요할 때 승인자·만료·추적 방식:
- 배포할 커밋과 아티팩트 식별 방법:
- 배포 승인에서 확인할 환경·데이터·보안 위험:
- 운영 확인 흐름과 중단 기준:
- 롤백 또는 롤포워드 조건:
- 아직 검증하지 못한 범위:

설명만 하지 말고 대상 커밋, 실제 명령, 종료 코드, 테스트 수, 아티팩트와 환경 식별자, 운영 확인 결과가 서로 연결되는 표를 작성해 주세요. 자동 검사 통과를 사람 승인이나 사용자 성공으로 확대하지 마세요.
```

AI가 “모든 테스트 통과”, “배포 준비 완료”라고 쓰면 테스트 목록과 실행 수, 대상 커밋, 배포 대상, 사람이 승인해야 할 잔여 위험을 다시 물어야 합니다.

## 확인 체크리스트

- [ ] 리뷰 활동과 승인 결정을 구분했나요?
- [ ] CI, 지속적 전달, 지속적 배포를 실제 운영 반영 방식으로 구분했나요?
- [ ] 리뷰와 자동 검사의 담당 위험이 겹치거나 비어 있지 않나요?
- [ ] 필수 검사의 대상 커밋·환경·명령·실행 결과를 확인했나요?
- [ ] 실패한 검사에 원인 분류와 복구 결과가 남았나요?
- [ ] 브랜치 보호와 배포 보호의 bypass 권한을 확인했나요?
- [ ] 우회에 승인자·사유·범위·만료·후속 작업이 있나요?
- [ ] 검증한 커밋과 배포 아티팩트가 연결되나요?
- [ ] 배포 성공과 운영의 사용자·데이터 성공을 따로 확인했나요?
- [ ] 롤백과 롤포워드 중 현재 변경에 가능한 경로를 시험했나요?

## 짧은 연습

현재 저장소의 변경 하나를 골라 `코드 리뷰 / 승인 / CI / 병합 / 배포 승인 / 운영 확인` 여섯 행의 표를 만드세요. 각 행에 질문, 판정 주체, 대상 커밋 또는 아티팩트, 통과 증거, 실패 때 행동을 씁니다. 그다음 CI 작업 하나를 의도적으로 실패시켰다고 가정하고, 재실행·수정·우회 중 어떤 행동을 선택할지와 그 증거를 설명해 보세요.

- [GitHub 보호 브랜치 안내](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)와 [배포 환경 안내](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments)는 2026-08-13 현재 필수 리뷰·상태 검사·배포 보호·우회 설정의 제품 범위를 확인하는 데 사용했습니다. 플랜·저장소·역할별 설정을 Git 자체나 모든 CI/CD 제품의 보편 동작으로 확대하지 않습니다.

## 기억할 문장

**자동 검사는 반복 가능한 사실을 제공하고, 사람은 그 사실이 현재 위험에 충분한지 판단하며, 배포 게이트는 사용자에게 영향을 줄 권한을 통제합니다. 어느 하나의 초록 표시도 나머지 책임을 대신하지 않습니다.**
