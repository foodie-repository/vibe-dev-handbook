## 왜 필요한가

“회원 기능을 만들어 주세요” 같은 큰 요청을 AI에게 한 번에 주면 화면, API, 데이터, 권한, 테스트와 배포가 한 변경에 섞입니다. 결과가 늦게 나오고, 어느 요구가 틀렸는지 찾기 어려우며, 실패했을 때 무엇만 되돌려야 하는지도 불분명해집니다.

반대로 작업을 파일 하나씩 잘게 나눈다고 점진적 전달이 되는 것도 아닙니다. 데이터베이스 파일만 먼저 20개 만들고, API를 모두 만든 뒤, 마지막에 화면을 붙이면 각 작업은 작아 보여도 사용자 흐름은 끝까지 통합되지 않습니다. 점진적 전달은 파일 수가 아니라 **작은 사용자 결과를 실제 경계 끝까지 연결하고 그 결과에서 학습하는 방식**입니다.

## 한 문장 정의

점진적 전달은 큰 목표를 각각 독립적인 수용 기준, 끝에서 끝까지 이어진 구현, 피드백 지점, 안전한 공개 조건과 복구 경로를 가진 작은 수직 조각으로 나누어 반복적으로 검증·전달하는 방식입니다.

## 샌드위치 한입 비유와 한계

수직 조각은 샌드위치를 위 빵, 채소, 속재료로 따로 먹는 대신 한입에 모든 층이 조금씩 들어오게 자르는 것과 비슷합니다. 한입만 먹어도 전체 맛의 조화를 시험할 수 있듯, 작은 사용자 흐름이 화면·규칙·데이터 경계를 통과하면 통합 위험을 일찍 볼 수 있습니다.

이 비유는 **작은 단위가 여러 계층을 관통한다**는 점에서만 맞습니다. 소프트웨어 조각은 크기가 같은 물리 조각이 아니고, 인가·동시성·데이터 마이그레이션 같은 위험은 한입처럼 깔끔하게 분리되지 않을 수 있습니다. 또한 아직 공개하지 않은 내부 기반 작업도 필요합니다. 따라서 모든 작업에 사용자 화면을 억지로 붙이거나, 큰 위험을 작은 티켓으로 잘랐다는 이유만으로 독립적이라고 주장해서는 안 됩니다.

## 수평 분할과 수직 조각을 구분합니다

다음은 모임 참가 기능을 두 방식으로 나눈 예입니다.

| 구분 | 작업 예 | 완료 때 관찰 가능한 결과 | 늦게 발견하는 위험 |
|---|---|---|---|
| 수평 분할 | 모든 테이블 작성 → 모든 API 작성 → 모든 화면 작성 | 각 계층 내부 산출물 | 화면과 API 계약, 인가, 오류 상태, 실제 데이터 통합 |
| 수직 조각 | 모임 목록 조회 → 참가 신청 → 자기 참가 취소 | 조각마다 사용자 또는 시스템 결과 | 남은 큰 흐름의 위험은 있지만 각 통합 경계는 일찍 확인 |

수평 작업이 항상 나쁜 것은 아닙니다. 공통 마이그레이션 도구, 관측 기반, 접근성 토큰처럼 여러 조각이 필요로 하는 기반 작업이 있을 수 있습니다. 다만 기반 작업은 “사용자 가치 완료”로 세지 말고 다음 수직 조각을 가능하게 하는 의존성으로 표시해야 합니다.

## 좋은 수직 조각의 다섯 조건

### 1. 관찰 가능한 한 결과가 있습니다

“API 파일 수정”이 아니라 “인증한 사용자가 모집 중인 모임에 참가를 요청하면 참가 확정 또는 구체적인 거절 결과를 받는다”처럼 씁니다. 결과는 사용자 화면일 수도 있고, 다른 시스템이 읽는 계약이나 운영자가 확인하는 안전한 상태일 수도 있습니다.

### 2. 독립적인 수용 기준이 있습니다

수용 기준은 구현 방법이 아니라 통과·실패를 판정할 조건입니다. 한 조각이 다른 모든 조각이 끝나야만 판정된다면 아직 너무 크거나 순서가 잘못됐을 수 있습니다.

```text wrap
조각: 모집 중인 모임에 한 번 참가하기

- 인증한 사용자가 모집 중이고 정원이 남은 모임에 참가하면 서버 권위 상태에 참가 관계가 한 건 생긴다.
- 같은 사용자의 같은 모임 중복 요청은 두 번째 참가 관계를 만들지 않는다.
- 정원이 찬 경우 참가를 거절하고 화면은 성공으로 남지 않는다.
- 응답을 잃어 결과가 불명확하면 참가 상태를 다시 조회해 판정할 수 있다.
```

### 3. 필요한 경계를 끝까지 연결합니다

화면 버튼만 만들거나 데이터 행만 넣는 것이 아니라, 현재 조각에 필요한 입력·서버 규칙·권위 데이터·응답·화면 상태·테스트와 관측을 연결합니다. 모든 계층을 많이 수정할 필요는 없지만 현재 결과에 필요한 경계가 빠지면 안 됩니다.

### 4. 안전하게 통합하거나 비활성화할 수 있습니다

미완성 후속 기능이 없어도 현재 조각이 기존 동작을 깨뜨리지 않아야 합니다. 공개하면 안 되는 코드가 먼저 합쳐져야 한다면 feature flag 같은 공개 제어, 호환 가능한 스키마 전환, 접근 불가능한 내부 경로를 설계합니다.

### 5. 실패 뒤 선택할 경로가 있습니다

이전 아티팩트로 되돌릴지, 기능을 끌지, 수정 변경을 앞으로 적용할지 정합니다. 특히 데이터가 새 형식으로 기록됐거나 외부 알림이 나간 뒤에는 코드 롤백만으로 원상 복구되지 않을 수 있습니다.

## 수용 기준은 조각의 경계선입니다

수용 기준이 없으면 “작게 만들었다”는 말이 파일·커밋 크기 이야기로 흐릅니다. 조각을 시작하기 전에 다음 네 종류를 최소한 확인합니다.

- **정상 결과**: 누가 어떤 조건에서 무엇을 할 수 있는가?
- **거절 결과**: 권한 없음, 잘못된 입력, 충돌, 상태 불일치를 어떻게 판정하는가?
- **결과 불명**: 시간 초과나 응답 손실 뒤 실제 처리 여부를 어떻게 다시 확인하는가?
- **회귀 경계**: 기존의 어떤 흐름과 데이터가 계속 유지돼야 하는가?

테스트 케이스는 수용 기준을 확인하는 여러 수단 중 하나입니다. 자동 테스트 통과만으로 문구 이해, 접근성, 운영 복구, 사용자 목적까지 모두 수용됐다고 단정하지 않습니다.

## feature flag는 배포와 공개를 분리합니다

feature flag 또는 feature toggle은 코드가 배포된 상태와 사용자가 기능을 사용할 수 있는 상태를 분리하는 조건입니다. 다음 상황에서 유용할 수 있습니다.

- 여러 조각을 공유 코드에 자주 통합하되 완성 전에는 일반 사용자에게 숨길 때
- 작은 사용자 집단이나 내부 계정에 먼저 공개해 신호를 관찰할 때
- 장애가 발생했을 때 새 기능 경로를 빠르게 끌 때

하지만 플래그 자체가 안전을 보장하지 않습니다.

1. 켜짐과 꺼짐 상태를 모두 시험해야 합니다.
2. 서버 권한 검사를 화면 플래그로 대신하면 안 됩니다.
3. 플래그를 꺼도 이미 기록한 데이터·보낸 메시지·변경한 외부 상태는 남을 수 있습니다.
4. 오래된 플래그와 분기 조합은 테스트 공간과 운영 복잡성을 늘리므로 소유자·만료·제거 조건이 필요합니다.

## 피드백은 다음 조각을 바꾸기 위한 입력입니다

작은 조각을 자주 배포하는 목적은 완료 개수를 늘리는 것이 아니라 틀린 가정을 빨리 발견하는 데 있습니다. 각 조각은 다음 피드백 중 무엇을 받을지 미리 정합니다.

| 피드백 | 확인 질문 | 다음 행동 예 |
|---|---|---|
| 사용자 | 결과와 오류를 이해하고 목적을 달성하는가? | 문구·흐름·수용 기준 수정 |
| 제품 | 이 조각이 실제 문제를 줄이는가? | 우선순위 변경 또는 기능 중단 |
| 기술 | 경계·데이터·성능·보안 가정이 맞는가? | 설계 수정, 다음 위험 조각 선행 |
| 운영 | 오류·지연·복구 비용이 허용 범위인가? | 공개 범위 축소, 관측·복구 보강 |

“좋아 보인다”는 피드백만 모으지 않습니다. 사용한 버전, 사용자 집단, 관찰 기간, 성공·실패 기준과 예상 밖 결과를 기록해야 다음 결정의 증거가 됩니다.

## 반복 사례: 모임 참가 기능을 다섯 조각으로 나누기

### 조각 1. 공개 모임 목록과 상세 조회

- 결과: 사용자가 모집 상태·정원·일정을 확인합니다.
- 수용: 없음·정상·모집 마감 상태를 구분하고 권위 데이터를 표시합니다.
- 피드백: 정보가 참가 판단에 충분한지 확인합니다.
- 복구: 읽기 흐름이므로 이전 화면·API 아티팩트로 되돌리고 데이터 스키마 호환성을 확인합니다.

### 조각 2. 참가 신청과 최소 결과 확인

- 결과: 인증한 사용자가 모집 중이고 정원이 남은 모임에 참가하며, 응답을 잃어도 자신의 관계와 모임 상태를 확인할 최소 조회 경로를 함께 제공합니다.
- 수용: 정상·미인증·중복·정원 마감·동시 요청과 응답 유실·조회 실패를 구분합니다. 조회 실패나 이전 요청의 종결·안전한 재시도 조건을 판정할 수 없는 경우에는 `결과 불명`을 유지하고 새 쓰기를 보류합니다. 현재 참가 상태만으로 특정 요청의 처리 결과를 단정하지 않습니다.
- 피드백: 거절 이유와 결과 불명 복구가 이해되는지 봅니다.
- 복구: 신규 참가 경로를 플래그로 끌 수 있지만 이미 확정된 참가 관계는 삭제하지 않습니다.
- 통합·공개 조건: 최소 자기 조회와 요청 결과·재시도 계약, 중복·정원 경쟁 판정, 오류·거절·불명 신호와 중지 담당자를 이 조각에서 확인합니다. 빠진 조건이 있으면 독립 수용·공개 완료로 세지 않으며, 조각 3이나 5가 나중에 보완할 것이라고 가정하지 않습니다.

### 조각 3. 자신의 참가 상태 조회 경험 확장

- 결과: 조각 2에서 검증한 최소 자기 조회를 재사용해 사용자가 필요할 때 현재 참가 상태와 확인 중인 상태를 더 쉽게 찾게 합니다. 최초 복구 경로를 여기까지 미루는 것이 아닙니다.
- 수용: 사용자·모임별 권위 상태와 이전 요청의 처리 결과를 구분하고, 새 화면에서도 안전한 재시도 조건을 확인하기 전에는 새 쓰기를 보류합니다.
- 피드백: 재시도 전에 상태 조회가 중복 행동을 줄이는지 봅니다.
- 복구: 조회 경로 장애 때 잘못된 성공·실패를 만들지 않고 `결과 불명`을 유지합니다.

### 조각 4. 자기 참가 취소

- 결과: 참가자가 자신의 `confirmed` 관계를 `cancelled`로 바꾸며 행과 이력을 보존합니다.
- 수용: 타인 취소를 거절하고, 반복 자기 취소는 현재 `cancelled`를 반환하되 추가 인원 감소나 취소 이력을 만들지 않는지 확인합니다. 재참가는 모임이 `open`이고 정원 여유와 활성 고유성 조건을 만족할 때만 허용합니다.
- 피드백: 취소 뒤 목록·상세·내 상태가 일관되게 보이는지 봅니다.
- 복구: 코드 롤백만으로 취소 상태를 다시 `confirmed`로 만들지 않습니다. 보존된 상태·이력을 기준으로 허용된 재참가 업무 조건을 다시 판정합니다.

### 조각 5. 공개 범위 확대와 운영 인수

- 결과: 각 앞선 조각의 기본 관측·중지·복구 조건을 재사용하고, 승인된 내부 집단에서 공개 범위를 단계적으로 넓혀 참가 성공률·거절 사유·오류를 관찰합니다. 기본 안전장치를 처음 도입하는 조각이 아닙니다.
- 수용: 플래그 대상, 신호의 분자·분모, 중단 기준, 담당자와 만료를 기록합니다.
- 피드백: 일반 공개 전 병목·혼란·데이터 불변식 문제를 찾습니다.
- 복구: 중단 기준을 넘으면 플래그를 끄고 현재 권위 데이터를 검증한 뒤 수정 방향을 정합니다.

이 순서는 사례의 한 선택일 뿐 표준이 아닙니다. 위험이 권한이나 동시성에 집중돼 있다면 부정 테스트와 데이터 불변식의 가장 작은 조각을 먼저 만들 수 있습니다.

## 롤백과 롤포워드를 조각마다 판단합니다

**롤백**은 이전 코드·설정·라우팅으로 되돌리는 방향이고, **롤포워드**는 추가 수정으로 안전한 새 상태로 전진하는 방향입니다. 어떤 쪽이 더 안전한지는 변경 유형에 따라 다릅니다.

| 변경 | 롤백 가능성 | 롤포워드가 필요한 신호 |
|---|---|---|
| 화면 문구 | 비교적 높음 | 이전 문구도 요구를 충족하지 않음 |
| 호환 API 추가 | 높을 수 있음 | 이미 새 클라이언트가 의존함 |
| 파괴적 스키마 변경 | 낮을 수 있음 | 새 형식 데이터가 기록돼 역변환이 손실을 만듦 |
| 외부 메시지 발송 | 코드만 되돌려도 부작용은 남음 | 정정 메시지·보상 작업이 필요함 |
| 보안 결함 수정 | 취약한 버전으로 복귀하면 위험 | 안전한 수정 변경을 빠르게 적용해야 함 |

복구 계획에는 트리거, 권한자, 명령이나 절차, 데이터 확인, 사용자 영향, 완료 오라클이 있어야 합니다. “Git revert 가능”은 운영 복구 전체의 증거가 아닙니다.

## 가짜 점진성을 찾는 질문

### 파일 수로만 자른 작업

`schema.sql 수정`, `api.ts 수정`, `page.tsx 수정`은 변경 위치이지 사용자 결과가 아닙니다. 세 파일을 하나씩 커밋해도 각 커밋을 독립적으로 수용할 수 없다면 수직 조각이 아닙니다.

### 마지막까지 통합하지 않는 작업

화면 mock, 가짜 API, 실제 데이터베이스를 각자 완성했지만 마지막 조각에서 처음 연결하면 통합 위험을 미뤘습니다. 대역은 빠른 학습에 쓸 수 있지만 실제 경계를 확인할 조각과 시점을 정해야 합니다.

### 기능 이름만 더 작게 바꾼 작업

“회원 기능”을 “회원 백엔드”와 “회원 프런트엔드”로 나누는 것은 계층 분할입니다. “이메일로 가입 요청 후 중복 이메일을 거절한다”처럼 한 결과와 실패를 판정할 수 있어야 합니다.

### 배포 불가능한 중간 상태

구버전 코드가 새 스키마를 읽지 못하거나 미완성 경로가 모든 사용자에게 노출되면 작은 커밋도 안전한 전달 단위가 아닙니다. 호환 단계, 플래그, 제한 공개 또는 한 번에 묶어야 할 최소 원자 범위를 정합니다.

## 판단 규칙

1. **사용자 또는 시스템 결과로 이름을 붙입니다.** 파일·계층·도구 이름은 구현 메모로 둡니다.
2. **한 조각에 한 핵심 위험을 우선 배치합니다.** 정상 경로만 작게 만들고 권한·데이터 위험을 뒤로 미루지 않습니다.
3. **수용 기준과 실패 오라클을 먼저 씁니다.** 구현이 끝난 뒤 성공 의미를 만들지 않습니다.
4. **통합 가능성과 공개 가능성을 구분합니다.** 코드는 합칠 수 있어도 사용자에게 켤 준비가 안 됐을 수 있습니다.
5. **피드백이 다음 계획을 바꾸게 합니다.** 미리 만든 전체 백로그를 그대로 수행하는 것이 목표가 아닙니다.
6. **복구가 독립적이지 않으면 조각도 독립적이지 않습니다.** 코드, 데이터, 외부 부작용을 함께 봅니다.

## 흔한 오해와 실패

- **“PR이 작으면 수직 조각이다”**: 줄 수가 적어도 관찰 가능한 결과와 독립 수용이 없을 수 있습니다.
- **“먼저 모든 기반을 완성해야 한다”**: 미래 요구를 추측한 기반이 커지고 실제 통합 피드백이 늦어집니다.
- **“feature flag면 미완성 코드가 안전하다”**: 서버 권한, 데이터 호환성, 오래된 플래그와 꺼짐 상태 검증을 놓칩니다.
- **“배포를 자주 하면 학습한다”**: 성공 기준과 피드백 기록이 없으면 단지 변경 횟수만 늘어납니다.
- **“롤백은 언제나 가장 빠르다”**: 새 데이터와 외부 부작용 때문에 이전 코드가 더 위험할 수 있습니다.
- **“정상 경로부터 만들고 보안은 나중에 붙인다”**: 수직 조각에서 가장 중요한 신뢰 경계를 빼고 가짜 성공을 만듭니다.

## AI와 작업할 때의 요청 계약

```text wrap
다음 큰 기능을 독립적으로 수용 가능한 수직 조각으로 나눠 주세요.

- 사용자 문제와 전체 목표:
- 가장 큰 데이터·권한·운영 위험:
- 기존 시스템과 호환해야 할 계약:
- 이번에 공개하지 않을 범위:

각 조각마다 다음을 작성해 주세요.
1. 사용자 또는 시스템이 관찰할 한 결과
2. 정상·거절·결과 불명·회귀 수용 기준
3. 화면·API·업무 규칙·권위 데이터 중 필요한 경계
4. 실제 경계와 대역을 각각 확인할 테스트
5. 통합 조건과 공개 조건
6. 받을 피드백과 다음 결정을 바꾸는 신호
7. 롤백·롤포워드·플래그 중 가능한 복구 경로와 한계
8. 선행 의존성과 아직 검증하지 못한 위험

파일 수나 계층별 작업 목록만으로 조각을 작다고 판정하지 마세요. 각 조각이 독립적으로 승인·거절되고 안전하게 통합될 수 있는지 반례도 제시해 주세요.
```

## 확인 체크리스트

- [ ] 작업 이름이 파일·계층이 아니라 관찰 가능한 결과인가요?
- [ ] 정상·거절·결과 불명·회귀 수용 기준이 있나요?
- [ ] 현재 결과에 필요한 화면·서버·데이터·관측 경계를 연결했나요?
- [ ] 기반 작업을 사용자 가치 완료로 잘못 세지 않았나요?
- [ ] 실제 경계를 확인할 시점이 정해졌나요?
- [ ] 조각을 독립적으로 리뷰하고 승인 또는 거절할 수 있나요?
- [ ] 통합 가능 상태와 사용자 공개 가능 상태를 구분했나요?
- [ ] feature flag의 켜짐·꺼짐, 소유자·만료·제거 조건이 있나요?
- [ ] 코드·데이터·외부 부작용을 포함한 복구 한계를 확인했나요?
- [ ] 피드백이 다음 조각의 순서나 범위를 바꿀 수 있나요?

## 짧은 연습

“사용자가 공개 모임을 조회하고 참가하며 자신의 상태를 확인하거나 취소한다”를 세 개 이상 수직 조각으로 나누세요. 각 조각에 한 문장 결과, 네 종류의 수용 기준, 실제 경계 테스트, 공개 방식, 피드백, 롤백 또는 롤포워드 경로를 씁니다. 참가 쓰기의 최소 결과 확인을 후속 조각에 미루지 마세요. 그다음 `데이터베이스부터 전부 만들기`와 `파일 다섯 개씩 나누기`가 왜 가짜 점진성인지 반례를 하나씩 적어 보세요.

## 출처와 적용 범위

- [Agile Manifesto 원칙](https://agilemanifesto.org/principles)은 가치 있는 소프트웨어를 이르고 빈번하게 전달하고, 작동하는 소프트웨어를 진행의 주요 척도로 삼으며, 정기적으로 방식을 조정하는 피드백 방향을 뒷받침합니다. 이 원문이 특정 스프린트 길이, 티켓 크기 또는 이 장의 수직 조각 양식을 정한다고 확대하지 않습니다.
- [Martin Fowler 사이트의 Feature Toggles](https://martinfowler.com/articles/feature-toggles.html)는 Pete Hodgson이 2016년에 공개하고 2017년에 갱신한 실무 설명으로 코드 배포와 기능 공개의 분리, 켜짐·꺼짐 시험, 오래된 플래그의 복잡성을 설명하는 데 사용했습니다. 모든 기능과 데이터 변경이 플래그 하나로 안전해진다고 일반화하지 않습니다.
- [Google Engineering Practices의 Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)는 작은 변경이 검토·되돌리기·결함 발견에 주는 조직 사례를 보조합니다. 특정 줄 수나 파일 수를 수직 조각의 보편 기준으로 사용하지 않습니다.
