## 먼저 결론

이 페이지의 용어는 같은 종류도, 한 번씩 차례로 통과하는 단계도 아닙니다. **PRD와 Software Design Description은 산출물**, **Spec-Driven Development는 명시적 스펙을 구현으로 잇는 접근**, **TDD와 BDD는 서로 다른 초점의 개발·협업 규율**, **ADR은 중요한 결정의 기록**, **SDLC는 전체 생명주기를 보는 범위**, **Agile·Scrum·Kanban은 가치·팀·흐름을 다루는 서로 다른 층**, **DevOps와 CI·지속적 전달·지속적 배포는 개발과 운영 사이의 책임과 변경 흐름**, **GitFlow와 trunk-based development는 대안적인 브랜치 방식**, **컨텍스트·스펙·하네스·루프는 AI 작업의 정보·목표·환경·반복 책임**을 설명합니다.

한 프로젝트가 이 이름을 모두 도입할 필요는 없습니다. 반대로 한 이름을 도입했다고 요구·설계·검증·운영 책임이 자동으로 채워지는 것도 아닙니다. 먼저 현재 위험과 필요한 증거를 정하고, 그 질문에 실제로 답하는 최소 산출물과 실무만 선택하세요.

## 다섯 범주를 먼저 분리하세요

| 범주 | 여기에 속하는 개념 | 주로 답하는 질문 | 범주를 섞을 때 생기는 오류 |
|---|---|---|---|
| 문서 산출물과 스펙 접근 | PRD, Software Design Description, Spec-Driven Development | 무엇을 왜 만들고, 어떤 구조로 실현하며, 명시적 스펙을 어떻게 작업으로 내리는가? | 세 개를 모두 같은 문서 양식이나 고정된 선행 단계로 봅니다. |
| 구현·테스트·협업 규율 | TDD, BDD | 작은 구현 피드백과 이해관계자 행동 예시를 어떻게 앞당기는가? | 테스트 파일이나 Given–When–Then 문법이 있으면 규율을 수행했다고 봅니다. |
| 결정 기록 | ADR | 중요한 선택을 어떤 맥락·대안·결과와 함께 남기는가? | 전체 설계 문서나 회의록과 같은 것으로 봅니다. |
| 생명주기·팀·흐름·운영 | SDLC, Agile, Scrum, Kanban, DevOps, CI, continuous delivery, continuous deployment, GitFlow, trunk-based development | 문제부터 운영 학습까지 팀과 변경 흐름을 어떻게 조직하는가? | 원칙·프레임워크·관행·브랜치 방식을 하나의 성숙도 사다리로 배열합니다. |
| AI 개발의 책임 설계 | context engineering, spec-driven development, harness engineering, loop engineering | 모델이 무엇을 보고, 무엇을 만들며, 어디서 행동하고, 언제 반복·중단·인계하는가? | 네 책임을 신제품 기능이나 업계 표준의 선형 네 단계로 봅니다. |

이 분류도 절대적인 학문 분류는 아닙니다. 예를 들어 BDD의 행동 예시는 요구 명세이면서 자동 테스트 입력이 될 수 있고, CI는 기술 자동화이면서 팀의 통합 규율이기도 합니다. 분류의 목적은 겹침을 없애는 것이 아니라 **주된 질문과 보장하지 않는 범위**를 분명히 하는 것입니다.

## 관계를 읽는 세 가지 축

### 산출물과 활동을 구분합니다

PRD·Software Design Description·ADR은 사람이 검토하고 갱신할 수 있는 기록입니다. Spec-Driven Development·TDD·BDD·CI는 일을 수행하고 피드백을 얻는 접근이나 규율입니다. Scrum·Kanban은 팀과 작업 흐름을 운영하는 방식이고, GitFlow·trunk-based development는 Git 브랜치를 구성하는 대안입니다. 기록이 있다는 사실은 해당 규율을 실제로 수행했다는 증거가 아니며, 규율을 수행했다고 모든 기록이 자동으로 최신이 되는 것도 아닙니다.

### 포함 관계와 선택 관계를 구분합니다

SDLC는 문제 발견부터 요구·설계·구현·검증·배포·운영·학습까지를 보는 가장 넓은 생명주기 렌즈입니다. 그 안에서 Agile 원칙을 따를 수도 있고, Scrum이나 Kanban을 함께 또는 선택적으로 적용할 수도 있습니다. CI는 변경 통합 피드백을 맡고, continuous delivery는 배포 가능한 상태를 유지하며, continuous deployment는 자동 게이트를 통과한 변경을 운영까지 자동 반영하는 더 좁은 선택입니다. continuous deployment를 하지 않아도 continuous delivery를 할 수 있습니다.

GitFlow와 trunk-based development는 앞뒤 단계가 아니라 브랜치 전략의 대안입니다. 한 팀이 전환기에 일부 관행을 섞을 수는 있지만, `develop`·release 브랜치를 오래 유지하는 모델과 기준 브랜치에 작은 변경을 자주 통합하는 모델의 피드백 비용은 다릅니다. 이름보다 실제 브랜치 수명, 통합 빈도, 리뷰·테스트·릴리스·복구 계약을 확인해야 합니다.

### 겹침과 피드백을 허용합니다

BDD에서 합의한 행동 예시는 PRD의 수용 기준을 구체화하고 TDD의 테스트 후보가 될 수 있습니다. TDD 중 인터페이스가 복잡하다는 증거를 발견하면 Software Design Description이나 ADR을 다시 볼 수 있습니다. CI 실패는 구현으로, 운영 실패는 설계·요구로 되돌아갈 수 있습니다. 컨텍스트·스펙·하네스·루프 책임은 이 모든 활동 위에서 AI가 사용할 정보, 목표, 행동 범위와 평가 반복을 조정합니다.

## 하나의 만능 선형 절차가 아닙니다

다음 흐름은 **추적 지점의 예**이지 모든 프로젝트의 고정 절차가 아닙니다.

```text
사용자 문제와 제품 목표
↕ PRD와 수용 기준
요구를 실현할 구조와 경계
↕ Software Design Description과 중요한 ADR
검토 가능한 스펙·계획·작업
↕ Spec-Driven Development, BDD 예시, 구현 안의 TDD 반복
공유 코드 통합과 자동 피드백
↕ CI
배포 가능한 결과와 운영 반영
↕ continuous delivery 또는 continuous deployment
실제 사용자·데이터·서비스 증거
↕ 운영 학습을 요구·설계·작업 방식에 반영
```

SDLC는 이 전체를 감싸는 생명주기 렌즈이고, Agile·Scrum·Kanban은 가치·팀·흐름을 조정하며, DevOps는 개발과 운영의 공동 책임과 피드백을 가로지릅니다. GitFlow 또는 trunk-based development는 변경을 통합하는 브랜치 경로를 선택합니다. 컨텍스트·스펙·하네스·루프는 AI가 각 지점에서 무엇을 보고·요구받고·실행하고·평가할지를 가로질러 설계합니다. 따라서 위 화살표를 “모든 용어를 차례로 도입하라”는 체크리스트로 읽으면 안 됩니다.

## 1. 문서 산출물과 스펙 접근

### PRD(Product Requirements Document)

- **범주**: 제품 요구 문서입니다.
- **목적·대표 출력**: 누구의 어떤 문제를 왜 무엇으로 해결할지 합의하고 사용자·문제·목표·범위·비범위·요구·수용 기준·성공 지표·제약을 남깁니다.
- **관계·순서·중첩**: 설계의 입력이 되지만 사용자 조사·설계 가능성·운영 결과에 따라 다시 협의됩니다. BDD 예시가 수용 기준을 구체화할 수 있고, Spec-Driven Development의 스펙이 PRD 일부를 더 실행 가능한 동작으로 내릴 수 있습니다.
- **성숙도·출처 상태**: 널리 쓰이는 제품 산출물 이름이지만 하나의 보편 PRD 표준 양식은 없습니다. 2026-08-13 확인한 ISO/IEC/IEEE 29148:2018은 요구공학의 현재 발행 범위를 뒷받침하며, 이 핸드북의 PRD 형식을 강제하지 않습니다.
- **일반화 금지선**: 기능 목록·기술 선택·테스트 케이스 전체·구현 계획을 PRD와 같은 것으로 보지 않습니다. PRD 존재를 사용자 문제 확인이나 제품 성공으로 확대하지 않습니다.

자세한 구분은 [PRD·두 종류의 SDD·TDD](../../06-requirements-design/prd-sdd-tdd/)에서 확인합니다.

### Software Design Description

- **범주**: 요구를 실현할 구조를 설명하는 설계 산출물입니다.
- **목적·대표 출력**: 구성요소의 책임·경계·인터페이스·데이터·상태·품질 속성·실패·배포·운영·트레이드오프를 검토 가능하게 만듭니다.
- **관계·순서·중첩**: PRD의 요구와 제약을 구현 가능한 구조로 내리고, 중요한 한 결정은 ADR로 분리할 수 있습니다. 구현·테스트·운영에서 발견한 사실을 다시 반영합니다.
- **성숙도·출처 상태**: IEEE 1016-2009가 역사적 정의를 제공하지만 2026-08-14 확인 상태는 `Inactive-Reserved`입니다. 현재 모든 프로젝트의 의무 문서 형식으로 쓰는 근거가 아닙니다.
- **일반화 금지선**: 기술 스택 목록, 모든 세부 구현, Spec-Driven Development, 실제 구현 완료를 같은 뜻으로 보지 않습니다.

### Spec-Driven Development

- **범주**: 문서 하나가 아니라 명시적 스펙을 계획·작업·구현으로 연결하는 개발 접근입니다.
- **목적·대표 출력**: 검토 가능한 spec·plan·tasks·구현 diff와 단계별 수용·검증 기록을 연결합니다.
- **관계·순서·중첩**: 중심 장은 2026-08-13에 확인한 GitHub Spec Kit 사례의 `Spec → Plan → Tasks → Implement` 네 연결을 설명하며 필요하면 앞 산출물로 돌아갑니다. 2026-11-15에 확인한 [공식 홈페이지](https://github.github.com/spec-kit/)는 구현 뒤 `Converge`까지 핵심 흐름에 포함하므로 교육용 네 연결을 현재 도구의 전체 흐름으로 보지 않습니다. PRD·Software Design Description을 입력으로 쓰거나 작은 변경에서는 한 브리프 안에 필요한 부분을 합칠 수 있습니다. AI 개발의 스펙 책임과 같은 축을 설명합니다.
- **성숙도·출처 상태**: GitHub Spec Kit의 날짜가 있는 제품·조직 사례이며 하나의 국제 표준이나 고정된 `SDD` 약어가 아닙니다. 과거 확인 기록과 이번 현재성 보충을 구분합니다.
- **일반화 금지선**: 긴 프롬프트, 완벽한 선행 설계, 특정 도구의 명령 순서, 구현 성공 보장으로 확대하지 않습니다.

`SDD`라고만 쓰면 Software Design Description과 Spec-Driven Development를 구분할 수 없습니다. 첫 등장에 영문 전체 이름과 **산출물인지 접근인지**를 함께 쓰세요.

## 2. 구현·테스트·협업 규율

### TDD(Test-Driven Development)

- **범주**: 구현 순간의 테스트 우선 규율입니다.
- **목적·대표 출력**: 다음 작은 동작을 테스트로 먼저 표현하고 기대한 이유의 실패(Red), 최소 구현의 통과(Green), 외부 동작을 유지한 구조 개선(Refactor)을 반복합니다.
- **관계·순서·중첩**: PRD의 요구·BDD의 예시·설계의 인터페이스가 테스트 후보가 될 수 있고, TDD에서 발견한 설계 문제를 Software Design Description이나 ADR로 되돌립니다. 전체 테스트 전략 안에서 일부 구현 피드백을 맡습니다.
- **성숙도·출처 상태**: 널리 확립된 개발 실무이며 2026-08-13 확인한 Martin Fowler의 방법론 설명을 직접 범위로 사용합니다. 하나의 테스트 도구나 모든 위험의 표준 검증 절차는 아닙니다.
- **일반화 금지선**: 테스트 파일 보유, 구현 뒤 테스트 추가, 모든 수준의 테스트, 사용자·보안·성능·배포·운영 성공을 TDD 수행과 같은 것으로 보지 않습니다.

### BDD(Behavior-Driven Development)

- **범주**: 이해관계자·개발·테스트가 관찰 가능한 행동 예시로 대화하고 명세하는 협업 접근입니다.
- **목적·대표 출력**: 사용자 역할·맥락·행동·결과와 Given–When–Then 같은 예시를 통해 모호한 요구와 수용 기준을 구체화합니다.
- **관계·순서·중첩**: PRD의 요구를 예시로 탐색하고 Software Design Description의 경계·TDD의 테스트·수용 테스트로 이어질 수 있습니다. BDD가 TDD보다 앞서야 한다거나 둘 중 하나만 선택해야 하는 것은 아닙니다.
- **성숙도·출처 상태**: 2026-11-22에 [Dan North의 원형 글](https://dannorth.net/blog/introducing-bdd/)과 [Cucumber의 BDD 설명](https://cucumber.io/docs/bdd/)에서 행동을 설명하는 언어와 사례 중심 협업을 확인했습니다. 특정 도구나 문법은 필수 조건이 아닙니다.
- **일반화 금지선**: Given–When–Then 문법 사용, 자동화 도구 도입, 테스트 파일 생성만으로 이해관계자 합의나 BDD 수행이 증명됐다고 보지 않습니다.

TDD와 BDD는 경쟁하는 약어가 아닙니다. TDD는 구현 피드백 순서에, BDD는 행동 예시를 통한 공동 이해에 더 직접 초점을 둡니다. 둘을 함께 써도 단위·통합·보안·접근성·운영 검증은 별도로 설계해야 합니다.

## 3. 결정 기록

### ADR(Architecture Decision Record)

- **범주**: 아키텍처적으로 중요한 한 결정의 기록입니다.
- **목적·대표 출력**: 당시 맥락·상태·대안·결정·결과·가정·증거·재검토 조건과 대체 관계를 남깁니다.
- **관계·순서·중첩**: Software Design Description이 전체 구조를 설명한다면 ADR은 그 안의 중요한 한 선택과 이유를 좁혀 기록합니다. 요구·구현·운영 증거가 바뀌면 기존 기록을 지우지 않고 새 ADR로 대체할 수 있습니다.
- **성숙도·출처 상태**: Michael Nygard의 2011년 원형 1차 기록과 2026-08-13 확인한 ISO/IEC/IEEE 42010:2022의 아키텍처 결정·근거 범위를 연결합니다. 이 페이지의 확장 필드가 유일한 표준 양식은 아닙니다.
- **일반화 금지선**: 회의록, 전체 아키텍처 설명, 기술 목록, 영원한 진리, 구현·검증·승인 완료와 같은 것으로 보지 않습니다.

작성과 재검토 방법은 [ADR과 트레이드오프 기록](../../06-requirements-design/adr-and-tradeoffs/)에서 확인합니다.

## 4. 생명주기·팀·흐름·운영 방식

### SDLC(Software Development Life Cycle)

- **범주**: 소프트웨어를 만들고 유지하는 전체 생명주기 렌즈입니다.
- **목적·대표 출력**: 발견·요구·설계·구현·검증·배포·운영·학습의 질문, 책임, 산출물과 종료 증거를 연결합니다.
- **관계·순서·중첩**: Agile·Scrum·Kanban·DevOps·CI/CD와 브랜치 전략을 포함해 여러 방식이 SDLC 안에서 선택·중첩될 수 있습니다. 운영 학습은 이전 요구와 설계로 되돌아갑니다.
- **성숙도·출처 상태**: 2026-08-14 확인한 ISO/IEC/IEEE 12207:2026 Published Edition 2가 병행·반복·재귀·점진 적용 가능한 생명주기 과정의 현재 표준 범위를 제공합니다.
- **일반화 금지선**: 워터폴의 고정 순서, 이 핸드북의 단계 이름, 필수 문서 목록, 단계 완료 표시와 같은 것으로 보지 않습니다.

전체 흐름과 증거는 [소프트웨어 개발 생명주기](../../07-workflow-methods/software-development-lifecycle/)에서 확인합니다.

### Agile

- **범주**: 가치·협업·피드백·적응을 중시하는 원칙군입니다.
- **목적·대표 출력**: 가치 있는 결과의 이른·빈번한 전달, 작동하는 소프트웨어를 통한 학습, 정기적인 성찰과 조정을 지향합니다.
- **관계·순서·중첩**: Scrum과 Kanban은 Agile 원칙을 적용할 수 있는 서로 다른 방식이지만 Agile 전체와 같은 뜻은 아닙니다. SDLC를 없애는 대신 피드백 주기와 결정 방식을 조정합니다.
- **성숙도·출처 상태**: 2001년 Agile Manifesto와 원칙이라는 역사적 1차 원문이 있으며 2026-08-13에 직접 확인했습니다. 인증 체계나 단일 프로세스 표준으로 쓰지 않습니다.
- **일반화 금지선**: 계획·문서·설계·승인·장기 책임이 필요 없다는 뜻, 모든 작업을 짧은 스프린트로 해야 한다는 뜻으로 확대하지 않습니다.

### Scrum

- **범주**: 목표·역할·이벤트·산출물을 일정한 주기로 운영하는 팀 프레임워크입니다.
- **목적·대표 출력**: 제품에서 앞으로 할 일의 목록(Product Backlog)은 제품이 도달하려는 상태(Product Goal)를 기준으로 정리합니다. 한 스프린트의 작업 계획(Sprint Backlog)은 그 기간의 단일 목표(Sprint Goal)를 향합니다. 실제로 완성한 결과물(Increment)은 제품에 적용하는 완료 기준(Definition of Done)을 충족해야 합니다.
- **관계·순서·중첩**: Agile 원칙을 적용하는 한 프레임워크이며, 제품·개발 팀 운영을 SDLC 안에 배치할 수 있습니다. Kanban의 흐름 시각화·WIP 제한 관행을 함께 사용할 수도 있습니다.
- **성숙도·출처 상태**: 2026-11-22에 [Scrum Guide](https://scrumguides.org/scrum-guide.html)의 Scrum Theory와 Scrum Events는 Sprint와 그 안의 점검·적응 기회를 설명합니다. 이 프레임워크를 모든 팀의 필수 절차로 보지 않습니다.
- **일반화 금지선**: Agile 전체, 프로젝트 관리 전체, 모든 조직에 맞는 역할·Sprint 길이, 회의 횟수만으로 성숙도를 판단하는 기준으로 사용하지 않습니다.

### Kanban

- **범주**: 작업 흐름을 시각화하고 진행 중 작업을 제한하며 흐름을 개선하는 방법입니다.
- **목적·대표 출력**: 명시적 흐름 단계, 작업 항목, WIP 제한, 막힘과 대기, 리드타임·사이클타임 같은 흐름 관찰을 만듭니다.
- **관계·순서·중첩**: Scrum을 대체하거나 보완할 수 있고, 운영·지원·콘텐츠처럼 도착 시점이 불규칙한 작업에도 적용할 수 있습니다. CI나 배포 자동화 자체는 아닙니다.
- **성숙도·출처 상태**: 2026-11-22에 [The Kanban Guide](https://kanbanguides.org/english/)에서 작업 흐름의 시작·끝, 진행 중 작업의 통제, 흐름 지표를 확인했습니다. 보드를 그리는 것만으로 흐름을 관리했다고 볼 수 없습니다.
- **일반화 금지선**: 칸이 있는 할 일 보드, 작업자 감시, 모든 팀에 같은 WIP 수치, Agile 전체와 같은 것으로 보지 않습니다.

### DevOps

- **범주**: 개발과 운영이 변경의 설계·전달·관찰·복구 책임을 함께 다루는 문화·조직·기술 실무의 묶음입니다.
- **목적·대표 출력**: 자동화된 변경 흐름, 공동 소유권, 환경·배포·관측·인시던트·복구 피드백과 개선 기록을 연결합니다.
- **관계·순서·중첩**: CI·continuous delivery·continuous deployment는 DevOps를 지원할 수 있는 관행이지만 DevOps 전체가 아닙니다. Agile의 빠른 학습과 SDLC의 운영·학습 구간을 가로지를 수 있습니다.
- **성숙도·출처 상태**: 2026-11-22에 [AWS의 DevOps 설명](https://aws.amazon.com/devops/what-is-devops/)은 개발과 운영이 책임을 공유하는 문화·실무·도구를 함께 다룹니다. 한 기관의 설명이지 특정 팀 구조나 배포 도구를 의무화하는 표준은 아닙니다.
- **일반화 금지선**: CI/CD 도구 설치, 클라우드 사용, 운영을 개발자에게 떠넘김, 조직명 변경, 배포 횟수 하나로 DevOps 완료를 주장하지 않습니다.

### CI(Continuous Integration)

- **범주**: 공유 코드에 변경을 자주 통합하고 자동 피드백으로 깨진 상태를 빠르게 복구하는 통합 규율입니다.
- **목적·대표 출력**: 기준 commit에 연결된 자동 빌드·정적 검사·테스트 결과와 로그, 통합 실패의 복구 기록을 만듭니다.
- **관계·순서·중첩**: 코드 리뷰와 병합 게이트의 입력이 되고 continuous delivery의 기초가 될 수 있습니다. trunk-based development와 잘 맞을 수 있지만 특정 브랜치 전략을 자동으로 요구하지 않습니다.
- **성숙도·출처 상태**: 2026-08-13 확인한 Martin Fowler의 2024년 갱신 방법론 설명을 직접 범위로 사용합니다.
- **일반화 금지선**: CI 서비스 설치, 브랜치에서 테스트 한 번 실행, 초록 표시, 모든 요구·보안·운영 위험의 통과와 같은 것으로 보지 않습니다.

### Continuous Delivery(지속적 전달)

- **범주**: 검증된 결과를 언제든 배포할 수 있는 상태로 유지하는 전달 관행입니다.
- **목적·대표 출력**: 추적 가능한 아티팩트, 환경별 검증, 승인 가능한 배포 후보, 배포·복구 절차를 만듭니다.
- **관계·순서·중첩**: 보통 CI 피드백 위에 배포 가능 상태를 만들며 운영 반영 전에 사람 승인을 둘 수 있습니다. continuous deployment의 기반이 될 수 있지만 자동 운영 배포와 같은 뜻은 아닙니다.
- **성숙도·출처 상태**: CI와 함께 2026-08-13 확인한 Martin Fowler의 2024년 갱신 설명에서 직접 구분합니다.
- **일반화 금지선**: 배포 횟수, 자동화 도구, 빌드 성공, 실제 사용자 공개나 운영 검증 완료와 같은 것으로 보지 않습니다.

### Continuous Deployment(지속적 배포)

- **범주**: 정해진 자동 게이트를 통과한 변경을 운영 환경까지 자동 반영하는 배포 방식입니다.
- **목적·대표 출력**: 대상 commit·아티팩트·환경에 연결된 자동 운영 배포 기록과 배포 후 검증·완화·복구 신호를 만듭니다.
- **관계·순서·중첩**: continuous delivery의 배포 가능 상태에 자동 운영 반영을 더한 선택입니다. 위험이 큰 변경에는 별도 승인·점진 공개·중단 조건을 둘 수 있으며, 모든 팀이 채택해야 하는 최종 단계가 아닙니다.
- **성숙도·출처 상태**: continuous delivery와 같은 직접 방법론 자료에서 구분되는 확립된 실무입니다.
- **일반화 금지선**: 무조건 빠른 배포, 승인·보안·데이터 전환 생략, 배포 성공을 사용자 성공·복구 성공으로 확대하지 않습니다.

CI·전달·배포의 증거 경계는 [코드 리뷰와 CI/CD](../../07-workflow-methods/code-review-ci-cd/)에서 확인합니다. `CD`만 쓰면 delivery와 deployment 중 어느 뜻인지 알 수 없으므로 처음에는 영문 전체 이름을 적으세요.

### GitFlow

- **범주**: `main`·`develop`과 feature·release·hotfix 같은 장기·목적별 브랜치를 사용하는 브랜치 모델입니다.
- **목적·대표 출력**: 병렬 개발·릴리스 준비·운영 수정의 통합 경로와 브랜치별 규칙을 분리합니다.
- **관계·순서·중첩**: CI/CD·Scrum·Kanban과 다른 축이며 trunk-based development와 대안 관계입니다. 릴리스 주기와 여러 지원 버전이 있을 때 검토할 수 있지만 통합 지연 비용이 생길 수 있습니다.
- **성숙도·출처 상태**: 2026-11-22에 [Vincent Driessen의 원형 글](https://nvie.com/posts/a-successful-git-branching-model/)은 릴리스와 긴급 수정이 개발·운영 브랜치에 다시 합쳐지는 방식을 설명합니다. 이를 Git이 요구하는 절차로 보지 않습니다.
- **일반화 금지선**: Git의 기본 동작, 모든 팀의 안전한 기본값, 브랜치가 존재하면 격리·테스트·릴리스가 보장된다는 뜻으로 사용하지 않습니다.

### Trunk-based development

- **범주**: 기준 브랜치에 작은 변경을 자주 통합하고 장기 분기를 줄이는 브랜치·통합 방식입니다.
- **목적·대표 출력**: 짧은 변경 단위, 빈번한 통합, 빠른 CI 피드백, 필요하면 feature flag로 배포와 공개를 분리하는 흐름을 만듭니다.
- **관계·순서·중첩**: CI와 continuous delivery를 지원할 수 있지만 리뷰·승인·테스트를 없애지 않습니다. GitFlow 다음의 성숙 단계가 아니라 위험·릴리스·팀 구조에 따라 선택할 대안입니다.
- **성숙도·출처 상태**: 2026-11-22에 [Trunk Based Development 소개](https://trunkbaseddevelopment.com/)는 주 통합선에 자주 합치면서 짧은 리뷰 브랜치를 사용할 수 있다고 설명합니다. 직접 push해야 한다는 뜻은 아닙니다.
- **일반화 금지선**: 검토 없이 `main`에 직접 push하기, 큰 미완성 변경 공개, feature flag가 모든 데이터·호환성·복구 위험을 해결한다는 뜻으로 보지 않습니다.

## 5. 컨텍스트·스펙·하네스·루프

이 네 표현은 경쟁 방법론이나 선형 도입 단계가 아니라 AI 개발의 서로 다른 책임입니다. 자세한 정의와 날짜 있는 조직 사례는 [컨텍스트·스펙·하네스·루프](../../11-ai-native/context-spec-harness-loop/)에서 확인합니다.

### Context engineering

- **범주**: AI가 현재 판단에 사용할 입력을 설계하는 실무입니다.
- **목적·대표 출력**: 최신 지시·정본 파일·검색 결과·도구 설명·작업 기억을 선택하고 우선순위·노출 범위·압축·폐기 조건을 관리합니다.
- **관계·순서·중첩**: 스펙도 컨텍스트의 일부가 될 수 있고, 하네스의 도구 결과와 루프의 이전 관찰이 다음 컨텍스트로 들어갑니다. 프롬프트 작성보다 넓은 책임입니다.
- **성숙도·출처 상태**: 여러 조직이 쓰는 현재 실무 표현이며 2026-08-13 확인한 Anthropic의 2025년 조직 사례가 있습니다. 단일 표준 정의는 아닙니다.
- **일반화 금지선**: 긴 프롬프트, 모든 파일 투입, 메모리 기능 사용, 정확성·최신성·비밀 보호 보장으로 확대하지 않습니다.

### Spec-driven development의 스펙 책임

- **범주**: AI 작업이 만들 결과·제약·비목표·수용 기준을 명시하는 책임입니다.
- **목적·대표 출력**: 관찰 가능한 동작, 실패 조건, 권한 경계, acceptance criteria, 작업 산출물과 추적 링크를 만듭니다.
- **관계·순서·중첩**: 앞의 Spec-Driven Development와 같은 축입니다. 컨텍스트가 무엇을 사실로 볼지 정한다면 스펙은 무엇을 수용할지 정하고, 하네스는 이를 어떻게 실행·검증할지, 루프는 실패를 어떻게 다음 시도에 반영할지 정합니다.
- **성숙도·출처 상태**: 2026-08-13 확인한 GitHub Spec Kit의 현재 사례를 사용하며 Software Design Description 표준이나 보편 AI 개발 순서가 아닙니다.
- **일반화 금지선**: 자연어 길이, 템플릿 준수, 에이전트가 생성한 계획, 틀린 스펙의 정교한 구현을 품질 보장으로 보지 않습니다.

### Harness engineering

- **범주**: AI가 행동하고 관찰·검증할 작업 환경을 설계하는 실무 표현입니다.
- **목적·대표 출력**: 저장소 지식, 도구, 권한, sandbox, fixture, 테스트, 로그, 평가자, 승인 게이트와 실패 복구 경로를 연결합니다.
- **관계·순서·중첩**: 컨텍스트와 스펙을 실제 행동·관찰로 이어 주고 루프가 사용할 검증 신호를 제공합니다. CI·테스트·배포 도구를 포함할 수 있지만 그 도구들의 책임을 대체하지 않습니다.
- **성숙도·출처 상태**: 여러 조직이 사용하는 신생 실무 표현이며 2026-08-13 확인한 OpenAI의 2026년 조직 사례와 Anthropic 사례가 있습니다. 합의된 국제 표준은 아닙니다.
- **일반화 금지선**: 특정 에이전트 제품·라이브러리·테스트 모음, 무제한 권한, 높은 자동화율을 안전성·정확성·생산성 보장으로 확대하지 않습니다.

### Loop engineering

- **범주**: 관찰·행동·평가·수정·중단·인계의 반복 조건을 설계한다는 신생 실무 표현입니다.
- **목적·대표 출력**: 평가 기준, 재시도·예산·시간 제한, 중단 조건, 상태 저장, 회귀 확인, 실패 분류와 handoff 기록을 만듭니다.
- **관계·순서·중첩**: 하네스가 제공한 행동·관찰을 반복하고 결과를 다음 컨텍스트·스펙·하네스 개선으로 되돌립니다. SDLC 전체의 피드백과 닮았지만 AI 작업의 실행·평가 반복을 더 좁게 봅니다.
- **성숙도·출처 상태**: 특히 신생인 편집·실무 표현이며 합의된 방법론 이름이나 보편 성숙도 모델이 아닙니다. 현재 Anthropic의 장시간 에이전트 조직 사례를 제한적으로 참고합니다.
- **일반화 금지선**: 무한 재시도, 여러 에이전트 사용, 한 번의 성공, 평가 점수 상승을 회귀 부재·안전·자율성 성숙으로 확대하지 않습니다.

## 프로젝트에 맞는 최소 조합을 고르세요

### 작은 개인 프로토타입

- 한 페이지에 사용자 문제·범위·비목표·수용 기준을 적습니다.
- 중요한 구조 선택과 실패 위험만 짧은 설계 메모로 남깁니다.
- 작은 Git 변경, 핵심 테스트와 수동 확인, 배포 후 smoke test를 연결합니다.
- AI를 쓴다면 허용 파일·금지 행동·검증 명령·중단 조건을 명시합니다.

### 외부 사용자가 있는 작은 서비스

- PRD 또는 동등한 요구 기록, 책임·데이터·권한·실패를 포함한 설계 설명, 중요한 ADR을 둡니다.
- 행동 예시와 수용 기준을 위험에 맞는 테스트 전략으로 연결하고 CI에서 통합 결과를 확인합니다.
- 배포 가능한 아티팩트, 승인·점진 공개·관측·롤백 또는 롤포워드 절차를 둡니다.
- 팀 흐름에는 Scrum·Kanban·다른 방식을 이름 때문에 선택하지 않고 실제 도착 패턴·WIP·피드백 비용을 기준으로 선택합니다.

### 데이터·보안·금전 위험이 큰 서비스

- 정식 요구·설계·위협 모델, 데이터 계보·마이그레이션·복구 계획과 독립 승인 게이트를 둡니다.
- 브랜치와 통합 방식은 장기 지원·감사·릴리스 제약과 빠른 피드백의 비용을 비교해 결정합니다.
- 단계적 배포, 운영 훈련, 권한 부정 테스트, 사본 복원 시험과 실제 사용자·데이터 오라클을 연결합니다.
- 규정과 계약은 일반 방법론 이름으로 대체하지 않고 해당 도메인의 공식 요구와 전문가 검토를 별도로 확인합니다.

방법론 이름을 많이 도입하는 것이 성숙함이 아닙니다. 위험에 맞는 결정, 빠른 반례, 추적 가능한 증거, 안전한 중단과 복구가 실제로 작동하는지가 더 중요합니다.

## 선택 전 확인 질문

- [ ] 지금 필요한 것이 문서 산출물, 구현 규율, 팀 운영, 흐름 관리, 배포 자동화, 브랜치 전략, AI 책임 중 무엇인지 분류했나요?
- [ ] `SDD`와 `CD`처럼 뜻이 둘 이상인 약어를 영문 전체 이름으로 풀어 썼나요?
- [ ] PRD·Software Design Description·ADR의 존재와 Spec-Driven Development·TDD·BDD의 실제 수행 증거를 구분했나요?
- [ ] SDLC·Agile·Scrum·Kanban·DevOps를 같은 범주나 성숙도 단계로 배열하지 않았나요?
- [ ] CI·continuous delivery·continuous deployment의 대상 commit·아티팩트·환경·승인·운영 증거를 구분했나요?
- [ ] GitFlow와 trunk-based development를 앞뒤 단계가 아닌 대안으로 비교했나요?
- [ ] context·spec·harness·loop를 제품 기능이나 보편 표준의 선형 절차로 설명하지 않았나요?
- [ ] 공식·1차 자료를 직접 확인하지 않은 정의와 날짜 있는 현재 확인을 구분했나요?
- [ ] 한 자동 검사·문서·도구·프레임워크의 성공을 사용자·데이터·보안·운영 성공으로 확대하지 않았나요?
- [ ] 작은 변경에는 필요한 최소 기록을, 되돌리기 어려운 변경에는 독립 검토·승인·복구 증거를 두었나요?

## 짧은 연습

“모임 참가 기능을 외부 사용자에게 제공한다”는 목표를 아래 다섯 축으로 나누세요.

| 축 | 적을 내용 |
|---|---|
| 산출물 | PRD의 사용자 문제·수용 기준, Software Design Description의 권한·정원·동시성 경계, ADR이 필요한 결정 한 개 |
| 구현·협업 | BDD 행동 예시 한 개, TDD로 먼저 실패시킬 작은 규칙 한 개, 전체 테스트 전략에서 추가할 위험 |
| 팀·흐름 | Scrum·Kanban·다른 방식 중 현재 도착 패턴과 WIP에 맞는 선택 이유 |
| 통합·전달 | CI 결과, continuous delivery 후보 아티팩트, 운영 반영 승인 또는 continuous deployment 중단 조건 |
| AI 책임 | context 정본, spec 수용 기준, harness 권한·검증, loop 재시도·중단·handoff 조건 |

마지막으로 각 항목 옆에 “이 기록이나 관행 하나만으로 증명되지 않는 것”을 한 줄씩 적으세요. 한 축을 다른 축의 증거로 대신했다면 다시 분리하세요.
