## 이 체크리스트를 사용하는 법

먼저 읽기: [AI 코딩 에이전트와 일하는 법](../../11-ai-native/working-with-coding-agents/)에서 작업 계약과 권한 경계를, [테스트 전략](../../08-quality/testing-strategy/)에서 위험에 맞는 증거를 확인하세요.

체크 표시는 질문을 빠뜨리지 않았다는 표시일 뿐 성공 증거가 아닙니다. 체크한 항목 수나 완료 비율은 연결된 핵심 장을 읽은 사실, 정확한 명령과 종료 코드, 실제 브라우저·데이터·운영 환경의 관찰, 사람 검토나 소유자 승인을 대신하지 않습니다. 증거가 없거나 현재 권한으로 확인할 수 없으면 `완료`로 바꾸지 말고 `미실행`, `실패`, `거절`, `미확인`, `승인 대기`처럼 실제 상태를 적으세요.

각 항목의 `증거`에는 가능하면 대상·시점·실행 위치·정확한 명령이나 행동·종료 코드·수량·관찰 결과·판정자를 남깁니다. 비밀·개인정보·운영 데이터 원문은 증거에 복사하지 않습니다. 같은 증거를 여러 단계의 성공으로 확대하지 말고, 다음 네 질문에 답하면서 구간을 넘으세요.

1. 무엇이 실패했거나 실행되지 않았고, 그 사실을 보여 주는 증거는 무엇인가요?
2. 누가 무엇을 어떤 근거로 거절하거나 승인 보류했나요?
3. 실패하면 피해를 어떻게 제한하고 이전에 검증된 상태나 대체 경로로 어떻게 복구하나요?
4. 복구나 수정 뒤 어떤 명령·브라우저·데이터·운영 확인을 다시 실행해야 하나요?

## 1. 작업 시작

먼저 읽기: [개발자처럼 문제를 나누는 법](../../01-mental-models/developer-thinking/)과 [권한·샌드박스·worktree](../../11-ai-native/permissions-sandbox-worktrees/)에서 목표 분해와 피해 반경별 권한을 확인하세요.

- [ ] 요청이 답변·검토·진단·변경·외부 실행 중 무엇인지 정했습니다. 증거: 허용된 행동과 금지된 행동이 적힌 작업 계약
- [ ] 저장소 경계·규칙·작업 폴더·브랜치·기준 커밋과 기존 변경을 확인했습니다. 증거: 실제 경로, 규칙 파일, 브랜치·HEAD, tracked·untracked·ignored 상태
- [ ] 목표와 비목표를 사용자 결과로 고정했습니다. 증거: 완료 뒤 관찰할 결과와 이번에 바꾸지 않을 기능·파일·환경
- [ ] 수정 가능한 파일과 읽기 전용 영역을 정했습니다. 증거: 파일별 변경 이유와 범위 밖 목록
- [ ] 정상·경계·실패 상황의 수용 기준을 정했습니다. 증거: 입력·행동·기대 결과와 각 기준의 판정 방법
- [ ] 검증할 위험과 검증하지 않을 위험을 나눴습니다. 증거: 정확한 검사·테스트·빌드·브라우저·데이터·운영 확인 목록과 미검증 범위
- [ ] 네트워크 접근과 새 다운로드가 필요하면 대상·목적·비용을 설명하고 사전 승인을 받았습니다. 증거: 승인자·승인 범위·시점 또는 네트워크 미사용 기록
- [ ] 외부 계정이나 서비스 접근이 필요하면 정확한 계정·환경·권한을 확인하고 사전 승인을 받았습니다. 증거: 승인된 대상과 최소 권한 또는 외부 계정 미사용 기록
- [ ] 실제 데이터 생성·수정·이동·삭제가 필요하면 대상·영향·중지 조건·복구 방법을 설명하고 사전 승인을 받았습니다. 증거: 승인 기록과 변경 전 상태 또는 데이터 변경 미실행 기록
- [ ] 비밀을 읽거나 설정해야 하면 노출·저장·로그·회전 경계를 별도 승인했습니다. 증거: 값 자체가 아닌 비밀 이름·대상 환경·보관 위치·승인 범위 또는 비밀 미접근 기록
- [ ] 프로젝트 정책상 로컬 커밋에 승인이 필요하면 승인 여부를 정했고, push·PR·배포·공개 게시 승인은 각각 따로 확인하기로 했습니다. 증거: 행동별 허용·금지·승인 대기 표
- [ ] 삭제·덮어쓰기·초기화처럼 파괴적인 행동이 필요하면 정확한 대상·백업·되돌리기 가능성을 확인하고 사전 승인을 받았습니다. 증거: 승인된 명령과 대상 또는 파괴적 행동 미실행 기록

판정 질문: 기준 상태가 예상과 다르면 작업을 멈췄나요? 승인 거절을 우회하지 않았나요? 잘못된 폴더나 브랜치에서 시작했다면 원래 상태를 보존한 채 어떻게 복구하고, 어느 시작 검사를 다시 실행할지 적었나요?

## 2. 진단

먼저 읽기: [디버깅과 관측 가능성](../../08-quality/debugging-observability/)과 [개발자처럼 문제를 나누는 법](../../01-mental-models/developer-thinking/)에서 증상·가설·구분 실험을 확인하세요.

- [ ] 재현할 증상을 시작 상태·입력·행동·기대 결과·실제 결과로 적었습니다. 증거: 재현 절차와 성공·실패·간헐적·미재현 중 현재 판정
- [ ] 오류가 난 실제 경계와 시간을 확인했습니다. 증거: 비밀을 제거한 오류 메시지, 상태 코드, 로그·지표·트레이스, 화면 또는 데이터 상태
- [ ] 관찰한 사실과 해석·가정·원인 후보를 분리했습니다. 증거: 각 가설을 지지하거나 반박하는 관찰 목록
- [ ] 가장 작은 안전한 구분 실험부터 실행했습니다. 증거: 실험 전 가설, 바꾼 한 조건, 실제 결과와 다음 판단
- [ ] 읽기 전용 진단 범위에서 파일·설정·데이터를 고치지 않았습니다. 증거: 진단 전후 상태와 변경 없음 또는 별도 승인받은 변경 기록
- [ ] 권한·데이터·네트워크·비용 때문에 확인하지 못한 경계를 숨기지 않았습니다. 증거: 미확인 대상, 막힌 이유, 필요한 승인이나 대체 증거
- [ ] 원인 후보와 복구 후보를 증거 없이 하나로 확정하지 않았습니다. 증거: 남은 후보·반대 증거·추가로 필요한 실험
- [ ] 수정이 필요하면 진단 계약을 자동으로 넓히지 않고 가장 작은 변경 계약을 따로 정했습니다. 증거: 승인된 변경 목표·범위·수용 기준 또는 변경 미실행 기록

판정 질문: 재현 실패와 제품 성공을 혼동하지 않았나요? 수정 제안이 거절되면 현재 상태를 보존했나요? 진단 과정에서 상태를 건드렸다면 무엇을 복구했고, 같은 시작 조건과 재현 절차로 다시 확인했나요?

## 3. 변경과 로컬 검증

먼저 읽기: [점진적 전달과 작업 분해](../../07-workflow-methods/incremental-delivery/)와 [테스트 전략](../../08-quality/testing-strategy/)에서 독립 작업 단위와 가장 작은 충분한 증거를 확인하세요.

- [ ] 변경을 한 사용자 결과로 독립 검토·거절·되돌리기 가능한 크기로 제한했습니다. 증거: 수정 파일 목록과 각 파일이 수용 기준에 필요한 이유
- [ ] 버그 수정이면 변경 전 실패를 재현했고, 불가능하면 그 이유를 기록했습니다. 증거: 실패한 정확한 명령·입력·출력 또는 재현 불가 사유
- [ ] 기존 사용자 변경과 범위 밖 파일을 보존했습니다. 증거: 변경 전후 `status`와 범위 밖 diff 없음
- [ ] 구현·문서·설정·테스트 변경을 실제 diff로 읽었습니다. 증거: 예상한 동작과 연결된 핵심 diff, 예상하지 않은 삭제·이름 변경·권한 변경 없음
- [ ] 테스트·기대값·스냅샷·건너뛰기·필터 변경이 실패를 숨기지 않습니다. 증거: 테스트 쪽 diff와 오라클의 독립 근거
- [ ] 스키마나 데이터 변경이 있으면 호환성·불변식·마이그레이션·중지 조건·복구를 검증했습니다. 증거: 승인된 전용 데이터에서의 전후 대사와 실패 뒤 데이터 상태
- [ ] fallback을 추가했다면 주 경로 실패와 기능·정확도·최신성 저하가 드러납니다. 증거: fallback 진입·종료 조건, 사용자·운영자 표시와 정상 경로 복구 기준
- [ ] 관련 검사와 테스트를 실제로 실행했습니다. 증거: 실행 위치·환경·정확한 명령·종료 코드와 통과·실패·건너뜀·취소 수
- [ ] 로컬 정적 검사와 로컬 빌드를 별도 상태로 확인했습니다. 증거: 각 명령·종료 코드·출력 요약이며, 실행하지 않은 쪽은 미실행 이유
- [ ] 위험에 따라 실제 브라우저·데이터·통합 경계를 확인했습니다. 증거: URL·화면 크기·행동·화면 상태 또는 데이터 질의·행 수·불변식·실제 경계와 대역의 구분
- [ ] 로컬 검사와 빌드 성공을 commit·push·PR·배포·공개·운영 성공으로 확대하지 않았습니다. 증거: 각 후속 상태를 `미실행`, `실패`, `완료`, `승인 대기` 중 하나로 따로 기록

판정 질문: 어떤 검사가 실패하거나 미실행됐나요? 수용 기준 미달 변경을 누가 거절했나요? 부분 변경과 데이터 부작용을 어떻게 되돌리거나 복구하나요? 수정 뒤 실패 재현부터 관련 검사·빌드·브라우저·데이터 확인 중 무엇을 다시 실행하나요?

## 4. 검토와 수용

먼저 읽기: [에이전트 결과 리뷰와 검증](../../11-ai-native/agent-review-and-verification/)에서 완료 주장, 독립 검토, finding 재판정과 수용 결정을 확인하세요.

- [ ] 실제 변경 파일과 작업 계약의 허용 범위를 대조했습니다. 증거: 전체 diff와 범위 밖 변경 0건 또는 승인된 예외
- [ ] 수용 기준마다 직접 증거 또는 미검증 표시가 있습니다. 증거: 기준별 명령·화면·데이터·사람 판정 연결표
- [ ] 명령의 실행 위치·환경·범위·종료 코드·수량을 확인했습니다. 증거: 현재 작업 트리에서 얻은 실제 출력 요약
- [ ] 낮은 층의 증거를 높은 층의 성공으로 확대하지 않았습니다. 증거: 정적 검사·테스트·빌드·브라우저·운영·사람 검토별 확인 범위와 빈틈
- [ ] 작성 과정과 분리된 관점으로 독립 검토했습니다. 증거: 고정된 입력 commit·diff·수용 기준, 검토자와 finding 목록
- [ ] finding을 요구와 직접 증거로 `confirmed defect`, `design decision`, `needs context`, `out of scope`, `false positive` 중 하나로 재판정했습니다. 증거: finding별 분류 이유와 근거 위치
- [ ] confirmed defect를 고친 뒤 원래 오라클과 전체 필수 게이트를 다시 실행했습니다. 증거: 수정 뒤 새 명령 결과와 재검토 판정
- [ ] 리뷰의 `PASS`나 체크 수를 사람 또는 소유자의 수용·공개 승인으로 취급하지 않았습니다. 증거: 수용자, 수용·조건부 수용·거절 상태와 남은 조건
- [ ] 거절·조건부 수용·미검증을 성공 보고에서 숨기지 않았습니다. 증거: 미달 기준, 영향, 다음 행동과 재검증 조건

판정 질문: 어떤 finding이나 수용 기준이 왜 거절됐나요? 거절된 변경을 보존·수정·되돌리는 선택은 무엇인가요? confirmed defect를 고친 뒤 같은 오라클로 재검증했나요? 최종 수용 권한자가 실제로 승인했나요?

## 5. 커밋과 원격 협업

먼저 읽기: [Git과 GitHub는 다릅니다](../../09-git-github/git-and-github/)와 [브랜치·커밋·Pull Request](../../09-git-github/branch-commit-pull-request/)에서 로컬 이력과 원격 협업의 차이를 확인하세요.

- [ ] 커밋 직전 `status`와 전체 diff에서 예상하지 않은 변경을 확인했습니다. 증거: tracked·untracked·ignored 상태와 삭제·이름·권한 변경 검토
- [ ] 관련 파일만 stage하고 cached diff 전체를 읽었습니다. 증거: staged 파일 목록·통계와 수용 기준에 필요한 정확한 변경
- [ ] 비밀·개인 설정·운영 데이터·무관한 생성물이 stage되지 않았습니다. 증거: 비밀 패턴 검사와 staged 범위 판정
- [ ] 프로젝트 정책상 필요한 로컬 commit 승인을 받았습니다. 증거: 승인자·대상 범위·시점 또는 정책상 자동 commit 근거
- [ ] 커밋이 실제로 생성되고 한 독립 작업만 담았습니다. 증거: 전체 commit SHA, 커밋 메시지, `show`의 파일·통계·내용
- [ ] push는 로컬 commit과 별도 승인을 받았고 정확한 원격·브랜치를 확인했습니다. 증거: 승인 기록과 push 결과 또는 `미실행`·`승인 대기` 상태
- [ ] PR 생성·갱신은 push와 별도 상태로 확인했습니다. 증거: 실제 PR 식별자·대상·상태·diff 또는 `미생성` 상태
- [ ] 원격 CI와 리뷰 결과를 로컬 결과와 구분했습니다. 증거: 현재 commit에 연결된 원격 실행·실패·건너뜀 수와 review 상태 또는 `미확인`
- [ ] merge와 릴리스를 PR 승인이나 CI 성공에서 추정하지 않았습니다. 증거: 실제 merge commit·보호 규칙·릴리스 식별자 또는 `미실행`
- [ ] 로컬 commit만 존재할 때 push·PR·배포·공개가 끝났다고 보고하지 않았습니다. 증거: 단계별 현재 상태와 다음 승인 주체

판정 질문: stage나 commit 검토에서 범위가 잘못돼 거절되면 무엇을 다시 분리하나요? push·PR·CI가 실패하면 같은 명령을 무작정 반복하지 않고 원격 상태를 확인했나요? 잘못 공유한 변경은 팀 정책에 맞는 새 commit이나 승인된 되돌리기로 복구하고 같은 diff·CI를 재검증하나요?

## 6. 배포와 공개

먼저 읽기: [빌드·배포·도메인·DNS](../../10-deployment-operations/build-deploy-domain-dns/)와 [환경 변수와 설정](../../10-deployment-operations/environment-variables-config/)에서 아티팩트·환경·공개 경계를 확인하세요.

- [ ] 로컬 check와 build 결과를 배포 결과와 분리했습니다. 증거: 로컬 명령 결과와 별도의 배포 실행 식별자 또는 배포 미실행 상태
- [ ] 배포 대상 환경·소스 commit·아티팩트·설정 조합을 확인했습니다. 증거: 환경 이름, 전체 SHA, 아티팩트 식별자와 비밀 값을 제외한 설정 버전
- [ ] 배포와 데이터 변경의 대상·영향·중지 조건·복구 계획을 검토하고 사전 승인을 받았습니다. 증거: 승인자·승인 범위·시점과 실행 책임자
- [ ] 마이그레이션 전에 백업이 생성됐다는 사실과 실제 복원 가능성을 구분했습니다. 증거: 백업 식별자·시점·보존 위치와 별도의 격리 복원 시험 결과 또는 미검증 표시
- [ ] 환경별 비밀·권한·도메인·DNS·인증서 설정을 안전하게 확인했습니다. 증거: 값이 아닌 설정 존재·대상·만료·권한 판정과 노출 없음
- [ ] 배포 실행이 실제로 끝났는지 확인했습니다. 증거: 배포 식별자·대상·시작·종료 시점·결과와 실패 로그 요약
- [ ] 배포된 환경에서 승인된 smoke test와 핵심 흐름을 확인했습니다. 증거: 대상 URL·버전·행동·응답·화면 또는 데이터 결과와 부작용 없음
- [ ] 배포 성공과 공개를 구분하고, 공개 게시에는 별도 소유자 승인을 받았습니다. 증거: 공개 승인자·대상 독자·접근 범위·게시 시점 또는 비공개 상태
- [ ] 실제 공개 URL을 외부에서 열 수 있는지 확인했습니다. 증거: 정확한 URL·확인 시점·접근 조건·핵심 화면이며, 로컬 미리보기 URL은 제외
- [ ] 오류율·지연·핵심 사용자 결과·데이터 무결성의 중지와 rollback 기준을 확인했습니다. 증거: 기준값·관찰 창·결정권자·실행 명령 또는 절차
- [ ] 배포 실패·검증 거절·공개 보류를 성공으로 덮지 않았습니다. 증거: 실패 단계, 사용자 영향, 현재 서비스 상태와 다음 결정

판정 질문: 배포나 공개 승인이 거절되면 원격 산출물과 데이터는 어떤 상태로 남나요? 실패 시 fallback·rollback·restore 중 무엇이 필요한가요? 실행 뒤 이전 버전으로 돌렸다면 버전·URL·핵심 흐름·데이터·모니터링을 다시 확인했나요?

## 7. 운영과 감시

먼저 읽기: [로그·모니터링·백업](../../10-deployment-operations/logs-monitoring-backup/)에서 관측 신호·알림·백업·복구 훈련을 확인하세요.

- [ ] 현재 운영 버전과 실제 서비스 상태를 확인했습니다. 증거: 배포 식별자·전체 SHA·환경·확인 시점과 핵심 endpoint 또는 사용자 흐름
- [ ] 사용자 결과에 연결된 로그·지표·트레이스와 데이터 품질 신호를 정했습니다. 증거: 신호 이름·단위·수집 위치·정상 범위·누락 상태
- [ ] 오류율·지연·가용성·핵심 사용자 성공률을 실제로 관찰했습니다. 증거: 시간 구간·대상 환경·현재 값·기준값·데이터 공백
- [ ] 알림의 임계값·수신자·대응 시간·중복 억제·에스컬레이션 경로를 확인했습니다. 증거: 활성 규칙과 승인된 시험 알림 결과 또는 미시험 표시
- [ ] fallback이 작동하면 기능·정확도·최신성 저하가 사용자와 운영자에게 보입니다. 증거: 진입 신호·표시 화면·제한 범위·주 경로 복귀 조건
- [ ] 실제 계정·데이터를 사용하는 운영 확인은 승인된 읽기 전용 범위를 우선했습니다. 증거: 승인된 대상·행동·부작용 없음 또는 데이터 변경 승인과 전후 대사
- [ ] 백업 작업의 성공 로그와 복원 성공을 구분했습니다. 증거: 최근 백업 식별자·보존·암호화 상태와 별도의 격리 복원·무결성 검사 결과
- [ ] runbook에 탐지·피해 제한·연락·rollback·restore·재검증·종료 조건이 있습니다. 증거: 현재 문서 위치·소유자·최근 훈련 시점과 발견된 공백
- [ ] 운영 학습과 미해결 위험을 다음 요구·테스트·감시·복구 훈련에 반영했습니다. 증거: 소유자·기한·추적 항목과 완료 판정 방법

판정 질문: 신호가 없어서 실패를 못 본 것과 실패가 없는 상태를 구분했나요? 운영 변경 승인이 거절되면 어떤 안전한 관찰을 계속할 수 있나요? fallback 중인 서비스를 정상으로 복구할 조건과 복귀 뒤 재검증할 사용자·데이터·지표는 무엇인가요?

## 8. 복구와 재검증

먼저 읽기: [되돌리기·충돌·릴리스](../../09-git-github/undo-merge-conflict-release/)와 [로그·모니터링·백업](../../10-deployment-operations/logs-monitoring-backup/)에서 변경 이력과 운영 복구를 확인하세요.

| 용어 | 실제 의미 | 단독으로 증명하지 못하는 것 |
|---|---|---|
| fallback | 주 경로가 실패할 때 제한된 대체 경로로 서비스를 이어 가는 것 | 주 경로가 복구됐거나 기능·정확도·최신성이 정상이라는 사실 |
| rollback | 코드·설정·배포 아티팩트를 이전에 검증된 버전 방향으로 되돌리는 것 | 데이터가 자동으로 이전 상태로 돌아갔거나 사용자 피해가 해소됐다는 사실 |
| restore | 백업이나 복제본에서 데이터·설정을 실제 대상에 되살리는 것 | 애플리케이션·권한·사용자 흐름까지 정상화됐다는 사실 |
| recovery | 피해 제한 뒤 fallback·rollback·수정·restore 등을 조합하고 필요한 서비스·사용자 결과·데이터를 재검증해 정상 상태를 회복하는 전체 과정 | 원인 제거, 재발 방지, 소유자 종료 승인까지 자동 완료됐다는 사실 |

- [ ] 먼저 사용자 피해·보안·데이터 손상과 확산을 제한했습니다. 증거: 영향 범위·중지 조치·시점·결정권자와 제한 뒤 상태
- [ ] 최근 변경·현재 버전·데이터 상태·관측 신호를 사실과 추측으로 나눴습니다. 증거: 타임라인, 배포·설정 이력, 로그·지표·질의 결과
- [ ] fallback·rollback·수정·restore 중 필요한 조합과 각 한계를 정했습니다. 증거: 선택 이유·대상·예상 부작용·성공 오라클·중지 조건
- [ ] 데이터 수정·삭제·restore나 파괴적 복구 명령 전에 정확한 대상과 별도 승인을 확인했습니다. 증거: 승인자·대상·백업·dry-run 또는 영향 미리보기와 실행 책임자
- [ ] backup 존재를 restore 성공으로 간주하지 않고 격리 환경에서 복원 가능성과 무결성을 검증했습니다. 증거: 복원 대상·복원 시점·행 수·해시·업무 불변식·실패 수
- [ ] rollback 뒤 코드·설정·스키마·데이터의 호환 조합을 확인했습니다. 증거: 실제 버전 조합, 마이그레이션 상태와 읽기·쓰기 핵심 흐름
- [ ] recovery 뒤 원래 실패 재현과 정상·경계·실패 경로를 다시 확인했습니다. 증거: 같은 입력·명령·브라우저·데이터 오라클의 새 결과
- [ ] 공개 URL·핵심 사용자 결과·데이터 무결성·오류율·지연·알림을 다시 확인했습니다. 증거: 대상·시간 구간·현재 값·기준값과 미검증 범위
- [ ] 복구 행동이 만든 새 비밀 노출·중복 처리·데이터 변경·사용자 피해를 확인했습니다. 증거: 보안·데이터 대사·외부 메시지·결제·권한 변경 점검 결과
- [ ] 서비스 정상화와 사건 종료를 구분하고 소유자 종료 승인을 받았습니다. 증거: 종료 승인자·시점·남은 위험·후속 소유자와 기한
- [ ] 원인·기여 요인·탐지 지연·거절된 대응·복구 판단·재발 방지 항목을 비난 없이 기록했습니다. 증거: 검토 기록과 각 후속 조치의 검증 기준

최종 판정에서도 체크 표시와 체크 수는 증거의 위치를 안내할 뿐입니다. 핵심 장의 판단 규칙, 실제 명령과 종료 코드, 브라우저·데이터·운영 관찰, 사람 검토와 소유자 승인을 직접 확인하고, 실패·거절·복구·재검증 기록이 남아 있을 때만 해당 범위의 완료를 판단하세요.
