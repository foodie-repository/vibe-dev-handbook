## 먼저 이렇게 찾으세요

아래 빠른 표는 뜻이 자주 섞이는 핵심 용어를 `한글 → 영문 → 약어 → 정의 → 관련 용어 → 흔한 오해 → 핵심 장` 순서로 보여 줍니다. 약어가 없으면 `—`로 표시합니다. 이어지는 범주별 표는 더 많은 용어의 정의와 보장하지 않는 범위를 찾는 색인입니다. 짧은 정의만으로 판단하지 말고 관련 핵심 장에서 시스템 위치·실패 방식·검증 증거까지 확인하세요.

| 한글 용어 | 영문 용어 | 약어 | 한 문장 정의 | 관련 용어 | 흔한 오해 | 핵심 장 |
|---|---|---|---|---|---|---|
| 제품 요구 문서 | Product Requirements Document | PRD | 누구의 어떤 문제를 왜 무엇으로 해결할지 합의하는 제품 요구 산출물입니다. | requirement, acceptance criterion | 기술 설계나 구현 완료 문서가 아닙니다. | [PRD·두 종류의 SDD·TDD](../../06-requirements-design/prd-sdd-tdd/) |
| 소프트웨어 설계 설명 | Software Design Description | SDD | 요구를 어떤 책임·경계·데이터·인터페이스로 실현할지 기록하고 전달하는 설계 설명입니다. | architecture, detailed design, ADR | Spec-Driven Development와 같은 뜻이 아니며 모든 프로젝트에 별도 파일 하나를 강제하지 않습니다. | [PRD·두 종류의 SDD·TDD](../../06-requirements-design/prd-sdd-tdd/) |
| 스펙 주도 개발 | Spec-Driven Development | SDD | 명시적 스펙을 계획·작업·구현으로 연결하고 단계별로 검토하는 개발 접근입니다. | specification, plan, task, traceability | Software Design Description이나 보편 표준 절차가 아닙니다. | [PRD·두 종류의 SDD·TDD](../../06-requirements-design/prd-sdd-tdd/) |
| 테스트 주도 개발 | Test-Driven Development | TDD | 다음 동작을 테스트로 먼저 표현하고 실패·최소 구현·리팩터링을 짧게 반복하는 구현 규율입니다. | test oracle, refactoring, regression | 테스트 문서나 사후 테스트 추가와 같은 뜻이 아닙니다. | [PRD·두 종류의 SDD·TDD](../../06-requirements-design/prd-sdd-tdd/) |
| 소프트웨어 개발 생명주기 | Software Development Life Cycle | SDLC | 발견부터 요구·설계·구현·검증·배포·운영·학습까지 소프트웨어를 만들고 유지하는 전체 생명주기입니다. | verification, validation, operations evidence | 모든 팀이 한 번씩 통과하는 고정 선형 순서가 아닙니다. | [소프트웨어 개발 생명주기](../../07-workflow-methods/software-development-lifecycle/) |
| 프레임워크 | framework | — | 반복 골격과 기본 제어 흐름을 제공하고 정한 수명 주기에서 사용자 코드를 호출할 수 있는 기술입니다. | library, runtime, platform | 제품 이름만으로 실제 제어 관계가 결정되지는 않습니다. | [아키텍처와 프레임워크](../../06-requirements-design/architecture-and-frameworks/) |
| 라이브러리 | library | — | 애플리케이션이 필요할 때 호출해 쓰는 재사용 코드 묶음입니다. | framework, dependency, module | 언제나 작거나 프레임워크보다 덜 중요한 기술이라는 뜻이 아닙니다. | [아키텍처와 프레임워크](../../06-requirements-design/architecture-and-frameworks/) |
| 런타임 | runtime | — | 코드를 실제로 실행하고 프로세스·파일·네트워크 기능에 접근하게 하는 엔진과 환경입니다. | process, environment, deployment environment | 프레임워크나 호스팅 플랫폼과 자동으로 같은 범위가 아닙니다. | [아키텍처와 프레임워크](../../06-requirements-design/architecture-and-frameworks/) |
| 플랫폼 | platform | — | 만들기·실행·배포·운영을 위한 기반 기능과 제한을 제공하는 환경입니다. | runtime, hosting, development tool | 데이터·권한·복구 책임을 전부 대신하는 기본 정답이 아닙니다. | [아키텍처와 프레임워크](../../06-requirements-design/architecture-and-frameworks/) |
| 대체 경로 | fallback | — | 주 경로가 실패하거나 사용할 수 없을 때 제한된 기능이나 다른 경로로 영향을 줄이는 대응입니다. | rollback, recovery, feature flag | 원래 상태로 되돌리거나 근본 원인을 해결했다는 뜻이 아닙니다. | [로그·모니터링·백업](../../10-deployment-operations/logs-monitoring-backup/) |
| 되돌리기 | rollback | — | 아직 확정되지 않았거나 새로 활성화한 변경을 정한 이전 상태로 되돌리는 방향입니다. | transaction rollback, deployment rollback, roll-forward | 데이터·스키마·외부 부작용까지 자동으로 되돌아간다고 볼 수 없습니다. | [되돌리기·충돌·릴리스](../../09-git-github/undo-merge-conflict-release/) |
| 복원 | restore | — | 백업에서 데이터나 설정을 다시 꺼내 사용 가능한 상태로 만드는 작업입니다. | backup, recovery, RPO, RTO | 서비스 전체가 정상화됐다는 뜻이 아닙니다. | [로그·모니터링·백업](../../10-deployment-operations/logs-monitoring-backup/) |
| 복구 | recovery | — | 데이터·설정·애플리케이션·권한·외부 상태를 연결하고 재검증해 필요한 서비스를 다시 제공하는 과정입니다. | restore, rollback, operations evidence | 파일 복원이나 프로세스 재시작 한 번과 같은 뜻이 아닙니다. | [로그·모니터링·백업](../../10-deployment-operations/logs-monitoring-backup/) |
| 지속적 통합 | Continuous Integration | CI | 팀 변경을 공유 코드에 자주 통합하고 각 통합을 자동 빌드와 테스트로 빠르게 확인하는 규율입니다. | code review, continuous delivery | CI 서비스의 초록 표시 하나와 같은 뜻이 아닙니다. | [코드 리뷰와 CI/CD](../../07-workflow-methods/code-review-ci-cd/) |
| 지속적 전달 | Continuous Delivery | CD | 검증된 변경을 언제든 배포할 수 있는 상태로 유지하되 운영 반영 결정을 별도로 둘 수 있는 방식입니다. | artifact, release, deploy | 운영 환경에 항상 자동 배포한다는 뜻이 아닙니다. | [코드 리뷰와 CI/CD](../../07-workflow-methods/code-review-ci-cd/) |
| 지속적 배포 | Continuous Deployment | CD | 정한 자동 게이트를 통과한 변경을 운영 환경까지 자동으로 반영하는 방식입니다. | continuous delivery, monitoring, rollback | 파이프라인 성공이 사용자·데이터·운영 성공을 보장하지 않습니다. | [코드 리뷰와 CI/CD](../../07-workflow-methods/code-review-ci-cd/) |
| 검증 | verification | — | 산출물과 시스템이 명시된 요구·설계·계약을 지키는지 증거로 확인하는 활동입니다. | validation, test oracle, evidence | 사용자 목적에 맞는지까지 혼자 증명하지 않습니다. | [테스트 전략](../../08-quality/testing-strategy/) |
| 타당성 확인 | validation | — | 결과가 실제 사용자 목적과 사용 맥락에 맞는지 증거로 확인하는 활동입니다. | verification, acceptance criterion | 자동 테스트 통과만으로 끝나지 않을 수 있습니다. | [테스트 전략](../../08-quality/testing-strategy/) |

## 시스템과 코드

| 용어 | 정의 |
|---|---|
| **software** | 컴퓨터가 수행할 명령뿐 아니라 설정, 데이터 구조, 문서, 운영 절차를 포함한 실행 시스템입니다. |
| **file** | 이름을 가진 데이터 단위입니다. 이름과 확장자만으로 원본·생성물·비밀 여부를 판단할 수 없으므로 상위 경로와 관리 규칙을 함께 확인합니다. |
| **directory / folder** | 파일과 다른 디렉터리의 이름을 묶어 계층을 만드는 공간입니다. 그래픽 화면에서는 보통 폴더라고 부릅니다. |
| **path** | 파일이나 디렉터리의 위치를 이름의 순서로 표현한 값입니다. 경로가 존재해도 파일의 역할·권한·Git 상태까지 보장하지는 않습니다. |
| **glob / pathname pattern** | `*`, `?`, `[...]` 같은 패턴을 파일명 후보와 맞춰 하나 이상의 경로를 선택하는 표현입니다. 정규 표현식과 같지 않으며 일치 실패·숨김 파일·재귀·인용 동작은 셸·도구·설정마다 확인해야 합니다. 삭제·이동·덮어쓰기 전에는 확장된 최종 대상 목록과 경계를 먼저 검증합니다. |
| **absolute path** | 파일 시스템 경로 계층의 시작점부터 대상을 표시한 경로입니다. 한 컴퓨터에서는 대상을 분명히 식별하지만 개인 설치 위치가 달라지면 재사용하기 어렵습니다. |
| **relative path** | 현재 작업 디렉터리나 도구가 정한 기준 위치에서 대상을 표시한 경로입니다. 기준 위치가 없으면 같은 문자열도 다른 대상을 가리킬 수 있습니다. |
| **current working directory(CWD)** | 실행 중인 셸이나 프로세스가 상대 경로를 해석할 때 사용하는 현재 디렉터리입니다. 설정 파일의 상대 경로는 다른 기준을 사용할 수 있습니다. |
| **project root** | 한 프로젝트의 설정·명령·소스 구조를 해석하는 기준 디렉터리입니다. Git 저장소 루트와 같을 수도 있고 하위에 있을 수도 있습니다. |
| **repository root** | Git이 현재 작업 트리의 최상위로 인식하는 디렉터리입니다. 작업 공간이나 프로젝트 루트와 같은지는 실제 Git 명령으로 확인해야 합니다. |
| **workspace** | 편집기나 코딩 에이전트가 이번 작업에서 열고 접근하도록 정한 범위입니다. 제품과 설정에 따라 하나의 저장소, 여러 저장소 또는 저장소 일부일 수 있습니다. |
| **generated file** | 다른 원본과 도구에서 다시 만들 수 있도록 생성된 파일입니다. Git 추적 여부와 무관하며 직접 수정하기 전에 원본·생성 명령·보존 필요성을 확인합니다. |
| **source code** | 사람이 읽고 수정하는 프로그램 원본입니다. |
| **abstraction** | 특정 목적에 필요한 속성과 동작을 드러내고 그 판단에 불필요한 구현 세부를 경계 뒤로 숨기는 설계입니다. 숨긴 세부가 없어지는 것은 아니며 외부 동작에 영향을 주면 다시 확인해야 합니다. |
| **abstraction leak** | 경계 뒤에 숨긴 성능·네트워크·데이터·실행 환경 같은 내부 특성이 외부 동작이나 사용자의 판단에 영향을 주는 상황입니다. 모든 내부를 공개하기보다 판정에 필요한 신호와 오류 계약을 보강합니다. |
| **trade-off** | 한 이점을 얻는 대신 생기는 비용과 제약을 함께 받아들이는 선택입니다. 장단점 나열이 아니라 현재 제약·우선순위·재검토 신호와 함께 기록합니다. |
| **component** | 시스템 안에서 한 책임을 중심으로 구분해 생각할 수 있는 부분입니다. 반드시 별도 서버나 프로세스일 필요는 없습니다. |
| **responsibility** | 구성요소가 맡고 보장해야 하는 일과 실패 처리 범위입니다. |
| **boundary** | 책임, 신뢰, 소유권 또는 실행 환경이 달라지는 경계입니다. 경계를 넘는 값은 검증이 필요합니다. |
| **trust boundary** | 서로 다른 신뢰 수준이나 권한 주체 사이에서 데이터와 제어가 오가는 경계입니다. 브라우저와 서버 사이처럼 사용자가 값을 바꿀 수 있는 경계에서는 신원·권한·입력과 중요한 업무 규칙을 신뢰 가능한 쪽에서 다시 검증합니다. |
| **interface** | 구성요소가 경계를 넘어 입력·출력·오류를 주고받는 약속입니다. API뿐 아니라 함수, 파일과 데이터 스키마도 인터페이스가 될 수 있습니다. |
| **source of truth** | 특정 상태의 최종 값을 결정하고 충돌을 해결하는 권위 있는 원본입니다. 시스템 전체에 하나만 있어야 한다는 뜻이 아니라 상태 종류마다 책임 위치가 다를 수 있습니다. |
| **runtime** | 코드를 실제로 해석·실행하고 프로세스·파일·네트워크 같은 시스템 기능에 접근하게 하는 엔진과 환경입니다. 지원 언어·버전·권한과 배포 환경의 호환 범위를 확인해야 합니다. |
| **library** | 애플리케이션이 필요할 때 호출해 사용하는 재사용 코드 묶음입니다. 실제 호출 주도권과 교체 경계는 생태계·패키지마다 확인해야 합니다. |
| **framework** | 애플리케이션의 반복 골격과 기본 제어 흐름을 제공하고 정해진 진입점·수명 주기에서 사용자의 코드를 호출할 수 있는 기술입니다. 라이브러리와의 구분은 생태계마다 겹치므로 이름보다 실제 제어 관계와 벗어날 때의 비용을 확인합니다. |
| **platform** | 애플리케이션을 만들고 실행·배포·운영할 기반 기능과 제한을 제공하는 환경입니다. 하나의 플랫폼이 런타임·호스팅·데이터·도구 역할을 함께 제공할 수 있으므로 실제 책임 범위를 확인해야 합니다. |
| **development tool** | 편집·검사·빌드·테스트·배포·관측 같은 개발 작업을 돕는 수단입니다. 도구의 실행 성공이 애플리케이션의 정확성·배포·사용자 성공을 자동으로 증명하지는 않습니다. |
| **SDLC(Software Development Life Cycle)** | 문제 발견부터 요구사항·설계·구현·검증·배포·운영·학습까지 소프트웨어를 만들고 유지하는 전체 생명주기입니다. 단계 이름과 순서는 조직마다 다르며 새 증거에 따라 이전 결정을 반복해서 수정합니다. |
| **architecture** | 중요한 품질과 제약을 만족하도록 구성요소의 책임·경계·관계·상태·데이터·배치를 정한 구조적 결정입니다. 그림이나 제품 목록이 아니라 결정 이유·대안·검증 증거·변경 조건과 함께 설명해야 합니다. |
| **detailed design** | 아키텍처가 정한 경계 안에서 모듈·API·스키마·상태 전이·오류 처리·알고리즘을 구현 가능한 수준으로 구체화한 설계입니다. 모든 상세 선택이 아키텍처 결정인 것은 아닙니다. |
| **implementation** | 설계를 실제 코드·설정·마이그레이션·테스트와 빌드 아티팩트로 실현하는 활동과 결과입니다. 구현 완료가 사용자 목적이나 운영 성공까지 자동으로 증명하지는 않습니다. |
| **technology stack / tech stack** | 시스템을 구현·실행·배포하는 데 선택한 언어·프레임워크·라이브러리·런타임·플랫폼·도구의 이름과 버전 묶음입니다. 책임 배치와 선택 이유가 없으면 아키텍처 설명을 대신하지 못합니다. |
| **quality attribute** | 기능의 종류가 아니라 시스템이 얼마나 빠르고 안전하고 접근 가능하며 변경·복구하기 쉬워야 하는지를 나타내는 품질 조건입니다. |
| **constraint** | 예산, 법규, 호스팅 범위, 개인정보 금지처럼 설계가 반드시 지켜야 하는 조건입니다. |
| **module** | 한 책임을 중심으로 관련 코드와 인터페이스를 묶은 단위입니다. |
| **dependency** | 프로젝트가 기능을 실행·빌드·검증하기 위해 필요로 하는 외부 또는 내부 구성요소입니다. 프로젝트가 직접 선언한 의존성과 그 구성요소가 다시 요구하는 전이 의존성을 구분해야 합니다. |
| **configuration** | 환경과 배포에 따라 달라지는 동작 값을 코드와 분리한 설정입니다. |
| **requirement** | 사용자의 문제와 목표를 실현하기 위해 시스템이 제공해야 할 능력이나 지켜야 할 조건입니다. 해결 방법 자체와 구분해야 합니다. |
| **acceptance criterion** | 요구사항이 충족됐는지 이해관계자가 관찰하고 판정할 수 있도록 조건과 기대 결과를 구체화한 기준입니다. 테스트 케이스 하나와 같은 뜻은 아닙니다. |
| **PRD(Product Requirements Document)** | 누구의 어떤 문제를 왜 무엇으로 해결할지 합의하는 제품 요구 문서입니다. 제품·조직마다 형식은 다르며 기술 설계와 구현 증거를 대신하지 않습니다. |
| **Software Design Description(SDD)** | 요구를 어떤 책임·경계·데이터·인터페이스로 실현할지 기록하고 설계 이해관계자에게 전달하는 설명입니다. `SDD`를 쓸 때는 Spec-Driven Development와 첫 등장부터 구분합니다. |
| **Spec-Driven Development(SDD)** | 검토 가능한 스펙을 계획·작업·구현으로 연결하는 개발 접근입니다. 하나의 보편 표준이나 Software Design Description 문서와 같은 뜻이 아닙니다. |
| **TDD(Test-Driven Development)** | 다음 작은 동작의 테스트를 먼저 쓰고 올바른 실패를 확인한 뒤 최소 구현과 리팩터링을 반복하는 구현 규율입니다. 테스트 문서 종류나 사후 테스트 추가를 뜻하지 않습니다. |
| **traceability** | 요구사항이 설계 결정, 작업, 테스트와 운영 증거 중 어디에 연결되는지 추적할 수 있는 성질입니다. |

## 웹과 풀스택

| 용어 | 정의 |
|---|---|
| **frontend** | 사용자의 입력과 화면, 브라우저 상태, 상호작용을 담당하는 계층입니다. |
| **backend** | 신뢰할 수 있는 업무 규칙, 권한, 데이터 처리, 외부 연동을 담당하는 서버 계층입니다. |
| **full-stack** | 사용자 화면부터 서버·데이터·배포와 운영까지 연결된 전체 범위입니다. 모든 기술을 한 사람이 깊게 안다는 뜻으로 제한하지 않습니다. |
| **client** | 한 상호작용에서 다른 구성요소에 기능이나 데이터를 요청해 서비스를 사용하는 역할을 맡은 프로그램입니다. 브라우저·모바일 앱·명령줄 도구가 대표적이며, 백엔드 프로그램도 외부 API를 호출할 때는 그 API의 클라이언트가 됩니다. |
| **server** | 한 상호작용에서 요청을 받아 규칙을 실행하고 데이터 또는 결과를 응답하는 역할을 맡은 프로그램입니다. 원격 또는 로컬에서 실행될 수 있고, 일상적으로는 그 프로그램이 실행되는 호스트나 환경까지 서버라고 부르므로 문맥을 확인해야 합니다. |
| **API** | 구성요소가 어떤 입력을 받고 어떤 결과·오류를 돌려주며 어떤 권한 조건을 요구하는지 정할 수 있는 인터페이스 계약입니다. API 설명이나 명세가 있다는 사실만으로 실행 중인 구현의 준수를 증명하지는 않습니다. |
| **endpoint** | API의 기능에 구체적인 메서드와 경로 등으로 접근하는 지점입니다. endpoint 하나가 API 전체나 백엔드 전체를 뜻하지는 않습니다. |
| **HTTP** | 웹에서 요청과 응답을 교환하는 프로토콜입니다. |
| **HTTPS** | HTTP 메시지를 전송 계층 보안(Transport Layer Security, TLS)으로 보호해 전송 중 도청과 변조 위험을 줄이는 통신 방식입니다. HTTPS를 쓴다는 사실만으로 서버의 권한·입력 검증이 자동으로 안전해지는 것은 아닙니다. |
| **URL** | 네트워크 자원의 위치와 접근 방식을 표현하는 주소입니다. |
| **status code** | HTTP 응답 결과의 범주를 나타내는 숫자 코드입니다. |
| **safe method** | 서버 자원의 상태를 의도적으로 바꾸지 않도록 정의된 HTTP 메서드의 성질입니다. 멱등성과 관련 있지만 같은 뜻은 아닙니다. |
| **idempotency** | 같은 요청을 여러 번 보내도 서버에 의도한 최종 효과가 한 번 보냈을 때와 같은 성질입니다. 변화가 전혀 없다는 뜻은 아닙니다. |
| **origin** | 브라우저가 출처를 구분할 때 사용하는 URL의 프로토콜 부분(`http` 또는 `https`), 호스트와 포트 조합입니다. 이 셋 중 하나가 다르면 다른 출처입니다. |
| **CORS(Cross-Origin Resource Sharing)** | 브라우저가 다른 출처의 응답을 현재 페이지에 공유할 수 있는지 서버의 응답 헤더와 대조하는 HTTP 기반 교차 출처 규칙입니다. 요청에 따라 사전 요청이 먼저 실행될 수 있으며 인증·인가를 대신하지 않습니다. |
| **mixed content** | HTTPS 문맥이 HTTP 자원을 불러와 보호 수준이 섞인 상태입니다. 자원 종류와 브라우저 정책에 따라 HTTPS로 자동 업그레이드되거나 차단될 수 있으므로 실제 요청·응답을 확인해야 합니다. |
| **JSON** | API에서 자주 사용하는 구조화된 텍스트 데이터 형식입니다. |
| **HTML(HyperText Markup Language)** | 웹 콘텐츠의 구조와 의미를 표현하는 마크업 언어입니다. 화면의 모양이나 모든 동작을 담당하지 않습니다. |
| **semantic HTML** | 콘텐츠와 조작의 목적에 맞는 HTML 요소와 구조로 제목·영역·목록·링크·버튼·입력의 의미를 표현하는 방식입니다. 올바른 요소 선택은 접근성의 기반이지만 이름·상태·키보드 흐름과 실제 사용 검증까지 자동으로 끝내지는 않습니다. |
| **CSS(Cascading Style Sheets)** | HTML 요소의 배치와 표현 규칙을 기술하는 스타일 언어입니다. 콘텐츠의 의미 구조를 대신하지 않습니다. |
| **JavaScript** | 브라우저에서 사용자 행동, 데이터 처리와 화면 상태 변화를 실행하는 프로그래밍 언어입니다. JavaScript가 HTML과 CSS의 책임까지 없애는 것은 아닙니다. |
| **DOM** | 브라우저가 문서 구조를 프로그램이 접근하고 변경할 수 있게 표현한 모델입니다. |
| **CSSOM(CSS Object Model)** | 스크립트가 스타일 시트·규칙·선언 같은 CSS 관련 상태에 접근하고 바꿀 수 있도록 정의한 객체 모델과 API입니다. 브라우저의 모든 내부 스타일 계산·레이아웃·페인트 구현을 그대로 나타내는 말은 아닙니다. |
| **accessible name** | 링크·버튼·입력 같은 사용자 인터페이스 구성요소를 보조 기술이 식별할 때 사용하는 이름입니다. 보이는 레이블이 있으면 같은 문구를 포함하고 실제 계산 결과를 확인해야 하며 `aria-label` 속성 하나와 동의어가 아닙니다. |
| **responsive design** | 뷰포트·확대·방향·입력 조건이 달라질 때 정보와 기능의 우선순위를 보존하면서 배치와 표현을 적응시키는 설계 방법입니다. 특정 모바일 화면 한 장의 모양이나 기기 이름별 픽셀 맞춤과 같지 않습니다. |
| **reflow** | 화면이 좁아지거나 콘텐츠가 확대될 때 정보·기능을 잃지 않고 읽기 흐름에 맞춰 재배치되는 동작입니다. WCAG의 정확한 판정에서는 2차원 배치가 필요한 콘텐츠의 예외와 나머지 페이지 범위를 구분해야 합니다. |
| **rendering** | 데이터와 문서와 스타일을 사용자가 보는 화면으로 만드는 과정입니다. |
| **state** | 시스템 또는 UI가 현재 기억하고 있는 값입니다. |
| **optimistic UI** | 서버 확정을 기다리기 전에 성공을 예상해 화면을 먼저 바꾸고 이후 실제 결과와 조정하는 표현 전략입니다. 빠른 피드백을 줄 수 있지만 권위 상태·인가·동시성·중복 방지를 보장하지 않으므로 pending·confirmed·rejected·unknown과 복구 경로를 구분해야 합니다. |
| **recovery oracle** | 결과가 불명확하거나 충돌한 뒤 현재 사실과 이전 작업의 처리 여부를 판정하는 근거와 조회 방법입니다. 화면 문구나 재시도 자체가 아니라 주체·대상·요청과 권위 상태를 연결해야 합니다. |
| **flow** | 사용자 행동, 데이터, 제어 또는 작업이 경계를 지나 입력에서 결과로 이어지는 경로입니다. 사용자 요청, 일정 기반 작업, 배포와 복구처럼 시작 조건과 발생 시점이 다른 흐름을 구분합니다. |

## 데이터와 백엔드

| 용어 | 정의 |
|---|---|
| **database** | 프로세스가 끝난 뒤에도 남아야 하는 상태를 구조와 무결성 규칙 아래 저장·조회·변경하고 동시 접근을 관리하는 시스템입니다. API의 요청 처리나 업무 권한 판단과 같은 책임은 아닙니다. |
| **schema** | 데이터 필드, 타입, 관계, 제약을 정의한 구조입니다. |
| **prepared statement / parameterized query** | 데이터 명령의 구조와 입력 값을 분리해 값이 명령 일부로 해석될 위험을 줄이는 실행 방식입니다. 구체적인 API는 데이터베이스·드라이버마다 확인해야 하며 인가·입력 범위·업무 규칙 검증을 대신하지 않습니다. |
| **data contract** | 데이터를 만드는 쪽과 사용하는 쪽이 필드·타입·의미·단위·시간·품질·변경·오류를 주고받는 약속입니다. 스키마 파일만 뜻하지 않으며 계약 준수가 원천 값의 정확성을 자동 보장하지는 않습니다. |
| **canonical schema** | 서로 다른 원천을 한 시스템 안에서 일관되게 변환·검증·전달하기 위해 선택한 내부 기준 스키마입니다. 모든 원천에 보편적인 정답이 아니며 의미 차이를 억지로 없애서는 안 됩니다. |
| **data lineage** | 값이 어느 원천과 버전에서 들어와 어떤 변환·검증·산출물을 거쳐 사용자 결과에 도달했는지 추적하는 연결입니다. |
| **data freshness** | 데이터가 사용자 목적과 원천 발표 주기에 비춰 얼마나 최근 상태인지를 나타내는 품질입니다. 원천 발표·수집·변환·배포 시점을 구분해 판단해야 합니다. |
| **checksum** | 파일이나 데이터의 바이트 내용에서 계산한 비교용 값입니다. 전송·보존 중 내용 변화 탐지에 유용하지만 데이터의 의미·정확성·신뢰성을 증명하지는 않습니다. |
| **data model** | 업무 세계의 개체와 관계와 규칙을 데이터로 표현한 모델입니다. |
| **authoritative state** | 참가 여부·정원 승인·게시 버전처럼 특정 판단에서 기준으로 선택한 상태입니다. 모든 질문에 하나의 저장소가 항상 권위 있는 것은 아니므로 결정별 원본과 재조회 경로를 지정해야 합니다. |
| **derived state** | 권위 상태를 계산·변환·복제해 만든 값입니다. 원본에서 다시 만들 수 있어야 하며, 원본과 같은 시점의 값을 항상 보장하지는 않습니다. |
| **entity** | 시스템에서 별도로 식별하고 상태를 기억할 업무 대상입니다. 테이블 하나와 항상 일치하지 않으며 사용자·모임·참가 관계처럼 수명과 식별 기준을 먼저 정해야 합니다. |
| **attribute** | 개체나 관계를 설명하는 이름·정원·상태·시각 같은 값입니다. 화면에 보이는 문구와 장기 보존할 업무 사실을 구분해야 합니다. |
| **relationship** | 사용자와 모임 사이의 참가처럼 개체들이 어떤 의미로 연결되는지를 나타냅니다. 연결 수, 수명, 삭제·권한 규칙을 함께 정해야 합니다. |
| **primary key** | 한 테이블의 각 행을 고유하게 식별하도록 선택한 열 또는 열 조합입니다. 사람이 보는 제목처럼 바뀌거나 중복될 수 있는 값과 구분해야 합니다. |
| **foreign key** | 한 테이블의 값이 다른 테이블의 기본 키 같은 참조 대상과 연결되도록 무결성을 검사하는 제약입니다. 참조 존재를 확인하지만 그 행동의 업무 권한까지 자동으로 판단하지는 않습니다. |
| **migration** | 이미 저장된 데이터를 보존하면서 스키마와 데이터를 한 상태에서 다음 상태로 옮기는 변경 절차입니다. 파일 작성, 대상 적용, 데이터 변환, 호환성과 검증은 서로 다른 완료 조건입니다. |
| **backfill** | 새 구조나 규칙에 맞도록 이미 저장된 행에 값을 채우거나 변환하는 작업입니다. 대상 수·모호한 값·부분 실패·재실행·검증 계약이 필요합니다. |
| **backward compatibility** | 새 구조나 코드가 기존에 약속한 입력·데이터·사용 방식과 함께 동작할 수 있는 성질입니다. 전환 중 구버전·신버전 코드의 읽기와 쓰기를 나눠 확인해야 합니다. |
| **migration rollback** | 이미 적용된 스키마·데이터 변경을 이전 상태로 되돌리는 복구 방향입니다. 확정 전 트랜잭션을 취소하는 `ROLLBACK`과 다르며, 정보가 손실됐거나 신형 데이터가 기록됐다면 역변환이 불가능할 수 있습니다. |
| **roll-forward** | 잘못되거나 미완료된 상태를 추가 변경으로 보정해 목표 상태로 전진하는 복구 방향입니다. 중지·재실행·데이터 검증 조건 없이 무조건 앞으로 적용한다는 뜻이 아닙니다. |
| **database constraint** | 고유성, 필수 값, 참조 관계처럼 저장소가 데이터 무결성을 검사하고 위반한 변경을 거절하도록 정의한 규칙입니다. 애플리케이션의 입력 검증과 업무 규칙을 보완하지만 모두 대신하지는 않습니다. |
| **transaction** | 여러 데이터 변경을 하나의 논리적 작업으로 묶어 모두 반영하거나 모두 취소할 수 있게 하는 단위입니다. 한 HTTP 요청과 항상 일치하지 않으며 동시 수정 충돌 정책을 자동으로 정하지도 않습니다. |
| **commit** | 트랜잭션 안의 변경을 데이터베이스에 확정하는 동작입니다. 화면의 성공 표시만으로 commit 완료를 독립적으로 증명할 수는 없습니다. |
| **transaction rollback** | 트랜잭션에서 아직 확정되지 않은 변경을 취소해 일관된 이전 상태로 되돌리는 동작입니다. 과거 백업을 복원하는 운영 절차와 같은 뜻은 아닙니다. |
| **cache** | 원본을 빠르게 읽기 위한 임시 사본입니다. 원본 버전·생성 시각·허용 용도·만료·재검증·오래됨 표시와 사본 손실 뒤 재생성 경로가 필요합니다. |
| **queue** | 비동기 작업이나 메시지를 생산자와 소비자 사이에서 전달하는 장치입니다. 전달·처리 완료와 업무 원본을 구분하고 중복·순서·재시도·최종 보류·관측 계약을 제품별로 확인해야 합니다. |
| **eventual consistency** | 여러 사본이 즉시 같지 않을 수 있지만 새 변경이 멈추고 전달·처리가 정상적으로 계속되면 정한 조건 아래 같은 목표 상태로 수렴하도록 설계한 성질입니다. 허용 지연·수렴 조건·영구 실패 처리를 명시해야 합니다. |
| **reprocessing** | 실패하거나 보류된 작업을 다시 실행하는 활동입니다. 메시지를 다시 전달하기 전에 현재 권위 상태, 이전 처리 결과와 외부 부작용을 확인해야 합니다. |
| **authentication** | 요청 주체가 주장하는 계정이나 신원과 실제로 연결돼 있는지 자격 증명 등으로 확인하는 과정입니다. 로그인 성공은 특정 데이터에 대한 권한까지 자동으로 부여하지 않습니다. |
| **authorization** | 확인된 주체가 특정 대상에 특정 행동을 해도 되는지 정책에 따라 판단하고 신뢰할 수 있는 경계에서 집행하는 과정입니다. `Authorization` 헤더에 자격 증명이 있다는 사실과 같은 뜻이 아닙니다. |
| **session** | 인증 사건이나 작업 상태를 여러 요청에 걸쳐 연결하는 지속 상태입니다. 저장 위치·수명·폐기·탈취 대응을 설계해야 하며 세션의 존재가 모든 권한 판단을 대신하지는 않습니다. |
| **token** | 신원·세션·API 접근 같은 자격을 전달하거나 증명하는 데이터입니다. 형식, 수명, 폐기, 저장 위치, 서명·암호화 여부를 확인해야 하며 토큰이 있다는 사실만으로 특정 행동의 권한이 확정되지는 않습니다. |
| **MAC(Message Authentication Code)** | 메시지 인증 코드는 비밀 키와 메시지로 계산한 값을 대조해 내용이 바뀌지 않았는지 확인하는 방식입니다. 디지털 서명과 키를 다루는 방식이 다르고 내용을 숨기는 암호화도 아니므로 실제 형식과 보장을 따로 확인해야 합니다. |
| **digital signature** | 키를 사용해 메시지의 출처와 변경 여부를 검증할 수 있게 하는 암호학적 장치입니다. 서명된 내용이 자동으로 비밀이 되는 것은 아닙니다. |
| **encryption** | 허가되지 않은 주체가 내용을 읽기 어렵게 데이터를 변환해 기밀성을 보호하는 장치입니다. 암호화만으로 발신자 신원·업무 권한·데이터 정확성이 자동으로 증명되지는 않습니다. |

## 개발과 운영

| 용어 | 정의 |
|---|---|
| **local environment** | 개발자의 컴퓨터에서 실행되는 환경입니다. 운영과 설정·권한·데이터가 다를 수 있습니다. |
| **development server** | 개발 중 빠른 피드백을 위해 실행하는 서버입니다. 운영 서버와 동일하지 않을 수 있습니다. |
| **terminal** | 셸의 입력과 출력을 보여 주는 명령줄 인터페이스 앱·창·탭입니다. 터미널 화면은 셸 자체나 실행 중인 모든 프로세스와 같은 것이 아닙니다. |
| **shell** | 입력한 글자를 명령·인자·확장·리디렉션으로 해석해 내장 동작을 수행하거나 프로그램을 실행하는 명령 언어 인터프리터입니다. 문법과 기본 동작은 셸·운영체제마다 다를 수 있습니다. |
| **command** | 셸이나 도구에 수행할 동작과 인자를 표현한 입력입니다. 명령 문자열, 그 명령이 만든 프로세스, 실행 결과를 서로 구분해야 합니다. |
| **process** | 운영체제가 관리하는 실행 중 프로그램 인스턴스입니다. 같은 프로그램도 여러 프로세스로 실행될 수 있고, 터미널 창이나 프로젝트 전체와 같은 것이 아닙니다. |
| **PID(process ID)** | 프로세스의 생존 기간 동안 그 프로세스를 식별하는 숫자입니다. 재사용될 수 있으므로 과거 PID나 PID 하나만으로 현재 프로세스의 소유권·종료 허가를 판단하지 않습니다. |
| **port** | TCP·UDP 같은 전송 프로토콜에서 통신 끝점의 서비스 접근 대상을 구분하는 16비트 번호입니다. 통신 세션 전체나 애플리케이션 정체·안전성·정상 동작을 번호 하나로 증명할 수 없으므로 양쪽 주소·포트와 프로토콜, 상태, owning PID를 목적에 맞게 함께 확인합니다. |
| **environment variable** | 프로세스가 이름과 값으로 읽을 수 있도록 실행 환경에서 전달하는 설정입니다. 프로세스가 해당 이름을 읽어야 효과가 있으며, 비밀값을 로그·명령 기록에 출력하지 않아야 합니다. |
| **foreground job / foreground process** | POSIX 셸 문맥에서 셸이 완료나 정지를 기다린 뒤 다음 명령을 받는 작업과, 제어 터미널의 전경 프로세스 그룹에 속한 프로세스를 가리킵니다. 셸·운영체제의 job control 지원 범위를 확인해야 합니다. |
| **background job / background process** | 셸이 기다리지 않고 다음 입력을 받을 수 있게 실행한 작업과, 제어 터미널의 배경 프로세스 그룹에 속한 프로세스를 가리킵니다. 터미널에서 보이지 않는 모든 프로세스가 같은 방식의 배경 작업인 것은 아닙니다. |
| **exit code** | 명령 프로세스가 종료되며 호출자에게 돌려주는 숫자 상태입니다. 보통 0은 그 명령이 정의한 성공일 뿐 제품·배포·사용자 흐름 전체 성공은 아니며, 정확한 의미는 도구 문서를 확인합니다. |
| **package manager** | 의존성 선언과 설정을 읽어 버전을 선택·설치·갱신하고 관련 매니페스트와 잠금 파일을 관리하는 도구입니다. 파일명·해석·설치 효과와 보장 수준은 생태계와 도구마다 다릅니다. |
| **manifest** | 프로젝트가 필요로 하는 직접 의존성·허용 버전·실행 명령·도구 조건 등을 선언하는 파일입니다. 실제 선택된 전이 의존성 전체나 현재 실행 환경을 혼자 증명하지는 않습니다. |
| **lockfile** | 패키지 관리자가 실제로 선택한 직접·전이 의존성 조합을 기록해 설치 재현성을 높이는 파일입니다. 런타임·운영체제·설정·권한·외부 상태까지 고정하지 않으며 기록 범위와 보장은 도구마다 다릅니다. |
| **environment isolation** | 한 프로젝트의 패키지·실행 상태가 다른 프로젝트나 시스템 설치와 섞이지 않도록 범위를 나누는 방식입니다. 운영체제·비밀·네트워크·외부 데이터까지 자동으로 격리한다는 뜻은 아닙니다. |
| **version drift** | 시간이나 컴퓨터에 따라 실제 런타임·패키지 관리자·직접·전이 의존성 버전이 검증한 기준에서 달라지는 현상입니다. 선언 파일과 실제 버전·잠금 파일·환경 증거를 비교해 확인합니다. |
| **build** | 소스를 실행 또는 배포 가능한 아티팩트로 변환하는 과정입니다. |
| **artifact** | 특정 빌드가 생성해 배포·검토·보존의 대상으로 삼는 파일 묶음, 패키지 또는 이미지입니다. 어떤 소스와 설정에서 만들었는지 추적해야 합니다. |
| **deploy** | 검증된 아티팩트를 대상 환경에 전달하고 활성화하는 과정입니다. |
| **release** | 검증된 변경을 특정 사용자 또는 전체 사용자에게 제품 버전으로 제공하는 결정과 절차입니다. 배포와 같은 뜻으로 쓰이는지는 문맥을 확인해야 합니다. |
| **deployment environment** | local·preview·staging·production처럼 설정·권한·데이터·사용자 영향과 운영 책임이 다른 실행 또는 배포 대상입니다. |
| **hosting** | 사용자 요청에 파일이나 애플리케이션을 제공하는 실행 환경입니다. |
| **domain** | 사람이 읽는 서비스 주소입니다. |
| **DNS** | 도메인을 실제 네트워크 대상과 연결하는 이름 체계입니다. |
| **DNS record** | DNS 이름에 IP 주소·다른 호스트 이름·메일 처리 정보 같은 값을 연결해 표현하는 항목입니다. 레코드 종류와 허용 방식은 대상과 제공자 지침을 확인해야 합니다. |
| **authoritative nameserver** | 특정 도메인의 권위 있는 DNS 레코드 정보를 제공하도록 위임된 서버입니다. |
| **DNS resolver** | 사용자를 대신해 DNS 정보를 조회하고 캐시된 응답 또는 권위 있는 정보에서 결과를 찾는 구성요소입니다. |
| **TTL(Time To Live)** | DNS 응답을 resolver가 캐시할 수 있는 시간을 나타내는 값입니다. 모든 사용자의 갱신 완료 시각을 보장하지는 않습니다. |
| **base path** | 한 호스트에서 사이트가 제공되는 URL 경로 접두사입니다. 프로젝트 페이지처럼 루트가 아닌 경로에 배포할 때 자산·링크에 일관되게 반영해야 합니다. |
| **TLS certificate** | 공개 키와 호스트 같은 신원 정보를 인증 기관의 서명 등으로 연결해 HTTPS 상대를 검증하는 데 사용하는 인증 자료입니다. 애플리케이션 권한·데이터 정확성을 보장하지 않습니다. |
| **CI(Continuous Integration)** | 팀원이 변경을 공유 코드에 자주 통합하고 각 통합을 자동 빌드와 테스트로 검증해 오류를 빠르게 찾고 복구하는 개발 규율입니다. 자동 검사 서비스 실행만으로 지속적으로 통합했다고 단정할 수 없습니다. |
| **continuous delivery** | 통합·검증된 변경을 운영 환경에 언제든 배포할 수 있는 상태로 유지하되 실제 릴리스는 별도 사람 또는 사업 결정을 남길 수 있는 전달 방식입니다. |
| **continuous deployment** | 정해진 자동 게이트를 통과한 변경을 운영 환경까지 자동으로 배포하는 방식입니다. 파이프라인 성공이 사용자 흐름·데이터·운영 성공을 자동으로 증명하지는 않습니다. |
| **vertical slice** | 사용자 또는 다른 시스템이 관찰할 한 결과를 위해 필요한 화면·업무 규칙·데이터 같은 경계를 얇게 끝까지 연결한 작업 단위입니다. 파일 수가 적거나 기술 계층 하나만 끝낸 작업과 같지 않습니다. |
| **feature flag / feature toggle** | 배포된 코드 안의 기능 경로를 조건에 따라 켜거나 끄는 공개 제어입니다. 인가·데이터 호환성·복구를 대신하지 않으며 켜짐·꺼짐 시험과 소유자·만료·제거 조건이 필요합니다. |
| **fallback** | 주 경로가 실패하거나 사용할 수 없을 때 제한된 기능·이전 호환 경로·다른 공급자처럼 준비한 대체 경로로 영향을 줄이는 대응입니다. 원래 상태 복원이나 근본 원인 해결을 자동으로 뜻하지 않습니다. |
| **rollback** | 아직 확정되지 않았거나 새로 활성화한 변경을 정한 이전 상태로 되돌리는 방향입니다. 트랜잭션·Git·배포에서 대상과 동작이 다르며 데이터·외부 부작용까지 자동으로 되돌아가지는 않습니다. |
| **deployment rollback** | 운영에 활성화한 코드·아티팩트·설정 또는 라우팅을 이전에 검증한 상태로 되돌리는 복구 방향입니다. 데이터·스키마·외부 부작용까지 자동으로 되돌아간다는 뜻은 아닙니다. |
| **observability** | 외부 신호로 시스템 내부 상태와 실패 원인을 추론할 수 있게 만드는 능력입니다. |
| **event** | 요청·로그인 실패·참가 확정·배포·백업 실행처럼 시스템에서 관찰할 가치가 있는 한 번의 사건입니다. 사건 기록이나 전달은 현재 업무 상태와 같지 않을 수 있으므로 대상·버전·발생 시각·원본 재조회 계약을 구분해야 합니다. |
| **log** | 개별 이벤트와 그 문맥을 시간 순서로 남긴 기록입니다. 비밀·개인정보를 최소화하고 환경·버전·안전한 상관 식별자를 연결해야 합니다. |
| **metric** | 요청 수·오류율·지연 시간·데이터 최신성처럼 수치를 시간에 따라 집계한 신호입니다. 집계 방식·단위·시간 구간을 함께 확인해야 합니다. |
| **trace** | 한 요청이나 작업이 여러 구성요소를 통과한 경로와 시간을 연결한 기록입니다. 샘플링과 누락된 계측 때문에 전체 요청을 대표하지 않을 수 있습니다. |
| **monitoring** | 미리 정한 상태와 조건을 지속적으로 관찰해 이상을 발견하는 활동입니다. 관측 가능성과 경계는 도구·조직에 따라 다르게 쓰일 수 있습니다. |
| **alert** | 신호가 정한 조건을 충족했을 때 사람이나 자동화가 행동하도록 보내는 통지입니다. 영향·긴급성·담당자·첫 조치와 연결돼야 합니다. |
| **incident** | 사용자·데이터·보안·운영 목표에 의미 있는 영향을 주어 조정된 대응이 필요한 사건입니다. 심각도는 오류 수보다 실제 영향으로 판정합니다. |
| **SLI(Service Level Indicator)** | 사용자가 중요하게 여기는 서비스 수준을 실제로 측정한 값입니다. 성공 정의·분자·분모·기간·제외 조건을 밝혀야 합니다. |
| **SLO(Service Level Objective)** | 선택한 SLI가 특정 기간에 달성해야 하는 내부 목표입니다. 문서에 쓴 목표와 실제 달성 증거를 구분해야 합니다. |
| **SLA(Service Level Agreement)** | 서비스 수준과 미달 시 책임을 외부 당사자와 약속한 계약입니다. 모든 프로젝트에 필요한 것은 아니며 실제 계약 범위를 확인해야 합니다. |
| **backup** | 손실·손상·삭제 뒤 복구하는 데 사용할 목적으로 원본과 분리해 보존한 사본입니다. 파일 존재보다 복원 시험이 중요합니다. |
| **restore** | 백업에서 데이터나 설정을 다시 꺼내 사용 가능한 상태로 만드는 작업입니다. 운영 서비스를 다시 제공하는 전체 복구와는 범위가 다릅니다. |
| **recovery** | 데이터·설정·애플리케이션·권한과 외부 상태를 연결하고 검증해 필요한 서비스를 다시 제공하는 과정입니다. |
| **RPO(Recovery Point Objective)** | 장애 뒤 어느 시점까지의 데이터 손실을 받아들일 수 있는지 나타내는 복구 시점 목표입니다. 실제 백업 간격과 복원 결과가 목표를 뒷받침해야 합니다. |
| **RTO(Recovery Time Objective)** | 장애 뒤 필요한 서비스를 어느 시간 안에 복구해야 하는지 나타내는 복구 시간 목표입니다. 절차·권한·인력과 시험 소요 시간을 포함해 판단합니다. |
| **runbook** | 반복 가능한 확인·완화·복구 절차와 권한·중지 조건·예상 결과를 기록한 운영 문서입니다. 명령 목록만으로는 충분하지 않습니다. |
| **operations evidence** | 실제 환경의 사용자 흐름·권위 데이터·로그·지표·트레이스·인시던트·복구 결과를 대상 버전과 시간 범위에 연결한 운영 증거입니다. 신호 하나나 대시보드 화면만으로 전체 상태를 증명하지는 않습니다. |

## 품질과 변경 관리

| 용어 | 정의 |
|---|---|
| **bug** | 기대 또는 명세와 실제 동작의 차이로 발생하는 결함입니다. |
| **performance budget** | 특정 사용자 결과가 정한 환경과 통계 조건에서 지켜야 할 시간·자원·용량의 한도입니다. 다른 프로젝트의 예시 수치를 복사하지 않고 초과 시 행동과 변경 전후 측정 방법을 함께 정합니다. |
| **baseline** | 변경 효과를 비교하기 전에 같은 대상·환경·입력·측정 방법으로 기록한 기준 결과입니다. 한 번의 수치가 모든 사용자와 환경을 대표하지 않으므로 표본·분포·실패와 조건을 함께 남깁니다. |
| **bottleneck** | 전체 결과의 처리량이나 지연을 현재 제한하는 구간입니다. 느려 보이는 화면이나 자원 사용량만으로 추측하지 않고 프로필과 구분 실험으로 확인합니다. |
| **asset** | 공격·실수로 노출·변조·삭제·중단됐을 때 보호할 가치가 있는 데이터·권한·기능·서비스입니다. 자산별 영향과 책임자를 알아야 위협과 통제의 우선순위를 정할 수 있습니다. |
| **threat** | 어떤 주체나 사건이 자산의 기밀성·무결성·가용성 또는 정당한 사용을 해칠 수 있는 가능성입니다. 취약점이나 실제 사고 하나와 같은 뜻으로 제한하지 않습니다. |
| **least privilege** | 사용자·서비스·에이전트·프로세스에 맡은 작업에 필요한 최소 권한만 필요한 기간 동안 부여하는 원칙입니다. 역할 이름이 아니라 실제 허용·거절 범위와 회수·우회 경로로 검증합니다. |
| **input validation** | 신뢰 경계를 넘는 값이 허용된 형식과 업무 의미를 만족하는지 신뢰 가능한 쪽에서 확인하고 잘못된 입력을 안전하게 거절하는 통제입니다. 인가·출력 인코딩·안전한 쿼리 구성을 대신하지 않습니다. |
| **secret** | 유출되면 시스템·데이터·외부 서비스에 권한을 줄 수 있는 비밀번호·개인 키·접근 토큰·연결 자격 같은 값입니다. 저장 위치뿐 아니라 생성·전달·사용·회전·폐기·유출 대응의 수명주기를 관리해야 합니다. |
| **code review** | 저자 외의 사람이 변경의 의도·설계·정확성·테스트·위험을 검토하는 활동입니다. 리뷰 의견이나 AI 설명이 있다는 사실은 권한 있는 승인 결정과 같지 않습니다. |
| **approval** | 검토 결과와 정책에 따라 특정 변경을 다음 상태로 진행하도록 허용하는 결정입니다. 승인 대상 커밋·범위·승인자·시각과 이후 변경 여부를 함께 추적해야 합니다. |
| **debugging** | 증상을 재현하고 증거와 가설로 원인을 좁혀 수정하는 과정입니다. |
| **symptom** | 사용자나 시스템에서 관찰된 기대와 실제의 차이입니다. 원인에 대한 설명과 분리해 대상 버전·환경·시각·영향 범위와 함께 기록합니다. |
| **hypothesis** | 관찰 사실을 설명하는 가능한 원인과, 맞거나 틀릴 때 예상되는 결과를 함께 제시한 검증 가능한 설명입니다. 어떤 결과에도 맞는 추측은 구분 실험에 쓸 수 없습니다. |
| **root cause** | 문제 발생에 기여한 조건 중 수정하면 같은 실패의 재발 가능성을 실질적으로 낮출 수 있는 근본 조건을 가리키는 표현입니다. 복잡한 시스템에서는 단일 원인보다 여러 기여 조건·탐지·복구 공백이 함께 있을 수 있습니다. |
| **regression** | 변경 때문에 이전에 되던 동작이 깨지는 현상입니다. |
| **static testing** | 소프트웨어를 실행하지 않고 요구사항·설계·코드·설정 같은 산출물을 검토하거나 분석해 결함을 찾는 활동입니다. 정적 검사 통과가 런타임 상태나 사용자 흐름을 증명하지는 않습니다. |
| **dynamic testing** | 소프트웨어를 정한 조건에서 실행하고 실제 결과를 기대 결과와 비교하는 테스트입니다. 실행하지 않은 경로와 잘못된 오라클의 위험은 남을 수 있습니다. |
| **manual testing** | 사람이 정한 절차를 직접 수행하거나 탐색하며 결과를 관찰·판정하는 테스트 방식입니다. 실행 범위·fixture·기대 결과·관찰 기록이 없으면 재현 가능한 증거로 쓰기 어렵습니다. |
| **automated testing** | 도구가 정한 절차와 판정을 반복 실행하도록 만든 테스트 방식입니다. 빠른 반복을 돕지만 잘못된 오라클·환경·누락된 위험을 자동으로 교정하지 않습니다. |
| **test coverage** | 정한 코드 요소·분기·요구·조건 중 테스트가 다룬 정도를 나타내는 측정입니다. 높은 수치만으로 오라클의 정확성·중요 위험·사용자 성공을 증명하지는 않습니다. |
| **unit test** | 작은 코드 단위의 동작을 빠르게 확인합니다. |
| **integration test** | 여러 구성요소와 실제 경계가 함께 동작하는지 확인합니다. |
| **end-to-end test** | 사용자 관점의 핵심 흐름을 시스템 끝에서 끝까지 확인합니다. |
| **contract test** | API·이벤트·파일처럼 경계를 넘는 입력·출력·오류 형식과 호환성을 확인합니다. 형식 호환성이 업무 의미 전체의 정확성을 보장하지는 않습니다. |
| **smoke test** | 새 빌드나 배포가 시작되고 최소 핵심 기능이 응답하는지 빠르게 확인합니다. 상세 회귀 테스트를 대신하지 않습니다. |
| **verification** | 산출물과 시스템이 명시된 요구·설계·계약을 지키는지 증거로 확인하는 활동입니다. 조직과 표준에 따라 한국어 번역과 세부 범위가 달라질 수 있습니다. |
| **validation** | 결과가 실제 사용자 목적과 사용 맥락에 맞는지 증거로 확인하는 활동입니다. 자동 테스트뿐 아니라 사용자 관찰과 사람 판단이 필요할 수 있습니다. |
| **test oracle** | 테스트가 실제 결과를 기대 결과와 비교할 때 사용하는 판정 근거 또는 방법입니다. 오라클이 틀리면 잘못된 동작을 정답으로 보호할 수 있습니다. |
| **test double** | 실제 구성요소 대신 테스트에서 사용하는 mock·stub·fake 등의 대역입니다. 대역의 성공이 실제 경계의 성공을 증명하지는 않습니다. |
| **test fixture** | 테스트를 재현하기 위해 준비하는 데이터·파일·상태와 환경입니다. 개인정보·비밀정보를 복사하지 않고 실행 사이에 격리해야 합니다. |
| **flaky test** | 제품 코드가 바뀌지 않았는데도 시간·순서·공유 상태·외부 환경 등에 따라 통과와 실패가 오가는 불안정한 테스트입니다. |
| **refactoring** | 외부 동작을 유지하면서 내부 구조를 개선하는 변경입니다. |
| **technical debt** | 현재 속도를 위해 미래의 변경·운영 비용을 받아들인 결정 또는 누적된 구조적 비용입니다. 모든 나쁜 코드와 동의어는 아닙니다. |
| **breaking change** | 기존 사용자나 구성요소와 호환되지 않는 인터페이스 변경입니다. |

## 출처와 적용 범위

이 용어집은 하나의 표준을 번역한 목록이 아닙니다. 웹·데이터·Git·품질·운영·보안처럼 책임이 다른 범주를 다음 공식·1차 자료 묶음과 관련 핵심 장의 검토된 정의에 연결했습니다. URL별 확인일·문서 상태·직접 적용 범위·일반화 금지선은 저장소의 `research/source-map.md`에서 관리합니다.

- 생명주기·요구·설계: [ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html), [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html), [IEEE 1016-2009](https://standards.ieee.org/ieee/1016/4502/), [ISO/IEC/IEEE 42010:2022](https://www.iso.org/standard/74393.html)
