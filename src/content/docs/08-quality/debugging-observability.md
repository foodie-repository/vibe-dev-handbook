## 왜 필요한가

오류가 보이면 가장 빠른 행동은 코드를 바꾸는 것처럼 느껴집니다. AI도 오류 메시지를 보고 여러 “가능한 수정”을 즉시 제안합니다. 하지만 재현과 가설 없이 여러 파일을 바꾸면 증상이 우연히 사라져도 어느 변경이 왜 효과가 있었는지 알 수 없습니다. 캐시·재시작·데이터 변화가 문제를 숨겼을 수도 있고, 실제 원인은 남아 다음 환경에서 다시 나타날 수 있습니다.

디버깅은 수정 아이디어를 많이 내는 일이 아니라 **관찰 가능한 사실로 가능한 원인을 줄이고, 구분 실험으로 원인과 우연을 가르는 과정**입니다. 관측 가능성은 이 과정에 필요한 신호를 운영 중에도 얻을 수 있게 시스템을 설계하는 능력입니다.

## 한 문장 정의

디버깅은 증상을 재현하고 관찰에서 가설을 세워 통제된 실험으로 원인을 좁힌 뒤 수정·회귀 증거로 확인하는 활동이고, 관측 가능성(observability)은 로그·지표·트레이스 같은 외부 신호로 시스템의 내부 상태와 실패 원인을 추론할 수 있게 하는 능력입니다.

## 탐정 비유와 한계

디버깅은 현장의 흔적을 모아 용의자를 줄이고 알리바이를 확인하는 탐정 일과 비슷합니다. 증상은 사건 신고, 로그와 지표는 흔적, 가설은 가능한 설명, 구분 실험은 설명을 반박하거나 지지하는 확인에 대응합니다.

이 비유는 **증거 없이 결론을 내리지 않고 경쟁 가설을 줄인다**는 점에서만 맞습니다. 소프트웨어 실험은 시스템 상태를 바꾸고 이후 결과에 영향을 줄 수 있으며, 운영 장애에서는 사용자·데이터 손상을 먼저 멈춰야 합니다. 또 복잡한 장애에는 단일 “범인”이 아니라 여러 조건의 결합이 있을 수 있습니다. 따라서 이 비유로 반드시 하나의 근본 원인을 찾거나 운영 환경에서 위험한 재현을 강행해서는 안 됩니다.

## 디버깅의 아홉 칸

| 칸 | 질문 | 남길 증거 | 다음으로 가면 안 되는 신호 |
|---|---|---|---|
| 증상(symptom) | 무엇이 실제로 잘못 보이나? | 사용자·시스템 관찰, 시각, 영향 범위 | “안 된다”처럼 결과가 모호함 |
| 기대(expected) | 어떤 계약과 기준상 무엇이 일어나야 하나? | 요구·수용 기준·이전 정상 결과 | 현재 구현 출력을 기대값으로 복사함 |
| 재현(reproduction) | 어떤 입력·환경·버전에서 반복되는가? | 최소 절차, 데이터·설정, 성공/실패 빈도 | 환경과 대상 버전을 모름 |
| 관찰(observation) | 추측을 섞지 않은 사실은 무엇인가? | 로그·상태·diff·지표·트레이스 | “아마 DB 문제”처럼 해석이 섞임 |
| 가설(hypothesis) | 관찰을 설명하는 가능한 원인은 무엇인가? | 예측과 반증 조건이 있는 후보 | 어떤 결과가 나와도 맞다고 주장 가능함 |
| 실험(experiment) | 어느 가설을 구분할 가장 작은 확인은 무엇인가? | 명령·입력·변경·예상 결과·부작용 | 여러 변수를 동시에 바꿈 |
| 원인(cause) | 어떤 조건이 증상을 만드는 데 필요했나? | 재현·제거·반례와 신뢰 수준 | 상관관계 하나만 있음 |
| 수정(fix) | 원인을 제거하며 새 위험을 최소화하는 변경은 무엇인가? | 좁은 diff, 설계 이유, 복구 경로 | 증상만 숨기거나 오류를 무시함 |
| 회귀 검증(regression testing) | 같은 결함이 돌아오지 않고 주변 동작도 유지되는가? | 이번 결함 재현의 실패→성공, 기존 정상·거절 테스트의 통과 유지, 운영 확인 | 이번 결함 재현 테스트가 수정 전에도 통과함 |

이 순서는 이상적인 진단 지도입니다. 데이터 손상이나 대규모 장애에서는 먼저 트래픽 제한·기능 비활성화·이전 안전 상태로 전환해 영향을 줄이고 증거를 보존한 뒤 진단할 수 있습니다. 완화와 원인 수정은 다른 완료 상태입니다.

## 1. 증상과 기대를 분리합니다

“참가 API가 고장났다”는 증상과 원인 추측이 섞인 문장입니다. 다음 가상 예시처럼 관찰과 기대를 분리합니다.

```text wrap
증상: 2026-08-13 14:02 KST, staging의 참가 버튼을 한 번 눌렀는데 10초 뒤 화면이 `결과를 확인할 수 없음`으로 바뀌었다.
기대: 요청이 확정되면 참가 상태를 보여 주고, 응답을 잃으면 현재 상태를 다시 조회할 수 있어야 한다.
영향: 테스트 계정 1개에서 재현했으며 다른 사용자와 production 영향은 아직 확인하지 않았다.
```

브라우저 메시지만 보지 말고 서버 응답, 권위 데이터, 사용자 영향의 시각을 분리합니다. 화면의 실패가 서버 미처리를 뜻하지 않고, HTTP 성공이 업무 성공을 뜻하지 않을 수 있습니다.

## 2. 재현 조건을 최소화합니다

재현 기록에는 대상 버전·환경·입력·선행 상태·행동·결과가 있어야 합니다.

- 커밋·아티팩트·배포 환경과 런타임 버전
- 테스트 계정의 권한과 비밀이 아닌 안전한 식별자
- 모임 상태·정원·현재 참가 여부 같은 선행 데이터
- 브라우저·네트워크 조건과 정확한 행동 순서
- 항상/간헐적, 성공·실패 횟수와 첫 발생 시각
- 최근 정상 버전과 관련 diff

운영 데이터로 재현하면 실제 사용자에게 부작용을 줄 수 있습니다. 비운영 환경과 비식별 fixture를 우선하고, 운영에서 확인해야 한다면 읽기 전용 관찰·권한·중단 조건·증거 보존을 먼저 정합니다.

## 3. 관찰과 해석을 두 열로 나눕니다

| 관찰 사실 | 아직 가설인 해석 |
|---|---|
| 브라우저는 10초 뒤 요청을 중단했다 | 서버가 느리다 |
| 같은 요청 ID의 서버 로그에 `registration committed`가 있다 | 사용자는 참가가 확정됐다 |
| 데이터베이스에 참가 관계 한 건이 보인다 | 중복 방지가 항상 안전하다 |
| 배포 직후 p95 지연이 올랐다 | 방금 배포한 코드가 원인이다 |

p95는 정한 표본·기간에서 측정값의 약 95%가 그 값 이하에 놓이는 95번째 백분위수입니다. 평균이나 최댓값이 아니며 개별 요청의 지연을 보장하지 않습니다. 집계 구간·표본 수·계산 방식을 함께 기록해야 비교할 수 있습니다.

오른쪽 문장은 가능하지만 추가 증거가 필요합니다. 예를 들어 서버 로그가 다른 환경의 것일 수 있고, 같은 요청 ID의 생성·전파가 틀렸을 수 있습니다. 데이터 행도 현재 사용자·모임과 일치하는 권위 상태인지 확인해야 합니다.

## 4. 반증 가능한 가설을 세웁니다

좋은 가설은 원인 후보와 함께 관찰 가능한 예측을 말합니다.

```text wrap
가설 A: 참가 트랜잭션은 성공했지만 응답 직렬화 뒤 네트워크가 끊겼다.
예측: 같은 안전한 요청 상관 ID로 commit 기록과 참가 관계가 있고, 재조회는 참가 확정을 돌려준다.

가설 B: 정원 잠금 대기로 서버가 클라이언트 시간 제한을 넘겼다.
예측: 실패 구간의 trace에서 데이터베이스 대기 시간이 길고, 경쟁 요청이 없는 fixture에서는 재현되지 않는다.

가설 C: 브라우저 코드가 성공 응답을 잘못 파싱했다.
예측: Network 응답은 계약에 맞지만 console에 파싱 오류가 있고, 같은 응답 fixture의 단위 테스트가 실패한다.
```

과거에 비슷한 장애가 있었다는 사실은 우선순위를 정하는 참고이지 현재 원인의 증거가 아닙니다. 영향·최근 변경·발생 가능성·검사 위험·검사 비용으로 순서를 정합니다.

## 5. 한 번에 한 가설을 구분합니다

실험은 “고쳐 보기”가 아니라 가설을 줄이는 질문입니다.

1. 바꾸지 않을 기준 상태를 기록합니다.
2. 한 변수 또는 한 관찰 지점만 선택합니다.
3. 가설이 맞을 때와 틀릴 때의 예상 결과를 먼저 씁니다.
4. 실행 명령·입력·환경·시각과 결과를 남깁니다.
5. 실험이 만든 변경을 되돌리고 다음 결과에 미친 영향을 기록합니다.

재시작, 캐시 삭제, 시간 제한 증가, 로그 레벨 변경도 실험입니다. 상태를 바꾸고 증상을 숨기거나 성능을 더 악화할 수 있으므로 “일단 해봤다”로 실행하지 않습니다.

## 무작위 수정은 금지합니다

다음 행동은 원인 탐색을 방해합니다.

- 여러 파일·설정·의존성을 한 번에 바꾸기
- 실패 로그를 없애거나 예외를 삼켜 화면만 정상처럼 보이게 하기
- 테스트를 삭제·완화하거나 통과할 때까지 재실행하기
- 관련 없어 보이는 패키지를 최신 버전으로 일괄 갱신하기
- 운영 데이터를 직접 수정한 뒤 이전 상태를 기록하지 않기

수정 후보가 여러 개면 각각 어떤 가설을 검증하는지, 성공·실패 때 무엇을 배울지 적습니다. 아무 결과도 가설을 줄이지 못하면 실험 설계를 다시 합니다.

## 6. 원인, 가까운 원인과 기여 조건을 구분합니다

“null 오류”는 증상에 가까운 표현일 수 있습니다. 왜 null이 들어왔고 어떤 계약과 방어가 실패했는지까지 봅니다. 다만 모든 사건에 단 하나의 “root cause”가 있다고 가정하지 않습니다.

- **가까운 원인**: 현재 실패를 직접 일으킨 조건
- **기여 조건**: 실패 가능성이나 영향을 키운 설계·운영 조건
- **탐지 공백**: 더 일찍 발견하지 못한 테스트·관측·경보의 빈틈
- **복구 공백**: 영향을 줄이거나 안전 상태로 돌아가는 데 막힌 조건

상관관계만으로 인과를 확정하지 않습니다. 배포 시각과 오류 증가가 같아도 트래픽·외부 서비스·데이터 변화가 공통 원인일 수 있습니다. 원인을 재현하기 위험하거나 불가능하면 “확정” 대신 가능한 원인과 신뢰 수준, 반례와 미확인 범위를 기록합니다.

## 7. 수정과 완화와 복구를 분리합니다

| 상태 | 목적 | 예 |
|---|---|---|
| 완화(mitigation) | 사용자·데이터 피해를 빠르게 줄임 | 신규 참가 플래그 끄기, 트래픽 제한 |
| 수정(fix) | 원인을 만드는 코드·설계·설정을 바꿈 | 응답 계약 수정, 잠금 범위 축소 |
| 복구(recovery) | 서비스·데이터를 필요한 상태로 되돌림 | 잘못 생성된 중복 판정·정정, 안전 버전 활성화 |
| 예방(prevention) | 같은 종류의 결함 가능성과 탐지 시간을 줄임 | 계약 테스트, 불변식 검사, 경보·runbook 보강 |

증상이 사라진 것만으로 네 상태가 모두 완료되지 않습니다. 완화 뒤에는 원인이 남을 수 있고, 코드를 수정해도 이미 잘못된 데이터가 복구되지 않을 수 있습니다.

## 8. 이번 결함의 회귀 증거는 수정 전 실패와 수정 후 성공을 연결합니다

회귀는 변경으로 이전 동작이 깨지는 현상이며, 회귀 검증은 이를 찾아내는 활동입니다. 이번 결함을 재현·보호하려고 추가하는 테스트는 수정 전 대상 버전에서 의도한 이유로 실패하고 수정 후 같은 조건에서 성공해야 합니다. 주변의 정상·거절 동작을 보호하는 기존 회귀 테스트는 수정 전후 모두 통과하는 것이 정상입니다.

- 최소 재현을 자동화할 수 있나요?
- 테스트 오라클이 요구·계약·권위 데이터에서 왔나요?
- 테스트가 현재 구현 출력을 그대로 복사하지 않았나요?
- 간헐 실패라면 반복·격리·시간·동시성 조건을 기록했나요?
- 실제 경계의 결함을 대역 테스트 하나로만 덮지 않았나요?
- 운영에서 같은 사용자 결과와 신호가 회복됐나요?

이번 결함을 검출하려는 테스트가 수정 전에도 통과했다면 그 결함을 보호한다는 근거가 되지 못합니다. 기존 회귀 테스트의 통과는 주변 동작이 유지된다는 별도의 증거입니다. 새 테스트가 지나치게 넓고 flaky하면 장기적으로 실패 신호를 무시하게 만들 수 있습니다.

## 로그·지표·트레이스는 서로 다른 질문에 답합니다

### 로그(log): 이 사건에 무슨 일이 있었는가?

로그는 배포, 요청, 인가 거절, 데이터 변경 같은 개별 이벤트와 문맥을 시간 순서로 남깁니다. 구조화된 이벤트 이름, 환경·서비스·버전, 안전한 상관 식별자, 결과와 오류 종류를 포함하면 서로 다른 구성요소의 기록을 연결하기 쉽습니다.

상세 로그가 많다고 유용한 것은 아닙니다. 정상 요청마다 전체 본문을 남기면 비용과 노이즈, 개인정보 위험이 커지고 중요한 사건을 찾기 어려워집니다.

### 지표(metric): 얼마나 자주, 얼마나 오래, 얼마나 크게 일어나는가?

지표는 요청 수·성공률·오류율·지연·큐 길이·데이터 최신성 같은 값을 시간 구간으로 집계합니다. 이상 탐지와 영향 크기 비교에 유용하지만 개별 사용자의 경로와 원인을 혼자 설명하지는 않습니다.

분자·분모·단위·집계 구간·분위수·환경·버전을 기록하지 않은 “오류율 2%”는 해석하기 어렵습니다. 평균만 보면 일부 사용자의 긴 지연이 숨을 수 있습니다.

### 트레이스(trace): 한 요청이 어디를 거쳐 시간을 썼는가?

트레이스는 한 요청이나 작업이 여러 구성요소를 통과한 작업 구간과 시간을 연결합니다. 이때 이름·시작·종료 등으로 기록하는 한 작업 구간을 스팬(span)이라고 합니다. 데이터베이스 스팬의 전체 시간에는 쿼리 실행과 여러 대기가 섞일 수 있어 그 시간만으로 잠금 대기를 확정하지 않습니다. 분산 경계의 병목과 오류 위치를 찾는 데 유용하지만 샘플링, 누락된 계측, 잘못된 컨텍스트 전파 때문에 모든 요청과 내부 상태를 대표하지 않을 수 있습니다.

### 세 신호를 연결하는 질문

```text wrap
지표: 참가 요청 지연이 언제부터 어느 환경·버전에서 증가했는가?
트레이스: 느린 요청은 어느 구성요소와 구간에서 시간을 썼는가?
로그: 그 구간의 구체 이벤트·거절·재시도·데이터 결과는 무엇인가?
권위 상태: 실제 참가 관계와 정원 불변식은 현재 어떤가?
```

세 신호를 수집했다는 사실은 관측 가능성 완료나 원인 규명 증거가 아닙니다. 현재 질문에 필요한 식별자·버전·경계가 연결되고, 신호의 누락과 표본 한계를 설명할 수 있어야 합니다.

## 모니터링과 관측 가능성을 구분합니다

**모니터링(monitoring)**: 미리 정한 조건과 상태를 지속적으로 보고 이상을 알리는 활동입니다. “오류율이 5분 동안 임계값을 넘으면 알림”처럼 알려진 실패를 빠르게 찾는 데 강합니다.

**관측 가능성(observability)**: 미리 모든 질문을 알지 못해도 외부 신호를 탐색해 내부 상태와 새로운 실패를 추론할 수 있는 시스템 능력입니다. 충분한 문맥·상관 관계·고유 차원을 남기고, 사람이 질문을 좁힐 수 있게 해야 합니다.

두 용어는 조직과 도구에서 겹쳐 쓰이기도 합니다. 이 장의 구분을 보편 표준으로 강제하지 말고, 실제로 어떤 질문과 행동을 지원하는지 봅니다. 모니터링 대시보드가 있어도 새로운 원인을 탐색할 문맥이 없을 수 있고, 탐색 가능한 telemetry가 있어도 사용자 영향에 대한 경보가 없을 수 있습니다.

## 개인정보와 비밀을 남기지 않는 관측 설계

진단을 위해 모든 값을 로그에 남기면 안 됩니다. OWASP Logging Cheat Sheet는 다음과 같은 값을 직접 기록하지 않고 제거·마스킹·해시·암호화 등으로 다루도록 안내합니다.

- 비밀번호, 접근 토큰, 세션 식별자
- 데이터베이스 연결 문자열, 암호화 키와 주요 비밀
- 건강·정부 식별자 등 민감 개인정보
- 전체 요청·응답 본문과 애플리케이션 소스처럼 불필요하게 넓은 내용

안전한 상관 식별자도 원래 개인정보와 다시 연결될 가능성, 생성 범위, 보존 기간과 접근 권한을 검토해야 합니다. 이메일·이름 대신 무작위 요청 ID를 쓰더라도 그 ID가 영구 사용자 추적 키가 되면 개인정보 위험이 남습니다.

로그 설계에는 다음이 필요합니다.

1. 진단할 사건과 필요한 최소 필드
2. 수집 목적과 법적·조직상 허용 범위
3. 마스킹·해시·토큰화와 원문 접근 경계
4. 환경·서비스·역할별 접근 권한
5. 보존·삭제·변조 방지·감사 정책
6. 로그 자체의 실패·유실·시간 오차와 탐지 방법

## 반복 사례: 참가 버튼의 결과 불명 문제

### 증상과 재현

staging의 특정 커밋에서 정원 1자리가 남은 모임에 두 테스트 사용자가 거의 동시에 참가하면 한 브라우저가 결과 불명을 표시합니다. 정상 기대는 한 명만 확정되고 다른 한 명은 정원 마감을 받으며, 응답 손실 뒤에는 상태를 재조회하는 것입니다.

### 관찰

- 참가 요청 수는 2건, 브라우저 시간 제한은 10초입니다.
- trace 한 건에서 데이터베이스 span이 11초입니다.
- 로그에는 두 요청 모두 시작됐지만 한 요청의 응답 이벤트가 없습니다.
- 권위 데이터에는 참가 관계 한 건만 있고 정원 불변식은 유지됩니다.

### 가설과 구분 실험

가설 A는 동시성 잠금 대기가 클라이언트 시간 제한을 넘겼다는 것입니다. 같은 fixture에서 경쟁 요청 유무만 바꾸고 trace의 데이터베이스 대기와 응답 시각을 비교합니다. 가설 B는 브라우저 파싱 오류이며 저장한 계약 응답 fixture로 파서 테스트를 실행합니다.

### 원인·수정·회귀

경쟁 요청에서만 데이터베이스 대기가 시간 제한을 넘고 파서 테스트는 통과했다면 A를 지지합니다. 실제 DB의 경쟁 구간과 대기 종류를 별도 계측해 대조해야 하며, 요청을 거의 동시에 시작했거나 스팬이 길었다는 사실만으로 잠금 원인을 확정하지 않습니다. 수정은 무조건 시간 제한을 늘리는 것이 아니라 잠금과 정원 판정 경계를 검토하고, 결과 불명 뒤 안전하게 현재 상태를 확인하는 경로를 마련하는 것입니다.

이번 결함을 직접 검출하는 테스트와 이미 유지되던 데이터 조건을 나눕니다. 승인된 격리 환경의 가상 데이터에서 경쟁·응답 지연 또는 유실 조건을 통제하고 다음을 판정합니다.

- 시간 초과 뒤 결과 불명을 표시하고, 처리 중일 수 있는 이전 요청이 안전하게 종결됐는지 확인하기 전에는 새로운 참가 쓰기를 보류합니다.
- 인증된 사용자가 자신의 현재 참가 상태를 재조회할 수 있고, 확인된 상태를 화면에 반영합니다. 현재 상태만으로 특정 과거 요청의 처리 결과나 종결을 단정하지 않습니다.
- 재조회가 실패하면 결과 불명을 유지합니다. 정해진 시간 안에 반드시 결과를 알 수 있다고 보장하거나 실패를 미참가로 바꿔 새 쓰기를 허용하지 않습니다.
- 수정 전에는 위 확인 경로가 없어 해당 테스트가 의도한 이유로 실패하고, 수정 후에는 같은 조건에서 확인 경로와 실패 시 불명 유지가 통과해야 합니다.
- 별도 장애 없는 정원 경쟁에서는 한 명 확정·다른 한 명 정원 마감, 활성 중복과 부분 변경이 없음을 확인합니다. 이 데이터 조건은 수정 전에도 지켜졌으므로 이번 결과 불명 결함의 해소를 단독으로 증명하지 않습니다.

지연 개선도 목표라면 같은 fixture·실제 경쟁 조건·환경·측정 구간에서 요청 지연의 분포·p95와 실패 수를 전후 비교합니다. 운영 신호의 지연·결과 불명 비율 회복은 별도 관찰이며 격리 테스트를 대신하지 않습니다.

이 사례의 신호는 한 가능한 진단 경로일 뿐 실제 제품·데이터베이스 동작을 주장하지 않습니다.

## AI와 작업할 때의 요청 계약

```text wrap
아직 코드를 수정하지 마세요.

1. 증상 / 기대 / 영향 범위 / 대상 버전·환경을 분리하세요.
2. 개인정보·비밀을 출력하지 않는 최소 재현 절차를 제시하세요.
3. 로그·지표·트레이스·권위 상태·최근 diff에서 관찰 사실만 표로 만드세요.
4. 가능한 원인 가설을 최대 세 개로 제한하고 각 가설의 예측·반증 조건을 쓰세요.
5. 한 번에 한 가설을 구분할 최소·읽기 전용 우선 실험과 부작용·중단 조건을 쓰세요.
6. 완화 / 원인 수정 / 데이터·서비스 복구 / 재발 방지를 구분하세요.
7. 이번 결함 재현 테스트의 수정 전 실패·수정 후 성공, 기존 회귀 테스트의 통과 유지, 운영 확인을 구분해 설계하세요.
8. 원인을 확정할 수 없으면 신뢰 수준·반례·미확인 범위를 남기세요.

여러 파일·설정·의존성을 동시에 바꾸거나, 오류를 숨기거나, 테스트가 통과할 때까지 재실행하지 마세요. 각 제안이 어떤 가설을 줄이는지 설명하세요.
```

AI가 수정안을 먼저 내면 “이 변경이 구분하는 가설은 무엇이며 반대 결과가 나오면 무엇을 배우는가?”를 물어야 합니다.

- [ ] 관찰 사실과 해석을 두 열로 나눴나요?
- [ ] 각 가설에 예측과 반증 조건이 있나요?
- [ ] 한 실험에서 한 변수만 바꾸고 부작용을 기록했나요?

최근 오류 하나를 `증상 / 기대 / 재현 / 관찰 / 가설 / 실험 / 원인 / 수정 / 회귀` 아홉 칸으로 다시 정리하세요. 관찰과 해석을 각각 다른 색으로 표시하고, 로그·지표·트레이스 중 현재 없는 신호 하나를 골라 어떤 최소 필드가 진단 시간을 줄이는지 쓰세요. 마지막으로 그 필드가 개인정보나 비밀을 노출하지 않는지도 검토하세요.

- [Google SRE Book의 Effective Troubleshooting](https://sre.google/sre-book/effective-troubleshooting/)은 관찰과 시스템 지식에서 반복 가설을 만들고 통제된 시험으로 반박하며, 재현·영향 완화·증거 보존·수정·재발 방지를 연결하는 운영 신뢰성 문맥에 사용했습니다. 이 장의 이상화된 절차를 모든 장애의 고정 순서나 단일 원인 보장으로 확대하지 않습니다.
- [OpenTelemetry Signals](https://opentelemetry.io/docs/concepts/signals/)와 [Observability Primer](https://opentelemetry.io/docs/concepts/observability-primer/)는 2026-08-13 현재 trace·metric·log의 서로 다른 신호 범위와 telemetry로 상태를 이해하는 관측 가능성 개념을 확인하는 데 사용했습니다. OpenTelemetry 구현을 모든 조직의 필수 도구로, 세 신호 수집을 완전한 계측·원인 규명으로 일반화하지 않습니다.
- [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)는 비밀번호·토큰·세션 식별자·연결 문자열·키·민감 개인정보의 직접 기록을 피하고 로그 접근·보호를 고려하는 범위에 사용했습니다. 이 지침 하나가 관할 법률·조직 보존 정책·모든 개인정보 판단을 대신한다고 확대하지 않습니다.
