## 먼저 결론

테스트를 많이 보유하는 것과 중요한 위험을 잘 검증하는 것은 같은 말이 아닙니다. **테스트 전략(test strategy)**: 실패했을 때 중요한 사용자 가치와 시스템 책임부터 찾고, 그 위험을 가장 작고 빠른 테스트와 실제 경계·화면·운영 증거의 조합으로 확인하는 계획입니다.

“테스트 통과”는 실행한 범위에서 관찰한 결과가 기대와 같았다는 뜻일 뿐입니다. 어떤 요구를 어떤 환경에서 어떤 명령으로 확인했는지, 확인하지 않은 위험이 무엇인지까지 알아야 완료 증거가 됩니다.

## 왜 필요한가

AI가 “모든 테스트가 통과했습니다”라고 보고하면 작업이 끝난 것처럼 느껴질 수 있습니다. 그러나 실제로는 기존 단위 테스트 한 파일만 실행했거나, 새 테스트가 잘못된 결과를 기대하거나, 데이터베이스와 브라우저를 가짜 객체로 바꾼 채 실제 연결을 한 번도 확인하지 않았을 수 있습니다. 테스트 명령이 성공했어도 빌드가 실패하거나 모바일 화면이 깨지고, 배포 환경의 설정과 데이터가 달라 운영에서만 문제가 나타날 수도 있습니다.

반대로 오류를 막겠다고 모든 경우를 브라우저 종단 간 테스트로 만들면 실행이 느리고 실패 원인이 모호해집니다. 작은 문구 변경에도 긴 검증을 기다리게 되고, 불안정한 테스트를 사람들이 무시하기 시작할 수 있습니다.

필요한 것은 테스트 종류를 외우는 일이 아니라 다음 네 질문에 답하는 일입니다.

1. 어떤 실패가 사용자·데이터·보안·운영에 중요한 피해를 주나요?
2. 그 실패를 가장 빠르고 정확하게 드러내는 관찰 지점은 어디인가요?
3. 작은 테스트가 가짜 경계나 가정 때문에 놓치는 위험은 무엇인가요?
4. 실행 결과가 실제 요구 충족을 증명하는지 누가 무엇으로 판정하나요?

## 한 문장 정의

- **테스팅(testing)**: 정한 목적에 따라 소프트웨어 산출물이나 실행 시스템을 평가하고 실제 증거를 판정 기준과 비교하는 검증 활동입니다.
- **동적 테스트(dynamic testing)**: 소프트웨어를 정한 조건에서 실행하고 실제 결과를 기대 결과와 비교하는 테스트입니다.
- **테스트 전략**: 중요한 위험마다 필요한 테스트 수준·데이터·환경·실행 시점·판정 기준과 보완 증거를 선택하는 계획입니다.

테스트는 더 넓은 검증 체계의 일부입니다. 문서와 설계 리뷰, 정적 분석, 형식 검사, 빌드, 실제 브라우저 확인, 접근성 점검, 배포 후 smoke test와 복구 훈련은 모두 중요한 증거가 될 수 있지만 전부 테스트 코드인 것은 아닙니다.

### verification과 validation을 구분하세요

- **verification**: 산출물과 시스템이 명시된 요구·설계·계약을 지키는지 확인하는 활동을 가리키는 경우가 많습니다.
- **validation**: 그 결과가 실제 사용자 목적과 사용 맥락에 맞는지 확인하는 활동을 가리키는 경우가 많습니다.

조직과 표준에 따라 한국어 번역과 세부 경계가 달라질 수 있으므로 “올바르게 만들었는가”와 “올바른 것을 만들었는가”라는 구호만 외우기보다 대상과 판정 기준을 함께 적는 편이 안전합니다.

예를 들어 날짜 필터가 명세대로 동작한다는 자동 테스트는 verification 증거가 될 수 있습니다. 실제 비개발자가 오류 문구를 이해하고 날짜를 바로 수정할 수 있는지는 사용자 관찰이나 사용성 검토 같은 validation 증거가 추가로 필요합니다. 그렇다고 자동화와 사람이 두 개념을 나누는 기준은 아닙니다. 사람이 설계 문서를 요구사항과 대조하는 리뷰도 verification 증거가 될 수 있고, 실제 사용 목적과 판정 기준을 담은 자동 시나리오도 validation에 기여할 수 있습니다. 다만 사용 맥락과 이해처럼 자동화가 표현하지 못한 부분까지 저절로 확인되는 것은 아닙니다.

### 정적·동적, 수동·자동을 한 축으로 섞지 마세요

**정적 테스팅(static testing)**: 소프트웨어를 실행하지 않고 요구사항·설계·코드·설정 같은 산출물을 검토하거나 분석해 결함을 찾는 활동입니다. 사람의 문서·코드 리뷰, 도구의 타입·규칙·데이터 흐름 분석이 예가 될 수 있습니다. **동적 테스트**는 대상 소프트웨어를 실행해 결과와 동작을 관찰합니다. 정적 분석 통과는 런타임 상태와 사용자 흐름을 증명하지 않고, 동적 테스트 통과는 읽지 않은 설계 누락과 실행하지 않은 경로를 증명하지 않습니다.

**수동 테스트(manual testing)와 자동 테스트(automated testing)**: 주로 누가 또는 무엇이 절차를 수행하고 판정하는지를 나타내는 다른 축입니다. 사람이 정한 절차를 직접 실행할 수도 있고, 탐색하며 예상하지 못한 문제를 찾을 수도 있습니다. 자동 검사는 빠르고 반복 가능하지만 오라클과 환경이 잘못되면 같은 오류를 빠르게 반복합니다. 수동 테스트도 실행 범위·fixture·기대 결과·관찰·판정 기록이 없으면 재현 가능한 증거가 되기 어렵습니다.

ISO/IEC/IEEE 29119 시리즈의 공개 안내는 조직·관리·동적 테스트 과정과 일반 개념을 설명하고, 정적 리뷰는 ISO/IEC 20246과 연결합니다. 위의 수동·자동 구분은 수행 방식에 대한 교육적 설명이며, 이번에 확인한 공개 안내의 명시적 열거로 귀속하지 않습니다. SWEBOK V4.0a도 코드를 실행하지 않는 static techniques와 실행 기반 테스트를 구분합니다. 이 표준 체계를 모든 팀의 유일한 분류로 강제하지 말고, 실제 산출물·실행 경계·수행 방식·오라클을 기록합니다.

## 비유로 이해하기: 출국 전 여러 검문

여행을 떠날 때 가방의 지퍼만 확인했다고 출국 준비 전체가 끝나지는 않습니다. 준비물 목록을 대조하고, 여권의 유효기간을 보고, 공항까지 가는 교통편을 확인하고, 탑승구에서 실제 예약과 신원을 확인합니다. 각 검문은 다른 실패를 더 잘 발견합니다.

- 빠른 단위 테스트는 물건 하나가 제대로 작동하는지 확인하는 것과 비슷합니다.
- 통합 테스트는 충전기와 기기가 실제로 연결되는지 확인하는 것과 비슷합니다.
- 종단 간 테스트는 집에서 출발해 탑승구까지 핵심 여정을 직접 따라가는 것과 비슷합니다.
- 배포 후 확인은 목적지에 도착한 뒤 예약과 수하물이 실제로 이어졌는지 확인하는 것과 비슷합니다.

이 비유가 맞는 지점은 한 번의 검사로 모든 위험을 덮을 수 없고, 실패 비용에 따라 서로 다른 검문을 조합해야 한다는 점입니다.

### 비유가 깨지는 지점

소프트웨어 테스트는 같은 조건을 자동으로 반복할 수 있지만, 실제 시간·네트워크·외부 서비스·사용자 행동은 완전히 고정되지 않습니다. 테스트 자체에도 코드와 데이터와 환경이 있어 잘못될 수 있습니다. 또한 모든 입력과 운영 상황을 다 실행하는 것은 불가능하므로, 테스트 통과는 수학적 무결함 증명이 아니라 선택한 표본과 관찰 범위에서 얻은 증거입니다.

## 요구에서 증거까지의 위치

테스트 전략은 구현이 끝난 뒤 테스트 파일을 추가하는 단계가 아닙니다. 요구와 설계를 검토할 때부터 어떤 실패가 중요한지, 어디에서 관찰할지, 누가 판정할지를 연결합니다.

```text
사용자 목표와 품질 요구
→ 실패 위험과 수용 기준
→ 책임·경계·데이터·인터페이스 설계
→ 가장 작은 충분한 테스트
→ 실제 구성요소·브라우저·배포 환경의 보완 증거
→ 결과와 남은 위험
→ 요구·설계·운영 방식 갱신
```

하나의 요구사항에 테스트가 하나씩만 대응하는 것도 아닙니다. “잘못된 날짜 범위는 저장하지 않고 사용자가 수정할 수 있어야 한다”라는 요구는 계산 규칙, API의 데이터 변경 방지, 화면의 오류 연결과 실제 수정 흐름을 서로 다른 증거로 확인해야 합니다.

반대로 하나의 종단 간 테스트가 여러 구성요소를 지나간다고 해서 각 구성요소의 모든 예외를 확인한 것은 아닙니다. 핵심 사용자 흐름은 넓은 테스트로 연결을 확인하고, 많은 경계 조건은 더 작고 빠른 테스트로 좁혀 확인하는 조합이 필요합니다.

## 테스트 수준은 실행 경계로 구분하세요

테스트 이름은 한 줄의 고정된 계층만 나타내지 않습니다. 단위·통합·종단 간 테스트는 주로 **얼마나 넓은 실행 경계를 함께 확인하는가**를 나타내고, 회귀 테스트와 smoke test는 주로 **어떤 목적과 시점에 확인하는가**를 나타냅니다. 계약 테스트는 경계를 오가는 합의에 초점을 두므로 단위·통합 같은 여러 실행 범위와 겹칠 수 있습니다. 세부 명칭은 팀과 도구마다 조금씩 다르므로 “단위 테스트 파일에 있다”는 위치보다 실제로 무엇을 함께 실행하고 무엇을 대역으로 바꿨는지 확인해야 합니다.

**회귀 테스트(regression test)**: 변경 때문에 [이전에 되던 동작이 깨지는 회귀](../../reference/development-glossary/)를 다시 발견하기 위한 테스트입니다. 작은 계산부터 전체 사용자 여정까지 어느 실행 범위에도 둘 수 있으며, 그 자체가 별도의 고정 계층을 뜻하지는 않습니다.

### 단위 테스트

함수, 규칙 또는 모듈처럼 작은 책임을 주변 실행 환경과 분리해 빠르게 확인합니다. 실패 원인을 좁히고 경계값을 많이 다루기 좋지만, 실제 데이터베이스·파일·브라우저·네트워크 연결과 설정은 증명하지 못합니다.

좋은 대상은 날짜 범위 판단, 단위 변환, 지표 계산, 상태 전이와 같이 입력과 기대 결과를 작게 표현할 수 있는 업무 규칙입니다.

### 통합 테스트

둘 이상의 실제 구성요소나 경계가 함께 맞물리는지 확인합니다. 애플리케이션과 데이터베이스, 변환기와 실제 파일 형식, 서버 라우트와 인증·권한 모듈처럼 인터페이스와 설정에서 생기는 문제를 찾습니다.

통합 테스트라고 부르면서 데이터베이스와 외부 경계를 모두 대역으로 바꿨다면 실제 통합의 핵심 위험은 남아 있습니다. 무엇이 진짜이고 무엇이 대역인지 기록해야 합니다.

### 계약 테스트

API, 함수, 이벤트 또는 데이터 파일을 주고받는 양쪽이 입력·출력·오류 형식과 호환되는지 확인합니다. 프런트엔드와 백엔드가 따로 바뀌거나 데이터 원천의 스키마가 변할 때 특히 유용합니다.

계약 테스트가 통과해도 서버 내부 업무 규칙과 실제 사용자 흐름 전체가 맞다는 뜻은 아닙니다. 형식 호환성과 의미 정확성을 구분해야 합니다.

### 종단 간 테스트

사용자가 시작한 핵심 작업을 브라우저·서버·데이터 같은 실제 경계를 지나 끝까지 확인합니다. 사용자 가치와 구성요소 연결에 가까운 증거를 주지만 느리고 실패 원인이 넓으며 환경 변화에 민감할 수 있습니다.

모든 세부 조합을 종단 간 테스트로 만들기보다 로그인, 핵심 조회, 저장, 결제처럼 실패 비용이 큰 대표 여정과 구성요소 연결을 확인하는 데 집중합니다.

### smoke test

새 빌드나 배포가 시작되고 최소 핵심 기능이 응답하는지 빠르게 확인합니다. 배포 직후 잘못된 설정, 누락된 파일과 기동 실패를 조기에 발견하는 데 유용하지만 상세 회귀 테스트를 대신하지 않습니다.

운영 환경의 smoke test는 대상과 실행 범위를 사전에 승인받고 권한 있는 환경에서만 수행합니다. 실제 사용자 데이터 변경이나 외부 메시지 발송을 일으키지 않는 읽기 전용 경로를 우선하고, 변경이 꼭 필요하다면 전용 테스트 계정과 되돌릴 수 있는 작은 요청, 중지 조건과 명확한 정리 절차를 승인 범위에 포함해야 합니다.

## 동적 테스트를 보완하는 증거도 필요합니다

| 증거 | 잘 발견하는 문제 | 이것만으로 부족한 범위 |
|---|---|---|
| 문서·설계 리뷰 | 요구 누락, 책임 혼동, 위험한 가정 | 실제 실행 결과 |
| 정적 테스팅·형식 검사 | 요구·설계·코드·설정의 누락, 문법, 타입, 규칙 위반, 끊어진 링크 | 실행 중 상태와 사용자 이해 |
| 빌드 | 배포 아티팩트 생성과 의존성 결합 | 운영 설정과 핵심 사용자 흐름 |
| 실제 브라우저 확인 | 렌더링, 상호작용, 반응형 화면 | 모든 데이터·서버 예외와 장기 운영 |
| 접근성 검토 | 의미 구조, 키보드, 보조 기술 사용 | 업무 규칙과 데이터 정확성 |
| 성능·부하 측정 | 응답 지연, 처리량, CPU·메모리 같은 자원 사용 | 기능 동작과 데이터 정확성 |
| 배포·운영 확인 | 실제 환경 설정, 연결, 관측과 복구 | 모든 입력 조합과 미래 장애 |

예를 들어 문서 사이트의 Markdown 링크 검사는 브라우저에서 링크가 읽기 좋은 이름으로 보이고 키보드로 이동 가능한지까지 증명하지 못합니다. 반대로 브라우저에서 한 번 눌러 본 사실은 저장소의 모든 내부 링크와 제목 앵커가 유효하다는 보장이 아닙니다. 자동 범위와 실제 사용 범위를 함께 확인해야 합니다.

## 테스트 전략을 위험에서 설계하는 법

테스트 목록부터 만들지 말고 중요한 실패를 먼저 적습니다. 각 실패에 대해 다음을 판단합니다.

1. **영향**: 사용자 피해, 데이터 손실, 보안 침해, 금전·법적 비용과 복구 비용이 얼마나 큰가요?
2. **가능성**: 경계값, 변경 빈도, 외부 연동과 과거 결함을 고려할 때 얼마나 자주 생길 수 있나요?
3. **발견 가능성**: 실패가 바로 보이나요, 조용히 잘못된 데이터가 쌓이나요?
4. **되돌리기 가능성**: 빠르게 복구할 수 있나요, 한 번 실행하면 되돌리기 어렵나요?
5. **가장 작은 관찰 지점**: 이 실패를 가장 빠르고 정확하게 드러내는 책임 경계는 어디인가요?
6. **남은 빈틈**: 작은 테스트에서 가짜로 바꾼 구성요소와 실제 환경 차이는 무엇인가요?

위험이 크고 발견이 늦으며 복구가 어려울수록 독립된 여러 증거와 사람 승인, 배포 전후 확인이 필요합니다. 위험이 낮고 되돌리기 쉬운 문구 수정에는 정적 검사와 실제 화면 확인만으로 충분할 수 있습니다. 모든 변경에 같은 검증 묶음을 강제하는 것이 엄격함은 아닙니다.

### 가장 낮은 수준이 아니라 가장 작은 충분한 수준을 고르세요

단위 테스트가 가장 빠르다고 해서 항상 최선은 아닙니다. 오류가 구성요소 연결에서만 발생한다면 통합 테스트가 가장 작은 충분한 증거입니다. CSS 반응형 문제는 함수 테스트보다 실제 브라우저가 더 직접적입니다. 운영 설정 오류는 배포 환경의 smoke test가 필요합니다.

좋은 전략은 중요한 실패를 직접 관찰할 수 있는 가장 작은 경계에서 시작하고, 그 테스트가 대체한 실제 경계를 더 넓은 증거로 보완합니다.

## 기대 결과는 어디서 오나요: 테스트 오라클

**테스트 오라클(test oracle)**: 테스트가 실제 결과와 비교하는 기대 결과나 판정 방법입니다. 오라클이 틀리면 테스트는 잘못된 동작을 정확하게 보호할 수 있습니다.

기대 결과의 근거가 될 수 있는 것은 승인된 수용 기준, 도메인 규칙, 표준, 이전에 검증된 기준 데이터, 독립된 계산과 사람의 전문 판단입니다. 현재 구현의 출력을 그대로 복사해 기대값으로 만들면 기존 결함까지 정답으로 고정할 수 있습니다. 큰 출력의 현재 모습을 승인 기준으로 삼는 [스냅샷 기반 검토도 차이를 읽지 않고 갱신하면 같은 함정](../../11-ai-native/agent-review-and-verification/#스냅샷-기반-검토의-함정)에 빠집니다.

데이터 분석에서는 특히 숫자의 출처·단위·시점과 허용 오차를 함께 기록해야 합니다. 단순히 스냅샷 파일이 이전과 같다는 이유만으로 경제적 의미와 최신성이 맞다고 판단할 수 없습니다.

## 대역과 테스트 데이터의 경계

**테스트 대역(test double)**: 실제 구성요소 대신 사용하는 mock, stub, fake 같은 대체 구성요소입니다. 빠르고 재현 가능한 테스트를 만드는 데 유용하지만 실제 서비스가 아니라 우리가 예상한 계약을 흉내 냅니다. 예상 자체가 틀리거나 실제 제공자가 바뀌면 모든 대역 테스트가 통과해도 연동은 실패할 수 있습니다.

**테스트 fixture**: 테스트를 같은 조건에서 재현하기 위해 미리 준비하는 작은 데이터·파일·상태와 환경입니다. 대역은 구성요소를 대신하고 fixture는 실행 조건을 준비한다는 차이가 있습니다.

- 대역을 쓴 경계와 이유를 기록합니다.
- 실제 계약 또는 샌드박스와 확인하는 더 넓은 테스트를 둡니다.
- 운영 비밀과 개인정보를 테스트 fixture에 복사하지 않습니다.
- 시간·무작위 값·네트워크 실패는 제어하되 실제 복구 경로도 별도로 확인합니다.
- 테스트 데이터는 작고 의도를 읽을 수 있게 만들고, 실행 간 상태가 남지 않도록 격리합니다.
- 실행 전 대상 환경·데이터베이스·계정이 전용 테스트 대상인지 확인합니다. 운영 연결에서는 파괴적 테스트와 자동 정리 절차를 실행하지 않습니다.

## 불안정한 테스트를 성공으로 취급하지 마세요

**Flaky test**: 코드가 바뀌지 않았는데 같은 테스트가 통과와 실패를 오가는 불안정한 테스트입니다. 시간, 실행 순서, 공유 상태, 비동기 대기, 네트워크와 외부 서비스가 흔한 원인입니다.

재실행해서 통과한 결과만 남기면 결함과 불안정성을 숨길 수 있습니다. 실패 로그와 환경을 보존하고 원인을 좁히며, 불안정한 테스트를 격리 목록에 임시로 제외한다면 소유자·해제 조건·복구 기한을 기록해야 합니다. 무조건 재시도 횟수를 늘리는 것은 해결이 아닙니다.

## 공개 데이터 대시보드에 적용하기

요구사항 `FR-014`를 “사용자는 지표의 정의·원천·기준 시점과 갱신 상태를 확인하고, 오래된 데이터에는 경고를 볼 수 있다”라는 복합 교육 예시로 두겠습니다. 이는 사례의 요구사항 ID가 아닙니다. [현재 대시보드 사례의 요구별 테스트](../../12-case-studies/analytics-dashboard-case-study/#테스트는-요구사항별-실패-위험을-겨냥합니다)와 연결할 때는 `D-01`의 가상 원천 표시, `D-02`의 거래일·단위·가격 기준, `D-03`의 버전·기준 시점, `D-04`의 오래됨과 이유 표시, `D-05`의 갱신 실패·마지막 정상 버전 보존을 각각 확인합니다. 실제 시장 데이터의 최신성이나 원천 정확성을 검증한 것으로 확대하지 않습니다.

### 먼저 위험을 적습니다

- 서로 다른 단위를 같은 숫자로 비교합니다.
- 원천 갱신 실패가 숨은 채 오래된 값을 최신 값으로 해석합니다.
- 실제 값 0, 값이 비어 있는 결측, 아직 수집하지 못한 상태와 품질 문제로 공개를 차단한 상태가 모두 같은 빈칸으로 보입니다.
- API에는 메타데이터가 있지만 화면에서 누락됩니다.
- 경고가 색으로만 표현되어 일부 사용자가 상태를 알 수 없습니다.
- 로컬 fixture에서는 통과하지만 배포 데이터 파일이 오래됐습니다.

### 위험을 증거에 연결합니다

- **변환 규칙**
  - 확인할 위험: 단위·날짜·오래됨 판단 오류
  - 대표 증거: 경계값 단위 테스트와 독립 기준값을 원천·변환 결과와 맞춰 보는 데이터 대사
- **데이터 저장·API**
  - 확인할 위험: 필수 메타데이터 누락, 스키마 불일치와 0·결측·미수집·차단 상태 혼용
  - 대표 증거: 실제 스키마를 사용하는 통합·계약 테스트
- **화면 상태**
  - 확인할 위험: 출처·시점·경고 누락과 수정 불가능한 오류
  - 대표 증거: 화면 구성요소별 상태 확인과 실제 브라우저·키보드 검토
- **사용자 여정**
  - 확인할 위험: 필터 선택부터 출처 확인까지 연결 실패
  - 대표 증거: 핵심 종단 간 테스트
- **배포·운영**
  - 확인할 위험: 오래된 파일 배포와 갱신 실패 미탐지
  - 대표 증거: 배포 smoke test, 데이터가 기준 시점에 맞게 갱신됐는지 보는 최신성(freshness) 감시와 복구 훈련

단위 테스트가 오래됨 계산을 정확히 확인해도 배포된 파일의 실제 시점은 모릅니다. 종단 간 테스트가 경고 하나를 봤어도 모든 지표의 단위와 원천 대사를 확인하지 않습니다. 각 증거가 잘하는 일과 못 하는 일을 함께 기록해야 합니다.

## TDD와 테스트 전략은 같은 것이 아닙니다

[PRD·두 종류의 SDD·TDD](../../06-requirements-design/prd-sdd-tdd/)에서 설명한 TDD는 원하는 작은 동작을 테스트로 먼저 표현하고 `Red → Green → Refactor`를 반복하는 구현 규율입니다. 테스트 전략은 시스템 전체의 위험을 어떤 테스트와 다른 증거로 다룰지 정하는 더 넓은 계획입니다.

TDD를 적용해 계산 규칙을 잘 설계했어도 실제 데이터베이스, 브라우저, 배포 설정, 보안, 성능과 복구는 별도 검증이 필요합니다. 반대로 탐색적 디자인이나 외부 서비스 연동처럼 TDD가 직접적이지 않은 영역에서도 테스트 전략과 검증 책임은 사라지지 않습니다.

최종 저장소에 테스트 파일이 있다는 사실만으로 TDD 순서를 거쳤다고 증명할 수 없고, TDD 과정 기록이 있다는 사실만으로 제품 전체의 테스트 전략이 충분하다고 증명할 수도 없습니다.

## 테스트 피라미드는 위험과 피드백 비용의 배분 모델입니다

테스트 피라미드는 빠르고 격리된 작은 테스트를 넓은 기반으로 두고 느리고 넓은 종단 간 테스트는 중요한 흐름에 집중하자는 방향을 보여 줍니다. 이 장에서는 이를 **실패 위험과 피드백 비용을 어느 증거에 배분할지 묻는 모델**로 사용합니다. 그러나 “단위 테스트 70%, 통합 20%, 종단 간 10%”처럼 고정 비율을 복사하면 시스템 위험을 놓칠 수 있습니다.

데이터 파이프라인은 스키마·품질·원천 통합 검증의 비중이 클 수 있고, 디자인 시스템은 실제 렌더링과 화면 변화 비교·접근성이 중요할 수 있습니다. 외부 서비스에 강하게 의존하는 제품은 계약과 장애 복구 검증이 중요합니다. 테스트 모양은 코드 구조가 아니라 실패 위험과 피드백 비용을 따라야 합니다.

단위·통합·계약·종단 간은 실행 경계와 초점, 정적 테스팅은 비실행 산출물 검사, 수동·자동은 수행 방식이라는 서로 다른 축입니다. 피라미드 그림에 모두 억지로 층으로 넣지 말고, 위험마다 가장 작은 충분한 증거와 실제 경계·사람 판단의 보완 증거를 배치합니다.

## 커버리지는 다룬 범위의 측정이지 실제 성공의 단독 증거가 아닙니다

**테스트 커버리지(test coverage)**: 정한 코드 요소·분기·요구·조건 중 테스트가 다룬 정도를 보여 주는 측정입니다. 높은 코드 커버리지는 어떤 줄이나 분기가 실행됐음을 보여 줄 수 있지만 기대값이 맞는지, 중요한 업무 위험을 주장으로 확인했는지, 실제 사용자가 목적을 달성했는지는 혼자 증명하지 못합니다.

커버리지는 미시험 영역을 찾고 위험에 비해 비어 있는 경로를 질문하는 데 사용합니다. 실제 성공 증거에는 요구·위험과 연결된 오라클, 실패 전·성공 후 결과, 실제 경계와 대상 환경, 사용자 결과, 미실행·건너뜀·flaky 상태가 함께 필요합니다. 모든 팀에 같은 커버리지 목표 수치를 적용하거나 수치가 오르면 품질이 같은 비율로 좋아졌다고 단정하지 않습니다.

## AI의 “테스트 통과” 보고를 검증하는 법

AI 보고는 결론이 아니라 검토할 주장입니다. 최소한 다음 증거를 확인합니다.

권한·비용·부작용이 허용하는 범위에서는 검토자가 현재 작업 트리에서 같은 명령을 독립적으로 다시 실행합니다. 운영 환경처럼 재실행 권한이 없거나 비용과 부작용이 큰 경우에는 임의로 실행하지 말고, 승인된 실행 기록·대상·시점과 남은 한계를 확인합니다.

1. **정확한 명령**: 실제로 어떤 명령과 옵션을 실행했나요?
2. **실행 위치·상태와 시점**: 어느 저장소·브랜치·commit에서 실행했나요? 그때의 미커밋 변경 상태와 실행 시점, 런타임·설정은 무엇인가요? 결과가 빌드 산출물이나 데이터에 의존한다면 해당 아티팩트·데이터 버전도 식별합니다.
3. **범위**: 전체 테스트인가요, 특정 파일이나 필터만 실행했나요?
4. **종료 코드와 수량**: [종료 코드(exit code)](../../reference/agent-output-glossary/)는 명령이 끝나며 돌려주는 숫자입니다. 보통 0은 해당 명령이 정의한 성공일 뿐 제품 전체 성공은 아닙니다. 종료 코드와 통과·실패·건너뜀 수는 각각 무엇인가요?
5. **테스트 쪽 변경**: 테스트 코드, 기대값, 스냅샷, 건너뛰기 표시, 필터와 테스트 실행 설정이 함께 바뀌었나요? 바뀌었다면 검증을 강화했나요, 실패를 숨겼나요?
6. **변경과의 연결**: 수정한 요구와 코드 경로를 어떤 테스트가 직접 확인하나요? 실행 후 제품 코드·테스트·기대값·설정·데이터가 달라졌다면 이전 성공을 현재 상태의 성공으로 옮기지 않고 변경 영향에 맞게 다시 확인합니다. 같은 브랜치라는 사실만으로 같은 상태를 실행했다고 볼 수 없습니다.
7. **실패 이유 확인**: 새 회귀 테스트는 수정 전 기대한 이유로 실패했나요?
8. **보완 증거**: 빌드, 실제 브라우저, 데이터베이스, 배포 환경과 수동 검토 중 무엇이 더 필요한가요?
9. **미실행 구분**: 실행하지 않음, 환경 때문에 실행 불가, 실행 후 실패와 성공을 분리했나요?

종료 코드 0만 복사하지 말고 명령 출력에서 테스트 수와 실패·건너뜀을 확인합니다. 도구와 설정에 따라 필터에 맞는 테스트가 0개여도 명령이 성공으로 끝날 수 있으므로 실제 실행 수를 반드시 확인합니다. 이전 실행의 로그나 다른 브랜치의 성공을 현재 변경의 증거로 사용하지 않습니다.

### 읽기 전용 검토 지시 예


## 흔한 실패와 복구

### 테스트 수나 커버리지 숫자를 목표로 삼습니다

실행된 줄의 비율이 높아도 잘못된 기대값, 중요한 경계와 운영 실패는 남을 수 있습니다. 커버리지는 미시험 영역을 찾는 보조 신호로 사용하고, 핵심 요구와 실패 위험별 오라클·실제 경계·사용자 결과를 직접 추적하세요.

### 구현 세부를 그대로 고정합니다

내부 함수 호출 순서와 DOM 구조만 확인하면 동작을 유지한 리팩터링도 실패하고, 정작 사용자 결과가 틀려도 통과할 수 있습니다. 책임 경계의 관찰 가능한 결과를 우선하고 내부 세부를 확인해야 하는 이유를 기록하세요.

### 대역만 통과시키고 실제 경계를 확인하지 않습니다

대역은 예상한 세계를 빠르게 검증할 뿐 실제 데이터베이스·브라우저·외부 API를 증명하지 않습니다. 최소 한 곳에서는 실제 계약과 설정을 사용하는 통합 또는 smoke 증거를 추가하세요.

### 새 테스트가 처음부터 통과합니다

이미 구현된 동작을 문서화한 것일 수도 있지만, 의도한 결함을 재현하지 못했거나 잘못된 경로를 검사했을 수도 있습니다. 버그 수정이라면 수정 전 상태에서 기대한 이유로 실패하는지 먼저 확인하고, 불가능했다면 그 한계를 기록하세요.

### 실패한 테스트를 무조건 제품 결함으로 봅니다

제품 코드, 테스트 코드, fixture, 환경과 요구 해석 중 어느 쪽이 틀렸는지 아직 모릅니다. 실패 메시지와 가장 작은 재현을 확인하고 [디버깅과 관측 가능성](../debugging-observability/)의 증거 흐름으로 원인을 좁히세요.

### 건너뜀과 미실행을 성공에 포함합니다

의존 서비스가 없어 테스트가 건너뛰었는데 전체 통과라고 보고하면 핵심 경계가 비어 있을 수 있습니다. skipped, 도구가 “실패할 것으로 예상됨”으로 따로 표시한 항목, 보류 상태와 필터 옵션을 별도로 보고하고 의도와 해제 조건을 기록하세요. 구체적인 표시 이름과 성공 집계 방식은 테스트 도구마다 다를 수 있습니다.

### 운영 데이터를 테스트에 복사합니다

실제 개인정보·토큰·회사 내부 데이터가 fixture와 스냅샷에 남을 수 있습니다. 합성 데이터나 명시적으로 공개·허용된 작은 데이터를 사용하고 비밀 검사와 데이터 삭제 정책을 적용하세요.

### 불안정한 테스트를 재실행으로 숨깁니다

통과할 때까지 반복하면 결과를 신뢰할 수 없습니다. 최초 실패를 보존하고 시간·순서·공유 상태·비동기 대기와 외부 의존성을 격리하며 재시도는 원인과 한계를 기록한 임시 완화로만 사용하세요.

### 모든 위험을 자동화하려고 합니다

초기 사용자 이해, 시각적 위계, 새로운 공격 시나리오와 복구 의사결정처럼 사람 탐색과 전문 판단이 더 직접적인 영역이 있습니다. 자동화하지 않았다는 이유로 생략하지 말고 담당자·절차·판정 기록을 검증 계획에 포함하세요.

## 변경 크기에 맞춘 최소 검증

### 낮은 위험: 책임 영향이 작은 문구와 내부 링크

일반 안내 문구처럼 틀려도 피해가 작고 쉽게 되돌릴 수 있는 변경을 뜻합니다. 가격, 법적 고지, 안전 경고, 투자 표현과 개인정보 안내는 짧은 문구라도 금전·법적·안전 책임을 만들 수 있으므로 낮은 위험으로 자동 분류하지 말고 해당 분야의 검토와 승인을 받아야 합니다.

- 콘텐츠·링크 정적 검사
- 빌드
- 해당 화면의 데스크톱·모바일 확인

### 중간 위험: 계산 규칙과 화면 상태

- 변경 전 실패를 확인한 단위 테스트 또는 화면 구성요소 상태 검사
- 관련 통합 테스트
- 빌드와 실제 사용자 흐름 확인
- 접근성·경계값 검토

### 높은 위험: 권한·데이터 변경·결제·마이그레이션

- 요구·설계·위협과 복구 계획의 독립 리뷰
- 단위·통합·계약·핵심 종단 간 테스트
- 본인이 소유하거나 명시적으로 허가받은 환경에서 분리된 계정과 가짜 데이터로 수행하는 권한 거절 부정 테스트
- 실패 주입, 백업·복구 또는 롤백 검증
- 운영과 유사한 환경에서의 승인된 검증
- 단계적 배포, 관측 지표와 중지 조건

높은 위험 작업은 테스트 명령이 많다는 이유로 충분해지지 않습니다. 누가 배포를 멈출 수 있는지, 데이터와 사용자를 어떻게 보호하고 어떻게 되돌릴지까지 계획해야 합니다.

## 완료 판단 체크리스트

- [ ] 중요한 사용자 목표와 실패 위험을 적었습니다.
- [ ] 각 위험에 가장 작은 충분한 테스트와 보완 증거가 연결됩니다.
- [ ] 테스트의 기대 결과가 요구·도메인 규칙·독립 기준 중 어디에서 왔는지 설명할 수 있습니다.
- [ ] 단위·통합·종단 간의 실행 범위와 회귀·smoke의 목적·시점, 계약 테스트의 초점을 구분했습니다.
- [ ] 정적·동적 테스트와 수동·자동 수행 방식을 구분하고 각각의 미확인 범위를 적었습니다.
- [ ] 대역·fixture·샌드박스로 대체한 실제 경계와 남은 빈틈을 기록했습니다.
- [ ] 기능 테스트가 대신하지 못하는 접근성·보안·성능·복구·데이터 품질 위험을 확인했습니다.
- [ ] 정확한 명령, 위치, 환경, 범위, 종료 코드와 테스트 수를 확인했습니다.
- [ ] 실행 당시 commit·미커밋 diff 상태·시점과 필요한 아티팩트·데이터 버전을 기록하고, 실행 이후 변경에 맞는 재검증 여부를 확인했습니다.
- [ ] 테스트·기대값·스냅샷·건너뛰기·필터·실행 설정의 변경이 실패를 숨기지 않는지 확인했습니다.
- [ ] skipped·미실행·실행 불가·실패·성공을 구분했습니다.
- [ ] 권한·비용·부작용이 허용되는 범위에서 현재 작업 트리의 명령을 독립적으로 다시 실행했습니다.
- [ ] 새 회귀 테스트가 수정 전 기대한 이유로 실패했는지 확인하거나 확인하지 못한 이유를 기록했습니다.
- [ ] coverage 수치를 오라클·중요 위험·사용자 성공의 대리 증거로 사용하지 않았습니다.
- [ ] 빌드와 실제 브라우저 또는 대상 환경 확인을 테스트 통과와 별도 증거로 남겼습니다.
- [ ] 운영 데이터와 비밀정보가 테스트 데이터·로그·스냅샷에 포함되지 않았습니다.
- [ ] 테스트 대상 환경·데이터베이스·계정이 전용 테스트 대상인지 확인했고 운영 연결에서 파괴적 테스트나 자동 정리를 실행하지 않았습니다.
- [ ] 운영 smoke test는 읽기 전용 수행을 기본으로 확인했습니다. 변경이 있었다면 사전 승인 범위·전용 대상·중지 조건·정리 결과를 기록했고, 미실행이나 적용외라면 그 상태와 이유를 구분했습니다.
- [ ] 남은 위험, 사람 판단, 배포 중지와 복구 조건이 드러납니다.

## 짧은 연습

자신의 핵심 사용자 흐름 하나를 고르세요. 기능 목록이 아니라 실패했을 때의 피해부터 다음 표를 채웁니다.

| 질문 | 작성할 내용 |
|---|---|
| 사용자 목표 | 사용자가 끝내려는 실제 작업 한 문장 |
| 중요한 실패 | 잘못된 결과·데이터 손실·권한·접근성·운영 실패 중 가장 큰 세 가지 |
| 가장 작은 증거 | 각 실패를 직접 관찰할 수 있는 테스트 또는 리뷰 |
| 실제 경계 증거 | 데이터베이스·브라우저·배포 환경에서 추가할 확인 |
| 판정 근거 | 기대 결과의 출처와 승인자 |
| 남은 위험 | 이번 범위에서 확인하지 못한 것과 복구 방법 |

그다음 AI가 제안한 테스트 계획과 비교하세요. 테스트 이름이 많다는 이유로 선택하지 말고, 세 가지 중요한 실패가 각각 직접 관찰되는지와 실제 경계의 빈틈이 남는지 설명해 보세요.

## 출처와 적용 범위

- [ISO/IEC/IEEE 29119-1:2022](https://www.iso.org/standard/81291.html)의 Edition 2·Published·stage 60.60은 2026-08-13의 확인 기록입니다. 2026-11-15에는 공개 페이지의 2022판·일반 개념 안내와 [ISO JTC 1/SC 7 시리즈 안내](https://committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiecieee-29119-series.html)의 조직·관리·동적 테스트 과정 및 ISO/IEC 20246 정적 리뷰 연결을 다시 확인했습니다. 현재 공개 안내에서 manual·automated·scripted·unscripted 열거는 확인하지 못해 그 귀속은 사용하지 않습니다. 이 부재를 표준 전체에 해당 분류가 없다는 뜻으로 해석하지 않으며, 유료 표준 전문이나 과거 edition·stage를 새로 확인했다고 주장하지 않습니다.
- [IEEE Computer Society SWEBOK 리소스](https://www.computer.org/education/bodies-of-knowledge/software-engineering/resources/)와 [SWEBOK V4.0a PDF](https://ieeecs-media.computer.org/media/education/swebok/swebok-v4.pdf)는 2025-09-25 update를 2026-08-13에 직접 확인해 unit·integration·system·acceptance 수준, 오라클·자동화·coverage criteria, 코드를 실행하지 않는 static techniques와 동적 테스트의 구분 범위에 사용했습니다. 이 수준을 중요도 순서·모든 팀의 파일 구조로, coverage를 테스트 효과·사용자 성공의 단독 증거로 확대하지 않습니다.
- [Martin Fowler 사이트의 Practical Test Pyramid](https://martinfowler.com/articles/practical-test-pyramid.html)은 2026-08-13 현재 Ham Vocke의 1차 실무 설명에서 빠르고 격리된 작은 테스트를 넓게 두고 느리고 넓은 테스트를 선택적으로 배치하는 방향을 확인하는 데 사용했습니다. 고정 비율·정확한 층 수·특정 도구를 보편 규칙으로 사용하지 않고 위험과 피드백 비용을 배분하는 판단 모델로만 적용합니다.
- [Google Testing Blog의 Flaky Tests](https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html)와 [Measuring Coverage](https://testing.googleblog.com/2014/07/measuring-coverage-at-google.html)는 각각 2016-05-27과 2014-07-14의 Google 조직 사례를 2026-08-13에 확인해 같은 코드에서 성공·실패가 바뀌는 신호 문제와 coverage를 미시험 영역 탐색에 쓰는 범위에 사용했습니다. Google의 규모·수치·재실행 정책을 다른 조직의 기준으로 사용하거나 coverage 목표를 정확성·회귀 부재의 증거로 확대하지 않습니다.

도구별 예상 실패·건너뜀·필터 0건·종료 코드의 의미는 이 출처 묶음이 보편적으로 정하지 않습니다. 실제 테스트 러너와 버전을 선택하면 해당 공식 문서와 실제 출력으로 다시 확인합니다. 테스트 수준의 명칭과 경계도 이름보다 실제 실행 범위·대역·오라클·미확인 위험으로 판정합니다.
