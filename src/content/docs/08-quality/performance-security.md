## 왜 필요한가

“빠르게 만들어 주세요”와 “안전하게 만들어 주세요”는 좋은 의도지만 합격 여부를 판정할 수 없는 요청입니다. AI는 캐시를 추가하거나 패키지를 바꾸고, 인증 화면이나 입력 검사 코드를 만들 수 있습니다. 그러나 어떤 사용자에게 무엇이 얼마나 빨라야 하는지, 무엇을 누구에게서 보호해야 하는지 정하지 않으면 복잡성만 늘고 실제 위험은 남습니다.

성능과 보안은 마지막에 한 번 검사하는 부가 기능이 아닙니다. 요구 단계에서 사용자 결과와 보호할 자산을 정하고, 설계에서 예산과 신뢰 경계를 배치하며, 구현·검증·배포·운영에서 실제 증거로 계속 확인하는 품질 책임입니다.

## 한 문장 정의

성능은 정한 사용자 결과를 허용 가능한 시간과 자원 안에서 제공하는 품질이고, 보안은 자산·위협·신뢰 경계를 식별해 위험에 비례하는 예방·탐지·대응·복구 통제를 설계하고 검증하는 지속적인 위험 관리입니다.

## 여행 시간표와 박물관 비유, 그리고 한계

성능 예산은 여행에서 “몇 시까지 도착하고 환승은 몇 번 이하로 한다”는 시간표와 비슷합니다. 총 소요 시간뿐 아니라 어느 구간에서 지연됐는지 알아야 병목을 고를 수 있습니다. 보안은 박물관이 작품이라는 자산, 출입구라는 경계, 도난·훼손이라는 위협을 식별하고 전시실마다 필요한 출입 권한·감지·복구 절차를 두는 일과 비슷합니다.

이 비유는 **목표를 먼저 정하고 구간별 위험에 맞춰 자원을 배분한다**는 점에서만 맞습니다. 소프트웨어 지연은 동시 요청·데이터 크기·기기·네트워크에 따라 분포가 달라지고, 공격자는 통제를 관찰해 새로운 경로를 시도합니다. 박물관처럼 물리적 경계가 고정돼 있지도 않습니다. 따라서 한 번의 빠른 이동이나 자물쇠 하나를 전체 성능·보안 완료 증거로 삼아서는 안 됩니다.

## 두 품질을 하나의 판단 흐름으로 봅니다

| 질문 | 성능 | 보안 | 필요한 증거 |
|---|---|---|---|
| 무엇을 지키는가? | 사용자가 완료해야 할 핵심 행동과 기다림 한도 | 개인정보·권한·업무 상태·가용성 같은 자산 | 요구·데이터 분류·사용자 영향 |
| 어디에서 위험이 생기는가? | 느린 경로, 자원 포화, 직렬 대기 | 진입점, 신뢰 경계, 과도한 권한, 제3자 의존성 | 흐름·프로필·위협 모델 |
| 어느 기준을 넘으면 실패인가? | 사용자 구간·환경·분위수·자원 예산 | 허용하지 않을 행동·노출·변조와 위험 수용 기준 | 수용 기준·성능 예산·보안 요구 |
| 무엇을 바꿀 것인가? | 측정된 병목을 줄이는 가장 작은 변경 | 우선 위협을 줄이는 예방·탐지·복구 통제 | 선택 이유·대안·부작용·복구 경로 |
| 효과를 어떻게 아는가? | 같은 조건의 변경 전후 측정과 회귀 | 통제 시험·거절 경로·감사 증거·대응 훈련 | 실행 결과와 대상 버전·환경 |

성능 최적화가 보안을 약화할 수도 있습니다. 권한 확인을 생략한 캐시, 민감한 응답의 과도한 사본, 검사 없이 재사용한 결과가 예입니다. 반대로 모든 요청에 비용이 큰 검사를 중복 적용하면 사용자가 기다리거나 시스템이 포화될 수 있습니다. 둘 중 하나를 포기하는 대신 실제 위험과 병목을 측정해 경계와 예산을 함께 설계합니다.

## 성능: 먼저 사용자 결과와 예산을 정합니다

### 성능 예산은 합격선을 기록한 프로젝트 계약입니다

**성능 예산(performance budget)**: 특정 사용자 결과가 정한 조건에서 지켜야 할 시간·자원·용량의 한도입니다. “빠르게”보다 다음 항목을 포함해야 합니다.

- **사용자 결과**: 첫 화면의 의미 있는 내용 표시, 검색 결과 확인, 참가 확정처럼 실제 목적
- **사용자 구간**: 새 방문·재방문, 지역, 접근 방식, 데이터 규모처럼 결과를 다르게 만드는 조건
- **환경**: 대상 기기·브라우저·네트워크·서버 사양·배포 환경·버전
- **지표와 통계**: 어떤 시작·종료 사건을 재는지, 단위, 표본 수, 중앙값·p95 같은 집계 방식
- **한도와 기간**: 어느 수치·비율·기간을 넘으면 실패인지
- **행동**: 초과할 때 릴리스를 멈출지, 원인을 조사할지, 어떤 예외를 누가 승인할지

p95는 정한 표본·기간에서 측정값의 약 95%가 그 값 이하에 놓이는 95번째 백분위수입니다. 평균이나 최댓값이 아니며 모든 개별 요청이 그 한도 안에 끝난다는 보장도 아닙니다. 표본 수·집계 구간·계산 방식을 함께 기록합니다.

예산 수치는 모든 사이트에 통하는 표준 정답이 아닙니다. 사용자 목적·기기·네트워크·사업 제약과 현재 기준선을 보고 프로젝트가 정하고, 실제 사용 증거와 요구 변화에 따라 기록을 남겨 조정합니다. 다른 글의 예시 수치를 그대로 복사하면 현재 사용자의 허용 가능한 기다림을 증명하지 못합니다.

### 기준선 없이는 개선을 말할 수 없습니다

변경 전 기준선(baseline)을 같은 조건에서 반복 측정합니다. 최소한 다음 문맥을 측정값과 묶습니다.

```text wrap
대상 결과: 모임 목록에서 상세 화면의 제목과 참가 가능 상태 확인
빌드·환경: staging, commit abc123, server profile S1
사용자 조건: 연습용 fixture 200개, 빈 캐시, 지정한 브라우저·기기·네트워크
측정 구간: 사용자의 클릭부터 제목과 참가 상태가 화면에 반영될 때까지
통계: warm-up 제외, 반복 횟수와 중앙값·p95, 실패 횟수
자원: 서버 CPU·메모리·DB 쿼리 수와 시간, 전송 바이트
```

위 값은 측정 계약의 형식을 보여 주는 예시이지 실제 제품의 합격 수치나 장비를 정한 것이 아닙니다. 평균 하나만 기록하면 일부 사용자의 긴 지연과 실패를 숨길 수 있고, 한 번의 가장 좋은 결과만 기록하면 재현성을 알 수 없습니다.

### 병목은 추측이 아니라 프로필에서 찾습니다

**병목(bottleneck)**: 전체 결과의 처리량이나 지연을 현재 제한하는 구간입니다. 화면이 늦게 보인다고 프런트엔드가 원인인 것은 아닙니다. 느린 데이터베이스 쿼리, 직렬 API 호출, 큰 전송량, 메인 스레드 작업, 자원 포화나 외부 서비스 대기가 원인일 수 있습니다.

1. 사용자 결과와 기준선을 재현합니다.
2. 브라우저 프로필·서버 trace·쿼리 계획·자원 지표에서 시간이 쓰인 구간을 분해합니다.
3. 가장 큰 구간이 실제 전체 결과를 제한하는지 가설과 예측을 씁니다.
4. 한 요인만 바꾸는 작은 실험으로 가설을 구분합니다.
5. 같은 조건의 변경 전후 결과와 실패·자원 비용을 비교합니다.
6. 주변 사용자 구간과 기능의 회귀를 확인합니다.

Chrome DevTools Performance 패널은 웹 페이지의 런타임 프로필을 보는 한 제품 사례이고, W3C User Timing·Resource Timing은 애플리케이션 구간과 자원 로딩 시간을 계측할 수 있는 웹 API 초안입니다. 이 도구들이 데이터베이스·외부 API·사용자 목적을 자동으로 설명하지 않으므로 서버와 권위 상태 증거를 함께 봅니다.

### 변경 전후 비교의 최소 계약

“캐시를 넣어 80% 빨라졌다”에는 분모와 조건이 없습니다. 다음을 함께 보고합니다.

- 같은 fixture·환경·버전 구분과 측정 코드
- 변경 전후의 표본 수·분포·실패 수
- 사용자 결과 지표와 CPU·메모리·쿼리·전송량 같은 자원 지표
- 다른 사용자 구간, 빈 캐시·찬 시작, 데이터 증가에서의 결과
- 정확성·최신성·접근성·보안·운영 복잡성에 생긴 부작용
- 성능 회귀 검사와 예산 초과 시 중단·복구 경로

특정 테스트에서 개선됐다는 증거를 모든 사용자·지역·부하의 보장으로 확대하지 않습니다. 측정 불확실성과 확인하지 않은 범위를 함께 남깁니다.

## 보안: 자산에서 시작해 위협과 경계를 그립니다

### 자산·위협·신뢰 경계를 먼저 식별합니다

- **자산(asset)**: 공격·실수로 노출·변조·삭제·중단됐을 때 보호할 가치가 있는 데이터·권한·기능·서비스입니다.
- **위협(threat)**: 어떤 주체나 사건이 자산의 기밀성·무결성·가용성 또는 정당한 사용을 해칠 수 있는 가능성입니다. 취약점 하나와 같은 뜻이 아닙니다.
- **진입점(entry point)**: 브라우저 요청, 업로드 파일, 관리자 도구, 외부 webhook, CI 입력처럼 데이터나 제어가 들어오는 위치입니다.
- **신뢰 경계(trust boundary)**: 서로 다른 신뢰 수준이나 권한 주체 사이에서 값과 제어가 오가는 경계입니다. 경계를 넘은 값은 신뢰 가능한 쪽에서 다시 검증합니다.

위협 모델은 그림 한 장이 아니라 다음 질문과 결정 기록입니다.

1. 무엇을 만들고 어디까지가 범위인가?
2. 중요한 자산과 주체는 누구인가?
3. 데이터와 제어가 어느 구성요소·외부 의존성·신뢰 경계를 통과하는가?
4. 오용·권한 상승·노출·변조·거부·공급망 실패가 어디에서 가능한가?
5. 영향·발생 가능성·노출 범위·탐지와 복구 난이도로 무엇을 먼저 줄일 것인가?
6. 예방·탐지·대응·복구 통제가 실제로 작동함을 무엇으로 시험할 것인가?
7. 어떤 잔여 위험을 누가 언제까지 수용하거나 다시 검토하는가?

위협 모델 문서가 있다는 사실은 현재 구현이 안전하다는 증거가 아닙니다. 설계·데이터·의존성·공격 경로가 바뀔 때 모델과 시험 결과를 다시 대조합니다.

## 핵심 보안 통제와 한계

### 최소 권한

**최소 권한(least privilege)**: 사용자·서비스·에이전트·프로세스에 맡은 작업에 필요한 최소 권한만 필요한 기간 동안 부여하는 원칙입니다. 읽기 작업에 관리자 쓰기 권한을 주지 않고, 배포 주체와 운영 데이터 변경 주체를 분리하며, 임시 권한에는 만료와 회수 경로를 둡니다.

역할 이름이 `viewer`라는 사실은 최소 권한 증거가 아닙니다. 실제 허용·거절 정책, 자원 범위, 기본 거절, 매 요청 집행, 권한 변경·회수와 우회 경로를 시험해야 합니다. 최소 권한만으로 훔친 자격 증명·취약한 코드·잘못된 업무 규칙이 없어지는 것도 아닙니다.

### 입력 검증

**입력 검증(input validation)**: 신뢰 경계를 넘는 값이 허용된 형식과 업무 의미를 만족하는지 신뢰 가능한 쪽에서 확인하고 잘못된 입력을 안전하게 거절하는 통제입니다.

- 문법 검증: 타입·길이·형식·허용 문자·필수 필드
- 의미 검증: 날짜 순서·정원·상태 전이·가격 범위 같은 업무 규칙
- 경계 검증: 브라우저뿐 아니라 외부 API 응답·업로드 파일·큐 메시지·관리 도구 입력
- 실패 계약: 안전한 오류 응답, 부작용 없음, 필요한 최소 진단 기록

클라이언트 검증은 빠른 피드백에는 유용하지만 사용자가 바꿀 수 있으므로 서버의 권한·업무 검증을 대신하지 않습니다. 입력 검증도 인가, 출력 인코딩, 안전한 쿼리 구성과 같은 다른 통제를 자동으로 대신하지 않습니다.

### 비밀 관리

**비밀(secret)**: 유출되면 시스템·데이터·외부 서비스에 권한을 줄 수 있는 비밀번호·개인 키·접근 토큰·연결 자격 같은 값입니다. 비밀 관리는 저장 위치 하나가 아니라 생성·배포·사용·회전·폐기·감사·유출 대응의 수명주기입니다.

- 소스·예시·로그·오류·스크린샷에 실제 비밀을 넣지 않습니다.
- 필요한 서비스와 환경에만 최소 범위·짧은 수명의 자격을 전달합니다.
- 비밀 값을 출력하지 않고 사용·실패·회전 사건을 감사할 수 있게 합니다.
- 소유자, 만료·회전, 회수와 유출 시 폐기·재발급 절차를 둡니다.
- 브라우저에 전달된 번들·정적 파일·응답 값은 사용자가 읽을 수 있다고 간주합니다.

환경 변수에 넣었다는 사실만으로 비밀이 암호화·격리·회전되는 것은 아닙니다. 공개 프런트엔드에서 키 이름을 난독화해도 비밀이 되지 않습니다.

### 의존성 위험

의존성은 직접 작성하지 않은 코드·빌드·배포 경로를 시스템에 들입니다. 위험은 알려진 취약점뿐 아니라 악성 변경, 출처 위조, 유지 중단, 전이 의존성, 호환성 파손, 과도한 권한과 업데이트 실패를 포함합니다.

1. 실제 직접·전이 의존성, 버전·출처·잠금 상태를 식별합니다.
2. 필요하지 않은 의존성과 실행 권한을 줄입니다.
3. 공식 보안 권고와 생태계의 검증 가능한 취약점 정보를 대상 버전에 대조합니다.
4. 업데이트 diff·빌드·테스트·라이선스·동작 변경을 검토합니다.
5. 배포 후 탐지 신호와 문제가 생길 때 되돌릴 버전·데이터 호환 경로를 준비합니다.

“최신 버전”이나 “스캐너 0건”은 안전 보장이 아닙니다. 데이터베이스가 알지 못하는 취약점, 잘못된 설정, 자체 코드와 업무 권한, 아직 공개되지 않은 문제는 남을 수 있습니다. 반대로 스캐너 경고 하나만으로 실제 노출과 우선순위를 확정하지 않고 사용 경로·권한·영향을 확인합니다.

## 위험과 개선을 우선순위화합니다

성능과 보안 모두 모든 문제를 동시에 없앨 수 없습니다. 다음 표로 선택 이유를 기록합니다.

| 항목 | 질문 |
|---|---|
| 사용자·자산 영향 | 얼마나 많은 사용자가 어떤 목적을 못 이루거나 어떤 자산이 노출·변조·중단되는가? |
| 발생 가능성과 노출 | 현재 경로·트래픽·권한·입력에서 얼마나 쉽게 반복되거나 악용되는가? |
| 피해 범위 | 한 요청·계정·환경에 제한되는가, 전체 데이터·서비스로 퍼지는가? |
| 탐지와 복구 | 얼마나 빨리 알고 안전 상태로 돌아갈 수 있으며 데이터·외부 부작용은 남는가? |
| 증거 신뢰도 | 실제 측정·프로필·재현·통제 시험인가, 추측·도구 경고·문서 존재뿐인가? |
| 변경 비용과 부작용 | 구현·운영 비용과 정확성·접근성·성능·보안의 새로운 위험은 무엇인가? |

심각한 비밀 노출이나 무단 권한 상승처럼 영향이 큰 문제는 성능 개선보다 먼저 공개·접근을 제한하고 자격을 폐기해야 할 수 있습니다. 다만 “보안은 항상 최우선”처럼 맥락 없는 문구 대신 실제 자산·영향·노출·복구 증거로 긴급성과 행동을 설명합니다.

## 반복 사례: 모임 참가 흐름

다음 수치는 측정 계약을 연습하기 위한 가정이며 실제 제품 기준이 아닙니다.

### 성능 계약과 병목 확인

목표는 참가자가 모임 상세에서 정원 상태를 확인하고 참가 결과를 알 수 있는 것입니다. 팀은 지정한 staging 빌드, 테스트 기기·네트워크, 200개 모임 fixture에서 클릭부터 확정·거절 상태 표시까지의 p95 예산을 정하고, 실패 수·DB 시간·전송량을 함께 기록합니다.

프로필에서 전체 시간의 대부분이 참가자 수를 반복 집계하는 쿼리에 쓰인다면 “프런트가 느리다” 대신 쿼리 병목 가설을 세웁니다. 인덱스나 조회 구조 한 가지만 바꾸고 같은 fixture에서 전후 분포를 비교합니다. 참가 정확성·정원 동시성·빈 캐시·더 큰 fixture의 회귀와 자원 비용도 확인합니다.

### 자산·위협·경계 확인

보호 자산은 계정 신원, 참가 관계, 연락 정보, 모임 정원과 취소 권한, 서비스 가용성입니다. 브라우저↔서버, 서버↔데이터베이스, CI↔배포 환경의 경계를 그립니다. 가능한 위협은 다른 사용자의 참가 취소, 조작한 정원 값, 동시 요청으로 인한 초과 참가, 로그의 토큰 노출, 취약한 인증 의존성입니다. 참가자에게 보내는 제품 알림은 첫 프로젝트의 비목표이며, 담당자에게 장애를 알리는 운영 경보와 다릅니다.

통제는 위협과 직접 연결합니다. 서버는 매 요청에서 현재 사용자와 대상 모임의 권한을 확인하고, 참가 입력의 형식·업무 상태를 검증하며, 데이터베이스 불변식과 트랜잭션으로 정원을 보호합니다. 서버의 데이터베이스 접근 자격은 필요한 환경·행동으로 제한하고 브라우저나 로그에 전달하지 않습니다. 의존성 버전·출처와 업데이트 결과를 기록하며, 기능 제한·안전 버전 전환·잘못된 상태 판정과 복구 절차를 둡니다.

### 완료 증거

- 지정한 조건에서 변경 전후 성능 분포와 예산 판정
- 정상·정원 마감·중복·동시 요청·무권한 취소의 테스트 결과
- 브라우저 요청을 조작해도 서버와 데이터 계층이 거절하고 불변식을 지킨 증거
- 비밀 없는 로그와 안전한 상관 식별자, 탐지 경보의 시험 결과
- 대상 빌드·환경에서 참가·취소 사용자 흐름과 권위 데이터 재조회
- 기능 제한·자격 폐기·이전 안전 버전·데이터 정정 절차의 연습 결과

화면이 빨라 보이고 정상 참가 한 건이 성공한 것만으로 성능 예산·무권한 경로·동시성·복구가 모두 통과한 것은 아닙니다.

## 흔한 실패와 교정

| 실패 | 왜 위험한가 | 교정 |
|---|---|---|
| 측정 없이 캐시·비동기화·재작성을 먼저 함 | 실제 병목을 못 줄이고 최신성·권한 위험을 추가함 | 기준선과 프로필로 병목 가설을 세우고 한 요인씩 비교함 |
| 한 기기·한 번의 최고 수치로 “빠르다”고 선언함 | 사용자 구간·분포·실패·환경 차이를 숨김 | 조건·표본·분위수·실패와 미확인 범위를 함께 기록함 |
| 보안 도구 경고 0건을 안전 완료로 선언함 | 도구 범위 밖 위협·설정·업무 권한이 남음 | 자산·경계·위협과 통제 시험·잔여 위험을 대조함 |
| 프런트 검증이나 숨긴 버튼을 인가로 사용함 | 요청을 직접 조작하면 우회할 수 있음 | 신뢰 가능한 경계에서 매 요청 권한과 업무 규칙을 집행함 |
| 관리자 키를 여러 환경·서비스에서 공유함 | 한 유출의 피해 범위와 회전 비용이 커짐 | 역할·환경·기간별 최소 권한과 회수·재발급 경로를 둠 |
| 의존성을 무조건 최신으로 일괄 갱신함 | 취약점은 줄어도 호환성·공급망·복구 위험이 생김 | 대상 위험을 확인하고 작은 diff·테스트·배포·rollback 증거를 남김 |
| 통제 문서와 체크 표시를 실행 증거로 사용함 | 현재 코드·설정·권한·복구가 문서와 다를 수 있음 | 대상 버전에서 허용·거절·탐지·복구 경로를 실제 시험함 |

## AI와 작업할 때의 요청 계약

```text wrap
아직 최적화나 보안 수정을 하지 마세요.

1. 핵심 사용자 결과, 사용자 구간, 대상 버전·환경과 현재 성능 기준선을 정의하세요.
2. 시간·자원 성능 예산과 초과 시 행동을 쓰되 외부 예시 수치를 보편 기준으로 사용하지 마세요.
3. 프로필·trace·쿼리·자원 지표에서 시간을 구간별로 나누고 병목 가설과 반증 조건을 제시하세요.
4. 자산·주체·진입점·데이터 흐름·신뢰 경계·위협을 표로 만드세요.
5. 최소 권한·입력 검증·비밀 수명주기·직접/전이 의존성 위험을 각 위협과 연결하세요.
6. 사용자·자산 영향, 발생 가능성, 피해 범위, 탐지·복구 난이도, 증거 신뢰도로 우선순위를 설명하세요.
7. 한 번에 한 요인만 바꾸는 최소 변경, 부작용, 중단 조건과 복구 경로를 제시하세요.
8. 같은 조건의 변경 전후 측정, 허용·거절·오용 테스트, 배포 후 사용자 결과와 권위 상태 증거를 설계하세요.
9. 확인하지 못한 환경·위협·도구 범위와 잔여 위험을 명시하세요.

실제 비밀·개인정보를 읽거나 출력하지 말고, 새 패키지 설치·네트워크·권한 확대·배포는 별도 승인 없이는 실행하지 마세요. “빠르다”, “안전하다”, “모든 취약점을 해결했다”는 포괄 결론을 쓰지 마세요.
```

AI가 기술 목록만 제안하면 “어떤 측정된 병목 또는 우선 위협을 줄이며, 어떤 증거가 틀렸음을 보여 줄 수 있는가?”를 다시 묻습니다.

- [ ] 미확인 범위·잔여 위험·재검토 조건과 책임자를 기록했나요?

## 짧은 연습

자신의 프로젝트에서 핵심 사용자 행동 하나를 골라 `결과 / 사용자 구간 / 환경 / 지표 / 통계 / 한도 / 초과 시 행동`으로 성능 예산을 작성하세요. 같은 흐름의 자산 세 개와 신뢰 경계 두 개를 그린 뒤 위협 세 개를 고릅니다. 각 위협에 예방·탐지·복구 증거를 하나씩 연결하고, 성능 문제와 함께 영향·가능성·복구 난이도로 우선순위를 정하세요. 마지막으로 외부 예시 수치나 보안 도구 결과를 과대 일반화한 문장이 없는지 확인하세요.

- [web.dev의 Your First Performance Budget](https://web.dev/articles/your-first-performance-budget)은 2018년 공개된 Google 교육 글을 2026-08-13 현재 확인해 사용자 목적·환경에 맞춘 시간·자원량·규칙 기반 예산의 교육 범위에 사용했습니다. 글의 예시 수치·기기·네트워크를 모든 사이트의 합격 기준으로 사용하지 않습니다.

OWASP가 단일 필수 방법을 정하거나 위협 모델 문서 하나가 현재 구현의 안전을 보장한다고 확대하지 않습니다.
