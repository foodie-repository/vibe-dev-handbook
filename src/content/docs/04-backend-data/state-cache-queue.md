## 먼저 결론

상태(state)는 시스템이 다음 판단에 사용하려고 기억하는 값입니다. 그러나 같은 사실처럼 보이는 값이 브라우저, 서버 메모리, 데이터베이스, 캐시와 큐에 여러 형태로 존재할 수 있습니다. 그래서 “값이 어디에 있는가”보다 **어느 상태가 이 결정을 내릴 권위를 갖고, 나머지 사본은 얼마나 늦거나 틀릴 수 있으며, 실패 뒤 무엇을 다시 확인할 것인가**를 먼저 정해야 합니다.

모임 참가 웹앱에서는 데이터베이스에 `commit`된 `events`와 `registrations`가 참가 여부와 정원의 권위 있는 상태입니다. 화면의 “남은 자리 1개”, 브라우저의 참가 버튼, 캐시된 모임 상세는 파생 상태일 수 있습니다. 세션은 여러 요청에서 인증된 주체를 연결하지만 참가 여부나 주최 권한 자체를 대신하지 않습니다. 큐는 나중에 처리할 작업이나 메시지를 전달하지만, 메시지가 존재한다는 사실만으로 현재 참가 상태가 확정되지는 않습니다.

첫 모임 캡스톤에는 별도 캐시와 메시지 큐가 필요하다고 입증되지 않았습니다. 단일 웹앱과 관계형 데이터베이스의 동기 요청 흐름으로 시작하고, 측정된 조회 부하나 요청보다 오래 살아야 하는 비동기 작업이 생길 때만 추가합니다. 새 구성요소는 속도나 분리를 얻는 대신 신선도·중복·순서·재처리·관측과 복구 책임을 늘립니다.

## 쉬운 말에서 정식 용어로

| 쉬운 질문 | 정식 용어 | 모임 웹앱의 예 | 틀릴 때의 위험 |
|---|---|---|---|
| 이 판단의 기준은 무엇인가요? | 권위 상태(authoritative state) | `commit`된 이벤트·참가 관계 | 오래된 화면을 기준으로 마지막 자리를 확정함 |
| 기준에서 다시 만든 값인가요? | 파생 상태(derived state) | 남은 자리 수, 버튼 상태, 집계 | 원본 변경 뒤 갱신되지 않아 서로 다르게 보임 |
| 여러 요청에서 무엇을 이어 가나요? | 세션(session) | 로그인한 주체와 세션 수명 | 로그인 사실을 모든 대상의 권한으로 오해함 |
| 빠르게 읽으려고 둔 사본인가요? | 캐시(cache) | 공개 모임 상세의 저장된 응답 | 오래된 모집 상태·정원을 현재 값처럼 표시함 |
| 나중에 처리할 전달 단위인가요? | 큐(queue) | 미래 알림 기능의 작업 대기 | 재전달을 새 업무 사실로 처리해 부작용을 반복함 |
| 어떤 일이 일어났다는 기록인가요? | 이벤트(event) | `registration.confirmed`라는 사건 설명 | 이벤트 전달과 현재 상태를 같은 것으로 오해함 |

**권위 상태(authoritative state):** 정원 승인, 참가 여부, 게시 버전처럼 특정 판단에서 기준으로 선택한 상태입니다. 모든 질문에 하나의 저장소가 항상 권위 있는 것은 아닙니다. 예를 들어 인증 세션의 수명은 세션 저장소가, 참가 관계는 애플리케이션이 선택한 관계형 데이터베이스가 기준일 수 있으므로 질문별로 지정해야 합니다.

**파생 상태(derived state):** 권위 상태에서 계산·변환·복제해 만든 값입니다. 다시 만들 수 있다는 점이 핵심이며, 원본과 같은 시점의 값을 항상 보장하지는 않습니다. 브라우저에 보이는 참가자 수나 캐시된 응답을 파생 상태로 선언했다면 불일치 때 버리고 원본에서 다시 만드는 경로가 필요합니다.

**최종적 일관성(eventual consistency):** 여러 사본이 즉시 같지 않을 수 있지만 새 변경이 멈추고 전달·처리가 정상적으로 계속되면 정한 조건 아래 같은 목표 상태로 수렴하도록 설계한 성질입니다. “언젠가는 맞는다”는 면책 문구가 아니며 수렴 조건, 허용 지연, 사용자 표시, 충돌과 영구 실패 처리를 정의해야 합니다.

## 비유: 원장, 열람용 사본, 작업 바구니

권위 상태는 도서관의 대출 원장, 캐시는 자주 찾는 정보를 복사해 둔 열람용 카드, 큐는 반납 책을 처리 순서대로 놓는 작업 바구니에 비유할 수 있습니다. 열람용 카드가 오래됐으면 원장을 다시 보고, 바구니에 같은 책이 두 번 표시됐으면 현재 대출 상태를 확인한 뒤 처리해야 한다는 차이를 설명하는 데 유용합니다.

그러나 소프트웨어에서는 이 비유가 금방 깨집니다. 메시지는 네트워크와 소비자 실패 때문에 재전달될 수 있고, 여러 소비자가 병렬로 처리하면 관찰 순서가 달라질 수 있습니다. 캐시는 계층마다 다른 정책을 가질 수 있으며, 권위 상태도 여러 데이터 저장소에 나뉠 수 있습니다. 사람 한 명이 원장과 바구니를 눈으로 동시에 통제한다고 가정하지 말고, 구성요소별 계약과 실제 관측 증거를 확인해야 합니다.

## 모임 참가 흐름의 상태 지도

가상 모임 `event-example-001`의 정원은 10명이고 데이터베이스에 확정된 활성 참가가 9명이라고 가정하겠습니다. 참가자 A의 브라우저가 “남은 자리 1개”를 표시하는 동안 참가자 B가 먼저 확정될 수 있습니다.

| 위치 | 담을 수 있는 값 | 이 사례의 책임 | 권위 여부 |
|---|---|---|---|
| 브라우저 UI 상태 | 로딩, 버튼 비활성, 마지막 응답, 낙관적 표시 | 사용자 의도와 진행 상태를 표현 | 참가 확정의 권위 아님 |
| 세션 | 인증된 주체, 만료·폐기 정보 | 여러 요청에서 “누가 요청했는가”를 연결 | 대상별 참가·주최 권한의 권위 아님 |
| HTTP 또는 애플리케이션 캐시 | 공개 모임 상세의 저장된 응답·계산 결과 | 허용된 범위에서 읽기 비용을 줄임 | 최신 정원 판정의 권위 아님 |
| 관계형 데이터베이스 | `events`, `registrations`, 제약과 트랜잭션 | 중복·모집 상태·정원을 판정하고 영속 상태를 확정 | 이 아키텍처의 참가 판단 권위 |
| 메시지 큐 | 처리 대기 메시지, 전달·재전달 상태 | 요청과 독립된 작업을 소비자에게 전달 | 현재 참가 관계의 권위 아님 |
| 로그·메트릭 | 작업 ID, 결과 분류, 지연·오류 집계 | 원인과 영향 범위를 좁힐 운영 증거 | 단독으로 현재 업무 상태를 확정하지 않음 |

사용자가 참가 버튼을 눌렀다는 브라우저 이벤트, 서버가 참가 요청을 받았다는 로그, 큐에 메시지가 있다는 사실, 데이터베이스에 참가가 `commit`됐다는 사실은 모두 다릅니다. 응답이 유실되면 화면은 실패를 보여도 데이터베이스에는 참가가 확정돼 있을 수 있으므로, 자신의 현재 참가 관계와 모임 상태를 권한 있는 읽기 계약으로 재조회해야 합니다.

## 파생 상태와 신선도 계약

신선도(freshness)는 사본이 판단 목적에 비춰 얼마나 최근 원본을 반영하는지를 나타냅니다. “5분 캐시” 같은 숫자 하나만으로 충분하지 않습니다. 어떤 시각 또는 버전의 원본에서 만들었는지, 언제까지 어떤 용도로 허용하는지, 원본 변경을 어떻게 알리는지, 오래됐거나 모르면 무엇을 표시하고 어떤 행동을 막을지 정해야 합니다.

모임 소개 문구처럼 조금 늦어도 피해가 작은 공개 읽기와 마지막 한 자리 승인처럼 즉시 현재 상태가 필요한 쓰기를 같은 캐시 정책으로 다루지 않습니다. 화면에 남은 자리가 보여도 서버와 데이터베이스는 참가 트랜잭션 안에서 최신 권위 상태를 다시 판정해야 합니다. 캐시 삭제 버튼은 한 계층의 사본을 지울 수 있을 뿐, 다른 브라우저·CDN·서버 메모리·데이터베이스의 상태가 모두 일치했다는 증거가 아닙니다.

| 신선도 질문 | 계약 예시 | 실패 시 행동 |
|---|---|---|
| 원본 버전은 무엇인가? | `event_version=8`에서 만든 상세 응답 | 버전이 모르면 최신이라고 표시하지 않음 |
| 언제 만들었나? | 생성 시각과 재검증 시각을 구분 | 시계·시간대와 관찰 시점을 함께 기록 |
| 어디에 써도 되나? | 공개 목록 표시에는 허용, 참가 승인에는 사용 금지 | 쓰기 판단에서 데이터베이스 재조회 |
| 오래되면 무엇을 보이나? | “상태를 다시 확인 중”과 마지막 확인 시각 | 성공·자리 보장을 먼저 표시하지 않음 |
| 어떻게 회복하나? | 재검증 또는 원본 재조회 뒤 파생 값 교체 | 실패한 사본을 권위 값으로 승격하지 않음 |

RFC 9111은 HTTP 캐시에서 응답의 현재 나이, 최신성 수명, fresh와 stale, 재검증 조건을 정의합니다. 이 규칙은 HTTP 캐시의 표준 범위이며 애플리케이션 메모리 캐시, 데이터베이스 읽기 사본, 모든 CDN 제품의 내부 정책을 자동으로 정하지 않습니다. 선택한 캐시 제품과 구성의 만료·무효화·일관성 보장은 별도로 확인해야 합니다.

## 세션은 상태지만 업무 원장은 아닙니다

세션은 로그인 같은 인증 사건을 여러 HTTP 요청에 연결할 수 있습니다. 서버는 세션에서 현재 주체를 확인한 뒤에도 요청한 모임, 자신의 참가 관계, 주최자 소유권과 현재 모집 상태를 신뢰할 수 있는 경계에서 다시 판단해야 합니다.

브라우저가 보낸 `participant_id`나 세션 안에 오래 저장된 `is_host=true`를 현재 권한의 최종 근거로 삼으면 계정·소유권·정책 변경을 놓칠 수 있습니다. 세션 수명·폐기·탈취 대응과 업무 데이터의 권위 원본을 분리하고, 권한이 바뀔 수 있는 행동은 현재 대상과 정책을 재확인합니다. 세션이 있다는 사실은 로그인 상태의 한 증거이지 모든 행동 허가가 아닙니다.

## 큐는 언제 필요한가

큐는 사용자의 요청이 끝난 뒤에도 살아야 하는 작업, 처리 속도를 분리해야 하는 부하, 일시적으로 소비자가 없어도 보존할 메시지가 있을 때 후보가 됩니다. 큐를 넣으면 요청자는 메시지를 **전달하려고 맡긴 상태**와 업무가 **실제로 완료된 상태**를 구분해야 합니다.

현재 모임 캡스톤은 알림·메일·캘린더가 비목표이고 참가 확정은 응답 전에 데이터베이스 트랜잭션으로 끝나야 합니다. 따라서 큐를 핵심 참가 경로에 넣지 않습니다. 미래에 알림 요구가 승인된다면 참가 확정 뒤 알림 작업을 비동기로 전달하는 후보를 검토할 수 있지만, “알림 전송 성공”과 “참가 확정”은 서로 다른 상태여야 합니다. 알림 실패 때문에 이미 확정된 참가를 임의로 취소해서도 안 됩니다.

큐 도입 판단은 다음 질문에서 시작합니다.

- 요청 안에서 끝내면 실제 사용자 지연이나 자원 한계를 넘나요?
- 작업이 요청 연결보다 오래 살아야 하나요?
- 처리 소비자가 잠시 없어도 작업을 보존해야 하나요?
- 같은 작업이 다시 전달돼도 안전하게 판별할 식별자와 결과 저장소가 있나요?
- 작업 완료·실패·보류 상태를 사용자와 운영자가 어디에서 확인하나요?
- 큐가 없을 때의 단순한 동기 처리보다 운영 복잡성이 정당한가요?

## 이벤트와 큐 메시지를 현재 상태로 오해하지 않기

이벤트는 “무슨 일이 일어났는가”를 설명하는 기록입니다. 큐 메시지는 이벤트나 명령을 소비자에게 전달하는 봉투일 수 있습니다. 같은 내용이 있어도 이벤트 ID, 대상 ID, 원본 버전, 발생 시각, 스키마 버전, 처리 상태를 구분해야 합니다.

`registration.confirmed` 이벤트가 전달됐다는 사실은 한 시점에 참가 확정이 있었다는 뜻일 수 있지만, 현재도 참가 중이라는 뜻은 아닙니다. 사용자가 곧 취소했거나 주최자가 모임을 취소했을 수 있기 때문입니다. 현재 상태에 따라 행동해야 하는 소비자는 메시지 내용만 믿지 말고 처리 직전에 권위 있는 원본을 다시 읽어야 합니다.

재조회는 필요하지만, 조회 직후 상태가 바뀌는 경쟁까지 없애지는 않습니다. 데이터베이스 안의 상태·버전 판정과 결과 갱신은 조건부 갱신이나 적절한 트랜잭션 전략으로 함께 보호해야 합니다. 조회와 무조건 갱신을 분리하면 그 사이 저장된 최신 결과를 덮을 수 있습니다. 외부 알림은 이 데이터베이스 경계 밖이므로 발송을 허용하는 기준 시점과 이후 취소 처리까지 별도 계약이 필요합니다.

이벤트를 데이터베이스의 유일한 원본으로 사용하는 이벤트 소싱 같은 아키텍처도 가능하지만, 이 책의 첫 모임 웹앱은 그런 구조를 채택하지 않습니다. 이벤트 로그를 추가했다는 이유만으로 권위 상태가 자동으로 바뀌지 않으며, 그 구조를 선택하려면 재생·버전·스냅샷·호환성과 복구 계약을 별도로 설계해야 합니다.

## 중복과 재전달을 정상 가능성으로 다루기

네트워크가 끊기면 생산자는 메시지가 받아들여졌는지 확신하지 못하고 다시 보낼 수 있습니다. 소비자는 작업을 끝냈지만 완료 확인을 보내기 전에 연결을 잃을 수 있습니다. RabbitMQ 공식 reliability 문서는 consumer acknowledgement 전에 연결이나 채널이 끊기면 확인되지 않은 전달이 다시 큐에 들어가 다른 소비자에게 재전달될 수 있는 제품 동작을 설명합니다. 이 문서는 한 메시징 제품의 계약이며 모든 큐의 동일 보장을 뜻하지 않습니다.

RabbitMQ에서 생산자 확인(publisher confirm)은 브로커가 제품 계약에 따라 메시지를 수락·보관하는 책임을 맡았다는 경계입니다. 소비자 확인(consumer acknowledgement)은 소비자가 전달받은 메시지를 처리했다고 브로커에 알리는 별도 경계입니다. 생산자 확인을 받았어도 소비자는 아직 실행하지 않았을 수 있고, 업무를 마친 뒤 소비자 확인만 유실될 수도 있습니다. 어느 확인도 임의의 외부 알림을 자동으로 정확히 한 번 성공시키지는 않습니다.

따라서 소비자는 “한 번만 전달될 것”이라는 희망보다 **같은 업무 식별자가 다시 와도 결과를 판별할 수 있는가**를 설계해야 합니다. 이것이 멱등 처리의 핵심입니다.

| 상황 | 나쁜 처리 | 필요한 계약 |
|---|---|---|
| 같은 알림 작업이 재전달됨 | 메시지 수신 횟수만큼 외부 부작용 반복 | 안정된 작업 ID와 처리 결과·외부 중복 방지 범위 확인 |
| 소비자가 DB 변경 뒤 완료 확인 전에 종료 | 무조건 처음부터 다시 변경 | 권위 상태와 기존 처리 결과를 조회한 뒤 남은 단계만 판단 |
| 영구 형식 오류가 계속 재시도됨 | 무한 재시도로 큐와 외부 서비스 압박 | 재시도 가능 오류 분류, 횟수·간격·최종 보류 위치·담당자 |
| 처리 중 일부만 성공 | 전체 성공으로 기록하거나 조용히 폐기 | 단계별 결과, 보상 또는 수동 복구, 재실행 시작점 |

멱등성은 함수 이름이나 메시지 키 하나로 자동 생기지 않습니다. 키의 범위와 수명, 처리 결과를 어디에 원자적으로 기록할지, 외부 서비스의 중복 방지 계약, 실패 뒤 재조회 방법을 확인해야 합니다.

## 순서는 업무 버전으로 검증하기

큐 이름이 FIFO처럼 보여도 모든 업무 사건의 전역 순서를 보장한다고 가정하지 않습니다. 여러 생산자·소비자, 재전달, 우선순위, 재시도 경로가 있으면 관찰 순서가 달라질 수 있고, 제품과 구성마다 보장이 다릅니다. RabbitMQ의 큐 문서도 순서가 여러 요인의 영향을 받을 수 있는 제품 범위를 설명하므로 선택한 큐의 구체 계약을 다시 확인해야 합니다.

모임이 `open → closed`로 바뀐 뒤 오래된 `open` 이벤트가 늦게 도착할 수 있다고 생각해 보겠습니다. 소비자가 도착 순서만 믿고 상태를 덮으면 마감된 모임을 다시 열 수 있습니다. 메시지의 `event_version`이나 업무 시각을 현재 원본 버전과 비교하고, 오래된 명령을 거절하거나 현재 상태에서 안전한 파생 결과만 다시 계산해야 합니다. 단, 버전 숫자만 추가한다고 전체 순서 문제가 해결되지는 않습니다. 버전 생성 주체, 비교 범위, 누락·분기·동률 처리와 원본 재조회 계약이 필요합니다.

## 재처리는 원본 확인에서 시작하기

재처리(reprocessing)는 실패하거나 보류된 작업을 다시 실행하는 활동입니다. “메시지를 다시 큐에 넣기”는 재처리의 일부일 뿐이며, 이전 시도 뒤 권위 상태와 외부 부작용이 어떻게 바뀌었는지 먼저 확인해야 합니다.

미래 알림 작업을 예로 들면 다음 순서를 사용할 수 있습니다.

1. 안정된 `job_id`, `event_id`, `registration_id`, 메시지 스키마 버전을 읽습니다.
2. 이전 처리 결과와 시도 횟수, 마지막 오류 분류를 확인합니다.
3. 데이터베이스에서 현재 모임과 참가 관계를 권한 있는 경로로 재조회하고, 상태·버전 판정과 발송 결정 기록을 함께 보호합니다.
4. 발송 결정 전에 참가나 모임의 취소가 확정됐다면 오래된 “확정 알림”을 보내지 않고 `superseded`처럼 명시한 결과로 끝냅니다.
5. 발송 결정 이후 취소와 외부 전송이 경쟁하면, 결정 시점의 상태를 기준으로 발송할지 가능한 취소·보상 경로를 적용할지 미리 정한 계약으로 판단합니다. 기존 외부 결과·중복 방지·결과 불명 처리도 확인합니다. 재조회 한 번으로 전송 시점의 상태나 취소 후 발송 금지까지 보장했다고 하지 않습니다.
6. 성공·재시도·영구 보류 결과를 안전한 식별자와 함께 기록하고, 완료 확인 시점은 선택한 큐 계약에 맞춥니다.

이 예시는 알림 기능을 현재 캡스톤에 추가하라는 요구가 아닙니다. 큐를 도입한 미래 범위에서 메시지의 과거 사실보다 현재 권위 상태를 우선하는 복구 원리를 보여 줍니다.

재조회 전에 취소가 확정된 경우, 재조회 뒤 외부 전송 전에 취소가 확정된 경우, 버전 비교 뒤 다른 작업의 최신 결과가 먼저 저장된 경우를 따로 시험합니다. 첫 경우에는 발송을 막고, 두 번째는 정한 발송 시점·취소 계약과 남는 한계를 확인하며, 세 번째는 조건부 갱신 실패 등으로 최신 결과를 보존해야 합니다. 외부 호출 동안 데이터베이스 잠금을 유지하는 방식을 모든 서비스의 해법으로 삼지 않습니다.

## 데이터베이스와 큐 사이의 부분 실패

데이터베이스 변경과 메시지 발행이 서로 다른 시스템에서 일어나면 두 작업을 단순히 하나의 트랜잭션이라고 부를 수 없습니다. 참가가 `commit`됐지만 이벤트 발행이 실패할 수도 있고, 메시지는 전달됐지만 데이터베이스 트랜잭션은 실패할 수도 있습니다.

“DB 저장 후 큐에 보내면 된다”는 두 줄 사이에 프로세스가 종료될 수 있습니다. 이 경계를 다룰 때는 선택한 데이터베이스와 메시징 제품의 공식 보장을 확인하고, 미발행 작업을 식별·재시도하는 기록, 처리자가 원본을 재조회하는 계약, 중복을 허용하되 안전하게 판별하는 방법을 설계해야 합니다. 같은 데이터베이스 트랜잭션에 발행할 이벤트 기록을 남기고 별도 전달자가 보내는 outbox pattern은 검토 후보 중 하나지만, 모든 제품의 자동 해법이나 이 캡스톤의 필수 구조로 제시하지 않습니다.

## 최종적 일관성을 허용할 곳과 허용하지 않을 곳

사용자에게 보이는 참가자 집계가 수 초 늦게 갱신되는 것은 명확한 “갱신 중” 표시와 재조회 경로가 있으면 허용할 수 있습니다. 그러나 마지막 자리 승인, 활성 참가 중복 방지, 자신의 참가 취소와 주최자 권한처럼 잘못되면 다른 사용자의 상태나 데이터 무결성을 깨뜨리는 판단은 오래된 사본으로 승인해서는 안 됩니다.

| 질문 | 지연 허용 후보 | 즉시 권위 상태가 필요한 후보 |
|---|---|---|
| 공개 목록의 참가자 수 표시 | 짧은 지연·마지막 확인 시각을 명시할 수 있음 | 숫자를 자리 보장으로 사용하지 않음 |
| 참가 신청 승인 | 낙관적 로딩 표시는 가능 | 중복·모집 상태·정원은 트랜잭션에서 판정 |
| 참가자의 자기 취소 | 화면 반영이 잠시 늦을 수 있음 | 현재 주체와 자신의 관계를 서버에서 확인 |
| 주최자 수정 | 목록 캐시 갱신은 늦을 수 있음 | 현재 소유권과 대상 버전을 확인 |

최종적 일관성은 보안·권한·정원 규칙을 느슨하게 해도 된다는 뜻이 아닙니다. 어떤 파생 상태가 얼마 동안 어긋날 수 있는지, 그동안 사용자가 무엇을 볼지, 영구 실패를 어떻게 탐지하고 수렴을 어떻게 증명할지까지 수용 기준으로 작성합니다.

## 장애 때 확인할 증거

| 증상 | 가능한 여러 원인 | 먼저 확인할 원본·증거 | 복구 판단 |
|---|---|---|---|
| 참가 버튼이 실패로 돌아감 | 요청 미도달, 서버 거절, commit 뒤 응답 유실 | 권한 있는 현재 참가 관계, 요청 상관 기록 | 무조건 재시도하지 않고 이미 확정됐는지 확인 |
| 두 화면의 남은 자리 수가 다름 | 캐시 버전, 응답 시각, 동시 참가 | 각 응답 버전·생성 시각과 DB의 현재 상태 | 쓰기는 DB에서 재판정, 사본은 재검증 |
| 큐 길이가 계속 증가함 | 소비자 중단, 영구 오류, 처리량 부족 | 준비·처리 중·재시도·보류 수와 오래된 작업 | 메시지를 삭제하기 전 영향과 재처리 계약 확인 |
| 같은 작업이 여러 번 보임 | 생산자 재시도, 소비자 재전달, 중복 생성 | 안정된 업무 ID, 전달 시도, 처리 결과 | 현재 상태와 기존 부작용을 대조해 멱등 처리 |
| 늦은 이벤트가 최신 값을 덮음 | 병렬 처리, 재전달, 버전 비교 누락 | 메시지 버전과 권위 상태 버전 | 오래된 작업 거절 또는 현재 상태에서 재계산 |
| 재시도 후에도 실패 | 영구 입력 오류, 권한 변경, 외부 장애 | 오류 분류, 시도 횟수, 현재 원본, 외부 결과 | 제한된 재시도 뒤 보류·사람 확인·안전한 종료 |

큐 대시보드의 “0개”나 캐시 hit 비율 하나도 전체 성공을 증명하지 않습니다. 작업이 잘못 폐기됐거나 다른 보류 위치로 이동했을 수 있고, 캐시가 빠르게 오래된 값을 제공할 수도 있습니다. 사용자 영향, 권위 상태, 처리 결과, 안전한 로그와 메트릭을 같은 시간 구간과 버전으로 연결합니다.

## 교육용 주가 fixture는 별도 사례입니다

교육용 주가 대시보드의 `EDU-FIXTURE`는 모임 참가 데이터와 다른 사례입니다. 모든 식별자·날짜·값은 가상이며 실제 시장·상품·현재 시세·투자 조언·데이터 권리의 근거가 아닙니다.

이 fixture에서는 `current_published_dataset_version`이 화면에 제공하기로 선택한 데이터셋 버전이고 표·차트·요약은 그 같은 버전에서 파생됩니다. 갱신 후보가 `blocked`이면 공개 버전을 마지막 정상 버전으로 유지하고 후보 상태와 지연 사유를 별도로 표시합니다. `freshness_status`는 후보 품질이 아니라 기준 시점과 기대 갱신 시각인 `expected_refresh_at`으로 판단합니다. 같은 차단 후보라도 기대 시각 전에는 `current`, 기대 시각 이상인데 승인된 갱신을 제공하지 못했다면 `stale`, 필요한 시각 정보가 없으면 `unknown`입니다. 각 신선도 판단의 이유도 표시하며 마지막 정상 사본이 최신 실제 시장 값이라는 뜻으로 확대하지 않습니다.

이 비교가 알려 주는 공통 원리는 “권위 버전과 파생 화면을 구분하고 신선도·실패를 숨기지 않는다”는 것뿐입니다. 모임 앱의 참가 트랜잭션이나 메시지 큐 설계를 주가 데이터 파이프라인에 그대로 적용하지 않고, fixture 계약을 실제 금융 판단으로 확장하지 않습니다.

## 흔한 오해와 실패

### “캐시는 빠른 데이터베이스입니다”

캐시가 어떤 데이터를 얼마나 오래 보관하고 원본 변경 뒤 어떻게 재검증되는지 없으면 빠른 오래된 사본일 뿐입니다. 사본 손실 때 원본에서 다시 만들 수 있는지도 확인합니다.

### “큐를 넣으면 요청이 안전해집니다”

큐는 작업 수명과 처리 속도를 분리할 수 있지만 업무 완료를 자동 보장하지 않습니다. 발행 전후 부분 실패, 중복, 순서, 소비자 실패, 최종 보류와 원본 재조회 책임이 생깁니다.

### “메시지는 한 번만 처리됩니다”

전달 보장은 제품·구성·생산자·소비자 확인 방식과 외부 부작용의 경계에 따라 달라집니다. 재전달 가능성을 전제로 업무 결과를 판별합니다.

### “이벤트가 왔으니 현재도 그 상태입니다”

이벤트는 과거 사건을 설명할 수 있지만 이후 변경을 포함하지 않을 수 있습니다. 현재 상태에 따른 행동은 권위 원본과 버전을 다시 확인합니다.

### “eventual consistency면 기다리면 됩니다”

영구 오류, 잘못된 순서 처리, 소비자 중단은 기다리기만 해서는 수렴하지 않을 수 있습니다. 허용 지연, 실패 탐지, 재처리, 보류와 사용자 표시를 설계해야 합니다.

## AI와 함께 상태 책임 검토하기

```text
가상 모임 참가 웹앱의 상태 책임을 읽기 전용으로 검토하라.

- events와 registrations의 commit된 관계를 참가·정원 판단의 권위 상태로 둔다.
- 브라우저 상태, 세션, 공개 상세 캐시, 로그, 미래 메시지 큐를 권위 상태와 구분한다.
- 현재 캡스톤에는 큐·별도 캐시를 추가하지 말고, 도입이 필요한 측정 신호와 승인된 요구만 제안한다.
- 신선도 버전·허용 지연·오래됨 표시·원본 재조회 조건을 적는다.
- 중복 발행·재전달, 순서 변화, DB commit과 메시지 발행 사이의 부분 실패를 반례로 만든다.
- 재처리 전 현재 모임·참가 관계와 기존 외부 부작용을 확인하는 순서를 쓴다.
- 교육용 주가 fixture를 모임 앱과 섞거나 실제 시장·투자·실시간 데이터로 표현하지 않는다.
- 특정 캐시·큐 제품의 전달·순서·보존 보장을 공식 문서 확인 없이 일반화하지 않는다.
- 실제 서비스·데이터베이스·큐·알림 성공을 주장하지 않는다.
```

AI가 새 제품이나 패턴을 제안하면 기능 이름보다 실패 경계와 제거 가능성을 봅니다. “보통 Redis”, “Kafka면 해결”, “정확히 한 번” 같은 문구만 있고 권위 원본·중복·순서·재처리·관측 증거가 없으면 결론을 채택하지 않습니다.

- [ ] 사용자 결정별 권위 상태와 저장 위치를 한 문장으로 지정했나요?

- [ ] 마지막 자리·중복·소유권처럼 오래된 사본으로 승인하면 안 되는 규칙을 표시했나요?
- [ ] 큐가 실제 문제를 해결하는지, 단순 동기 흐름보다 필요한지 증거로 판단했나요?
- [ ] 이벤트의 과거 사건과 현재 업무 상태를 구분했나요?
- [ ] 생산자·소비자 실패에서 중복 발행·재전달을 예상했나요?

- [ ] 재시도 가능한 오류와 영구 오류, 횟수·간격·보류 위치·담당자를 정했나요?
- [ ] DB `commit`과 큐 발행 사이의 부분 실패를 탐지·재처리할 경로가 있나요?
- [ ] 재처리 전에 권위 원본과 기존 외부 부작용을 다시 확인하나요?
- [ ] eventual consistency의 허용 지연·수렴 조건·영구 실패·사용자 표시를 적었나요?
- [ ] 선택한 제품과 버전의 캐시·큐 보장을 공식 문서와 실제 실패 시험으로 확인했나요?
- [ ] 실제 서비스·알림·데이터 최신성 성공을 검증 없이 주장하지 않았나요?

## 짧은 연습

미래에 모임 참가 확정 알림을 추가한다고 가정하되, 현재 캡스톤 범위에는 구현하지 마세요.

1. 참가 관계, 화면의 성공 표시, 세션, 캐시된 모임 상세, 큐 메시지와 알림 결과 중 무엇이 어떤 질문의 권위 상태인지 적습니다.
2. 데이터베이스 `commit` 뒤 메시지 발행 전에 프로세스가 종료되는 실패와, 알림 전송 뒤 완료 확인 전에 소비자가 종료되는 실패를 그립니다.
3. 같은 `job_id`가 세 번 전달되고 그 사이 참가가 취소됐을 때 재처리 결과를 씁니다.
4. 늦은 `registration.confirmed` 이벤트의 재조회 전 취소, 재조회 후 전송 전 취소, 버전 비교 후 최신 결과 저장을 나눠 오라클을 만듭니다. 발송 결정 시점의 계약과 외부 전송 취소의 한계를 밝히고 최신 상태를 덮지 않는 조건을 적습니다.
5. 큐 없이 동기 처리할 때와 큐를 넣을 때의 사용자 지연, 중복, 운영·복구 비용을 비교하고 도입 조건을 정합니다.

좋은 답은 제품명을 많이 쓰는 답이 아닙니다. 권위 원본, 사본의 허용 지연, 전달의 불확실성, 중복·순서·부분 실패와 재처리 전 원본 확인이 연결된 답입니다.
