## 먼저 결론

데이터 모델은 현실 업무에서 무엇을 기억하고 어떤 관계와 규칙을 지킬지 정한 표현이고, 스키마(schema)는 그 표현을 데이터베이스의 테이블·열·타입·키·제약으로 구체화한 구조입니다. 마이그레이션(migration)은 이미 저장된 데이터를 보존하면서 스키마와 데이터를 한 상태에서 다음 상태로 옮기는 변경 절차입니다.

세 가지를 구분하면 “화면에 필드를 하나 추가해 주세요”라는 요청도 더 정확한 질문으로 바뀝니다. 그 값은 어떤 업무 개념인가요? 어느 개체에 속하나요? 기존 행에는 어떤 값이 들어가나요? 구버전 코드가 새 구조를 읽어도 괜찮나요? 실패하면 이전 코드로 돌아갈 수 있나요, 아니면 데이터를 보정해 앞으로 가야 하나요? 완료 증거는 파일 존재가 아니라 대상 데이터베이스의 구조, 데이터 불변식, 애플리케이션 호환성과 사용자 흐름을 함께 확인한 결과입니다.

## 왜 필요한가

새 프로젝트의 빈 데이터베이스에서는 테이블을 다시 만들어도 잃을 데이터가 없을 수 있습니다. 하지만 사용자가 이미 모임을 만들고 참가한 서비스에는 과거 상태가 있습니다. 열 이름을 즉시 바꾸거나 필수 열을 빈 값 없이 추가하거나 관계를 삭제하면, 새 코드뿐 아니라 이전 코드·배치 작업·관리 도구·이미 저장된 행이 동시에 영향을 받을 수 있습니다.

코드와 스키마가 같은 순간에 모든 실행 위치에서 바뀐다고 가정하면 위험합니다. 배포가 순차적으로 진행되거나 오래 실행 중인 작업이 남아 있거나 실패 후 이전 애플리케이션 버전으로 되돌릴 수 있기 때문입니다. 데이터 변경은 Git에서 파일을 되돌리는 것만으로 이미 확정된 행을 자동 복원하지도 않습니다. 따라서 구조 변경은 “어떤 명령을 실행할까”보다 **기존 상태, 전환 동안의 호환성, 실패 지점, 검증 오라클, 복구 방향**을 먼저 설계해야 합니다.

## 쉬운 말에서 정식 용어로

모임 참가 웹앱을 예로 들겠습니다. **개체(entity):** 모임, 사용자, 참가 신청처럼 따로 식별하고 기억할 대상입니다. **속성(attribute):** 모임 제목·정원·모집 상태처럼 개체를 설명하는 값입니다. **관계(relationship):** “한 사용자가 한 모임에 참가한다”처럼 개체 사이의 연결입니다.

| 쉬운 질문 | 정식 용어 | 모임 웹앱의 예 | 확인할 규칙 |
|---|---|---|---|
| 무엇을 따로 기억하나요? | 개체 | `events`, `users`, `registrations` | 참가 자체를 단순 버튼 상태가 아니라 별도 관계로 보존하는가? |
| 무엇으로 설명하나요? | 속성 | 제목, 정원, 모집 상태, 참가 시각 | 화면 편의를 위한 문구와 업무 사실을 구분했는가? |
| 무엇과 무엇이 연결되나요? | 관계 | 참가가 사용자와 모임을 연결 | 존재하지 않는 사용자나 모임을 참조하지 않는가? |
| 한 항목을 무엇으로 식별하나요? | 키(key) | `event_id`, `registration_id` | 화면에 보이는 제목처럼 바뀌거나 중복될 값을 식별자로 쓰지 않는가? |
| 어떤 상태를 저장 단계에서 거절하나요? | 제약(constraint) | 필수 값, 참조 무결성, 중복 참가 방지 | 애플리케이션 검증을 우회해도 깨지면 안 되는 규칙인가? |

**기본 키(primary key):** 한 테이블의 각 행을 고유하게 식별하는 키입니다. **외래 키(foreign key):** 다른 테이블의 기본 키 등을 참조해 관계를 표현합니다. 외래 키가 있다고 해서 “이 사용자가 이 모임에 참가할 권한이 있는가”라는 업무 인가까지 자동으로 해결되는 것은 아닙니다. 반대로 애플리케이션에서 존재 여부를 확인했다는 이유만으로 동시 변경 중에도 참조 무결성이 보장되는 것은 아니므로, 저장소 제약과 애플리케이션 규칙의 역할을 나눠야 합니다.

## 비유: 좌석 배치도와 실제 좌석 교체

데이터 모델은 공연장의 “구역·좌석·예매 관계”를 정한 좌석 체계, 스키마는 그 체계를 좌석 번호판과 예매 장부의 칸으로 구체화한 배치도에 비유할 수 있습니다. 마이그레이션은 공연장을 운영하면서 번호판과 장부 형식을 바꾸는 작업에 가깝습니다. 새 번호를 먼저 붙이고, 기존 예매를 새 번호와 연결하고, 연결이 모두 맞는지 확인한 뒤에야 옛 번호를 제거해야 한다는 순서를 이해하는 데 유용합니다.

그러나 이 비유는 여기서 깨집니다. 데이터베이스에는 여러 애플리케이션 인스턴스와 작업이 거의 동시에 읽고 쓸 수 있고, 제약·트랜잭션·격리 수준에 따라 보이는 상태와 충돌 방식이 달라집니다. 복사와 변환은 대량으로 일어나며 일부 행만 실패할 수도 있습니다. 실제 좌석 번호판처럼 사람이 현장에서 한 번에 통제한다고 가정하지 말고, 선택한 데이터베이스와 배포 방식의 공식 동작을 확인해야 합니다.

## 모임 참가 관계를 모델링하기

모임 상세 화면에는 “참가 중”이라는 한 줄만 보일 수 있지만, 데이터 책임은 더 구조적입니다. `events`는 모임 자체, `users`는 사용자, `registrations`는 누가 어느 모임에 참가했는지를 나타내는 관계입니다. 참가 관계를 `events.participant_ids` 같은 자유 형식 목록 하나에 넣으면 사용자별 참가 시각·상태·취소 이력, 중복 방지와 참조 검증이 어려워집니다.

아래 SQL은 PostgreSQL 18 문서의 테이블·제약 개념을 모임 사례에 적용한 **교육용 구조 예시**입니다. 그대로 실행할 범용 운영 스키마가 아니며, 식별자 타입·시간대·삭제 정책·부분 고유성·동시성 처리는 선택한 데이터베이스와 요구사항에 맞춰 다시 설계해야 합니다.

이 장의 `host_user_id`는 기준 사례와 API 장의 `host_id`, `participant_user_id`는 `participant_id`와 같은 역할을 가리킵니다. 뒤의 고유성 설명과 공동 주최자 표도 이 대응을 사용합니다. 사용자를 참조한다는 뜻을 드러낸 예시 이름이며, 실제 데이터베이스 열을 바꾸거나 새 식별자를 추가하라는 지시가 아닙니다.

```sql
CREATE TABLE users (
  user_id text PRIMARY KEY
);

CREATE TABLE events (
  event_id text PRIMARY KEY,
  host_user_id text NOT NULL REFERENCES users(user_id),
  title text NOT NULL,
  capacity integer NOT NULL CHECK (capacity > 0),
  status text NOT NULL CHECK (status IN ('open', 'closed', 'cancelled')),
  starts_at timestamptz NOT NULL
);

CREATE TABLE registrations (
  registration_id text PRIMARY KEY,
  event_id text NOT NULL REFERENCES events(event_id),
  participant_user_id text NOT NULL REFERENCES users(user_id),
  status text NOT NULL CHECK (status IN ('confirmed', 'cancelled')),
  registered_at timestamptz NOT NULL,
  UNIQUE (event_id, participant_user_id)
);
```

이 예시는 구조를 읽는 출발점일 뿐입니다. `UNIQUE (event_id, participant_user_id)`는 한 사용자가 같은 모임에 여러 행을 갖지 못하게 하지만, 취소 뒤 재참가를 새 행으로 보존할 요구가 있다면 맞지 않을 수 있습니다. `capacity > 0`은 정원이 양수임을 검사하지만 동시 참가 요청이 남은 자리보다 많아지지 않게 하는 전체 트랜잭션을 대신하지 않습니다. `status`의 허용값도 업무 상태 전이 전체를 표현하지 않습니다. 제약이 실제 불변식과 맞는지 반례부터 검토해야 합니다.

## 데이터 모델, 스키마, 화면을 같은 것으로 보지 않기

같은 데이터 모델도 관계형 테이블, 문서 구조, 이벤트 기록 등 여러 스키마로 구현할 수 있습니다. 반대로 테이블이 있다는 사실만으로 업무 모델이 명확하다는 뜻은 아닙니다. 화면의 카드와 입력 폼은 사용자에게 보이는 표현이고, 데이터 모델은 화면이 사라져도 지켜야 하는 업무 의미입니다.

| 변경 요청 | 먼저 물을 모델 질문 | 스키마 후보 | 화면만 바꿔서는 안 되는 이유 |
|---|---|---|---|
| 모임 장소를 온라인·오프라인으로 구분 | 장소 유형과 상세 값은 어떤 조합이 유효한가? | 유형 열과 유형별 상세 필드 또는 별도 개체 | 숨긴 입력도 직접 요청으로 보낼 수 있고 기존 행의 의미가 남음 |
| 대기 참가를 지원 | 확정·대기·취소의 상태와 전이, 순서 기준은 무엇인가? | 참가 상태와 대기 순서·시각 | 버튼 문구만으로 정원·승격 규칙을 보존할 수 없음 |
| 주최자를 여러 명 허용 | 공동 주최 관계의 권한과 수명은 무엇인가? | `event_hosts` 관계 테이블 | `host_user_id` 한 열을 복제하면 권한과 중복 규칙이 모호해짐 |

모델 결정을 시작할 때 요구사항의 명사를 곧바로 테이블로 옮기지 않습니다. 사용자 행동과 상태 수명, 식별 기준, 관계의 수, 반드시 지켜야 할 불변식, 삭제·보존·감사 요구를 함께 봅니다. 지나치게 이른 일반화도 피합니다. 첫 모임 웹앱에 필요하지 않은 범용 콘텐츠 관리 구조나 모든 미래 상태를 담는 자유 형식 필드를 넣으면 검증할 규칙이 오히려 사라집니다.

## 마이그레이션은 파일이 아니라 상태 전환입니다

마이그레이션 파일은 변경 의도를 기록하고 반복 가능한 실행 단위를 만드는 데 도움이 됩니다. 하지만 파일이 저장소에 있다는 사실은 대상 데이터베이스에 적용됐거나, 모든 행이 변환됐거나, 새 코드와 구버전 코드가 호환되거나, 실패 복구가 검증됐다는 증거가 아닙니다.

안전한 변경은 흔히 **확장(expand) → 백필(backfill) → 검증(validate) → 전환(switch) → 정리(contract)** 순서로 나눠 생각할 수 있습니다. 이 장의 다섯 단계는 Parallel Change의 확장·이행·정리 구조와 데이터베이스 필드를 새로 만들고 구·신 필드에 함께 쓰고 기존 데이터를 복사한 뒤 새 필드로 읽기를 전환하고 옛 필드를 제거하는 예시를, 마이그레이션 테스트 원칙과 결합해 입문자용으로 세분한 것입니다. 검증 항목과 중지 조건은 모임 사례의 수용 오라클이며 모든 제품에 그대로 적용되는 명령 묶음이나 무중단 보장은 아닙니다.

### 예: `location_text`를 장소 유형과 상세로 나누기

기존 `events.location_text`에는 `온라인`, `회의실 A`, 빈 문자열처럼 서로 다른 의미가 섞여 있다고 가정하겠습니다. 새 요구는 `location_type`을 `online` 또는 `offline`으로 구분하고, 오프라인일 때 상세 장소가 필요하다는 것입니다.

1. **확장:** 기존 열을 지우지 않고 새 열을 nullable 상태로 추가합니다. 구버전·신버전 코드와 배치·관리 도구의 모든 쓰기 경로를 먼저 식별합니다. 백필 전에 호환 코드, 변경을 반영하는 동기화 경로 또는 통제된 쓰기 중지 중 선택한 보호가 유효해야 합니다. 새 열만 기록한 값을 구버전도 읽을 수 있는지 확인하지 못하면 그 쓰기나 구버전 복귀를 허용하지 않습니다.
2. **백필:** 기존 행을 명시한 변환 규칙에 따라 새 열로 채웁니다. 읽은 행의 버전과 쓰기 시점의 버전을 함께 검사하는 조건부 갱신 등으로, 그 사이 들어온 최신 쓰기를 덮지 않게 합니다. 충돌 행은 최신 원본으로 다시 처리하고 해석할 수 없는 값은 추측하지 않고 별도 실패 집합으로 남깁니다.
3. **검증:** 전체 행 수, 값 분포, 미분류 행, 허용되지 않은 조합, 표본과 사용자 흐름을 대조합니다. 원본 열과 변환 결과를 연결하고 백필 이후의 새 쓰기도 대조 범위에 포함합니다. 한 번의 성공 결과 뒤에도 쓰기 보호와 불일치 관찰을 유지합니다.
4. **전환:** 전환 직전까지의 새 쓰기가 새 표현에 반영되고 미해결 충돌·불일치가 없다는 수렴 조건을 통과한 뒤에만 새 열을 읽기 권위로 사용합니다. 그 조건을 전환 순간까지 유지할 수 없으면 중지합니다. 공존하는 쓰기 경로의 보호는 의존이 사라졌다는 증거가 있을 때 해제합니다.
5. **정리:** 구버전 코드와 작업이 더 이상 옛 열을 사용하지 않고 복구 판단이 끝났다는 증거가 있을 때만 필수 제약을 강화하거나 옛 열을 제거합니다.

```sql
ALTER TABLE events ADD COLUMN location_type text;
ALTER TABLE events ADD COLUMN location_detail text;
```

이 두 줄이 성공해도 변경은 끝나지 않습니다. 대형 테이블에서 DDL이 잠금·재작성·성능에 미치는 영향, 한 트랜잭션에서 가능한 범위, 오류 시 동작은 데이터베이스 버전과 명령에 따라 다릅니다. 운영 적용 전에는 선택한 제품의 공식 문서와 운영과 격리된 대표 데이터로 실행 계획·잠금·시간·실패 조건을 확인해야 합니다.

## 백필을 별도 작업으로 다루기

**백필(backfill):** 새 구조나 새 규칙에 맞도록 이미 저장된 행에 값을 채우거나 변환하는 작업입니다. 신규 쓰기 코드가 새 열을 채우는 것과 기존 수백만 행을 바꾸는 것은 부하·실패·재실행 위험이 다릅니다.

백필 계획에는 최소한 다음이 필요합니다.

- 대상 행을 어떤 조건으로 선택하고 몇 건이어야 하는지
- 한 행을 두 번 처리해도 같은 결과가 되는지, 아니라면 중복을 어떻게 탐지하는지
- 배치 크기와 중지 조건, 진행 위치를 어떻게 기록하는지
- 해석할 수 없는 원본 값과 부분 실패를 어디에 격리하는지
- 작업 중 들어오는 새 쓰기와 충돌하거나 빠지는 구간이 없는지
- 완료 뒤 원본과 결과를 어떤 쿼리와 표본으로 대조하는지

예를 들어 백필이 `회의실 A`를 읽은 뒤 사용자가 `회의실 B`로 수정했다면, 늦은 백필은 A로 덮지 않고 충돌로 남겨 B를 기준으로 다시 처리해야 합니다. 검증 뒤 전환 전에 구버전 쓰기가 들어오면 새 표현에 반영됐는지 다시 대조하며, 따라잡지 못했다면 전환하지 않습니다. 새 코드가 옛 표현으로 되돌릴 수 없는 값을 기록했다면 단순히 구버전으로 복귀해서도 안 됩니다. 먼저 쓰기 제한과 정보 보존·변환 가능성을 확인하고, 불가능하면 롤포워드 후보를 검토합니다.

AI에게 “빈 값을 알아서 채워 줘”라고 요청하면 데이터 의미를 발명할 위험이 큽니다. 변환표, 모호한 값 처리, 재실행 계약, 허용 오차와 승인자를 먼저 고정해야 합니다. 사용자가 입력한 실제 장소를 임의의 기본값으로 덮는 것은 기술적 성공이 아니라 데이터 손상일 수 있습니다.

## 호환성은 읽기와 쓰기를 나눠 확인하기

**하위 호환성(backward compatibility):** 새 구조나 새 코드가 기존에 약속한 입력·데이터·사용 방식과 함께 동작할 수 있는 성질입니다. 마이그레이션에서는 최소 네 조합을 봅니다.

| 실행 조합 | 핵심 질문 | 대표 실패 |
|---|---|---|
| 구버전 코드 + 확장된 스키마 | 새 열이 추가돼도 옛 읽기·쓰기가 유지되는가? | 전체 열 순서 가정, 새 필수 제약으로 쓰기 실패 |
| 신버전 코드 + 아직 백필 중인 데이터 | 새 열이 비어 있는 과거 행을 안전하게 읽는가? | null을 예상하지 못해 화면·작업 실패 |
| 구버전과 신버전 코드가 동시에 쓰기 | 두 표현이 불일치하지 않는가? | 한쪽 열만 갱신돼 원본과 파생 값 분기 |
| 신버전 코드 + 정리된 스키마 | 옛 열 의존이 정말 사라졌는가? | 오래 실행된 작업이나 관리 도구가 제거 열을 참조 |

호환성은 “빌드가 된다”만으로 확인할 수 없습니다. 이전 애플리케이션 버전과 다음 스키마, 다음 애플리케이션 버전과 전환 중 데이터라는 교차 조합을 테스트하고, 실제 대상의 스키마 버전과 애플리케이션 버전을 연결해 기록해야 합니다.

## 롤백과 롤포워드를 구분하기

**마이그레이션 롤백(migration rollback):** 스키마·데이터 변경을 이전 상태로 되돌리는 복구 방향입니다. **롤포워드(roll-forward):** 잘못되거나 미완료된 상태를 추가 변경으로 보정해 목표 상태로 전진하는 방향입니다. 트랜잭션 안에서 아직 확정되지 않은 SQL을 취소하는 `ROLLBACK`과, 이미 운영에 확정된 마이그레이션 전체를 되돌리는 절차는 같은 문제가 아닙니다.

추가한 nullable 열처럼 이전 코드가 무시할 수 있고 데이터 손실이 없는 변경은 애플리케이션을 먼저 되돌린 뒤 열을 남겨 관찰할 수 있습니다. 반대로 여러 원본 값을 하나로 합치거나 열을 삭제한 변경은 역변환에 필요한 정보가 없어 단순 롤백이 불가능할 수 있습니다. 이미 신버전 코드가 새 형식으로 쓴 데이터가 있다면 이전 코드가 읽지 못할 수도 있습니다. 이때는 쓰기를 제한하고 영향 범위를 확인한 뒤 보정 마이그레이션으로 앞으로 가는 편이 안전할 수 있지만, 어느 방향이 맞는지는 실제 변경과 복구 증거로 결정해야 합니다.

| 결정 질문 | 롤백 후보가 되려면 | 롤포워드 후보가 되려면 |
|---|---|---|
| 정보가 보존됐는가? | 이전 표현을 손실 없이 다시 만들 수 있음 | 새 표현을 기준으로 오류 행을 식별·보정할 수 있음 |
| 이전 코드가 읽을 수 있는가? | 새로 기록된 데이터까지 이전 코드와 호환됨 | 이전 코드 복귀보다 신버전 수정이 영향이 작음 |
| 쓰기가 계속되는가? | 복귀 동안 두 표현의 분기를 통제함 | 쓰기 제한·재처리로 목표 상태를 수렴시킬 수 있음 |
| 검증된 절차가 있는가? | 격리된 대표 데이터에서 역변환과 사용자 흐름을 시험함 | 보정 작업의 재실행·중지·검증을 시험함 |

백업은 중요한 별도 보호 수단이지만 “백업이 있다”는 문구만으로 복원 가능성이 증명되지는 않습니다. 복원 시험, 복구 시점, 마이그레이션 버전, 애플리케이션 호환성을 함께 확인해야 합니다. 자세한 운영 판단은 [로그·모니터링·백업·복구](../../10-deployment-operations/logs-monitoring-backup/)에서 이어집니다.

## 데이터 검증은 행 수 하나로 끝나지 않습니다

마이그레이션 완료 조건은 실행 종료 코드만이 아니라 데이터 불변식과 사용자 결과로 작성합니다. 변환 전후 행 수가 같아도 값이 잘못 매핑될 수 있고, 전체 합계가 같아도 특정 모임의 참가가 다른 모임으로 연결될 수 있습니다.

| 검증 층 | 모임 웹앱에서 묻는 질문 | 증거 예시 |
|---|---|---|
| 구조 | 열·타입·키·제약·인덱스가 목표 버전과 같은가? | 대상 DB의 스키마 조회 결과와 승인된 마이그레이션 버전 |
| 개수 | 대상·성공·보류·실패 행 수의 합이 맞는가? | 백필 요약과 실패 집합, 전후 조건별 count |
| 값 | 허용값·null·범위·조합 규칙을 지키는가? | `location_type` 분포와 모순 조합 0건 쿼리 |
| 관계 | 모든 참가가 존재하는 모임·사용자를 가리키는가? | orphan 참조 검사와 외래 키 검증 |
| 업무 불변식 | 중복 활성 참가나 정원 초과가 없는가? | 반례 쿼리, 동시 요청 테스트, 제약 위반 테스트 |
| 사용자 흐름 | 과거·신규 모임을 조회·생성·수정할 수 있는가? | 격리 환경의 대표 fixture 기반 흐름 결과 |
| 운영 | 잠금·지연·오류·재시작이 허용 범위였는가? | 시간 구간이 있는 메트릭·로그와 중지·재실행 기록 |

검증 쿼리 자체도 검토 대상입니다. `status = 'confirmed'`만 세야 하는데 취소 행까지 포함하거나 시간대 경계를 잘못 잡으면 그럴듯한 0건이 나올 수 있습니다. 기대값의 근거, 쿼리 버전, 대상 환경, 실행 시각과 결과를 묶고, 고위험 변경은 독립 검토자가 반례를 확인해야 합니다.

## 흔한 오해와 실패

### “ORM이 있으니 스키마를 몰라도 됩니다”

ORM은 객체와 데이터베이스 작업을 연결하는 도구일 수 있지만 업무 개체·관계·제약·동시성·마이그레이션 순서를 대신 결정하지 않습니다. 생성된 마이그레이션도 SQL과 실제 대상 구조를 검토해야 합니다.

### “새 열을 추가했으니 끝났습니다”

구조가 생긴 것과 기존 행이 의미 있는 값으로 채워진 것, 새 코드가 그 값을 사용하는 것, 옛 의존을 제거해도 되는 것은 서로 다른 단계입니다. 각 단계의 수치와 실패 집합을 남깁니다.

### “개발 환경에서 성공했으니 운영에서도 같습니다”

데이터 양·분포·동시 쓰기·권한·데이터베이스 버전과 설정이 다를 수 있습니다. 실제 운영 성공을 주장하지 말고, 대상과 닮은 격리 환경에서 대표 데이터와 실패·중지·재실행을 먼저 검증합니다.

### “되돌리기 SQL만 있으면 안전합니다”

삭제·병합·형 변환으로 정보가 사라졌다면 역방향 명령이 있어도 원래 의미를 복원하지 못할 수 있습니다. 이미 기록된 신형 데이터와 이전 코드의 호환성도 따로 확인합니다.

### “화면이 정상이라 데이터도 정상입니다”

한 화면 표본은 캐시된 값이나 우연히 정상인 행을 보여 줄 수 있습니다. 구조·분포·관계·업무 불변식과 대표 사용자 흐름을 서로 다른 증거로 확인해야 합니다.

## AI와 함께 변경 계획 만들기

AI에게 제품 이름과 “마이그레이션해 줘”만 전달하지 말고 다음 계약을 줍니다.

```text
가상 모임 웹앱의 events.location_text를 location_type과 location_detail로 분리하는 변경 계획을 작성하라.

- 현재 스키마와 목표 스키마, 기존 값 분포는 첨부한 읽기 전용 결과만 사용한다.
- online/offline으로 직접 분류할 수 없는 값은 추측하지 말고 unresolved 집합으로 남긴다.
- 구버전 코드와 신버전 코드가 공존하는 확장·백필·검증·전환·정리 단계를 나눈다.
- 백필 전 모든 쓰기 경로의 보호, 최신 쓰기를 덮지 않는 조건, 전환 직전 수렴 조건과 구버전 복귀 가능성을 명시한다.
- 각 단계의 중지 조건, 재실행 조건, 읽기·쓰기 호환성, 검증 쿼리와 기대 불변식을 적는다.
- 롤백과 롤포워드 가능 조건을 따로 쓰고, 정보 손실이 있는 단계를 표시한다.
- 실제 운영 적용·백업·복원·서비스 성공을 주장하지 않는다.
- 선택한 데이터베이스 버전에서 잠금·트랜잭션·DDL 동작을 공식 문서로 다시 확인해야 할 지점을 표시한다.
```

받은 결과에서는 SQL 문법보다 가정과 상태 전이를 먼저 검토합니다. 대상·실패 집합·재실행 계약이 빠졌거나, 모호한 기존 값을 자동으로 기본값에 매핑하거나, 백업 파일 존재를 복구 완료로 표현하면 보완해야 합니다.

- [ ] 현재 스키마·데이터 분포·사용 중인 코드와 작업을 읽기 전용으로 확인했나요?
- [ ] 확장·백필·검증·전환·정리 단계를 독립적으로 중지하고 확인할 수 있나요?
- [ ] 구버전/신버전 코드와 전환 중 데이터의 읽기·쓰기 조합을 시험했나요?
- [ ] 백필의 대상 수, 성공·보류·실패 수, 재실행·중복 처리 계약이 있나요?
- [ ] 롤백이 정보와 호환성을 실제로 복원하는지, 아니면 롤포워드가 필요한지 구분했나요?
- [ ] 구조·개수·값·관계·업무 불변식·사용자 흐름·운영 신호를 서로 다른 증거로 확인했나요?
- [ ] 대상 데이터베이스 제품과 버전의 DDL·잠금·트랜잭션 동작을 공식 문서에서 확인했나요?
- [ ] 실제 운영 적용, 백업 복원 또는 서비스 성공을 검증 없이 주장하지 않았나요?

## 짧은 연습

가상 모임 웹앱에 `events.starts_at`만 있고 시간대 정보가 불명확한 상태에서 `timezone`을 추가한다고 가정해 보세요.

1. 기존 값의 의미를 판단하기 전에 확인할 데이터와 문서를 적습니다.
2. `timezone`을 즉시 필수로 만들 때 깨질 구버전 코드와 기존 행을 찾습니다.
3. 확장·백필·검증·전환·정리 단계마다 완료 증거와 중지 조건을 한 개 이상 적습니다.
4. 시간대를 추론할 수 없는 행을 임의 변환하지 않는 처리 규칙을 씁니다.
5. 이전 코드로 돌아가는 롤백과 데이터를 보정하는 롤포워드 중 어떤 조건에서 무엇을 선택할지 설명합니다.

정답은 특정 SQL 한 줄이 아닙니다. 모호한 원본을 보존하고, 전환 중 호환성을 지키며, 잘못된 결과를 수치와 반례로 발견하고, 복구 방향을 실제 증거로 선택할 수 있는지가 핵심입니다.
