## 왜 필요한가

개발 서버를 켰는데 터미널이 멈춘 것처럼 보이거나, 새 서버를 시작했더니 "port already in use" 오류가 날 때가 있습니다. 이때 무작정 터미널을 닫거나 검색된 PID를 종료하면 다른 작업의 서버, 테스트, 데이터 처리, 사용자 세션까지 끊을 수 있습니다. 반대로 오래된 프로세스를 그대로 두면 다른 주소의 앱을 보고도 새 변경이 반영됐다고 착각할 수 있습니다.

안전하게 해결하려면 화면인 터미널, 명령을 해석하는 셸, 실행 중인 프로세스, 그 프로세스를 식별하는 PID, 네트워크 연결을 구분하는 포트를 따로 봐야 합니다. "무엇이 실행 중인가"뿐 아니라 "누가 시작했고, 어떤 작업과 데이터를 다루며, 지금 종료해도 되는가"를 확인해야 합니다.

## 한 문장 정의

**터미널은 명령줄 세션을 보여 주는 인터페이스이고, 셸은 입력을 명령과 인자로 해석하며, 프로세스는 실행 중인 프로그램 인스턴스이고, PID는 그 생존 기간의 식별자이며, 포트는 전송 프로토콜 안에서 통신 끝점의 서비스 접근 대상을 구분하는 번호입니다.**

| 개념 | 쉬운 설명 | 확인할 증거 | 혼동하면 안 되는 것 |
|---|---|---|---|
| 터미널(terminal) | 셸의 입력·출력을 보여 주는 앱·창·탭 | 현재 창·탭, 프롬프트, 스크롤백 | 셸 자체, 실행 중인 모든 프로세스 |
| 셸(shell) | 글자를 명령·인자·확장·리디렉션으로 해석하고 프로그램을 실행하는 명령 언어 인터프리터 | 셸 종류·버전, CWD, 설정, 프롬프트 | 터미널 화면, 실행된 애플리케이션 |
| 명령(command) | 셸이나 도구에 수행할 동작과 인자를 표현한 입력 | 입력한 원문, 실행 위치, 해석된 대상 | 그 명령으로 생긴 프로세스나 결과 |
| 프로세스(process) | 운영체제가 관리하는 실행 중 프로그램 인스턴스 | PID, 실행 파일·명령, 소유자, 시작 시각, 상태 | 소스 파일, 터미널 창, 제품 전체 |
| PID(process ID) | 프로세스 생존 기간 동안 식별하는 숫자 | 현재 시점의 프로세스 조회 | 영구 ID, 종료 권한이나 소유권 증거 |
| 포트(port) | TCP·UDP 같은 전송 프로토콜에서 통신 끝점의 서비스 접근 대상을 구분하는 16비트 번호 | 프로토콜, 로컬 주소·포트, 상태, 소켓을 소유한 프로세스의 ID(owning PID) | 통신 세션 전체, 애플리케이션 자체, 안전성·정상 동작 증거 |
| 환경 변수(environment variable) | 프로세스가 이름과 값으로 읽을 수 있는 실행 설정 | 변수 이름·주입 위치·필수 여부 | 코드 상수, 비밀의 안전한 저장소 |
| 종료 코드(exit code) | 명령 프로세스가 끝나며 호출자에게 돌려주는 숫자 상태 | 실제 코드, 오류 출력, 도구 문서 | 사용자 목표·배포·운영 성공 전체 |

## 비유: 상담 창구와 담당자

터미널을 상담 창구 화면, 셸을 요청을 읽고 담당 부서로 전달하는 접수 담당자, 명령을 접수 문장, 프로세스를 실제로 일하는 담당자라고 생각해 보겠습니다. PID는 지금 근무 중인 담당자의 임시 사번이고, 포트는 외부 요청이 찾아오는 내선번호와 비슷합니다. 환경 변수는 담당자가 근무를 시작할 때 전달받은 업무 조건, 종료 코드는 한 업무가 어떤 상태로 끝났는지 접수 창구에 돌려주는 짧은 표지입니다.

이 비유가 맞는 지점은 화면과 해석자와 실제 실행 주체가 다르고, 같은 프로그램도 여러 프로세스로 실행될 수 있으며, 요청이 도달할 번호와 실행 인스턴스를 함께 확인해야 한다는 점입니다.

하지만 비유는 여기서 깨집니다. 프로세스 하나가 여러 포트·파일·자식 프로세스를 다룰 수 있고, 포트 번호 하나만으로 프로토콜·주소·네트워크 범위를 알 수 없습니다. 프로세스가 터미널에서 분리되거나 다른 관리 도구 아래에서 계속 살아 있을 수도 있습니다. PID는 재사용될 수 있으므로 과거 로그의 숫자를 현재 프로세스라고 믿어서도 안 됩니다.

## 명령이 실행되는 흐름

터미널에서 개발 서버 명령을 입력하면 보통 다음 관계가 이어집니다.

1. 터미널이 키 입력과 셸 출력을 표시합니다.
2. 셸이 현재 작업 디렉터리(CWD), 따옴표, 변수, 글롭, 리디렉션과 명령 이름을 해석합니다.
3. 셸 내장 동작을 수행하거나 실행 파일을 찾아 새 프로세스를 만듭니다.
4. 프로세스는 인자와 환경을 읽고 파일·네트워크 같은 자원에 접근합니다.
5. 서버라면 특정 프로토콜·주소·포트에 소켓을 열고 요청을 기다립니다.
6. 짧은 명령은 작업을 마치고 종료 코드를 돌려주며, 장기 실행 서버는 종료 요청이 올 때까지 계속 실행됩니다.
7. 셸은 전경 작업을 기다리거나 배경 작업을 관리한 뒤 다시 프롬프트를 보여 줍니다.

여기서 출력이 계속 이어지고 프롬프트가 돌아오지 않는다고 터미널이 고장 난 것은 아닙니다. 전경에서 서버가 정상적으로 기다리는 중일 수 있습니다. 반대로 프롬프트가 돌아왔다고 서버가 반드시 종료된 것도 아닙니다. 배경 작업, 다른 터미널 세션, 서비스 관리자, IDE나 에이전트가 시작한 프로세스일 수 있으므로 실제 프로세스와 수신 포트를 확인해야 합니다.

## 전경과 배경, 터미널 세션

POSIX 셸 문맥의 **전경 작업(foreground job)**: 셸이 끝나거나 멈출 때까지 기다린 뒤 다음 프롬프트를 내는 작업입니다. **배경 작업(background job)**: 셸이 기다리지 않고 다음 입력을 받을 수 있게 실행한 작업입니다. 대화형 셸의 작업 제어(job control)는 작업 번호와 프로세스 그룹을 관리할 수 있지만, 지원 범위와 명령은 셸·운영체제·설정마다 다릅니다.

다음 상태를 서로 구분해야 합니다.

- 전경 서버가 현재 터미널의 입력을 받고 있음
- 같은 셸이 관리하는 배경 작업이 실행 중임
- 다른 터미널 창·탭에서 프로세스가 실행 중임
- IDE·코딩 에이전트·테스트 도구가 별도 프로세스를 시작함
- 서비스 관리자나 컨테이너가 프로세스를 관리함
- 부모가 끝난 뒤 시스템 프로세스가 부모 역할을 이어받음

마지막 상태를 판정할 때 **부모 프로세스의 ID(PPID)가 1이라는 사실만 보고 버려진 프로세스라고 판단하거나 종료해서는 안 됩니다.** POSIX.1-2024도 부모 프로세스 수명이 끝난 뒤 PPID가 구현이 정한 시스템 프로세스의 ID로 바뀔 수 있다고 정의합니다. 숫자 1은 운영체제와 관리 방식에 따라 의미가 다르며, 서비스 관리·세션·소유자·실행 명령·작업 문맥을 확인하지 않은 종료 근거가 될 수 없습니다.

터미널 창을 닫을 때 프로세스가 함께 끝나는지도 보편 규칙이 아닙니다. 셸, 터미널, 신호 처리, 프로세스가 분리된 방식에 따라 달라집니다. 활성 작업을 보존하려면 창을 닫아 시험하지 말고, 현재 세션과 프로세스 트리를 읽기 전용으로 확인해야 합니다.

## 환경 변수는 프로세스 실행 조건입니다

환경 변수는 `PORT`, `NODE_ENV` 같은 이름과 값으로 프로세스에 전달되는 실행 조건입니다. 셸에서 변수를 만들었다고 모든 프로그램이 자동으로 읽는 것은 아니며, 자식 프로세스에 어떤 값이 전달되는지는 내보내기 방식·셸·운영체제·실행 도구에 따라 다릅니다. 애플리케이션도 그 이름을 읽도록 구현돼 있어야 합니다.

예를 들어 같은 소스라도 한 프로세스는 `PORT=4321`, 다른 프로세스는 `PORT=4322` 조건으로 시작될 수 있습니다. 실제 문법은 POSIX 계열 셸, PowerShell, CI 설정, 호스팅 제품마다 다르므로 예시를 그대로 옮기지 말고 현재 환경의 공식 문서를 확인합니다.

비밀 키를 환경 변수로 주입하더라도 값 자체를 명령 기록, 로그, 스크린샷, 오류 보고서에 출력하지 않습니다. 재현 기록에는 필요한 변수 이름·형식·필수 여부와 주입 출처를 남기고 실제 비밀값은 별도 비밀 관리 경계에 둡니다.

## 포트를 정확히 읽는 법

포트 번호는 단독 주소가 아닙니다. 적어도 다음 정보를 함께 봅니다.

| 확인 항목 | 질문 |
|---|---|
| 전송 프로토콜 | TCP인가요, UDP인가요? |
| 로컬 주소 | 루프백 주소에만 묶였나요, 여러 네트워크 인터페이스에 노출됐나요? |
| 로컬 포트 | 어떤 번호에서 수신 중인가요? |
| 연결 상태 | 요청을 기다리는 listener인가요, 이미 연결된 세션인가요? |
| owning PID | 현재 이 소켓을 소유한 프로세스는 무엇인가요? |
| 프로세스 정체 | 실행 명령·경로·사용자·시작 시각·부모와 자식은 무엇인가요? |

IANA의 공식 레지스트리는 서비스 이름과 포트 번호가 TCP·UDP·SCTP·DCCP 같은 전송 프로토콜의 서로 다른 서비스를 구분하는 데 쓰인다고 설명합니다. 통신 세션 전체를 구분하려면 포트 하나만이 아니라 프로토콜과 양쪽 주소·포트 같은 추가 정보가 필요합니다. 등록된 번호에서 트래픽이 보인다는 사실도 그 애플리케이션이 맞다거나 안전한 트래픽이라는 증거가 아닙니다. 로컬 개발 포트는 번호만 보고 프로세스의 정체·소유권·정상 동작을 판단하지 않습니다.

## 포트 충돌을 안전하게 진단하는 순서

### 1. 오류와 의도를 보존합니다

실행한 명령, CWD, 전체 오류, 요청한 프로토콜·주소·포트, 기대한 URL을 기록합니다. "이미 사용 중"과 "접근 권한 없음"과 "주소 형식 오류"는 다른 문제입니다.

### 2. 기존 서버가 의도한 서버인지 먼저 확인합니다

같은 작업에서 이미 정상 서버를 띄워 둔 것이라면 새 프로세스를 만들 필요가 없을 수 있습니다. 현재 URL의 화면·응답, 시작 로그, worktree·commit·빌드 시점을 확인합니다. 브라우저 탭 하나가 열린 사실만으로 어떤 프로세스의 응답인지 확정하지 않습니다.

### 3. 수신 소켓과 owning PID를 읽기 전용으로 찾습니다

macOS·Linux 계열에서는 설치된 `lsof`, `ss`, `netstat`나 운영체제 도구가 서로 다른 형식과 옵션을 사용합니다. Windows PowerShell의 `Get-NetTCPConnection`은 로컬 포트와 `OwningProcess` 같은 속성으로 TCP 연결을 조회할 수 있습니다. 이 장은 하나의 명령을 보편 해법으로 고정하지 않습니다. 현재 운영체제와 도구 버전의 도움말을 확인하고, TCP/UDP·주소·상태·PID가 함께 보이는 읽기 전용 조회를 선택합니다.

Windows PowerShell의 예시는 다음처럼 조회 단계만 나눌 수 있습니다.

```powershell
Get-NetTCPConnection -LocalPort 4321
Get-Process -Id <조회된-PID>
```

첫 명령의 결과에서 로컬 주소와 `State`를 확인하고, 진단할 수신 대기 소켓(listener)의 `Listen` 행에 있는 `OwningProcess`를 선택한 뒤 두 번째 명령으로 세부 정보를 조회합니다. 연결 행이 여러 개라면 첫 PID를 무조건 선택하지 않습니다. `<조회된-PID>`는 설명용 자리표시자이므로 그대로 실행하지 않습니다. macOS·Linux에서도 먼저 현재 포트의 listener와 PID를 조회하고, 그 PID의 세부 정보를 별도 명령으로 확인하는 두 단계를 유지합니다. 이 조회는 종료 승인이 아닙니다.

### 4. PID의 정체와 소유권을 확인합니다

다음 질문에 답하기 전에는 종료하지 않습니다.

- PID가 여전히 같은 프로세스를 가리키나요? 조회 직후 다시 확인했나요?
- 프로세스 이름만 아니라 전체 실행 명령과 실행 파일 경로가 맞나요?
- 어떤 사용자와 도구가 시작했나요?
- CWD, worktree, commit 또는 프로젝트 경계를 확인할 수 있나요?
- 시작 시각과 부모·자식 프로세스 트리는 무엇인가요?
- 활성 브라우저·테스트·데이터 처리·편집 세션이 의존하나요?
- 로그나 메모리에 아직 보존되지 않은 결과가 있나요?

PID는 생존 기간에만 고유하고 재사용될 수 있습니다. 오래된 로그의 PID, 프로세스 이름 한 개, 포트 번호, `PPID=1` 중 어느 하나도 종료 권한의 충분한 증거가 아닙니다.

### 5. 종료 대신 재사용·다른 포트를 먼저 비교합니다

기존 프로세스가 필요한 작업이면 그대로 재사용하거나 새 서버에 충돌하지 않는 포트를 지정하는 편이 안전할 수 있습니다. 다만 다른 포트 사용이 URL·CORS·테스트·콜백·문서화된 계약을 바꿀 수 있으므로 임시 번호를 조용히 바꾸지 않습니다.

### 6. 소유 세션에서 정상 종료를 먼저 요청합니다

현재 작업이 시작한 전경 프로세스이고 보존할 상태가 없음을 확인했다면, 그 프로세스를 실행한 터미널에서 애플리케이션이 지원하는 종료 방법을 사용합니다. Apple의 macOS Terminal 공식 안내에서는 `Control-C`가 신호를 보내 대부분의 현재 명령을 종료한다고 설명하지만, 모든 프로그램의 정상 종료를 보장하지는 않습니다. 애플리케이션의 자체 shutdown 명령과 저장 절차가 있으면 그것을 우선합니다.

별도 PID를 대상으로 조치할 때도 먼저 애플리케이션이나 관리 서비스가 제공하는 정상 종료 절차를 확인하고 기다립니다. 운영체제 수준에서 프로세스를 종료하는 것은 이 절차와 별개입니다. POSIX 계열에서는 프로세스나 프로세스 그룹에 신호를 보내는 방식이 쓰이고, Windows PowerShell의 `Stop-Process`는 이름·PID·프로세스 객체로 로컬 프로세스를 멈춥니다. `Stop-Process`를 애플리케이션의 저장·정리 절차를 거치는 정상 종료 요청으로 간주하지 마세요. 확인 프롬프트나 `-Force` 사용 여부도 정상 저장을 보장하지 않습니다. 정상 종료 방법과 보존할 상태를 먼저 확인하고, 운영체제 수준의 종료가 필요하면 정확한 대상·영향·복구 방법과 권한을 확인한 뒤 진행합니다. 명령 구문·신호·확인·권한·자식 프로세스 영향은 운영체제와 도구마다 다릅니다.

정상 종료 단계를 건너뛰는 강제 종료(`SIGKILL` 같은 수단)는 정리·저장·연결 종료 기회를 없애거나 의존 프로세스·서비스에 영향을 줄 수 있으므로 마지막 수단입니다. 정확한 대상, 영향, 복구 방법, 권한을 다시 확인하고 정상 종료가 실패했다는 증거가 있을 때만 별도 승인을 받아 사용합니다.

### 7. 종료 결과와 새 서버를 따로 검증합니다

종료 명령이 출력 없이 끝났다고 완료가 아닙니다. 원래 PID가 종료됐는지, 자식 프로세스가 남지 않았는지, 포트가 더 이상 수신 중이 아닌지 다시 조회합니다. 그다음 새 서버를 시작해 새 PID·주소·포트·로그·종료 코드를 기록하고, 기대 URL과 사용자 흐름을 확인합니다.

## 종료 코드와 출력은 서로 다른 증거입니다

POSIX 셸에서는 명령마다 exit status가 뒤 명령의 제어 흐름에 영향을 줄 수 있습니다. 일반적으로 0은 그 명령이 정의한 성공, 0이 아닌 값은 다른 결과나 오류를 뜻하지만 정확한 의미는 명령 문서를 읽어야 합니다. 셸이 명령을 찾지 못했을 때와 찾았지만 실행할 수 없을 때처럼 특정 값에 의미가 있는 경우도 있고, 신호로 종료됐을 때의 표현에는 구현 차이가 있습니다.

따라서 다음을 함께 확인합니다.

- 실행한 정확한 명령과 CWD
- 표준 출력과 오류 출력
- 종료 코드
- 실제 실행된 테스트·검사 수
- 생성되거나 바뀐 파일·프로세스·포트
- 사용자가 관찰해야 하는 결과

종료 코드 0은 명령 자체의 성공 범위만 말합니다. 예를 들어 개발 서버 시작 명령이 실행 중이면 아직 종료 코드가 없을 수 있고, 빌드 성공은 공개 URL·운영 데이터·사용자 흐름 성공을 자동으로 증명하지 않습니다.

## 두 사례에서 판단이 달라지는 지점

재현용으로 고정한 교육용 가상 데이터(fixture)를 쓰는 주가 대시보드의 로컬 정적 미리보기라면 상태를 쓰지 않는 서버를 종료하는 대신 다른 비충돌 포트로 새 미리보기를 띄우고 정확한 URL을 기록하는 선택이 비교적 쉬울 수 있습니다. 그래도 빌드 입력·fixture 버전·브라우저 탭이 어느 서버를 보는지는 확인해야 합니다.

모임 참가 웹앱의 서버는 로그인 세션, 참가 요청, 데이터베이스 연결과 진행 중인 상태 변경을 다룰 수 있습니다. 같은 포트를 점유한다는 이유만으로 종료하면 요청 중단·부분 처리·세션 손실이 생길 수 있으므로, 소유자·활성 요청·저장 상태·정상 shutdown·재시작과 데이터 재확인 절차가 더 중요합니다. 이 차이는 특정 제품의 동작을 가정한 것이 아니라 **프로세스가 보존해야 하는 상태와 사용자 영향**에 따라 종료 기준이 달라진다는 판단 예입니다.

## 흔한 오해와 실패, 복구

|---|---|---|
| "터미널 창을 닫았으니 서버도 끝났다" | 분리·배경·다른 관리자 아래에서 계속 실행될 수 있다 | 실제 PID·프로세스 트리·수신 포트를 다시 조회한다 |
| "프롬프트가 안 나오니 멈췄다" | 전경 서버가 정상적으로 요청을 기다리는 중일 수 있다 | 시작 로그·수신 주소·별도 브라우저 요청으로 상태를 확인한다 |
| "포트 번호가 같으니 내 서버다" | 프로토콜·주소·프로세스·worktree가 다를 수 있다 | listener와 owning PID, 명령·CWD·시작 시각을 연결한다 |

| "강제 종료가 가장 확실하다" | 정리·저장 기회를 없애고 자식·의존 서비스에 영향을 줄 수 있다 | 소유 세션의 정상 종료와 유예 시간을 먼저 사용한다 |
| "종료 명령이 조용히 끝났으니 성공했다" | 기본 출력이 없거나 비동기 종료일 수 있다 | PID·포트·자식 프로세스·애플리케이션 상태를 재조회한다 |

| "종료 코드 0이면 사용자가 원하는 결과도 성공했다" | 명령이 정의한 좁은 성공일 뿐이다 | 파일·화면·데이터·네트워크 등 수용 증거를 별도로 확인한다 |

## AI에게 요청하고 검토하는 프롬프트

```text
현재 포트 충돌을 먼저 읽기 전용으로 진단해 주세요.

- 운영체제, 셸, CWD, 저장소·worktree 경계와 실행하려던 정확한 명령을 확인하세요.
- 오류의 프로토콜·주소·포트와 기대 URL을 기록하세요.
- 현재 listener와 owning PID를 읽기 전용으로 조회하세요.
- PID마다 전체 실행 명령, 실행 경로, 소유자, 시작 시각, 부모·자식 트리, 가능한 CWD와 관련 세션을 확인하세요.
- PID·프로세스 이름·포트·PPID=1 중 하나만으로 종료 대상을 결정하지 마세요.
- 활성 브라우저, 테스트, 데이터 처리, 다른 사용자·에이전트 세션과 저장되지 않은 결과를 보존하세요.
- 재사용, 다른 승인된 포트, 소유 세션의 정상 종료를 비교하세요.
- 아직 프로세스를 종료하거나 강제 신호를 보내지 말고 정확한 대상·영향·복구 방법과 필요한 승인을 보고하세요.
- 승인 뒤에는 정상 종료를 먼저 사용하고, 원래 PID·자식·포트 해제와 새 서버 PID·주소·로그·사용자 흐름을 각각 검증하세요.
- 환경 변수 값과 비밀정보는 출력하지 마세요.
```

AI가 "오래된 프로세스를 정리하겠습니다"라고만 말하면 근거가 부족합니다. 어떤 조회가 어떤 PID를 반환했고, 현재 작업이 소유한 프로세스라는 증거가 무엇이며, 종료 시 영향을 받는 세션과 복구 방법이 무엇인지 요구해야 합니다.

## 판단 규칙

1. 터미널·셸·명령·프로세스를 같은 것으로 부르지 않습니다.
2. 프롬프트와 창 상태만으로 프로세스 생존을 판단하지 않습니다.
3. PID는 현재 생존 기간의 식별자이지 소유권·종료 허가가 아닙니다.
4. 포트는 프로토콜·주소·상태·owning PID와 함께 봅니다.
5. 프로세스 이름·포트·PID·`PPID=1` 하나만으로 종료하지 않습니다.
6. 활성 세션·자식 프로세스·저장되지 않은 결과를 먼저 보존합니다.
7. 재사용·비충돌 포트·정상 종료를 강제 종료보다 먼저 검토합니다.
8. 정상 종료 뒤에도 PID·자식·포트 해제를 다시 확인합니다.
9. 환경 변수는 실행 조건이며 실제 비밀값을 로그와 보고서에 남기지 않습니다.
10. 종료 코드·출력·파일·네트워크·사용자 결과를 서로 다른 증거로 봅니다.
11. 운영체제·셸·도구별 명령과 신호 동작을 보편 규칙으로 일반화하지 않습니다.

위 확인일과 버전은 당시 기록입니다. 2026-11-15에는 POSIX·포트·Windows 도구의 관련 설명과 Apple 명령 실행·종료 본문을 다시 확인했습니다. Apple의 과거 짧은 주소가 현재 목차를 반환하므로 위 링크는 실제 명령 본문으로 연결했습니다. 현재 IANA 갱신일과 Microsoft 문서 전체의 접근 가능 여부는 확인하지 못했으며, 반환된 관련 절의 범위만 근거로 삼습니다. 과거 주소·버전과 이번 확인의 상세 범위는 출처 지도에 별도로 보존합니다.
