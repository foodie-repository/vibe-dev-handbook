## 먼저 결론

파일을 제대로 찾으려면 이름만 보지 말고 **어느 경계를 기준으로 한 경로인지**, **그 파일이 원본인지 생성물인지**, **현재 도구가 그 파일을 어떤 상태로 보는지**를 함께 확인해야 합니다. `docs/guide.md`와 `src/content/docs/guide.md`는 이름이 비슷해도 다른 파일이고, 같은 `src/content/docs/guide.md`도 현재 작업 디렉터리가 달라지면 상대 경로가 다른 곳을 가리키거나 아예 실패할 수 있습니다.

AI가 “문서를 수정했습니다”라고 말했을 때도 다음 세 질문부터 확인하세요.

1. 어느 저장소의 어떤 경로를 수정했나요?
2. 사람이 관리하는 원본을 수정했나요, 다시 생성될 결과물을 수정했나요?
3. `git status`, 실제 변경 전후 차이(diff), 빌드된 페이지 중 무엇으로 변경을 확인했나요?

이 세 질문에 답할 수 있으면 “파일이 어디 있지?”라는 문제를 넘어 “어느 파일을 고쳐야 결과가 지속되는가?”를 판단할 수 있습니다.

## 왜 필요한가

비개발자는 Finder나 편집기에서 보이는 폴더를 프로젝트 전체라고 생각하기 쉽습니다. 그러나 개발 도구는 현재 터미널 위치, Git 저장소 경계, 설정 파일의 기준 위치, 빌드 입력 폴더처럼 서로 다른 기준으로 경로를 해석합니다. 파일 이름이 맞아도 기준이 다르면 명령은 엉뚱한 파일을 읽거나 `파일을 찾을 수 없음`으로 끝납니다.

이 핸드북 저장소가 좋은 예입니다. 루트의 `docs/`에는 편집 정책과 검토 기록 같은 **내부 프로젝트 문서**가 있고, `src/content/docs/`에는 웹사이트에 공개되는 **학습 원고**가 있습니다. `docs/`만 열어 보고 “학습 문서가 부족하다”고 판단하면 잘못된 경계를 본 것입니다. 반대로 공개 원고를 만들면서 `docs/project/`에 넣으면 파일은 존재해도 사이트에는 나타나지 않습니다.

빌드 결과를 직접 고치는 문제도 자주 생깁니다. 예를 들어 `dist/`의 HTML을 수정하면 당장은 브라우저에서 바뀐 것처럼 보일 수 있지만, 다음 빌드가 원본 Markdown으로 `dist/`를 다시 만들면 수정이 사라집니다. 파일을 찾았다는 것과 **지속적으로 수정해야 할 원본을 찾았다는 것**은 다른 판단입니다.

경로 이해는 단순한 컴퓨터 사용법이 아닙니다. 변경 범위, 재현 가능성, Git 검토, 자동화, 배포, 비밀정보 보호를 연결하는 개발의 기본 안전장치입니다.

## 파일·폴더·경로는 무엇인가요

- **파일(file)**: 이름을 가진 데이터 단위입니다. Markdown 원고, 이미지, 설정, 프로그램 코드, 로그와 데이터셋이 모두 파일일 수 있습니다.
- **디렉터리(directory)**: 파일과 다른 디렉터리의 이름을 묶어 계층을 만드는 공간입니다. 그래픽 화면에서는 보통 폴더(folder)라고 부릅니다. 이 장에서는 둘을 같은 대상으로 다루되, 터미널과 공식 문서에서 `directory`라는 표현이 더 자주 보인다는 점을 기억합니다.
- **경로(path)**: 파일이나 디렉터리의 위치를 이름의 순서로 표현한 값입니다. 예를 들어 `src/content/docs/index.md`는 `src` 안의 `content`, 그 안의 `docs`에 있는 `index.md`를 가리킵니다.

파일 확장자도 이름의 일부입니다. `guide.md`, `guide.html`, `guide.pdf`는 같은 제목처럼 보여도 서로 다른 파일이며 역할도 다를 수 있습니다. 파일 탐색 도구의 설정에 따라 확장자나 점으로 시작하는 이름이 화면에서 숨겨질 수 있으므로, 개발 작업에서는 표시 설정이나 터미널 목록으로 전체 파일명과 상위 경로를 함께 확인합니다.

경로는 위치를 가리키지만 파일의 의미까지 말해 주지는 않습니다. `report.csv`라는 이름만으로 원본 데이터인지 임시 내보내기인지, 개인정보가 있는지, Git이 관리하는지 알 수 없습니다. 위치와 책임은 폴더 규칙·설정·Git 상태·생성 명령을 함께 읽어야 판단할 수 있습니다.

## 건물 주소에 비유하기

파일 시스템을 건물로 생각해 보겠습니다. 디렉터리는 건물과 층과 방, 파일은 방 안의 문서, 경로는 그 문서를 찾아가는 주소입니다.

- **절대 경로**는 도시와 건물부터 적은 전체 주소와 비슷합니다.
- **상대 경로**는 “지금 방에서 복도로 나가 옆방으로 가세요”라는 안내와 비슷합니다.
- **현재 작업 디렉터리**는 안내를 시작하는 현재 위치입니다.
- **프로젝트 루트**는 한 프로젝트의 안내 데스크, **저장소 루트**는 Git이 변경 이력을 관리하는 구역의 입구와 비슷합니다.

이 비유가 맞는 지점은 상대 안내가 시작 위치에 따라 달라지고, 같은 이름의 방이 여러 층에 있을 수 있으며, 먼저 경계를 확인해야 한다는 점입니다.

### 비유가 깨지는 지점

컴퓨터의 경로는 물리적 주소보다 조건이 많습니다. 심볼릭 링크처럼 서로 다른 경로가 같은 대상을 가리킬 수 있고, 파일이 존재해도 권한 때문에 읽지 못할 수 있습니다. 파일 시스템과 운영체제 설정에 따라 대소문자를 같은 이름으로 보거나 다른 이름으로 볼 수 있으며, 프로그램 설정의 상대 경로는 터미널의 현재 위치가 아니라 설정 파일이나 프로젝트 루트를 기준으로 해석될 수도 있습니다.

주소만으로 그 방이 원본 보관실인지 폐기 예정 사본인지 알 수 없듯이, 경로만으로 원본·생성물·캐시·비밀정보를 구분할 수도 없습니다. 따라서 비유는 **위치를 찾는 관계**까지만 설명하고, 책임·권한·Git 상태·생성 규칙은 별도로 확인해야 합니다.

## 경계를 이루는 여섯 가지 위치

개발 로그에서 “루트”, “작업 공간”, “프로젝트”라는 말은 자주 섞입니다. 다음 위치가 실제로 같은 경로일 수도 있지만, 이름만 보고 같다고 가정하면 안 됩니다.

| 용어 | 뜻 | 확인할 질문 |
|---|---|---|
| **파일 시스템 루트(root directory)** | 파일 시스템 경로 계층의 시작점입니다. macOS와 Linux 계열 예시에서는 `/`로 표현합니다. | 프로젝트 루트와 `/`를 혼동하고 있지 않나요? |
| **홈 디렉터리(home directory)** | 현재 사용자에게 배정된 기본 디렉터리입니다. 셸에서 흔히 `~`로 줄여 쓰지만 `~`는 사용하는 셸이나 도구가 먼저 확장하는 표현입니다. | 설정이 개인 홈의 파일에 몰래 의존하지 않나요? |
| **현재 작업 디렉터리(current working directory, CWD)** | 실행 중인 셸이나 프로세스가 상대 경로를 해석할 때 사용하는 현재 위치입니다. | 이 명령을 정확히 어느 디렉터리에서 실행했나요? |
| **프로젝트 루트(project root)** | 해당 프로젝트의 설정·명령·소스 구조를 해석하는 기준 디렉터리입니다. | 어떤 설정 또는 명령이 이 위치를 프로젝트 루트로 정하나요? |
| **저장소 루트(repository root)** | Git이 현재 작업 트리의 최상위로 인식하는 디렉터리입니다. | `git rev-parse --show-toplevel` 결과와 일치하나요? |
| **작업 공간(workspace)** | 편집기나 코딩 에이전트가 이번 작업에서 열고 접근하도록 정한 범위입니다. 하나의 저장소, 여러 저장소 또는 저장소 일부일 수 있습니다. | 이 도구가 실제로 읽고 쓸 수 있는 경로는 어디까지인가요? |

작은 저장소에서는 CWD·프로젝트 루트·저장소 루트·작업 공간이 모두 같은 디렉터리일 수 있습니다. 그러나 여러 패키지를 한 저장소에서 관리하거나, 상위 작업 공간에 여러 저장소를 열거나, 하위 디렉터리에서 명령을 실행하면 서로 달라집니다. “보통 같다”는 경험을 현재 프로젝트의 증거로 사용하지 마세요.

## 절대 경로와 상대 경로

다음 예시는 macOS와 Linux 계열 셸의 표기입니다. Windows는 `C:\Users\name\project`처럼 드라이브 문자와 역슬래시를 사용하는 경로가 흔하며, 사용하는 셸·프로그램·파일 시스템에 따라 세부 규칙이 다릅니다.

### 절대 경로

절대 경로(absolute path)는 파일 시스템의 시작점에서 대상까지 전체 위치를 적습니다.

```text
/projects/vibe-dev-handbook/src/content/docs/index.md
```

현재 작업 디렉터리가 달라도 같은 컴퓨터와 파일 시스템에서는 같은 위치를 가리키기 쉽다는 장점이 있습니다. 반면 사용자 이름과 설치 위치가 다른 컴퓨터에서는 그대로 재사용할 수 없습니다. 프로젝트 설정이나 공개 문서에 개인 컴퓨터의 절대 경로를 저장하면 다른 개발자와 CI에서 실패할 수 있습니다.

### 상대 경로

상대 경로(relative path)는 정해진 기준 위치에서 대상까지의 이동을 적습니다. CWD가 `/projects/vibe-dev-handbook`일 때 다음 경로는 같은 대상을 가리킵니다.

| 표현 | 해석 결과 | 의미 |
|---|---|---|
| `src/content/docs/index.md` | `/projects/vibe-dev-handbook/src/content/docs/index.md` | CWD 아래에서 바로 내려감 |
| `./src/content/docs/index.md` | `/projects/vibe-dev-handbook/src/content/docs/index.md` | `.`은 현재 디렉터리 |
| `../vibe-dev-handbook/src/content/docs/index.md` | `/projects/vibe-dev-handbook/src/content/docs/index.md` | `..`로 부모에 갔다가 다시 내려옴 |

같은 `src/content/docs/index.md`를 `/projects`에서 해석하면 `/projects/src/content/docs/index.md`를 찾게 됩니다. 그 파일이 없으면 실패하고, 우연히 존재하면 더 위험하게도 엉뚱한 파일을 읽을 수 있습니다.

`~`는 흔히 홈 디렉터리로 확장되지만 모든 파일 API와 설정 형식이 이를 셸처럼 처리하는 것은 아닙니다. 환경 변수, `.`과 `..`, 따옴표, 공백도 셸과 프로그램에 따라 해석 단계가 다릅니다. 경로가 로그에 보인다고 추측으로 이어 붙이지 말고, 해당 명령이나 설정이 기준으로 삼는 위치를 확인하세요.

### Windows에서는 접두사를 함께 봅니다

Windows 경로는 역슬래시를 쓴다는 사실만 외우면 부족합니다. Win32 파일 API의 해석에서는 시작 부분이 기준 위치와 네임스페이스를 결정하므로, 드라이브 문자 뒤의 역슬래시 하나만 빠져도 다른 경로가 됩니다.

| 표현 | Win32 파일 API에서의 기준 | 주의할 점 |
|---|---|---|
| `C:\projects\guide.md` | `C:` 드라이브의 루트부터 시작 | 드라이브까지 지정한 절대 경로 |
| `\\server\share\guide.md` | 네트워크의 서버·공유 위치를 나타내는 UNC(Universal Naming Convention) 경로 | 로컬 드라이브 경로가 아님 |
| `C:projects\guide.md` | `C:` 드라이브에 대해 기억된 현재 디렉터리부터 시작 | `C:\projects\guide.md`와 같다고 보면 안 됨 |
| `\projects\guide.md` | 현재 드라이브의 루트부터 시작 | 절대 경로이지만 드라이브까지 지정한 완전한 경로는 아님 |

파일명의 대소문자도 “Windows는 무조건 구분하지 않고 Linux는 무조건 구분한다”로 암기하지 마세요. Windows의 일반적인 동작은 대소문자를 구분하지 않는 쪽이지만 NTFS 디렉터리는 설정에 따라 구분할 수 있고, WSL에서 어느 파일 시스템을 다루는지에 따라서도 달라집니다. macOS·Linux에서도 파일 시스템과 마운트 설정, 사용하는 도구의 규칙을 함께 확인해야 합니다. 이식 가능한 프로젝트에서는 대소문자만 다른 파일명을 만들지 않고, 참조하는 이름의 철자를 실제 파일과 정확히 맞추는 편이 안전합니다.

### 언제 무엇을 쓰나요

- 저장소 안에서 공유하는 설정·문서·작업 지시는 재현 가능한 **저장소 또는 프로젝트 기준 상대 경로**를 우선합니다.
- 현재 컴퓨터에서 오류 대상을 정확히 식별하거나 클릭 가능한 로컬 파일을 전달할 때는 **절대 경로**가 유용합니다. 공개 문서와 커밋에는 개인 사용자명과 민감한 폴더 구조가 남지 않는지 확인합니다.
- 명령을 전달할 때는 경로만 적지 말고 **실행 위치**를 함께 적습니다.
- 설정 파일의 상대 경로는 CWD 기준이라고 단정하지 말고 해당 도구의 문서와 기존 설정 패턴을 확인합니다.

## 같은 프로젝트를 여섯 관점으로 보기

하나의 파일도 도구마다 서로 다른 질문으로 봅니다. 한 관점의 증거를 다른 관점의 성공으로 확대하지 않는 것이 중요합니다.

| 관점 | 주로 보여 주는 것 | 보여 주지 않는 것 |
|---|---|---|
| Finder·파일 탐색기 | 화면에 표시된 디스크의 폴더와 파일, 이름, 크기, 수정 시각 | 설정에 따라 숨겨진 이름·확장자, Git 이력, 빌드 입력 여부, 웹 공개 여부 |
| 터미널·프로세스 | CWD를 기준으로 명령이 읽고 쓰는 경로와 실행 결과 | 사용자가 의도한 프로젝트인지, 원본인지 |
| Git | 저장소 경계 안에서 tracked·untracked·ignored와 커밋 차이 | 저장소 밖 파일, 제품 동작, ignore된 비밀의 안전성 |
| 편집기·코딩 에이전트 | 열린 작업 공간과 허용된 읽기·쓰기 범위 | 디스크 전체, 승인되지 않은 외부 상태, 자동으로 최신인 원격 상태 |
| 빌드 도구 | 설정에 따른 입력, 변환, 생성 아티팩트 | 실제 배포·공개 URL 성공, 생성물의 의미 정확성 |
| 웹 브라우저 | URL로 요청한 공개 자원과 렌더링 결과 | 서버나 저장소의 실제 파일 경로, 커밋되지 않은 로컬 변경 |

예를 들어 저장소 파일 `src/content/docs/02-work-environment/files-folders-paths.md`는 빌드 뒤 `/02-work-environment/files-folders-paths/` 같은 웹 경로의 HTML 페이지가 됩니다. 배포 환경에 `base` 경로가 설정되면 이 경로 앞에 프로젝트 접두사가 붙을 수 있습니다. 웹 경로에는 `src/content/docs`와 `.md`가 보이지 않습니다. URL 경로와 파일 시스템 경로는 닮아 보여도 서로 다른 주소 체계이며, 둘의 연결은 프레임워크 설정과 빌드 규칙이 만듭니다.

## 이 핸드북 저장소를 실제로 읽어 보기

이 저장소의 핵심 구조를 학습 목적에 맞게 줄이면 다음과 같습니다.

```text
vibe-dev-handbook/                 ← 프로젝트 루트이자 Git 저장소 루트
├── .gitignore                     ← Git이 기본 상태에서 제외할 로컬 파일 규칙
├── AGENTS.md                      ← 에이전트 작업 규칙
├── PROJECT_CONTEXT.md             ← 프로젝트 목적·결정·현재 상태
├── WORKSPACE_MAP.md               ← 폴더별 책임
├── package.json                   ← 실행 명령·패키지·Node 요구사항
├── astro.config.mjs               ← 사이트와 배포 base 등 Astro 설정
├── docs/
│   └── project/                   ← 편집 정책·검토 기록, 공개 학습 본문 아님
├── research/                      ← 출처와 조사 메모
├── src/
│   ├── content.config.ts          ← 공개 콘텐츠의 로더와 메타데이터 규칙
│   ├── content/docs/              ← 웹사이트에 공개할 학습 원고의 원본
│   └── assets/diagrams/           ← 게시용 SVG와 Mermaid 원본
├── scripts/                       ← 콘텐츠·빌드 검증 자동화
├── tests/                         ← 자동화의 회귀 테스트
├── CONTENT_MAP.md                 ← 공개 원고 상태·문자 수를 명령으로 동기화
├── dist/                          ← 빌드가 다시 만드는 정적 사이트 아티팩트
└── node_modules/                  ← 설치한 외부 패키지 사본
```

`src/content/docs/`와 `docs/`는 모두 Markdown을 포함할 수 있지만 책임이 다릅니다. 공개 장을 고칠 때는 전자를, 편집 정책과 내부 검토 기록을 고칠 때는 후자를 선택합니다. `dist/`와 `node_modules/`는 현재 `.gitignore`에 들어 있으며 원본 콘텐츠가 아닙니다. `CONTENT_MAP.md`는 Git이 추적하지만 그 안의 상태·문자 수 목록은 `npm run sync:content-map`이 공개 원고에서 다시 계산하므로 수치만 손으로 맞추지 않습니다.

이처럼 **Git이 추적하는가**, **사람이 직접 관리하는 원본인가**, **사이트에 공개되는가**는 서로 다른 축입니다. `CONTENT_MAP.md`처럼 추적되는 생성 정보도 있고, `research/`처럼 추적되지만 공개 사이트 본문이 아닌 자료도 있으며, `dist/`처럼 사이트에 배포될 수 있지만 로컬 Git에서는 무시되는 생성물도 있습니다.

## 원본·생성물·도구 생성 파일·개인 파일을 구분하기

수정할 파일을 찾으면 다음 네 종류 중 어디에 속하는지 먼저 판정합니다.

| 종류 | 역할 | 수정 원칙 | 이 저장소의 예 |
|---|---|---|---|
| **원본(source)** | 사람이 의도를 기록하고 다음 결과를 만드는 입력 | 필요한 검토와 검증을 거쳐 직접 수정 | `src/content/docs/`, `src/assets/diagrams/source/`, 설정과 테스트 |
| **생성물(generated artifact)** | 원본과 도구에서 다시 만들 수 있는 결과 | 생성 명령과 원본을 먼저 찾고 직접 수정은 피함 | `dist/`, 콘텐츠 지도의 자동 동기화 영역 |
| **도구 생성·캐시·설치 사본(tool-generated/cache/install copy)** | 타입 정보·속도·로컬 실행을 위해 도구가 다시 만들거나 받을 수 있는 데이터 | 어떤 도구가 만드는지와 재생성 조건을 확인 | `.astro/`, `node_modules/` |
| **개인·비밀·로컬 상태** | 사용자 설정, 토큰, 실제 데이터, 도구별 작업 상태 | 공개·커밋 금지 여부와 권한을 먼저 확인 | `.env`, 로컬 도구 상태, 개인 데이터 파일 |

생성물이라고 항상 삭제해도 되는 것은 아닙니다. 생성에 필요한 원본·도구·버전이 없거나 생성 비용이 크면 중요한 보존 대상일 수 있습니다. 반대로 Git이 추적한다고 모두 사람이 손으로 편집하는 원본도 아닙니다. 파일 머리말, 생성 스크립트, `package.json`의 명령, `.gitignore`, 저장소 규칙을 함께 읽으세요.

실제 토큰이나 비밀번호가 든 `.env`와 가짜 값만 담아 필요한 설정 이름을 공유하는 `.env.example`도 구분해야 합니다. 예시 파일은 프로젝트 규칙에 따라 추적할 수 있지만 실제 비밀을 복사해서는 안 됩니다.

**단일 진실 공급원(source of truth)**: “프로젝트에 가장 중요한 파일 하나”라는 뜻이 아닙니다. 공개 원고의 원본, 콘텐츠 상태 기준, 배포 결정처럼 질문마다 최종 판단을 맡는 위치가 다를 수 있습니다. 같은 정보를 여러 파일에 복사했다면 어느 쪽을 먼저 바꾸고 어떻게 동기화하는지 규칙이 필요합니다.

## Git의 tracked·untracked·ignored는 파일의 역할이 아닙니다

Git은 파일의 교육적 의미나 보안 수준이 아니라 버전 관리 상태를 보여 줍니다.

- **tracked**: Git 이력이나 스테이징 영역이 알고 있는 파일입니다. 수정하면 status와 diff에 나타날 수 있습니다.
- **untracked**: 작업 트리에는 있지만 아직 Git이 이력 대상으로 추가하지 않은 파일입니다. 기본 `git diff`에는 내용이 보이지 않을 수 있습니다.
- **ignored**: `.gitignore` 같은 규칙 때문에 기본 상태와 추가 대상에서 제외되는 파일입니다. 이미 추적된 파일이나 과거 커밋을 자동 제거하지 않으며, 비밀을 암호화하거나 접근을 막지도 않습니다.

**staged**는 다음 커밋 후보로 스테이징 영역에 골라 둔 상태입니다. `git status`가 깨끗하다는 말은 Git이 현재 기준에서 보고할 미커밋 변경이 없다는 뜻입니다. 빌드가 성공했다거나 원격 저장소와 같다거나 ignore된 파일이 안전하다는 뜻은 아닙니다. 반대로 `git diff`가 비어도 untracked 파일이나 이미 staged인 변경이 남아 있을 수 있습니다. 자세한 상태 판정은 [Git과 GitHub는 다릅니다](../../09-git-github/git-and-github/)에서 이어집니다.

## 개발자가 경로 문제를 좁히는 순서

경로 오류가 보이면 파일을 이곳저곳 복사하거나 명령을 반복하기 전에 기준부터 고정합니다. 아래 명령은 macOS와 Linux 계열 셸의 예시이며, Windows에서는 PowerShell 등 현재 사용하는 셸의 대응 명령과 경로 표기를 확인하세요.

### 1. 명령과 오류를 그대로 보존합니다

실행한 명령, 실행 위치, 전체 오류 메시지와 대상 경로를 기록합니다. `없음`, `권한 거절`, `다른 파일을 읽음`, `빌드 뒤 되돌아감`은 원인이 다릅니다.

### 2. 현재 작업 디렉터리를 확인합니다

```bash
pwd
```

`pwd`는 현재 셸의 작업 디렉터리를 보여 줍니다. 편집기 터미널, 별도 터미널 창, 에이전트 도구는 서로 다른 CWD를 가질 수 있으므로 오래된 출력으로 대신하지 않습니다.

### 3. 대상의 실제 이름과 존재를 확인합니다

```bash
ls -la path/to/parent
```

대상 상위 디렉터리의 전체 목록에서 이름·확장자·대소문자를 확인합니다. `No such file or directory`는 경로 또는 대상이 없다는 신호이고 `Permission denied`는 대상이나 상위 경로에 접근할 권한이 없다는 별도 신호입니다. 둘을 같은 “파일 없음”으로 처리하지 마세요.

### 4. Git 저장소 루트를 확인합니다

```bash
git rev-parse --show-toplevel
```

Git 저장소 안이라면 Git이 인식하는 작업 트리 최상위를 보여 줍니다. 저장소 밖이거나 Git 저장소가 아니면 실패할 수 있으며, 그 실패를 임의의 경로로 추측해 채우지 않습니다.

### 5. 대상 경로를 기준 위치와 결합합니다

상대 경로를 CWD·프로젝트 루트·설정 파일 위치 중 어디에서 해석하는지 확인합니다. 경로에 공백이나 특수문자가 있으면 사용하는 셸의 인용 규칙에 맞게 전체 경로를 따옴표로 묶습니다.

### 6. 파일의 책임과 생성 규칙을 찾습니다

상위 폴더의 규칙 문서, 설정, 파일 머리말, 생성 스크립트를 읽습니다. 같은 이름의 파일이 여럿이면 검색 결과 수와 각 상위 경로를 비교합니다.

### 7. Git 상태를 서로 다른 증거로 봅니다

```bash
git status --short --branch
git diff -- path/to/file
git diff --staged -- path/to/file
git ls-files -- path/to/file
git check-ignore -v -- path/to/file
```

각 명령은 현재 브랜치와 상태, 스테이징되지 않은 tracked 변경, staged 변경, 추적 여부와 ignore 규칙의 출처라는 서로 다른 범위를 보여 줍니다. 기본 `git status`는 ignored 파일을 보여 주지 않습니다. `git check-ignore -v`의 출력은 일치한 규칙·출처·경로를 보여 주며, 출력이 있다는 사실만으로 제외 여부를 판정하지 않습니다. 패턴이 `!`로 시작하는 부정 패턴이면 제외의 예외로 다시 포함되는 경우입니다. 예를 들어 이 저장소의 `.env.*`와 `!.env.example`은 일반 제외와 예외를 구분합니다. 출력이 없다면 먼저 오류 없이 조회했는지 확인하고, 대상이 기본 검사에서 빠지는 tracked 파일인지 `git ls-files` 결과와 대조합니다. 정상 조회한 untracked 대상이라면 일치한 규칙이 없다는 뜻입니다. 한 출력이 비었다고 다른 상태까지 비었다고 결론 내리지 않습니다.

### 8. 글롭과 파괴적 작업의 최종 대상을 확인합니다

**글롭(glob 또는 pathname pattern):** `*`, `?`, `[...]`처럼 하나의 경로 문자열을 여러 파일명 후보와 맞추는 패턴입니다. 흔히 셸이 명령 실행 전에 패턴을 실제 경로 목록으로 확장하지만, 일치 항목이 없을 때의 처리, 숨김 파일 포함 여부, 재귀 표현과 인용 규칙은 셸·도구·설정마다 다릅니다. 정규 표현식과도 같은 문법이 아니므로 현재 실행 환경의 규칙을 확인해야 합니다.

읽기 전용 검색에서는 글롭이 편리하지만 삭제·이동·덮어쓰기·권한 변경 같은 파괴적 작업에 그대로 쓰면 예상보다 넓은 대상이 선택될 수 있습니다. 다음 기준을 모두 확인하기 전에는 실행하지 않습니다.

1. `pwd`, 프로젝트 루트, 저장소 루트와 작업 공간 경계를 다시 확인합니다.
2. 해석되지 않은 환경 변수, 명령 치환, 글롭, 기준이 넓은 상대 경로가 최종 대상을 결정하게 두지 않습니다.
3. 현재 셸과 도구에 맞는 비변경 방식으로 확장될 최종 경로 목록과 개수를 먼저 확인합니다.
4. `..`와 심볼릭 링크를 따라간 실제 대상이 허용 범위 안인지 확인합니다.
5. 파일 시스템 루트 `/`, 홈 디렉터리, 저장소 루트, 작업 공간 루트처럼 넓은 경계 자체가 대상이면 거절합니다.
6. 가능하면 휴지통 이동·백업·새 사본 작성처럼 복구 가능한 방법을 우선합니다.
7. 대상이나 복구 범위가 조금이라도 불명확하면 멈추고 확인을 요청합니다.

명령 문자열이 짧거나 익숙하다는 사실은 안전 증거가 아닙니다. 파괴적 작업에서는 **명령을 만들 때 의도한 경로**가 아니라 **실제로 확장·정규화되어 영향을 받을 최종 대상**을 승인해야 합니다.

### 9. 원본을 한 단위만 수정하고 같은 경로에서 검증합니다

의도한 원본만 수정한 뒤 다시 status와 diff를 보고, 프로젝트가 정한 테스트·빌드·브라우저 확인을 실행합니다. 생성물을 수정했다면 원본에서 다시 생성했을 때 변경이 유지되는지 확인해야 합니다.

## 자주 만나는 실패와 복구

| 증상 | 흔한 원인 | 먼저 할 복구 |
|---|---|---|
| 파일을 수정했는데 사이트가 바뀌지 않음 | 편집기에서 저장하지 않음, 내부 `docs/`와 공개 `src/content/docs/` 혼동, 빌드 미실행, 다른 서버 확인 | 파일 저장 여부·콘텐츠 루트·빌드 입력·현재 실행 중인 서버와 URL을 확인 |
| 빌드 뒤 수정이 사라짐 | `dist/` 같은 생성물을 직접 편집 | 생성 명령을 찾고 원본을 수정한 뒤 재생성 |
| 내 컴퓨터에서만 작동함 | 개인 절대 경로, 홈 파일, 대소문자 차이, 커밋되지 않은 파일 의존 | 저장소 상대 경로·추적 상태·CI 환경의 파일명과 설정 확인 |
| `git diff`가 비었는데 새 파일이 있음 | 파일이 untracked·ignored이거나 변경이 이미 staged | `git status --short`, `git diff --staged`, 실제 파일 목록을 함께 확인 |
| 같은 이름의 다른 파일이 수정됨 | CWD가 다르거나 검색 결과 하나만 보고 선택 | 저장소 루트와 전체 상위 경로를 비교하고 대상 책임 확인 |
| 글롭이 예상보다 많은 파일을 선택함 | `*`·`?`·대괄호 패턴, 변수 또는 상대 경로가 셸·도구에서 넓게 확장됨 | 실행을 멈추고 최종 대상 목록·개수·링크 대상과 루트 경계를 비변경 방식으로 다시 확인 |
| `No such file` 또는 찾을 수 없음 | 기준 위치 오류, 이름·확장자·대소문자 불일치, 이동된 경로 | CWD와 실제 파일명, 참조하는 설정·링크를 확인 |
| `Permission denied` | 대상 또는 상위 경로의 접근 권한이 거절됨. 최종 파일의 존재는 아직 확인하지 못했을 수 있음 | 권한이 필요한 이유와 최소 범위를 확인하고 우회 복사보다 승인 경계 검토 |
| `..`를 포함한 경로가 작업 공간 밖으로 나감 | 상대 경로 정규화 뒤 허용 범위를 벗어나거나 심볼릭 링크가 바깥을 가리킴 | 링크를 따라간 최종 대상과 샌드박스(격리된 작업 범위)·쓰기 허용 루트를 확인 |
| 링크는 열리지만 다른 파일이 나타남 | 심볼릭 링크, 복사본, 오래된 캐시, 다른 브랜치·worktree | 링크의 최종 대상, 현재 브랜치와 worktree(한 저장소의 별도 작업 디렉터리), 캐시·생성 시점을 분리해 확인 |
| URL의 경로를 디스크에서 찾을 수 없음 | 웹 라우트와 파일 시스템 경로를 같은 것으로 생각하거나 배포 base 접두사를 빠뜨림 | 프레임워크의 라우팅·base·빌드 규칙과 실제 네트워크 응답 확인 |

경로 오류를 해결하려고 파일을 여러 위치에 복사하면 잠깐 증상이 사라질 수 있지만 어느 사본이 원본인지 더 불명확해집니다. 먼저 기준 위치와 책임을 찾고, 복사가 정말 필요한 구조라면 생성·동기화 규칙을 명시하세요.

## AI에게 경로가 있는 작업을 맡기는 법

“문서를 보강해 줘”보다 다음 정보를 함께 주면 잘못된 파일을 수정할 가능성을 줄일 수 있습니다.

```text
저장소 루트: 현재 Git이 인식하는 최상위 경로를 먼저 확인할 것
수정 대상: src/content/docs/02-work-environment/files-folders-paths.md
읽기 전용 참고: AGENTS.md, PROJECT_CONTEXT.md, docs/project/editorial-guide.md
직접 수정 금지: docs/의 내부 검토 기록, dist/, node_modules/, 저장소 밖 파일
파괴적 작업: 삭제·이동·덮어쓰기·권한 변경 금지. 필요하면 최종 대상 목록과 복구 방법을 먼저 보고하고 승인을 기다릴 것
원본·생성물: 공개 Markdown이 원본이며 CONTENT_MAP.md의 상태·문자 수는 명령으로 동기화
수용 기준: 절대·상대 경로와 CWD를 구분하고 실제 저장소 사례·실패 복구·연습을 포함
검증: git diff --check, npm run sync:content-map, npm run check
검증의 쓰기 효과: sync 명령은 CONTENT_MAP.md를, build를 포함한 check는 dist/를 생성 규칙으로 갱신하지만 직접 편집하지 않음
외부 권한: 새 의존성·네트워크·push·배포 금지
```

작업 전에는 에이전트가 `pwd`, 저장소 루트, 현재 브랜치와 status, 대상 파일의 실제 존재를 보고하게 하세요. 작업 뒤에는 “수정했습니다”라는 설명보다 대상 파일의 diff, 새로 생긴 untracked 파일, 검증 명령의 종료 코드와 빌드된 페이지를 확인합니다. 위 계약의 `git diff --check`는 공백 오류와 해결되지 않은 충돌 표시를 점검하지만 내용의 정확성까지 증명하지는 않습니다.

에이전트가 절대 경로를 출력했다면 그 경로가 현재 작업 공간과 저장소 안인지 확인합니다. 반대로 저장소 상대 경로만 출력했다면 어느 저장소를 기준으로 했는지 확인합니다. 경로 형식이 구체적이라는 이유만으로 대상이 올바르다고 믿지 않습니다.

## 판단 규칙

1. **이름보다 전체 경로와 책임을 먼저 봅니다.** 같은 이름의 파일이 여러 개 있을 수 있습니다.
2. **상대 경로에는 기준 위치를 붙입니다.** CWD 또는 도구가 정한 기준을 말하지 않은 상대 경로는 정보가 부족합니다.
3. **공유 설정에는 개인 절대 경로를 남기지 않습니다.** 저장소 상대 경로, 환경 설정 또는 명시적 구성으로 바꿉니다.
4. **생성물보다 원본과 생성 명령을 찾습니다.** 예외적으로 생성물을 추적한다면 갱신 절차를 함께 둡니다.
5. **Git 상태와 파일 역할을 분리합니다.** tracked는 원본이라는 뜻이 아니고 ignored는 안전하다는 뜻이 아닙니다.
6. **경로 오류와 권한 오류를 구분합니다.** 존재하지 않는 파일을 찾는 문제와 대상 또는 상위 경로의 접근이 거절된 문제는 해결 방법이 다릅니다. 상위 경로에 접근하지 못했다면 최종 파일의 존재도 아직 확인되지 않았을 수 있습니다.
7. **로컬 파일 경로와 웹 URL을 구분합니다.** 둘의 매핑은 설정·라우팅·빌드 결과로 확인합니다.
8. **작업 공간 밖으로 나가는 경로는 멈추고 확인합니다.** `..`, 심볼릭 링크, 홈 경로와 외부 마운트(컴퓨터에 연결된 다른 디스크·네트워크 저장소)는 권한·데이터 경계를 바꿀 수 있습니다. 문자열 경로뿐 아니라 링크를 따라간 최종 대상도 확인합니다.
9. **변경 전후에 같은 기준으로 확인합니다.** 다른 CWD·브랜치·서버·브라우저 탭을 비교하면 잘못된 결론이 생깁니다.
10. **파괴적 작업은 확장 뒤의 최종 대상을 승인합니다.** 해석되지 않은 변수·명령 치환·글롭·넓은 상대 경로에 의존하지 않고, 최종 목록·개수·링크 대상·루트 경계·복구 방법을 확인합니다.

## 짧은 연습

### 연습 1: 프로젝트 경계 지도 만들기

자신의 프로젝트에서 CWD, 프로젝트 루트, 저장소 루트, 작업 공간의 경로를 각각 적으세요. 같다면 “같음”이라고 추측하지 말고 어떤 명령·설정·화면으로 확인했는지 옆에 적습니다.

| 경계 | 실제 경로 또는 범위 | 확인 증거 |
|---|---|---|
| 현재 작업 디렉터리 |  | `pwd` 결과 |
| 프로젝트 루트 |  | 설정·실행 명령의 기준 |
| Git 저장소 루트 |  | `git rev-parse --show-toplevel` 결과 |
| 작업 공간 |  | 편집기·에이전트의 열린 폴더와 권한 |

| 상대 경로 | 해석한 절대 경로 | 존재하지 않을 때와 다른 파일이 있을 때의 결과 |
|---|---|---|
| `vibe-dev-handbook/README.md` |  |  |
| `./vibe-dev-handbook/README.md` |  |  |
| `../projects/vibe-dev-handbook/README.md` |  |  |

### 연습 2: 파일을 역할별로 분류하기

프로젝트에서 파일이나 폴더 여덟 개를 고르고 `원본·생성물·도구 생성/캐시/설치 사본·개인/비밀 상태` 중 하나로 분류하세요. 각 항목에 Git 상태, 생성 또는 복구 방법, 공개 여부를 추가합니다. 한 항목이 여러 축에서 다른 상태를 가질 수 있다는 점을 확인하는 연습입니다.

### 연습 3: 두 개의 `docs`를 설명하기

이 저장소의 `docs/project/editorial-guide.md`와 `src/content/docs/02-work-environment/files-folders-paths.md`를 비교해 다음 질문에 답하세요.

1. 두 파일은 각각 누구를 위한 문서인가요?
2. 어느 파일이 웹사이트의 학습 장으로 빌드되나요?
3. 각 파일을 수정했을 때 무엇으로 결과를 확인해야 하나요?
4. `dist/`에서 대응 HTML을 직접 수정하면 왜 다음 빌드 뒤 사라질 수 있나요?

답은 파일 이름이 아니라 `WORKSPACE_MAP.md`, 빌드 설정, Git 상태와 실제 빌드 결과를 근거로 작성하세요.

### 연습 4: AI 작업 계약 작성하기

자신의 프로젝트에서 가장 작은 문서 또는 코드 변경 하나를 고르고 다음 표를 채우세요. 다른 사람이나 새 AI 세션에 표만 전달한 뒤, 어느 파일을 읽고 수정하며 무엇을 만들거나 실행해도 되는지 같은 범위로 해석하는지 확인합니다. 해석이 다르면 실제 작업을 시작하기 전에 계약을 고칩니다.

| 저장소와 실행 위치 |  |
| 수정 대상 |  |
| 읽기 전용 참고 |  |
| 직접 수정 금지 |  |
| 원본과 생성물 |  |
| 수용 기준 |  |
| 검증 명령과 쓰기 효과 |  |
| 네트워크·설치·커밋·배포 권한 |  |

POSIX.1-2024의 [용어 정의](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap03.html)와 [경로명 해석 규칙](https://pubs.opengroup.org/onlinepubs/9799919799/basedefs/V1_chap04.html#tag_04_16)은 `/`로 시작하는 절대 경로, 현재 작업 디렉터리 등에서 시작하는 상대 경로, `.`·`..`와 심볼릭 링크의 기본 범위를 뒷받침합니다. `~`와 글롭은 파일 시스템 경로 자체의 보편 문법이 아니라 POSIX 셸의 [단어·경로명 확장과 패턴 일치](https://pubs.opengroup.org/onlinepubs/9799919799/utilities/V3_chap02.html) 범위로 다루며, 실제 일치 실패·숨김 파일·재귀 처리·인용 동작은 현재 셸과 도구에서 다시 확인해야 합니다. Windows의 접두사·UNC·상대 경로 차이는 Microsoft의 [파일·경로·네임스페이스 공식 문서](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)를, 대소문자 기본 동작과 디렉터리별 예외는 [Windows·WSL 대소문자 공식 문서](https://learn.microsoft.com/en-us/windows/wsl/case-sensitivity)를 기준으로 설명했습니다.

Git 상태 설명은 [git status 공식 문서](https://git-scm.com/docs/git-status), [gitignore 공식 문서](https://git-scm.com/docs/gitignore), [git check-ignore 공식 문서](https://git-scm.com/docs/git-check-ignore)와 [Pro Git](https://git-scm.com/book/ko/v2)의 안정된 개념 범위에 연결했습니다. 이 저장소에서 공개 콘텐츠가 `src/content/docs/`에 놓이고 사이트로 빌드되는 구조는 저장소 규칙과 [Starlight 프로젝트 구조 공식 문서](https://starlight.astro.build/guides/project-structure/)를 기준으로 설명했습니다. `base`·`dist/`·캐시 디렉터리의 제품 범위는 [Astro 설정 참조](https://docs.astro.build/en/reference/configuration-reference/)를, Finder의 확장자 가시성은 [Apple 공식 안내](https://support.apple.com/en-au/guide/mac-help/mchlp2304/mac)를 확인했습니다. POSIX 규칙이나 특정 제품의 현재 동작을 모든 운영체제와 프로그램에 그대로 확대하지 않았으며, 실제 경로는 운영체제·파일 시스템·셸·API·도구 설정을 함께 확인해야 합니다.
