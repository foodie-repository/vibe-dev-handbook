## 왜 필요한가

AI에게 기능을 추가해 달라고 하면 종종 "패키지를 설치하겠습니다"라는 답이 돌아옵니다. 이때 무엇을 설치하는지, 왜 필요한지, 어느 파일이 바뀌는지, 다른 컴퓨터에서도 같은 조합이 만들어지는지 모르면 화면이 한 번 뜬 것만 보고 중요한 결정을 넘기게 됩니다. 의존성은 기능을 빠르게 가져오는 수단이지만, 동시에 버전 충돌·공급망 위험·업데이트 비용·실행 환경 차이를 프로젝트 안으로 들이는 선택입니다.

이 장의 목표는 특정 명령을 외우는 것이 아닙니다. 실행 주체와 설치 도구, 필요한 패키지의 선언과 실제 설치 조합, 프로젝트별 환경 경계를 나누어 질문하고 증거로 확인하는 것이 목표입니다.

## 한 문장 정의

**런타임은 코드를 실행하고, 의존성은 프로젝트가 기대는 구성요소이며, 패키지 관리자는 그것을 해석·설치하고, 매니페스트는 필요한 범위를 선언하며, 잠금 파일은 선택된 조합을 기록하고, 환경 격리는 프로젝트마다 실행·설치 경계를 나누는 장치입니다.**

이 여섯 가지는 연결되지만 같은 것이 아닙니다.

| 개념 | 맡는 책임 | 확인할 대표 증거 | 단독으로 보장하지 않는 것 |
|---|---|---|---|
| 런타임(runtime) | 소스 코드를 해석하거나 실행하고 운영체제 기능에 접근하게 한다 | 런타임 종류와 실제 버전 출력 | 필요한 패키지 설치, 애플리케이션의 정확성 |
| 의존성(dependency) | 프로젝트가 직접 또는 간접으로 기대는 외부·내부 구성요소가 된다 | 매니페스트, 잠금 파일, 의존성 트리 | 안전성, 유지보수성, 프로젝트 적합성 |
| 패키지 관리자(package manager) | 의존성 선언과 저장소 정보를 읽어 버전을 선택하고 설치한다 | 실행한 도구·버전·종료 코드·변경 파일 | 모든 생태계에서 같은 해석과 설치 결과 |
| 매니페스트(manifest) | 프로젝트 이름, 명령, 직접 의존성과 허용 버전 범위 같은 의도를 선언한다 | 예: `package.json`; 생태계별 공식 선언 파일 | 전이 의존성까지 포함한 정확히 같은 설치 조합 |
| 잠금 파일(lockfile) | 해결된 버전과 의존 관계 등 설치 조합을 기록해 재현 가능성을 높인다 | 예: `package-lock.json`; 매니페스트와 함께 검토한 변경 전후 차이(diff) | 운영체제·CPU·런타임·외부 저장소까지 같은 환경 |
| 환경 격리(environment isolation) | 한 프로젝트의 실행 도구와 설치 대상을 다른 프로젝트와 분리한다 | 활성 환경, 설치 위치, 실제 실행 파일 경로 | 완전한 보안 격리, 운영 환경과의 완전한 동일성 |

## 비유: 조리법과 식재료 상자

프로젝트를 요리라고 생각해 보겠습니다. 런타임은 조리할 수 있는 주방, 의존성은 다른 곳에서 만든 소스와 재료, 패키지 관리자는 목록을 읽어 재료를 가져오는 담당자입니다. 매니페스트는 "어떤 종류와 범위의 재료가 필요한가"를 적은 조리법이고, 잠금 파일은 이번에 실제로 고른 생산자·규격·조합을 적은 납품 명세에 가깝습니다. 환경 격리는 다른 요리의 재료 상자와 섞이지 않게 프로젝트별 작업대를 나누는 일입니다.

이 비유가 맞는 지점은 역할 구분입니다. 조리법만으로 실제 납품 조합을 알 수 없고, 같은 조리법도 담당자와 공급 조건이 다르면 결과가 달라질 수 있습니다.

하지만 비유는 여기서 깨집니다. 소프트웨어 의존성은 설치될 때 다른 의존성을 다시 불러오는 **전이 의존성**을 가질 수 있고, 설치 스크립트를 실행하거나 빌드 결과에 포함될 수도 있습니다. 잠금 파일이 있어도 운영체제·CPU·런타임 버전·환경 변수·외부 저장소 상태까지 모두 고정되는 것은 아닙니다. 환경 격리도 별도 작업대 정도의 분리이지, 자동으로 악성 코드와 비밀정보 접근을 막는 보안 경계라고 볼 수 없습니다.

## 시스템에서 어디에 놓이는가

설치와 실행을 한 흐름으로 보면 책임이 더 잘 보입니다.

1. 사람이 요구와 제약을 확인하고 새 의존성이 필요한지 결정합니다.
2. 매니페스트가 직접 의존성과 허용 범위를 선언합니다.
3. 패키지 관리자가 매니페스트와 기존 잠금 파일을 읽어 구체 버전을 해결합니다.
4. 잠금 파일이 선택된 조합을 기록하고, 설치 영역에 실제 파일이 놓입니다.
5. 런타임이 애플리케이션 코드를 실행하면서 설치된 의존성을 불러옵니다.
6. 테스트·빌드·정적 검사가 그 조합에서 기대 결과가 나오는지 확인합니다.
7. 변경을 통합할 때 자동으로 검사하는 지속적 통합(Continuous Integration, CI)이나 다른 깨끗한 환경에서 같은 입력으로 다시 설치해 재현성을 확인합니다.

여기서 **선택**과 **설치**와 **실행**은 서로 다른 사건입니다. 매니페스트를 수정했다고 설치가 끝난 것이 아니고, 설치 명령의 종료 코드가 0이라고 기능이 맞는 것도 아니며, 로컬 실행 성공이 다른 환경의 재현성을 증명하지도 않습니다.

## 매니페스트와 잠금 파일을 함께 읽는 법

Node.js 프로젝트의 한 예에서는 `package.json`이 직접 의존성과 허용 버전 범위를 선언하고, `package-lock.json`이 해결된 의존성 트리를 기록합니다. npm 공식 문서는 `package-lock.json`이 팀원·배포·지속적 통합이 같은 의존성 트리를 설치할 수 있도록 커밋하는 파일이라고 설명합니다. 반면 `npm ci`는 기존 잠금 파일을 요구하고, 매니페스트와 잠금 파일이 맞지 않으면 잠금 파일을 고쳐 쓰지 않고 오류로 끝냅니다.

따라서 두 파일의 diff는 다른 질문에 답합니다.

- 매니페스트 diff: 무엇을 직접 필요로 하게 되었고 허용 범위가 왜 바뀌었는가?
- 잠금 파일 diff: 그 선언을 해결하면서 실제 어떤 버전과 전이 의존성 조합이 바뀌었는가?

잠금 파일이 크게 바뀌었다고 무조건 오류는 아니지만, 요청한 패키지 하나와 무관해 보이는 대규모 변화가 생기면 패키지 관리자 버전, 기존 잠금 파일 상태, 설치 옵션을 먼저 확인해야 합니다. 반대로 사람이 잠금 파일의 일부를 임의로 고쳐 숫자만 맞추는 것도 해결책이 아닙니다. 매니페스트와 공식 도구를 원본으로 삼아 다시 생성하고 검증해야 합니다.

## 환경 격리와 버전 드리프트

**버전 드리프트(version drift):** 개발자 컴퓨터, CI, 미리보기, 운영처럼 서로 다른 환경에서 런타임이나 패키지의 실제 버전 조합이 의도와 달라지는 현상입니다. "어제는 됐는데 오늘은 안 된다"거나 "내 컴퓨터에서는 된다"는 말 뒤에는 다음 차이가 숨어 있을 수 있습니다.

- 런타임의 종류나 버전
- 패키지 관리자 버전과 해결 규칙
- 매니페스트와 잠금 파일의 일치 여부
- 운영체제·CPU·파일 시스템의 대소문자 처리
- 환경 변수, 권한, 시간대, 로케일
- 전역 설치 도구와 프로젝트 안에 고정된 도구의 차이
- 캐시되거나 이전 설치에서 남은 파일

Python의 `venv`는 프로젝트마다 독립된 패키지 디렉터리를 가진 가상 환경을 만드는 대표적인 예입니다. Python 공식 문서는 가상 환경을 일회용으로 보고 소스 코드와 함께 Git에 넣지 않으며, 이동하기보다 요구 사항에 따라 다시 만드는 방식을 안내합니다. 그러나 가상 환경은 기본적으로 Python 패키지 경계를 나누는 장치입니다. 운영체제 전체, 네트워크, 파일 권한, 환경 변수, 데이터베이스까지 자동으로 격리하는 것은 아닙니다.

Node.js 프로젝트의 로컬 설치 영역과 잠금 파일, Python의 가상 환경과 의존성 선언은 같은 목적의 일부를 공유하지만 파일명·해결 규칙·활성화 방식·설치 명령은 다릅니다. 다른 언어 생태계에도 각자의 매니페스트와 잠금 또는 해석 규칙이 있습니다. **한 생태계의 명령이나 잠금 의미를 다른 생태계의 보편 규칙으로 옮기지 말고, 현재 프로젝트가 채택한 공식 문서와 실제 파일을 확인해야 합니다.**

## 설치 전에 반드시 승인할 것

새 패키지 설치는 로컬 파일을 바꾸고 외부 저장소에 접근하며, 경우에 따라 설치 스크립트를 실행하고 잠금 파일을 크게 갱신할 수 있습니다. 그러므로 AI가 패키지 이름을 제안했다는 이유만으로 바로 설치하지 않습니다. 최소한 다음 계약을 먼저 확인합니다.

1. 해결할 요구와 현재 실패 증거는 무엇인가?
2. 표준 기능이나 이미 설치된 의존성으로 해결할 수 없는가?
3. 추가할 정확한 패키지와 선택 이유는 무엇인가?
4. 공식 저장소·라이선스·유지 상태·지원 런타임을 어디서 확인했는가?
5. 매니페스트, 잠금 파일, 설정, 생성 파일 중 무엇이 바뀔 예정인가?
6. 네트워크 접근, 설치 스크립트, 비밀정보, 운영 환경에 어떤 영향이 있는가?
7. 실패하면 어떤 파일과 환경을 보존하고 어떻게 원래 상태로 돌아갈 것인가?
8. 설치 뒤 어떤 테스트·빌드·재현 검사를 통과해야 하는가?

이 질문에 답한 뒤 설치 권한과 네트워크 권한을 별도로 승인합니다. 승인받은 패키지 하나가 비슷한 패키지 여러 개, 전역 설치, 새 런타임, 운영 배포까지 자동으로 허용하는 것은 아닙니다.

## 재현 가능한 검증 순서

재현성은 "잠금 파일이 있다"는 속성이 아니라, 같은 입력을 깨끗한 경계에서 다시 사용해 같은 설치와 검사를 얻는지 확인하는 과정입니다.

### 1. 변경 전 기준을 보존한다

현재 런타임과 패키지 관리자 버전, 작업 트리 상태, 기존 매니페스트·잠금 파일, 통과하던 검사 결과를 기록합니다. 무관한 사용자 변경이 있으면 섞지 않습니다.

### 2. 승인된 최소 변경만 설치한다

정확한 프로젝트 루트와 환경을 확인한 뒤 승인된 패키지와 범위만 적용합니다. 전역 설치를 로컬 의존성 대신 사용하거나, 실패했다고 잠금 파일과 설치 디렉터리를 무조건 삭제하지 않습니다.

### 3. 선언과 해결 결과를 함께 검토한다

매니페스트와 잠금 파일 diff를 나란히 보고 새 직접 의존성, 바뀐 전이 의존성, 실행 스크립트와 설정 변화를 확인합니다. 예상하지 않은 파일이 바뀌면 그 자리에서 중단합니다.

### 4. 기능과 품질을 확인한다

작은 관련 테스트부터 시작해 정적 검사와 빌드를 실행합니다. 명령의 종료 코드, 실제 실행된 테스트 수, 오류와 경고, 생성된 아티팩트를 함께 봅니다. "명령을 실행했다"가 아니라 기대 결과를 관찰해야 합니다.

### 5. 깨끗한 환경에서 다시 설치한다

프로젝트가 채택한 잠금 기반 설치 방식으로 기존 로컬 잔여물에 기대지 않는 설치를 수행합니다. 예를 들어 npm의 `npm ci`는 잠금 파일과 매니페스트가 맞지 않으면 실패하고 잠금 파일을 자동 수정하지 않는 CI용 설치 방식입니다. 다만 실행 전에 공식 문서의 현재 동작과 기존 설치 디렉터리 제거 영향을 확인하고 승인을 받아야 합니다.

### 6. 실행 환경 차이를 기록한다

로컬과 검증 환경의 런타임·운영체제·설정 차이를 남깁니다. 모든 환경을 완전히 같게 만드는 대신, 결과에 영향을 주는 차이를 명시하고 허용 범위를 테스트합니다.

## 실제 사례에서 판단이 달라지는 지점

모임 참가 웹앱에 날짜 계산 패키지를 추가한다고 가정해 보겠습니다. "날짜를 보기 좋게 표시"하는 요구만 있다면 런타임의 표준 기능으로 충분할 수 있습니다. 반면 여러 시간대의 모집 마감 규칙을 일관되게 계산해야 하고 표준 기능만으로 오류 가능성이 커진다면 검증된 패키지가 비용을 줄일 수 있습니다.

결정은 패키지의 유명세가 아니라 요구와 실패 비용에 따라 달라집니다. 화면 표시만 담당하는지, 서버의 모집 마감 판정에도 쓰이는지에 따라 책임과 테스트가 다릅니다. 서버 판정에 들어가면 시간대·경계 시각·잘못된 입력·업데이트 호환성을 포함한 테스트가 필요하고, 브라우저에 포함되면 번들 크기와 공개 코드·라이선스도 확인해야 합니다. 이 사례는 특정 날짜 패키지를 권장하지 않으며 실제 후보는 채택 시점의 공식 문서로 다시 확인합니다.

## 흔한 오해와 실패, 복구

| 오해 또는 실패 | 왜 위험한가 | 먼저 할 복구 |
|---|---|---|
| "패키지를 설치했으니 기능이 끝났다" | 설치 성공은 요구 충족과 테스트 성공을 증명하지 않는다 | 설치 diff를 보존하고 수용 기준에 맞는 테스트부터 실행한다 |
| "잠금 파일이 있으니 어디서나 똑같다" | 런타임·OS·CPU·환경 변수와 외부 저장소는 잠금 파일 밖에 있다 | 환경 버전과 설정 차이를 기록하고 깨끗한 환경에서 재검증한다 |
| "잠금 파일은 생성물이니 커밋하지 않아도 된다" | 팀과 CI가 다른 조합을 선택할 수 있다 | 현재 생태계 공식 정책을 확인하고 매니페스트와 함께 일관되게 관리한다 |
| "오류가 나면 설치 폴더와 잠금 파일부터 지운다" | 원인과 기존 재현 정보를 동시에 없앨 수 있다 | 오류·버전·diff를 보존하고 매니페스트 불일치, 권한, 네트워크를 먼저 분리한다 |
| "전역 설치가 되니 프로젝트도 재현된다" | 다른 컴퓨터와 CI에는 같은 전역 도구가 없을 수 있다 | 프로젝트 선언 또는 명시된 도구 버전으로 옮기고 새 환경에서 확인한다 |
| "가상 환경이면 안전한 샌드박스다" | 보통 패키지 경계를 나눌 뿐 파일·네트워크·비밀 접근을 막지 않는다 | 실행 권한과 접근 범위를 별도로 제한하고 비밀·운영 데이터를 배제한다 |
| "업데이트는 최신일수록 항상 좋다" | 호환성 변경과 전이 의존성 변화가 함께 들어올 수 있다 | 변경 이유·지원 범위·릴리스 정보를 확인하고 작은 단위로 업데이트·검증한다 |

설치가 실패했을 때는 먼저 기존 매니페스트·잠금 파일·사용자 작업과 오류 출력을 보존합니다. 아직 커밋하지 않은 무관한 변경을 덮어쓰지 말고, 승인된 설치가 만든 diff만 식별합니다. 원상 복구가 필요하면 정확히 그 파일과 프로젝트별 설치 환경을 대상으로 하며, 범위가 불명확하면 삭제 명령을 실행하지 않고 확인을 요청합니다.

## AI에게 요청하고 검토하는 프롬프트

```text
현재 프로젝트에 새 의존성이 필요한지 읽기 전용으로 먼저 검토해 주세요.

- 해결할 요구와 현재 관찰 증거를 한 문장씩 분리하세요.
- 표준 기능과 이미 설치된 의존성으로 해결하는 대안을 먼저 확인하세요.
- 새 패키지가 필요하다면 정확한 이름, 책임, 직접·전이 의존성 영향, 지원 런타임, 라이선스와 유지 상태를 공식 문서 기준으로 제시하세요.
- 현재 매니페스트·잠금 파일·런타임·패키지 관리자·환경 격리 방식을 확인하세요.
- 예상 변경 파일, 네트워크 접근, 설치 스크립트, 전역 설치 여부, 실패 시 보존·복구 경계를 설명하세요.
- 설치나 파일 변경은 하지 말고 승인을 기다리세요.
- 승인 뒤에는 매니페스트와 잠금 파일 diff, 종료 코드, 관련 테스트·정적 검사·빌드, 깨끗한 환경 재설치 결과를 증거로 보고하세요.
- 한 생태계의 명령과 잠금 의미를 다른 생태계에 일반화하지 마세요.
```

AI의 답변에서 패키지 이름만 있고 대안·지원 범위·변경 파일·검증이 없으면 아직 설치 계약이 아닙니다. "문제없습니다" 같은 결론 대신 확인한 파일 경로, 도구와 버전, 명령 결과, 남은 불확실성을 요구해야 합니다.

## 확인 체크리스트

- [ ] 현재 코드를 실행하는 런타임과 실제 버전을 확인했다.
- [ ] 직접 의존성과 전이 의존성을 구분했다.
- [ ] 패키지 관리자와 그 버전을 확인했다.
- [ ] 매니페스트가 선언하는 범위와 잠금 파일이 기록하는 실제 조합을 구분했다.
- [ ] 새 패키지가 정말 필요한지 표준 기능·기존 의존성과 비교했다.
- [ ] 설치 전에 정확한 대상·네트워크·스크립트·변경 파일에 대한 승인을 받았다.
- [ ] 전역 설치나 개인 컴퓨터의 우연한 상태에 기대지 않는다.
- [ ] 환경 격리가 제공하는 범위와 제공하지 않는 보안 경계를 설명할 수 있다.
- [ ] 매니페스트와 잠금 파일 diff에서 예상하지 않은 변화를 확인했다.
- [ ] 관련 테스트·정적 검사·빌드의 종료 코드와 실제 결과를 확인했다.
- [ ] 깨끗한 환경에서 잠금 기반 설치와 검증을 재현했다.
- [ ] 런타임·OS·설정 차이와 남은 버전 드리프트 가능성을 기록했다.
- [ ] 실패 시 기존 사용자 작업과 재현 증거를 보존하는 복구 경계를 정했다.
