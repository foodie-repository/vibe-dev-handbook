## 먼저 결론

좋은 사용자 경험은 정상 화면 하나를 예쁘게 만드는 일이 아니라 사용자가 **지금 무슨 상태인지, 무엇이 확정됐는지, 다음에 무엇을 할 수 있는지** 이해하게 만드는 일입니다. 화면은 초기·로딩·빈 결과·성공·입력 검증 실패·업무 충돌·전달 오류·결과 불명·재시도 상태를 구분하고, 각 상태에서 가능한 행동과 복구 경로를 보여 줘야 합니다.

버튼을 누르자마자 “완료”라고 표시하는 낙관적 UI는 빠른 피드백을 줄 수 있지만 서버의 권위 상태를 바꾸지는 않습니다. 요청이 거절되거나 응답이 끊기면 화면 표시를 되돌리는 것만으로 충분하지 않을 수 있습니다. 같은 쓰기를 다시 보내기 전에 현재 권위 상태와 이전 요청의 처리 결과를 확인할 복구 오라클이 필요합니다.

## 왜 필요한가

AI에게 “로딩과 에러 처리를 넣어 주세요”라고 요청하면 진행 중임을 나타내는 회전 표시(spinner)와 공통 오류 문구만 생기기 쉽습니다. 그러나 검색 결과가 0건인 정상 상태와 요청 실패가 같은 빈 화면으로 보이거나, 입력 오류와 정원 충돌이 모두 “다시 시도하세요”가 되거나, 중복 클릭이 같은 참가 요청을 여러 번 보내거나, 이전 응답이 최신 선택을 덮어쓸 수 있습니다. 사용자는 무엇을 고쳐야 하는지 알지 못하고 시스템은 실제 상태와 화면 상태가 어긋납니다.

정상 경로만 데모하면 미리 준비한 대표 시험 데이터·상태(fixture)에서는 좋아 보일 수 있습니다. 실제 환경에서는 느린 응답, 여러 탭, 중복 행동, 권한 변경, 동시 사용자, 응답 유실과 오래된 캐시가 생깁니다. 상태 설계는 이런 실패를 없다고 가정하는 대신 각 경계가 어떤 사실을 보장하고 실패 뒤 무엇으로 복구할지 정합니다.

## 한 문장 정의

- **UI 상태(UI state)**: 사용자가 현재 보고 조작할 화면을 결정하는 선택값·입력값·진행 여부·응답·오류·표시 정보의 현재 묶음입니다.
- **상태 전이(state transition)**: 사용자 행동, 응답, 시간 초과나 외부 변화 때문에 UI가 한 상태에서 다른 상태로 바뀌는 일입니다.
- **권위 상태(authoritative state)**: 참가 여부나 현재 공개 데이터셋처럼 특정 판단에서 최종 기준으로 선택한 서버·데이터 상태입니다. 모든 질문에 하나의 저장소가 항상 권위 있다는 뜻은 아닙니다.
- **낙관적 UI(optimistic UI)**: 서버 확정을 기다리기 전에 성공을 예상해 화면을 먼저 바꾸고 이후 실제 결과와 조정하는 표현 전략입니다.
- **복구 오라클(recovery oracle)**: 결과가 불명확하거나 충돌한 뒤 현재 사실과 이전 작업의 처리 여부를 판정하는 근거와 조회 방법입니다.

상태 이름은 프레임워크가 자동으로 완성해 주는 보편 목록이 아닙니다. 제품의 사용자 행동·서버 계약·데이터 권위·실패 비용에 맞게 정해야 합니다. `isLoading`, `error`, `data` 같은 변수 세 개가 있어도 동시에 모순된 값이 가능하거나 결과 불명·충돌을 표현하지 못하면 상태 계약이 충분하지 않습니다.

## 택배 조회로 이해하기

UI 상태를 택배 조회 화면에 비유할 수 있습니다. “접수”, “이동 중”, “배송 완료”, “주소 확인 필요”는 현재 상황과 다음 행동을 알려 줍니다. 사용자가 배송 요청 버튼을 눌렀다는 사실, 화면에 접수 표시가 나타난 사실, 물류 시스템에 실제 접수된 사실은 서로 다른 증거입니다.

### 비유가 맞는 지점

- 사용자는 내부 구현보다 현재 상태와 다음 행동을 알아야 합니다.
- 화면 표시와 실제 업무 원본의 확정 시점이 다를 수 있습니다.
- 같은 지연도 정상 처리 중인지, 정보가 필요한지, 실패했는지에 따라 다음 행동이 달라집니다.
- 결과가 불명확하면 추측보다 추적 번호 같은 식별자로 권위 기록을 확인해야 합니다.

### 비유가 깨지는 지점

웹 요청은 한 상자가 한 경로로 이동하는 것보다 쉽게 복제되고 거의 동시에 처리될 수 있습니다. 여러 탭과 기기가 같은 상태를 바꿀 수 있고, 응답이 끊겨도 서버 변경은 이미 확정됐을 수 있습니다. 또한 UI 상태에는 입력 중 값·열린 메뉴·키보드 포커스처럼 서버에 저장하지 않는 로컬 상태도 있습니다. 이 비유만으로 HTTP 메서드의 멱등성, 데이터베이스 원자성, 낙관적 갱신이나 접근 가능한 상태 알림을 보장할 수는 없습니다.

## 시스템에서의 위치

모임 참가 흐름을 상태와 증거로 나누면 다음과 같습니다.

```text wrap
서버에서 받은 현재 참가 가능 상태
→ 사용자가 참가 버튼을 누름
→ UI가 submitting 상태와 중복 행동 방지 표시
→ 서버가 인증·인가·모집 상태·정원·중복을 현재 권위 상태에 대조
→ accepted / validation / conflict / authorization / server error 응답
→ UI가 응답 범주와 최신 권위 상태를 화면에 반영
→ 응답 유실이면 결과 불명 상태에서 현재 참가 상태 재조회
→ 사용자에게 확정 결과와 다음 행동을 전달
```

UI가 로딩을 표시하는 일과 서버가 참가를 확정하는 일은 같은 상태 전이가 아닙니다. 서버 응답도 데이터베이스 확정, 전송 성공, 브라우저 수신, 프런트엔드 상태 반영, DOM·픽셀과 사용자 이해를 각각 자동 보장하지 않습니다. [프런트엔드와 백엔드의 경계](../../03-full-stack/frontend-backend-boundary/)에서 서버의 최종 집행을, [브라우저·DOM·렌더링](../browser-dom-rendering/)에서 응답 이후의 증거 표면을 이어서 확인할 수 있습니다.

## 최소 상태를 정상·실패·불명으로 나누세요

| 상태 | 뜻 | 사용자에게 보여 줄 것 | 허용할 행동 | 완료 증거 |
|---|---|---|---|---|
| initial | 아직 조회·변경을 시작하지 않음 | 목적과 시작 조건 | 입력·조회·변경 시작 | 초기 조건과 기본 초점 |
| loading | 읽기 요청을 기다리는 중 | 무엇을 불러오는지, 필요하면 진행 표시 | 취소·다른 안전한 탐색 | 해당 요청과 현재 선택의 연결 |
| empty | 조회는 정상 완료됐고 결과가 0건 | “없음”의 의미와 만들기·조건 변경 | 새 항목·필터 해제 | 성공 응답과 같은 필터의 0건 |
| success | 현재 목적에 맞는 결과가 있음 | 핵심 정보·기준 시점·가능한 다음 행동 | 조회·수정·후속 행동 | 응답·권위 상태·UI 결과 대조 |
| validation | 입력이 계약에 맞지 않음 | 대상 필드·이유·고치는 방법 | 입력 수정·재제출 | 잘못된 입력 보존과 오류 연결 |
| conflict | 요청 형식은 맞지만 현재 업무 상태와 충돌 | 최신 상태·충돌 이유 범주·다시 선택할 행동 | 재조회·대안 선택 | 최신 권위 상태와 거절 뒤 불변조건 |
| error | 실패와 업무 결과·영향 범위가 계약과 근거로 확인됨 | 안전한 오류 범주·확인된 영향·유지된 입력·다음 행동 | 계약상 안전한 재시도·문의·다른 경로 | 오류 출처와 미적용·종결 등 확인된 업무 결과 |
| unknown | 서버 적용 여부를 알 수 없음 | 결과 불명임과 확인 중인 사실 | 권위 상태 조회, 중복 쓰기 보류 | 요청 식별자·현재 상태·이전 결과 대조 |
| retrying | 정한 조건 아래 다시 시도 중 | 대상 작업·횟수 또는 대기 조건 | 취소·상태 조회 | 재시도 정책과 최종 결과 |

`empty`는 오류가 아닙니다. “내 모임 없음”은 정상 조회 결과일 수 있고 다음에 “모임 만들기”를 안내할 수 있습니다. `validation`은 사용자가 고칠 입력을 가리키고, `conflict`는 같은 입력이라도 최신 업무 상태 때문에 더는 허용되지 않는 상황입니다. 모임 정원이 다른 참가자 때문에 찼다면 버튼을 반복하는 것보다 최신 상태와 다른 모임 같은 선택을 보여 줘야 합니다.

`error`와 `unknown`도 다릅니다. 입력·권한·정원 거절이나 확인된 롤백처럼 계약상 변경 미적용과 요청의 종결을 확인했다면 그 결과를 표시할 수 있습니다. 그러나 오류 응답을 받았다는 사실만으로 업무 변경의 실패를 알 수는 없습니다. 데이터베이스 확정 뒤 응답 처리에서 오류가 나거나 중간 서버가 오류를 반환했다면 변경은 이미 적용됐을 수 있습니다. 적용 여부를 모르면 오류 응답이 있어도 `unknown`으로 두고 새 쓰기를 보류합니다. 결과 조회마저 실패하면 불명을 유지합니다. 부분 영향이 가능한 다른 업무는 그 범위와 복구 계약을 별도로 확인하며, 원자적으로 참가를 확정하는 이 모임 사례에 임의의 부분 적용을 가정하지 않습니다.

## 서버 권위 상태와 화면 사본을 구분하세요

브라우저의 UI 상태는 빠른 상호작용을 위한 사본이거나 아직 보내지 않은 입력일 수 있습니다. 참가 여부, 정원, 게시 버전처럼 다른 사용자·탭·기기가 함께 바꾸는 사실은 서버·데이터 경계의 권위 상태에서 다시 확인해야 합니다. 새로고침 뒤 사라지는 표시나 한 탭의 메모리를 업무 원본으로 사용하지 않습니다.

| 질문 | UI 상태가 맡는 일 | 권위 경계가 맡는 일 | 어긋남을 찾는 증거 |
|---|---|---|---|
| 버튼을 누를 수 있나 | 마지막으로 받은 상태로 가능한 행동 안내 | 요청 시점의 권한·업무 규칙 재판정 | 직접 요청·다른 탭·최신 조회 |
| 참가가 확정됐나 | 진행·낙관·확정·거절을 구분해 표시 | 참가 관계·정원·중복 불변조건 확정 | 응답과 현재 자신의 참가 상태 재조회 |
| 대시보드 값이 최신인가 | 현재 공개 버전·신선도·경고 표시 | 승인된 데이터셋 버전과 후보 상태 결정 | 화면 버전·전달 파일·메타데이터 대조 |
| 오류 뒤 무엇이 남나 | 입력과 사용자의 다음 행동 보존 | 변경 미적용·부분 적용·확정 여부 판정 | 안전한 로그·요청 식별자·권위 상태 |

서버 권위가 중요하다고 모든 UI 상태를 서버에 저장할 필요는 없습니다. 열린 메뉴, 현재 탭, 입력 중인 검색어와 키보드 포커스는 보통 로컬 상호작용 상태입니다. 반대로 브라우저에 있다고 모두 임시인 것도 아닙니다. URL의 검색 조건처럼 공유·새로고침·뒤로 가기에 필요한 상태는 URL이나 다른 명시적 계약에 둘 수 있습니다. 상태마다 수명·소유자·복구 경로를 정하세요.

## 낙관적 UI는 확정 표시가 아닙니다

낙관적 UI는 즉각적인 반응이 중요한 행동에서 유용할 수 있습니다. 사용자가 참가 버튼을 누르자마자 카운트를 잠정 변경하거나 항목을 목록에 먼저 보일 수 있습니다. 그러나 다음 네 상태를 하나로 합치지 마세요.

1. **intent**: 사용자가 행동을 요청했습니다.
2. **pending optimistic**: 화면은 예상 결과를 먼저 보여 주지만 서버 확정 전입니다.
3. **confirmed**: 서버와 권위 상태가 요청을 확정했습니다.
4. **rejected 또는 unknown**: 명시적 거절이 왔거나 적용 여부를 알 수 없습니다.

낙관적 표시에는 어떤 값을 임시로 바꿨는지, 새 요청이 겹치면 어떻게 합칠지, 거절 시 무엇을 복원할지, 다른 최신 응답이 왔을 때 어느 결과를 채택할지 정해야 합니다. 삭제·결제·외부 전송처럼 되돌리기 어렵거나 중복 비용이 큰 행동은 빠른 느낌보다 명시적 확인과 권위 결과가 더 중요할 수 있습니다. 낙관적 UI를 모든 행동의 기본값으로 일반화하지 마세요.

단순 롤백만으로 복구되지 않는 경우도 있습니다. 사용자가 낙관적 참가 뒤 다른 화면에서 후속 행동을 했거나, 다른 탭이 최신 상태를 바꿨다면 이전 로컬 스냅샷으로 되돌리면 새 사실을 덮을 수 있습니다. 이때는 최신 권위 상태를 다시 읽고 현재 사용자 의도와 조정해야 합니다.

## 중복 행동과 재시도를 별도로 설계하세요

버튼을 잠시 비활성화하면 같은 탭의 빠른 중복 클릭을 줄일 수 있지만 서버 중복 방지의 최종 증거는 아닙니다. 사용자는 여러 탭·기기·직접 요청을 사용할 수 있고, 네트워크나 중간 구성요소가 재시도할 수도 있습니다. 서버는 업무 키·고유성·현재 상태·요청 식별자 같은 계약으로 허용 효과를 판정해야 합니다.

RFC 9110에서 멱등 메서드는 같은 요청을 여러 번 보낸 의도된 서버 효과가 한 번 보낸 것과 같다는 HTTP 의미입니다. 모든 `POST`가 자동으로 한 번만 처리된다는 뜻도, 응답이 항상 같다는 뜻도 아닙니다. 비멱등 요청은 원래 요청이 적용되지 않았음을 알거나 해당 작업의 의미가 멱등임을 아는 수단 없이 자동 재시도하지 말아야 한다는 경계를 참고해, 실제 API별 중복·재시도 계약을 정합니다.

| 상황 | 화면 방어 | 서버·데이터 방어 | 복구 확인 |
|---|---|---|---|
| 빠른 두 번 클릭 | pending 동안 같은 행동 비활성화·진행 표시 | 중복 참가 고유성·현재 상태 확인 | 자신의 참가 관계 1건과 카운트 |
| 응답 유실 뒤 재시도 | 결과 불명 표시, 즉시 중복 쓰기 보류 | 요청 식별·업무 키 또는 현재 상태 판정 | 처리 결과 조회 endpoint·권위 상태 |
| 오래된 응답 도착 | 현재 선택·요청 버전과 맞는 응답만 채택 | 읽기 응답에 기준 시점·버전 제공 가능 | 화면 선택·응답 버전·DOM 대조 |
| 여러 탭 동시 변경 | 포커스 복귀·새로고침·충돌 안내 | 동시성·불변조건·권한 재판정 | 최신 상태 재조회와 거절 뒤 데이터 |

## 복구 오라클을 먼저 정하세요

복구 오라클은 “다시 눌러 본다”가 아니라 실패 뒤 무엇이 사실인지 판정하는 근거입니다. 모임 참가라면 `현재 인증된 사용자의 이 모임 참가 관계`, `현재 확정 참가 수`, `이전 요청 식별자의 처리 결과`가 후보가 될 수 있습니다. 대시보드라면 `current_published_dataset_version`, `last_normal_dataset_version`, `refresh_candidate_status`와 지연 사유가 복구 판단을 돕습니다.

좋은 복구 오라클은 다음 질문에 답합니다.

- 어떤 주체·대상·작업의 결과를 확인하나요?
- 어느 저장소·API·버전이 이 판단에서 권위 있나요?
- 이전 요청과 현재 상태를 어떤 안전한 식별자로 연결하나요?
- 미적용, 적용, 거절, 처리 중, 알 수 없음을 구분하나요?
- 조회가 실패하면 사용자는 무엇을 보며 언제 중단하거나 문의하나요?
- 화면 표시·응답·데이터가 모순되면 어느 쪽을 다시 확인하나요?

로그 한 줄이나 토스트 문구만으로 업무 결과를 판정하지 않습니다. 로그는 누락·중복·지연될 수 있고 사용자에게 보여 줄 권한 범위와 다릅니다. 권위 상태 조회도 실제 API·데이터 계약과 권한 아래에서 안전하게 제공해야 합니다.

## 상태 전이를 표로 쓰세요

모임 참가의 예시는 다음처럼 쓸 수 있습니다.

| 현재 상태 | 사건 | 다음 상태 | 화면 결과 | 서버·데이터 판정 | 실패·복구 |
|---|---|---|---|---|---|
| eligible | 참가 클릭 | submitting | 버튼 진행 중, 중복 클릭 감소 | 요청 수신 전 | 취소 가능 범위 표시 |
| submitting | 성공 응답+취소되지 않은 모임의 최신 참가 상태 | confirmed | 현재 참가 상태와 자기 취소 행동 | 모임 상태와 참가 관계·정원 확인 | 화면·권위 상태 대조 |
| submitting | 입력 거절 | validation | 해당 입력과 이유 연결 | 변경 없음 | 입력 보존·수정 |
| submitting | 정원·중복 충돌 | conflict | 최신 상태와 대안 | 거절·불변조건 유지 | 재조회·다른 행동 |
| submitting | 계약상 미적용·종결이 확인된 오류 | error | 확인된 영향·안전한 재시도 조건 | 변경 미적용과 요청 종결 확인 | API 계약에 따라 재시도 조건 확인 |
| submitting | 연결 종료·응답 유실 또는 적용 여부를 모르는 오류 응답 | unknown | 결과 불명과 확인 중 표시 | 적용 여부 미확인 | 자신의 참가 상태·요청 결과 조회 |
| unknown | 취소되지 않은 모임의 현재 참가 확인 | confirmed | 현재 참가 상태 표시 | 모임 상태와 현재 참가 관계 확인; 특정 요청의 적용 여부는 별도 처리 결과로 판정 | 중복 쓰기 없음 |
| submitting / unknown / confirmed | 권위 조회에서 모임 취소 확인 | event-cancelled | 모임 취소를 우선 안내하고 참가 기록은 이력으로 표시 | event.cancelled가 registration.confirmed보다 우선 | 새 참가 금지, 남은 confirmed의 자기 취소는 계약상 허용 |
| unknown | 현재 미참가와 안전한 재시도 조건 확인 | eligible | 계약에 따라 다시 시도 가능 | 이전 요청의 종결·미적용 또는 안전한 멱등 재시도 조건 확인 | API 계약에 따른 요청 식별자 유지·발급 정책 |

현재 참가 여부는 조회한 시점의 상태이지 특정 이전 요청의 처리 결과와 같지 않습니다. 이전 요청이 뒤늦게 확정되거나 다른 탭에서 참가·취소했을 수 있으므로, 요청 식별자와 연결된 처리 결과 또는 API가 보장하는 멱등·중복 방지 계약으로 재시도 조건을 확인합니다. 이 근거를 조회하지 못하거나 안전성을 판정할 수 없으면 `unknown`을 유지하고 새 쓰기를 보류합니다.

현재 참가의 유효성은 모임 상태와 자신의 참가 관계를 함께 읽어 판정합니다. `open + confirmed`와 `closed + confirmed`는 현재 참가를 표시하지만, `closed`는 신규 참가를 막는 모집 마감이지 모임 취소가 아닙니다. `cancelled + confirmed`는 모임 취소와 보존된 참가 이력을, `cancelled + cancelled`는 모임 취소와 자신의 참가 취소를 구분해 표시합니다. 취소된 모임에서 남은 자신의 `confirmed`를 `cancelled`로 바꾸는 행동은 허용하되 재참가는 허용하지 않습니다. 모임 취소를 확인했다는 사실도 특정 이전 요청의 적용 여부를 대신 증명하지 않습니다.

상태 전이표는 코드 구현을 자동으로 증명하지 않습니다. 각 행의 이벤트를 재현하고 응답·현재 상태·DOM·픽셀·키보드 흐름과 데이터 오라클을 확인해야 합니다. 그래도 전이표가 있으면 “오류 처리” 같은 모호한 요청을 어떤 조건·결과·증거가 필요한지 바꿀 수 있습니다.

## 접근 가능한 상태 피드백

로딩·성공·오류와 충돌은 색상과 애니메이션만으로 전달하지 않습니다. 현재 상태 이름, 영향을 받는 대상, 다음 행동을 텍스트로 보여 줍니다. WCAG의 상태 메시지는 문맥을 바꾸지 않고 작업의 결과·진행·대기·오류 등을 알려 주는 내용이며, 해당 메시지는 포커스를 옮기지 않아도 보조 기술이 제시할 수 있도록 역할이나 속성으로 프로그램적으로 식별돼야 합니다. 검색 결과 목록 자체와 “검색 중”, “결과 0건” 같은 상태 메시지는 구분합니다. 모든 DOM 변화를 즉시 읽게 하거나 모든 메시지에 같은 강도의 알림을 붙이지 말고, 목적에 맞는 전달 방식과 실제 읽기 결과를 확인합니다. 대화상자나 오류 요약으로 문맥·포커스를 바꾸는 설계는 별도 포커스 계약으로 검증합니다.

입력 검증 오류는 해당 입력과 프로그램적으로 연결하고 잘못된 값을 가능한 한 보존합니다. 오류 요약으로 포커스를 옮겼다면 어떤 입력으로 돌아갈지 키보드 경로를 제공합니다. 재시도 버튼은 “다시 시도”만 반복하지 말고 무엇을 다시 수행하는지 이름에서 알 수 있게 하세요. 자세한 기준은 [접근성과 반응형 설계](../accessibility-responsive-design/)에서 확인합니다.

## 두 사례의 상태 계약

### 모임 참가 웹앱

- 읽기 상태: 초기·로딩·모임 없음·목록 성공·조회 오류를 구분합니다.
- 쓰기 상태: 참가 가능·제출 중·확정·입력 오류·권한 거절·정원/중복 충돌·서버 오류·결과 불명을 구분합니다.
- 권위 원본: 인증된 자신의 참가 관계와 현재 모임 상태·정원은 서버·데이터 경계에서 판정합니다.
- 중복 방어: 화면 비활성화는 편의이고 서버의 고유성·동시성 검사가 최종선입니다.
- 복구 오라클: 응답 유실 뒤 자신의 현재 참가 상태와 필요하면 요청 처리 결과를 조회합니다.

### 교육용 주가 대시보드

- 읽기 상태: fixture 로딩·선택 결과 없음·성공·계약 오류·전달 오류를 구분합니다.
- 값 상태: `valid`, `warning`, `blocked`, `review_required`를 화면 로딩 상태와 혼합하지 않습니다.
- 신선도 상태: `current`, `stale`, `unknown`은 값 품질과 다른 차원으로 이름과 이유를 표시합니다.
- 권위 원본: 현재 공개 데이터셋 버전과 마지막 정상 버전, 후보 상태를 전달 메타데이터에서 확인합니다.
- 복구 오라클: 실패 후보로 정상 화면을 덮지 않고 현재 공개·마지막 정상 버전과 지연 이유를 대조합니다.

이 대시보드 값은 `EDU-FIXTURE`라는 교육용 가상 데이터입니다. 상태 계약이 완전해도 실제 시세·권리·최신성·투자 판단을 증명하지 않습니다.

## 대표 실패와 복구

### 로딩이 끝나지 않습니다

성공·오류·취소·시간 초과 전이 중 하나가 빠졌거나 오래된 요청이 현재 상태를 잡고 있을 수 있습니다. 현재 선택과 요청 식별자를 연결하고 모든 종료 경로에서 pending 상태가 해제되는지 재현하세요. spinner를 강제로 숨기는 것은 요청 결과와 권위 상태를 복구한 것이 아닙니다.

### 빈 결과와 오류가 같은 화면입니다

정상 0건과 요청 실패를 같은 `data.length === 0` 분기로 처리하면 사용자는 조건을 바꿀지 재시도할지 모릅니다. 응답 성공 여부와 결과 수를 분리하고, empty에는 새로 만들기·필터 해제, error에는 안전한 재시도·상태 설명을 제공합니다.

### 오래된 응답이 최신 선택을 덮습니다

사용자가 기간 A를 선택한 뒤 B로 바꿨는데 A 응답이 늦게 오면 화면과 필터가 어긋날 수 있습니다. 요청 취소가 가능한지 검토하고, 최소한 응답이 현재 선택·요청 버전과 일치할 때만 채택하세요. Network 순서, 현재 선택, DOM의 표시 버전을 함께 확인합니다.

### 낙관적 성공이 서버 거절 뒤 남습니다

정원 충돌이 왔는데 화면 카운트와 버튼만 성공 상태로 남으면 사용자는 참가했다고 믿습니다. pending·confirmed를 구분하고 명시적 거절에서는 최신 권위 상태로 조정하며 충돌 이유와 다음 행동을 표시합니다.

### 결과 불명에서 무조건 재시도합니다

연결이 끊겼다는 사실은 서버 미적용의 증거가 아닙니다. 같은 쓰기를 반복하기 전에 자신의 참가 상태나 요청 처리 결과를 조회하고, API의 멱등·중복 계약을 확인하세요. 조회도 실패하면 unknown을 숨기지 말고 중단·문의 경로를 제공합니다.

### 오류 메시지가 내부 정보만 보여 줍니다

stack trace나 데이터베이스 오류를 사용자에게 그대로 노출하면 복구에 도움이 되지 않고 민감 정보가 새어 나갈 수 있습니다. 사용자에게는 안전한 범주·영향·다음 행동과 상관 식별자만 필요한 범위로 제공하고, 상세 진단은 접근 통제된 로그에 남깁니다.

다음처럼 상태·전이·오라클을 포함한 읽기 전용 검토를 먼저 요청하세요.

```text wrap
이 기능의 UI 상태와 사용자 경험을 읽기 전용으로 검토하라.
initial, loading, empty, success, validation, conflict, error, unknown, retrying 상태와 각 상태로 들어오고 나가는 사건을 전이표로 작성하라.
브라우저 로컬 상태, URL 상태, 서버 응답 사본, 권위 상태를 구분하고 각 상태의 소유자·수명·새로고침·여러 탭·복구 경로를 표시하라.
낙관적 UI의 intent/pending/confirmed/rejected/unknown, 중복 클릭·오래된 응답·응답 유실·동시 요청을 점검하라.
각 실패 뒤 사용자가 볼 문구·허용 행동·키보드 포커스와 서버·데이터 복구 오라클을 적어라.
화면 비활성화·HTTP 200·토스트·로그·자동 테스트 하나를 권위 상태나 사용자 완료의 전체 증거로 사용하지 마라.
실제 API·데이터·프레임워크에서 확인하지 못한 멱등성·동시성·재시도 동작은 미확인으로 남기고 파일은 수정하지 마라.
```

AI가 만든 상태 목록은 현재 구현과 서버 계약을 확인하기 전까지 가설입니다. 실제 요청·응답, DOM·픽셀, 키보드 흐름과 권위 상태를 대조하고, 실패 상태를 의도적으로 재현한 뒤에만 수용하세요.

## 확인 체크리스트

- [ ] initial·loading·empty·success·validation·conflict·error·unknown·retrying을 필요한 범위에서 구분했습니다.
- [ ] 각 상태로 들어오는 사건, 나가는 행동과 종료 조건을 정했습니다.
- [ ] 빈 결과와 오류, 입력 검증과 업무 충돌, 명시적 실패와 결과 불명을 분리했습니다.
- [ ] UI 사본과 서버·데이터 권위 상태의 책임과 재조회 경로를 정했습니다.
- [ ] 로컬·URL·서버 상태의 소유자·수명·새로고침·여러 탭 동작을 확인했습니다.
- [ ] 낙관적 표시의 pending·confirmed·rejected·unknown과 조정 방법을 정했습니다.
- [ ] 중복 클릭 방어와 서버의 중복·멱등·동시성 판정을 구분했습니다.
- [ ] 오래된 응답이 최신 선택을 덮지 않도록 요청·선택 버전을 연결했습니다.
- [ ] 응답 유실 뒤 같은 쓰기를 반복하기 전 사용할 복구 오라클이 있습니다.
- [ ] 오류에서 입력과 안전한 문맥을 보존하고 다음 행동·중단 조건을 설명합니다.
- [ ] 색상 외 상태 문구, 프로그램적 상태 전달과 키보드 포커스를 확인했습니다.
- [ ] 응답·권위 상태·DOM·픽셀·사용자 이해를 서로 다른 완료 증거로 확인했습니다.
- [ ] 토큰·쿠키·개인정보·내부 stack trace를 사용자 문구와 검증 기록에 노출하지 않습니다.

|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |

그다음 다음 실패를 하나씩 가정하세요: 빠른 두 번 클릭, 다른 탭의 동시 변경, 오래된 응답, 명시적 충돌, 서버 적용 뒤 응답 유실. 각 경우 화면 표시만 되돌리면 충분한지, 최신 권위 상태를 어떻게 확인할지 적으세요.

RFC 9110은 HTTP 메서드 의미와 자동 재시도 주의의 범위를 제공하지만 애플리케이션별 `POST` 중복 방지·요청 식별자·업무 오라클을 자동으로 정하지 않습니다. WCAG는 오류·상태의 접근 가능한 전달을 뒷받침하지만 서버 권위·동시성·데이터 정확성까지 보장하지 않습니다. 모임·대시보드 상태는 저장소의 교육 계약이며 실제 서비스·시장 데이터·배포 성공의 증거가 아닙니다.

출처의 확인일·적용 범위와 제품 일반화 금지선은 저장소의 `research/source-map.md`에서 관리합니다. PBSG-003은 이 장뿐 아니라 접근성·반응형, ADR과 대시보드의 접근 가능한 상태 계약 전체를 직접 대조한 뒤 `confirmed`로 전환했습니다.
