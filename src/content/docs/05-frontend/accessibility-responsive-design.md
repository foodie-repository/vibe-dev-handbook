## 먼저 결론

접근성은 장애를 포함해 서로 다른 감각·운동·인지 조건과 보조 기술을 사용하는 사람이 콘텐츠와 기능을 인지하고 조작하고 이해할 수 있게 만드는 품질입니다. 반응형 설계는 화면 크기·확대·방향·입력 환경이 달라져도 정보 우선순위와 기능을 유지하도록 표현 구조를 적응시키는 방법입니다. 둘은 겹치지만 같은 말이 아닙니다.

모바일 폭에서 카드가 한 열로 잘 쌓였어도 키보드로 참가 버튼에 도달하지 못하고 버튼의 이름을 보조 기술이 읽지 못하면 접근 가능한 화면이 아닙니다. 반대로 의미 있는 HTML과 레이블이 있어도 확대했을 때 본문이 화면 밖으로 잘리고 고정 헤더가 포커스를 덮으면 사용할 수 없습니다. 색과 모양이 예쁜 한 장의 스크린샷, 자동 검사 0건, 특정 화면 폭 한 번 통과 중 어느 것도 전체 완료 증거가 되지 않습니다.

## 왜 필요한가

AI에게 “접근성 있게 반응형으로 만들어 주세요”라고만 요청하면 `aria-label` 몇 개와 미디어 쿼리가 추가될 수 있습니다. 그러나 핵심 흐름의 키보드 순서, 포커스 이동, 입력 이름과 오류의 연결, 색상 없이 상태를 읽는 방법, 확대 뒤 리플로, 차트의 동등한 정보, 서버 실패 뒤 복구 행동은 여전히 빠질 수 있습니다. 속성이 많아졌다는 사실과 사람이 작업을 끝낼 수 있다는 사실은 다릅니다.

접근성은 특정 사용자를 위한 부가 기능만도 아닙니다. 명확한 제목·레이블·상태, 키보드 조작, 확대 가능한 글, 예측 가능한 오류 복구는 일시적인 부상, 밝은 야외, 작은 화면, 느린 네트워크처럼 누구나 만날 수 있는 조건에서도 도움이 됩니다. 다만 “모두에게 편리하다”는 말만으로 장애 당사자에게 필요한 구체 기준과 실제 검증을 생략해서는 안 됩니다.

## 한 문장 정의

- **접근성(accessibility)**: 다양한 사용자가 콘텐츠와 기능을 인지·조작·이해하고, 현재 기술과 보조 기술에서 견고하게 사용할 수 있도록 설계하고 검증하는 품질입니다.
- **반응형 설계(responsive design)**: 뷰포트·확대·방향·입력 조건이 바뀔 때 정보와 기능의 우선순위를 보존하면서 배치와 표현을 적응시키는 설계 방법입니다.
- **의미 있는 HTML(semantic HTML)**: 모양이 아니라 콘텐츠와 조작의 역할에 맞는 HTML 요소와 구조를 선택하는 일입니다. 브라우저와 보조 기술이 제목·목록·버튼·입력 같은 관계를 해석하는 출발점입니다.
- **접근 가능한 이름(accessible name)**: 링크·버튼·입력 같은 사용자 인터페이스 구성요소를 보조 기술이 식별할 때 사용하는 이름입니다. 보이는 레이블과 일치하거나 그 문구를 포함해야 사용자가 같은 대상을 찾기 쉽습니다.
- **리플로(reflow)**: 화면이 좁아지거나 콘텐츠가 확대될 때 정보·기능을 잃지 않고 읽기 흐름에 맞춰 재배치되는 동작입니다.

접근성은 체크리스트 하나로 모든 장애와 사용 맥락을 완전히 보장하는 상태가 아닙니다. WCAG 성공 기준은 중요한 공통 기준이지만 실제 사용자 목적, 사용 기술, 콘텐츠 종류와 법적 요구는 별도로 확인해야 합니다. 반응형도 특정 기기 이름별 픽셀을 맞추는 작업이 아니라 조건 변화에서 중요한 정보와 행동을 보존하는 설계입니다.

## 건물의 출입구로 이해하기

접근성을 건물의 출입구·안내 표지·엘리베이터·비상 경로에, 반응형 설계를 같은 안내를 좁은 복도와 넓은 로비에 맞게 재배치하는 일에 비유할 수 있습니다. 입구가 보이고 표지가 읽히며 목적지까지 이어져야 실제로 이용할 수 있고, 공간이 달라지면 표지와 통로의 배치를 조정해야 합니다.

### 비유가 맞는 지점

- 사람마다 사용하는 경로와 도구가 다르므로 하나의 입력 방식만 가정하면 배제됩니다.
- 입구 하나가 열렸다는 사실보다 목적 행동의 시작부터 완료·복구까지 이어지는 경로가 중요합니다.
- 공간이 좁아져도 중요한 안내와 기능을 없애지 않고 우선순위를 다시 배치해야 합니다.
- 표지의 문구, 현재 위치와 다음 행동이 분명해야 스스로 이동할 수 있습니다.

### 비유가 깨지는 지점

웹 인터페이스는 물리적 건물처럼 고정되지 않습니다. 같은 DOM도 CSS, JavaScript 상태, 브라우저 확대, 입력 장치와 보조 기술에 따라 다르게 표현되고, 사용자가 글자 크기·대비·동작 감소 같은 환경 설정을 바꿀 수 있습니다. 또한 물리적 경사로 하나처럼 접근성 기능을 따로 붙이는 방식보다 올바른 HTML 요소·이름·상태·키보드 동작을 기본 구조에 넣는 편이 중요합니다. 이 비유만으로 WCAG 적합성이나 실제 보조 기술 호환을 판정할 수는 없습니다.

## 시스템에서의 위치

접근성과 반응형 설계는 CSS 마지막 단계가 아니라 요구에서 운영까지 이어집니다.

```text
사용자 목적과 사용 조건
→ 콘텐츠 구조와 정보 우선순위
→ 의미 있는 HTML과 접근 가능한 이름
→ 키보드·포커스·입력·상태 전이
→ 색·대비·크기·반응형 배치·리플로
→ 브라우저 DOM과 실제 픽셀
→ 키보드·확대·보조 기술·사용자 흐름 검증
→ 실패 수정과 회귀 확인
```

요구사항에는 “접근성 지원” 같은 추상 문구보다 완료할 행동과 조건을 적습니다. 예를 들어 “모임 목록에서 자신의 참가를 키보드만으로 취소하고, 확인 대화상자가 열린 뒤 포커스가 제목 또는 첫 조작 대상으로 이동하며, 서버 거절 시 오류와 재시도 방법을 읽을 수 있다”처럼 씁니다. 설계는 구조·이름·상태·포커스 책임을 정하고, 구현은 HTML·CSS·JavaScript와 서버 오류 계약에 반영하며, 검증은 자동 검사와 실제 조작을 나눠 수행합니다.

## 접근성의 여덟 가지 기본 질문

### 1. 의미 구조가 화면 모양 없이도 남나요

제목에는 제목 요소, 순서 없는 목록에는 목록, 이동에는 링크, 실행에는 버튼, 입력에는 해당 입력 유형과 레이블을 사용합니다. 클릭 이벤트가 붙은 `div`를 버튼처럼 꾸미면 기본 키보드 동작·역할·상태를 다시 구현해야 하고 작은 누락이 쌓입니다. 네이티브 요소가 목적에 맞으면 먼저 사용하고, 복합 위젯이 정말 필요할 때만 명시적 역할과 키보드 패턴을 추가합니다.

시각적 크기만으로 제목 계층을 만들거나 빈 줄과 위치만으로 그룹을 표현하지 마세요. CSS를 끄거나 DOM의 역할을 살폈을 때도 페이지 제목, 영역, 목록과 폼의 관계가 설명돼야 합니다. 의미 구조는 보기 좋은 픽셀을 없애는 것이 아니라 같은 정보를 다른 방식으로 탐색할 수 있게 하는 기반입니다.

### 2. 키보드만으로 핵심 흐름을 완료하나요

`Tab`과 `Shift+Tab`으로 조작 대상에 도달하고, Enter·Space·화살표·Escape 같은 키가 해당 구성요소의 관례에 맞게 동작하는지 확인합니다. 마우스 포인터를 올려야만 보이는 메뉴나 드래그만 가능한 정렬은 키보드 대안을 제공해야 합니다. 모든 요소에 `tabindex="0"`을 붙이는 것은 해결이 아닙니다. 읽기 전용 텍스트까지 불필요하게 포커스 순서에 넣으면 오히려 탐색 비용이 커집니다.

DOM 순서와 시각 순서가 크게 다르면 키보드 사용자가 화면에서 포커스를 잃기 쉽습니다. 양수 `tabindex`로 순서를 억지로 고정하기보다 DOM과 시각 구조를 같은 논리 순서로 맞추는 편을 우선합니다. 모바일·데스크톱에서 재배치될 때도 중요한 행동의 논리 순서가 유지돼야 합니다.

### 3. 포커스의 현재 위치와 이동 이유가 보이나요

포커스 표시를 지우지 말고 배경과 구분되는 시각 신호를 제공합니다. 대화상자를 열거나 오류 요약으로 이동하거나 비동기 갱신 뒤 내용을 바꿀 때는 포커스를 어디로 옮길지 정합니다. 닫은 뒤에는 가능하면 대화상자를 연 조작 대상으로 돌아가야 합니다. 로딩 때문에 대상이 사라질 때는 사용자가 길을 잃지 않을 안정적인 위치를 제공해야 합니다.

고정 헤더·쿠키 배너·하단 도구막대가 포커스 대상을 완전히 덮지 않는지도 확대 상태에서 확인합니다. 화면에 보이는 포커스 테두리와 보조 기술이 인식하는 현재 대상이 같은지 실제 키보드 흐름으로 확인하세요.

### 4. 보이는 레이블과 접근 가능한 이름이 맞나요

아이콘만 있는 버튼은 목적을 설명하는 접근 가능한 이름이 필요합니다. 입력은 자리표시자만으로 이름을 대신하지 말고 지속해서 보이는 레이블과 연결합니다. 화면에 “참가 취소”라고 보이는데 보조 기술 이름이 “삭제”라면 음성 입력 사용자와 화면 낭독 사용자 모두 같은 대상을 찾기 어렵습니다. 보이는 문구가 있으면 접근 가능한 이름에 그 문구를 포함하는 것을 기본으로 합니다.

ARIA는 의미 없는 요소를 자동으로 완성하는 장식이 아닙니다. 네이티브 HTML의 역할과 상태를 사용할 수 있으면 먼저 사용하고, `aria-label`, `aria-labelledby`, `aria-describedby`, `aria-live`는 실제 이름·설명·상태 전달 책임이 있을 때 적용합니다. 속성이 존재하는지만 보지 말고 브라우저 접근성 트리나 보조 기술이 읽는 결과를 확인합니다.

### 5. 색상 없이도 상태와 행동을 구분하나요

성공을 초록색, 오류를 빨간색, 선택을 파란색만으로 표현하지 않습니다. 텍스트, 아이콘 모양, 패턴, 위치와 프로그램적 상태를 함께 사용합니다. 텍스트와 중요한 조작 요소의 대비는 현행 WCAG 기준에 대조하되, 비활성·로고·장식 등 예외 범위와 큰 텍스트 판정도 정확히 구분합니다. 색상 표본 하나의 대비 통과가 포커스·아이콘 경계·상태 전체의 사용성을 증명하지는 않습니다.

다크 테마, 고대비 설정, 링크의 방문·호버·포커스 상태에서도 다시 확인합니다. 배경 이미지나 반투명 오버레이 위의 글자는 실제 렌더된 조합이 달라질 수 있으므로 선언한 색상 토큰만으로 판정하지 않습니다.

### 6. 비텍스트 콘텐츠의 목적을 다른 방식으로 얻나요

정보를 전달하는 이미지에는 문맥에 맞는 텍스트 대안을 제공합니다. 장식 이미지는 보조 기술의 탐색을 방해하지 않도록 빈 대체 텍스트 등 적절한 방법으로 제외합니다. 이미지 안에 글자를 넣었다면 그 글자와 의미를 다른 방식으로도 제공해야 합니다. “차트 이미지”처럼 모양만 말하는 대체 텍스트는 데이터의 핵심 결론과 상태를 전달하지 못합니다.

교육용 주가 대시보드에서는 차트와 표가 같은 선택 결과를 사용하고, 대상·값·단위·거래일·가격 기준·값 상태·신선도 상태와 이유를 동등한 표 또는 텍스트 요약에서 확인할 수 있어야 합니다. 차트의 모든 픽셀을 문장으로 반복할 필요는 없지만, 차트만 보지 못하면 중요한 판단 정보를 잃어서는 안 됩니다. 대체 텍스트 하나가 키보드 조작 가능한 필터와 프로그램적 상태 알림까지 대신하지도 않습니다.

### 7. 확대와 좁은 뷰포트에서 정보·기능이 보존되나요

글자를 200%까지 확대할 수 있는지, 320 CSS 픽셀 상당의 폭에서 일반 읽기 콘텐츠가 정보·기능 손실과 양방향 스크롤 없이 리플로되는지 확인합니다. WCAG 리플로 기준은 표·지도·다이어그램처럼 의미상 2차원 배치가 필요한 일부 콘텐츠에 예외를 두지만, 그 예외가 페이지의 제목·본문·검색·페이지 이동까지 넓어지는 것은 아닙니다. 표와 코드는 필요한 경우 자체 스크롤 컨테이너를 사용하고, 페이지의 나머지 문단과 조작은 뷰포트 안에 유지합니다.

반응형 설계는 데스크톱 화면을 비율로 줄이는 일이 아닙니다. 여러 열을 한 열로 바꾸고, 보조 정보를 접을 수 있게 하며, 핵심 행동을 먼저 배치하되 숨긴 기능에도 이름 있는 조작과 키보드 경로를 제공합니다. 작은 화면에서 삭제한 정보가 사용자 판단에 필요한지, 접힌 메뉴를 열지 못하는 입력 방식이 있는지 확인하세요.

### 8. 동적 상태가 보이고 읽히며 복구 가능한가요

로딩·빈 결과·성공·입력 오류·충돌·서버 오류·재시도를 화면 상태로 구분합니다. WCAG의 상태 메시지는 문맥을 바꾸지 않고 작업의 결과·진행·대기·오류 등을 알려 주는 내용입니다. 해당 메시지는 포커스를 옮기지 않아도 보조 기술이 제시할 수 있도록 역할이나 속성으로 프로그램적으로 식별돼야 합니다. 검색 결과 목록 자체와 “검색 중”, “결과 0건” 같은 메시지는 구분합니다. 모든 DOM 변화를 알리거나 모든 메시지에 긴급 알림을 적용하라는 뜻은 아닙니다. 목적에 맞는 전달 방식과 실제 읽기 결과를 확인하고, 대화상자나 오류 요약으로 문맥·포커스를 바꾸는 경우에는 그 포커스 계약을 따로 검증합니다.

서버가 참가 요청을 거절하면 색상과 토스트만 잠깐 보여 주지 말고 오류의 대상·이유 범주와 다시 할 행동을 연결합니다. 응답이 끊겨 결과를 모르면 같은 쓰기를 무조건 반복하기보다 권위 있는 참가 상태를 재조회하고, 화면의 낙관적 표시를 확정 상태와 구분합니다. 접근 가능한 오류 문구가 있어도 서버 권한·중복·정원 규칙이 안전하다는 뜻은 아니며, 서버가 안전하게 거절해도 사용자가 복구 방법을 알 수 없으면 사용자 흐름은 끝나지 않았습니다.

## 두 사례로 확인하기

### 모임 참가 웹앱

모임 카드는 제목 요소와 목록 구조를 유지하고, 상세 이동은 링크, 참가·취소는 버튼으로 제공합니다. 참가 버튼의 보이는 문구와 접근 가능한 이름을 일치시키고, 진행 중에는 중복 실행을 줄이되 서버의 최종 중복·정원 검사를 대신한다고 주장하지 않습니다. 성공하면 확정된 참가 상태와 다음 행동을, 충돌이나 결과 불명에서는 재조회·재시도 경로를 텍스트로 보여 줍니다.

모바일에서는 제목·일시·장소·모집 상태·핵심 행동을 먼저 읽게 하고 보조 메타데이터를 뒤로 배치할 수 있습니다. 그러나 참가 취소를 화면 폭 때문에 없애거나 메뉴 안에 넣고 키보드 포커스가 열리지 않게 해서는 안 됩니다. 대화상자·오류·새로고침 뒤의 포커스와 서버의 권위 상태를 각각 확인합니다.

### 교육용 주가 대시보드

상품·기간 선택에는 지속적인 레이블을 연결하고 키보드만으로 값을 바꿀 수 있어야 합니다. 선택 결과는 표·차트·요약이 같은 데이터 버전과 필터를 사용하고, 색상 외에 `warning`, `blocked`, `review_required`, `stale` 같은 상태 이름과 이유를 읽을 수 있게 합니다. 차트의 핵심 값과 상태는 표 또는 텍스트 요약으로도 접근할 수 있어야 합니다.

좁은 화면에서는 표만 자체 가로 스크롤을 허용하고 페이지 제목·필터·상태·페이지 이동은 뷰포트 안에 리플로되는지 확인합니다. 차트 SVG의 대체 텍스트 존재만으로 동등 정보나 작은 글자 판독을 증명하지 않습니다. 이 사례의 현재 값은 `EDU-FIXTURE`이며 실제 시장 데이터·권리·투자 판단의 근거가 아닙니다.

## 자동 검사와 실제 검증을 분리하세요

| 검증 층 | 확인하는 것 | 놓칠 수 있는 것 | 남길 증거 |
|---|---|---|---|
| 정적·자동 검사 | 누락된 대체 텍스트, 일부 이름·역할·대비·문법 규칙 | 이름의 문맥 적합성, 포커스 흐름, 실제 작업 성공 | 도구·버전·대상 URL·규칙·오류 수와 원본 결과 |
| DOM·접근성 구조 | 제목·영역·레이블·이름·역할·상태의 프로그램적 관계 | 실제 픽셀 잘림, 입력 장치와 보조 기술별 사용성 | 대상 요소와 계산된 이름·역할·설명·상태 |
| 키보드 흐름 | 도달 가능성, 논리 순서, 포커스 표시·복귀, 대화상자·메뉴 동작 | 화면 낭독 문구와 음성 입력 일치 | 시작 조건, 누른 키, 기대·실제 포커스와 결과 |
| 확대·반응형 화면 | 200% 텍스트 확대, 320 CSS 픽셀 상당 리플로, 잘림·겹침·스크롤 범위 | 보조 기술 읽기 순서와 서버 상태 정확성 | 뷰포트·확대율·테마·스크린샷·overflow 측정 |
| 보조 기술·사용자 흐름 | 실제 이름·상태 알림·탐색·완료와 복구 가능성 | 다른 브라우저·OS·장애 맥락 전체 | 브라우저·OS·보조 기술 버전, 과업, 관찰 결과와 미확인 범위 |
| 서버·데이터 증거 | 권위 상태, 거절·중복·충돌·응답 유실 뒤 복구 | 사용자가 결과를 이해했는지 | 요청·응답, 안전한 로그, 데이터 재조회와 UI 상태 대조 |

한 층의 성공을 다른 층의 증거로 바꾸지 마세요. 자동 검사 0건은 도구가 아는 규칙에서 발견한 문제가 없다는 뜻이고, 키보드 한 흐름 통과는 그 브라우저·경로의 관찰입니다. WCAG 적합을 주장하려면 적용 기준·수준·전체 페이지와 완전한 프로세스 범위·접근성 지원 기술 등 해당 적합성 요구를 별도로 평가해야 합니다.

## 대표 실패와 복구

### 모든 것을 ARIA로 고칩니다

클릭 가능한 `div`에 역할과 키 이벤트를 계속 덧붙이면 네이티브 버튼이 이미 제공하는 동작을 불완전하게 복제하기 쉽습니다. 목적에 맞는 HTML 요소로 돌아갈 수 있는지 먼저 확인하고, 복합 위젯만 필요한 역할·상태·키보드 패턴을 적용한 뒤 계산된 접근 가능한 이름과 실제 조작을 다시 검사합니다.

### 포커스 표시를 디자인 때문에 지웁니다

마우스로는 화면이 깔끔해 보여도 키보드 사용자는 현재 위치를 잃습니다. 기본 포커스 표시를 제거하기 전에 충분히 구분되는 대체 스타일을 만들고 라이트·다크 테마와 확대 상태, 고정 요소에 가리지 않는지를 확인합니다.

### 모바일에서 내용을 숨기기만 합니다

작은 화면에 맞추려고 오류 상세·데이터 상태·핵심 행동을 없애면 정보 우선순위를 조정한 것이 아니라 기능을 잃은 것입니다. 필수 정보와 보조 정보를 구분하고 보조 정보는 이름 있는 펼침 조작으로 제공하며, 키보드·터치·확대에서 열고 닫는 흐름을 검증합니다.

### 화면 폭만 줄여 반응형을 통과시킵니다

390px 스크린샷이 좋아 보여도 200% 확대와 320 CSS 픽셀 상당 리플로에서 본문이 잘리거나 고정 요소가 포커스를 덮을 수 있습니다. 뷰포트 폭·브라우저 확대·글자 크기 변경을 별도 조건으로 검사하고, 표·코드·그림의 내부 스크롤과 페이지 전체 overflow를 구분합니다.

### 차트에 대체 텍스트 한 줄만 붙입니다

“주가 차트”라는 대체 텍스트는 대상·값·단위·기간·상태·사유를 제공하지 않습니다. 핵심 요약과 동등한 표를 연결하고, 필터·상태 변화·포커스가 보조 기술에 전달되는지 확인합니다. 표가 있다는 사실도 표와 차트가 같은 선택 결과를 쓴다는 증거는 아니므로 데이터 버전을 대조합니다.

### 오류는 보이지만 다음 행동이 없습니다

빨간 토스트에 “실패”만 표시하면 사용자는 입력을 고칠지, 최신 상태를 다시 읽을지, 같은 행동을 재시도할지 모릅니다. 오류를 대상과 연결하고 안전한 이유 범주·유지된 입력·재조회·재시도 조건을 설명한 뒤, 키보드 포커스가 오류나 다음 행동으로 이어지는지 확인합니다.

## AI와 작업할 때

“WCAG를 적용해 줘”보다 다음처럼 범위·사용자 흐름·증거를 고정한 읽기 전용 검토를 먼저 요청하세요.

```text wrap
이 화면의 접근성과 반응형 설계를 읽기 전용으로 검토하라.
핵심 사용자 흐름, 의미 있는 HTML, 키보드 순서와 동작, 포커스 표시·이동·복귀, 보이는 레이블과 접근 가능한 이름, 색상 외 상태, 대비, 이미지·차트의 동등 정보, 동적 상태 알림을 표로 작성하라.
200% 텍스트 확대와 320 CSS 픽셀 상당의 리플로에서 정보·기능 손실, 페이지 전체 양방향 스크롤, 고정 요소의 포커스 가림을 확인하라. 표·코드·다이어그램의 필요한 내부 스크롤은 페이지 overflow와 구분하라.
모임 참가의 성공·충돌·서버 오류·결과 불명과 교육용 주가 대시보드의 valid·warning·blocked·review_required·stale 상태에서 사용자가 다음 행동을 이해하는지 확인하라.
자동 검사, DOM·접근성 구조, 키보드, 픽셀, 보조 기술, 서버·데이터 증거를 서로 대체하지 말고 직접 확인하지 못한 항목은 미확인으로 남겨라.
파일은 수정하지 말고 WCAG 성공 기준·브라우저·보조 기술의 범위를 임의로 일반화하지 마라.
```

AI가 제안한 `aria-*` 속성과 CSS는 구현 후보일 뿐입니다. 실제 DOM의 계산된 이름·역할·상태, 키보드 과업, 확대·리플로 픽셀, 보조 기술의 읽기 결과와 서버의 권위 상태를 다시 확인해야 합니다. 한 브라우저의 성공을 다른 브라우저·OS·보조 기술 조합 전체의 완료로 보고하지 마세요.

## 확인 체크리스트

- [ ] 핵심 사용자 흐름과 실패·복구 행동을 접근성 요구로 적었습니다.
- [ ] 제목·영역·목록·링크·버튼·입력에 목적에 맞는 HTML을 사용했습니다.
- [ ] 마우스 없이 핵심 흐름을 완료하고 모든 조작 대상에 논리 순서로 도달합니다.
- [ ] 포커스가 보이고 대화상자·오류·동적 갱신 뒤 이동과 복귀가 예측 가능합니다.
- [ ] 보이는 레이블과 접근 가능한 이름이 일치하고 입력·오류·설명이 프로그램적으로 연결됩니다.
- [ ] 성공·오류·선택·값 상태를 색상 하나로만 전달하지 않습니다.
- [ ] 텍스트·조작 요소·포커스 표시의 실제 렌더 대비를 테마와 상태별로 확인했습니다.
- [ ] 정보 이미지와 차트는 목적에 맞는 텍스트 대안·표·요약을 제공하고 장식은 탐색에서 제외합니다.
- [ ] 200% 텍스트 확대와 320 CSS 픽셀 상당의 리플로에서 정보·기능 손실을 확인했습니다.
- [ ] 표·코드·다이어그램의 내부 스크롤과 페이지 전체 overflow를 구분했습니다.
- [ ] 로딩·빈 결과·성공·입력 오류·충돌·서버 오류·결과 불명·재시도 상태를 구분했습니다.
- [ ] 자동 검사, DOM·접근성 구조, 키보드, 화면, 보조 기술과 서버·데이터 증거를 각각 남겼습니다.
- [ ] 확인한 브라우저·OS·보조 기술·뷰포트·확대율·테마와 미확인 범위를 기록했습니다.
- [ ] 한 화면·도구 통과를 WCAG 전체 적합이나 모든 사용자의 성공으로 확대하지 않습니다.
