### 3. P1 review 전 필수

**P1-01 두 분류 축의 관계가 명시되지 않음**

대상: `한 문장 정의` 절의 다섯 항목 나열과 `클라이언트와 서버는 고정된 신분이 아니라…`.

근거: 클라이언트·서버(한 상호작용에서의 요청/응답 역할)와 프런트엔드·백엔드(책임 영역)를 같은 목록에 연속 배치하면서 두 축이 다른 분류라는 문장이 없습니다. 뒤의 `브라우저에는 웹 서버가 서버이지만…` 예시는 역할 반전만 다루고 축의 차이는 다루지 않습니다.

위험: 학습 목표 1이 "클라이언트=프런트엔드, 서버=백엔드"라는 등식으로 굳어집니다. 백엔드가 외부 API를 호출할 때 클라이언트가 되는 상황, 명령줄 도구처럼 프런트엔드라 부르지 않는 클라이언트를 설명하지 못합니다.

수정: 정의 목록 뒤에 두 축을 구분하는 2~3문장을 추가하고(역할축/책임축), 기존 웹 서버 예시를 그 구분의 사례로 연결합니다.

**P1-02 8단계 추적 표의 전달 방식 전제가 밝혀지지 않음**

대상: `한 사용자 작업을 끝에서 끝까지 추적하기` 표의 4단계·6단계.

근거: 2단계는 `API 또는 데이터 파일 경로`로 정적 전달을 포함하지만 4단계 증거는 `서버 로그와 계약 테스트`, 6단계는 `서버가 결과와 메타데이터…돌려줌`으로 동적 서버를 전제합니다. 같은 대시보드를 다루는 `12-case-studies/analytics-dashboard-case-study.md`는 첫 조각의 전달 방식을 정적으로 확정했습니다.

위험: 두 장을 대조한 독자가 어느 쪽이 맞는지 판단하지 못하고, 정적 사이트에 존재하지 않는 서버 로그를 증거로 요구하게 됩니다.

수정: 표 도입 문장에 "API를 사용하는 경우를 기준으로 한다"를 밝히고, 4·6단계 증거 칸에 정적 전달일 때의 대응(빌드 시점 데이터 검증 결과, 파일 응답과 배포 메타데이터)을 한 줄로 병기합니다.

**P1-03 브라우저로 내려간 값이 모두 공개된다는 경고가 없음**

대상: 책임 표의 `비밀값은 어디에 두는가?` 행과 `풀스택은 항상 동적 서버를 뜻하지 않습니다` 절.

근거: 본문의 신뢰 경계 설명은 `브라우저에서 보낸 값`(클라이언트→서버)과 숨긴 기능만 다룹니다. 서버·빌드에서 브라우저로 내려간 값(번들 JavaScript, 정적 JSON, 설정값)이 전부 열람 가능하다는 반대 방향은 없습니다. 사례 장은 C-02에서 브라우저 번들을 명시적 점검 대상으로 둡니다.

위험: 정적 전달을 권장하는 절과 결합해 키·내부 규칙·비공개 행을 정적 파일이나 번들에 넣는 실제 유출로 이어집니다. 되돌릴 수 없는 공개 사고입니다.

수정: 비밀값 행 또는 정적 전달 절에 "브라우저에 전달된 파일과 번들은 모두 읽을 수 있는 것으로 간주한다"는 한 문장과 체크리스트 한 항목을 추가합니다.

**P1-04 전송 구간 보호(HTTPS)가 빠짐**

대상: 8단계 표 3단계 `전달 | 네트워크와 중간 구성요소가 요청을 대상에 전달`.

근거: 이 장은 신뢰 경계를 핵심 주제로 삼지만 전송 구간 도청·변조와 HTTPS를 한 번도 언급하지 않습니다. `03-full-stack/http-request-response.md`는 공개 환경의 HTTPS를 기본값으로 명시했고 용어집에도 `HTTPS` 항목이 있습니다.

위험: 서버 검증만 갖추면 경계가 안전하다는 인상을 줍니다. 같은 트랙 안에서 보안 기준이 장마다 달라 보입니다.

수정: 3단계 증거 칸 또는 신뢰 경계 문단에 공개 환경의 HTTPS 확인을 한 문장으로 추가하고 HTTP 장으로 링크합니다.

**P1-05 응답 단절 뒤 재시도의 중복 부작용이 연결되지 않음**

대상: `서버 변경은 성공했지만 응답이 끊기면 클라이언트는 실패처럼 보더라도 실제 저장 상태를 다시 확인해야 할 수 있습니다.`

근거: "다시 확인"까지만 말하고 재전송 시 중복 생성·중복 결제 위험과 멱등성 개념을 언급하지 않습니다. HTTP 장은 같은 상황을 안전성·멱등성·멱등 키로 상세히 다루지만 이 문맥에서 그 장으로의 연결이 없습니다.

위험: 독자와 AI가 실패로 보이는 쓰기 요청을 그대로 재시도하도록 유도되어 데이터 중복이 발생합니다.

수정: 해당 문단에 "다시 보내기 전에 같은 요청이 이미 반영됐는지 확인한다"는 한 문장과 HTTP 장 앵커 링크를 추가합니다.

**P1-06 출처가 증명하지 못하는 범위를 밝히지 않음**

대상: 마지막 문장 `출처의 확인일과 적용 범위는 저장소의 research/source-map.md에서 관리합니다.`

근거: `research/source-map.md`가 이 장에 매핑한 출처는 SWEBOK topics(요구~운영의 책임·증거)와 MDN HTTP(요청·응답 역할과 네트워크 경계) 둘뿐입니다. 상태의 권위·캐시 무효화·낙관적 화면 변경, 정적 전달의 충분 조건과 동적 백엔드 신호, 프런트엔드 검증의 보안적 한계는 이 두 범위 밖입니다. 같은 저장소의 `software-is-a-system.md`, `analytics-dashboard-case-study.md`, `http-request-response.md`는 모두 "이 출처가 증명하지 않는 것"을 본문 끝이나 후속 조사 대기 목록에 남겼는데 이 장만 없습니다.

위험: 루브릭 `근거` 항목과 `ready` 승격 조건인 출처 추적성을 충족하지 못하고, 미확인 주장이 확인된 사실처럼 읽힙니다.

수정: 마지막 문단에 미뒷받침 범위 열거 문장을 추가하고 `research/source-map.md`의 `후속 조사 대기`에 이 장 항목을 신설합니다.

**P1-07 서버가 항상 다른 원격 기계라는 오해가 남음**

대상: `서버는 반드시 한 대의 물리적 컴퓨터를 뜻하지 않습니다.`

근거: 이 문장은 "한 대가 아닐 수 있다"만 부정하고, 서버가 사용자 자신의 컴퓨터에서 실행될 수 있다는 반대 방향은 다루지 않습니다. HTTP 장은 `http://localhost` 예시를 쓰고 용어집에는 `development server`, `local environment`가 있으며 이 저장소도 개발 서버로 사이트를 확인합니다.

위험: 비개발자가 `npm run dev`로 뜬 로컬 서버를 클라이언트·서버 모델과 연결하지 못해, 로컬 확인 결과를 공개 환경 증거로 혼동합니다.

수정: 같은 문단에 "서버는 원격 장비일 수도, 지금 쓰는 컴퓨터에서 실행 중인 프로그램일 수도 있다"는 한 문장을 추가합니다.

**P1-08 핵심 개념이 정식 용어·용어집과 연결되지 않음**

대상: `상태의 원본과 사본을 구분하세요` 절의 `권위 있는 원본`, `신뢰 경계에서 다시 검증합니다`, 그리고 관련 링크의 `개발 용어집의 웹과 풀스택` 앵커.

근거: 이 장의 두 축인 `source of truth`와 `trust boundary`는 용어집 `시스템과 코드` 절에 표제어로 있는데 본문에는 영문 병기가 없고, 관련 링크는 두 용어가 없는 `#웹과-풀스택` 앵커만 가리킵니다. `AGENTS.md`의 "쉬운 말로 정의한 뒤 정식 용어를 연결" 원칙과 완료 정의의 용어집 일치 조건에 어긋납니다. 또한 용어집의 `client`·`server` 정의에는 이 장의 핵심 주장인 "역할" 관점이 없어 두 문서가 어긋납니다.

위험: 독자가 다른 문서나 AI 출력에서 같은 개념을 만나도 연결하지 못하고, 용어 단일화라는 프로젝트 규칙이 깨집니다.

수정: 두 용어의 영문 병기를 본문 첫 등장 위치에 넣고, 관련 링크에 용어집 `시스템과 코드` 앵커를 추가하며, 용어집 `client`·`server` 정의에 상호작용 역할이라는 문구를 반영합니다.

### 4. P2 개선 권장

**P2-01 백엔드를 `서버 측 영역`으로만 규정** — 정의 절. 빌드 시 데이터 수집·변환·품질 판정처럼 실행 중인 서버 없이 수행되는 백엔드성 책임의 위치가 불명확합니다. 정적 전달 절과 사례 장의 구조를 설명하기 어렵습니다. 정의에 "실행 중인 서버뿐 아니라 빌드·배치 작업에서 수행될 수도 있다"는 단서를 붙입니다.

**P2-02 정적 전달에도 남는 호스팅 응답 책임 미언급** — `이 경우에도 데이터 생성, 빌드, 배포, 브라우저 상태와 운영 확인까지…` 문장. 파일을 응답하는 호스팅 계층과 그 계층의 HTTPS·캐시·접근 설정 책임이 빠져 "정적이면 서버가 없다"는 오해가 남습니다. 열거에 호스팅 응답 계층을 한 항목 추가합니다.

**P2-03 지속 연결과 서버 주도 전달 예외 없음** — 정의 절의 `요청을 받아 …응답하는`. 요청·응답 왕복만이 상호작용이라는 인상을 줍니다. 비유가 깨지는 지점에 이미 접수 후 별도 알림이 언급되므로, 같은 문단에 "연결을 유지한 채 서버가 먼저 갱신을 보내는 방식도 있다"는 한 문장을 덧붙입니다.

**P2-04 초기 로드와 이후 상호작용의 흐름 차이 미구분** — `시스템에서의 위치` 코드 블록. `05-frontend/browser-dom-rendering.md`는 두 흐름을 나눠 제시하는데 이 장은 단일 사슬만 제시합니다. 뒤의 완충 문단에 "첫 페이지 표시와 이후 상호작용은 순서가 다르다"를 한 문장 추가합니다.

**P2-05 동시 요청·부분 실패·늦게 도착한 응답 없음** — 실패 위치 표. 한 화면이 여러 요청을 만들 때의 부분 성공과 오래된 응답 반영은 브라우저 장 표에는 있으나 이 장에는 없습니다. 실패 표 `클라이언트 상태` 행에 한 항목을 보탭니다.

**P2-06 신뢰 경계를 클라이언트 방향으로만 프레이밍** — `클라이언트가 보낸 신원·권한·가격·소유권과 중요한 입력을 그대로 믿지 않습니다.` 서버가 받는 외부 API 응답·원천 파일도 경계를 넘는 입력이라는 점(`software-is-a-system.md`가 다루는 관점)이 빠졌습니다. 판단 규칙 5에 외부 응답을 한 구절 추가합니다.

**P2-07 충돌 처리에 방향이 없음** — 상태 표의 `누가 원본을 바꿀 수 있고 충돌을 어떻게 처리하는가?`. 질문만 있고 판단의 최소 갈래(마지막 쓰기 우선, 버전 확인 후 거절, 사용자에게 병합 요청)가 없어 판단 기준으로 쓰기 어렵습니다. 한 문장으로 갈래만 제시합니다.

**P2-08 정적 갱신과 캐시의 시차 미언급** — 정적 전달 절. 갱신이 새 빌드·배포로 이루어지고 캐시 때문에 즉시 반영되지 않을 수 있다는 점(사례 장이 다루는 내용)이 빠져 상태 절의 사본 논의와 이어지지 않습니다. 한 문장 추가.

**P2-09 최신성 신호가 선택 기준에 없음** — 동적 백엔드 신호 다섯 항목. 사례 장은 "최신성이 짧아 빌드·배포 주기로 감당할 수 없음"을 명시적 전환 신호로 둡니다. 목록에 한 항목 추가.

**P2-10 개발자 도구 명칭 한계 미표시** — `브라우저 Network의 실제 요청`, `Console과 Network`. 다른 두 장은 브라우저별 명칭이 다를 수 있음을 명시했는데 이 장만 단정합니다. 첫 등장 위치에 짧은 단서를 답니다.

**P2-11 연습 표가 본문 8단계와 매핑되지 않음** — 연습의 7행(`경계와 계약`, `데이터 원본·사본`, `운영 확인` 등)이 본문 표의 8단계와 이름·개수가 달라 독자가 본문을 그대로 재사용하지 못합니다. 행 이름을 본문 단계와 일치시키거나 대응 관계를 한 줄로 안내합니다.

**P2-12 비유의 깨지는 지점에 역할 반전이 없음** — `비유가 깨지는 지점` 문단. 이 장의 핵심 주장인 역할 반전(주방이 다른 곳에 주문을 넣는 상황)과 동시 다수 손님이 빠져 비유가 핵심 개념을 강화하지 못합니다. 한 문장 추가.

**P2-13 같은 주제의 인접 장으로 링크가 없음** — `관련 용어와 출처` 목록. 이 장의 `프런트엔드와 백엔드는 책임으로 나눕니다` 절과 주제가 겹치는 `03-full-stack/frontend-backend-boundary.md`(`seed`)가 링크 목록에 없습니다. HTTP 장은 그 장을 후속으로 안내하고 있어 트랙 내 안내가 어긋납니다. 링크를 추가하고 두 장의 역할 분담을 한 구절로 밝힙니다.

### 5. 잘된 점

- 증거 범위를 서로 대신 쓰지 못하게 하는 서술이 일관됩니다. `Network 탭의 200은 응답 교환이 성공 범주였다는 증거이지…`와 층별 실패 표, 체크리스트가 같은 원칙을 세 번 다른 형식으로 검증합니다.
- 정적 전달을 기본값으로 두면서도 `실제 권한과 비밀정보 책임이 있는데 정적 화면만으로 감추려 해도 안전하지 않습니다`로 반대 방향 위험을 함께 막았습니다. 과설계 회피와 책임 은폐 방지가 균형을 이룹니다.
- 흐름 코드 블록 직후의 `이 흐름은 학습을 위한 기본 지도이지 모든 시스템의 고정 배치도가 아닙니다`와 세 가지 반례는 질문 3의 위험을 대부분 선제적으로 해소합니다.
- 프런트엔드 검증이 보안 경계가 아니라는 원칙과 "그렇다고 모든 계산을 서버로 옮기라는 뜻은 아니다"는 반대 오해가 한 절 안에서 함께 제시됩니다.
- AI 작업 지시 예시가 범위·추적 순서·산출물·미확인 표시·금지 사항을 모두 포함하고, 뒤이어 `그럴듯한 아키텍처 설명은 증거가 아닙니다`로 검증 책임을 사람에게 되돌립니다.
