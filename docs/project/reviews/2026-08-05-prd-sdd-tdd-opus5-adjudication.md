P2-7과 P2-13은 기각했으므로 BDD 설명과 링크 대상의 상태 주석은 추가하지 않습니다.

## 반영 작업의 수용 기준

- 독자가 PRD와 Software Design Description은 산출물, Spec-Driven Development는 접근, TDD는 구현 규율이라고 구분하고 `Plan`이 별도 설계 문서를 항상 추가하는 단계가 아님을 설명할 수 있습니다.
- Spec Kit의 네 단계와 이 핸드북이 만든 종료 질문·증거 기준을 구분하며, 현재 확인일과 재확인 필요성이 드러납니다.
- ADR, 수직 기능 조각, source of truth와 대사를 문맥 안에서 쉬운 말로 이해할 수 있습니다.
- TDD 예시는 내부 함수 호출보다 외부 부작용과 요구 결과를 우선하며, 최소 구현이 하드코딩·품질 면제라는 오해를 만들지 않습니다.
- TDD를 단위 테스트에만 제한하지 않으면서 시각·접근성·외부 연동·성능·복구에는 다른 직접 증거가 필요하다는 경계를 유지합니다.
- 관계도와 텍스트가 검증·운영 학습이 요구·설계로 되돌아가는 반복을 표현하고, SVG `title`·`desc`와 Markdown 대체 텍스트가 일치합니다.
- 연습이 네 개념의 범주와 두 SDD 의미를 실제로 답하게 하며 모바일에서 과도한 열 수를 만들지 않습니다.
- 직접 확인하지 않은 PRD·설계 설명·TDD·Spec Kit 세부가 `research/source-map.md`의 후속 조사 대기로 추적됩니다.
- P1 11건과 P2 13건 각각의 반영 위치 또는 부분 수용·기각 이유를 이 문서에서 역추적할 수 있습니다.
- 공개 원고의 `contentStatus`는 반영·검증·실제 요청 기록이 끝나기 전까지 `draft`를 유지합니다.

- `docs/project/reviews/2026-08-05-prd-sdd-tdd-review-prep.md`: 정상 검토·재판정과 향후 반영 결과 기록

## 상태와 증거 경계

재판정 시점에는 Opus 지적의 타당성과 다음 수정 범위만 정했으므로 원고는 `draft`이며 `reviewEvidence`도 추가하지 않습니다. 후속 구현에서 최소 보완, 자체 루브릭 재점검, `npm run check`, 데스크톱·모바일 렌더링, SVG 접근성 확인과 실제 `request:` 기록을 모두 확인한 뒤에만 `review` 승격을 판단합니다. AI 독립 검토와 Codex 재판정은 사람 기술·편집 검토와 실제 비개발자 독자 테스트를 대신하지 않으며, 직접 출처 확인 없이는 `ready`를 논의하지 않습니다.
