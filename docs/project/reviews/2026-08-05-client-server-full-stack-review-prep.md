# 클라이언트·서버·풀스택 검토 준비 기록

## 목적과 현재 상태

이 문서는 공식 Build Track 두 번째 장인 `src/content/docs/03-full-stack/client-server-full-stack.md`의 자체 품질 점검과 독립 검토 요청 범위를 기록합니다. 원고는 사용자 작업, 책임, 신뢰 경계, 상태와 증거를 하나의 흐름으로 추적하고 Opus 5 Max 독립 검토·Codex 재판정·지적 반영·자동 검증을 마쳐 `review`로 진입했습니다. 사람 기술·편집 검토와 실제 비개발자 독자 테스트, 직접 1차 출처 확인은 아직 통과하지 않았습니다.

2026-08-05 03:45 KST의 첫 시도는 단기 사용 구간 초과와 API `429`로 모델 실행 전에 종료됐습니다. 이후 호스트의 `claude.ai` 로그인과 Pro 구독을 다시 확인하고 `claude-opus-5`·`max`·계획 모드·`Read` 전용으로 실행한 검토는 종료 코드 0과 정상 결과를 만들었습니다. P0 0건·P1 8건·독립 루브릭 16/18·치명 항목 없음·`draft` 유지 권고, 실제 Opus 사용, 웹 요청과 권한 거부 0건 및 13개 입력 파일의 검토 전후 결합 지문 불변을 확인했습니다.

첫 실행의 결과 본문은 Codex의 마지막 터미널 폴링 표시 한도 때문에 중간이 잘렸고 즉시 결과 전용 재실행은 모델 실행 전 단기 세션 한도로 종료됐습니다. 세션 한도 재설정 뒤 같은 13개 파일을 다시 읽힌 첫 복구 실행도 긴 보고서 뒤 별도 후속 문장 때문에 비스트리밍 JSON의 마지막 필드에 전문이 남지 않았습니다. 두 번째 복구 실행에서는 최종 메시지 하나에 보고서 전문만 작성하도록 계약하고 최대 14턴으로 제한해 P0 0건·P1 8건·P2 13건·잘된 점·9항목 루브릭 16/18·치명 항목 없음·추가 출처 목록·`draft` 유지 권고를 손실 없이 회수했습니다. 실제 Opus 사용, 웹 요청·권한 거부 0건과 현재 13개 입력 파일의 검토 전후 결합 지문 불변도 확인했습니다. 전체 실행 메타데이터와 정본은 `docs/project/reviews/2026-08-05-client-server-full-stack-opus5-review.md`, Codex의 P1 수용 7건·부분 수용 1건과 P2 수용 10건·부분 수용 3건 판정은 `docs/project/reviews/2026-08-05-client-server-full-stack-opus5-adjudication.md`에 기록합니다. 계정 식별 정보는 기록하지 않습니다.

## 자체 점검에서 보완한 범위

1. 클라이언트와 서버를 고정된 장비가 아니라 한 상호작용에서 바뀔 수 있는 역할로 정의했습니다.
2. 사용자 행동, 클라이언트 상태, 네트워크, 서버 규칙, 데이터, 응답, 화면과 사용자 완료를 분리하고 각 단계의 직접 증거를 연결했습니다.
3. 프런트엔드의 빠른 피드백과 서버의 신원·권한·업무 규칙·데이터 무결성 책임을 구분하되 모든 계산을 서버로 옮기는 규칙으로 일반화하지 않았습니다.
4. 상태 종류마다 권위 있는 원본과 사본, 갱신·만료·충돌 질문이 다름을 명시했습니다.
5. 정적 전달도 전체 제품 흐름을 가질 수 있으며 실제 책임이 생길 때만 동적 백엔드를 추가하도록 선택 신호를 제시했습니다.
6. 같은 빈 차트 증상을 층별 실패와 증거로 분해하고 한 층의 성공을 전체 성공으로 확대하지 않도록 했습니다.
7. AI 지시에 범위, 상태, 실패, 증거, 미확인 표시와 민감정보 금지를 포함했습니다.

2. 클라이언트·서버와 프런트엔드·백엔드의 범주가 잘못 동일시되거나 책임이 지나치게 단정된 부분이 있나요?
3. 사용자 행동에서 요청·서버 판단·데이터·응답·화면·사용자 완료로 이어지는 기본 흐름이 모든 웹 시스템의 고정 구조처럼 읽히나요?

5. 상태의 권위 있는 원본과 사본, 갱신·만료·충돌, 낙관적 화면 변경과 응답 단절 설명에 중요한 예외가 빠졌나요?
6. 화면, Network, 서버 로그, 데이터 품질 결과와 사용자 작업 완료의 증거 범위를 정확히 구분했나요?
7. 정적 전달과 동적 백엔드 선택 신호가 과설계를 피하면서 실제 서버 책임을 숨기지 않도록 구성됐나요?
8. 식당 비유의 맞는 지점과 깨지는 지점, 대시보드 사례, 판단 규칙, 실패 모드, 체크리스트와 연습이 학습 목표를 관찰 가능하게 검증하나요?
9. 현재 출처가 직접 뒷받침하지 못하거나 추가 공식·1차 자료 확인이 필요한 주장은 무엇인가요?
10. 품질 루브릭 9개 항목을 0~2점으로 평가하고 치명 항목 여부를 판정해 주세요.

## 승격 경계

Opus 정본 결과를 손실 없이 확보하고 Codex 재판정, 지적 반영, 정적 검사·빌드·브라우저 검증과 `request:` 증거 기록을 마쳐 대상은 `review`로 진입했습니다. 이 상태는 출판 준비 완료가 아니라 독립 검토가 시작됐다는 뜻입니다. AI 검토와 자동 검증은 사람 기술·편집 검토와 실제 비개발자 독자 테스트를 대신하지 않으며, 직접 출처 확인과 네 종류의 `ready` 증거를 갖추기 전에는 `ready`로 승격하지 않습니다.
