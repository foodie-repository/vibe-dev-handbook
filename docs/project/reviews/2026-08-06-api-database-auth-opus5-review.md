**P1-2. 권한 부정 테스트의 허가 범위가 없습니다** (`api-database-auth.md:111`, `:150`, `:237`)

"보고서 ID만 다른 값으로 바꿨을 때 다른 사용자의 데이터가 보이거나 수정되는지 테스트해야 합니다"라는 문장에 *본인이 소유·운영하는 시스템에서, 테스트 계정과 테스트 데이터로* 라는 조건이 없습니다. `http-request-response.md:248`은 같은 성격의 연습에 "자신의 프로젝트나 안전한 공개 사이트에서"라는 범위를 붙였고 `RULES.md` 8번은 회사 데이터·개인정보 사용을 금지합니다. 비개발자 독자가 이 지시를 자신이 권한을 갖지 않은 서비스나 동료의 실제 보고서에 적용하면 무단 접근·개인정보 열람이 됩니다. **최소 수정:** 111행과 150행에 "본인이 소유하거나 테스트 권한을 받은 환경에서 테스트 계정 A·B와 가짜 데이터로" 조건을 한 문장씩 추가.

**P1-3. JWT와 MAC이 정의 없이 사용됩니다** (`api-database-auth.md:105`, `:182`, `:258`)

본문은 JWS·JWE만 설명하고 **JWT가 무엇인지, JWT가 JWS 또는 JWE 형식으로 표현될 수 있다는 관계**를 말하지 않습니다. 그런데 연습 2(258행)는 "API에 JWT를 보내므로"라는 문장을 반박하게 하고, 흔한 오해(182행)도 JWT를 전제합니다. `MAC`도 병기·설명 없이 두 번 등장하며 `development-glossary.md`에는 JWT·JWS·JWE·MAC 항목이 없습니다(`digital signature`, `encryption`, `token`만 있음). `editorial-guide.md`는 "영문 용어는 첫 등장에 한국어 뜻과 함께 표기"를, `AGENTS.md` 5절은 "쉬운 말로 정의한 뒤 정식 용어 연결"을 요구합니다. 정의 없이는 독자가 "JWT니까 암호화돼 있다"는 오해를 스스로 반박할 수 없어, 토큰에 개인정보를 담아도 안전하다고 판단할 위험이 남습니다. **최소 수정:** 105행에 "JWT(JSON Web Token)는 자격·정보를 담는 토큰 형식이며 서명만 적용한 JWS 형태일 수도, 암호화한 JWE 형태일 수도 있습니다"와 "MAC(메시지 인증 코드)" 병기를 넣고, 용어집 `token` 항목 뒤에 JWT 한 줄을 추가.

**P1-4. 인증 실패 응답의 일반화(계정 열거 방지)가 빠졌습니다** (`api-database-auth.md:99`, `:141`, `:229`)

**P1-5. 계약의 "호환성 조건"이 단어로만 등장합니다** (`api-database-auth.md:67`, `:176`)

**P2-4. 다이어그램에 응답 단계 실패 분기 없음** (`api-database-auth-flow.svg:83–106`, `.mmd:16–22`, 본문 `:53`, `:133`). 본문이 강조한 "commit 뒤 응답 유실" 부분 성공이 SVG·Mermaid·대체 텍스트 어디에도 없습니다. 또 SVG 2단계 실패 라벨은 "형식·계약 오류"인데 `desc`와 본문 대체 텍스트는 "형식 오류"로만 적혀 세 산출물의 라벨이 어긋납니다. 7단계에 점선 분기 1개(응답 전달 실패)를 추가하고 라벨을 통일하십시오.

**P2-5. 증거 표에 관찰 주체 구분이 없음** (`:139–146`). "정책 집행 위치", "인증 검증 로그의 요청 ID", "트랜잭션 rollback" 확인은 비개발자가 직접 볼 수 없고 AI·개발자에게 요청해야 하는 항목입니다. 표 앞에 "직접 볼 수 있는 증거와 요청해서 받아야 하는 증거"를 한 문장으로 구분하면 216–219행의 AI 요청과 연결됩니다.

**P2-6. 문자열 결합 위험을 찾을 신호가 없음** (`:119`, `:243`). 개념은 정확하지만 AI 산출물에서 무엇을 보고 판단할지(쿼리 실행 지점, 값 전달 방식)가 없어 체크 항목 "입력이 쿼리 구조와 분리된 값으로 전달되나요?"를 비개발자가 판정할 수 없습니다. AI 계약에 "쿼리 실행 지점과 값 전달 방식을 보여 주세요" 한 줄을 넣는 것이 최소 수정입니다.

**P2-7. 출처 목록과 출처 지도 불일치** (`:284` vs `source-map.md:55`, `:56`). 원고는 PostgreSQL을 `/docs/18/`로, 지도는 `/docs/current/`로 기록합니다. 또 지도에는 이 장의 적용 출처로 MDN HTTP가 있지만 원고 목록(278–284행)과 276행의 출처 유형 문장("표준, 미국 연방 디지털 신원 지침, OWASP 실무 지침과 PostgreSQL 제품 문서")에는 없습니다. 브리프의 `draft` 수용 기준(`:255`)은 URL·확인일·적용 범위 일치를 요구하므로 한쪽으로 맞추고 MDN을 "설명용 보조 자료"로 명시하십시오.

**P2-8. 위임 대상 장이 아직 스텁이고 분량이 브리프 상한을 넘음** (`:268`, `:270`, 브리프 `:223`). 링크된 `data-model-schema-migration.md`와 `performance-security.md`는 모두 `contentStatus: seed`의 40여 줄 스텁이라 독자가 약속된 깊이를 찾지 못합니다. 동시에 원고는 브리프 목표 8,000~12,000자를 16% 초과한 13,911자로 보고돼 있습니다. 링크 뒤에 "현재 시드 단계" 표시를 하거나, 초과 분량의 근거를 브리프 위임 기준에 맞춰 기록하십시오.

**P2-9. 핵심 정의 구획이 고르지 않음** (`:34–39`). 정의 목록은 API·데이터베이스·인증·인가 4개인데 이 장에서 계속 쓰는 **백엔드**의 한 문장 정의가 없고(첫 등장 20행에 교차 링크도 없음), 엔드포인트 정의만 목록 밖 문단에 묻혀 있습니다. 용어집(`:58`)은 endpoint를 "메서드와 경로 **등**으로"라고 더 넓게 정의해 미세한 차이도 있습니다. 백엔드는 `client-server-full-stack.md`로 링크하고 엔드포인트는 목록 항목으로 옮기면 됩니다.

**P2-10. 비유 절에 소제목이 없음** (`:41–47`). 내용상 맞는 지점(45행)과 깨지는 지점(47행)은 모두 있지만, 인접 장(`http-request-response.md:40·47`, `client-server-full-stack.md:45·52`)이 쓰는 `### 비유가 맞는 지점 / 깨지는 지점` 구조와 달라 독자가 한계 서술을 놓치기 쉽습니다.

**P2-11. Network 탭 관찰 문단에 근거 장 링크와 명칭 주의가 없음** (`:148`). `client-server-full-stack.md:77`은 "`Network`와 `Console`은 브라우저에 따라 이름과 위치가 다를 수 있습니다"를 명시합니다. 148행에 같은 주의와 HTTP 장 관찰 절차 링크를 붙이면 실제 관찰 가능성이 올라갑니다.

**P2-12. 이 장의 비목표가 본문에 없음.** 브리프 `:96–108`은 로그인 구현, 비밀번호 저장, OAuth·SSO, 키 관리를 명시적 비목표로 두었지만 원고에는 범위 문장이 없습니다. 체크리스트는 "세션과 토큰의 수명·폐기·탈취 대응을 확인했나요?"(239행)를 요구하면서 어디서 배울지 알려 주지 않습니다. 24행 뒤에 "이 장은 로그인 구현·비밀번호 저장·OAuth·키 관리를 다루지 않습니다" 한 문장을 권합니다.

**P2-13. 트랜잭션 경계를 정하는 주체가 모호** (`:22`). "데이터베이스는 … 필요한 여러 변경을 하나의 트랜잭션으로 묶습니다"는 요약은 경계를 정하는 쪽이 애플리케이션이라는 사실을 흐립니다. 123·125행은 정확하므로 22행만 "애플리케이션이 정한 트랜잭션 단위로 함께 반영하거나 함께 취소합니다"로 바꾸면 됩니다.

- **성공 응답과 `commit`의 비대칭을 양방향으로 다뤘습니다**(`:133`). 응답 유실 뒤 재전송 위험까지 연결한 서술은 연습 3과 정확히 맞물립니다.
