# 브라우저·DOM·렌더링 검토 준비 기록

## 목적과 현재 상태

이 문서는 `src/content/docs/05-frontend/browser-dom-rendering.md`의 자체 품질 점검, 독립 Opus 검토 요청, Codex 재판정·반영과 자동·브라우저 검증 범위를 기록합니다. 원고는 이 증거를 갖춰 `review`로 표시하지만, 사람 기술·편집 검토와 실제 비개발자 독자 테스트를 아직 통과하지 않았습니다.

2026-08-05 샌드박스 안에서 실행한 `claude auth status`는 인증 저장소를 읽지 못해 `loggedIn: false`를 반환했지만, 호스트 권한에서 다시 확인한 결과 Claude Code 로그인과 Pro 구독은 정상이었습니다. 첫 검토 요청은 모델 실행 전에 API `429`로 종료됐고 Claude Code는 세션 한도가 오전 7시(Asia/Seoul)에 재설정된다고 반환했습니다. 당시 메타데이터상 입력·출력 토큰 0, 모델 사용 기록 없음, 웹 검색·웹 가져오기 0건, 권한 거부 0건이므로 검토 본문은 생성되지 않았습니다.

세션 한도 재설정 뒤 호스트 인증을 다시 확인하고 Claude Code 2.1.221, `claude-opus-5`, 추론 강도 `max`, 계획 모드와 `Read` 도구만으로 같은 범위의 검토를 재실행했습니다. 재실행은 종료 코드 0으로 정상 완료됐고 P0 0건·P1 10건·P2 12건·독립 루브릭 16/18·치명 항목 없음과 `draft` 유지 권고를 받았습니다. 11개 입력 파일과 대상 원고의 검토 전후 SHA-256이 일치했고 웹 검색·웹 가져오기·권한 거부는 모두 0건입니다. 결과 전문과 실행 메타데이터는 `docs/project/reviews/2026-08-05-browser-dom-rendering-opus5-review.md`에 기록했으며, 개인정보인 계정 이메일과 조직 식별자는 기록하지 않습니다.

## 자체 점검에서 수용한 보완

1. 초기 HTML·CSS·JavaScript 표시와 이후 사용자 행동·HTTP 응답에 따른 갱신을 한 흐름에 섞지 않고 두 흐름으로 분리했습니다.
2. 모든 사용자 행동이 HTTP 요청으로 이어지지는 않는다고 명시했습니다.
3. 개발자 도구 탭 이름이 브라우저마다 다를 수 있으므로 `Elements`와 `Inspector`를 예로 들고 이름보다 증거 종류를 찾도록 수정했습니다.

## Opus 재판정 반영 결과

1. P1-01·P1-02·P1-04·P2-01·P2-02·P2-04를 묶어 자원·언어, DOM 모델과 렌더링 과정을 구분하고 앱 코드의 상태 반영과 브라우저 화면 계산을 별도 경계로 설명했습니다.
2. P1-03·P1-05를 묶어 같은 문서 안의 갱신과 새 문서 로드를 분리하고 서버 응답·UI 상태·현재 DOM·렌더링 화면·사용자 작업 결과의 다섯 증거 계층을 맞췄습니다.
3. P1-06·P2-03·P2-09·P2-10을 묶어 연결된 시드 장의 범위를 과장하지 않고 환경 차이, 상태 중복, 좁은 viewport·실제 기기와 Tab 포커스 확인의 최소 행동을 추가했습니다.
4. P2-05·P2-06·P2-07·P2-08을 묶어 차트 진단의 관찰 위치, 개발자 도구를 먼저 여는 순서, Console 메시지의 출처와 Elements 임시 편집의 증거 한계를 추가했습니다.
5. P1-07·P1-08을 묶어 공개 사이트 연습을 로그인·저장·결제 없는 조회·필터로 제한하고 관찰한 증상을 HTML·CSS·JavaScript·DOM·렌더링 책임에 다시 연결하게 했습니다.
6. P2-11은 배포 뒤 이전 화면·자산 증상과 버전·Network 증거만 추가하고 원인·복구 설명은 배포 장으로 위임했습니다.
7. P1-09·P1-10은 직접 출처 대기 범위를 `research/source-map.md`에 기록하고 실제 반영·검증 뒤 정본 Opus `request:`와 `automated:` 증거를 frontmatter에 추가했습니다. P2-12는 기각해 용어집을 수정하지 않았습니다.

## 반영 뒤 검증

- `npm run sync:content-map`으로 원고 상태와 본문 문자 수를 생성 규칙에 따라 동기화했습니다.
- `ASTRO_TELEMETRY_DISABLED=1 npm run check`에서 Node 테스트 26개·공개 콘텐츠 58개·전체 Markdown/MDX 117개·학습 SVG 11개·정적 페이지와 생성 HTML 59개를 통과했습니다.
- Playwright로 1440×1000과 390×844에서 H1 1개·표 5개·체크 항목 12개·핵심 보완 문구와 상태 배지를 확인했고 페이지·본문·표 가로 넘침과 Console 오류·경고는 0건입니다.
- 자체 루브릭은 17/18이고 치명 항목은 없습니다. 근거 항목 1점은 DOM·렌더링·개발자 도구와 WCAG 세부의 직접 공식 출처가 아직 확인되지 않았기 때문입니다.

검토자는 다음 질문에 답해야 합니다.

1. 비개발자가 HTML·CSS·JavaScript·DOM·렌더링의 책임을 잘못 동일시하게 만드는 문장이 있나요?
2. 서버 응답, 현재 DOM, 렌더링 결과와 사용자 작업 성공의 증거 경계가 정확한가요?
3. 초기 표시, 사용자 행동, 비동기 응답, 상태 변경과 다시 렌더링의 관계가 특정 프레임워크의 보편 규칙처럼 쓰였나요?
4. Elements·Inspector, Console과 Network 설명에서 브라우저별 차이나 보안·개인정보 경계가 빠졌나요?
5. 무대 공연 비유가 맞는 지점과 깨지는 지점이 충분한가요?
6. 대시보드 사례, 판단 규칙, 실패 모드, 체크리스트와 연습이 학습 목표를 실제로 검증하나요?
7. 현재 출처가 직접 뒷받침하지 못하거나 더 구체적인 공식 문서 확인이 필요한 주장은 무엇인가요?
8. 품질 루브릭 9개 항목을 각각 0~2점으로 평가하고 치명 항목 여부를 판정해 주세요.

결과는 `P0 치명 오류`, `P1 review 전 필수`, `P2 개선 권장`, `잘된 점`, `루브릭 점수`, `추가 출처 확인 목록` 순으로 작성하고, 각 지적에 대상 문장이나 제목을 포함해야 합니다. 웹 검색, 파일 수정, Bash, 외부 플러그인과 하위 에이전트는 사용하지 않습니다.

## 승격 경계

Opus 검토 결과를 Codex가 원고와 프로젝트 규칙에 대조해 P1 수용 8건·부분 수용 2건, P2 수용 8건·부분 수용 3건·기각 1건으로 재판정하고 7개 최소 보완 묶음을 반영했습니다. 첫 실행의 세션 한도 실패는 기술 검토로 세지 않으며, 정상 Opus 결과와 Codex 재판정도 AI 검토이므로 사람 `technical:`·`editorial:`·`reader:` 증거를 대신하지 않습니다. 최소 보완·`request:` 기록·자동 검증·렌더링 확인을 모두 갖춰 `review`로 올리지만, 사람 기술·편집 검토, 실제 비개발자 독자 테스트와 직접 공식 출처 확인 전이므로 `ready`로 승격하지 않습니다.
