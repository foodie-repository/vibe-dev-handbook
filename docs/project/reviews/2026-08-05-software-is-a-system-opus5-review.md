# P1 review 전 필수

### P1-01 · 구성요소와 책임 렌즈의 정의가 순환적입니다

- **대상**: 「시스템을 보는 여섯 렌즈」, 「1. 구성요소」 — "구성요소(component)는 한 책임을 중심으로 묶어 생각할 수 있는 부분입니다"
- **이유**: 구성요소를 "한 책임의 묶음"으로 정의하면 렌즈 1과 렌즈 2가 같은 대상을 두 번 세게 됩니다. 실제로 대시보드 사례 표에서 구성요소 6개와 책임 6개가 1:1로 대응해(공개 원천→원천 확인, 수집 작업→단위 정규화) 두 렌즈가 서로 다른 질문이라는 근거가 본문에서 사라집니다. 학습 목표 1이 "여섯 개의 렌즈로 설명한다"이므로 렌즈를 구별하지 못하면 목표가 관찰되지 않습니다.
- **최소 수정**: 구성요소는 "무엇이 존재하고 실행되는가", 책임은 "무엇을 보장하고 어떤 실패를 처리하는가"로 질문을 분리하고, 한 구성요소가 여러 책임을 가질 수 있고 한 책임이 여러 구성요소에 흩어질 수 있다는 문장 1~2개를 추가합니다(이미 있는 "같은 업무 규칙이 브라우저와 서버와 배치 작업에 복제되면" 문단과 연결하면 됩니다).

### P1-02 · 구성요소 예시에 경계와 실행 환경이 섞여 있습니다

- **대상**: 「1. 구성요소」의 "외부 API와 배포 환경", 대시보드 표 구성요소 행의 "데이터 전달 경계"
- **이유**: 이 장이 가르치려는 범주 구분이 대표 예시에서 무너집니다. 배포 환경은 구성요소가 실행되는 곳이고, 데이터 전달 경계는 이 장의 정의상 경계·인터페이스 렌즈에 속합니다. 12장은 같은 단계를 "전달 계약"으로 부르며 계약으로 다루므로 명칭도 어긋납니다.
- **최소 수정**: 구성요소 행은 "버전이 붙은 정적 데이터 파일 또는 읽기 전용 API"처럼 책임을 가진 부분으로 바꾸고, 전달 계약은 경계와 인터페이스 행으로 옮기며, 배포 환경은 구성요소 목록이 아니라 실행 환경·제약 서술로 이동합니다.

### P1-03 · 제약이 판단 규칙과 체크리스트에서 사라집니다

- **대상**: 「6. 제약과 품질 속성」, 판단 규칙 7 "속도·보안·비용·접근성·변경 용이성·복구 중 현재 중요한 품질을 우선순위로 기록합니다", 체크리스트의 우선순위 항목
- **이유**: 렌즈 이름에는 제약이 있지만 대표 질문·판단 규칙·체크리스트는 모두 "우선순위" 언어만 사용합니다. 그 결과 개인정보 금지, 데이터 이용 조건, 법규, 예산처럼 협상 대상이 아닌 조건이 속도와 경쟁하는 항목으로 읽힙니다. 12장은 같은 항목을 C-01~C-04라는 별도 제약으로 두고 "공개됐다는 사실만으로 재배포를 허용한다고 보지 않습니다"라고 명시하므로 사례와도 어긋납니다. 이 장의 대시보드 표 역시 "공개 데이터만 사용"만 적어 이용 조건 확인 필요성이 지워졌습니다.
- **최소 수정**: 판단 규칙 7을 두 단계로 나눠 "먼저 협상 불가한 제약을 목록으로 고정하고, 남은 품질 속성만 우선순위를 매긴다"로 바꾸고, 체크리스트에 "지켜야 하는 제약(권리·개인정보·법규·예산·호스팅 범위)을 우선순위와 분리해 적었나요?" 항목을 1개 추가합니다. 대시보드 표의 제약 칸은 "확인된 이용 조건 범위의 공개 데이터만 사용"으로 조정합니다.

### P1-04 · 소유·신뢰 경계 표시가 없어 외부 구성요소 취급이 장 안에서 충돌합니다

- **대상**: 「3. 경계와 인터페이스」의 "경계(boundary)는 책임과 신뢰가 바뀌는 지점", 대시보드 표의 "공개 원천", 「흔한 오해와 실패」의 "외부 서비스를 내부 구성요소처럼 신뢰함"
- **이유**: 경계 정의가 용어집(`boundary`: "책임, 신뢰, 소유권 또는 실행 환경이 달라지는 경계")보다 좁아 소유권과 실행 환경이 빠졌습니다. 그 상태에서 외부 기관이 발표하는 공개 원천이 내부 구성요소와 같은 열에 아무 표시 없이 나열되는데, 흔한 오해 절은 외부 서비스를 내부처럼 신뢰하는 것을 실패로 듭니다. 같은 장 안에서 상반된 신호를 줍니다.

- **대상**: 「5. 흐름」, 대시보드 표 흐름 행 "원천 발표부터 수집·검사·저장·전달·렌더링까지의 정상 및 실패 경로"
- **이유**: 한 줄로 묶으면 사용자가 필터를 바꾸면 수집과 품질 검사가 실행된다고 읽힙니다. 정적 전달에서는 수집·검사·빌드가 조회 이전에 끝나 있고 사용자 요청은 산출물을 읽을 뿐입니다. 3장이 "정적 사이트는 실행 중인 업무 API 없이 미리 만든 파일과 읽기 전용 데이터만으로" 동작한다고 설명하고, 12장이 "갱신이 새 산출물과 새 배포로 이루어진다"고 못 박은 것과 충돌합니다. 본문이 "정해진 시각의 데이터 수집, 큐에 쌓인 작업, 배포와 장애 복구도 흐름"이라고 옳게 적어 놓고도 대표 예시에서 이를 한 줄로 합쳐 버립니다.
- **최소 수정**: 흐름 행을 트리거별 3줄(① 사용자 조회 흐름 ② 일정에 따른 수집·검증·빌드·배포 흐름 ③ 실패 감지와 복구 흐름)로 나누고, 각 줄에 시작 조건과 관찰 위치를 한 칸씩 적습니다.

### P1-08 · 증거 표에 로컬과 공개 환경의 구분이 없습니다

- **대상**: 「화면 동작과 시스템 완성도를 구분하기」 표의 "배포 후 핵심 흐름 확인" 행
- **이유**: 이 행이 로컬 미리보기인지 실제 공개 URL인지 표시하지 않습니다. 12장은 "로컬 빌드 성공은 원격 CI가 같은 환경에서 성공함, 공개 호스팅이 올바른 파일을 제공함, 실제 URL과 하위 경로에서 데이터·자산이 열림"을 보장하지 않는다고 명시했고, `PROJECT_CONTEXT.md`도 실제 GitHub Pages 배포 검증이 남았다고 기록합니다. 이 장이 증거 범위를 가르치는 장이므로 자기 기준을 스스로 지키지 않는 셈이 됩니다. 같은 표의 "화면 모형이 보임" 행도 아직 확인되지 않은 것에서 접근성·모바일을 빠뜨립니다.
- **최소 수정**: 행을 "로컬 빌드·미리보기 확인"과 "공개 URL에서 핵심 흐름 확인"으로 나누고, 화면 모형 행의 미확인 열에 "키보드·보조 기술·작은 화면"을 추가합니다.

### P1-09 · 브라우저 개발자 도구 명칭을 단정합니다

- **대상**: 「실제 작업에서 보이는 시스템 증거」의 "**화면과 Network 탭**"
- **이유**: 특정 브라우저 UI의 패널 이름을 확인 없이 사실처럼 씁니다. `PROJECT_CONTEXT.md`는 5장에서 "브라우저별 개발자 도구 명칭의 한계"를 이미 보완했다고 기록하는데 이 장에는 같은 보완이 없습니다. 또한 `research/source-map.md`의 이 파일 행은 SWEBOK 2건뿐이고 MDN 근거가 없어, 저장소 안에서 이 주장을 추적할 경로도 없습니다. 루브릭 치명 항목 중 "특정 제품의 현재 기능을 확인하지 않고 단정함"에 근접합니다.
- **최소 수정**: "브라우저 개발자 도구의 네트워크 기록(브라우저마다 이름이 다를 수 있습니다)"으로 바꾸거나, 5장과 같은 MDN 적용 범위 행을 이 파일에 대해 `source-map`에 추가합니다.

### P1-10 · AI 지시 예시에 금지 범위가 없습니다

- **대상**: 「AI와 작업할 때」의 지시 블록 — "현재 저장소를 읽고 수정 없이"
- **이유**: 3장 예시는 "토큰·쿠키·개인정보·비공개 데이터는 출력하지 말고 파일은 수정하지 마라", 12장 예시는 "네트워크·설치·파일 수정·Git·배포는 금지한다"까지 적습니다. `AGENTS.md` 4절도 네트워크 접근, 패키지 설치, `git commit`·`push`를 승인 전 금지 행동으로 규정합니다. 이 장의 예시만 "수정 없이"에 그쳐, 학습 목표 3("AI 작업 지시에 책임과 경계와 검증을 포함한다")을 예시가 스스로 충족하지 못합니다.
- **최소 수정**: 지시 마지막에 "네트워크·설치·파일 수정·Git·배포는 금지한다 / 토큰·개인정보는 출력하지 마라 / 확인한 파일 경로와 미확인 범위를 구분해 보고하라" 3줄을 추가합니다.

### P1-11 · 학습 목표 3이 연습과 체크리스트에서 관찰되지 않습니다

- **대상**: 「짧은 연습」, frontmatter의 `learningObjectives` 세 번째 항목
- **이유**: 연습은 렌즈 표 채우기와 실패 한 건 추적만 요구하고, 체크리스트 마지막 항목은 "AI가 제시한 구조와 완료 주장을 확인했나요?"로 AI 출력 검증만 다룹니다. 독자가 책임·경계·검증을 포함한 지시를 실제로 작성하는지 확인할 산출물이 없습니다. `AGENTS.md` 9절 완료 정의의 "목표가 지켜짐"을 이 장 안에서 증명하지 못합니다.
- **최소 수정**: 연습 마지막에 "표에서 `미확인` 칸 하나를 골라 범위·권한·산출물·검증 방법을 포함한 읽기 전용 지시문을 5줄 이내로 쓰세요" 한 단계를 추가합니다.

### P1-12 · flow 표제어와 미증명 범위 문장이 빠졌습니다

- **대상**: 「관련 용어와 출처」 — 용어 목록과 출처 목록
- **이유**: 여섯 렌즈 중 `flow`만 `development-glossary.md`에 표제어가 없습니다(software, component, responsibility, boundary, interface, state, quality attribute, constraint, architecture는 모두 있음). 또 3장은 "출처의 확인일과 적용 범위는 저장소의 `research/source-map.md`에서 관리합니다"로, 12장은 출처가 무엇을 증명하지 못하는지 한 문단으로 닫는데 이 장에는 둘 다 없습니다. `RULES.md` 7번과 루브릭 근거 항목의 취지에 미달합니다.
- **최소 수정**: 용어집에 `flow` 표제어를 추가하고(또는 이 장에서 흐름을 렌즈 이름으로만 쓰는 이유를 밝히고), 출처 절 끝에 "확인일과 적용 범위는 `research/source-map.md`에서 관리합니다"와 "이 출처들은 소프트웨어공학 교육 범위를 뒷받침하지만 브라우저 도구 동작, 캐시 최신성, 정적 배포의 세부는 증명하지 않습니다" 두 문장을 추가합니다.

# P2 개선 권장

### P2-01 · frontmatter `description`이 여섯 렌즈 중 둘을 빠뜨립니다
- **대상**: "구성요소, 경계, 상태, 흐름, 제약으로 이해합니다"
- **이유**: 책임과 품질 속성이 빠져 본문의 "여섯 렌즈" 프레임과 어긋납니다. 목록·검색 결과에서 먼저 보이는 문장입니다.
- **최소 수정**: 여섯 이름을 그대로 쓰거나 "여섯 개의 시스템 렌즈"로 요약합니다.

### P2-02 · 집 비유 목록이 일곱 항목이라 렌즈 수와 어긋납니다
- **대상**: 「집으로 이해하기」의 "설계도, 점검표와 검사 기록은 **명세와 검증 증거**입니다"
- **이유**: 여섯 렌즈와 같은 형식의 목록에 일곱 번째 항목이 있어 독자가 렌즈를 일곱 개로 셀 수 있습니다.
- **최소 수정**: 해당 줄을 목록에서 분리하고 "이것은 일곱 번째 렌즈가 아니라 모든 렌즈에 걸치는 증거입니다"를 덧붙입니다.

### P2-03 · 집 비유에 '완공' 프레임이 남아 있습니다
- **대상**: 「비유가 맞는 지점」의 "완공 사진과 안전 검사 기록은 서로 다른 증거입니다"
- **이유**: 완공이라는 종료 시점이 존재한다는 전제가 유지됩니다. 12장은 "한 번의 '교정 완료'로 끝내지 않고 변경마다 데이터와 사용자 흐름을 다시 확인해야 합니다"라고 명시합니다. 이 장의 핵심 주장(화면 동작 ≠ 시스템 완료)과도 직접 연결되는 한계입니다.
- **최소 수정**: 「비유가 깨지는 지점」에 "집에는 완공이 있지만 소프트웨어에는 종료 시점이 없고 변경·배포마다 증거를 다시 만들어야 합니다" 한 문장을 추가합니다.

### P2-04 · 비유에서 사람이 흐름으로만 매핑됩니다
- **대상**: 「집으로 이해하기」의 "사람, 전기와 물이 이동하는 경로는 **흐름**입니다"
- **이유**: 사용자와 운영자가 흐름의 내용물처럼 읽혀 P1-05의 혼동을 강화합니다.
- **최소 수정**: 깨지는 지점에 "집 비유에서 사람은 이동 경로로만 나타나지만, 소프트웨어에서 사용자와 운영자는 입력을 만들고 결과를 판단하며 때로 승인 책임까지 맡는 행위자입니다" 한 문장을 추가합니다.

### P2-05 · 재사용한 그림의 단순화 한계가 표시되지 않습니다
- **대상**: 「예: 데이터 분석 대시보드를 시스템으로 보기」의 SVG
- **이유**: 12장은 같은 그림에 대해 "되먹임을 첫 단계로 돌아가는 한 화살표로 단순화했고 사용자와 운영자를 한 상자에 묶었지만 두 역할이 같다는 뜻은 아닙니다"라고 밝혔습니다. 이 장에는 그 단서가 없어 오해가 그대로 옮겨옵니다.
- **최소 수정**: 그림 아래 문단에 같은 취지의 한 문장을 추가합니다.

### P2-06 · 책임 정의가 용어집보다 좁습니다
- **대상**: 「2. 책임」의 "구성요소가 맡고 보장해야 하는 일입니다"
- **이유**: 용어집 `responsibility`는 "…와 실패 처리 범위"까지 포함합니다. 이 장의 실패 모드 절과 판단 규칙 5가 실패 처리를 책임으로 다루므로 정의만 어긋납니다.
- **최소 수정**: 정의 문장에 "그리고 그 일이 실패했을 때 처리할 범위"를 넣습니다.

### P2-07 · 두 실패 모드가 서로 반대 신호로 읽힙니다
- **대상**: 「흔한 오해와 실패」의 "모든 것을 하나의 백엔드로 묶음"과 "복잡한 구조가 더 전문적이라고 생각함"
- **이유**: 앞 항목은 나누라고, 뒤 항목은 합치라고 읽혀 판단 기준 없이 나란히 놓입니다. 3장은 "가장 단순한 충분한 구조를 선택하고, 필요 신호가 생기면 숨기지 않는다"로 이를 중재합니다.
- **최소 수정**: 앞 항목 제목을 "모든 책임을 '백엔드'라는 한 단어로 묶음"으로 바꿔 배포 분리가 아니라 책임 구분의 문제임을 드러내고, 뒤 항목에 3장의 판단 기준을 한 줄 인용합니다.

### P2-08 · 사본 자체가 실패처럼 읽힙니다
- **대상**: 「흔한 오해와 실패」의 "**같은 진실을 여러 곳에 저장함**"
- **이유**: 용어집 `source of truth`는 "시스템 전체에 하나만 있어야 한다는 뜻이 아니라 상태 종류마다 책임 위치가 다를 수 있습니다"라는 예외를 명시하고, 3장도 "입력 중인 필터의 권위는 브라우저일 수 있고 저장된 보고서의 권위는 데이터베이스일 수 있습니다"로 같은 예외를 답니다. 현재 표현은 캐시와 사본을 그 자체로 잘못된 것으로 오해하게 합니다.
- **최소 수정**: 제목을 "권위를 정하지 않은 채 같은 값을 여러 곳에서 고침"으로 바꾸고, 상태 종류마다 권위가 다를 수 있다는 예외 문장을 덧붙입니다.

### P2-09 · 증거 문구가 바로 위 표와 대응하지 않습니다
- **대상**: "`빌드 통과`, `로컬 요청 성공`, `모바일 화면 확인`, `복구 연습 완료`는 서로 다른 주장을 증명합니다"
- **이유**: 표의 네 행(화면 모형/대표 요청/실패 테스트/배포 확인)과 이름이 달라 독자가 대응을 스스로 만들어야 합니다.
- **최소 수정**: 표에 "이 증거를 부르는 이름" 열을 넣거나 본문 예시를 표의 행 이름과 같은 표현으로 바꿉니다.

### P2-10 · 용어 목록에 본문이 가르친 세 용어가 빠졌습니다
- **대상**: 「관련 용어와 출처」의 "software, component, responsibility, boundary, interface, state, quality attribute, architecture"
- **이유**: 본문이 실제로 가르치는 `constraint`, `source of truth`(권위 있는 원본), `trust boundary`(신뢰가 바뀌는 지점)가 빠져 있습니다. 세 용어 모두 용어집에 표제어가 있습니다.
- **최소 수정**: 목록에 세 용어를 추가합니다.

### P2-11 · 아키텍처를 정의하지 않고 세 번 언급만 합니다
- **대상**: "복잡한 아키텍처를 먼저 설계하라는 뜻도 아닙니다", "정답 아키텍처를 고르는 공식이 아니라", "큰 아키텍처를 발명하라는 요청이 아닙니다"
- **이유**: 정의 없이 부정문으로만 등장해, 비개발자가 "여섯 렌즈로 시스템 지도를 그리는 일"과 "아키텍처를 결정하는 일"을 같은 것으로 볼 위험이 있습니다. 용어집은 architecture를 "구조적 결정"으로 정의하므로 관찰과 결정의 차이가 핵심인데 본문에 그 구분이 없습니다. `06-requirements-design/architecture-and-frameworks`는 지정된 11개 파일 밖이라 상태와 내용을 확인하지 못했습니다. 12장은 미완성 링크 대상에 상태 주석을 다는 선례를 남겼습니다.
- **최소 수정**: "이 장은 현재 구조를 관찰하는 지도를 만들고, 아키텍처는 그 위에서 내리는 구조적 결정입니다" 한 문장을 넣고, 링크 대상의 현재 상태를 확인해 필요하면 12장처럼 주석을 답니다.

### P2-12 · 판단 규칙 3에 산출물이 없습니다
- **대상**: 판단 규칙 3 "…여러 곳의 복제된 진실을 피합니다"
- **이유**: 다른 일곱 규칙은 "적습니다·정합니다·그립니다·기록합니다"로 산출물이 남지만 이 규칙만 회피 지시라 확인할 대상이 없습니다.

# 추가 출처 확인 목록

먼저 범위를 구분합니다. 이 검토에서 외부 출처를 새로 열지 않았습니다. `research/source-map.md`가 **증명하는 것**은 이 파일에 대해 SWEBOK 2건(전체 지도, 세부 주제)이 2026-08-04 확인일과 함께, "생명주기를 잇는 시스템으로 보는 교육 범위" 및 "렌즈가 세부 주제를 연결하는 범위"라는 적용 범위로 기록됐다는 사실뿐입니다. **증명하지 못하는 것**은 그 문서들이 아래 개별 주장을 실제로 뒷받침하는지, 그리고 링크 대상의 현재 내용입니다.

1. **여섯 렌즈 구성 자체** — 표준 분류가 아니라 이 핸드북의 편집 장치임을 본문에 표시하거나, 렌즈별로 대응하는 SWEBOK 지식 영역을 `source-map` 적용 범위에 지정해야 합니다. 현재는 "렌즈가 세부 주제를 연결한다"는 저장소 자체의 서술뿐입니다.
2. **브라우저 개발자 도구의 네트워크 기록과 패널 명칭** — 이 파일 행에 MDN 근거가 없습니다(3장·5장 행에는 있음). 웹 플랫폼 1차 자료 확인이 필요합니다.
3. **"한 데이터가 브라우저·캐시·데이터베이스에 서로 다른 시점의 사본으로 존재"** — 캐시와 최신성에 관한 1차 자료가 이 파일 행에 없습니다.

# 상태 권고

- **현재 `draft` 유지가 맞습니다.** frontmatter에 `reviewEvidence`가 없어 `docs/project/content-lifecycle.md`의 draft→review 조건 중 "독립 리뷰어에게 검토를 요청"과 "`request:`로 시작하는 기록"이 충족되지 않았습니다. `PROJECT_CONTEXT.md`가 검토 계약만 준비하고 실제 요청은 없다고 기록한 것과 일치합니다.
- **`review`로 올리기 전 필요한 것**: P1 12건 처리(또는 부분 수용·기각 근거를 검토 기록에 남기기) → 자체 루브릭 재점검 → `npm run check` 성공 확인(저는 명령을 실행하지 않았습니다) → 작성 맥락을 공유하지 않은 독립 리뷰어에게 실제 요청 → `reviewEvidence`에 `request:` 기록. P2는 `review` 승격을 막지 않습니다.
- **`ready`는 아닙니다.** 사람 기술 검토, 사람 편집 검토, 비개발자 독자 테스트, 출처 확인 중 어느 것도 이 파일에 기록돼 있지 않습니다. 점수 16/18로 15점 임계는 넘지만, 루브릭 문서가 밝히듯 점수는 필요조건일 뿐입니다.
- **이 검토 문서의 지위**: `content-lifecycle.md`는 "AI 검토 본문 또는 사람이 근거를 직접 확인하지 않고 AI 지적을 승인한 기록은 사람 `technical:` 증거가 아니다"라고 명시합니다. 이 검토 결과는 `technical:` 증거로 쓸 수 없고, 검토 요청·재판정 기록의 일부로만 보관해야 합니다.
