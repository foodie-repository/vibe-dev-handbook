## 3. P1 review 전 필수

**[P1-1] `tracked` 정의가 스테이징 영역을 배제합니다**

189행 “Git이 이미 **현재 이력의** 관리 대상으로 알고 있는 파일”. `09-git-github/git-and-github.md` 76행은 “Git **이력이나 스테이징 영역이** 알고 있는 파일”로 정의합니다. `git add`만 한 새 파일은 이력에 없지만 tracked입니다. 위험: 독자가 새 파일을 무조건 untracked로 분류해 193행이 경고한 “이미 스테이징된 변경”을 놓칩니다. 수정: 09장 정의 문구에 맞춰 “이력 또는 스테이징 영역이 알고 있는”으로 통일.

**[P1-2] ignored인지 untracked인지 판정할 명령이 없습니다**

229~236행 진단 6단계는 `git status --short --branch`, `git diff`, `git diff --staged`, `git ls-files`만 제시합니다. 249행 실패 표는 원인을 “untracked·ignored이거나 staged”로 나누라고 요구하고 체크리스트 298~299행도 ignored 구분을 묻지만, 제시된 네 명령은 ignored와 untracked를 같은 “빈 출력”으로 되돌립니다(`git ls-files`는 둘 다 결과 없음, 기본 `status`는 ignored 미표시). 위험: 비개발자가 절차를 그대로 따라도 원인 분기에 도달하지 못하고 “파일이 사라졌다”고 잘못 결론냅니다. 수정: 6단계에 `git check-ignore -v -- 경로`(또는 `git status --short --ignored`) 한 줄과 “기본 status는 ignored를 보여 주지 않음” 한 문장 추가.

**[P1-3] 파일이 실제로 존재하는지 확인하는 단계가 없습니다**

199~240행 진단 1~7단계에는 CWD·저장소 루트·Git 상태 명령은 있으나, 대상 디렉터리의 실제 항목과 정확한 파일명을 보는 명령이 하나도 없습니다. 5단계(223~225행)는 “검색 결과 수와 각 상위 경로를 비교합니다”라고만 하고 수단을 주지 않습니다. 위험: 251~252행이 구분하라고 한 `No such file`(부재)과 `Permission denied`(권한)를 독자가 실행 가능한 방법으로 확인하지 못합니다. 수정: 2단계와 3단계 사이에 대상 상위 폴더의 목록 확인 한 줄(예: `ls -la 상위경로`)과 “출력이 없으면 부재, 오류 메시지가 다르면 권한 문제”라는 판정 문장 추가.

**[P1-4] `staged`를 정의 없이 판정하게 합니다**

193·236·249행이 “스테이징된 변경”과 `staged`를 쓰고 체크리스트 298행은 “tracked·untracked·ignored와 staged 상태를 서로 구분했나요?”라고 묻지만, 이 장은 스테이징을 정의하지 않습니다. `reference/development-glossary.md`에도 staging/staged 항목이 없습니다(15~46행, 143~162행 확인). 사이드바 순서상 02장은 09장보다 먼저 읽힙니다. 위험: 독자가 판정 불가능한 항목을 체크하며 이해했다고 오인합니다. 수정: 193행에 한 문장 정의(“다음 커밋에 넣으려고 골라 둔 상태”) 추가 또는 용어집에 항목 추가 후 링크.
