3. **비유·상태·접근성의 최소 행동**: P1-06, P2-03, P2-09, P2-10을 묶어 현재 시드 장의 실제 범위, 환경 차이, 상태 중복과 viewport·실제 기기·포커스 확인을 과장 없이 연결합니다.
4. **개발자 도구의 관찰 순서와 한계**: P2-05, P2-06, P2-07, P2-08을 묶어 관찰 위치, 재현 순서, Console 출처와 임시 DOM 편집의 증거 범위를 정리합니다.
5. **안전한 연습과 학습 목표 검증**: P1-07과 P1-08을 묶어 되돌릴 수 있는 공개 상호작용만 허용하고 다섯 책임을 실제 증상에 다시 연결하게 합니다.
6. **배포 뒤 이전 화면 증상**: P2-11을 증상 표와 배포 장 교차 링크에만 최소 반영하고 캐시 세부 강의는 위임합니다.
7. **출처·생명주기 증거**: P1-09와 P1-10을 묶어 직접 출처 대기 범위를 기록하고, 실제 반영·검증 뒤에만 `request:`·`automated:` 증거와 `review` 승격을 적용합니다. P2-12는 기각해 용어집 변경을 만들지 않습니다.

## 반영 작업의 수용 기준

- 독자가 HTML·CSS·JavaScript라는 자원·언어, DOM이라는 모델과 렌더링이라는 과정을 같은 종류로 오해하지 않습니다.
- 코드의 상태 반영과 브라우저 화면 계산, 같은 문서 안 갱신과 새 문서 로드를 구분합니다.
- 서버 응답·UI 상태·현재 DOM·렌더링 화면·사용자 작업 성공을 서로 대신할 수 없는 증거로 설명합니다.
- 개발자 도구의 탭 이름·Console 출처·임시 DOM 편집·viewport와 실제 기기의 증거 한계를 과장 없이 설명합니다.
- 연습은 제3자 상태를 바꾸지 않는 되돌릴 수 있는 상호작용으로 제한하고 학습 목표 1의 책임 구분을 실제로 요구합니다.
- 직접 확인하지 않은 DOM·렌더링·개발자 도구·WCAG 세부는 `research/source-map.md`의 후속 조사 대기로 남습니다.
- P1 10건과 P2 12건 각각의 반영 위치 또는 부분 수용·기각 이유를 이 문서에서 역추적할 수 있습니다.
- 공개 원고의 `contentStatus`는 반영·검증·증거 기록이 끝나기 전까지 `draft`를 유지합니다.

## 상태와 증거 경계

재판정 시점에는 Opus 지적의 타당성과 다음 수정 범위만 정했으므로 원고는 `draft`이며 `reviewEvidence`도 추가하지 않습니다. 후속 구현에서 최소 보완, 자체 루브릭 재점검, `npm run check`, 렌더링 확인과 실제 `request:` 기록을 모두 확인한 뒤에만 `review` 승격을 판단합니다. AI 독립 검토와 Codex 재판정은 사람 기술·편집 검토와 실제 비개발자 독자 테스트를 대신하지 않으며, 직접 출처 확인 없이는 `ready`를 논의하지 않습니다.
