## 3. 위치별 finding

**R21-I01 — Important/P1 — 부분 스테이징 뒤 커밋 후보와 검증한 상태를 연결해야 합니다.**

- **위치:** `src/content/docs/09-git-github/branch-commit-pull-request.md`의 「커밋은 독립 검토 가능한 의미 단위입니다」 마지막 문단, 「AI와 함께 작업하는 안전 순서」 3~5단계, 체크리스트의 검증한 파일 선택 항목.
- **최소 인용:** “경로나 변경 조각 단위로 stage 후보를 나누고”, “검증한 파일만 로컬 커밋 후보로 선택했습니다.”
- **관찰·근거:** 작업 트리를 검증한 뒤 일부 조각만 stage하면 index는 테스트한 상태와 달라질 수 있습니다. 본문은 staged diff와 남긴 변경을 읽도록 하지만 제외한 코드·설정·데이터 제약에 검증 결과가 의존했는지는 확인하지 않습니다. 인접 `git-and-github.md`는 이 차이와 필요한 후보 검증을 명시합니다.
- **영향·기준:** 테스트한 파일과 커밋할 스냅샷을 같은 증거 대상으로 취급하면 불완전한 커밋을 검증 완료로 보고할 수 있습니다. C02·C04·C06.
- **최소 수정:** 부분 스테이징 또는 검증 이후 변경 시 작업 트리와 후보의 차이·의존성을 확인하고, 필요하면 사용자 변경을 보존한 별도 환경에서 후보 스냅샷을 검증하도록 추가합니다. 체크리스트도 “파일”보다 “후보 스냅샷과 연결된 검증”으로 정밀하게 고칩니다.
- **재확인:** 작업 트리에는 필요한 데이터 제약이 있지만 index에는 없는 사례에서 기존 테스트 결과만으로 후보 성공을 선언하지 않아야 합니다.
- **계보 구분:** R08-I03의 해소를 재개하는 지적이 아닙니다. 그때 전체 검토하지 않았던 R21 원고의 자체 절차에 대한 새 finding입니다. 이번 준비 6파일은 별도의 index 일치 증거가 있으므로 해당 불일치 사례로 간주하지 않습니다.

**R21-I02 — Important/P1 — 안전 점검 명령이 untracked 표시 설정에 의존합니다.**

- **위치:** 같은 원고의 upstream 절 명령 블록, 「커밋은 독립 검토 가능한 의미 단위입니다」의 status·diff 블록과 앞뒤 안내.
- **최소 인용:** `git status --short --branch`, `git status --short`, “untracked 파일은 … status와 파일 내용을 함께 확인합니다.”
- **관찰·근거:** 제시한 명령은 `status.showUntrackedFiles` 설정에 따라 새 파일을 숨기거나 새 디렉터리로 묶을 수 있습니다. 이 장은 해당 출력을 untracked 검토의 출발점으로 쓰지만 명시적 표시 옵션과 한계를 설명하지 않습니다. 제공된 R08 기록과 현재 중심 장은 이를 `--untracked-files=all`로 보완했습니다.
- **영향·기준:** 새 소스·개인 설정·비밀이 있는 파일을 확인 목록에서 놓칠 수 있습니다. C04·C06.
- **최소 수정:** 안전 점검용 status 예에 `--untracked-files=all`을 명시하고 기본 출력의 설정 의존성, ignored 파일은 여전히 별도라는 한계를 짧게 설명합니다.
- **재확인:** untracked 표시를 숨긴 가상 저장소에서도 권장 점검이 새 파일을 열거해야 하며 ignored까지 포함한다고 설명해서는 안 됩니다.
- **계보 구분:** R08-I01은 해당 중심 장에서 해소된 상태로 유지합니다. 여기서는 별도 명령 블록과 안전 절차를 가진 R21 원고를 판단했습니다.

**R21-I03 — Important/P1 — reset의 commit 형식과 경로 지정 형식을 구분하지 않습니다.**

- **위치:** `src/content/docs/09-git-github/undo-merge-conflict-release.md`의 「`git reset`: branch tip과 index·작업 트리의 기준을 바꿀 수 있습니다」.
- **최소 인용:** “reset은 선택한 mode에 따라 현재 branch가 가리키는 commit, index와 작업 트리를 서로 다른 범위로 바꿉니다.”
- **관찰·근거:** 이어지는 soft·mixed·hard 설명은 commit을 대상으로 하는 형식의 설명입니다. 제공된 R21-S05·S16은 경로 지정 형식이 index만 변경하고 HEAD와 작업 트리는 바꾸지 않는다고 구분합니다. 본문은 이러한 형식 차이를 명시하지 않습니다.
- **영향·기준:** “stage만 취소”와 “브랜치 기준 이동”을 판단해야 하는 장에서 reset의 영향 범위를 모드만으로 판정하게 됩니다. C02·C04·C05·C06.
- **최소 수정:** 모드 목록이 commit 형식에 대한 설명임을 밝히고, 경로 지정 형식은 선택한 경로의 index만 바꾸며 HEAD·작업 트리를 이동하지 않는다는 문장을 추가합니다. 실행 지시를 늘릴 필요는 없습니다.
- **재확인:** stage만 해제하는 후보와 브랜치 tip을 옮기는 후보의 전후 상태 표가 서로 달라야 합니다.

**R21-I04 — Important/P1 — hard reset의 미추적 파일 손실 범위가 빠져 있습니다.**

- **위치:** 같은 원고의 reset 모드 목록, 「reset mode를 복사해 실행합니다」.
- **최소 인용:** “`--hard` … 추적 파일의 로컬 변경을 잃을 수 있습니다.”
- **관찰·근거:** R21-S05는 hard reset이 untracked 경로도 덮어쓸 수 있다고 명시합니다. 대상 tracked 파일을 쓰는 데 방해되는 미추적 파일·디렉터리가 제거될 수 있다는 경계가 본문에 없습니다.
- **영향·기준:** 손실 경계를 tracked 수정으로만 이해하면 아직 Git에 넣지 않은 작업을 보호하지 못할 수 있습니다. 복구 명령을 안전하게 구분하는 핵심 수용 기준에 해당합니다. C05·C06.
- **최소 수정:** tracked 로컬 수정뿐 아니라 대상 파일 배치를 방해하는 미추적 파일·디렉터리도 손실될 수 있음을 추가합니다. 모든 untracked 파일을 일괄 삭제한다고 일반화하지는 않습니다.
- **재확인:** 손실 예측과 보존 목록에 충돌하는 미추적 경로가 포함돼야 합니다. 검증이 필요하면 비민감 임시 저장소에 한정하고 실제 프로젝트에서 hard reset을 시험하지 않습니다.

**R21-I05 — Important/P1 — 보호 브랜치가 tracked 미커밋 수정과 index 상태도 보존하지 못한다는 설명이 필요합니다.**

- **위치:** 같은 원고의 「명령 전에 여섯 상태를 분류하세요」 표 뒤 보존 문단, 「파괴 가능성이 있는 작업의 안전 계약」 보존 단계, 로컬 커밋 재구성 사례.
- **최소 인용:** “패치·보호 브랜치·독립 사본처럼 되돌아갈 기준”, “untracked 파일과 외부 상태는 브랜치가 보호하지 않기 때문입니다.”
- **관찰·근거:** 보호 브랜치는 커밋을 가리키는 참조입니다. untracked뿐 아니라 아직 커밋되지 않은 tracked 수정과 index에만 있는 별도 내용도 보존하지 않습니다. 기본 diff 하나 역시 staged·unstaged·untracked 전체를 보존하지 않습니다. 현재 문장은 보호되지 않는 대표 대상을 일부만 열거해 보존 수단과 상태의 대응이 부족합니다.
- **영향·기준:** 커밋을 가리키는 보호 참조만 만든 뒤 index·작업 트리를 변경하면 필요한 수정이 그 참조에 없을 수 있습니다. C02·C06.
- **최소 수정:** 보호 참조는 커밋된 이력만 보존한다는 점을 명시하고, staged·unstaged·untracked 상태별로 보존할 내용과 복원 방법을 따로 확인하도록 연결합니다. 패치도 어떤 비교에서 생성됐고 어떤 내용을 포함하지 않는지 확인하게 합니다.
- **재확인:** HEAD=A, index=B, 작업 파일=C, 별도 untracked 파일이 있는 경우 각 상태의 보존 위치와 복원 방법을 설명할 수 있어야 합니다. 자동 stash·사용자 변경 삭제를 기본 해결책으로 추가하지 않습니다.

**R21-I06 — Important/P1 — 모바일에서 복구 검토 지시문의 자연어를 가로로 왕복하며 읽어야 합니다.**

- **위치:** 같은 원고의 「AI의 되돌리기 제안을 검토하는 읽기 전용 지시」의 `text` 블록.
- **최소 인용:** “미커밋, staged, 로컬 전용 commit, 공유 commit, tag·release, 배포·데이터·외부 효과를 구분하라.”
- **관찰·근거:** PNG 22·23과 45·46에서 긴 문장이 오른쪽으로 이어집니다. 오른쪽 끝을 읽는 화면에서는 문장 앞부분과 짧은 지시가 화면 밖으로 나갑니다. 제공된 관측값의 가로 이동은 350px이며 실제 이미지와 부합합니다. 데스크톱 PNG 16·39에서는 전체 문장을 읽을 수 있습니다.
- **영향·기준:** 이 블록은 복구 범위와 실행 금지를 전달하는 핵심 학습 지시입니다. 2차원 배치가 필요한 표나 문법 보존이 필요한 셸 명령과 달리 자연어 문장에 반복적인 가로 이동을 요구할 이유가 없습니다. C01·C07·C08.
- **최소 수정:** 기존 지원 방식인 `text wrap`처럼 해당 자연어 블록에 표시 줄바꿈을 적용합니다. 문장 내용·빈 줄·목록을 보존하며 화면 폭을 맞추기 위한 원문 하드랩이나 전역 코드 블록 스타일 변경은 하지 않습니다.
- **재확인:** 390px 라이트·다크에서 지시문 전체가 가로 이동 없이 읽혀야 합니다. 데스크톱에서도 겹침이 없고, 명령 블록과 표의 기존 표현은 유지돼야 합니다. 이것만으로 키보드·보조 기술 적합성을 주장하지 않습니다.

**R21-M01 — Minor/P2 — 첫 커밋 전 `git diff HEAD`의 실패 조건이 설명되지 않습니다.**

- **위치:** `branch-commit-pull-request.md`의 커밋 전 네 명령 블록.
- **최소 인용:** `git diff HEAD`.
- **관찰·근거:** 첫 커밋 전에는 비교 대상 HEAD 커밋이 없어 이 명령이 실패합니다. 현재 중심 장에는 status·새 파일 내용·`git diff --staged`를 사용하는 대안이 있습니다. R21은 해당 예외를 설명하거나 그 설명으로 직접 연결하지 않습니다.
- **영향·기준:** 초기 저장소에서 정상적인 기준 부재를 저장소 오류로 오해할 수 있습니다. C02·C04.
- **최소 수정:** 첫 커밋 전 예외와 대안을 한 문장으로 추가하거나 중심 장의 해당 설명으로 연결합니다.
- **재확인:** HEAD가 있는 상태와 없는 상태의 비교 기준을 구별할 수 있어야 합니다. 이 원고가 `git diff HEAD`를 staged·unstaged의 합집합이라고 직접 설명하지는 않으므로 별도 순변화 오류를 추가하지 않습니다.

**R21-M02 — Minor/P2, 두 원고 공통 — 승인 정책과 로컬·원격 병합의 범위를 일관되게 표시해야 합니다.**

- **위치:** `branch-commit-pull-request.md`의 「AI와 함께 작업하는 안전 순서」 6단계, `undo-merge-conflict-release.md`의 충돌 해결 7단계.
- **최소 인용:** “push·PR·리뷰 요청·병합·배포는 각각 별도 승인”, “원격 공유나 병합은 별도 승인 뒤 수행합니다.”
- **관찰·근거:** PR 절에서는 “GitHub PR 병합”으로 정확히 한정하지만 다른 절에서는 `병합`만 사용합니다. 로컬 merge도 가능한 문맥이며, 이 승인 절차가 Git 내장 조건인지 핸드북 정책인지와 이미 승인된 범위의 처리도 해당 절에서는 드러나지 않습니다. 중심 장은 이 둘을 명시적으로 구분합니다.
- **영향·기준:** 병합을 모두 외부 쓰기로 읽거나 이미 승인된 행동도 매번 새 승인이 필요한 것으로 읽을 여지가 있습니다. 전체 문맥에 승인 경계가 있으므로 Minor로 판정합니다. C04·C06·C08.
- **최소 수정:** 로컬 병합과 GitHub PR 병합의 상태 변화·승인 범위를 구분하고, 승인 절차는 핸드북 정책이며 기존 명시적 승인·상시 정책을 범위 안에서 따른다고 짧게 연결합니다.
- **재확인:** 로컬 통합, 원격 공유, 원격 PR 병합의 권한을 서로 추론하지 않아야 합니다. R08-XI01의 PR 생성·push 분리는 해소 상태를 유지합니다.

**R21-M03 — Minor/P2 — restore의 기본 source가 옵션에 따라 달라진다는 설명이 부족합니다.**

- **위치:** `undo-merge-conflict-release.md`의 `git restore` 설명.
- **최소 인용:** “작업 트리 내용을 index 같은 원본에서 복원하며 옵션에 따라 index도 바꿀 수 있습니다.”
- **관찰·근거:** R21-S03은 기본 복원 위치와 source를 구분합니다. 기본 작업 트리 복원은 index를 사용하지만 `--staged`가 있으면 기본 source는 HEAD입니다. 현재 설명은 source를 확인하라고 요구하면서 그 기본 선택 규칙은 제공하지 않습니다.
- **영향·기준:** stage만 취소할지 작업 파일도 바꿀지 판단하는 초보자에게 필요한 국소 설명이 빠져 있습니다. C02·C04·C05.
- **최소 수정:** 기본 source의 차이와 `--source`로 명시할 수 있다는 점을 설명합니다. source에 없는 tracked 경로가 삭제될 수 있다는 한계도 짧게 덧붙이면 복원의 의미가 분명해집니다.
- **재확인:** HEAD·index·작업 트리가 다른 상태에서 복원 대상과 읽을 source를 각각 식별할 수 있어야 합니다.

**R21-M04 — Minor/P2 — revert의 새 커밋 생성 설명에 `--no-commit` 예외가 없습니다.**

- **위치:** 같은 원고의 `git revert` 설명.
- **최소 인용:** “선택한 commit의 효과를 취소하는 새 commit을 만듭니다.”
- **관찰·근거:** 기본 동작 설명으로는 맞지만 R21-S04가 구분한 `--no-commit`은 자동으로 새 커밋을 만들지 않습니다. 이 장은 명령의 성공과 이력의 완료 상태를 구분하는 역할을 갖습니다.
- **영향·기준:** 옵션을 사용한 실행 결과를 새 커밋 생성 완료로 오해할 수 있는 국소 예외입니다. C04·C05.
- **최소 수정:** “기본적으로”를 명시하고 `--no-commit`에서는 반대 변경을 준비하되 자동 커밋하지 않는다고 추가합니다.
- **재확인:** 반대 변경 적용, 새 커밋 생성, 원격 공유, 운영 복구를 각각 별도 증거로 판정해야 합니다.

**R21-PM01 — Minor/P2, 캡처 코드 — 최종 검증 전에 완료 상태를 기록합니다.**

- **위치:** `.superpowers/sdd/2026-08-12-public-beta-master-plan/render-r21-inputs.mjs`의 마지막 `persist(true)`와 뒤의 예상 상태·오류 검사.
- **최소 인용:** `persist(true);` 이후 예상 상태 누락 검사와 `process.exitCode=1`.
- **관찰·근거:** 코드상 `run-status.json`에 `complete: true`를 쓴 뒤 누락·중복 상태를 검사하고 HTTP·H1·배지·overflow·오류를 판정합니다. 이 마지막 검사에서 실패하면 종료 코드는 실패해도 완료 표시는 true로 남을 수 있습니다.
- **영향·기준:** 중단 후 상태 파일만 읽는 절차에서는 “캡처 순회 종료”와 “검증을 통과한 실행 완료”가 혼동될 수 있습니다. 현재 두 실행은 별도 종료 코드와 결과가 통과했으므로 이번 이미지의 무효 사유는 아닙니다. C09·C12.
- **최소 수정:** 최종 검사까지 통과한 뒤 완료를 기록하거나, `captureComplete`와 `validationPassed`처럼 의미를 분리합니다. 실패 시 상태 파일에도 실패를 남깁니다.
- **재확인:** HTTP 오류나 예상 상태 누락을 주었을 때 성공 완료 표시가 남지 않아야 합니다. 전체 브라우저 재실행보다 최종 상태 판정 로직의 좁은 검증으로 확인할 수 있습니다.

같은 R21 reviewer의 지속 세션에서 수정의 영향 범위를 재검토해야 합니다. R02 승계 예외는 적용하지 않습니다.
