Important 3건은 서로 다른 원인입니다. 방법론의 **출처 자체 미정비**, 제품 설명의 **검토 입력에 필요한 본문 부족**, 화면의 **빌드·소스 연결 부족**을 중복 집계하지 않았습니다. 기존 `PBSG-014`·`PBCA-007`은 새 결함처럼 재발견한 것으로 처리하지 않고 R25에서 여전히 해소되지 않은 항목으로 연결합니다.

입력의 실제 완독과 이미지 판독은 완료했습니다. 제공된 controller 검증은 입력 해시 오류 0건을 보고하지만, 검토 후 불변성 감사와 최초 응답의 정본 저장은 아직 제가 확인한 사실이 아닙니다. 미해결 Important는 0건이 아니며, 필수 근거 부족을 높은 루브릭 점수로 상쇄하지 않습니다.

원고의 강점도 분명합니다. 두 SDD와 TDD는 산출물·접근·규율로 구분돼 있고, 현재 제품 기능이 데이터·권한·복구 책임을 대신하지 않는다는 경계도 반복해서 명시됩니다. 특히 체크리스트는 각 단계의 증거와 실패·거절·복구·재검증 질문을 연결해, 단순한 체크 수를 완료로 오인하지 않도록 구성돼 있습니다.

**R25-I01 — 방법론 여섯 묶음의 필수 출처 공백이 남아 있습니다.**

- **위치·심각도:** `src/content/docs/reference/methodology-map.md`의 BDD·Scrum·Kanban·DevOps·GitFlow·Trunk-based development 및 「관련 장과 출처 경계」 — **Important / P1**
- **최소 인용:** “직접 공식·1차 source cluster는 아직 완결되지 않았으므로 … 내부 출처 공백을 유지합니다.”
- **관찰 근거:** 원고는 여섯 개념의 정의뿐 아니라 목적·출력·관계·선택 조건을 설명하고, 최소 조합과 연습에서도 사용하게 합니다. 동시에 source-map·source-gap·콘텐츠 감사는 `PBSG-014`와 `PBCA-007`을 유지합니다. 이번 방법론 발췌 7개도 이 여섯 묶음의 직접 출처를 보충하지 않습니다.
- **영향·적용 규칙:** 공백을 솔직히 표시한 점은 적절하지만, 표시만으로 참고편의 주요 정의와 선택 조언에 필요한 근거가 충족되지는 않습니다. 정의가 틀렸다고 확정한 지적은 아니며, C02·C05의 필수 근거가 미완료라는 판정입니다.
- **최소 수정:** 여섯 묶음에 대해 해당 정의·관계·선택 조건을 뒷받침하는 공식·1차 자료의 URL, 확인일, 실제 읽은 절, 적용 한계를 연결합니다. 근거가 다른 범위를 말하면 그 부분만 좁게 고칩니다. 기존 미확인 기록은 역사로 보존합니다.
- **재확인 기준:** 여섯 묶음 각각에 대해 `원고 주장 → 직접 본문 → 적용 범위`를 대조할 수 있어야 합니다. 정의·관계·최소 조합·연습에 같은 변경이 일관되게 반영되고, 기존 gap과 감사 항목의 해소 근거가 연결돼야 합니다.

- **위치·심각도:** `src/content/docs/reference/agent-output-glossary.md`의 「검증과 산출물」, `test` 행 — **Minor / P2**

- **관찰 근거:** `development-glossary.md`는 `static testing`을 소프트웨어를 실행하지 않는 검토·분석으로, `dynamic testing`을 실행하고 결과를 비교하는 테스트로 구분합니다. 출력 용어집의 현재 설명은 후자에 해당하지만 행 이름은 일반적인 `test`입니다.
- **영향·적용 규칙:** 독자가 두 용어집을 오갈 때 “테스트는 반드시 프로그램을 반복 실행하는 것”으로 일반화할 수 있습니다. 실제 에이전트 실행 로그를 설명하는 문맥에서는 유용하므로 핵심 오류보다는 범위 표시 문제입니다. C04 적용입니다.

Supabase의 Postgres 기반, Auth와 RLS, grants와 RLS의 구분, 스키마 기반 API, Edge Functions의 작업 경계, secret key의 RLS 우회는 제공된 발췌에서 직접 대조할 수 있었습니다. 반면 로그의 오래된 프로젝트 조건 등 일부 세부는 충분하지 않았습니다. Sites의 최신 발췌에 Edu가 나열되지 않았다는 사실만으로 Edu 미지원이나 기능 제거를 결론 내리지 않았고, public beta 표기가 보이지 않는다는 이유로 정식 출시를 추정하지도 않았습니다.

Codex 출처 사이에도 읽기 전용 명령 실행 설명의 차이가 있습니다. `Agent approvals & security` 발췌는 읽기 전용 sandbox 안의 명령 실행을 설명하지만, `Sandboxing` 발췌의 요약은 명령 실행에 승인이 필요한 것으로 표현합니다. 호스트·설정·문서 문맥을 확인하지 않고 한쪽을 모든 환경의 보편 계약으로 채택하지 않았습니다. 원고가 실제 설정을 확인하도록 안내하는 방향은 유지할 가치가 있습니다.

시각 증거는 20상태를 포괄하지만 전체 페이지의 모든 행·열·스크롤 위치를 포괄하지 않습니다. 모바일 표의 가로 이동은 관측과 양 끝 이미지에서 확인되지만, 다음은 확인하지 못했습니다.

- 표와 흐름 블록의 실제 키보드 접근·가로 이동
- 스크린리더의 표 머리글·셀 관계 해석
- 확대·다른 너비·다른 브라우저에서의 재배치
- 긴 표의 모든 중간 열과 하단 행
- Sites 표의 실제 모바일 표현
- 색 대비의 정량 측정과 전체 접근성 적합성

R24 검색 이미지에서는 `백엔드`, `authentication`, `SDD`의 관련 결과와 도착 화면을 확인했습니다. 문장 검색은 사용법 페이지의 자기 예시를 반환합니다. 후자는 `passed: true`여도 문제 해결 문서에 도달했다는 뜻이 아니며, R24 재판정이 이미 구분한 한계를 유지합니다. 검색 이미지의 이전 배지 문구도 역사적 픽셀로 취급했습니다.

**6. 재확인 기준**

최초 결과는 이번 응답의 판정·건수·점수·한계를 그대로 보존해야 합니다. 제가 결과 파일을 저장하거나 커밋한 것은 아닙니다. controller가 원응답과 정본의 일치, 입력의 검토 후 불변성, 실제 실행 프로필 및 정상 종료를 확인해 보존하기 전에는 최초 결과의 정본 저장이 완료됐다고 볼 수 없습니다.

후속 검토는 **동일 R25 reviewer가 이 대화에서** 다음 범위를 재확인하는 방식으로 이어갑니다.

1. **원고 수정과 출처 보충을 분리해 제출합니다.** `R25-I01`에는 여섯 방법론의 직접 근거와 관련 원고 diff를, `R25-P-I01`에는 부족한 제품 본문과 주장별 판정을 제공합니다. 출처만 보충해 문장이 그대로인 경우도 그 사실을 구분합니다.
2. **새 입력을 다시 고정합니다.** 변경 파일의 전후 SHA-256, 새 결합 SHA-256, 기존 입력 중 재사용할 불변 범위, finding별 영향 범위를 제공합니다. 최초 manifest·요청·결과를 소급 수정하지 않습니다.
3. **렌더의 생성 기준을 연결합니다.** `R25-P-I02`에 대해 기존 빌드 증거를 복구하거나 필요한 빌드·캡처를 새로 생성하고, 고정 원고와 실제 제공 아티팩트의 관계를 남깁니다.
4. **화면 수정은 영향 범위만 확인합니다.** 제목을 바꾸면 해당 페이지의 양 너비·양 테마 상단과 검색·목차 표기를 확인합니다. 캡처 절차를 고치면 `R25-P-M01`의 목표 절·목차 표시가 안정된 새 관측을 제공합니다. 불변 화면 전체를 이유 없이 다시 만들 필요는 없습니다.
5. **관련 자동 검증의 실제 결과를 제공합니다.** 원고·링크·메타데이터·출처 연결의 관련 검사와 필요한 빌드 결과를 명령·실행 기준·종료 코드·수량으로 구분합니다. 테스트 통과를 출처의 사실 확인으로 사용하지 않습니다.
6. **해소 판정을 별도 결과로 남깁니다.** 동일 ID별로 `RESOLVED`, 미해소, 추가 문맥 필요를 판정하고, 최초 결과의 Important·Minor와 점수를 덮어쓰지 않습니다. 준비의 BLOCKED 해소와 원고의 수정 완료를 각각 확인한 뒤에만 R25 전체 판정을 다시 내립니다.
