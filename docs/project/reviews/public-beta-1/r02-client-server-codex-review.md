원고는 클라이언트/서버의 **상호작용 역할**과 프런트엔드/백엔드의 **책임**을 구분합니다. W-01·W-03·W-04에서도 화면, HTTP 응답, 서버 판단, 권위 데이터와 사용자 이해를 서로 다른 증거로 취급합니다. HTTPS·캐시·정적 전달·재시도에 관한 설명을 구현 성공의 증거로 확대하지 않으며, 제공된 공식 근거의 좁은 적용 범위와도 대체로 일치합니다.

다만 계약 3절과 7절은 해시·입력 불변성 미확인을 점수와 별개의 차단 조건으로 둡니다. 이번 입력에는 기존 결합 해시와 개별 해시 **선언**이 있지만, controller의 전송 전후 비교 결과 및 개정·이미지 대응표·전송 payload의 별도 고정 결과는 제시되지 않았습니다. 실제 이미지가 보이고 문장이 완독 가능하다는 사실은 이 바이트 검증을 대신하지 않습니다.

따라서 **미해결 내용상 Critical/Important는 0건이지만, 유효 M5 검토 증거의 선행 조건은 아직 충족됐다고 확인할 수 없습니다.** 과거 BLOCKED나 원고의 `draft` 상태를 변경하는 판정도 아닙니다.

## 3. 위치별 finding

**R02-B01 — 입력 불변성의 실행 증거 미확인**

- **분류:** 계약상 차단 항목. 원고의 Critical/Important/Minor 건수와 별도로 관리합니다.
- **위치:** 이미지 전달 개정의 「실행 순서와 권한」, 공통 계약 3·7절, 이번 INPUT METADATA 및 EXECUTION MANIFEST.
- **최소 인용:** “전달 전후 불변성을 기록합니다.” / “실제 완독·해시·기준 SHA·모델·effort를 확인할 수 없으면 … `BLOCKED`”
- **관측 근거:** 개별·결합·보충 해시 선언은 제공됐습니다. 그러나 실제 전송 전후 비교 결과와 개정·이미지 대응표·전송 payload의 별도 SHA 및 검증 결과는 제공되지 않았습니다. reviewer는 도구를 사용하지 않았으므로 이를 직접 계산하지 않았습니다.
- **영향:** 이번에 읽은 내용과 고정된 원시 파일 묶음의 바이트 일치를 확정할 수 없습니다. 이는 불일치를 발견했다는 뜻이 아니라 일치의 실행 증거가 미확인이라는 뜻입니다.
- **최소 조치:** controller가 이미 수행한 검증이 있다면 그 결과를 연결하고, 없다면 승인된 controller 절차에서 원본·payload·전송 후 입력의 대응과 불변성을 확인해야 합니다. reviewer에게 금지된 도구 사용을 요구할 필요는 없습니다.
- **재확인 조건:** 기준 SHA, 고정 26개 입력, 보충 및 개정, 이미지 18개 대응, 전송 payload에 대한 검증 결과를 연결해야 합니다. 실제 모델·effort·구독 경로·fresh 실행 조건도 controller의 실행 기록으로 확인해야 하며, 현재 응답의 사용자 제공 프로필 기록을 독립적인 런타임 확인으로 바꾸면 안 됩니다.

**R02-M01 — 트랜잭션과 동시성 보장의 차이를 표 가까이에서 명시하면 좋습니다**

- **심각도:** Minor/P2.
- **위치:** [대상 원고의 「한 사용자 작업을 끝에서 끝까지 추적하기」 5단계](../../../../src/content/docs/03-full-stack/client-server-full-stack.md), 88행.
- **최소 인용:** “같은 트랜잭션에서 참가 관계를 `confirmed`로 확정하고 정원 초과와 활성 중복을 막음”
- **관측 근거:** 이 표는 책임을 설명하지만, 이 장 안에서는 트랜잭션으로 묶는 것과 동시성 전략을 선택하는 것의 차이를 직접 풀어 주지 않습니다. 제공된 PostgreSQL 근거와 캡스톤은 원자성만으로 정원 경합이 해결되지 않으며 잠금·격리·제약 등의 전략이 필요하다고 명확히 구분합니다.
- **영향:** 처음 읽는 독자가 “트랜잭션 안에 넣으면 정원 초과까지 자동 방지된다”고 압축해서 기억할 여지가 있습니다.
- **Minor 판단 이유:** 원고는 별도로 제약·동시성 테스트, 마지막 한 자리의 결과, 권위 데이터 재조회를 요구합니다. 전체 문맥이 자동 보장을 단정하는 것은 아니므로 핵심 검증 계약의 실질 오류로 보지는 않았습니다.
- **최소 수정:** 표 뒤에 “트랜잭션으로 묶는 것만으로 동시 요청의 정원 초과가 자동 방지되지는 않으므로, 선택한 데이터베이스의 동시성 전략과 고유성 제약을 함께 검증합니다.” 정도의 한 문장을 추가합니다.
- **재확인 조건:** 책임 표와 보완 문장을 PostgreSQL 근거·W-04 계약에 대조하고, 특정 잠금 기법이나 격리 수준을 보편적 정답으로 제시하지 않는지 확인합니다.

**R02-M02 — 첫 등장 용어의 설명이 일부 부족합니다**

- **심각도:** Minor/P2.
- **위치:** 대상 원고의 「식당으로 이해하기」, 「한 사용자 작업을 끝에서 끝까지 추적하기」, 「흔한 실패와 복구 질문」.
- **최소 인용:** “API 계약”, “Build Track”, “UI 상태, DOM”, “ADR로 추가 여부를 기록”
- **관측 근거:** 클라이언트·서버 등 중심 용어는 잘 정의하지만, API·UI·DOM·ADR와 Build Track은 이 장에서 처음 접하는 독자를 위한 짧은 뜻풀이가 일관되게 붙어 있지 않습니다. 관련 용어집과 인접 장 링크는 있습니다.
- **영향:** 시스템 관계를 이해하려는 초보자가 증거 표와 판단 규칙을 읽는 도중 외부 용어 확인을 반복해야 합니다.
- **최소 수정:** 첫 사용에만 짧은 설명이나 직접 연결을 붙입니다. 예를 들어 “브라우저의 문서 구조인 DOM”, “아키텍처 결정 기록인 ADR”, “모임 앱을 단계별로 만드는 Build Track”처럼 설명할 수 있습니다.
- **재확인 조건:** 새 설명이 용어집과 일치하고, 모든 약어를 장황하게 반복하거나 본문 흐름을 끊지 않는지 확인합니다.

**R02-M03 — PostgreSQL 18이라는 출처명과 가변 `current` URL이 어긋날 수 있습니다**

- **심각도:** Minor/P2.
- **위치:** 대상 원고 「관련 용어와 출처」의 PostgreSQL 트랜잭션·격리·제약 링크.
- **최소 인용:** “PostgreSQL 18 트랜잭션” → `https://www.postgresql.org/docs/current/tutorial-transactions.html`
- **관측 근거:** 공개 원고의 세 링크는 `/current/`를 사용합니다. 반면 10월 23일 보충은 판단 근거를 명시적인 `/18/` 문서로 제한하고, 10월 15일의 `current=18`은 역사 관찰이라고 분리합니다.
- **영향:** 향후 `current`가 다른 버전으로 이동하면 독자는 “18”이라고 표시된 링크에서 다른 버전의 문서를 보게 됩니다. 현재 `current`의 실제 대상이 바뀌었다고 단정하는 finding은 아닙니다.
- **최소 수정:** 공개 원고의 해당 세 링크를 제공된 근거와 같은 `/docs/18/` 경로로 고정합니다. 역사 요청서·매니페스트·과거 확인 기록은 그대로 보존합니다.
- **재확인 조건:** 출처명·URL·근거의 버전이 일치하는지 확인하고, 원고 변경 전후 SHA와 영향 범위를 기록합니다.

공유 SVG에서 Mermaid의 하단 간선별 설명이 각각 인쇄되지는 않지만, 실제 그림의 방향·범례·노드 설명이 조회/변경·호출/반환의 의미를 보존합니다. 이를 별도의 의미 불일치 finding으로 올리지는 않았습니다.

## 5. 미확인 사실·남은 위험·검토 한계

- **해시와 전송:** 선언된 SHA 문자열을 읽고 대응을 대조했지만 원시 바이트를 재계산하지 않았습니다. PNG 서명·치수·재인코딩 여부, payload 해시와 전송 전후 불변성은 별도 실행 증거가 필요합니다.
- **프로필과 구독:** `gpt-6-astra/high` 등은 사용자 제공 실행 정보로 기록했습니다. 실제 런타임 설정·공식 구독 경로를 reviewer가 독립 관찰한 것으로 표시할 수 없습니다.
- **현재성:** 외부 웹을 새로 열지 않았습니다. 10월 23일 보충은 제공된 근거로 대조했고, RFC·PostgreSQL 18·SWEBOK의 버전 고정 범위는 역사 접근일 그대로 사용했습니다. 최신 DB 버전, 오늘의 `current` 대상, 표준의 현재 대체 여부를 확정하지 않았습니다.
- **실제 앱:** 모임 앱의 인가·원자성·고유성·정원·재시도·복구 구현은 확인하지 않았습니다. 원고가 제시하는 계약과 시험 기준의 타당성을 검토한 것입니다.
- **시각 범위:** 18개 이미지 모두 읽었으나 모두 그림 crop입니다. 페이지 전체 가로 넘침, 주변 본문·표·코드의 배치, 확대 시 재배치, 실제 화면 판독기와 키보드, 현재 브라우저의 테마 전환을 증명하지 않습니다.
- **모바일 글자:** 보조 레이블과 범례도 판독 가능했지만 작은 크기입니다. SVG 정의와 선언 폭의 비례로는 핵심 약 17.9px·보조 약 12.8px에 해당하며, 이는 실제 기기에서 계측한 결과가 아닙니다.

## 6. 재확인 기준

1. **R02-B01을 먼저 확인해야 합니다.** controller는 고정 입력·이미지 대응·payload·전송 전후 해시 결과와 실제 프로필·fresh 실행·구독 경로 증거를 연결해야 합니다. 전달 성공, 실제 판독 성공, 바이트 불변성을 별도 항목으로 판정해야 합니다. 단순히 이 응답을 저장하거나 매니페스트에 PASS를 쓰는 것으로 해소되지 않습니다.

2. **Minor 3건을 모두 재판정해야 합니다.** 수용·부분 수용·기각과 근거, 반영 위치 또는 비반영 이유를 기록해야 합니다. M01은 동시성 보장 설명, M02는 첫 등장 용어, M03은 버전 링크만 좁게 다루면 됩니다.

3. **원고를 수정하면 변경 전후 해시와 영향 범위를 기록해야 합니다.** 역사 요청서·매니페스트·원본 PNG·과거 실패 기록은 보존하고, 새 검토 입력과 기존 증거의 관계를 별도로 남겨야 합니다. 위 세 Minor의 산문·링크 수정만 있다면 영향 문단과 해당 근거를 좁게 재검토할 수 있습니다.
