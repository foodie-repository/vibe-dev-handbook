**나. `scripts/r18-closeout.mjs`의 정확한 9전이와 8개 증거 pin**

9개 전이는 다음 범위와 일치합니다.

| 전이 대상 | 변경 내용 |
|---|---|
| ADR 원고 | frontmatter의 review 전이와 증거 참조 |

`r18PreCloseoutBytes()`는 **현재 전체 해시가 등록된 after와 정확히 같을 때만** 역변환합니다. 치환 대상의 유일성을 확인하고, 역변환 결과의 전체 해시가 before인지 다시 검사합니다. 알 수 없는 바이트 변경은 정상화해 숨기지 않고 그대로 돌려줍니다.

8개 증거 pin은 완료 판단, 최초 요청, 최초 manifest, 최초 검토 정본, 현재 재판정, Fix1 정본, Fix1 검증, 최초 입력 준비 검증입니다. 원응답 SHA와 `raw+LF` 정본 SHA도 구분돼 있습니다. 특히 최초 정본 `77d51dd5…`와 Fix1 정본 `085a9f41…`을 서로 다른 결과로 보호하므로, 후속 PASS가 최초 NEEDS CHANGES를 덮어쓰지 않습니다.

검사 범위도 구분해 확인했습니다. `validateR18Closeout()`의 직접 현재 pin 검사는 **9전이 중 PROJECT_CONTEXT·ROADMAP을 제외한 7개와 증거 8개**입니다. 두 요약 문서를 포함한 **9개 전체의 현재·이전 해시와 역변환은 첫 번째 closeout 테스트가 검사**합니다. 따라서 “함수 하나가 9개 모두를 직접 pin 검사한다”는 해석은 하지 않습니다. 이번 전체 검사와 index 증거에서는 두 요약 문서까지 포함됩니다.

**다. 역사 입력 복원과 현재 상태 검사의 분리**

호출 순서는 적절합니다.

1. 현재 closeout의 pin을 검사합니다.
2. closeout 전이를 정확히 되돌려 Fix1 바이트를 얻습니다.
3. Fix1의 네 전이를 되돌려 최초 고정 입력 바이트를 얻습니다.
4. 최초 manifest·개별 입력·문맥·결합 해시를 대조합니다.

`validateR18Current()`만 보면 closeout 이전의 정상 Fix1 바이트도 받아들일 수 있지만, `validateR18Inputs()`가 앞에서 **현재 closeout pin 검사까지 함께 수행**하므로 현재 상태의 rollback을 통과시키지 않습니다. 새 테스트는 누락·변조·rollback을 closeout 검사와 입력 검사 양쪽에서 거부하는지 확인합니다.

최초 manifest 122항목·문맥 9개 검증의 `reviewComplete:false`, `releaseReady:false`는 **입력 검증 함수의 권한 경계**입니다. 현재 행렬의 R18 done을 취소하는 값도 아니고, 입력 해시 검사가 독립 검토를 대신한다는 뜻도 아닙니다.

R17로 이어지는 것은 기존 역사 바이트의 복원 연결입니다. **reviewer 승계 예외를 R18에 적용한 흔적은 없습니다.**
