R14-M01은 두 원고에 공통으로 적용되므로 묶음 집계에서는 한 건으로 셌습니다.

주요 수정 사유는 **가설 표가 현재 참가 관계의 존재를 해당 요청의 성공 처리와 충분히 구분하지 않아, 서로 다른 원인 후보를 가려내는 증거로 잘못 사용할 수 있다는 점**입니다. 본문은 반복 요청을 금지하고 증거의 한계를 여러 차례 설명하므로 즉각적인 위험 행동을 지시하는 Critical로 보지는 않습니다. 그러나 이 장이 가르치는 핵심인 판별 가능한 실험에 직접 영향을 주므로 Important입니다.

입력 완독은 완료했습니다. 전달된 고정 입력과 검증 기록에서 누락이나 불일치를 발견하지 않았으므로 `BLOCKED`로 판정하지 않습니다. 다만 미해결 Important가 1건이므로 R14 통과 조건은 충족하지 않습니다.

준비 코드에서는 고정 manifest 자체의 해시, 개별 바이트·크기, local 모드의 결합 해시·PNG 식별, 지정 문맥의 해시·행 내용, 양쪽 렌더 관측 manifest를 확인하는 흐름을 읽었습니다. 테스트는 누락·변조·manifest 교체·문맥 행 변조·local PNG와 provenance 실패를 다루며, 검사 성공을 `reviewComplete`나 `releaseReady`로 승격하지 않습니다. **검토한 고정 입력 준비 단위의 로컬 체크포인트 요건에 대한 코드 검토 측면은 적합합니다.** 이는 실제 커밋 수행이나 원고 승인이라는 뜻이 아닙니다.

## 3. 위치별 finding

**R14-I01 — 현재 참가 관계만으로 해당 요청의 성공·거절 가설을 구분할 수 없습니다.**

- **심각도:** Important / P1
- **위치:** `src/content/docs/01-mental-models/developer-thinking.md`의 「좋은 가설은 반대 증거를 포함한다」 가설 표, 특히 둘째·셋째 행. PNG 11·19·20·40·48·49에서도 같은 내용을 확인했습니다.
- **최소 인용:** 거절 가설의 반대 증거인 “성공 처리 기록이나 확정된 참가 관계가 있음”, 응답 실패 가설의 예상 증거인 “같은 사용자의 참가 관계가 이미 확정됨”.
- **관찰 근거:** 제시된 시작 상태는 버튼을 한 번 눌렀다는 사실이며, 그 전에 참가 관계가 없었다는 조건은 없습니다. 이미 참가한 사용자가 다시 신청하면 중복 규칙에 따라 이번 요청은 거절되면서 기존 `confirmed` 관계는 그대로 남을 수 있습니다. 따라서 현재 확정 관계의 존재는 거절 가설의 반대 증거가 아니며, 이번 요청이 확정된 뒤 응답만 실패했다는 가설도 구분해 주지 못합니다. 반대로 요청 뒤 별도 취소가 있었다면 현재 관계가 없거나 취소 상태라는 사실만으로 앞선 확정을 부정할 수도 없습니다.
- **영향:** 독자는 안전한 현재 상태 조회와 특정 요청의 원인 규명을 같은 증거로 취급할 수 있습니다. 본문이 요구한 “서로 다른 결과를 예측하는 검사”를 대표 표 자체가 충족하지 못하는 경우가 생깁니다.
- **적용 근거:** C02·C03·C04·C06, 모임 브리프의 활성 중복 금지와 자기 조회 계약, 용어집의 `recovery oracle`, Google SRE 발췌의 판별력·제한적 증거 원칙.
- **필요한 최소 수정:** 현재 참가 상태를 확인하는 목적과 이번 요청의 처리 결과를 판정하는 목적을 한두 문장으로 분리하고, 표의 성공·거절 증거를 **같은 요청에 연결된 처리 기록**으로 한정하세요. 현재 관계만 확인했다면 원인은 아직 판별할 수 없다고 명시하면 됩니다. 요청 식별 증거가 없는 교육 예시를 유지하려면 사전 관계가 `not_registered`이고 관찰 구간에 다른 변경이 없다는 통제 조건을 명시해야 합니다. 자기 조회에서는 브리프에 맞게 모임 상태도 함께 읽고, 취소된 모임의 보존 이력을 유효 참가로 해석하지 않아야 합니다.
- **재확인 기준:** 다음 세 경우가 구분되어야 합니다. ① 기존 참가 관계가 있는 상태의 중복 거절, ② 이번 요청 확정 뒤 응답 유실, ③ 조회 실패나 별도 상태 변경 때문에 판별 불가인 경우. ①과 ②에서 모두 `confirmed`가 보일 수 있음을 설명하고, 어느 경우에도 상태 조회를 무조건 POST 재전송 허가로 바꾸지 않는지 확인합니다.

**R14-M01 — 초반 핵심 사례의 `fixture`를 쉬운 한국어로 먼저 설명하지 않습니다.**

- **심각도:** Minor / P2
- **위치:** `src/content/docs/01-mental-models/developer-thinking.md`의 「왜 필요한가」 두 번째 문단, `src/content/docs/01-mental-models/abstraction-and-tradeoffs.md`의 「추상화에는 비용이 있다」 사례 문단.
- **최소 인용:** “교육용 fixture 행”, “교육용 주가 fixture를 읽어 변환한 정적 페이지”.
- **관찰 근거:** 두 원고 모두 fixture의 가상·고정 범위를 뒤에서 제한하지만, 처음 만나는 독자에게 fixture라는 단어가 무엇인지 직접 연결해 주지는 않습니다. 문제 분해 장에서는 도입부터 `fixture 행`을 알아야 정상 빈 결과의 뜻을 이해할 수 있습니다. 제공된 용어집에는 `test fixture`의 정의가 있으나 본문의 첫 등장과 바로 연결되어 있지 않습니다.
- **영향:** 도메인 전문가나 비개발자가 핵심 사례를 이해하기 전에 용어를 따로 찾아야 합니다. 실제 데이터나 도구 이름으로 오인할 여지도 작게 남습니다.
- **적용 근거:** C01·C04·C08, 쉬운 정의 뒤 정식 용어를 연결한다는 콘텐츠 원칙.

- **재확인 기준:** 첫 등장만 읽어도 고정된 가상 입력이라는 뜻을 이해할 수 있고, 실제 시세·실제 제공자·투자 판단을 뜻하지 않는 기존 경계가 유지되는지 확인합니다.

## 5. 미확인 사실·남은 위험·검토 한계

**현재 참가 관계의 조회는 안전한 다음 행동을 고르는 데 유용하지만, 과거 요청의 처리 결과를 항상 복원하지는 못합니다.** R14-I01 수정에서 이 한계를 명확하게 유지해야 합니다. 현재 관계, 모임의 현재 상태, 요청 처리 기록이 각각 무엇을 답하는지 구분하는 것이 핵심입니다.

시각 검토는 제공된 두 경로의 1440px·390px, light·dark 총 8상태와 상단·3열 이상 표·프롬프트에 한정됩니다. 2열 표는 요청서에 포함된 DOM 폭 자료를 읽었으며 별도 픽셀 판독을 하지 않았습니다. 모바일 표의 내부 가로 스크롤과 프롬프트의 가로 구간은 내용을 잃은 것으로 판정하지 않았습니다. 다만 캡처가 프로그램적으로 이동했다는 사실만으로 실제 사용자가 키보드나 보조 기술로 같은 구간에 도달할 수 있다고 판단할 수는 없습니다.

1440px 일부 표에서 짧은 분류명이 두 줄로 나뉘고, 모바일 문제 분해 장 제목의 마지막 `법`이 둘째 줄에 놓입니다. 제공된 화면에서는 의미를 읽을 수 있고 겹침·소실이 없어 별도의 공개 차단 finding으로 올리지 않았습니다. 정확한 대비 비율이나 WCAG 적합성을 측정한 것은 아닙니다.

controller가 보고한 HTTP 200, H1 하나, 테마 상태, 이미지 요소 0, 전역 overflow·console·외부 요청 관련 결과는 제공된 실행 기록의 증거입니다. 정적 이미지 판독만으로 이를 독립적으로 재실행하거나 모든 동작을 검증한 것은 아닙니다. 검색·404·키보드·1024px·전체 사이트·배포 환경·비로그인 공개 URL은 이번 검토에서 확인하지 않았습니다.

공식 출처는 제공된 관련 절과 추적 가능한 발췌 범위만 사용했습니다. SEI 글 전체의 모든 처방, C4의 모든 모델 규칙, SWEBOK 전문, SRE의 모든 운영 사례를 확인했다고 확대하지 않습니다. C4의 추가 수준은 필요성과 명시적 정의가 있으면 가능하다는 제공 문맥을 유지했고, ACM의 과거 403을 현재 성공으로 바꾸지 않았습니다.

준비 코드 테스트 중 local 증거 테스트는 첫 PNG 존재 여부에 따른 skip 조건이 있습니다. 제공된 이번 실행에서는 건너뜀 0으로 기록되어 있으므로 local 검증이 실행된 기록과 부합합니다. 향후 PNG 없는 환경에서 일반 정적 검사만 통과한 결과를 58개 실제 이미지 검증으로 사용할 수는 없습니다.

이번 reviewer는 작성자·controller와 분리된 fresh context이지만 같은 제공자의 모델을 사용합니다. 교차 제공자 검토의 다양성이 생긴 것은 아닙니다. 고정 입력·독립 문맥·재판정·같은 reviewer의 후속 재검토·별도 R26이 그 한계를 완화하는 절차입니다.

응답 후 입력 불변성, 실제 응답의 정본 저장, 최초 결과의 분리 커밋, 후속 동일 세션 복구는 아직 관측하지 않았습니다. 이를 완료했다고 기록하지 않습니다.

## 6. 재확인 기준

1. **최초 결과를 원고 수정 전에 보존해야 합니다.** controller는 이번 응답을 형식·완독·해시·실행 프로필·권한 기준으로 검증하고, 응답 후 입력 불변성 감사를 수행한 뒤 `docs/project/reviews/public-beta-1/r14-mental-support-codex-review.md` 정본에 저장해야 합니다. 정상 결과의 별도 커밋을 먼저 기록하고 이후 수정 이력과 분리합니다. reviewer는 저장이나 커밋을 수행하지 않았습니다.

2. **R14-I01을 먼저 재판정해야 합니다.** 현재 원고·모임 브리프·용어집의 recovery oracle 정의에 대조하여 수용·부분 수용·기각 근거를 남겨야 합니다. 수정한다면 가설 표와 바로 인접한 설명을 중심으로 좁게 고치고, 현재 상태만으로 이번 요청의 원인을 확정하지 않도록 해야 합니다.

3. **R14-M01·M02도 처리 결과를 남겨야 합니다.** 적용하면 첫 fixture 설명과 링크 문구만 좁게 변경하고, 미적용이면 사유와 남은 영향을 기록합니다. Minor를 Important와 같은 공개 차단 항목으로 확대할 필요는 없습니다.

4. **같은 reviewer의 후속 입력에는 변경 범위와 새 식별자가 필요합니다.** 수정 전후 원고 해시, 새 기준 commit 또는 고정 후보 식별자, 정확한 diff, 재판정 문서, 수정된 절의 충분한 앞뒤 문맥을 제공해야 합니다. R14-I01은 사전 참가 상태·중복 거절·응답 유실·조회 실패 또는 별도 상태 변경의 구분을 재검토합니다. R02 승계 예외를 적용하지 않고 같은 저장 reviewer 세션을 복구해야 합니다.

5. **수정의 영향에 맞는 자동·시각 증거를 갱신해야 합니다.** 관련 정적 검사에서 실제 종료 코드와 실행·통과·실패·건너뜀 수를 남기고, 공개 원고가 바뀌면 수정된 출력에 대한 빌드 증거를 새로 확보해야 합니다. 가설 표와 첫 설명의 레이아웃이 달라지면 두 테마·두 화면 폭에서 해당 영역을 다시 캡처하고 실제로 읽어야 합니다. 기존 이미지로 새 텍스트의 렌더 성공을 증명하지 않습니다. 변경 영향이 없는 나머지 이미지는 원고·CSS·렌더 입력과 diff 근거를 연결하여 재사용할 수 있습니다.

6. **최종 상태 전이는 별도입니다.** Important 해소에 대한 같은 reviewer의 재검토 응답과 controller의 검증·저장 전에는 R14를 PASS로 바꾸지 않습니다. 이후 R14가 통과하더라도 소유자 승인, 전체 문서 `ready`, R26, RC, M5 전체 완료, M6/M7, push·배포·공개 URL 성공을 승인하거나 완료한 것으로 해석하지 않습니다.
