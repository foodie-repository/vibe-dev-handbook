원고의 중요한 장점은 다음과 같습니다.

- 단위·통합·종단 간의 실행 범위와 회귀·smoke의 목적, 계약 테스트의 초점을 한 계층으로 섞지 않습니다.
- 정적·동적과 수동·자동을 별도 축으로 설명하며, verification/validation도 자동화 여부로 구분하지 않습니다.
- “가장 낮은 수준”보다 “가장 작은 충분한 수준”을 선택하게 하고, 대역이 가린 실제 경계를 추가 증거로 확인하게 합니다.
- 오라클의 독립성, flaky 최초 실패 보존, 실행 0건·건너뜀·필터·스냅샷 변경을 구체적인 검토 대상으로 제시합니다.
- 위험 목록에서 테스트 종류로 넘어간 뒤 AI 보고 검토와 완료 체크리스트로 이어지는 흐름이 자연스럽습니다. 표도 증거의 강점과 한계를 함께 보여 줍니다.
- FR-014를 사례의 실제 요구 ID로 오인하지 않게 명시하고, D-01~D-05 연결을 고정 사례 문맥과 일치시켰습니다. 이를 R13 전체 검토로 확대하지 않습니다.

PASS를 막는 사유는 **공개 출처로 확인되지 않은 ISO 귀속**과 **검증 결과의 대상 버전을 고정하는 실무 지침의 누락**입니다. 입력 전체를 읽는 데 필요한 자료가 없어서 `BLOCKED`인 상황은 아닙니다.

준비 코드의 경우, **고정 입력 검사용 구현은 정적 검토상 적합하지만 최종 `safe-to-checkpoint` 판정은 보류**합니다. 제공된 controller 검사 성공은 인정하되, 준비 테스트의 실제 실행 결과, 적용되는 자동 검사, 커밋 대상의 독립적 분리·staged diff 증거는 제공되지 않았습니다. 이는 원고 검토의 차단 사유가 아니라 로컬 체크포인트의 별도 완료 조건입니다.

- **관찰 근거:** S01은 일반 테스트 개념을 확인하지만 해당 열거를 제공하지 않습니다. S02는 조직·관리·동적 테스트와 ISO/IEC 20246의 정적 리뷰 연결을 제공하면서, 현재 본문에서 해당 열거를 확인하지 못했다고 명시합니다. 과거 source-map의 확인 기록은 있지만, 해당 귀속을 재현할 수 있는 당시 원문 발췌는 이번 입력에 없습니다.
- **영향:** 독자는 ISO 공개 페이지에서 직접 확인된 분류와 핸드북의 교육적 구분을 같은 근거 수준으로 받아들일 수 있습니다. 새 출처 기록에는 공백이 명시됐는데 원고와 현재 근거 상태에는 그 제한이 반영되지 않아 `confirmed`의 범위도 불분명합니다. C05와 SOURCE·EVIDENCE 기준에 해당합니다.
- **최소 수정:** ISO 귀속을 이번 자료가 직접 지지하는 일반 개념·조직·관리·동적 테스트 및 정적 리뷰 연결로 좁힙니다. 수동·자동 구분 자체는 유지할 수 있으나, 확인되지 않은 열거까지 해당 공개 페이지가 뒷받침한다고 쓰지 않습니다. 열거를 유지하려면 추적 가능한 직접 근거를 추가합니다. 과거 2026-08-13 기록은 보존하고 현재 원고·source-gap·감사 기록에 좁은 재판정 또는 보충 기록을 연결합니다.

**R07-I02 — 테스트 성공을 정확한 코드·아티팩트 상태에 연결하는 필수 기록이 빠져 있습니다.**

- **심각도:** Important / P1

- **관찰 근거:** 명령, 환경, 범위, 실행 수와 종료 코드는 요구하지만 실행 당시 commit·미커밋 변경 상태·아티팩트 식별자 및 실행 시점을 명시적으로 요구하지 않습니다. “이전 실행의 로그 … 사용하지 않습니다”라는 금지는 있으나 같은 브랜치에서 실행 후 변경이 생겼는지 판정하는 기록 방법이 없습니다. 인접 `agent-review-and-verification.md`는 기준 상태에 branch·HEAD·dirty를 요구하고, 디버깅 발췌도 대상 버전·환경·시각을 연결합니다.

- **최소 수정:** 실행 환경 항목에 **대상 commit과 미커밋 diff 상태, 실행 시점, 필요한 경우 아티팩트·데이터 버전**을 추가하고, 실행 이후 변경 여부를 확인하게 합니다. 모든 작업에 별도 해시 체계를 강제할 필요는 없으며, 어떤 상태를 실행했는지 식별할 수 있어야 합니다. 프롬프트와 체크리스트에도 같은 요구를 짧게 반영합니다.
- **재확인 기준:** “같은 브랜치에서 테스트 후 코드 변경” 사례를 새 기록 기준으로 구분할 수 있어야 합니다. 이전 상태의 성공을 현재 상태의 성공으로 사용하지 않고 변경 영향에 맞는 재검증을 요구해야 합니다.

- **관찰 근거:** 본문과 개발 용어집은 요구사항 커버리지까지 포함하는 넓은 개념을 정의합니다. 코드 실행 커버리지는 실행 흔적을 나타내지만 요구사항 커버리지까지 동일하게 설명할 수는 없습니다. 본문은 뒤에서 “높은 코드 커버리지”로 좁혀 정확하게 설명하므로 오류는 주로 제목에 있습니다.
- **영향:** 제목 중심으로 읽는 독자는 요구사항과 테스트의 연결 정도를 나타내는 측정도 코드 실행률과 같은 것으로 이해할 수 있습니다. C04·C08에 해당합니다.
- **최소 수정:** 제목을 코드 커버리지로 한정하거나, 커버리지 일반에 대해 “다룬 범위의 측정이며 정확성·사용자 성공을 단독으로 증명하지 않는다”는 표현으로 바꿉니다.
- **재확인 기준:** 제목과 정의의 적용 대상이 일치하고, 코드 실행률과 요구사항 커버리지를 같은 측정으로 취급하지 않아야 합니다.

**R07-M02 — 테스트 대역의 첫 정의가 외부 서비스로 불필요하게 제한됩니다.**

- **심각도:** Minor / P2
- **위치:** `src/content/docs/08-quality/testing-strategy.md`의 「대역과 테스트 데이터의 경계」 첫 문단
- **최소 인용:** “실제 외부 서비스 대신 사용하는 mock, stub, fake”

- **영향:** 초보 독자가 내부 구성요소를 가짜 구현으로 바꾼 테스트의 한계를 대역 사용으로 인식하지 못할 수 있습니다. C04의 용어 일치 기준에 해당합니다.
- **최소 수정:** “실제 구성요소 대신 사용하는”으로 정의를 넓히고 외부 서비스는 대표 예로 둡니다.
- **재확인 기준:** 개발 용어집 정의와 일치하고, 외부 네트워크 사용 여부와 무관하게 대체된 책임 경계를 기록하도록 읽혀야 합니다.

**R07-M03 — 운영 smoke 체크리스트가 본문에서 허용한 승인된 변경 예외를 표현하지 못합니다.**

- **심각도:** Minor / P2
- **위치:** `src/content/docs/08-quality/testing-strategy.md`의 「smoke test」 마지막 문단과 「완료 판단 체크리스트」 운영 smoke 항목
- **최소 인용:** 본문의 “변경이 꼭 필요하다면 전용 테스트 계정과 되돌릴 수 있는 작은 요청”, 체크리스트의 “실데이터 변경·외부 메시지 부작용 없이 수행했습니다”
- **관찰 근거:** 본문은 읽기 전용을 우선하면서도 사전 승인된 변경·중지·정리 절차를 예외로 설명합니다. 체크리스트는 해당 예외나 미수행·적용외 상태를 표현하지 않고 무부작용 실행을 완료 조건처럼 적습니다.
- **영향:** 본문에 맞게 승인된 변경 경로를 검증한 독자가 체크리스트를 정직하게 완료하기 어렵습니다. 안전을 약화하는 문제는 아니지만, 계획한 예외와 실제 수행 증거가 어긋납니다. C06·C08에 해당합니다.
- **최소 수정:** 읽기 전용 수행을 기본으로 확인하되 변경이 있었다면 승인 범위·전용 대상·중지 조건·정리 결과를 기록하게 합니다. 운영 smoke가 필요하지 않거나 실행하지 않았다면 그 상태도 구분하게 합니다.
- **재확인 기준:** 읽기 전용 실행, 승인된 변경 실행, 미실행·적용외를 각각 사실대로 기록할 수 있어야 합니다.

준비 코드 검토에서는 다음을 확인했습니다.

- manifest의 **바이트 해시를 먼저 고정 상수와 비교**합니다. 따라서 manifest 내용과 내부 개별·결합 해시를 함께 바꾸는 방식으로 현재 검사기를 통과시킬 수 없습니다.
- 각 전체 입력은 해시와 바이트 길이를 확인하고, 경로·내용 길이와 실제 바이트를 framing한 결합 해시에도 포함합니다.
- 파일 읽기 실패는 오류를 누적하며 정상 결과로 흡수하지 않습니다.
- 요청서 파싱 실패, 문맥 파일 해시 불일치, 명시 행 범위의 텍스트 불일치를 각각 오류로 남깁니다.
- 이미지 0개 조건과 R07 식별자를 확인하며 반환값에서 `reviewComplete: false`, `releaseReady: false`를 유지합니다.
- 테스트는 정상 입력, 누락·변경, manifest 교체, 정확한 문맥 행 비교, 요청서 파싱 실패·결합 해시 변화를 다룹니다. 문맥 변경 테스트가 해시 오류와 함께 행 불일치 오류도 확인하므로 행 비교 분기 자체를 검증하는 의미가 있습니다.

이 구현은 **고정된 R07 payload 전용 검사기**입니다. 임의 manifest에 대한 범용 스키마 검증이 없다는 이유만으로 결함으로 판정하지 않았습니다. 승인된 manifest 바이트가 먼저 고정되기 때문입니다.

다만 R06 JSON 안의 사례 원본 경로·해시는 이 코드에서 재귀적으로 다시 검사하지 않습니다. 현재 검토에서는 별도로 제공된 controller의 사례 원본·발췌 재확인 증거를 사용합니다. 따라서 이 검사기 하나의 성공을 “모든 중첩 출처까지 다시 검증했다”는 주장으로 확대하면 안 됩니다. 현재 요청은 그 별도 증거를 구분해 제공했으므로 준비 finding으로 집계하지 않았습니다.
