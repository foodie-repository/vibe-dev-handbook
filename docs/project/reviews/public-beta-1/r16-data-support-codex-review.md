**R16-I01 — 구체적인 마이그레이션 순서에 백필 전 쓰기 보호와 전환 직전 수렴 조건이 빠져 있습니다.**

- **심각도:** Important / P1.
- **위치:** `src/content/docs/04-backend-data/data-model-schema-migration.md` → 「예: `location_text`를 장소 유형과 상세로 나누기」의 1~4단계, 「백필을 별도 작업으로 다루기」, AI 변경 계획.

- **관찰·근거:** 장 전체는 동시 쓰기 위험을 인식하고 있고, 앞선 출처 설명에는 구·신 필드 쓰기와 복사 순서도 있습니다. 그러나 독자가 따라 읽는 구체적인 단계에서는 새 열 추가 후 바로 백필하고 검증한 다음 읽기를 전환합니다. **구버전의 옛 열 쓰기를 언제부터 어떻게 반영하는지, 백필이 최신 쓰기를 덮지 않게 하는 조건, 검증 이후의 변경을 어떻게 따라잡는지**가 단계의 선행 조건으로 명시되지 않습니다. 제공된 Parallel Change·CI·Evolutionary Database Design 근거와 호환성 표가 요구하는 공존 문제를 실제 예시에 연결해야 합니다.
- **영향:** 백필이 `회의실 A`를 읽은 뒤 사용자가 `회의실 B`로 수정하고, 백필이 늦게 새 열에 A를 쓰면 두 표현이 갈라집니다. 한 차례 전체 검증이 통과한 뒤 구버전 쓰기가 발생해도 전환 시점에는 다시 불일치할 수 있습니다. “충돌이 없는지 확인한다”는 질문만으로는 이 순서를 안전한 변경 계획으로 사용할 수 없습니다.
- **최소 수정:** 백필 전에 모든 쓰기 경로를 식별하고, 호환 코드·동기화 경로·통제된 쓰기 중지 등 선택한 보호가 먼저 유효해야 한다고 명시합니다. 백필은 읽은 버전과 현재 버전의 비교 등으로 최신 변경을 덮지 않게 하고, 충돌 행은 재처리 대상으로 남기도록 설명합니다. 읽기 전환은 새 쓰기를 포함한 대조·수렴 조건을 통과한 뒤에만 허용합니다. 특정 제품이나 이중 쓰기 구현을 필수로 강제할 필요는 없습니다.
- **재확인 기준:** ① 백필의 읽기와 쓰기 사이에 수정 발생, ② 검증 후 읽기 전환 전 구버전 쓰기 발생, ③ 새 코드의 새 형식 쓰기 후 구버전 복귀라는 세 반례에서 최신 정보가 보존되고 전환·중지 조건을 판단할 수 있어야 합니다.

**R16-I02 — 차단된 갱신 후보를 현재 데이터셋의 `stale` 판정으로 곧바로 연결합니다.**

- **심각도:** Important / P1.
- **위치:** `src/content/docs/04-backend-data/state-cache-queue.md` → 「교육용 주가 fixture는 별도 사례입니다」.

- **관찰·근거:** 제공된 `research/stock-dashboard-case-brief.md`는 후보 품질과 공개 버전의 신선도를 분리합니다. 같은 차단 후보라도 기대 갱신 시각 전에는 `current`, 기대 시각 이상인데 갱신하지 못했으면 `stale`, 필요한 시각이 없으면 `unknown`입니다. 대상 문장은 그 조건 없이 `blocked → stale`로 연결합니다.
- **영향:** 아직 갱신 기한이 오지 않은 정상 공개 버전을 오래된 것으로 표시하거나, 판단 기준이 없는 상태를 `unknown` 대신 `stale`로 단정할 수 있습니다. 이 장의 핵심인 “서로 다른 상태의 책임을 구분한다”는 설명과도 충돌합니다.
- **최소 수정:** 차단 후보의 상태·사유는 별도로 표시하고 현재 공개 버전은 유지하되, 신선도는 기준 시점과 `expected_refresh_at`에 따라 `current`·`stale`·`unknown`으로 판단한다고 바꿉니다. `stale`은 기대 시점이 지났는데 승인된 갱신이 제공되지 않은 조건으로 한정합니다.
- **재확인 기준:** 동일한 차단 후보에 대해 11:59Z·12:01Z·기대 시각 없음의 세 예가 각각 `current`·`stale`·`unknown`이 되고, 공개 버전의 바이트는 모두 유지돼야 한다는 사례 계약과 일치해야 합니다.
- **적용 기준:** C03·C04·C05.

**R16-I03 — 처리 직전 원본 재조회가 외부 부작용까지 안전하게 묶는다는 인상을 줍니다.**

- **심각도:** Important / P1.
- **위치:** `src/content/docs/04-backend-data/state-cache-queue.md` → 「이벤트와 큐 메시지를 현재 상태로 오해하지 않기」, 「재처리는 원본 확인에서 시작하기」의 3~6단계, 짧은 연습 4번.
- **최소 인용:** “처리 직전에 권위 있는 원본을 다시 읽어야 합니다”, “여전히 처리 대상이면 … 남은 단계를 실행합니다”, “취소 뒤 도착해도 잘못된 알림이나 상태 덮어쓰기를 하지 않는 오라클”.
- **관찰·근거:** 현재 원본을 확인하는 방향은 맞고, 본문은 멱등 결과의 원자적 기록과 DB·큐 부분 실패도 설명합니다. 다만 **원본 재조회와 알림 전송 사이에 참가 취소가 확정되는 경우**는 별도의 경계로 남습니다. 조회 결과가 참이었다는 사실은 뒤의 외부 호출 시점에도 참이라는 보장이 아닙니다. 같은 이유로 버전 비교 후 별도의 무조건 갱신을 하면 오래된 작업이 최신 파생 상태를 덮을 수 있습니다.
- **영향:** 독자가 재조회 한 번을 경쟁 조건의 해결책으로 채택하거나, 외부 알림까지 DB 트랜잭션과 같은 보장을 갖는다고 오해할 수 있습니다. 원본 확인 직후 취소가 일어나는 반례에서는 현재 절차만으로 연습의 강한 오라클을 충족하지 못합니다.
- **최소 수정:** 재조회는 필요 조건이며 이후 경쟁까지 제거하지 않는다고 명시합니다. DB 안의 상태·버전 판정과 결과 갱신은 조건부 갱신 또는 적절한 트랜잭션 전략으로 함께 보호하도록 연결합니다. 외부 알림은 ‘어느 시점의 참가 상태를 기준으로 발송을 허용하는지’, 발송 결정 후 취소의 처리, 결과 불명·중복 방지의 한계를 별도 계약으로 정하도록 합니다. 외부 호출 동안 DB 잠금을 유지하는 방식을 보편 해법으로 제시할 필요는 없습니다.
- **재확인 기준:** ① 재조회 전에 취소 확정, ② 재조회 후 외부 전송 전에 취소 확정, ③ 버전 비교 후 최신 결과가 먼저 저장되는 세 순서를 구분하고, 보장 가능한 결과와 남는 경계를 명시해야 합니다.
- **적용 기준:** C02·C04·C06.

**R04-M05 — 필드명 대응 설명 부재를 수용하며, R16에서도 `OPEN`으로 유지합니다.**

- **심각도:** Minor / P2. 기존 이월 ID를 유지하며 새 중복 finding으로 세지 않습니다.

- **직접 판정:** 두 이름은 모두 사용자를 참조하는 주최·참가 관계를 나타내므로 **관계 의미 자체가 다른 오류는 아닙니다.** 하지만 동일 반복 사례의 필드를 다른 이름으로 쓰면서 대응을 밝히지 않아 독자가 인가 규칙과 SQL의 열을 추측해서 연결해야 합니다. 교육용 예시라는 일반적인 주의 문구만으로 이 대응 문제는 해소되지 않습니다.

- **재확인 기준:** SQL, 고유성 설명, 공동 주최자 표와 현재 API 장·브리프를 추측 없이 연결할 수 있어야 합니다.
- **적용 기준:** C03·C04·C08.

**R16-M04 — 생산자 확인과 소비자 확인의 구분을 독자에게 명시하지 않습니다.**

- **심각도:** Minor / P2.
- **위치:** `src/content/docs/04-backend-data/state-cache-queue.md` → 「중복과 재전달을 정상 가능성으로 다루기」, 「재처리는 원본 확인에서 시작하기」.
- **최소 인용:** “메시지가 받아들여졌는지”, “완료 확인 시점은 선택한 큐 계약에 맞춥니다.”
- **관찰·근거:** 제공된 RabbitMQ 근거는 생산자 확인과 소비자 acknowledgement의 책임을 구분합니다. 원고는 생산자의 불확실성과 소비자의 확인 유실을 각각 설명하지만 두 확인이 **누구에게 무엇을 확인하는지**를 한 번에 명확히 정의하지 않습니다.
- **영향:** 입문자가 브로커의 수신 확인을 소비자의 업무 완료로 읽거나, 소비자의 ack를 외부 알림의 정확히 한 번 성공과 연결할 여지가 남습니다.
- **최소 수정:** 생산자 확인은 선택한 제품 계약에 따른 브로커 측 수락·보관 범위이고, 소비자 확인은 전달받은 메시지를 어떻게 처리했는지 브로커에 알리는 별도 경계라고 짧게 구분합니다. 둘 중 어느 것도 임의의 외부 부작용을 자동으로 정확히 한 번 완료시키지 않는다고 연결합니다.
- **재확인 기준:** “브로커 수신 확인 후 소비자 미실행”, “업무 완료 후 ack 유실”을 서로 다른 상태로 설명할 수 있어야 합니다.
- **적용 기준:** C02·C04·C05.
