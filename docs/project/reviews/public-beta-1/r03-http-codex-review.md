**3. 위치별 finding**

위치는 제공된 원문의 절과 최소 인용으로 식별합니다. 실제 행 번호를 도구로 확인하지 않았으므로 임의의 행 번호는 붙이지 않습니다.

**R03-I01 — Important: HTTP 성공과 업무 완료를 연결할 때 접수와 완료의 구분이 빠집니다.**

위치: `src/content/docs/03-full-stack/http-request-response.md`의 「상태 코드 범주」, 「성공·거절·실패를 구분하는 응답」.

최소 인용은 `2xx | 요청을 성공적으로 처리함`과 `조회·참가·취소 성공 | 해당 동작에 맞는 2xx`입니다.

현재 모임 예시는 동기적으로 참가를 확정한 뒤 응답하므로 그 예시 자체는 일관됩니다. 그러나 장 앞부분은 `POST`를 “특정 처리를 시작”하는 데도 사용한다고 설명하고, 제공된 클라이언트·서버 문맥은 오래 걸리는 작업의 **접수와 별도 상태 조회·알림에 의한 완료**를 구분합니다. 일반 HTTP 설명에는 이 차이를 성공 응답 해석에 연결하는 문장이 없습니다.

독자는 `2xx`를 받으면 보고서 생성이나 다른 후속 작업까지 끝났다고 확대할 수 있습니다. C02·C04의 정확한 경계와 C06의 완료 증거 구분에 영향을 줍니다.

최소 수정은 상태 코드 표 뒤에 “HTTP 성공과 업무 완료 여부는 해당 상태 코드와 API 계약의 작업 상태를 함께 확인한다”는 설명을 넣고, 모임의 참가 성공 예시는 **확정 후 응답하는 계약**임을 짧게 명시하는 것입니다. 비동기 상태 코드의 구체적 예시를 추가한다면 그 코드의 규범 원문도 좁게 보충해야 합니다. 제공된 발췌만으로 특정 비동기 상태 코드의 세부를 새로 검증했다고 표시해서는 안 됩니다.

재확인 기준은 독자가 **접수됨·처리 중·업무 완료·결과 불명**을 HTTP 성공 하나로 합치지 않고, 각각 어떤 계약상 상태나 조회 결과로 구분하는지 설명할 수 있는지입니다.

**R03-I02 — Important: 서버 오류까지 “데이터가 바뀌지 않았음”의 공통 검증 대상으로 읽힙니다.**

위치: 같은 파일의 「성공·거절·실패를 구분하는 응답」 마지막 문단, 「상태 코드 범주」의 `5xx` 행.

최소 인용은 다음 두 곳입니다.

> “인증 실패, 권한 거절, 입력 오류, 이미 참가함, 정원·마감, 버전 충돌과 서버 오류를 클라이언트가 안정적으로 구분하고 데이터가 바뀌지 않았음을 테스트할 수 있는 계약”

> “서버가 정상적인 요청을 처리하지 못함”

첫 문장은 서버 오류를 포함한 모든 나열 항목에서 데이터 불변을 요구하는 것으로 읽힙니다. 하지만 같은 장은 응답 전달 실패를 저장 실패로 단정하지 말라고 설명하고, API 장도 **저장 중 실패와 전체 rollback**, **commit 뒤 응답 실패**를 별도 상태와 증거로 나눕니다. 제공된 근거에는 일반적인 서버 오류 응답만으로 데이터 불변을 확정할 수 있다는 근거가 없습니다. `5xx`라는 범주만으로 입력까지 정상이라고 확정하는 표현도 과합니다.

이 문장을 그대로 검증 지시로 옮기면 서버 오류를 “변경 없음”으로 취급하거나, 실제 확정 여부를 확인하기 전에 재시도를 결정할 수 있습니다. C02·C06의 실패·복구 및 증거 경계에 해당합니다.

최소 수정은 데이터 불변 요구를 **변경 전에 거절하도록 계약한 인증·인가·입력·업무 거절**에 연결하고, 서버 오류·전달 실패는 계약과 처리 단계에 따라 **rollback 확인 또는 권위 상태·처리 기록 확인**으로 나누는 것입니다. `5xx`의 쉬운 설명도 “서버 측 처리 오류를 나타내는 범주”처럼 원인과 입력 유효성을 단정하지 않는 표현으로 좁히면 됩니다.

재확인 기준은 변경 전 거절, 저장 중 실패, 확정 뒤 전달 실패를 나눠 읽었을 때 각각 **변경 없음·취소 확인·이미 확정됐을 가능성**이 구분되는지입니다. 문서 수정 검증을 위해 실제 앱을 새로 구현할 필요는 없습니다.

**R03-I03 — Important: CORS의 사전 요청 성공 후 응답 차단 경로가 빠져 있습니다.**

위치: 같은 파일의 「실제 작업에서 보이는 신호 → 브라우저 개발자 도구」.

최소 인용은 다음과 같습니다.

> “사전 요청 실패로 본 요청이 진행되지 않을 수 있습니다. 반대로 사전 요청이 필요 없는 교차 출처 요청은 서버에 도달해 처리됐지만 … JavaScript가 응답을 사용하지 못할 수 있습니다.”

제공된 10월 25일 Fetch 근거는 **preflight 실패 반환 → network fetch → CORS check**의 순서를 명시합니다. 따라서 사전 요청이 성공해 본 요청으로 진행한 뒤에도 응답 공유 검사에서 실패하는 경우를 설명할 수 있어야 합니다. 현재 문장은 사전 요청 실패와 사전 요청 없는 요청의 사후 실패만 대비합니다.

본문 전체의 “CORS 오류가 서버 미처리 증거는 아니다”라는 결론은 맞습니다. 다만 사전 요청이 있었던 쓰기 요청을 진단하는 독자에게 가장 필요한 중간 경로가 빠져, `OPTIONS` 성공을 응답 사용 가능의 보장으로 오해할 여지가 있습니다. C02·C04·C05에 해당합니다.

최소 수정은 “사전 요청이 성공한 경우에도 본 요청의 응답이 CORS 공유 조건을 만족하지 않으면 JavaScript가 사용하지 못할 수 있다”는 한 문장을 추가하는 것입니다. 본 요청의 서버 처리 여부는 여전히 상태 재조회와 처리 기록으로 확인하도록 연결합니다.

재확인 기준은 다음 세 경우가 모두 설명되는지입니다.

1. 사전 요청 실패로 본 요청이 진행되지 않은 경우.
2. 사전 요청 성공 후 본 요청은 처리됐지만 응답 공유가 실패한 경우.
3. 사전 요청 없이 본 요청이 처리된 뒤 응답 공유가 실패한 경우.

세 경우를 모두 서버 미처리 또는 모두 서버 처리로 단정하지 않아야 합니다.

**R03-M01 — Minor: CORS 판단에 필요한 ‘출처’와 HTTPS 설명의 TLS가 첫 등장 때 충분히 풀리지 않습니다.**

위치: 같은 파일의 「한 문장 정의」와 「브라우저 개발자 도구」.

최소 인용은 `HTTP 메시지를 TLS로 보호하는 HTTPS`, `서버가 다른 출처에 응답을 공유`입니다.

제공된 용어집은 origin을 프로토콜·호스트·포트의 조합으로 정의하지만, 이 장에서는 “다른 출처”를 판단할 기준을 직접 설명하지 않습니다. TLS도 약어를 먼저 사용합니다. 비개발자는 경로만 다른 경우와 포트가 다른 경우를 구분하지 못한 채 CORS 설정을 점검할 수 있습니다. C04·C08의 첫 용어 설명 문제입니다.

최소 수정은 TLS를 처음 사용할 때 “전송 계층 보안”으로 풀고, CORS 문단에 출처의 세 구성요소를 한 문장으로 넣는 것입니다. 전체 용어집을 반복할 필요는 없습니다.

재확인 기준은 같은 호스트에서 경로만 바뀐 경우와 포트·프로토콜이 바뀐 경우를 독자가 구분할 수 있는지입니다.

**R03-M02 — Minor: 상태와 본문을 함께 사용하라는 설명에 본문 없는 응답의 예외가 빠집니다.**

위치: 같은 파일의 「응답을 읽는 세 가지 칸」 및 「성공·거절·실패를 구분하는 응답」의 성공 행.

최소 인용은 `둘 중 하나만 사용하면 클라이언트가 안정적으로 판단하기 어렵습니다`와 `응답 본문과 권위 있는 참가 상태가 일치하는지 확인`입니다.

같은 장은 자기 취소 성공을 `204 No Content`로 올바르게 제시합니다. 제공된 RFC 발췌도 204에 content나 trailers가 없다는 경계를 명시합니다. 그런데 앞선 일반 지침과 성공 행에는 이 예외가 없어 모든 성공 응답에서 본문을 읽어야 한다는 지시로 옮겨질 수 있습니다. C04·C08에 해당합니다.

최소 수정은 “본문이 있는 응답에서는”이라는 조건을 넣고, 204처럼 본문 없는 응답은 상태·필요한 헤더와 계약상 재조회로 확인한다고 설명하는 것입니다.

재확인 기준은 204 예시가 빈 본문을 정상으로 취급하며, 필수 JSON 파싱이나 필수 성공 본문을 요구하지 않는지입니다.

**R03-M03 — Minor: 참가 예시의 이벤트 버전 규칙이 추가 가정으로 명시되지 않습니다.**

위치: 같은 파일의 「자신의 참가 신청」.

최소 인용은 `기대한 event.version을 … 함께 판단해야 합니다`, `{"expectedEventVersion":7}`, `{"…","eventVersion":8}`입니다.

사례 브리프는 `event.version`을 동시 수정 감지용 정수로 설명하고, 캡스톤은 주최자 수정의 버전 계약을 명시합니다. HTTP 예시는 참가 POST에서도 기대 버전을 검사하고 참가 후 버전을 7에서 8로 바꿉니다. 이것이 잘못된 설계라고 판단할 근거는 없습니다. 다만 **참가도 이벤트 버전을 바꾸는 설계를 이 예시에 추가했다는 사실**과 그 적용 범위가 설명되지 않습니다.

독자는 참가 때 버전 검사·증가가 HTTP나 공통 사례의 필수 규칙이라고 받아들일 수 있습니다. C03·C04의 사례 계약 추적 문제입니다.

최소 수정은 이 예시에서 기대 버전을 사용하는 이유와 참가 확정 시 버전도 증가시키는 가정을 한두 문장으로 명시하는 것입니다. 이를 공통 사례의 필수 계약으로 채택할 의도가 없다면 선택한 API 설계의 예시임을 분명히 하면 됩니다.

재확인 기준은 어떤 동작이 버전을 증가시키는지, 다른 참가가 먼저 확정된 경우 기존 기대 버전을 어떻게 처리하는지, 실제 계약이 없는 프로젝트에 이 규칙을 임의로 추가하지 않는지가 명확한지입니다.

**R03-M04 — Minor: Network 기록을 시작한 뒤 오류를 재현해야 한다는 순서가 빠집니다.**

위치: 같은 파일의 「브라우저 개발자 도구」.

최소 인용은 `화면 오류를 재현한 직후 실패한 요청 하나를 고르고`입니다.

제공된 Chrome 직접 근거는 Network 패널이 열려 있는 동안 활동을 기록한다고 명시합니다. 현재 절차는 처음 개발자 도구를 사용하는 독자가 오류를 먼저 재현하고 패널을 열어도 해당 요청을 찾을 수 있다고 읽을 여지가 있습니다. 이는 기술 정의 오류보다는 실습 순서의 국소 누락입니다. C02·C08에 해당합니다.

최소 수정은 “Network 패널을 열고 기록 중인지 확인한 뒤 오류를 재현한다”는 순서로 바꾸는 것입니다.

재확인 기준은 처음 패널을 여는 독자도 요청 기록을 확보한 뒤 URL·메서드·상태·본문을 확인할 수 있는 절차인지입니다.

**R03-PREP-M01 — Minor, 준비 코드 전용: 핵심 발췌 대조와 로컬 증거 실패 경로를 직접 확인하는 테스트가 없습니다.**

위치: `tests/r03-review-inputs.test.mjs` 전체. 관련 구현은 `scripts/r03-review-inputs.mjs`의 context segment 검사와 `localEvidence` 분기입니다.

최소 인용은 테스트의 `Buffer.from('drift')`, `assert.ok(r.errors.length>0,path)` 및 구현의 `context segment mismatch`, `render provenance mismatch`입니다.

현재 테스트는 기본 준비 검증, 지정 텍스트·문맥 파일의 누락과 뒤쪽 바이트 추가, 고정 manifest 변경을 검사합니다. 그러나 문맥 뒤에 `drift`를 추가하는 테스트는 발췌 구간 자체를 바꾸지 않으므로 **행 범위와 삽입 발췌의 정확한 대조가 실제로 동작하는지**를 직접 입증하지 않습니다. 또한 `localEvidence: true`의 PNG·결합 해시·렌더 계보 실패 경로를 직접 확인하는 테스트가 없습니다.

최소 수정은 기존 발췌 안의 한 줄을 바꿨을 때 해당 `context segment mismatch`가 실제로 포함되는지 검사하고, 로컬 증거 모드에서 PNG 누락·변경과 렌더 manifest 변경을 구분해 거절하는 대표 테스트를 보강하는 것입니다. 단순히 `errors.length > 0`만 확인하면 다른 해시 오류가 발췌 검사 누락을 가릴 수 있습니다.

재확인 기준은 관련 검사를 제거했을 때 대응 테스트가 실패하고, 원본 입력에서는 `reviewComplete: false`, `releaseReady: false`가 유지되는지입니다. 이번 reviewer는 테스트를 실행하지 않았습니다.

준비 코드의 나머지 판단은 다음과 같습니다.

- manifest 바이트의 SHA를 고정 상수와 먼저 대조하므로, manifest의 기대 해시를 함께 바꾸는 것만으로 입력 변조를 승인할 수 없습니다.
- 개별 파일 해시 불일치와 누락은 오류로 누적되며 성공 결과로 지워지지 않습니다.
- 로컬 증거 모드에서는 경로 길이·내용 길이를 포함한 바이트 프레이밍으로 결합 해시를 대조합니다.
- 문맥 파일 전체 해시와 지정 행의 실제 문자열을 각각 대조합니다.
- 기본 모드의 PNG 및 일부 로컬 증거 생략은 `localEvidence: 'not-checked'`로 표시됩니다. 전체 로컬 증거 검증으로 표현하지 않습니다.
- request 파싱 실패는 오류에 남습니다. 고정 manifest와 request 해시가 전제되는 이 검사기에 대해, 일반 목적 JSON 스키마 검사가 없다는 이유만으로 우회 결함을 만들지는 않았습니다.
- PNG의 전체 바이트 해시와 최소 서명·IHDR 확인은 파일 식별·형식 점검입니다. 디코딩 성공·픽셀 가독성·현재 페이지 상태를 증명하지 않으며, 이번 별도 이미지 판독과도 역할이 다릅니다.
- `reviewComplete`와 `releaseReady`는 항상 `false`로 반환됩니다. 입력 검사를 원고 PASS나 공개 준비 완료로 승격하지 않습니다.

**5. 미확인 사실·남은 위험·검토 한계**

**과거 캡처 증거와 이번 관측은 서로 다른 증거입니다.** Task20의 `accepted_state`와 DOM·source 검사, 이후 부모 관찰 및 Task21 QA는 제공된 기록으로 읽었습니다. 이번에는 그 기록의 PASS를 재사용해 그림을 통과시키지 않고 실제 PNG 18개를 각각 보았습니다. 반대로 이번 crop 판독을 현재 사이트 전체의 DOM·상호작용·접근성 검증으로 확대하지 않습니다.

- **응답 후 불변성 및 정본 저장:** controller의 후속 감사·결과 저장·재판정은 아직 일어나지 않았습니다.

**6. 재확인 기준**

원고의 다음 수정은 **R03-I01~I03과 R03-M01~M04가 위치한 문단·표·예시를 중심으로 좁게 진행**하면 됩니다. 전면 재작성은 필요하지 않습니다.

1. **의미 수정과 계약 연결을 확인합니다.** HTTP 성공과 업무 완료, 변경 전 거절과 처리 결과 불명, CORS의 세 경로를 구분합니다. 본문 없는 응답·버전 예시의 가정·첫 용어·Network 기록 순서도 해당 위치에서 보완합니다.
2. **변경된 입력을 다시 고정합니다.** controller가 원고와 필요한 근거의 변경 전후 SHA, 새 입력별·결합 SHA, 영향 범위를 기록해야 합니다. 준비 검사기의 고정 manifest SHA를 갱신하는 경우에도 변경 자체가 검토 통과를 의미하지 않도록 유지해야 합니다.
3. **같은 reviewer 세션에서 영향 범위를 재검토합니다.** 수정 diff, 수정된 절의 충분한 전후 문맥, 필요한 추가 공식 발췌, 새 고정 입력 정보를 제공하면 이 finding ID를 기준으로 해소 여부를 재판정할 수 있습니다. R02 승계 예외는 적용하지 않습니다.
4. **필요한 검증만 수행합니다.** 원고 변경에 대한 저장소의 정적 검사와 빌드 결과를 controller가 확인해야 합니다. HTTP 표·코드 블록의 배치가 바뀌면 해당 장의 모바일·데스크톱 표시를 좁게 확인합니다. 공통 SVG·Mermaid와 렌더 조건이 바뀌지 않았다면 이번 그림 판독을 이유 없이 다시 수집할 필요는 없습니다. 그림이 바뀌면 세 소비 문맥의 관련 시각 증거를 새 입력으로 제공해야 합니다.
5. **준비 코드의 테스트 공백은 별도로 확인합니다.** R03-PREP-M01을 반영한다면 정확한 발췌 불일치와 로컬 증거 실패를 검출하는 테스트 결과를 제공해야 합니다. 이 결과는 원고의 Important 해소를 대신하지 않습니다.
6. **응답 후 감사와 정본화를 수행합니다.** controller가 이번 입력의 응답 후 불변성, 응답 완전성, 실제 프로필·권한, 결과 형식을 확인하고 정본으로 저장해야 합니다. finding의 수용·부분 수용·기각은 근거와 함께 별도로 기록해야 합니다.

현재 결과는 **실제 R03 원고 검토의 `NEEDS CHANGES`와 별도 준비 코드의 좁은 검토 의견**입니다. 소유자 승인, `ready`, RC, M5 전체, M6/M7, 커밋·푸시·배포·공개 URL의 승인이나 완료를 부여하지 않습니다.
