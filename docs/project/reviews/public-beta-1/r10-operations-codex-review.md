**2. 판정과 건수**

**원고: `NEEDS CHANGES` — Critical 0건 / Important 3건 / Minor 3건.**

입력 누락이나 실제 이미지 미전달을 이유로 하는 `BLOCKED` 사유는 없습니다. 대상 원고와 지정 전체 텍스트, 문맥 발췌, 실제 PNG 18개를 읽었습니다. 입력 불변성은 제공된 controller 검증 기록에 근거하며, 응답 후 재검사는 남아 있습니다.

원고의 강점은 명확합니다. 내부 프로세스 생존·HTTP 성공·신호 수집·알림 전달·백업 생성·복원·사용자 복구를 서로 다른 증거로 설명합니다. 업무상 거절과 시스템 실패를 무조건 합산하지 않으면서 인가 거절 급증도 정상으로 단정하지 않습니다. RPO·RTO를 사업 목표와 실제 시험 기록으로 연결하고, 코드 롤백과 데이터·외부 상태 복구가 다르다는 점도 잘 설명합니다.

다만 다음 세 문제가 핵심 운영 판단에 영향을 줍니다.

1. 회전·재발급할 수 있는 자격 증명과 과거 암호문을 해독하는 데 필요한 키를 구분하지 않습니다.
2. NIST SP 800-61r3의 적용 대상을 공식 Audience보다 부정확하게 좁혀 설명합니다.
3. 사고 이력, 현재 데이터 불변식, 수정 후 인가·동시성 회귀를 분리하지 않은 재개 기준이 있습니다.

**준비 코드: Critical 0건 / Important 0건 / Minor 0건. 준비 단위의 로컬 체크포인트 대상으로 적합합니다.**

이 판단은 `scripts/r10-review-inputs.mjs`와 `tests/r10-review-inputs.test.mjs`의 정적 검토 및 제공된 실행·index 증거에 한정합니다.

- manifest 자체의 고정 해시를 먼저 검사하므로, 입력과 manifest를 함께 다시 해싱해 임의 변경을 승인하는 구조가 아닙니다.
- 개별 바이트·크기, 명시 문맥의 파일 해시와 행 내용, local 모드의 결합 해시·PNG 헤더·두 렌더 manifest를 검사합니다.

**3. 위치별 finding**

**R10-I01 — Important/P1: 비밀의 재발급과 과거 암호문 복구에 필요한 키 보존을 구분해야 합니다.**

- **위치:** `src/content/docs/10-deployment-operations/logs-monitoring-backup.md`의 「백업 계획은 복원 질문에서 시작하세요」 3번 및 이어지는 문단, 「백업·복구 체크리스트」.
- **최소 인용:** “비밀 자체가 아닌 비밀 관리 위치·회전·재발급 절차”, “비밀을 백업에 복사하는 대신 회전·재발급 절차가 있습니다.”
- **관찰·근거:** 원고 앞부분은 암호화 키가 없으면 백업을 읽지 못한다고 정확히 경고합니다. 그러나 실행 가능한 계획과 체크리스트에서는 비밀의 복구를 회전·재발급으로 일괄 대체합니다. API 토큰이나 비밀번호를 새로 발급하는 것과, 기존 백업을 암호화한 키를 다시 사용할 수 있게 복구하는 것은 다릅니다. 새 키만 만들어서는 과거 암호문을 해독할 수 없습니다. 앞의 경고와 뒤의 행동 기준 사이에 중요한 연결이 빠져 있습니다. C02·C04·C06에 해당합니다.
- **영향:** 초보 독자는 비밀 관리 시스템을 잃었을 때 새 키 발급 절차만 있으면 암호화 백업도 복구할 수 있다고 판단할 수 있습니다. 백업 파일과 재발급 절차가 모두 있어도 데이터가 복구 불가능해질 수 있습니다.
- **최소 수정:** 일반 Git·문서·무차별 백업에 비밀을 복사하지 않는 원칙은 유지하되, 다음 두 종류를 구분하십시오. 재발급 가능한 접근 자격은 회전·폐기·consumer 전환을 설계하고, 기존 암호문에 필요한 키·키 버전·복구 재료는 승인된 전용 보관·복구 체계에서 보호하며 필요한 보존 기간 동안 실제 해독 가능성을 시험해야 합니다. 관리형 키의 내보내기 가능 여부나 특정 복구 기능은 제품별 확인 대상으로 남기면 됩니다.
- **재확인 기준:** 비밀 관리 서비스 또는 주 접근 계정의 상실을 가정해도 필요한 이전 백업을 해독할 수 있는지 확인하는 기준이 본문과 체크리스트에 연결돼야 합니다. “새 키 발급 = 기존 백업 해독”으로 읽히는 문장이 없어야 합니다.
- **심각도 판단:** 원고가 키 상실 위험과 암호화 해제 시험 자체를 이미 언급하므로 보안·데이터 손실 위험을 전면 무시한 Critical로 분류하지 않았습니다. 다만 실제 복구 계획을 잘못 완성하게 만드는 중요한 경계 오류입니다.

**R10-I02 — Important/P1: NIST SP 800-61 Rev. 3의 적용 대상 설명이 제공된 공식 Audience와 맞지 않습니다.**

- **관찰·근거:** 보충 근거 `research/public-beta-review-source-excerpts/r10-operations-2026-11-15.md`의 R10-S03은 공식 PDF Audience를 다음과 같이 직접 제시합니다. “This publication is intended for use by most organizations, regardless of sector, size, or other factors.” 이는 발행 기관의 연방 성격과 별개로 문서의 의도된 사용 대상을 넓게 명시합니다. 원고가 “연방 전용”이라고 단정한 것은 아니지만, “연방 정보 시스템 중심”이라는 적용 범위 설명은 이 Audience를 정확하게 전달하지 못합니다. **R10-I03 — Important/P1: 사고 후 재개 기준에서 과거 위반 이력, 현재 데이터 상태, 수정된 동작의 검증을 분리해야 합니다.**

- **위치:** `src/content/docs/10-deployment-operations/logs-monitoring-backup.md`의 「개발 사례: 모임 참가 웹앱」 불변식 위반 대응 4번.
- **최소 인용:** “불변식 쿼리로 `confirmed <= capacity`와 타인 취소 위반 0건을 확인하고 … 공개 조회·참가·자기 취소 smoke 흐름 … 뒤 제한을 해제합니다.”
- **관찰·근거:** `confirmed <= capacity`는 현재 데이터의 불변식으로 조회할 수 있습니다. 반면 타인 취소의 무권한 여부는 당시 주체·권한·대상·변경 이력이 필요합니다. 이미 확인된 무권한 취소 사건은 복구 뒤에도 역사적 사건으로 남아야 하므로, 시간 범위 없이 “위반 0건”을 요구하면 앞의 증거 보존 원칙과 충돌합니다. 정상 참가·자기 취소 smoke만으로는 타인 취소 거절이나 동시성 결함의 수정도 검증되지 않습니다. 제공된 모임 브리프의 W-03·W-04와 캡스톤은 활성 중복 0건, 인가 부정 테스트, 같은 시작 장벽의 경쟁 시험을 구분합니다. C02·C03·C06에 해당합니다.
- **영향:** 과거 사건을 없애야 재개할 수 있다고 오해하거나, 정상 경로만 성공한 상태에서 인가·동시성 결함이 남은 쓰기를 다시 열 수 있습니다.
- **최소 수정:** 재개 판정을 다음 세 증거로 나누십시오. 현재 데이터의 정원·활성 중복 등 불변식과 피해 정정 결과, 보존된 사건 이력 및 조치 이후 명시된 관찰 구간의 추가 위반 여부, 원인에 맞는 격리 회귀 시험입니다. 타인 취소는 거절·데이터 불변을 확인하고, 정원 경쟁 결함은 기존 동시성 오라클을 다시 확인한 뒤 승인된 smoke와 재개 판단으로 연결하면 됩니다.
- **재확인 기준:** 과거 사고 건수는 보존되면서 현재 상태와 재발 여부를 판정할 수 있어야 합니다. 현재 행 조회만으로 과거 인가를 증명하거나, 정상 smoke만으로 무권한·동시성 경로를 검증한 것으로 쓰지 않아야 합니다.

**R10-M01 — Minor/P2: 사례의 즉시 쓰기 제한을 사전에 승인된 운영 권한과 직접 연결하면 좋겠습니다.**

- **위치:** `src/content/docs/10-deployment-operations/logs-monitoring-backup.md`의 모임 웹앱 불변식 위반 대응 1번.
- **최소 인용:** “위험한 쓰기를 가장 작은 안전한 범위에서 즉시 제한합니다.”
- **관찰·근거:** 알림 절, 런북 정의, 인수인계 체크리스트에는 승인과 권한 경계가 있습니다. 다만 구체적인 대응 목록의 첫 조치는 누가 어떤 사전 권한으로 실행하는지 연결하지 않고 명령형으로 제시합니다. 같은 목록의 시험에는 별도 운영 승인을 명시해 두 조치의 권한 표현이 비대칭입니다. C06에 해당합니다.

**6. 재확인 기준**

동일 reviewer 후속 검토에서는 이번 finding ID를 유지하고, 변경된 입력과 직접 영향 범위만 다시 읽으면 됩니다. R02 successor 예외를 적용하거나 유효한 R01～R09 전체 검토를 반복할 필요는 없습니다.

1. **I01:** 원고의 비밀 복구 본문과 체크리스트, 필요하다면 관련 설정 장의 좁은 문맥을 함께 제출하십시오. 재발급 가능한 자격과 기존 암호문에 필요한 키·버전의 보존·복구·해독 시험을 구분했는지 확인합니다. 특정 제품 기능을 새로 주장한다면 해당 기능의 공식 근거도 필요합니다.
2. **I02:** NIST 적용 대상 수정 문단, 현재 출처 매핑 또는 정정 부록, 관련 감사 재판정을 제출하십시오. SP 800-61r3·SP 800-34r1·CISA의 적용 범위를 분리하고 과거 날짜·기록을 보존했는지 확인합니다.
3. **I03:** 사고 후 재개 문단과 연결된 오라클을 제출하십시오. 과거 사건 보존, 현재 데이터 정합성, 추가 위반의 관찰 기간, 인가 부정·동시성 회귀, 승인된 smoke와 재개 결정을 구분했는지 확인합니다.
4. **M01～M03:** 사전 승인된 긴급 대응 권한 연결, 그림 앞 관찰 안내, 인접 사례의 비목표 정렬을 각각 좁은 diff로 제시하십시오. Minor를 보류한다면 이유·영향·후속 담당 범위를 재판정 기록에 남기면 됩니다.
5. **입력 고정:** 변경 파일의 전후 SHA-256, 새 개별·결합 해시, 현재 기준 commit과 정확한 diff를 제공하십시오. 기존 frozen manifest와 최초 검토 기록을 덮어써 역사적 입력을 바꾸지 않아야 합니다.
6. **자동·시각 검증:** 수정 영향에 맞는 콘텐츠·참조·정적 검사와 필요한 빌드·산출물 검사를 수행한 기록을 제출하십시오. 그림 앞 문장이나 본문 배치가 바뀌면 해당 문맥을 라이트·다크·데스크톱·태블릿·모바일에서 다시 확인해야 합니다. SVG/Mermaid가 불변이면 기존 그림 crop의 의미·픽셀 증거는 범위를 밝혀 재사용할 수 있지만, 변경된 본문의 렌더 증거로 쓰면 안 됩니다.
7. **controller 마무리:** 응답 후 입력 불변성, 실제 프로필·읽기 전용 실행, 결과 완전성, 정본 저장과 finding 재판정을 확인하십시오. 준비 6개 파일의 체크포인트는 최신 staged 범위와 제공 검사 이후의 변경 여부를 다시 대조해야 합니다.

이번 응답은 **R10의 실제 원고 검토 결과와 준비 코드의 별도 검토 의견**입니다. 소유자 승인, `ready`, RC, M5 전체 완료, M6/M7, commit·push·배포 또는 공개 URL 성공을 승인하거나 실행하지 않았습니다.
