**R17-I02 — 서버 오류 응답을 받았다는 사실만으로 업무 변경 결과가 알려진 것으로 분류할 수 있습니다**

- **심각도:** Important/P1.
- **위치:** `src/content/docs/05-frontend/ui-state-and-ux.md` → 「최소 상태를 정상·실패·불명으로 나누세요」의 `error` 정의, 「상태 전이를 표로 쓰세요」의 `submitting → error` 행.
- **최소 인용:** “요청·처리·전달 중 실패가 확인됨”, “명시적 서버 오류”, “미적용 또는 계약된 부분 영향”.
- **관찰 근거:** 전이표는 명시적 서버 오류를 `error`로, 연결 종료·응답 유실을 `unknown`으로 분류합니다. 그러나 오류 응답이 명확히 도착했더라도, 그 응답이 참가 변경의 미적용·종결을 보장하지 않을 수 있습니다. 예를 들어 변경 확정 뒤 응답 작성이나 중간 전달 계층에서 오류가 발생하면, 오류 수신 사실과 업무 적용 여부는 서로 다른 사실입니다. 원고의 “서버 응답도 데이터베이스 확정…을 각각 자동 보장하지 않는다”는 설명과도 연결해야 합니다.
- **영향·적용 기준:** 독자가 `5xx 등 오류 응답 수신 → 결과가 알려진 error`, `응답 없음 → unknown`으로 구현하면 적용된 쓰기를 미적용으로 취급할 수 있습니다. 제공된 모임 brief는 해당 참가 변경의 원자적 판정과 commit 뒤 응답 유실을 구별하므로, 이 사례에서 근거 없이 부분 변경을 일반적인 허용 결과로 제시하는 것도 피해야 합니다. C04·C06의 상태·증거·재시도 경계 문제입니다.
- **최소 수정:** `error`는 API 계약과 증거로 업무 결과 또는 영향 범위가 확인된 실패에 사용한다고 명시하세요. **오류 응답을 받았어도 적용 여부가 불명확하면 `unknown`**이라는 분기를 추가하면 됩니다. 모임 전이표의 “명시적 서버 오류”는 “계약상 미적용·종결이 확인된 오류”로 좁히고, 일반 시스템의 계약된 부분 영향은 사례와 구분하세요.
- **재확인 기준:** 입력·권한·정원 거절, commit 전 rollback이 확인된 오류, commit 뒤 오류 응답, 중간 계층 오류, 결과 조회 실패를 각각 대입합니다. HTTP 결과와 업무 결과를 독립적으로 판정하고, 적용 여부가 불명확한 경로는 새 쓰기를 자동 허용하지 않아야 합니다.
- **R05와의 관계:** R05-I02가 고친 현재 상태와 특정 요청 결과의 구분은 유지됩니다. 이번 문제는 **`unknown`에 들어가는 분류 조건**에 관한 새 finding입니다.

**R17-I03 — 모임 취소가 참가 이력보다 우선한다는 상태 계약이 참가 확정·복구 전이에 반영되지 않습니다**

- **심각도:** Important/P1.
- **위치:** `src/content/docs/05-frontend/ui-state-and-ux.md` → 「상태 전이를 표로 쓰세요」의 성공·현재 참가 확인 행, 「두 사례의 상태 계약 → 모임 참가 웹앱」.
- **최소 인용:** “참가 완료와 취소 행동”, “권위 상태에서 현재 참가 확인 → confirmed”, “현재 참가 관계 확인”.
- **관찰 근거:** 제공된 `meeting-webapp-case-brief.md`는 모임 취소 시 기존 참가 행을 이력으로 보존하고, **`event.cancelled`를 우선 안내하여 `confirmed` 기록을 유효 참가로 표시하지 않는다**고 명시합니다. 자기 조회도 참가 관계뿐 아니라 모임 상태를 반환합니다. 그런데 원고의 대표 전이는 참가 관계 확인을 중심으로 `confirmed` 표시로 이어지며, 취소된 모임의 참가 이력을 별도로 표현하는 조건이 없습니다.
- **영향·적용 기준:** 참가 확정 후 주최자가 모임을 취소했거나, 응답 유실 뒤 재조회에서 `event.cancelled + registration.confirmed`를 받는 경우, 표를 그대로 구현하면 “참가 완료”가 현재 유효한 참가로 남을 수 있습니다. 이는 특정 이전 요청의 처리 여부와는 다른 **현재 업무 상태의 해석 오류**입니다. C03·C04·C06에 해당합니다.
- **최소 수정:** 참가 관계와 모임 상태를 함께 읽고, 모임이 취소됐으면 모임 취소를 우선 표시하며 참가 기록은 이력으로 구분한다고 명시하세요. 대표 전이에 이 분기 한 줄을 추가하거나 현재 참가 확인 행에 조건을 붙이면 충분합니다. 기존 자기 취소 허용 계약은 유지해야 합니다.
- **재확인 기준:** `open + confirmed`, `closed + confirmed`, `cancelled + confirmed`, `cancelled + cancelled`를 대입해 표시와 행동을 확인합니다. 특히 `closed`를 모임 취소로 취급하지 않고, `cancelled + confirmed`를 유효 참가로 표시하지 않아야 합니다.
- **R05와의 관계:** 현재 참가 관계만으로 특정 요청의 인과관계를 단정하지 않도록 한 R05 수정은 여전히 유효합니다. 이번 finding은 **모임 상태와 참가 상태를 결합하는 우선순위**에 관한 것입니다.

**R17-M01 — 지정 모임 사례의 비목표인 대기 기능이 가능한 대안처럼 등장합니다**

- **심각도:** Minor/P2.
- **위치:** `src/content/docs/05-frontend/ui-state-and-ux.md` → 「최소 상태를 정상·실패·불명으로 나누세요」의 표 다음 설명.
- **최소 인용:** “최신 상태와 대기·다른 모임 같은 선택”.
- **근거·영향:** 지정 brief는 대기 명단을 비목표로 명시합니다. 일반적인 다른 제품의 대안으로 대기 기능을 설명할 수는 있지만, 현재 문장은 같은 모임 사례가 제공하는 행동처럼 읽힙니다. C03의 사례 범위 일관성에 해당합니다.
- **최소 수정:** “최신 상태와 다른 모임 같은 선택”으로 좁히거나, 대기 기능은 이 사례 밖의 별도 제품 예시라고 구분하세요.
- **재확인 기준:** 현재 사례에서 제공하지 않는 대기 신청·알림·대기 명단을 구현된 기능이나 필수 수용 기준으로 읽지 않아야 합니다.

**R17-M02 — UI 장의 첫 `spinner`·`fixture`가 초보자에게 설명 없이 제시됩니다**

- **심각도:** Minor/P2.
- **위치:** `src/content/docs/05-frontend/ui-state-and-ux.md` → 「왜 필요한가」의 첫째·둘째 문단.
- **최소 인용:** “spinner와 공통 오류 문구”, “대표 fixture에서는”.
- **근거·영향:** spinner의 쉬운 풀이가 없고, fixture의 가상 시험 자료라는 성격은 뒤의 대시보드 절과 용어집에서 확인해야 합니다. 독립적인 핵심 장의 도입으로서는 첫 용어 설명이 늦습니다. C04·C08에 해당합니다.
- **최소 수정:** 첫 등장에 “진행 중임을 나타내는 회전 표시(spinner)”, “미리 준비한 시험 데이터·상태(fixture)” 정도로 설명하고 이후 표현은 유지하세요.
- **재확인 기준:** 이 장만 순서대로 읽어도 두 용어의 역할을 이해할 수 있고, 뒤의 `EDU-FIXTURE`가 실제 시장 자료가 아님을 분명히 구분해야 합니다.

**R17-M03 — 프로그램적 상태 메시지의 적용 조건과 포커스 이동의 차이가 본문에서 모호합니다**

- **심각도:** Minor/P2. 두 원고의 공동 finding입니다.
- **위치:** 접근성 장의 「8. 동적 상태가 보이고 읽히며 복구 가능한가요」, UI 장의 「접근 가능한 상태 피드백」.
- **최소 인용:** “필요할 때 보조 기술이 프로그램적으로 알 수 있게”, “사용자의 판단과 다음 행동을 바꾸는 결과에 집중”.
- **근거·영향:** 알림 과잉을 피하라는 설명은 적절합니다. 다만 제공된 SC 4.1.3·Understanding 발췌가 구분하는 **문맥 전환이 아닌 상태 메시지**, **포커스를 받지 않고도 역할·속성을 통해 전달할 수 있어야 하는 조건**, **결과 목록 자체와 검색 중·결과 건수 메시지의 차이**가 본문에는 드러나지 않습니다. “필요할 때”라는 재량만으로 프로그램적 전달을 생략하거나, 알림을 위해 매번 포커스를 옮기는 해석을 남깁니다. C04·C05에 해당합니다.
- **최소 수정:** 상태 메시지에 해당하는 경우와 포커스 이동을 수반하는 문맥 전환을 한두 문장으로 구분하세요. 해당 상태 메시지는 포커스를 옮기지 않아도 보조 기술이 인식할 수 있게 하고, 모든 DOM 변화에 강한 알림을 붙이라는 뜻은 아니라고 연결하면 됩니다.
- **재확인 기준:** “검색 중”, “결과 0건”, 저장 결과, 입력 오류 요약, 대화상자 열기를 구분해 설명할 수 있어야 합니다. 특정 ARIA 속성 하나를 모든 경우의 필수 해법으로 지정하지 않아야 합니다.

**R17-P-M01 — 참조 검사 수의 최신 보고와 제공된 실행 기록이 다릅니다**

- **분류·심각도:** 별도 준비 증거 Minor/P2. 원고 finding 합계에 포함하지 않습니다.
- **위치:** 이번 요청의 실행 요약, `r17-input-preparation-validation.md`, `r17-input-check.log`.
- **최소 인용:** 요청 요약의 `refs363`과 준비 기록·완료 로그의 `refs362`, “참조 검증 통과: 362개 Markdown/MDX”.
- **근거·영향:** 제공된 로그는 362를 직접 뒷받침합니다. 363이 이후 파일 추가에 따른 다른 실행이라면 양쪽 기록이 모두 성립할 수 있지만, 그 실행 연결은 현재 자료에서 확인되지 않습니다. C12의 대상·실행·증거 연결 문제입니다.
- **최소 수정:** 과거 로그를 소급 변경하지 말고, 363이 나온 별도 실행의 대상·결과를 연결하거나 현재 직접 확인 가능한 수를 362로 보고하세요.
- **재확인 기준:** 각 수가 어느 시점·입력의 실행인지 추적 가능해야 합니다. 전체 테스트 통과나 원고 판정을 바꾸는 결함으로 확대하지 않습니다.

**별도 준비 코드 검토 — C0/I0/M0**

`r17-review-inputs.mjs`와 테스트 전체를 정적으로 대조한 결과, 이번 고정 입력 범위에서 실패를 성공으로 바꾸는 구체적인 우회 경로는 발견하지 않았습니다.

- 매니페스트 자체를 하드코딩된 SHA로 먼저 고정하므로 입력과 매니페스트를 함께 다시 계산하는 변경을 그대로 수용하지 않습니다.
- 텍스트·로컬 PNG의 개별 SHA와 바이트 길이를 검사하고, 로컬 모드에서는 실제 읽은 바이트로 결합 해시를 비교합니다.
- 문맥 파일의 전체 SHA와 지정 행의 내장 발췌를 별도로 비교합니다.
- 두 렌더 provenance 매니페스트를 로컬 모드에서 검사합니다.
- PNG의 시그니처·IHDR 검사와 고정 바이트 해시는 파일 동일성의 증거이며, 시각 판독을 자동 수행한다고 주장하지 않습니다.
- 기본 모드는 `localEvidence: "not-checked"`를 반환합니다. 로컬 이미지 테스트의 조건부 skip 가능성도 존재하지만, 이번 제공 실행은 skip 0이며 별도 localEvidence 검사도 성공으로 보고됐습니다.
- 항상 `reviewComplete: false`, `releaseReady: false`를 유지합니다.

이 코드는 고정된 R17 묶음의 검사기입니다. 임의 매니페스트를 받는 범용 스키마 검증기나 실제 이미지 전달·판독 완료 검사기로 평가하지 않았습니다.
