입력 부족이나 실제 이미지 미독을 이유로 한 `BLOCKED`는 없습니다. 지정 입력을 모두 읽었고, controller의 검토 전 입력 검증 증거에 불일치가 없습니다. 다만 미해결 Important가 3건이므로 PASS 조건을 충족하지 않습니다.

원고의 중심 설명은 대체로 정확합니다. 특히 다음 부분은 유지할 가치가 있습니다.

- 빌드·아티팩트·환경 배치·DNS·HTTPS·사용자 결과·운영 인수의 증거를 분리합니다.
- CI에서 다시 빌드한 결과를 기존 로컬 아티팩트와 같은 바이트라고 가정하지 않습니다. 정적 사이트의 환경별 빌드도 다른 아티팩트로 취급합니다.
- DNS 이름 조회와 HTTPS 상대 검증, 애플리케이션 인가·데이터 정확성을 구분합니다.
- 코드 롤백이 데이터 스키마·외부 부작용까지 복구하지 않는다는 점을 설명합니다.
- 모임 W-05의 smoke·동시성·복원 요구를 실제 운영 실행 이력으로 표현하지 않습니다.

준비 검사기·테스트는 **고정된 R09 입력의 변경 탐지라는 한정된 목적에 적합합니다.** manifest 자체의 해시를 먼저 고정하고, 개별 입력의 해시·길이, local 모드의 결합 해시, 문맥 원본 해시와 발췌 행, PNG 헤더, 렌더 provenance를 확인합니다. 기본 모드에서 PNG 검사를 생략하는 경우에도 `localEvidence: not-checked`를 반환하고, `reviewComplete`와 `releaseReady`를 항상 false로 둡니다. 이 설계는 준비 검사 통과를 원고 검토 완료로 승격하지 않습니다.

제공된 테스트는 정상 입력, 텍스트·문맥의 누락과 변경, manifest 교체, 발췌 행 변경, local PNG 누락·손상과 provenance 변경을 다룹니다. 고정 manifest를 먼저 해시로 제한하는 검사기이므로, 임의의 새 manifest를 받아들이는 범용 검증기 수준의 요구를 추가하지 않았습니다.

검증 수치는 모두 **controller가 제공한 실행 증거**로 수용했습니다.

| 증거 | 수용한 결과와 한계 |
|---|---|
| 전체 정적 검사 | 253 pass / 0 fail / 0 skipped, 콘텐츠 59개, 참조 276개·학습 SVG 14개, 계획 중복·누락 0, exit 0 |
| 공백 수정 후 재고정 | 영향받은 pin을 갱신한 뒤 focused 5/5, errors 0이라는 controller 기록 |
| 빌드 | 공개 출력·설정·의존성이 불변이라는 근거로 R08 build 60 / Pagefind 60 / built 60 증거를 재사용한 기록. R09에서 새 빌드를 실행한 것으로 계산하지 않음 |
| 스테이징 | 준비 6개 경로의 index와 working bytes 일치, 현재 추적 402개에서 mismatches 없음, unstaged 없음 |
| 공개 안전 검사 | 402개 파일, finding 0, exit 0. 원고 품질·배포 성공·공개 승인 전체를 뜻하지 않음 |

따라서 **준비 6파일은 독립 로컬 체크포인트에 적합한 검토 결과**입니다. 원고와 감사에서 발견한 문제를 입력에 숨기지 않고 그대로 검토 대상으로 전달한 점도 적절합니다. 이 판단은 커밋 실행이나 원고 PASS, M5 완료, 상태 승격을 뜻하지 않습니다.

**3. 위치별 finding**

**R09-I01 — Important / P1 — 현재 DNS 용어 근거에서 RFC 8499의 대체 상태가 드러나지 않습니다.**

- **위치:** [대상 원고의 「관련 용어와 출처」](../../../../src/content/docs/10-deployment-operations/build-deploy-domain-dns.md), `research/source-map.md`의 해당 원고 DNS 근거 행.
- **최소 인용:** “DNS의 기본 개념과 용어를 정의하는 RFC 1034·8499”.
- **관찰 근거:** 2026-11-15 고정 근거 자료는 RFC 8499가 RFC 9499로 대체됐다고 명시하고, RFC 9499의 TTL·recursive resolver·authoritative server 관련 적용 범위를 제공합니다. 원고의 현재 출처 안내에는 이 상태나 후속 문서가 없습니다.
- **영향·적용 기준:** 독자가 DNS 용어의 현행 기준과 역사적 참고를 구분할 수 없습니다. 이는 단순히 오래된 날짜가 있다는 문제가 아니라, 이번에 확인한 대체 상태가 현재 교육 원고의 근거 연결에 반영되지 않은 문제입니다. C05·SOURCE와 문서 상태 추적 기준에 해당합니다.
- **최소 수정:** 현재 DNS 용어의 주된 연결을 RFC 9499로 바꾸거나 추가하고, RFC 8499는 대체된 역사적 참고라는 상태를 명시합니다. 2026-08-13 확인 이력은 보존하고, 2026-11-15 재확인 내용·적용 범위를 source-map의 새 기록 또는 정정 연결로 남깁니다.
- **재확인 기준:** 원고의 링크·설명·source-map이 RFC 9499와 대체 관계를 일치되게 가리켜야 합니다. TTL을 전 세계 동시 갱신 보장으로 확대하지 않는 기존 문장은 유지해야 합니다. 기존 인용이 모두 틀렸다는 식으로 역사를 개작할 필요는 없습니다.

**R09-I02 — Important / P1 — 배포 승인 여부와 기존 환경을 읽어 검증할 권한을 동일하게 취급합니다.**

- **위치:** [대상 원고의 「AI의 배포 보고를 검증하는 읽기 전용 지시」 뒤 설명](../../../../src/content/docs/10-deployment-operations/build-deploy-domain-dns.md).
- **최소 인용:** “실제 배포가 승인되지 않았다면 … 원격 CI·공개 URL·DNS·HTTPS는 미검증으로 남겨야 합니다.”
- **관찰 근거:** 새로운 배포·DNS 설정 변경은 외부 쓰기입니다. 반면 이미 존재하는 CI 결과, 공개 URL, DNS 응답이나 인증서의 읽기 확인은 별도의 접근 범위에서 허용될 수 있습니다. 현재 문장은 배포 승인이 없다는 이유만으로 이 읽기 검증까지 불가능하거나 미검증이어야 한다고 일반화합니다.
- **영향·적용 기준:** 독자가 변경 권한과 증거 수집 권한을 혼동하고, 허용된 읽기 검증으로 실제 확인한 결과도 보고하지 못하게 됩니다. 이 저장소에 현재 원격 배포가 없다는 사실은 유지하되, 일반적인 검토 지시에서는 두 권한을 분리해야 합니다. C04·C06 및 증거 범위 판단 기준에 해당합니다.
- **최소 수정:** 새 배포·설정 변경에는 해당 승인이 필요하다는 문장과, 기존 환경의 읽기 접근이 허용됐을 때 확인할 수 있는 증거를 분리합니다. 접근이 허용되지 않았거나 실제 확인하지 않은 항목을 미검증으로 남기도록 고칩니다. 엄격한 읽기 전용 지시에서의 “로컬 빌드”도 기존 결과를 읽는 것인지, 산출물을 생성하는 새 실행까지 허용하는지 구분하면 좋습니다.
- **재확인 기준:** ① 배포 권한은 없지만 기존 공개 환경의 읽기 검증은 허용된 경우, ② 원격 접근 자체가 허용되지 않은 경우, ③ 배포 작업만 성공하고 사용자 검증을 하지 않은 경우를 서로 다른 상태로 보고할 수 있어야 합니다. 수정이 새 네트워크 접근이나 배포의 포괄 승인으로 읽혀서도 안 됩니다.

**R09-A-I01 — Important / P1 — 시각 감사의 DNS 점선 설명이 실제 SVG·Mermaid·원고와 다릅니다.**

- **위치:** [시각 감사의 PBV-05 의미 동기화 설명](../../public-beta-visual-audit.md).
- **최소 인용:** “점선 이름 조회 `사용자→DNS→호스팅`”.
- **관찰 근거:** 실제 Mermaid는 `D -.->|이름 조회 결과| U`이고, SVG도 `data-from="D" data-to="U"`입니다. PNG-02·05·08·11·14·17과 대응 문맥 이미지에서 점선 화살촉은 모두 사용자 노드에 닿습니다. 사용자→DNS 또는 DNS→호스팅 점선은 없습니다. 원고와 alt 역시 DNS가 브라우저에 대상 정보를 알려 준다고 설명합니다.
- **영향·적용 기준:** 실제 그림은 올바르지만, 감사 기록은 존재하지 않는 연결을 “일치시켰다”고 서술합니다. 이는 후속 의미 검사나 회귀 수정에서 잘못된 topology를 정답으로 삼게 할 수 있는 검증 기록 오류입니다. C07·C12에 해당합니다.
- **최소 수정:** 실제 관계를 `도메인·DNS→사용자 브라우저: 이름 조회 결과`로 명시하고, 콘텐츠 응답 `호스팅→사용자`와 구분합니다. 해당 문장이 보존해야 할 과거 감사 기록이면 원문을 지우지 말고 정정 기록을 추가해 현재 판정에서 어느 설명을 사용해야 하는지 명확히 합니다.
- **재확인 기준:** 현재 감사 요약이 실선 4개·점선 1개와 각 시작·도착 노드를 정확히 설명해야 합니다. 감사 문장에 맞추려고 올바른 그림을 `사용자→DNS→호스팅`으로 바꾸면 안 됩니다. 감사 텍스트만 정정한다면 이 사유만으로 새 PNG 촬영을 요구하지 않습니다.

**R09-M01 — Minor / P2 — base path 예시에서 저장소 이름이 바뀝니다.**

- **위치:** [대상 원고의 「이 저장소의 GitHub Pages 사례」](../../../../src/content/docs/10-deployment-operations/build-deploy-domain-dns.md).
- **최소 인용:** `https://account-name.github.io/project-name/` 다음의 “`/handbook/logo.svg` 같은 프로젝트 기준 경로”.
- **관찰 근거:** 앞 URL의 경로 접두사는 `/project-name/`입니다. 이 예시에서 같은 사이트의 자산을 가리키려면 `/project-name/logo.svg`가 되어야 합니다. 실제 workflow도 저장소 이름을 `PUBLIC_BASE_PATH=/$REPO_NAME`으로 전달합니다.
- **영향·적용 기준:** 경로 오류로 404가 나는 이유를 설명하는 문단 안에서 다른 접두사를 제시해 초보 독자를 혼란스럽게 합니다. C04·C08에 해당합니다.
- **최소 수정:** 자산 예시를 `/project-name/logo.svg`로 맞추거나 앞 URL을 `/handbook/`으로 통일합니다.
- **재확인 기준:** URL·base 값·자산 경로 세 가지가 같은 예시를 설명해야 합니다. 실제 저장소 설정을 변경할 필요는 없습니다.

**R09-M02 — Minor / P2 — `nameserver` 전체를 authoritative nameserver로 정의합니다.**

- **위치:** [대상 원고의 「자주 보는 DNS 개념」](../../../../src/content/docs/10-deployment-operations/build-deploy-domain-dns.md).
- **최소 인용:** “**nameserver**: 도메인의 권위 있는 DNS 정보를 제공하도록 위임된 서버”.
- **관찰 근거:** 이 설명은 authoritative nameserver의 역할을 설명합니다. 제공된 RFC 근거는 resolver와 authoritative server의 역할을 구분하고, 개발 용어집도 이 정의에 `authoritative nameserver`라는 이름을 사용합니다.
- **영향·적용 기준:** 관리 화면의 권위 서버와 재귀 조회를 담당하는 DNS 서버를 구분하는 장에서 용어 범위를 좁혀 정의합니다. 다만 주변 본문은 resolver와 권위 응답을 구분하고 있어 국소 수정으로 해결할 수 있습니다. C04에 해당합니다.
- **최소 수정:** 항목명을 `권위 있는 네임서버(authoritative nameserver)`로 바꾸고, 담당 zone의 정보를 제공하는 역할임을 명확히 합니다.
- **재확인 기준:** 용어집·RFC 근거·본문의 resolver 및 권위 응답 설명과 역할이 일치해야 합니다. 모든 DNS 서버가 권위 서버라고 읽히지 않아야 합니다.

**R09-M03 — Minor / P2 — 제품 매핑 안내가 연결 대상의 최신 제공 상태를 정확히 설명하지 않습니다.**

- **위치:** [대상 원고의 「현재 호스팅 예시는 책임 판정 뒤에 읽습니다」 상자](../../../../src/content/docs/10-deployment-operations/build-deploy-domain-dns.md). 대조 입력은 `current-tool-mapping.md`의 제공 발췌입니다.
- **최소 인용:** “2026-08-13에 확인한 Vercel·Codex Sites의 빌드·런타임·호스팅 경계 … 따로 정리했습니다.”
- **관찰 근거:** 연결 대상은 2026-08-20 기준으로 Vercel 8개 URL의 재확인 실패와 현재 주장 `not-confirmed`를 명시하며, Sites는 `Sites – ChatGPT`라는 명칭과 public beta 조건을 설명합니다. 호출 문구는 이 변경을 알리지 않고 과거 기능 정리를 현재 참고편이 그대로 제공하는 것처럼 소개합니다.
- **영향·적용 기준:** 독자는 Vercel의 현재 기능을 확인한 표로 예상하고 이동할 수 있습니다. 다만 원고가 2026-08-13이라는 날짜를 명시하고 제품 채택·계정 사용·배포 성공을 주장하지 않으므로, 미확인 제품 기능을 단정한 치명 항목으로 판정하지 않았습니다. C05·C08의 국소 연결 설명 문제입니다.
- **최소 수정:** 제품 예시의 마지막 확인일, 재확인 실패, 명칭과 적용 한계를 해당 참고편에서 확인하도록 안내합니다. 과거 `Codex Sites` 명칭을 유지하려면 당시 명칭이라는 점을 표시합니다. 날짜만 새 날짜로 바꾸거나 미확인 상태를 confirmed로 바꾸지 않습니다.
- **재확인 기준:** 호출 문구가 Vercel의 확인 실패와 Sites의 날짜·조건부 범위를 숨기지 않아야 합니다. 새로운 제품 조사·계정 접근·채택·배포는 이 finding 해소의 필수 범위가 아닙니다.
