**2. 판정과 건수**

| 구분 | 판정 | Critical | Important | Minor |
|---|---|---:|---:|---:|
| R04 원고·그림·제공 문맥 검토 | **NEEDS CHANGES** | 0 | 2 | 8 |
| 별도 준비 코드 검토 | **PASS — 제공 코드의 정적 검토 범위** | 0 | 0 | 0 |

원고는 API 계약과 실행 증거, 인증과 객체·행동 인가, 서명과 암호화, 사전 조회와 확정, `commit`과 응답 전달을 대체로 정확하게 구분합니다. 특히 응답 유실을 곧바로 저장 실패로 간주하지 않게 하고, 권한 있는 재조회와 처리 기록을 요구하는 설명은 일관됩니다.

수정이 필요한 중요한 이유는 두 가지입니다.

- `rollback`의 취소 범위를 명확히 한정하지 않아, 다른 트랜잭션이 정상 확정한 변경까지 “이전 상태”로 돌아가야 한다는 잘못된 검증 오라클로 읽힐 수 있습니다.
- 주최자의 정원 변경을 본문에서 다루면서도, 참가 요청과 정원 축소가 같은 불변식을 지켜야 한다는 연결이 AI 계약·체크리스트·테스트에 빠져 있습니다. 제시된 테스트를 모두 통과해도 허가된 주최자의 변경으로 `confirmed > capacity`가 될 수 있습니다.

필수 입력의 누락이나 미독으로 인한 `BLOCKED` 사유는 발견하지 않았습니다. 텍스트·그림·지정 문맥의 검토는 완료했지만, **미해결 Important 0건 조건은 충족하지 않았습니다.** 응답 후 해시 불변성, controller의 정본 저장·재판정과 이후 상태 전이는 아직 완료 사실이 아닙니다.

준비 코드는 좁은 검토 범위에서 체크포인트 후보로 적합합니다. 다만 제공된 `CONTROLLER INPUT VALIDATION`은 입력 검증 실행 결과이며, 준비 테스트 파일의 실행 결과나 최종 staged 범위까지 입증하지는 않습니다. 따라서 **코드 검토상 체크포인트 적합성은 긍정적이고, 실제 체크포인트의 모든 실행 게이트 충족 여부는 미확인**입니다. 이는 commit 실행이나 상태 승격에 대한 승인이 아닙니다.

**3. 위치별 finding**

아래 ID는 이번 R04에서 새로 부여한 안정 ID입니다. 기존 PBVA finding을 임의로 재작성하거나 과거 PASS를 소급 취소하지 않습니다.

**R04-I01 — 트랜잭션 rollback의 취소 범위와 검증 오라클이 지나치게 넓습니다.**

- **심각도:** Important / P1.
- **위치:** `src/content/docs/04-backend-data/api-database-auth.md` → 「6. `registrations`와 정원 판단을 트랜잭션으로 확정합니다」, 「성공과 실패를 무엇으로 구분할까」의 저장 실패 행.
- **최소 인용:** “트랜잭션 시작 전의 일관된 상태로 되돌리는 동작”, “이벤트·참가 관계가 모두 이전 상태인지”.
- **관찰·근거:** 제공된 PG-TX 발췌는 rollback이 “다른 트랜잭션의 확정 결과를 되돌리는 일”이 아니라고 명시합니다. 본문은 동시 요청을 핵심 사례로 삼지만, 위 정의와 표에서는 **실패한 트랜잭션 자신의 미확정 변경**이라는 범위가 빠져 있습니다.
- **영향:** A의 참가가 정상 확정되고 B가 실패한 시험에서 전체 이벤트·참가 데이터를 시작 전 상태와 동일해야 한다고 검사하면, A의 정당한 확정을 오류로 판단할 수 있습니다. 구현 검토에서도 정상 변경을 되돌리는 잘못된 복구 방향으로 이어질 수 있습니다.
- **최소 수정:** 정의를 “해당 트랜잭션이 만든 미확정 변경을 취소하며, 다른 트랜잭션의 정상 확정 결과는 유지한다”로 한정합니다. 표의 오라클도 “실패한 요청에 귀속되는 부분 변경 0건, 다른 정상 확정 변경 유지, 전체 불변식 유지”로 바꿉니다.
- **재확인 기준:** A가 참가를 확정하고 B가 저장 도중 실패하는 반례에서 A의 참가가 남아 있어도 정상 rollback으로 판정할 수 있어야 합니다.
- **적용 기준:** C02·C04·C05, 실패·복구 오라클의 정확성.

**R04-I02 — 주최자의 정원 변경과 참가 요청이 공유하는 일관성 책임이 검증 계약에서 빠져 있습니다.**

- **심각도:** Important / P1.
- **위치:** 대상 원고 → 「4. 이벤트·참가 관계를 조회하고 인가합니다」, 「6. … 트랜잭션으로 확정합니다」, 「AI와 작업할 때 사용할 계약」, 「확인 체크리스트」.
- **최소 인용:** “이 모임의 `capacity`나 `event.status`를 바꿀 수 있다”, “마지막 한 자리 동시 요청: 성공 1건, 안전한 실패 1건”.
- **관찰·근거:** 본문은 주최자의 `capacity` 변경을 인가 사례로 포함하고 `confirmed <= capacity`를 불변식으로 요구합니다. 그러나 구현·검증 요청은 주로 참가 A/B의 경쟁을 다룹니다. 제공된 캡스톤 W-04는 정원 축소가 현재 확정 수 이상이어야 하며, 축소 `PATCH`와 참가 `POST`의 경쟁까지 같은 일관성 경계에서 검증하도록 명시합니다.
- **영향:** 참가 경로의 잠금·격리·고유성이 모두 맞아도 주최자 경로가 정원을 독립적으로 줄이면 불변식이 깨집니다. 예를 들어 정원 10·확정 9에서 주최자가 9로 줄이는 동안 새 참가가 확정되면, 두 경로의 사전 검사만으로 최종 정원 9·확정 10이 될 수 있습니다.
- **최소 수정:** 주최자 API 전체를 추가 설명할 필요는 없습니다. “같은 불변식에 영향을 주는 주최자의 마감·정원 변경도 참가 처리와 조정돼야 한다”는 문단과, 정원 축소의 하한 규칙 및 경쟁 테스트 한 항목을 AI 계약·체크리스트에 추가하면 됩니다. 상세 설명은 제공된 캡스톤 W-04로 연결할 수 있습니다.
- **재확인 기준:** `capacity=10`, 확정 9에서 정원을 9로 줄이는 요청과 새 참가 요청을 경쟁시켰을 때, 캡스톤의 두 허용 최종 상태인 `(9,9)` 또는 `(10,10)`과 부분 저장 0건을 검증하도록 설명돼야 합니다.
- **적용 기준:** C02·C03·C04, 인접 사례 계약과 데이터 불변식의 연결.

- **영향:** 소스에는 자기 호출이 있지만 픽셀에서는 끝이 막힌 꺾은 선처럼 보입니다. 기존 “화살촉 소실 0”이라는 관찰을 이번 이미지 전체에 그대로 이어 쓸 수 없습니다.
- **최소 수정:** 자기 호출의 돌아오는 구간과 5번 레이블 배경이 겹치지 않도록 간격 또는 경로를 좁게 조정합니다.
- **재확인 기준:** 상세 PNG의 세 뷰포트×두 테마에서 자기 호출의 진행 방향과 돌아오는 화살촉을 직접 판독할 수 있어야 합니다.
- **적용 기준:** C07.

**R04-M02 — 상세 그림의 “제약으로 1건만 확정”이 본문의 동시성 설명보다 단정적입니다.**

- **심각도:** Minor / P2.
- **위치:** 상세 SVG 4번 보조 레이블과 해당 PNG 6개.
- **최소 인용:** “제약으로 1건만 확정”.
- **관찰·근거:** 본문과 PG-CONSTRAINT 발췌는 정원 규칙에 적합한 격리·잠금·조건부 변경·제약 조합을 검증해야 한다고 설명합니다. Mermaid의 대응 문구도 특정 수단을 고정하지 않는 “트랜잭션 확정 경계에서 1건만 확정”입니다.
- **영향:** 그림만 빠르게 읽으면 활성 참가 고유성 같은 저장소 제약 하나가 서로 다른 두 참가자의 정원 경쟁까지 해결하는 것으로 오해할 수 있습니다. 본문이 이를 보완하므로 국소 표현 문제로 분류했습니다.
- **최소 수정:** “동시성 전략으로 1건만 확정” 또는 특정 수단을 지우고 “1건만 확정”으로 바꿉니다.
- **재확인 기준:** SVG·MMD·alt·본문 어디에서도 단순 제약의 존재를 정원 동시성 보장으로 등치하지 않아야 합니다.
- **적용 기준:** C04·C05·C07.

**R04-M03 — 상세 그림의 복구 응답에서 A 자신의 확정 상태가 생략됩니다.**

- **심각도:** Minor / P2.
- **위치:** 상세 SVG 10번 메시지, 대응 Mermaid 10번 메시지.
- **최소 인용:** SVG의 “`confirmed≤capacity` / 활성 중복·부분 저장 0”, MMD의 “`A confirmed·count≤capacity·활성 중복 0·부분 저장 0`”.
- **관찰·근거:** Mermaid와 본문은 A의 현재 참가 상태와 전체 불변식을 함께 확인합니다. SVG는 9번에서 참가 조회를 요청하고 11번에서 “이미 확정”을 반환하지만, 중간 반환 레이블에는 전체 불변식만 표시합니다.
- **영향:** 전체 확정 수가 정원 이하라는 사실만으로 A 자신의 참가가 확정됐다고 판단할 수는 없습니다. 앞뒤 문맥에서 A의 상태 조회를 설명하므로 핵심 개념 오류보다는 복구 근거를 덜 명확하게 전달하는 문제입니다.
- **최소 수정:** 10번 반환에 “A의 참가 confirmed”와 “확정 수≤정원”을 구분해 표시합니다. 상태값과 개수의 표기도 구분하면 더 명확합니다.
- **재확인 기준:** 그림만 읽어도 “내 참가 상태 확인”과 “전체 데이터 불변식 확인”이 서로 다른 검증임을 알 수 있어야 합니다. 수정 후 모바일 판독성도 확인합니다.
- **적용 기준:** C04·C07.

**R04-M04 — `401` 설명에 필수 인증 challenge 헤더 조건이 없습니다.**

- **심각도:** Minor / P2.
- **위치:** 대상 원고 → 「3. 인증 상태로 요청 주체를 확인합니다」 및 인증 실패 응답 표.
- **최소 인용:** “HTTP API에서는 `401 Unauthorized`를 사용할 수 있지만”.
- **관찰·근거:** 제공된 RFC 9110 발췌는 `401` 응답에 적용 가능한 challenge를 담은 `WWW-Authenticate` 헤더를 보내야 한다고 명시합니다. 본문은 `401`의 뜻과 오류 본문·재인증 계약을 설명하지만 이 헤더 조건은 언급하지 않습니다.
- **영향:** 독자가 API 계약을 검토할 때 상태 코드와 오류 본문만 맞으면 충분하다고 판단할 수 있습니다. 구체적인 잘못된 wire 예시를 제시한 것은 아니므로 Minor로 분류합니다.
- **최소 수정:** `401`을 선택할 때는 인증 방식에 맞는 `WWW-Authenticate` challenge도 계약·응답에서 확인해야 한다는 문장 하나를 추가합니다.
- **재확인 기준:** 인증 실패 계약 확인 항목이 상태 코드뿐 아니라 해당 필수 헤더도 포함해야 합니다.
- **적용 기준:** C04·C05.

**R04-M05 — 인접 스키마 예시의 사용자 참조 필드명이 반복 사례의 기준 이름과 연결되지 않습니다.**

- **심각도:** Minor / P2, 인접 문맥 finding.
- **위치:** `src/content/docs/04-backend-data/data-model-schema-migration.md` → 「모임 참가 관계를 모델링하기」의 SQL. 대상 원고·사례 브리프·캡스톤과의 연결.
- **최소 인용:** SQL의 `host_user_id`, `participant_user_id`; 다른 제공 문맥의 `host_id`, `participant_id`.
- **관찰·근거:** SQL이 교육용 구조 예시라는 한계는 명시돼 있습니다. 그러나 같은 모임 사례의 동일한 관계를 다른 이름으로 표기하면서 이름 대응을 설명하지 않습니다.
- **영향:** 초보자가 인가 규칙의 `events.host_id`를 SQL에서 찾거나, 활성 고유성의 `(event_id, participant_id)`를 실제 열과 연결할 때 불필요한 혼동이 생깁니다.
- **최소 수정:** 사례 기준 이름을 사용하거나, SQL 앞에 두 이름의 대응을 한 문장으로 명시합니다. 이름 변경을 실제 DB 마이그레이션 지시로 확대하지 않습니다.
- **재확인 기준:** 인가·관계·고유성 설명에서 사용하는 필드가 인접 SQL의 어느 열인지 추측 없이 연결돼야 합니다.
- **적용 기준:** C03·C04·C08.

**R04-M06 — 현재 원고가 참조하는 조사 브리프에 분할 이전 그림 계약이 남아 있습니다.**

- **심각도:** Minor / P2, 지원 문서 finding.
- **위치:** `research/meeting-api-database-auth-research-brief.md` → 「7단계 다이어그램 계약」.
- **최소 인용:** “제목은 Mermaid와 SVG 모두 … 고정합니다”, “실패 분기는 … 포함합니다”.
- **관찰·근거:** 현재 자산은 정상 책임 개요와 동시성·응답 유실 상세로 분할됐고 제목도 달라졌습니다. Task20 감사는 그 변경을 추적하지만, 브리프의 해당 절은 분할 전 계약이 현재도 유효한 지시처럼 남아 있습니다. 대상 원고는 이 브리프를 상세 판단 근거로 계속 참조합니다.
- **영향:** 후속 작성자가 브리프를 정본으로 읽으면 이미 채택한 두 그림을 다시 합치거나, 개요에 실패 분기를 되넣는 변경을 할 수 있습니다.
- **최소 수정:** 기존 기록을 소급 개작하지 말고, 해당 절이 Task20 분할 이전 계약임을 표시하고 현재 두 자산·채택 기록을 연결합니다.
- **재확인 기준:** 현재 유효한 그림 계약과 과거 계약이 분명히 구분되고, 과거 결정의 내용은 보존돼야 합니다.
- **적용 기준:** C07·C08·C12.

**R04-M07 — AI 테스트 계약의 비밀 사용 금지가 테스트 전용 자격 증명까지 금지하는 것으로 읽힙니다.**

- **심각도:** Minor / P2.
- **위치:** 대상 원고 → 「AI와 작업할 때 사용할 계약」의 실행 범위.
- **최소 인용:** “실제 토큰·세션 값·연결 문자열·개인정보를 사용하거나 출력하지 않음”.
- **관찰·근거:** 같은 계약은 인증된 정상 참가·취소와 인증·인가 부정 테스트를 요구합니다. 인증을 실제로 검증하는 격리 테스트에는 테스트 계정의 유효한 자격 증명이나 테스트 DB 접속 설정이 필요할 수 있지만, 문구는 사용과 출력을 함께 전면 금지합니다.
- **영향:** AI가 인증 검증을 우회한 대역만으로 정상 인증 시험을 대체하거나, 실행 가능한 테스트 계약을 구성하지 못할 수 있습니다.
- **최소 수정:** 운영·개인용 자격 증명의 사용 금지와, 승인된 격리 환경의 테스트 전용 자격 증명 사용을 구분합니다. 테스트 전용 값도 출력·로그·보고서에는 노출하지 않는다는 제한은 유지합니다.
- **재확인 기준:** 실제 인증 경계를 시험할 수 있으면서 운영 비밀·개인정보의 사용과 모든 비밀 출력은 금지하는 계약이어야 합니다.
- **적용 기준:** C02·C06.

**R04-M08 — 보안 인접 문맥이 비목표인 알림 서비스를 기본 모임 구성처럼 다룹니다.**

- **심각도:** Minor / P2, 인접 문맥 finding.
- **위치:** `src/content/docs/08-quality/performance-security.md` 제공 발췌 187–193행.
- **최소 인용:** “외부 알림 서비스 경계를 그립니다”, “취약한 알림 의존성”, “알림 서비스 자격”.
- **관찰·근거:** `meeting-webapp-case-brief.md`는 알림을 비목표로 명시합니다. 보안 장의 제공 문맥은 이를 후속 확장이나 별도 가정이라고 표시하지 않습니다.
- **영향:** API 장에서 안전한 상세 설계를 위해 보안 장으로 이동한 독자가 알림 서비스와 그 자격 관리를 첫 모임 사례의 필수 구성으로 받아들일 수 있습니다. 대상 API 장 자체가 알림 기능을 요구하는 것은 아닙니다.

|---|---|
| manifest 고정 | JSON을 신뢰하기 전에 파일 전체를 하드코딩된 `r04ManifestSha`와 비교합니다. 입력과 manifest의 선언 해시를 함께 바꿔도 이 고정값에서 거절됩니다. |
