## 2. 판정과 건수

**원고 판정: `NEEDS CHANGES` — Critical 0건 / Important 4건 / Minor 2건.**

핵심 문제는 다음 네 가지입니다.

1. 요구와 검증을 연결하는 중심 추적 표가 데스크톱·태블릿에서 한 글자씩 세로로 끊어져 학습 기능을 제대로 수행하지 못합니다.
2. 개별 행의 `blocked`와 데이터셋 갱신 후보의 `blocked`가 일부 설명·오라클에서 섞여, 고정된 6행 fixture를 어떤 후보 상태로 게시할지 확정할 수 없습니다.
3. D-05 오라클이 차단·검토 대기 후보에 `stale` 사유를 요구하면서, 본문의 갱신 예정 시점에 따른 독립적인 신선도 판정과 충돌합니다.
4. “타입·허용값·단위 조합을 검사한다”는 요구에 비해 행 계약에 타입·허용 조합·거래량 단위가 충분히 고정돼 있지 않습니다.

다음 사항은 확인했습니다.

- 대상 CSV와 브리프는 같은 14필드·6행입니다.
- `IDX-X`, `STK-A`, `STK-B`, `MARKET-X`, `EDU-FIXTURE`, `v1`, `tf-v1`의 가상 경계가 유지됩니다.
- 복합 선택 키 `(instrument_id, instrument_type, market)`와 거래일을 결합하는 설명이 여러 절에서 일관되게 사용됩니다.
- 체크섬을 의미·정확성·권리의 증거로 확대하지 않습니다.
- 정적 전달과 API 전환 조건, 로컬 커밋과 push·CI·배포·공개 확인, 복원과 사용자 흐름 재검증을 구분합니다.
- 입력 완독은 충족했습니다. 미해결 Critical·Important 0건 조건은 **충족하지 못했습니다**.

**준비 코드 판정은 원고와 별도입니다.**

| 검토 단위 | 판정·건수 | 의미 |
|---|---|---|
| `r13-review-inputs.mjs`와 해당 테스트 | 검토 범위 내 Critical 0 / Important 0 / Minor 0 | 고정 manifest 교체 거부, 텍스트·문맥 변조 검출, 로컬 이미지·출처 파일 검사, 완료 상태 비승격을 확인했습니다. |

| 준비 작업의 로컬 체크포인트 적합성 | **제공된 증거 범위에서 적합** | 원고 결함과 분리된 준비 작업으로 보존할 수 있습니다. 원고 PASS나 결과 전달 감사 완료를 뜻하지 않습니다. 실제 커밋 여부는 확인하지 않았습니다. |

준비 검증에 관해서는 신규 집중 검사 5/5, 전체 정적 검사 294/294, 실패·건너뜀 0, 콘텐츠 59개, SVG 14개, 계획 100점 기록을 읽었습니다. 전체 정적 로그의 참조 수는 321개이고, 요청에서 보고서 추가 뒤 최종 참조 수를 322개로 구분해 제공했습니다. 이를 같은 실행의 동일 출력으로 합치지 않습니다.

빌드 60개·Pagefind 60개는 **변경 없는 공개 출력에 대한 R12 closeout 증거 재사용**으로 취급합니다. 신규 빌드로 계산하지 않습니다. Staged 6개, 검사 대상 475개, 공개 안전 finding 0개, index와 작업 파일 475개 일치, diff check 0이라는 제공 기록 역시 준비 후보의 근거이며 원고의 의미·판독성 검증을 대신하지 않습니다.

## 3. 위치별 finding

아래에서 `대상 원고`는 `src/content/docs/12-case-studies/analytics-dashboard-case-study.md`를 뜻합니다. 행 번호를 임의로 만들지 않고 절·표·항목으로 위치를 지정합니다.

**R13-I01 — Important/P1: 중심 추적 표가 데스크톱·태블릿에서 문장을 읽기 어려운 형태로 렌더링됩니다.**

- **위치·최소 인용:** 대상 원고 「D-01~D-05 요구에서 복구까지 추적합니다」의 10열 표, 특히 `사용자 행동` 열. 관련 CSS는 `src/styles/custom.css`의 `@media (max-width: 50rem)` 안에만 있는 `min-width: 8rem`입니다.
- **관찰 근거:** PNG-37·41·43·45에서 열 제목 “사용자 행동”과 D-01의 “사용자가 첫 화면과 출처 패널에서…”가 한 글자씩 세로로 이어집니다. PNG-38·42·44·46에서는 오라클·복구 등의 문장도 매우 좁은 폭에서 여러 조각으로 나뉘고 첫 행 아래에 큰 빈 공간이 남습니다. Controller 측정값인 사용자 행동 열 약 48.8px, 첫 행 약 780.5px는 이 시각 관측과 부합합니다. 이 숫자는 제가 다시 측정한 값은 아닙니다.
- **영향·적용 기준:** 캡스톤의 핵심인 한 요구의 행동→검증→복구 관계를 따라가기 어렵습니다. 1440px와 1024px 양 테마에서 반복되므로 국소 장식 문제가 아니라 C01·C02·C07·C08의 학습 흐름 문제입니다. HTTP 200, 전역 overflow 0, 캡처 exit 0으로 상쇄되지 않습니다.
- **최소 수정:** D-01~D-05와 각 요구의 아홉 추적 항목을 보존하면서, 요구별 짧은 소절·세로 표로 나누거나 해당 표의 모든 대상 폭에서 문장 판독이 가능한 열 폭과 내부 스크롤을 확보하세요. 글자를 더 작게 만드는 방식은 해결 기준에 맞지 않습니다. 전역 표 스타일을 바꾼다면 다른 소비 문서의 영향을 함께 확인해야 합니다.
- **재확인:** 1440·1024·390px 양 테마에서 D-01~D-05 전 항목을 실제 크기로 읽고, 한 글자 세로 분해·잘림·겹침·불필요한 페이지 전체 가로 스크롤이 없는지 확인합니다. 내부 스크롤을 유지하면 중간 열과 마지막 행, 키보드 진입·이동·탈출 및 행 식별 가능성까지 확인해야 합니다.

**R13-I02 — Important/P1: 행의 표시 상태와 데이터셋 후보의 게시 상태 사이에 결정 규칙이 빠져 있습니다.**

- **위치·최소 인용:** 대상 원고 「값 상태와 행동」의 “`review_required`… 게시하지 않는 후보 상태”, 「품질 게이트」의 “`valid`·`warning`·`blocked`·`review_required`… 기록”, 테스트 표의 “차단… 마지막 정상 버전·지연 이유 표시”, 「전달·배포 메타데이터」. 같은 문제는 `research/stock-dashboard-case-brief.md`의 행 계약·검토 대기·전달 규칙에도 걸칩니다.
- **관찰 근거:** 고정 CSV는 `valid` 4행, `warning` 1행, `blocked` 1행을 포함합니다. 화면 설명은 이 묶음에서 STK-B의 경고 값과 차단 사유를 보여 주도록 요구합니다. 반면 후보 게시 규칙은 `blocked` 후보 전체를 게시하지 않도록 요구합니다. 행별 `value_status`를 어떤 규칙으로 데이터셋의 `refresh_candidate_status`에 반영하는지, 의도적으로 차단된 행을 포함한 기본 fixture 묶음 자체는 어떤 상태로 승인하는지 명시돼 있지 않습니다.
- **영향·적용 기준:** 구현자가 “차단 행 하나라도 있으면 전체 후보 차단”으로 읽으면 기본 fixture의 화면 시나리오를 게시할 수 없고, “차단 행만 빼면 후보 승인”으로 읽으면 데이터셋 전체를 막아야 할 실패도 통과시킬 수 있습니다. 또한 차단 행을 표시 모델에서 완전히 제거하면 표와 요약에 결측·차단 이유가 사라집니다. C02·C03·C04의 핵심 데이터·게시 계약 문제입니다.
- **최소 수정:** 행 상태, 데이터셋 후보 품질 판정, 공개 버전 선택을 별도로 정의하세요. 기본 6행 묶음의 후보 판정과 그 이유를 명시하고, 행별 차단 사유는 표·대체 텍스트에 남기되 정상 수치·차트 점·계산에서 제외한다는 규칙을 고정해야 합니다. 데이터셋 전체를 차단하는 조건과 허용된 부분 결측을 구분하고, `final_value_status`가 어느 대상의 최종 판정인지도 연결하세요. 새 필드명이나 일반화된 정책 엔진을 반드시 추가할 필요는 없습니다.
- **재확인:** 기본 6행을 보존한 정상 시나리오와 데이터셋 전체가 차단되는 갱신 시나리오를 분리해 기대 결과를 대조합니다. 기본 묶음에서는 단위별 정상 수치 4개·경고 수치 1개와 차단 행의 사유가 계약대로 전달돼야 하며, 전체 차단 후보에서는 현재 공개 데이터 버전이 바뀌지 않아야 합니다. 두 경우를 같은 오라클로 판정하지 않아야 합니다.

**R13-I03 — Important/P1: D-05의 실패 오라클이 차단 상태와 `stale`을 결합합니다.**

- **위치·최소 인용:** 대상 원고 D-05 추적 표의 테스트 오라클: “차단·검토 대기·권리 불명 후보에서 공개 버전 digest는 불변이고 상태·지연·`stale` 이유가 보이며”.
- **관찰 근거:** 「신선도는 값 품질과 다른 차원입니다」는 품질과 갱신 적시성을 분리하고, 「갱신과 게시 규칙」은 “갱신 기대를 넘기면 `stale`”이라고 설명합니다. 갱신 예정 시점 전에 새 후보가 차단되더라도 현재 공개 버전은 아직 `current`일 수 있습니다. 기대 시점을 판단할 정보가 없으면 `unknown`일 수도 있습니다.
- **영향·적용 기준:** 추적 표를 그대로 테스트로 옮기면 차단 후보 발생만으로 현재 데이터셋을 `stale`로 만들거나, 올바른 `current` 상태를 실패 처리할 수 있습니다. 이는 이 장이 강조하는 품질·신선도 독립성을 오라클에서 깨뜨립니다. C02·C04에 해당합니다.
- **최소 수정:** 후보 차단 사유와 현재 공개 데이터의 신선도 판정을 각각 요구하도록 오라클을 바꾸세요. `stale` 사유는 기준 시점이 기대 갱신 조건을 넘긴 경우에 요구하고, 예정 전에는 `current`, 판단 근거가 부족하면 `unknown`과 그 사유를 유지하도록 명시하면 됩니다.
- **재확인:** 동일한 차단 후보를 두고 기준 시점이 예정 전·예정 후·판정 정보 부족인 세 시나리오를 비교합니다. 공개 데이터 버전은 모두 유지하면서 신선도는 각각 계약대로 달라져야 합니다. `warning/current`, `warning/stale`, `valid/stale` 조합도 서로 독립적으로 설명할 수 있어야 합니다.

**R13-I04 — Important/P1: 행 계약이 요구하는 타입·허용 조합·거래량 단위가 검사 기준으로 충분히 정의되지 않았습니다.**

- **위치·최소 인용:** 대상 원고 「fixture 행 계약」, 「품질 게이트」의 “헤더·타입·허용값을 확인”, 「계약·데이터 검사」의 “`unit`, `price_basis`, `value_status`, `missing_reason`의 허용 조합을 검사”. 브리프의 「행 계약」도 동일한 정의 수준입니다.
- **관찰 근거:** 필드별 의미와 일부 예외는 설명하지만, 숫자 필드의 계약상 타입·허용 범위, `volume`의 단위, `value_type`의 현재 허용 범위, 빈 값과 상태·사유의 허용 조합을 한정한 규칙은 없습니다. 특히 주식의 `unit: KRW`는 가격 단위이고 `volume: 1000000`의 단위까지 정의하지 않습니다. 선택 키와 거래일로 중복을 판정하는 규칙은 현재 `value_type: close` 및 가격 기준이 고정된 범위에서 이해할 수 있지만 그 범위도 검사 규칙으로 명시돼 있지 않습니다.
- **영향·적용 기준:** 기본 6행의 문자열 일치는 검사할 수 있어도, “타입이나 단위 조합이 잘못된 입력을 거절했다”는 독립 판정을 만들 때 구현자가 계약을 보충해야 합니다. 가상 데이터여도 내부 단위와 상태 조합은 확정돼야 합니다. C02·C03·C04의 데이터 계약·검증 기준 문제입니다.
- **최소 수정:** CSV 14필드와 6행은 유지하고, 현재 fixture 범위에 한정한 짧은 계약 표를 추가하세요. 타입·null 허용, 실제로 사용하는 열거값, `value_type: close`의 고정 범위, 가상 거래량의 단위, 주식·지수의 단위/가격 기준 조합, 값·상태·사유 조합을 명시하면 됩니다. 실제 시장 규칙을 조사하거나 새로운 일반 스키마를 설계할 필요는 없습니다. 값 0·잘못된 타입·키 충돌 등의 추가 시험 입력은 기본 6행과 분리된 파생 시험 fixture로 표시하세요.
- **재확인:** 기본 6행이 정의된 규칙을 만족하고, 잘못된 타입·단위 조합·중복 키·사유 없는 결측이 각각 어떤 규칙으로 거절되는지 독립적으로 설명할 수 있어야 합니다. 값 0을 빈 값으로 바꾸지 않고, 비적용 거래량과 수집 누락을 구분해야 합니다.

**R13-M01 — Minor/P2: `missing_reason`의 설명이 실제 경고 행에서 사용하는 의미보다 좁습니다.**

- **위치·최소 인용:** 대상 원고와 브리프의 “`value_status`, `missing_reason`: … 빈 값의 이유를 분리합니다.” CSV의 STK-B 첫 행은 값 `20000`이 존재하면서 `missing_reason: late_source`입니다.
- **근거·영향:** 현재 fixture에서는 이 필드가 결측 사유뿐 아니라 경고 사유도 전달합니다. “빈 값의 이유”로만 설명하면 값이 있을 때 사유를 버리거나 잘못된 조합으로 판단하기 쉽습니다. C04·C08에 해당합니다.
- **최소 수정:** 헤더를 바꾸지 말고 이 교육용 계약에서 `missing_reason`이 경고·차단 사유까지 담는다는 제한적 용례를 명시하세요. `late_source`가 현재 공개 데이터셋의 `stale`과 같은 뜻은 아니라는 설명도 연결하면 됩니다.
- **재확인:** 값이 있는 `warning/late_source`와 빈 값인 `blocked/source_missing`이 모두 계약에 맞고, 표·차트 대체 정보에서 사유가 유지되는지 확인합니다.

**R13-M02 — Minor/P2: 네 직접 개념 출처가 공개 원고에서는 이름만 제시돼 독자가 바로 추적하기 어렵습니다.**

- **재확인:** 네 링크가 정확한 문서·버전을 가리키며, 전체 PROV/DCAT/SLSA 적합성이나 실제 재현 가능한 빌드 달성으로 설명이 확대되지 않았는지 확인합니다.

**R13-P-M01 — 준비 자료 Minor/P2: 나머지 표 이미지 8개의 관측 파일 연결이 pilot 파일을 가리킵니다.**

- **최소 수정:** 최초 고정 요청을 소급 덮어쓰지 말고, 후속 정정 기록에서 PNG-41~48의 올바른 관측 경로를 명시하세요. 현재 포인터를 수정해 새 입력으로 삼는 경우에는 전후 해시와 변경 이유를 남겨야 합니다.
- **재확인:** 8개 ID가 remaining 관측 파일의 해당 폭·테마·좌우 캡처와 연결되는지 확인합니다. 준비 검사 코드의 바이트 불변 검사가 올바른 출처 연결 자체까지 검증한다고 설명해서는 안 됩니다.

- **보존·전달:** 지속 세션 설정은 제공된 preflight에 근거합니다. 세션 저장·재개 성공과 정본 저장·별도 커밋·응답 후 전달 감사까지 제가 실행하거나 확인한 것은 아닙니다.

## 6. 재확인 기준

후속 작업은 **이번 최초 결과를 그대로 보존한 뒤**, controller의 finding 재판정과 최소 수정, 같은 reviewer의 영향 범위 재검토로 연결해야 합니다. 정상 결과를 원고 수정 전에 별도 커밋한다는 계약을 유지하되, 이 응답 자체를 저장·커밋 완료로 기록해서는 안 됩니다.

재검토 입력에는 다음이 필요합니다.

1. **Finding별 재판정:** R13-I01~I04, R13-M01~M02, 준비 자료의 R13-P-M01 각각에 수용·부분 수용·기각과 직접 근거를 남깁니다. 서로 다른 범주의 finding을 합쳐 일부를 누락하지 않아야 합니다.
2. **새 고정 입력:** 수정 원고·브리프·필요한 CSS·출처 연결·준비 정정 기록의 전체 변경 부분과 주변 문맥, 전후 개별 SHA-256 및 새 결합 해시를 제공합니다. 변경 없는 SVG·MMD·다른 소비 문맥은 불변 근거와 함께 유지할 수 있습니다.
3. **행·후보·공개 상태 오라클:** 기본 6행을 보존하면서 행별 표시와 데이터셋 후보 승인, 현재 공개 버전 선택을 각각 판정할 수 있어야 합니다. 차단 행의 사유가 사라지지 않고 전체 차단 후보가 공개 버전을 바꾸지 않는지 확인합니다.
4. **신선도 오라클:** 기준 시점을 고정해 예정 전·예정 후·판정 불명과 품질 상태의 조합을 대조합니다. 차단 발생만으로 `stale`을 만들지 않아야 합니다.
5. **행 계약 검증:** 14필드·6행·복합 선택 키를 유지하고 타입·단위·빈 값·상태·사유의 허용 조합을 확인합니다. 추가 실패 입력은 기본 fixture와 구분해 출처와 기대 결과를 제시합니다.
6. **현재 시각·조작 증거:** 표를 수정한 아티팩트로 1440·1024·390px 양 테마를 다시 관측합니다. 우선 대표 상태를 읽고 문제가 해결됐는지 확인한 뒤 나머지 상태로 확장합니다. 전체 추적 항목을 읽을 수 있는 증거와 필요한 키보드·초점·스크롤 관측을 포함합니다.
7. **자동 검증과 빌드:** 실제 수정 범위에 맞는 검사와 프로젝트 필수 게이트의 명령·환경·종료 코드·통과·실패·건너뜀 수를 제공합니다. 공개 원고나 CSS가 바뀌면 기존 R12 빌드를 수정 후 출력의 증거로 사용할 수 없으므로 해당 변경을 포함한 빌드와 렌더 근거가 필요합니다.
8. **증거 보존:** 과거 PNG·manifest·최초 판정·실패 이력은 보존합니다. 잘못된 provenance 포인터는 정정 관계를 남기며, 새로운 결과로 과거 입력을 소급 정상화하지 않습니다.

같은 지속 세션의 후속 검토에서는 이번 finding과 수정 영향 범위를 이어서 판단하며 R02의 successor 예외를 적용하지 않습니다. **현재 응답은 원고 수정이 필요한 최초 검토 결과이며, 소유자 승인·`ready`·RC·M5 전체 완료·M6/M7·commit·push·배포·공개 URL을 승인하거나 실행한 결과가 아닙니다.**
