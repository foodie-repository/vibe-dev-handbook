R08의 주요 수정 사유는 다음 세 가지입니다.

1. `git status --short --branch`가 untracked를 숨기는 설정을 따를 수 있는데도, 안전 루프는 이 출력을 전체 변경 지도로 사용합니다.
2. 로컬에서도 가능한 merge를 GitHub상의 병합과 구분하지 않고 외부 상태 변경으로 묶습니다.
3. 검증 후 일부 변경만 스테이징할 때, 실제로 검증한 상태와 커밋할 상태가 같은 동작을 갖는지 확인하는 단계가 부족합니다.

**입력 완독은 충족했고, 응답 전 해시 확인은 controller 증거로 충족했습니다. 미해결 Critical은 0건이지만 Important는 4건이므로 PASS 조건을 충족하지 않습니다.** 아래 16/18점은 이 조건을 상쇄하지 않습니다.

준비 코드와 체크포인트는 별도로 판단했습니다. 검사기는 manifest 자체의 고정 해시를 먼저 확인하고, 개별 파일의 바이트·길이, 문맥 파일 해시와 실제 발췌 줄, 로컬 증거 모드의 결합 해시·PNG 헤더·렌더 manifest를 검사합니다. 기본 모드는 `localEvidence: "not-checked"`를 반환하고, 어느 모드에서도 `reviewComplete`와 `releaseReady`를 `false`로 유지합니다. 테스트에는 텍스트 누락·변조, manifest 교체, 발췌 불일치, PNG 누락·손상과 렌더 provenance 변경의 거절이 포함됩니다. 고정된 R08 입력 검사라는 범위에서 수정이 필요한 코드 결함은 발견하지 않았습니다.

controller가 제공한 정적 검사 **242 pass / 0 fail / 0 skipped / exit 0**, 기존 R07 빌드 재사용 사유, staged 6개와 현재 추적 파일 383개의 일치, release 검사 **383개 / finding 0 / exit 0**는 준비 단위의 검증 증거로 인정합니다. **제가 실행한 검사는 아닙니다.**

따라서 준비 6파일은 제공된 실행 전 상태를 기준으로 **입력 준비만을 보존하는 로컬 체크포인트에 적합합니다.** 실제 체크포인트 직전의 범위·불변성 재확인은 controller 책임이며, 이 판단은 원고 PASS나 커밋 실행·외부 공유 승인으로 확장되지 않습니다.

## 3. 위치별 finding

**R08-I01 — Important/P1 — untracked 표시 설정 때문에 안전 루프의 변경 목록이 불완전할 수 있습니다.**

- **위치:** `src/content/docs/09-git-github/git-and-github.md`의 「`git status --short --branch`」, 세 diff 표 뒤 안내, 「AI 변경을 검토하는 최소 안전 루프」 1·4단계.
- **최소 인용:** “untracked 파일을 요약합니다.”, “전체 상태 지도를 먼저 보고”.
- **관찰·근거:** 제공된 2026-11-15 Git status 근거는 untracked 표시가 옵션과 `status.showUntrackedFiles` 설정에 따라 달라진다고 명시합니다. 본문의 명령에는 이를 명시적으로 재정의하는 옵션이 없습니다. 설정이 `no`이면 새 파일이 있어도 목록에 보이지 않을 수 있고, `normal`이면 미추적 디렉터리 내부가 개별 파일 대신 묶여 표시될 수 있습니다. 용어집은 이미 “untracked·ignored 포함 여부와 사용한 명령”을 확인하도록 요구합니다.
- **영향·적용 기준:** 새 소스·비밀·개인 설정이 표시되지 않은 상태를 전체 변경 지도로 받아들일 수 있습니다. 이 장의 핵심 검증 계약에 해당하므로 C04·C05·C06의 Important입니다. 다만 본문의 clean 정의가 “보고하지 않는다”고 표현한 점은 적절하며, 이를 모든 파일 부재의 단정으로 과장해 지적하지 않습니다.
- **최소 수정:** 안전 루프에서 새 파일을 빠짐없이 열거하려는 명령을 `git status --short --branch --untracked-files=all`처럼 명시하고, 기본 status는 설정에 따라 untracked를 숨기거나 디렉터리 단위로 묶을 수 있음을 한 문장으로 설명합니다. ignored 파일은 별도라는 경계도 유지합니다.
- **재확인:** untracked 표시를 숨긴 가상 저장소에서도 권장 점검이 새 파일을 드러내는지, ignored 파일까지 자동 포함한다고 설명하지 않는지 확인합니다.

**R08-I02 — Important/P1 — 로컬 merge와 GitHub 병합의 외부 효과를 구분해야 합니다.**

- **위치:** 대상 원고의 「W-03 참가·중복 신청 방지의 Git 안전 경계」 중 「별도 승인」, 「AI 변경을 검토하는 최소 안전 루프」 9단계. 관련 표현은 「작업 트리에서 GitHub까지의 흐름」 6번에도 있습니다.
- **최소 인용:** “push, Pull Request, merge와 배포는 … 서로 다른 외부 상태 변경”.
- **관찰·근거:** 로컬 `git merge`는 현재 로컬 브랜치·index·작업 트리에 영향을 줄 수 있으며 원격 쓰기를 필수로 하지 않습니다. 반면 GitHub에서 PR을 병합하면 원격 기준 브랜치가 바뀝니다. 원고는 pull 설명에서 로컬 통합으로 merge를 사용하면서, 승인 설명에서는 구분 없이 외부 행동으로 분류합니다.
- **영향·적용 기준:** 독자가 “merge는 항상 원격 작업”이라고 배우거나 로컬 통합과 원격 병합의 권한·검증 대상을 혼동할 수 있습니다. Git과 GitHub의 경계를 설명하는 핵심 목표에 영향을 주므로 C01·C04·C06에 해당합니다.
- **최소 수정:** 외부 승인 문맥의 `merge`를 “GitHub에서의 PR 병합”으로 한정하고, 로컬 merge는 별도의 로컬 변경이라는 설명을 추가합니다. 함께 “승인은 Git 명령의 내장 조건이 아니라 이 핸드북의 작업 안전 정책이며, 승인된 범위·상시 정책에 따라 집행한다”고 밝혀 동작과 정책을 구분합니다.
- **재확인:** 로컬 merge와 GitHub PR 병합 각각에 대해 바뀌는 상태·승인 범위·직접 증거를 구별할 수 있어야 합니다. 사람의 승인 절차를 두는 정책 자체를 기술 오류로 취급하지 않습니다.

**R08-I03 — Important/P1 — 검증한 작업 트리와 부분 스테이징한 커밋 후보의 일치를 확인해야 합니다.**

- **위치:** 대상 원고의 W-03 변경 분리 문단, 「AI 변경을 검토하는 최소 안전 루프」 5~8단계, 「확인 체크리스트」의 검증 결과 연결 항목.
- **최소 인용:** “검증 실행” → “스테이징 후보 선택” → “스테이징 diff 재검토”.
- **관찰·근거:** 원고는 일부 변경 조각을 스테이징하고 나머지를 작업 트리에 남기는 흐름을 적극적으로 설명합니다. 이 경우 앞서 테스트한 작업 트리에는 커밋에서 제외할 코드·설정·테스트가 포함돼 있을 수 있습니다. staged diff가 요구에 맞아 보인다는 사실만으로 그 스냅샷이 같은 검증을 통과했다고 볼 수는 없습니다.
- **영향·적용 기준:** 테스트 통과 후 구성한 커밋이 실제로는 의존 변경을 빠뜨리거나, 남겨 둔 코드 때문에만 테스트가 통과하는 상황이 가능합니다. C02·C06의 “검증 증거와 변경 단위의 연결” 문제입니다. controller가 별도로 입증한 이번 준비 6파일의 index·작업 파일 일치에는 이 지적을 적용하지 않습니다.
- **최소 수정:** 부분 스테이징 또는 검증 이후 변경이 있으면, 검증한 상태와 커밋 후보의 차이가 결과에 영향을 주는지 확인하고 필요한 경우 후보 스냅샷을 보존된 별도 환경에서 검증하도록 명시합니다. 기존 사용자 변경을 버리거나 자동 stash하라는 절차는 추가하지 않습니다.
- **재확인:** 테스트한 작업 트리에는 필요한 보조 변경이 있지만 index에는 없는 가상 사례에서, 기존 테스트 결과만으로 커밋 준비 완료를 선언하지 않는지 확인합니다.

**R08-M01 — Minor/P2 — pull 설명에 ff-only와 squash의 범위를 보완하면 현재 근거와 더 정확히 맞습니다.**

- **위치:** 대상 원고의 「로컬 브랜치와 원격 상태를 구분하세요」, 「pull을 무해한 새로고침으로 사용합니다」.
- **최소 인용:** “보통 fetch한 뒤 현재 설정에 따라 merge 또는 rebase로 … 통합합니다.”
- **관찰·근거:** 제공된 현재 공식 자료에는 `--ff-only`, `--rebase`, `--no-rebase`, `--squash`와 관련 설정이 있습니다. 본문은 “보통”, “설정에 따라”, “실행돼 … 충돌할 수 있다”고 제한하므로 모든 pull이 merge 또는 rebase를 반드시 실행한다고 단정한 오류는 아닙니다. 다만 독자가 분기된 이력에서 ff-only가 통합을 거절하는 경우나 squash의 결과를 이해할 단서가 없습니다.
- **영향·적용 기준:** 현재 문서의 선택 조건을 설명하는 데 남은 국소적 예외 부족입니다. C04·C05에 따라 Minor로 분류합니다.
- **최소 수정:** “fetch 뒤 옵션·설정에 따라 fast-forward만 허용하거나 merge·rebase·squash 방식으로 반영하며, 통합을 거절할 수도 있다”는 정도로 보완합니다. squash가 즉시 새 커밋을 만든다고 설명하지 않으며, 현재 문서의 기본값을 모든 설치 버전에 적용하지 않습니다.
- **재확인:** 버전·옵션·설정 확인이 유지되고, 네 방식과 거절 결과를 하나의 고정 기본 동작으로 합치지 않아야 합니다.

**R08-M02 — Minor/P2 — 첫 커밋 전에는 `git diff HEAD`가 유효하지 않다는 예외가 필요합니다.**

- **위치:** 대상 원고의 「`git diff --staged`」, 「`git diff HEAD`」, 「“변경 없음”과 “커밋 준비 완료”를 혼동하지 마세요」. 인접 `branch-commit-pull-request.md`의 네 명령 예에도 같은 설명을 연결할 수 있습니다.
- **최소 인용:** “현재 커밋과 tracked 작업 상태의 차이”, `## No commits yet on main`.
- **관찰·근거:** 첫 커밋 전에는 `HEAD`가 가리키는 커밋이 없어 `git diff HEAD`가 오류를 냅니다. 반면 제공된 공식 diff 근거에 따르면 이 상태의 `git diff --staged`는 staged 전체를 보여 줍니다. 원고는 초기 저장소를 직접 예로 들지만 이 차이를 설명하지 않습니다.
- **영향·적용 기준:** 초보자가 제시된 명령을 같은 방식으로 적용하다 정상적인 초기 상태를 저장소 고장으로 오해할 수 있습니다. C02·C04의 국소 설명 보완입니다.
- **최소 수정:** 첫 커밋 전에는 `git diff HEAD` 대신 status·새 파일 내용·`git diff --staged`를 사용한다고 짧게 덧붙입니다.
- **재확인:** 첫 커밋이 없는 상태와 있는 상태에서 각 비교의 기준이 분명해야 합니다.

**R08-M03 — Minor/P2 — `git diff HEAD`는 staged·unstaged 변경을 각각 보존한 합집합이 아닙니다.**

- **위치:** 대상 원고의 「`git diff HEAD`」와 세 diff 비교 표.
- **최소 인용:** “스테이징된 변경과 스테이징되지 않은 변경을 함께 보지만”.
- **관찰·근거:** HEAD의 내용 A를 B로 바꿔 스테이징한 뒤 작업 트리를 다시 A로 돌려놓으면, `git diff HEAD`는 비어도 index에는 B가 남아 있습니다. 표의 “작업 트리 ↔ HEAD” 비교 기준은 맞지만, 설명은 staged·unstaged 각각의 변경을 모두 열거하는 것으로 읽힐 여지가 있습니다.
- **영향·적용 기준:** 본문이 다른 두 diff도 함께 보도록 하므로 즉각적인 전체 절차 실패로 보지는 않습니다. 다만 빈 출력의 해석을 가르치는 장에서 중요한 국소 표현이며 C04에 해당합니다.
- **최소 수정:** “HEAD와 최종 작업 트리 사이의 순변화를 보여 주며, staged·unstaged 변경이 서로 상쇄되면 index의 별도 상태를 드러내지 못한다”고 보완합니다.
- **재확인:** 위 A→B→A 사례에서도 `git diff --staged` 확인이 필요하다는 결론이 유지돼야 합니다.

**R08-XI01 — Important/P1, 인접 문맥 — PR 생성이 사용자의 push 수행이나 대상 저장소 push 권한을 증명하지는 않습니다.**

- **위치:** `src/content/docs/09-git-github/branch-commit-pull-request.md`의 「Pull Request는 검토 계약입니다」.
- **최소 인용:** “PR을 열었다는 사실은 push 권한과 원격 쓰기가 실제로 수행됐다는 뜻입니다.”
- **관찰·근거:** 이미 원격에 존재하는 브랜치를 대상으로 PR을 생성할 수 있으므로, PR 생성자가 해당 작업에서 push를 수행했다는 결론은 나오지 않습니다. fork에서 대상 저장소로 PR을 제안하는 경우에도 대상 저장소의 코드 push 권한과 PR 생성 가능성은 같은 권한이 아닙니다. 제공된 Pull Request 근거가 뒷받침하는 것은 변경을 제안·논의하는 협업 기능의 생성입니다.
- **영향·적용 기준:** PR URL을 push 실행·권한의 증거로 잘못 사용할 수 있어 R08이 설명하는 단계별 증거 분리와 충돌합니다. C04·C06에 해당하며, 해당 인접 장의 소유 행에서 처리할 Important입니다.
- **최소 수정:** “PR 생성은 GitHub의 협업 상태를 바꾸는 외부 쓰기다. push의 수행 여부와 원격 브랜치 상태·권한은 별도 증거로 확인한다”고 고칩니다.
- **재확인:** 이미 존재하는 원격 브랜치에서의 PR 생성과 fork PR 모두에서 push 수행·대상 저장소 push 권한을 추론하지 않아야 합니다.

**R08-XM01 — Minor/P2, 인접 문맥 — 모임 복구 사례에 명시적 비목표인 대기·알림이 들어갑니다.**

- **위치:** `src/content/docs/09-git-github/undo-merge-conflict-release.md`의 「중복 참가 방지 변경에서 결함이 발견됐다면」.
- **최소 인용:** “다른 사용자의 참가·취소·대기 상태”, “이미 발송한 알림”.
- **관찰·근거:** 제공된 사례 브리프와 R12 본문은 대기 명단과 알림을 비목표로 두고, 참가 상태는 `confirmed | cancelled`로 제한합니다. 복구 장에서는 이 기능들이 현재 모임 사례에 존재하는 것처럼 질문합니다.
- **영향·적용 기준:** 복구 원칙 자체는 유효하지만, 정해진 교육용 사례의 구현 범위가 불필요하게 늘어납니다. C03·C04의 문맥 일관성 문제입니다.
- **최소 수정:** 사례 안에서는 참가·취소와 실제 정의된 상태만 사용합니다. 알림 같은 일반적인 외부 부작용 예를 유지하려면 이 사례 밖의 확장 예라고 명확히 분리합니다.
- **재확인:** W-03/W-04 설명이 현재 사례의 상태·비목표와 일치해야 합니다. R12 자체의 전체 검토를 다시 수행할 필요는 없습니다.

**R08-XM02 — Minor/P2, 인접 문맥 — 사례 링크 표시명이 실제 제목과 다릅니다.**

- **위치:** `src/content/docs/09-git-github/branch-commit-pull-request.md`의 「관련 용어와 출처」.
- **최소 인용:** “모임 예약 웹앱: 요구에서 운영까지”.
- **관찰·근거:** 연결된 고정 원고의 제목은 “첫 풀스택 프로젝트: 모임 참가 웹앱”입니다. 경로 오류를 주장하는 것이 아니라 표시명 불일치입니다.
- **영향·적용 기준:** 동일 사례가 예약 앱과 참가 앱으로 달리 불려 탐색과 용어 일관성이 약해집니다. C03·C08에 해당합니다.
- **최소 수정:** 링크 표시명을 실제 제목 또는 명확한 축약형 “모임 참가 웹앱”으로 맞춥니다.
- **재확인:** 링크 대상 제목·사례 명칭이 일치하는지 확인합니다.

## 6. 재확인 기준

같은 R08 reviewer의 저장 세션에서 다음 범위를 재확인하면 됩니다. R02 승계 예외를 적용하거나 새 reviewer가 기존 판단을 이어받은 것으로 처리하지 않습니다.

1. **R08-I01~I03 수정 확인:** status 표시 옵션과 한계, 로컬 merge와 GitHub PR 병합, 검증한 상태와 부분 스테이징 후보의 연결을 수정된 문단·안전 루프·체크리스트에서 함께 대조합니다.
2. **R08-M01~M03 확인:** pull의 버전·설정·통합 거절·squash 범위, 첫 커밋 전 HEAD 부재, `git diff HEAD`의 순변화 한계를 좁게 재검토합니다.
3. **인접 finding 재판정:** R08-XI01과 R08-XM01~XM02는 controller가 해당 소유 행에 연결해 수용·부분 수용·기각을 기록합니다. R08에서는 수정된 관련 문맥의 일관성만 재확인하고 해당 행 전체 검토로 확대하지 않습니다.
4. **새 입력 고정:** 변경 파일의 전후 diff, 새 개별 SHA-256·결합 SHA-256, 갱신된 요청·manifest와 finding 재판정을 제공합니다. 기존 R08 입력과 최초 결과는 역사로 보존합니다.
5. **자동 검증:** controller가 수정 범위에 맞는 정적 검사와 필요한 빌드 검증을 수행하고 정확한 명령·범위·종료 코드를 제공합니다. 설명의 반례를 확인할 필요가 있으면 비민감 가상 저장소에서 status 설정, unborn HEAD, staged·작업 트리 차이를 좁게 검증합니다.
6. **시각 증거:** 그림이 불변이면 현재 그림 관찰은 해당 자산에 계속 사용할 수 있습니다. 다만 본문 수정으로 위치·줄바꿈이 바뀐 문맥 crop은 새 원고의 화면 증거로 자동 전용하지 않습니다. 변경된 문맥에 필요한 라이트·다크·모바일 증거를 새로 연결하고, SVG·Mermaid·alt가 바뀌면 함께 재검토합니다.
7. **응답 후 감사와 정본 저장:** controller가 이번 응답 이후 입력 불변성, 실제 모델·effort·권한, 전체 출력과 이미지별 관찰을 확인한 뒤 정본에 저장해야 합니다. 이 단계는 현재 완료된 것으로 계산하지 않습니다.
