**메타데이터와 완료 상태의 연결이 적절합니다.**

대상 원고의 diff는 `contentStatus: review`와 세 `reviewEvidence` 항목의 추가에 한정됩니다. `request:`는 최초 고정 요청, `independent:`는 실제 수정 후 PASS 정본, `adjudication:`은 최종 controller 판단을 가리킵니다. Controller 문서는 다시 최초 결과·Fix1 결과·일곱 항목의 재판정으로 연결되므로, 최초 `NEEDS CHANGES`를 현재 PASS로 덮어쓰지 않습니다.

`CONTENT_MAP.md`, 계획 인벤토리, R13 체크 행, 행렬의 표·JSON, 프로젝트 요약과 출처 지도도 같은 전이를 반영합니다. 출처 지도는 문서 수정의 해소를 기록하면서 PBSG-019/026과 실제 구현·배포·공개 미검증을 유지합니다.

**정본 경로 추가는 동일 응답의 계약 경로 연결로 처리됩니다.**

`r13-stock-capstone-codex-rereview.md`는 기존 `r13-stock-capstone-fix-round-1.md`와 동일 raw+LF 바이트를 사용하는 것으로 명시돼 있습니다. 새 파일을 독립 검토 한 번으로 추가 계산하지 않으며 기존 파일을 이동·삭제·수정하지 않는다는 경계도 있습니다.

제공된 Fix1 본문은 이전 판정과 일치합니다. 일본어 한 문장을 포함한 원응답도 그대로 보존했고, 재판정 문서가 그 의미를 “reviewer가 해시 재계산과 역변환을 실행하지 않았다”는 한계로 설명합니다. 원문 보존을 위해 해당 문장을 소급 편집할 필요는 없습니다.

**정확한 전이와 역사 복원의 순서가 유지됩니다.**

`scripts/r13-closeout.mjs`에는 여덟 콘텐츠·상태 파일의 전후 해시와 교체 쌍이 있습니다. `r13PreCloseoutBytes()`는 다음 조건으로 작동합니다.

1. 지정 경로이고 전체 바이트가 정확한 `after` 해시일 때만 복원합니다.
2. 교체 문자열이 정확히 한 번 존재하는지 확인합니다.
3. 교체를 역순으로 적용합니다.
4. 복원 결과가 `before` 해시와 다르면 오류를 냅니다.

알 수 없는 변경은 그대로 반환하므로 임의의 편집을 정상 역사로 치환하지 않습니다. `r13PreFixBytes()`는 **closeout 전이 제거 → Fix1 전이 제거** 순서로 최초 입력까지 복원하며, 기존 Fix1 교체 내용과 해시는 바꾸지 않습니다.

**역사 복원이 현재 완료 상태의 rollback을 허용하지 않습니다.**

`validateR13Current()`는 closeout 전이를 제거한 뒤 Fix1의 네 파일 상태를 검사합니다. 이 함수만 보면 정확한 Fix1 바이트도 허용되지만, 현재 진입점인 `validateR13Inputs()`가 **`validateR13Closeout()`의 현재 해시 검사도 함께 수행**합니다. 따라서 대상 원고를 Fix1의 `draft` 바이트로 되돌려 역사 검사를 통과시키더라도 현재 closeout 검사가 실패합니다.

여덟 전이 전체의 현재 해시·역변환은 새 테스트에서 검사합니다. 다만 `validateR13Closeout()` 자체의 상시 pin 목록에서는 `PROJECT_CONTEXT.md`와 `ROADMAP.md`를 제외합니다. 그러므로 **“이 함수 하나가 여덟 파일 모두의 누락·rollback을 거절한다”라고 확대해서는 안 됩니다.** 이번 후보에서는 두 파일을 포함한 여덟 전이 테스트와 index 대조가 별도로 제공되며, 나머지 여섯 전이 파일과 정본 증거는 closeout 검사에서 직접 보호됩니다. 이 구분은 기존 검사 구조와도 일치합니다.
