**2. 판정과 건수**

**원고 및 제공 문맥 판정: NEEDS CHANGES**

| 구분 | Critical | Important | Minor |
|---|---:|---:|---:|
| R05 대상 원고·공유 그림 | 0 | 1 | 4 |
| 제공된 인접 장의 일관성 문제 | 0 | 1 | 0 |
| 합계 | **0** | **2** | **4** |
| 별도 준비 코드 검토 | **0** | **0** | **0** |

대상 장의 강점은 명확합니다. 서버 응답, UI 상태, 현재 DOM, 화면 픽셀, 사용자 과업을 구별하고, 파싱·스타일·렌더링을 고정된 직렬 구현으로 설명하지 않습니다. 임시 DOM 편집과 실제 소스 수정, 앱의 render와 브라우저 렌더링, 기기 에뮬레이션과 실제 기기 검증의 경계도 유지합니다.

수정이 필요한 핵심은 다음 두 가지입니다.

- 지연 로딩 진단표에서 **Network 열에 DOM 존재 증거를 배치**했습니다. 이 장의 중심 교육 목표인 증거 표면의 구분과 직접 충돌합니다.
- 인접 UI 상태 장의 전이표가 **현재 참가 여부와 특정 이전 요청의 처리 여부를 동일시**합니다. 현재 상태 조회만으로 재시도 안전성까지 판정하는 오해를 만들 수 있습니다.

입력 완독 조건은 충족했습니다. 사전 바이트 일치 조건은 제공된 controller 실행 증거에 근거합니다. **미해결 Critical/Important 0 조건은 충족하지 않았습니다.** 응답 후 불변성 감사와 결과 정본 저장은 아직 완료된 사실이 아닙니다.

준비 코드에 대해서는 **독립 코드 검토 관점의 safe-to-checkpoint 판단은 YES**입니다. 고정된 이번 입력을 검사하는 범위에서 체크포인트를 막을 코드 결함을 발견하지 않았습니다. 다만 테스트 실행 결과·종료 코드와 변경 분리·스테이징 상태는 제공되지 않았으므로, **전체 체크포인트 실행 조건이 충족됐다고 인증하거나 커밋을 승인하는 판단은 아닙니다.**

**3. 위치별 finding**

**R05-I01 — 지연 로딩 진단표의 Network 열에 DOM 증거가 들어가 있습니다**

- **위치:** `src/content/docs/05-frontend/browser-dom-rendering.md` → 「지연 로딩과 렌더링 실패를 구분하세요」의 네 상태 비교표, 마지막 행.
- **심각도:** Important/P1.
- **최소 인용:** `DOM 존재, 렌더링 실패 | 필요한 노드는 존재 | 숨김·0 크기·화면 밖·겹침`
- **관찰 근거:** 해당 열의 제목은 순서대로 `상태 | Network | DOM·상태 | 화면 | 다음 확인`입니다. 따라서 “필요한 노드는 존재”가 Network의 관찰 사실로 제시됩니다. 같은 장의 앞선 표는 Network가 요청·응답을 보여 주고 Elements가 현재 노드를 보여 준다고 정확하게 구분합니다.
- **영향·적용 기준:** 초보자가 빈 영역을 진단할 때 Network에서 DOM 존재를 확인할 수 있다고 읽거나, 필요한 자원의 요청·응답 여부를 건너뛸 수 있습니다. C02·C04의 핵심 판단 규칙과 증거 구분에 해당합니다.
- **최소 수정:** Network 칸은 “관련 요청·응답은 별도로 확인하며, 이 증거만으로 노드 존재를 판단하지 않음”처럼 바꾸고, “필요한 노드가 존재”는 DOM·상태 칸으로 옮기세요. 숨김·크기·겹침은 스타일·레이아웃 및 픽셀 확인과 연결하면 됩니다.
- **재확인 기준:** 네 행 모두에서 각 칸의 사실을 해당 증거 표면으로 실제 확인할 수 있는지 대조합니다. 특히 “요청 있음/없음”, “노드 있음/없음”, “보임/안 보임”이 서로 다른 판정으로 남아야 합니다.

**R05-I02 — 현재 참가 상태를 특정 이전 요청의 적용·미적용 증거로 단정합니다**

- **위치:** `src/content/docs/05-frontend/ui-state-and-ux.md` → 「상태 전이를 표로 쓰세요」의 마지막 두 행. 같은 장의 「복구 오라클을 먼저 정하세요」 및 용어집의 `recovery oracle` 정의와 함께 대조했습니다.
- **심각도:** Important/P1. **인접 문맥 finding**이며 해당 장의 정식 행 검토를 대신하지 않습니다.
- **최소 인용:** `권위 상태에서 참가 확인 … 이전 요청 적용 확인`, `미참가 확인+재시도 허용 … 이전 요청 미적용 확인`.
- **관찰 근거:** 제공된 장 자체가 여러 탭·기기·동시 요청과 응답 유실을 인정하고, 복구 오라클에서 현재 상태와 “이전 요청 식별자의 처리 결과”를 구별합니다. 그런데 전이표는 현재 참가 여부만으로 이전 요청의 처리 결과까지 확인된 것으로 씁니다.
- **영향·적용 기준:** 현재 미참가라는 관측은 그 순간의 상태를 알려 줍니다. 이전 요청이 아직 처리 중인지, 다른 변경이 있었는지, 어느 요청이 현재 상태를 만들었는지는 별도 계약과 증거가 필요합니다. 이 구분이 없으면 결과 불명 상태에서 새 쓰기를 안전하게 재시도할 수 있다고 오해할 수 있습니다. C04·C06의 복구·재시도 경계에 해당합니다.
- **최소 수정:** 참가 확인 행은 “현재 참가 상태 확인”으로 한정하고, 이전 요청 적용 여부는 요청 식별자와 연결된 처리 결과가 있을 때만 확정하세요. 미참가 행은 “현재 미참가 확인”과 “이전 요청 종결·미적용 또는 안전한 멱등 재시도 조건 확인”을 분리하세요. “재시도 허용”이 무엇으로 판정되는지도 짧게 명시하면 됩니다.
- **재확인 기준:** 이전 요청이 조회 뒤 늦게 확정되는 경우, 다른 탭이 참가·취소한 경우, 처리 결과 조회가 실패한 경우를 전이표에 대입합니다. 현재 상태 조회만으로 특정 요청의 인과관계나 재시도 안전성을 확정하지 않아야 합니다.
