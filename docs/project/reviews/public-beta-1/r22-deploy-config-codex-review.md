## 2. 판정과 건수

**원고 판정: `NEEDS CHANGES` — Critical 0건, Important 7건, Minor 2건입니다.**

중요 지적은 다음과 같습니다.

- AI 프롬프트가 설정과 비밀을 상호 배타적으로 분류하게 합니다.
- 변수 이름의 발견과 실제 비밀값의 노출을 구분하지 않습니다.
- 길이·fingerprint의 안전 조건이 없어 비밀의 파생 정보를 무조건 출력 가능한 것으로 읽힐 수 있습니다.
- 읽기 전용 프롬프트에 실제 비밀 접근과 원격 접근의 허용 범위가 없습니다.
- Node `--env-file` 현재 주장에 필요한 직접 출처가 제공 발췌에서 누락돼 있습니다.
- Astro `import.meta.env`와 `astro:env`의 노출 규칙을 명시적으로 나누지 않습니다.
- 모바일 양쪽 테마에서 자연어 프롬프트의 가로 왕복 읽기가 필요합니다.

입력은 모두 읽었고 필수 이미지도 36개 모두 판독했습니다. 따라서 **입력 미독 때문에 `BLOCKED`로 판정하지 않습니다.** 다만 미해결 Important가 7건이므로 PASS 조건을 충족하지 않습니다. 응답 후 불변성 감사와 정본 저장은 아직 완료 증거가 아닙니다.

**준비 검사기·테스트·캡처에 대한 별도 판정:** 제공된 코드와 기록에서 새로 확정한 Critical 0건, Important 0건, Minor 0건입니다. 이는 준비 작업의 제한된 검토 결과이며 원고 PASS를 뜻하지 않습니다.

## 3. 위치별 finding

아래 F01~F09의 대상 파일은 모두 `src/content/docs/10-deployment-operations/environment-variables-config.md`입니다. 별도 위치가 필요한 경우 비교 근거를 함께 적었습니다.

**R22-F01 — Important/P1: AI 분류 지시가 설정과 비밀을 상호 배타적인 범주로 만듭니다.**

- **위치·최소 인용:** 「AI의 설정 보고를 검토하는 읽기 전용 지시」의 `- config 또는 secret`. 「한 문장 정의」에는 “데이터베이스 비밀번호는 설정에 사용되면서 동시에 비밀”이라고 설명합니다.
- **근거·영향:** 본문은 설정의 역할과 값의 민감도가 다른 축이라는 점을 올바르게 설명하지만, 실전 프롬프트는 둘 중 하나를 고르게 합니다. 독자가 비밀을 설정 관리 대상에서 제외하거나, 설정으로 분류했다는 이유로 비밀 통제를 누락할 수 있습니다. C04·C06에 해당합니다.
- **최소 수정:** 역할과 민감도를 별도 열로 나누세요. 예를 들어 “설정으로 쓰이는 목적”과 “공개 가능·서버 전용·자격 비밀 여부”를 따로 기록하게 합니다. 사용 시점도 같은 값이 여러 단계에서 소비된다면 단계별로 기록할 수 있게 하면 좋습니다.
- **재확인:** DB 연결 자격 한 행에 설정의 역할과 비밀 통제가 동시에 남는지, 공개 URL에는 비밀 통제를 불필요하게 부과하지 않는지 확인합니다.

**R22-F02 — Important/P1: 변수 이름의 발견을 비밀값 노출 사고와 동일시합니다.**

- **위치·최소 인용:** 「클라이언트 노출은 빌드 결과에서 확인하세요」의 “`SERVER_DATABASE_URL`이나 `SERVER_SIGNING_KEY`가 client bundle·HTML·network response·로그에 나타나면 … 노출 사고입니다.”
- **근거·영향:** 앞에서는 설정 이름·schema·비밀 참조를 Git에 둘 수 있다고 설명합니다. 공개 코드에 변수 이름이나 마스킹된 누락 오류가 있다는 사실과, 사용 가능한 자격 값이 노출됐다는 사실은 다릅니다. 현재 문장은 이름 검색 결과만으로 사고를 확정하게 해 오탐과 불필요한 대응을 유도합니다. C04·C06의 진단 정확성 문제입니다.
- **최소 수정:** “해당 변수의 실제 비밀값 또는 악용 가능한 파생값이 노출된 경우”로 판정 대상을 명확히 하세요. 변수 이름 발견은 전달 경로를 조사할 단서이며, 내부 이름 자체의 민감성은 별도로 분류한다고 설명하면 충분합니다.
- **재확인:** 가짜 fixture로 이름만 있는 경우, 마스킹된 값, 실제 값을 흉내 낸 가짜 노출, 인코딩된 가짜 값의 네 경우를 구분할 수 있는지 검토합니다. 실제 비밀을 시험 입력으로 사용하지 않습니다.

**R22-F03 — Important/P1: 길이·fingerprint를 안전한 진단 출력으로 허용하는 조건이 없습니다.**

- **위치·최소 인용:** 「로딩 우선순위는 도구별 계약입니다」의 “비밀값이 아닌 fingerprint”, 「디버깅을 위해 값을 그대로 출력합니다」의 “이름·존재 여부·길이·version·안전한 fingerprint만 사용하세요.”
- **근거·영향:** fingerprint는 생성 방식·입력의 추측 가능성·공개 범위에 따라 비밀 후보를 대조하는 자료가 될 수 있습니다. 비밀 원문을 출력하지 않았다는 이유만으로 길이와 파생값까지 안전해지지는 않습니다. 현재는 “안전한”이라는 수식어만 있고 독자의 판단 조건이 없습니다. C02·C06에 해당합니다.
- **최소 수정:** 기본 출력은 승인된 이름·존재 여부·비밀 관리 시스템의 비민감 버전 식별자로 제한하세요. 비밀값의 길이·해시·일부 문자열을 임의로 생성해 출력하지 않으며, 파생 식별자는 승인된 진단 정책이 있을 때만 사용한다고 명시합니다.
- **재확인:** 프롬프트와 체크리스트가 agent에게 비밀을 읽어 fingerprint를 계산하도록 유도하지 않는지 확인합니다. 진단 예시는 비밀값으로 계산하지 않은 가짜 버전 ID만으로 구성할 수 있습니다.

**R22-F04 — Important/P1: 읽기 전용 프롬프트가 비밀 접근·원격 조회의 권한 경계를 지정하지 않습니다.**

- **위치·최소 인용:** 「AI의 설정 보고를 검토하는 읽기 전용 지시」의 “설정 관련 source, schema, build와 deployment 선언을 읽기 전용으로 점검하라”, “실제 값을 출력하거나 파일·환경·외부 서비스를 변경하지 마라.”
- **근거·영향:** 출력·변경 금지는 읽기 권한의 범위를 정하지 않습니다. 이 문장만 복사하면 실제 `.env`, 인증 저장소, 운영 로그나 원격 배포 설정을 읽어도 된다고 해석할 여지가 있습니다. 제공된 프로젝트 규칙은 비밀·개인정보 접근도 승인 대상으로 분리하고, 인접 배포 장의 프롬프트도 원격 읽기 범위를 명시합니다. C06의 실전 권한 계약 문제입니다.
- **최소 수정:** 허용된 파일·기존 비식별 증거만 읽도록 범위를 지정하고, 별도 승인 없는 실제 `.env`·인증·비밀·개인정보 접근과 원격 조회를 금지하세요. 기존 빌드 증거를 읽는 것과 새 빌드·검증 명령 실행도 분리합니다. 접근할 수 없는 항목은 미검증으로 보고하게 합니다.
- **재확인:** 브리프 템플릿·인접 배포 장과 대조해 로컬 읽기, 원격 읽기, 명령 실행, 외부 쓰기가 각각 구분되는지 확인합니다. 실제 계정 접근 시험은 필요하지 않습니다.

**R22-F05 — Important/P1: 현재 Node CLI 옵션 주장에 직접 근거가 빠져 있습니다.**

- **위치·최소 인용:** 「로딩 우선순위는 도구별 계약입니다」의 “Node.js는 현재 자체 `.env` 형식과 `--env-file` 같은 기능을 문서화”.
- **근거·영향:** 현재 제공된 S1 발췌는 `CLI Options` 제목과 도입만 있고 옵션 목록이 없습니다. 발췌 마지막 적용 경계도 `--env-file`의 직접 근거로 사용하지 않는다고 명시합니다. 2026-08-13의 확인 이력은 보존할 수 있지만 이것으로 2026-11-16의 현재 옵션 주장을 직접 확인했다고 할 수 없습니다. C05·C12에 해당합니다. **기능이 없다는 지적이 아니라 현재 검토 근거가 그 주장까지 도달하지 못했다는 지적입니다.**
- **최소 수정:** 현재 발췌가 직접 뒷받침하는 자체 `.env` 형식·문자열 처리 설명만 남기거나, controller가 공식 CLI 옵션의 해당 절을 추적 가능한 새 발췌로 제공해야 합니다. 새 확인을 추가할 때에는 8월 기록을 덮어쓰지 말고 별도 날짜·버전·범위로 연결합니다.
- **재확인:** 원고에 남은 현재 제품 주장마다 제공된 공식 절을 연결할 수 있어야 합니다. 설치 가능한 모든 Node 버전이나 `package.json`의 최소 버전에 v26.12.0 문서의 기능 범위를 확대하지 않아야 합니다.

**R22-F06 — Important/P1: Astro의 두 환경 변수 API를 구분할 설명이 부족합니다.**

- **위치·최소 인용:** 「로딩 우선순위는 도구별 계약입니다」의 “Astro는 Vite 기반 build-time 치환, client의 `PUBLIC_` prefix와 `astro:env` schema를 제공”.
- **근거·영향:** 제공된 S2에서 `import.meta.env`의 `PUBLIC_` 규칙과 `astro:env`의 schema 규칙은 구분됩니다. `astro:env/client`의 공개 변수는 `context: "client", access: "public"`로 지정하며, 예시 이름 `API_URL`에는 `PUBLIC_`가 없습니다. 또한 public server는 서버 번들에 포함되지만 secret server는 최종 번들에서 제외됩니다. 현재 한 문장으로는 독자가 같은 prefix 규칙이 두 API에 모두 적용되거나, 서버 변수는 모두 번들에서 제외된다고 오해하기 쉽습니다. C04·C05·C06에 해당합니다.
- **최소 수정:** `import.meta.env`와 `astro:env`를 짧은 두 설명으로 나누세요. 전자는 Vite 치환·`PUBLIC_`, 후자는 `context`·`access`와 public server/secret server의 차이를 연결하고, SSR 실행 시 접근은 adapter에 따라 확인하도록 유지합니다. 전체 제품 매뉴얼을 추가할 필요는 없습니다.
- **재확인:** `PUBLIC_` 없는 client public 변수, server public 변수, server secret 변수의 세 사례를 출처 발췌와 대조합니다. `astro.config.mjs`에서의 `process.env` 사용도 `astro:env` 사용으로 오인하지 않아야 합니다.

**R22-F07 — Important/P1: 모바일에서 자연어 프롬프트를 가로로 왕복해야 읽을 수 있습니다.**

- **위치·최소 인용:** 「AI의 설정 보고를 검토하는 읽기 전용 지시」의 `text` 코드 블록.
- **관측 근거:** `R22-PNG-17/18`, `R22-PNG-35/36`에서 첫 지시·긴 목록·하단 금지 문장이 좌우 구간으로 갈립니다. 오른쪽으로 이동하면 문장 시작이 사라집니다. `R22-PNG-06/24`에서는 같은 내용이 desktop 폭에 들어갑니다.
- **영향:** 안전 제한과 확인할 증거를 연속해서 읽어야 하는 실전 프롬프트에서 모바일 독자가 조건을 놓치기 쉽습니다. 표의 2차원 관계나 dotenv 한 줄의 문법 보존과 달리, 이 자연어 지시는 가로 배치를 유지할 이유가 없습니다. 문서 전체 `overflow: false`는 블록 내부 문제를 해소하지 않습니다. C01·C07·C08에 해당합니다.

## 5. 미확인 사실·남은 위험·검토 한계

실제 `.env`, 인증 정보, 비밀값, 제품 계정, 설정 화면, 비밀 회전·폐기·세션 무효화, 배포와 운영 데이터에는 접근하지 않았습니다. 따라서 원고의 절차가 특정 제품·계정·adapter에서 실제로 성공한다는 증거는 없습니다. 공개 설정 endpoint를 통한 client runtime 전달 역시 표의 계약 예시이며, 이 저장소가 이를 구현했다는 뜻이 아닙니다.

공식 자료는 제공된 발췌의 선언 범위만 읽었습니다. Node의 손상·중복된 코드 추출을 실행 예제로 인정하지 않았고, Astro 코드의 추출 손실도 정상 실행 코드로 인증하지 않았습니다. Vercel의 Config/Secret·Custom environments 추가 설명을 원고의 필수 제품 기능 목록이나 실제 사용 가능성으로 확대하지 않았습니다. OWASP 5.1의 환경 변수 권고는 컨테이너 주입 문맥이며, 모든 OS 프로세스가 다른 프로세스의 환경 변수를 읽을 수 있다는 근거가 아닙니다.

## 6. 재확인 기준

controller는 먼저 이 최초 결과를 원래 고정 입력에 대한 결과로 보존해야 합니다. **원고 수정 전에 정상 결과 정본을 별도 커밋하고, 응답 후 입력 불변성 감사를 수행한다는 요청 계약을 유지해야 합니다.** 저는 파일 저장·커밋·상태 변경을 수행하지 않았습니다.

후속 작업과 같은 reviewer의 재확인은 다음 범위면 충분합니다.

1. **F01~F09를 각각 재판정합니다.** 수용·부분 수용·기각과 근거, 실제 반영 위치를 기록합니다. 건수를 줄이기 위해 서로 다른 원인의 지적을 합치거나 미해결 항목을 삭제하지 않습니다.
2. **수정 원고 전체와 좁은 diff를 제공합니다.** 설정/비밀, 이름/값, 진단 정보, 읽기 권한, Astro API 설명은 서로 영향을 주므로 수정 단락뿐 아니라 프롬프트·체크리스트·연습과의 정합성까지 다시 읽겠습니다.
3. **F05의 근거 공백을 해소합니다.** 현재 CLI 옵션 주장을 좁히거나 공식 해당 절을 새로 고정해 제공합니다. 2026-08-13 기록은 그대로 보존하고 새 확인일·문서 버전·적용 범위를 별도로 기록합니다.
4. **수정된 공개 출력은 새로 빌드합니다.** 지금의 R21 build60 재사용 근거는 공개 출력 불변에 한정됩니다. 본문이나 프롬프트 표시가 바뀐 뒤에는 그 새 산출물에 대한 빌드·built 검증과 관련 정적 검사가 필요합니다.
