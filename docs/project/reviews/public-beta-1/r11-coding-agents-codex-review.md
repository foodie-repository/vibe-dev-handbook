## 2. 판정과 건수

**원고 및 직접 연결된 템플릿의 판정: `NEEDS CHANGES` — Critical 0 / Important 2 / Minor 2.**

| 구분 | Critical | Important | Minor | 판정 |
|---|---:|---:|---:|---|
| R11 대상 원고 | 0 | 2 | 1 | `NEEDS CHANGES` |
| 연결된 작업 브리프 템플릿 | 0 | 0 | 1 | 국소 보완 필요 |
| 합계 | **0** | **2** | **2** | **`NEEDS CHANGES`** |
| 입력 준비 검사기·테스트 코드 | 0 | 0 | 0 | 제공 범위의 코드 검토 적합 |

원고의 중심 구조는 타당합니다. 요청의 동사에서 권한을 해석하고, 모델의 판단과 도구의 행동, 하네스의 제한·관측을 구분합니다. 독립 리뷰의 `PASS`를 수용이나 공개 승인으로 확대하지 않으며, finding 재판정과 권한 있는 수용자의 결정을 명시합니다. 병렬 작업에서도 파일뿐 아니라 DB·포트·캐시·외부 계정의 소유권과 통합 책임을 다룹니다.

다만 `blocked`를 정반대 의미로 정의한 문장은 상태 해석이라는 학습목표를 직접 훼손합니다. W-03의 “활성 참가 한 건”이라는 불변식은 순차 중복 시험만으로 통과할 수 있는 현재 예시보다 강한 검증 계약이 필요합니다. 입력 부족으로 막힌 검토는 아니지만, **미해결 Important 0건 조건을 충족하지 못했습니다.**

준비 코드에서는 고정 manifest 자체의 해시, 각 입력의 해시·길이, 로컬 모드의 결합 해시, 문맥 원본과 발췌 행, PNG 서명·IHDR, 렌더 provenance를 검사하는 흐름을 확인했습니다. 기본 모드가 PNG를 검사하지 않았음을 `localEvidence: "not-checked"`로 반환하고, 어느 모드에서도 `reviewComplete`와 `releaseReady`를 `false`로 유지하는 점도 적절합니다. 이 검사기를 이미지 의미 판독이나 원고 심사기로 해석하지 않았습니다.

제공된 실행 증거는 다음 범위로 인정했습니다.

- 로컬 입력 검사: errors 0.
- 집중 테스트: 5/5, 실패 0·건너뜀 0이라는 controller 제공 결과.
- 첨부 정적 검사 로그: 273/273, 실패 0·취소 0·건너뜀 0, 콘텐츠 59개, 참조 300개, 학습 SVG 14개, 계획 배정 합계 100점·중복 0·누락 0.
- 최신 요청문: 참조 301개, exit 0이라는 별도 controller 보고. 첨부된 로그의 300개를 301개로 바꿔 읽지 않았습니다.
- 변경 없는 산출물: 유효한 R10 closeout의 build 60 / Pagefind 60 / built 60, exit 0 재사용이라는 제공 근거.
- index 증거: staged 6개, 현재 후보 440개 대조 불일치 0, unstaged 목록 없음, 공개 안전 검사 440개·finding 0·exit 0.

**준비 단위는 제공된 코드·테스트·입력 및 index 증거 범위에서 로컬 체크포인트 후보로 적합합니다.** 이는 원고 Important 두 건의 해소나 R11 PASS를 뜻하지 않습니다. controller의 응답 형식 검증·응답 후 입력 감사·정본 저장은 아직 완료되지 않았으며, 이 응답은 commit 실행이나 상태 승격을 승인하지 않습니다.

- **관찰 근거:** 입력·권한·외부 상태의 부재를 설명하면서 결과를 “진행할 수 있다”로 적었습니다. 제공된 `src/content/docs/reference/agent-output-glossary.md`는 같은 용어를 “현재 범위에서 진행할 수 **없다**는 상태”로 정의합니다. 검토 계약의 blocked와 재개 조건도 후자의 의미입니다.

- **역사적 렌더:** 원고·SVG·Mermaid의 바이트 불변이라는 제공 근거에 따라 당시 이미지를 사용했습니다. 사이트의 모든 현재 런타임·CSS·브라우저 조건까지 새로 검증한 것은 아닙니다.
- **상호작용과 공개 게이트:** 검색, 키보드·포커스, 스크린리더, 현재 콘솔·요청 실패, 비로그인 공개 URL, 원격 CI·배포는 새로 확인하지 않았습니다. 과거 manifest의 checks를 제가 실행한 결과로 재기록하지 않습니다.
- **증거의 시점:** 첨부 로그의 refs 300과 최신 요청의 refs 301은 구분해서 보존해야 합니다. 제공 정보만으로 실패나 회귀라고 단정하지 않으며, 새 정본 기록에서 어느 실행의 수치인지 명시하면 됩니다.
- **검토 다양성:** fresh context와 역할·권한 분리는 적용했지만 다른 제공자의 모델 검토나 실제 사람 기술·독자 검토를 수행한 것은 아닙니다.
- **후속 상태:** R01~R10의 유효 결과를 재검토하지 않았고, 인접 장·용어집·캡스톤을 읽은 사실을 해당 행의 완료로 계산하지 않았습니다. 과거 Claude pending/blocked도 그대로 역사적 상태입니다.

## 6. 재확인 기준

1. **controller가 네 finding을 각각 재판정해야 합니다.** 수용·부분 수용·기각과 그 근거를 남기며, 기각할 경우 원고의 현재 문장이나 실제 검증 계약이 지적의 전제를 어떻게 반박하는지 연결해야 합니다.

2. **같은 reviewer에게 영향 범위를 제공해야 합니다.** 수정된 원고의 해당 절과 앞뒤 문맥, 템플릿, 수정 diff, 새 개별·결합 SHA-256을 제공하면 됩니다. I01은 출력 용어집의 `blocked` 정의, I02는 W-03의 동시 중복·데이터 제약 관련 문맥, M01은 제품 기능의 미확인 경계, M02는 표준 보고·수용 체크리스트와 대조합니다. 의미가 바뀌지 않은 R01~R10은 반복할 필요가 없습니다.

3. **I02의 해소는 교육용 계약의 보완으로 판단합니다.** 이 저장소에 실제 모임 앱을 새로 구현하거나 운영 DB 시험을 실행할 필요는 없습니다. 수정된 브리프가 순차 검사만 하는 구현을 충분하다고 받아들이지 않고, 같은 참가자의 동시 요청과 실제 고유성 보호·최종 데이터 오라클을 명시하는지 확인합니다.

4. **원고 수정 후 새 자동 검증 증거를 제공해야 합니다.** 관련 정적 검사·콘텐츠·참조·계획 검사와 필요한 빌드 결과의 명령·환경·종료 코드·통과·실패·건너뜀 수를 남깁니다. 고정 입력 검사기가 원래 입력을 계속 보호하도록 하며, 새 해시로 과거 입력이나 검토 결과를 덮어쓰지 않아야 합니다.

5. **시각 증거는 변경 영향을 기준으로 갱신해야 합니다.** 그림을 바꾸지 않으면 SVG·Mermaid와 direct 그림 crop의 기존 증거를 보존할 수 있습니다. 원고 문장이 바뀌면 기존 전체 페이지 PNG를 수정 원고의 동일 바이트 증거로 사용할 수 없으므로, 바뀐 절의 실제 렌더와 필요한 모바일·양테마 배치를 새로 확인해야 합니다. 긴 전체 페이지의 축소본은 계속 배치 증거로만 사용합니다.

6. **준비 단위와 원고 단위의 종료 조건을 분리해야 합니다.** 준비 코드 C0/I0/M0과 로컬 체크포인트 후보 적합성은 유지할 수 있지만, 원고의 Important 2건이 해소·재검토되기 전에는 R11 PASS로 바꾸지 않습니다. 응답 후 감사·정본 저장·필요한 재판정과 재검토는 controller가 별도로 확인해야 합니다.

이 결과는 소유자 승인, `ready`, RC, M5 전체 완료, M6/M7, commit·push·배포 또는 공개 URL 성공을 승인하거나 실행한 기록이 아닙니다.
