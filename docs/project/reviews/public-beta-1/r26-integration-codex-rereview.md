**준비 코드와 이전 바이트 복원에 대한 판단**

`r26-fix-transition.mjs`는 **13개 지정 파일**을 대상으로 합니다. 24개 변경 전체를 자동 복원하거나 pin 검사하는 함수가 아닙니다.

- 입력의 전체 SHA가 지정된 `after`와 정확히 같을 때만 줄 구간을 역순으로 되돌립니다.
- 복원 후 전체 SHA가 `before`와 다르면 예외를 냅니다.
- 대상 밖 파일, 이전 바이트, 알 수 없는 변경에는 복원을 적용하지 않습니다.
- `validateR26Fix()`는 별도로 각 대상의 **현재 `after` SHA**를 요구하고, 누락과 drift를 구분합니다.

이 구조에서 **과거 바이트를 읽기용으로 복원하는 것과 현재 파일을 rollback해도 통과시키는 것은 다릅니다.** 새 테스트는 API 파일을 대표로 이전 바이트·drift 바이트가 복원 함수에서 그대로 유지되면서 현재 후보 검사에서는 거부되는지 확인합니다. 정상 후보 검사는 13개 전체를 순회합니다.

다만 부정 입력 시험이 13개 파일 각각의 모든 변형·누락을 전수 시험한 것은 아닙니다. 현재 제공된 테스트를 그 이상으로 보고하지 않습니다.

기존 R04·R13·R23·R24·R25 테스트가 R26 수정 전 스냅샷을 사용하도록 바뀐 것은 타당합니다. **과거 metadata-only 전이에서 본문이 불변이었다는 주장**을 검사하면서 현재 R26의 의미 수정을 섞지 않기 위한 조정입니다. 현재 본문이 R26 이전과 같다고 주장하는 변경이 아닙니다.

R25 완료 검사는 R26의 정확한 후보를 역사 입력으로 변환해 기존 pin을 검사합니다. 따라서 **이전 행의 완료 검사 단독으로 R26 현재 후보의 rollback 차단까지 증명해서는 안 됩니다.** 현재 후보 판정에는 `validateR26Fix()`와 이를 실행하는 테스트를 함께 사용해야 합니다. 앞서 확인한 `check:static`의 `node --test` 경로와 이번 전체 432개 통과 보고는 그 구분과 맞습니다.

R16은 역사 상수 전체를 다시 쓰지 않고 현재 validator에서 한 필드만 정정합니다. 테스트는 기존 잘못된 문자열로 되돌린 경우도 거부합니다. 최초 판정·후속 결과·다른 상태 필드를 느슨하게 허용하는 변경은 발견하지 못했습니다.

**B01의 입증 범위와 미증명 범위도 구분합니다.**

제공된 최초 실행기 코드는 stderr를 메모리에 누적하고, 특정 문자열 및 error notification을 만나면 엄격하게 실패 처리합니다. 이벤트 처리에서도 진단과 허용된 item 유형을 검사하며, 정상 수신·완료 응답·불변성 확인 뒤에만 정상 receipt를 쓰도록 돼 있습니다.

다만 두 가지 한계가 있습니다.

- 종료 보고의 진단 개수 필터는 `diag()`의 전체 필터와 완전히 같지 않습니다.
- 원 stderr 본문이 없으므로 **그 한 건의 원인·정확한 발생 시점·권한에 미친 영향을 코드만으로 복원할 수 없습니다.**

따라서 047은 계속 **returned-not-certified·BLOCKED·exit 1**입니다. Code Mode 경고와 동일 원인이라고 추정하지 않으며, 예외를 적용해 무오류로 바꾸지 않습니다.

현재 후속 판정은 047의 정상 종료를 전제로 하지 않습니다. **실제 수신 입력·PNG 연결·반환 응답·사후 불변성의 오프라인 대조, 같은 세션에서 반환된 048의 독립 판단과 exit 0 기록, 이번 Fix1의 원문·직접 근거·새 이미지 판독**을 각각의 범위에서 사용합니다. 이 연결을 확인한 뒤에도 과거 진단의 원인을 계속 추정해야만 현재 원고를 판단할 수 있는 것은 아닙니다.

원 진단이 사라졌다는 뜻이 아니라 **현재 판단이 의존하는 증거와 의존하지 않는 미확인 역사를 분리한 것**입니다.

**6. 재확인 기준**

**현재 제공된 Fix1 후보에 대해 추가 원문·이미지 보강을 요구할 사항은 없습니다.** 59개 원고·기존 68개 PNG를 다시 보내거나, 이번 수정과 무관한 화면을 재촬영할 필요도 없습니다.

향후 처리는 다음 경계를 유지해야 합니다.

1. **이번 결과의 대상은 고정된 Fix1 후보입니다.** pin이나 파일 SHA가 달라지면 변경된 문장·코드·증거 연결만 좁게 다시 확인해야 합니다. 이번 PASS를 후속 미검토 변경에 전용하지 않습니다.
2. **현재 후보 검사와 역사 복원을 함께 유지합니다.** 이전 행의 pin 검사만 통과했다고 R26 후보를 인정하지 않습니다. `validateR26Fix()`가 요구하는 현재 바이트와 관련 테스트 통과를 별도로 확인해야 합니다.
3. **기존 Minor 5건은 원래 ID로 유지합니다.** 수정하면 해당 문맥과 필요한 렌더·테스트만 재검토하고, 현행 유지라면 M0로 기록하지 않습니다.
4. **047·048 원응답과 실행 상태는 보존합니다.** 047의 진단 원인은 미확인으로 남기고, 이번 PASS를 최초 실행의 무오류 인증으로 쓰지 않습니다. 048도 당시 BLOCKED 결과 그대로입니다.
5. **controller의 사후 검증·정본 저장은 별도입니다.** 이번 응답의 실제 모델·effort·수신 입력·응답·사후 불변성과 형식이 연결됐는지 확인한 뒤 결과를 저장해야 합니다. reviewer는 그 미래 작업의 성공을 선인증하지 않습니다.
6. **controller closeout·M5 전체·ready·RC·소유자 승인·M7은 각각 별도입니다.** 같은 SHA의 최종 기술 점검, 실제 공개 환경 확인, 외부 쓰기 승인이 이번 내용 PASS로 자동 충족되지 않습니다.

**최종 반환: R26 Fix1 변경 영향 재검토 `PASS`, 현재 잔여 C0/I0/M5.** R26 신규 지적은 모두 해소됐고, 기존 비차단 Minor 5건과 명시한 증거 한계는 유지합니다. 파일 변경·커밋·push·배포·공개 URL 생성이나 상태 승격은 실행하거나 승인하지 않았습니다.
