중요한 수정 사유는 세 가지입니다.

1. **동시 요청 시험의 최종 행 수만으로 경쟁 조건 지적을 오탐으로 닫을 수 있습니다.** 실제 경쟁 구간을 만들거나 관측했는지, 사전 검사만 하는 결함 구현을 시험이 검출하는지 확인하는 조건이 빠져 있습니다.
2. **자연어 프롬프트 세 블록이 가로 스크롤을 요구합니다.** 모바일에서는 문장 앞뒤를 함께 읽기 어렵고, 권한 원고의 변경 프롬프트는 데스크톱에서도 가로 이동이 필요합니다.
3. **파괴적 작업의 사전 확인 단계에 interactive mode를 preview와 병렬로 제시합니다.** Interactive mode는 선택에 따라 실제 삭제를 수행할 수 있으므로, 승인 전 허용되는 조작 범위를 명시해야 합니다.

원고의 장점도 분명합니다. 주장·계획·변경·증거, 독립 검토·재판정·수용, 컨텍스트·스펙·하네스·루프, 승인·샌드박스·worktree의 차이를 일관되게 설명합니다. 제품 기능과 교육용 계약을 실제 서비스 성공으로 확대하지 않으며, 과거 출처 확인일을 이번 확인일로 덮어쓰지도 않았습니다.

다만 **미해결 Important 3건이 있으므로 점수가 기준을 넘더라도 PASS가 아닙니다.** 입력 완독은 충족했지만, 입력 불변성의 사후 감사·controller 재판정·필요한 수정 및 같은 reviewer의 재검토는 아직 남아 있습니다.

**R23-I01 — 동시성 지적을 오탐으로 닫는 증거 조건이 부족합니다.**

- **심각도:** Important / P1
- **위치:** `src/content/docs/11-ai-native/agent-review-and-verification.md`의 「오탐·기각·재검증 예시」 2~5번. 관련 위치는 `permissions-sandbox-worktrees.md`의 「진단 계약과 변경 계약을 분리합니다」 변경 프롬프트입니다.
- **최소 인용:** “두 요청을 동시에 시작하는 재현 테스트”, “최종 활성 행이 1건이면 해당 지적은 현재 구현에 대한 `false positive`로 기각합니다.”
- **관찰·근거:** 두 요청을 함께 시작했더라도 애플리케이션 또는 DB가 우연히 순차 처리하면 사전 조회만 있는 결함 구현도 활성 행 1건을 만들 수 있습니다. 원고는 mock과 실제 제약의 차이는 경고하지만, **실제 경쟁 구간의 통제·관측**을 기각 조건에 넣지 않았습니다. 제공된 사례 브리프와 캡스톤은 시작 장벽만으로 교차 실행을 입증하지 않으며 실제 DB의 독립 연결과 경쟁 구간 증거가 필요하다고 더 엄격하게 설명합니다.
- **영향:** 독자가 재현되지 않은 한 번의 결과를 결함 부재의 증거로 받아들여 유효한 동시성 finding을 닫을 수 있습니다. 이 장이 가르치는 “직접 증거로 재판정한다”는 핵심과 충돌합니다.
- **적용 기준:** C03·C04·C06, 판단 기준·실패 모드·실전 연결.
- **최소 수정:** 기각 조건에 실제 데이터 경계, 독립 요청/연결, 선택한 보호 전략에 맞는 경쟁 구간 통제 또는 관측, 성공·거절·부분 변경과 최종 행의 대조를 추가합니다. 사전 조회만 하는 결함이 시험에서 드러나는지도 확인하게 합니다. 이 조건을 입증하지 못하면 `false positive` 대신 **“현재 시험에서 미재현·동시성 검증 미완료”**로 남깁니다. 권한 원고의 짧은 프롬프트도 같은 조건을 직접 적거나 해당 검증 계약을 명시적으로 참조해야 합니다.
- **재확인:** 시험 요청이 순차 실행되어도 통과하는 사례를 새 문장이 오탐 기각 근거로 허용하지 않는지 확인합니다. 실제 DB 시험은 이번 문서 검토에서 실행할 일이 아니며, 교육 계약의 정확성과 인접 문맥의 일치를 재검토하면 됩니다.

**R23-M02 — 외부 효과 표에 로컬 commit이 구분 없이 포함됩니다.**

- **심각도:** Minor / P2
- **위치:** `permissions-sandbox-worktrees.md`의 「권한을 열 개의 질문으로 나눕니다」 표, `external effect` 행.
- **최소 인용:** “commit·push·PR·message·deploy·DNS·결제·운영 변경 중 무엇인가요?”
- **관찰·근거:** 같은 장 뒤에서는 로컬 commit과 remote push·PR·deploy를 정확히 구분합니다. 표의 예시는 그 구분을 생략합니다. Git hook을 통해 외부 효과가 생길 수 있다는 본문 설명과도 별도로 구분해야 합니다.
- **영향:** 로컬 이력 기록 자체와, hook 또는 원격 작업이 일으키는 외부 효과를 같은 범주로 이해할 수 있습니다.
- **적용 기준:** C04·C06.
- **최소 수정:** 로컬 commit은 Git 상태 변경으로 분류하고, 외부 효과 행에는 push·PR·메시지·배포 등을 둡니다. 필요하면 “commit에 연결된 hook의 외부 호출은 별도 효과”라고 좁게 덧붙입니다.
- **재확인:** 표·후속 설명·에이전트 출력 용어집의 commit 정의가 일치하는지 확인합니다.

**R23-M03 — 판단에 필요한 일부 용어가 쉬운 설명보다 먼저 등장합니다.**

- **심각도:** Minor / P2
- **위치:** 세 원고의 첫 정의·비유·초기 표와 실패·복구 설명.

- **관찰·근거:** 관련 용어집과 인접 장에 설명이 있는 용어도 있지만 해당 위치에서 뜻을 바로 연결하기 어렵습니다. 특히 RAG·grader·probe는 이 세 원고만 따라 읽는 독자에게 설명 부담을 남깁니다.

- **재확인:** 추가 설명이 기존 용어집의 정의·범위와 충돌하지 않고 본문을 불필요하게 늘리지 않는지 확인합니다.

## 6. 재확인 기준

1. **이 최초 결과를 원고 수정 전에 보존합니다.** Controller는 입력·모델·권한·형식과 사후 해시를 확인한 뒤 원래 결과 정본에 저장해야 합니다. 이 응답의 판정·건수·점수를 수정 결과로 덮어쓰지 않습니다. 필요한 별도 커밋은 controller의 절차이며 제가 실행한 작업이 아닙니다.

2. **각 finding을 독립적으로 재판정합니다.** R23-I01~I03, R23-M01~M03, 준비 자료의 R23-P-M01에 대해 수용·부분 수용·기각과 근거를 남깁니다. 준비 자료의 Minor를 원고의 Important 해소로 계산하지 않습니다.

3. **내용 수정은 지적된 계약만 좁게 보완합니다.**
   - I01: 실제 경쟁 구간 증거, 결함 검출 능력, 미재현과 오탐의 구분.
   - I03: interactive mode의 목록 조회와 실제 적용 사이 승인 경계.
   - M01~M03: 제목 계층, 로컬 commit 분류, 첫 용어 설명.
   - 과거 출처 날짜·감사 이력·초안 상태는 보존합니다.

4. **I02는 표시 변경과 실제 렌더를 함께 확인합니다.** 세 자연어 블록의 내용·의미상 개행을 보존한 채 줄바꿈을 적용하고 새 빌드를 수행합니다. 영향받는 두 경로의 1440px·390px 양 테마에서 문장 전체와 내부 가로 넘침을 확인합니다. 공통 CSS를 바꾸면 영향을 받는 다른 소비 문맥도 검증 범위에 포함해야 합니다.

5. **자동 검사는 실제 변경과 연결합니다.** 콘텐츠·참조·필요한 회귀·빌드 및 빌드 출력 검증의 명령·대상 상태·종료 코드·실행 수·건너뜀을 제공합니다. 이전 R22 빌드를 수정된 원고의 새 렌더 증거로 사용하지 않습니다. 본문이 바뀌면 해당 콘텐츠 지도와 검사 기준도 정해진 절차에 따라 맞춥니다.

6. **후속 입력은 새 해시와 좁은 영향 범위로 고정합니다.** 수정 파일 전체, 전후 diff, 새 개별·결합 해시, controller 재판정, 필요한 인접 문맥과 새 실제 PNG를 같은 reviewer에게 제공합니다. 변경하지 않은 그림과 다른 원고의 유효 증거는 변경 영향이 없다는 근거와 함께 유지할 수 있습니다.

7. **최종 상태는 별도로 판단합니다.** 미해결 Important가 해소되고 필요한 재검토·사후 감사가 끝나기 전까지 R23 통과로 전환하지 않습니다. 이후 R23이 통과하더라도 그것만으로 소유자 승인·`ready`·RC·M5 전체·M6/M7·push·배포·공개 URL 성공이 성립하지 않습니다.
