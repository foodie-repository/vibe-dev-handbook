| 88, 107 | 오른쪽 이동 후 롤포워드가 필요한 신호가 읽힙니다. | 첫 열 일부는 왼쪽으로 사라집니다. |
| 89, 108 | AI 요청의 여덟 항목과 첫·마지막 문장 앞부분이 보입니다. | 마지막 독립 수용 지시가 오른쪽으로 이어집니다. |
| 90, 109 | 마지막 문장의 독립 승인·거절·안전한 통합 부분이 이어집니다. | 목록 대부분이 화면 밖입니다. |
| 91, 110 | “반례도 제시해 주세요”라는 마지막 지시가 읽힙니다. | 세 위치를 합쳐 전체 요청을 판독했습니다. |

판독 총수는 **SDLC 46개 + CI/CD 26개 + 점진적 전달 38개 = 110개**입니다. controller의 판독은 대표 확장 전 13개와 이후 2개를 합친 15개라는 별도 기록으로 유지합니다.

SVG와 Mermaid는 **6노드·7연결, 실선 5개와 귀환 2개, 초점 2묶음**으로 일치합니다. 발견=문제 이해, 배포·운영의 묶음, 학습=피드백이라는 앞뒤 설명과 alt도 일치합니다. 실제 이미지에서 양 테마의 주 흐름·점선·A/B·화살촉을 식별할 수 있었습니다. 다만 이 판독은 1440·390폭의 제공 이미지에 한정되며, SVG의 접근성 속성이 실제 보조 기술에 어떻게 전달되는지는 확인하지 않았습니다.

**2. 판정과 건수**

**원고 판정: NEEDS CHANGES — Critical 0건, Important 5건, Minor 5건.**

| 구분 | Critical | Important | Minor | 판정 |
|---|---:|---:|---:|---|
| 세 원고와 직접 연결된 시각·문맥 문제 | 0 | 5 | 5 | NEEDS CHANGES |
| 입력 준비 검사 코드·테스트·캡처 작업의 별도 검토 | 0 | 0 | 0 | 제공 범위에서 수정이 필요한 결함을 발견하지 않음 |
| 필수 입력 미독·누락 | — | — | — | 발견하지 않음 |
| 사후 전달·불변성 감사 | — | — | — | 아직 대기, 이번 응답에서 완료 처리하지 않음 |

원고의 중심 설명은 상당 부분 일관됩니다. 리뷰 활동과 승인 결정, CI 규율과 자동 검사 서비스, 지속적 전달과 지속적 배포, 플래그와 서버 인가, 코드 롤백과 데이터·외부 부작용 복구를 구분합니다. SDLC의 여덟 단계가 편집 지도이고 그림은 여섯 묶음이라는 설명도 명확합니다.

그러나 **독립 수용을 설명하는 대표 사례가 후속 조각의 복구 기능에 의존하고, 고정 사례의 취소 상태 전이와 삭제 표현이 충돌**합니다. 또한 자동 검사 표시의 의미와 운영 검증의 실행 권한을 더 정확하게 제한해야 합니다. 세 원고에서 공통으로 관찰된 자연어 가로 스크롤은 핵심 요청과 수용 기준을 읽는 데 실질적인 부담을 줍니다.

준비 검사기·테스트는 원고와 분리해 평가했습니다. 고정 manifest의 교체, 텍스트·문맥 변경, 로컬 PNG 누락·손상과 provenance 변경을 거부하는 방어가 있으며, 반환값은 `reviewComplete: false`, `releaseReady: false`를 유지합니다. 기본 실행에서 로컬 PNG를 검사하지 않는 경계와 로컬 증거 실행을 구분하고, 로컬 이미지가 없는 환경에서 관련 테스트가 건너뛰어질 수 있다는 점도 코드에 드러납니다. 이번 제공 로그에서는 실제로 건너뜀 0건입니다.

이 별도 검토는 준비 체크포인트의 근거가 될 수 있지만, reviewer가 커밋을 승인·실행한 것이 아니며 원고 PASS나 공개 가능 판정을 뜻하지 않습니다.

**R19-I02 — Important/P1 — 참가 신청 조각이 다음 조각의 복구 경로에 의존하지만 독립 수용·공개 조건이 명시되지 않습니다.**

- **위치:** `src/content/docs/07-workflow-methods/incremental-delivery.md` — `좋은 수직 조각의 다섯 조건`, `반복 사례: 모임 참가 기능을 다섯 조각으로 나누기`의 조각 2·3·5.
- **최소 인용:** “응답을 잃어 결과가 불명확하면 참가 상태를 다시 조회해 판정할 수 있다.” / “조각 3. 자신의 참가 상태 조회” / “조각 5. 운영 신호와 제한 공개”.
- **관찰 근거:** 앞에서는 결과 불명 복구를 참가 조각의 수용 기준으로 요구합니다. 그러나 대표 분해에서는 참가 신청을 조각 2로 먼저 두고, 그 복구에 필요한 자기 조회를 조각 3으로 둡니다. 조각 2가 기존 조회를 재사용하는지, 조각 3까지 공개를 보류하는지, 최소 조회를 함께 구현하는지 설명하지 않습니다. 기본 관측·중단 조건과 조각 5의 확대된 제한 공개도 구분되지 않습니다.
- **영향·규칙:** 독자가 정상 쓰기를 먼저 완료·공개한 뒤 복구와 관측을 붙이는 분해를 좋은 예로 받아들일 수 있습니다. “이 순서는 표준이 아니다”라는 문구만으로 선행 의존성은 해소되지 않습니다. C02·C03·C04·C06에 해당합니다.
- **최소 수정:** 조각 2에 최소 자기 조회·결과 불명 유지·재시도 보류와 필요한 관측을 포함하거나, 이미 검증된 선행 기능을 명시합니다. 조각 3은 조회 UX 확장으로 구분할 수 있습니다. 별도 구현을 유지한다면 조각 2의 수용·공개 보류 조건과 조각 3의 의존 관계를 명시합니다. 조각 5는 기본 안전장치의 최초 도입이 아니라 공개 범위 확대와 운영 인수로 설명합니다.
- **재확인:** 조각 2만 완료된 상태에서 응답 유실·조회 실패·중복 요청·정원 경쟁을 어떻게 판정하는지 설명할 수 있어야 합니다. W-03 브리프와 인접 UI 원고의 “조회 실패 시 unknown 유지, 새 쓰기 보류” 계약에 맞아야 합니다.

**R19-I03 — Important/P1 — 자기 취소가 상태 전이인 고정 사례에서 삭제된 관계를 전제로 설명합니다.**

- **위치:** `src/content/docs/07-workflow-methods/incremental-delivery.md` — `조각 4. 자기 참가 취소`.
- **최소 인용:** “코드 롤백으로 삭제된 관계를 자동 복원하지 않습니다.”
- **관찰 근거:** 고정 사례 브리프는 자기 취소를 `confirmed → cancelled`로 정의하고, 반복 취소는 추가 인원 감소·취소 이력을 만들지 않는다고 명시합니다. 인접 UI 원고도 모임 상태와 참가 관계의 상태를 함께 읽습니다. 현재 대표 사례 문장은 취소를 행 삭제로 읽게 만듭니다.
- **영향·규칙:** 이력 보존, 반복 취소의 안전성, 재참가와 운영 복구의 기준이 달라집니다. 일반적인 삭제 복구 경고 자체는 맞지만 현재 사례의 데이터 계약과는 일치하지 않습니다. C03·C04·C06에 해당합니다.
- **최소 수정:** “취소로 바뀐 참가 상태를 코드 롤백만으로 다시 confirmed로 만들지 않는다”는 방향으로 수정하고, 행·이력 보존과 재참가의 업무 조건을 짧게 연결합니다.
- **재확인:** 타인 취소 거절, 반복 취소의 추가 부작용 0, 취소 상태 보존, 허용된 재참가 조건이 브리프와 일치해야 합니다. 교육 원고 수정만으로 실제 DB 시험을 했다고 기록하지 않습니다.

**R19-I04 — Important/P1 — 초록 상태 표시를 실제 검사 실행·통과의 증거로 단정하는 문장이 남아 있습니다.**

- **위치:** `src/content/docs/07-workflow-methods/code-review-ci-cd.md` — `CI는 초록 체크를 만드는 서비스가 아닙니다`.
- **최소 인용:** “초록 체크는 그 커밋이 그 환경에서 그 검사를 통과했다는 좁은 증거입니다.”
- **관찰 근거:** 제공된 R19-S08은 GitHub 필수 상태 검사 조건에 `successful, skipped, or neutral`이 포함됨을 명시합니다. 원고는 앞에서 실제 실행 수·로그를 요구하지만, 위 문장은 상태 표시 자체를 실제 검사 통과로 해석하게 합니다.
- **영향·규칙:** 실행되지 않은 검사도 병합 조건을 만족할 수 있는 제품 경계를 독자가 놓칠 수 있습니다. 이는 원고의 핵심인 표시와 증거의 구분에 직접 영향을 줍니다. C04·C05·C09·C10에 해당합니다.
- **최소 수정:** 실제 실행 기록이 확인된 검사 통과와 서비스의 상태 표시·병합 허용을 구분합니다. GitHub에서는 skipped·neutral이 필수 상태 조건을 충족할 수 있으므로 실제 실행 수, 건너뜀, 조건식과 로그를 확인한다는 짧은 예외를 추가합니다.
- **재확인:** 실행 0건·조건부 건너뜀·neutral 결과를 실제 테스트 통과로 보고하지 않아야 합니다. 플랜·역할·bypass의 제품 설명을 실제 원격 저장소 설정 확인으로 확대하지 않아야 합니다.

**6. 재확인 기준**

1. **이 최초 결과를 수정 전에 보존합니다.** controller는 정본 저장·응답 형식·전달 완전성·사후 입력 불변성 감사를 수행하고, 계약에 따른 최초 결과 보존 커밋을 원고 수정과 분리해야 합니다. 이번 reviewer는 저장이나 커밋을 수행하지 않았으며, 아직 완료됐다고 보고하지 않습니다.

2. **10개 finding을 각각 재판정합니다.** 수용·부분 수용·기각과 그 근거, 수정 위치 또는 비반영 이유를 안정 ID에 연결합니다. 동일 원인의 자연어 가로 스크롤은 I01로 통합하되 세 원고의 모든 해당 위치를 추적합니다.

3. **원고 수정은 좁게 수행합니다.** 참가 신청의 최소 복구·관측 의존성, 자기 취소 상태 전이, 실제 검사 실행과 상태 표시, 운영 smoke 권한, 출처 연도, 검증 용어, 커밋·아티팩트 표현과 알림 비목표만 필요한 범위에서 수정합니다. 여덟 편집 단계와 여섯 그림 묶음의 관계를 전면 재설계할 필요는 없습니다.

4. **변경 전후 바이트와 증거를 새로 연결합니다.** 수정한 원고·필요한 문맥·출처·렌더 증거의 개별 및 결합 SHA-256, 정확한 diff, 재판정 기록을 제공합니다. 이전 결과와 해시를 덮어쓰지 않습니다.

5. **의미와 화면에 맞는 검증을 수행합니다.** 관련 정적·콘텐츠·참조 검사와 변경 후 빌드 결과를 구분해 제공하고, 자연어 wrap 수정은 세 경로의 데스크톱·모바일 양 테마에서 실제 이미지로 확인합니다. 긴 문장 끝까지 가로 이동 없이 읽히는지, 원문·목록·복사 대상 텍스트와 ASCII 도식이 보존됐는지가 핵심입니다. 미실행 접근성 범위는 계속 별도 상태로 둡니다.

6. **같은 R19 reviewer의 후속 검토로 이어갑니다.** 이 대화의 고정 입력과 finding ID를 기준으로 수정 영향 범위와 새 증거를 다시 읽겠습니다. 세션의 실제 저장·복구 성공은 controller가 확인해야 하며, R02 승계 예외는 적용하지 않습니다. 최초 입력에서 이미 읽은 비변경 범위는 이유 없이 재검토하지 않습니다.
