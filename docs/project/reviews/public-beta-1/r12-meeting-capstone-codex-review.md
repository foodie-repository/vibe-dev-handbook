좋은 부분도 명확합니다. W-02의 `host_id`와 W-03의 `participant_id`를 인증 주체에서 결정하고, 참가 현황 조회 전에 소유권을 확인하며, 거절 시 데이터와 응답의 비공개 필드를 함께 검증하도록 한 점은 적절합니다. W-04는 단순한 사전 조회나 트랜잭션 선언만으로 정원 경쟁이 해결되지 않는다고 설명합니다. W-05와 추적 표는 로컬 commit, 아티팩트 생성, 환경 배치, 공개 흐름, 격리 복원과 운영 인수를 구분합니다. 이 구조를 유지한 좁은 수정으로 해결할 수 있습니다.

- **관찰 근거:** 명시된 읽기 API는 공개 모임 조회와 주최자 전용 참가 현황 조회입니다. 공개 조회는 참가자 식별자를 제외하고, 참가 현황 조회는 일반 참가자에게 거절합니다. 따라서 참가자가 응답 유실 뒤 자신의 `confirmed`·`cancelled`·미신청 상태를 어떤 허용된 읽기 계약으로 구분하는지 현재 캡스톤만으로 결정할 수 없습니다. 인접 API 장도 존재하지 않는 조회 경로를 추측하지 말라고 명시합니다.
- **영향·규칙:** 복구 오라클의 데이터는 언급하지만 실제 사용자에게 허용된 확인 경계가 비어 있습니다. AI가 주최자 전용 조회를 재사용하거나 공개 응답에 개인 참가 정보를 넣는 식으로 빈칸을 채울 수 있습니다. C02·C04·C06에 해당합니다.
- **최소 수정:** 교육용 설계 계약으로 자기 참가 상태를 읽는 방법 하나를 명시합니다. 메서드·경로를 정하거나 별도 상태 확인 계약을 두되, 인증 주체 결정, 대상 모임, 자기 관계만 반환하는 범위, 미신청·취소·확정의 구분, 조회 실패 시 결과 불명 유지와 재시도 조건을 포함합니다. 실제 구현됐다는 표현은 사용하지 않습니다.
- **재확인:** A의 확정 응답 유실 뒤 A가 자기 상태를 확인할 수 있고, B의 관계나 전체 참가자 목록은 얻지 못하는지 계약과 부정 테스트 오라클로 대조합니다. 조회도 실패한 경우와 이미 처리된 POST를 다시 보낸 경우를 구분합니다.

**R12-I03 — Important/P1: 상태 이름은 있지만 허용 전이와 모임 취소의 데이터 효과가 충분히 정의되지 않았습니다.**

- **위치·최소 인용:** 원고 「상태와 데이터 관계」의 “`closed`는 주최자가 모집을 마쳤거나 정원 정책상 더 받지 않는 상태”, W-02의 “수정·취소·마감”, W-03 참가·취소와 W-04 상태 판정; 사례 브리프 「상태 모델」.
- **관찰 근거:** 정원 도달을 `event.status = closed`로 저장할지, `open` 상태에서 현재 인원으로 참가만 거절할지 결정되지 않았습니다. 정원 도달로 닫힌 뒤 참가 취소나 정원 증가가 일어나면 자동 재개하는지, 수동 마감을 유지하는지도 알 수 없습니다. 모임 자체가 `cancelled`로 바뀔 때 기존 `confirmed` 참가를 유지할지 함께 취소할지, 참가자가 마감·모임 취소 뒤 자기 참가를 취소할 수 있는지도 명시되지 않았습니다.
- **영향·규칙:** 같은 상태 이름으로 서로 다른 구현·UI·집계·복구 결과가 나올 수 있습니다. 허용 문자열 검사만으로 업무 상태 계약을 완성했다고 오해하게 합니다. C02·C03·C04의 상태·실패·오라클 일관성 문제입니다.
- **최소 수정:** 작은 상태 전이 표나 짧은 규칙으로 시작 상태, 행위 주체, 허용 전이, 재개 허용 여부와 모임 취소 시 참가 데이터 효과를 정합니다. 재개가 비목표라면 명시적으로 거절하도록 정해도 됩니다. 자동 정원 마감과 수동 마감을 구분할 필요가 없다면 정원 가득 참을 별도 저장 상태로 만들지 않는 단순한 정책도 가능합니다.
- **재확인:** 만석 뒤 자기 취소, 수동 마감 뒤 빈자리 발생, 정원 증가, 취소된 모임 수정·재참가, 모임 취소와 참가의 경쟁에서 허용 최종 상태가 하나의 계약으로 설명되어야 합니다. 모임 취소 때 기존 참가 행을 반드시 모두 취소하라고 강제하는 finding은 아닙니다.

**R12-I04 — Important/P1: 연습 문제의 ‘성공·실패 응답 수’는 응답 유실 상황의 판정 기준으로 불완전합니다.**

- **위치·최소 인용:** 원고 「짧은 연습」의 “A의 브라우저는 응답을 받지 못했으며 B는 정원 마감 응답”, 3번 “최종 `confirmed` 수, 성공·실패 응답 수, 활성 중복 수로 테스트 오라클”.
- **관찰 근거:** 이 상황에서 클라이언트가 받은 성공 응답 수와 서버에서 확정한 참가 수는 같지 않습니다. A의 결과는 응답만으로 알 수 없으며, B의 정원 마감 응답도 권위 상태 재조회 없이 A의 확정을 직접 입증하지 않습니다. W-04의 전달 정상 조건에서 사용하는 ‘성공 1건·거절 1건’을 이 연습의 관측 응답 수에 그대로 적용할 수 없습니다.
- **영향·규칙:** 앞에서 설명한 `commit`과 응답 유실의 구분을 마지막 학습 평가에서 다시 흐릴 수 있습니다. C02·C04의 복구 오라클과 C08의 정확한 표현에 해당합니다.
- **최소 수정:** 서버의 확정·거절 건수, 클라이언트가 실제로 수신한 응답, 전달 실패·결과 불명을 별도로 적게 합니다. 최종 인원과 A 상태는 재조회 전에는 미확인이라고 답할 수 있어야 합니다. 통제된 시험에서 A의 `commit` 후 응답 유실을 의도한 것이라면 그 주입 조건을 명시합니다.
- **재확인:** 모범 판정이 ‘A 확정 1건, A가 받은 성공 응답 0건, B의 거절 응답 1건, A의 전달 실패 1건’을 서로 다른 항목으로 설명할 수 있어야 합니다. 원고에 없는 고정 조건을 가정해 무조건 최종 3명이라고 단정해서는 안 됩니다.

**R12-I05 — Important/P1: 동시성·원자성 시험의 실행 조건과 증거 범위가 더 구체적이어야 합니다.**

- **위치·최소 인용:** 원고 W-04 직접 증거의 “같은 시작 장벽”, “둘 중 정확히 하나만 `commit`”, 추적 표의 “결정적 경쟁 테스트”, 수용 기준의 “중간 실패는 전체 `rollback`”.
- **관찰 근거:** 같은 장벽에서 요청을 시작해도 실제 서버·DB의 읽기와 쓰기가 겹쳤는지는 보장되지 않습니다. 잘못된 사전 조회 구현도 우연히 순차 실행되면 통과할 수 있습니다. 또한 제시된 시험은 주로 마지막 자리 경쟁과 정원 축소 경쟁이며, 저장 도중 실패를 주입해 해당 트랜잭션의 부분 변경을 확인하는 시험은 직접 증거에 구체화되어 있지 않습니다. ‘정확히 한 건 확정’의 시험도 별도 저장 장애·외부 변경이 없는 조건을 명시해야 합니다.
- **영향·규칙:** 결과 숫자가 맞는 한 번의 실행을 동시성 전략과 원자성 전체의 증거로 과대평가할 수 있습니다. 인접 API 장은 두 작업 외 변경과 별도 장애가 없는 조건, 다른 요청의 정상 확정 결과 보존을 더 분명히 설명합니다. C02·C04·C12에 해당합니다.
- **최소 수정:** 경쟁 시험이 두 독립 처리 경로와 실제 데이터 경계를 사용한다는 점, 선택한 전략에 맞춰 경쟁 구간을 통제하거나 관측하는 방법을 적습니다. 특정 잠금 기법을 강제할 필요는 없습니다. 별도 장애가 없는 경쟁 시험과 저장 중 실패 시험을 나누고, 후자에는 해당 요청의 부분 변경 0건과 다른 정상 확정 변경 유지라는 오라클을 붙입니다. 실제 교차 실행을 통제하지 않는다면 ‘결정적’이라는 표현도 좁혀야 합니다.
- **재확인:** 잘못된 사전 조회만 사용하는 구현이 왜 이 시험에서 검출되는지 설명할 수 있어야 합니다. 경쟁 성공·업무 거절, 직렬화 실패와 유한 재시도 소진, 저장 중 실패, `commit` 뒤 응답 유실을 같은 실패로 합치지 않아야 합니다.

**R12-M01 — Minor/P2: 이미 취소된 참가의 반복 DELETE를 무조건 실패 사례로 표현하면 멱등성의 의미가 흐려집니다.**

- **위치·최소 인용:** 원고 W-03 실패 상태의 “이미 취소된 참가를 성공처럼 다시 취소합니다.”
- **근거·영향:** RFC 9110 §9.2.2에서 멱등성은 의도한 효과에 관한 성질이며 응답이 항상 같다는 뜻이 아닙니다. 반복 DELETE에 안전한 성공 응답을 주거나 이미 취소됨을 별도 응답으로 알리는 계약 모두 가능합니다. 현재 문구도 ‘새 취소가 발생한 것처럼 거짓 보고하지 않는다’는 뜻으로 읽을 수 있어 명백한 HTTP 위반으로 판단하지는 않습니다. 다만 초보자는 반복 성공 응답 자체를 오류라고 배울 수 있습니다.
- **최소 수정:** 이번 사례가 선택한 반복 취소 응답 정책을 밝히고, 핵심은 추가 상태 변경·중복 부작용이 없다는 점이라고 설명합니다.
- **재확인:** 첫 취소, 같은 취소 재시도, 취소 응답 유실 뒤 재조회에서 상태·확정 인원·이력과 응답 의미가 일치해야 합니다.

**R12-M02 — Minor/P2: 핵심 검증 용어의 첫 등장에 짧은 풀이가 부족합니다.**

- **위치·최소 인용:** 원고의 `fixture`, “테스트 오라클”, “같은 시작 장벽”, “데이터 불변식”, `commit`·`rollback`.
- **근거·영향:** 제공된 용어집과 인접 장에는 관련 정의가 있지만, 이 원고에서는 수직 기능 조각·인증·인가·운영 인수와 달리 검증 용어 일부가 설명 없이 사용됩니다. 특히 DB `commit`과 Git `commit`의 구분은 뒤에서 나오므로 검색으로 들어온 독자는 앞부분에서 혼동할 수 있습니다. C01·C04·C08의 국소 설명 문제입니다.
- **최소 수정:** 첫 사용 지점에 오라클은 ‘실제 결과를 맞다고 판정할 기준’, fixture는 ‘시험을 위해 준비한 가상 데이터와 상태’, 시작 장벽은 ‘여러 시험 요청의 출발을 맞추는 장치’처럼 한 문장 풀이를 붙입니다. DB 확정과 Git 이력 기록도 첫 관련 위치에서 구분합니다.
- **재확인:** 새 용어집이나 긴 이론 절을 추가하지 않고, 독자가 W-04의 시험 조건과 결과를 자기 말로 설명할 수 있는지 확인합니다.

**R12-M03 — Minor/P2: W-05의 ‘일반 백업 제외’ 문구는 보호된 데이터 백업과 비밀 보관을 구분해야 합니다.**

- **위치·최소 인용:** 원고 추적 표 W-05의 “비밀·토큰·개인정보를 소스·브라우저·로그·일반 백업에 넣지 않습니다.”
- **근거·영향:** ‘일반 백업’을 통제되지 않은 임의 복사본으로 읽으면 적절한 제한입니다. 그러나 정의가 없어 개인정보가 포함된 업무 데이터를 승인된 DB 백업에서도 모두 제외해야 한다는 뜻으로 읽힐 수 있습니다. 그러면 참가 관계·소유권의 복원 요구와 충돌합니다. 인접 운영 장은 보호된 데이터 백업, 재발급 가능한 자격과 과거 암호문을 해독할 키의 복구 체계를 구분합니다.
- **최소 수정:** 예제·소스·브라우저·로그에 실제 개인정보와 비밀을 넣지 않는 규칙과, 실제 운영에서 필요한 데이터는 승인된 접근 통제·암호화·보존 정책 아래 백업하는 규칙을 분리합니다. 비밀과 복호화 키는 별도 보호·복구 체계에 연결합니다.
- **재확인:** 교육용 가상 데이터만 사용하는 현재 범위를 유지하면서도, 운영 인수 설명이 필요한 업무 데이터나 과거 백업 해독 재료를 누락하라는 지침으로 읽히지 않아야 합니다.
