# 웹앱·주식 분석 이중 사례 체계 설계 명세

## 1. 결정 상태

- 상태: 승인됨·구현 대기
- 승인일: 2026-08-07
- 적용 대상: 공개 학습 경로, 핵심 장의 반복 사례, 12부 사례와 캡스톤, 관련 조사·검토·문맥 문서
- 현재 상태와의 경계: 이 명세는 목표 사례 체계를 정의하지만 공개 문서와 기존 `review` 증거를 즉시 변경하지 않습니다. 구현 계획과 파일별 영향 감사를 거쳐 한 독립 작업 단위씩 전환합니다.

## 2. 결정 요약

핸드북은 일반적인 소프트웨어 개발을 설명하는 **소규모 모임 일정·참가 신청 웹앱**을 기본 반복 사례로 사용하고, 데이터 분석에서 판단 기준이 달라지는 지점을 설명하는 **공개 주가 데이터 분석 대시보드**를 보조 반복 사례로 사용합니다. 12부에서는 두 사례를 각각 요구사항부터 배포·운영 인수까지 연결하는 독립 캡스톤으로 제공합니다.

모든 장에 두 사례를 같은 분량으로 반복하지 않습니다. 개념 차이가 독자의 판단을 실제로 개선할 때만 두 사례를 비교하며, 각 장에서 하나의 사례만으로 학습 목표를 충분히 달성할 수 있으면 더 적합한 사례 하나를 사용합니다.

## 3. 배경과 해결할 문제

현재 정보 구조에는 `첫 풀스택 프로젝트`와 `데이터 분석가의 대시보드 사례`가 모두 있지만, 전자는 약 2,680자의 `draft`이고 후자는 약 23,947자의 `review`여서 깊이와 노출이 크게 다릅니다. 공식 Build Track 설명과 여러 핵심 장도 공개 반도체 데이터 대시보드를 반복 사례로 사용하므로, 공개 독자는 핸드북 전체를 데이터 분석가 또는 반도체 도메인 중심 자료로 받아들일 수 있습니다.

핸드북의 기본 독자는 비개발자 출신 바이브 코더이며, 이들이 일반적으로 만들려는 결과에는 웹앱이 포함됩니다. 동시에 데이터 분석가·PM·도메인 전문가도 핵심 독자이므로 분석 작업의 데이터 품질·재현성·해석 책임을 개발 사례에 묻히게 해서는 안 됩니다. 두 독자군을 모두 지원하되 원고를 기계적으로 두 배로 늘리지 않는 사례 체계가 필요합니다.

## 4. 목표와 비목표

### 목표

- 웹앱 개발에서 프런트엔드·백엔드·API·데이터베이스·인증·테스트·Git·배포·운영이 어떻게 연결되는지 하나의 익숙한 사례로 설명합니다.
- 데이터 분석에서 원천·스키마·품질·재현성·해석 한계·대시보드 전달이 어떻게 연결되는지 관심도가 높은 주식 데이터 사례로 설명합니다.
- 같은 용어가 개발 제품과 분석 제품에서 어떤 증거와 실패 위험으로 달라지는지 필요한 지점에서 비교합니다.
- 공개 배포 시 특정 산업 종사자나 데이터 분석가만을 위한 핸드북처럼 보이지 않게 합니다.
- 기존 검토 증거와 현재 공개 상태를 훼손하지 않고 파일별 영향에 따라 다시 검토할 범위를 정합니다.
- 특정 도구가 바뀌어도 남는 아키텍처·프레임워크 역할·개발 절차·사고법·용어와 방법론을 학습의 정본으로 유지합니다.
- 순서대로 완주하는 독자와 검색으로 필요한 개념·용어·사례만 찾는 독자가 모두 독립적으로 이해할 수 있는 진입점을 제공합니다.

### 비목표

- 모든 장에 두 개의 장문 사례를 의무적으로 추가하지 않습니다.
- 주식 투자법, 종목 추천, 수익률 보장, 자동매매 또는 실시간 시세 서비스를 가르치지 않습니다.
- 캡스톤을 실제 상용 서비스 전체 구현 튜토리얼이나 특정 프레임워크 강좌로 만들지 않습니다.
- Supabase·Vercel·Codex Sites·Claude Code·Codex 같은 현재 제품의 버튼·화면·프롬프트 사용법을 핵심 학습 목표로 삼지 않습니다.
- 사례 전환을 이유로 현재 정보 구조의 13개 학습 영역, Astro Starlight, 배포 구조 또는 콘텐츠 상태 모델을 바꾸지 않습니다.
- 과거 독립 검토 기록을 새 사례에 맞게 소급 수정하지 않습니다.

## 5. 사례 A: 소규모 모임 일정·참가 신청 웹앱

### 사례 목적

주최자가 일정·정원·설명을 정해 모임을 만들고 공개 링크를 공유하면, 참가자가 내용을 확인해 참가하거나 취소하고 주최자는 참가 현황을 확인해 모집을 마감하는 작은 웹앱으로 일반적인 제품 개발 흐름을 설명합니다. 특정 산업 지식 없이도 사용자 역할, 읽기와 쓰기, 인증과 인가, 상태 전이, 동시 요청, 실패, 배포와 운영 책임을 이해할 수 있어야 합니다.

### 수직 기능 조각

1. **W-01 공개 모임 조회**: 제목·설명·일정·정원·모집 상태를 공개 링크에서 확인하고 로딩·빈 결과·취소·오류 상태를 구분합니다.
2. **W-02 주최자 생성과 소유권**: 인증된 사용자가 모임을 만들고 자신이 만든 모임만 수정·취소하도록 주체·대상·행동의 인가를 연결합니다.
3. **W-03 참가와 취소**: 인증된 참가자가 한 모임에 한 번만 참가하고 자신의 참가만 취소하도록 API 계약·관계·고유성 제약을 연결합니다.
4. **W-04 정원·마감과 동시성**: 모집 중인 모임만 참가를 받고 마지막 한 자리에 동시에 들어온 요청이 정원을 넘지 않도록 업무 규칙·트랜잭션·충돌 응답을 연결합니다.
5. **W-05 배포와 운영 인수**: 비밀·환경 설정·운영 데이터베이스·로그·백업·복원·공개 사용자 흐름 확인을 연결합니다.

### 첫 범위의 경계

- 첫 수직 조각은 공개 모임 한 건의 조회로 제한하고, 쓰기와 소유권 위험을 다루는 다음 조각부터 인증을 연결합니다.
- 첫 완주 범위에는 모임 생성·공개 조회·참가·취소·정원·모집 마감·주최자 권한만 포함합니다.
- 결제·환불·채팅·댓글·알림·지도·캘린더 연동·반복 모임·대기 명단·추천·공개 검색·파일 업로드와 운영자 신고 시스템은 포함하지 않습니다.
- 마이크로서비스·메시지 큐·별도 캐시는 실제 요구가 입증되기 전에는 추가하지 않습니다.
- 참가자 개인정보는 학습에 필요한 최소 범위로 제한하고 예시·fixture·로그에는 실제 개인정보를 사용하지 않습니다.
- 모임 취소와 데이터 보존은 삭제 버튼 구현보다 사용자 안내·감사 가능한 상태·백업·복원 책임을 먼저 질문하도록 설계합니다.

## 6. 사례 B: 공개 주가 데이터 분석 대시보드

### 사례 목적

시장지수와 관심 종목의 가격·거래량 변화를 비교하는 교육용 분석을 통해 데이터 원천에서 변환·검증·시각화·배포·갱신·복구까지의 책임을 설명합니다. 핵심은 투자 결론이 아니라 데이터가 무엇을 뜻하고 언제 기준이며 어떤 변환과 품질 상태를 거쳐 화면에 도달했는지를 검증하는 것입니다.

### 분석·제품 조각

1. **D-01 원천과 권리**: 데이터 정의, 기준 시점, 이용 조건, 재배포 범위와 수집 경계를 확인합니다.
2. **D-02 계약과 품질**: 종목·시장·통화·거래일·값·값 상태·갱신 시점·원천 버전과 변환 버전을 명시하고 결측·미수집·비적용·품질 차단을 구분합니다.
3. **D-03 분석과 재현성**: 입력 버전, 전처리, 수정주가 여부, 계산식, 기간 경계와 결과 재현 증거를 연결합니다.
4. **D-04 대시보드 전달**: 표와 차트가 같은 데이터 계약을 사용하고 로딩·성공·빈 결과·오래된 데이터·품질 경고·오류 상태를 구분합니다.
5. **D-05 배포와 운영 인수**: 정적 전달과 API를 책임으로 선택하고 갱신 실패 감지, 마지막 정상 버전, 복원과 공개 흐름 재확인을 연결합니다.

### 금융·데이터 안전 경계

- 매수·매도 추천, 목표 가격, 수익 보장과 자동 주문은 범위 밖입니다.
- 분석 결과와 투자 판단을 구분하고 과거 데이터가 미래 성과를 보장하지 않는다는 한계를 표시합니다.
- 실시간 시세와 초단위 수집은 첫 범위에 포함하지 않습니다.
- 실제 원천을 선택하기 전에는 명시적인 교육용 fixture와 가상 종목·값을 사용하고 실제 데이터처럼 표현하지 않습니다.
- 실제 원천을 사용할 때는 공식 문서에서 지표 정의, 조정 방식, 거래일·시간대, 이용 조건과 재배포 허용 범위를 확인해 `research/source-map.md`에 확인일·적용 범위·한계를 기록합니다.
- API 키, 유료 원천, 개인 포트폴리오와 주문·계좌 데이터는 저장소·프롬프트·브라우저 번들·공개 예시에 포함하지 않습니다.

## 7. 학습 경로에서의 역할

공식 Build Track은 하나의 사례를 그대로 복제하는 경로가 아니라, 웹앱 개발을 기본 축으로 삼고 데이터 분석에서 검증 책임이 달라지는 지점을 비교하는 완주 경로로 재정의합니다. 공개 문서 목록과 순서의 단일 진실 공급원은 계속 `src/content/docs/start-here/learning-paths.md`가 담당하며, 이 명세는 사례 선택 규칙을 담당합니다.

목표 Build Track은 현재의 핵심 개념 장 11개에 `첫 풀스택 프로젝트`와 `데이터 분석가의 대시보드 사례`를 더한 13개 장입니다. 후속 구현에서 `src/content/docs/start-here/learning-paths.md`의 목록과 순서를 갱신하기 전까지는 현재 12개 장을 공식 집계로 유지하며, 설계 목표 수치와 현재 검증 수치를 섞지 않습니다.

### 장별 기본 사례 배치

| 학습 영역 | 기본 사례 | 보조 사례를 함께 쓰는 조건 |
|---|---|---|
| 시스템 사고 | 웹앱과 주식 대시보드 짧은 비교 | 화면 성공, 데이터 성공과 운영 성공이 다름을 보여 줄 때 |
| 클라이언트·서버·HTTP | 모임 조회·참가·취소 흐름 | 읽기 중심 조회와 정적 데이터 전달의 차이를 설명할 때 주식 대시보드 추가 |
| API·데이터베이스·인증 | 주최자 소유권·참가 관계·정원 | 데이터 계약과 사용자 권한의 계약 차이를 보여 줄 때 주식 대시보드 추가 |
| 브라우저·DOM·렌더링 | 모임 상세·참가 버튼·모집 상태 | 표·차트·데이터 품질 상태가 별도 화면 증거를 요구할 때 주식 대시보드 추가 |
| 요구사항·설계·테스트 | 장의 학습 목표에 더 적합한 사례 | 제품 기능 위험과 분석 정확성 위험을 구분해야 할 때 두 사례 비교 |
| Git·배포·운영·AI 작업 | 모임 참가 웹앱 | 데이터 버전·갱신·재현성·정적 전달 책임이 결론을 바꿀 때 주식 대시보드 추가 |
| 데이터 전용 주제 | 주식 분석 대시보드 | 사용자 계정·쓰기·권한과 비교가 필요할 때 모임 참가 웹앱 추가 |
| 사례와 캡스톤 | 두 사례를 독립 장으로 제공 | 공통 체크리스트에서는 차이를 나란히 비교 |

### 편집 규칙

- 반복 사례의 표시 이름은 `개발 사례: 모임 참가 웹앱`과 `데이터 분석 사례: 주가 데이터 대시보드`로 통일합니다.
- 사례는 앞선 정의를 대신하지 않으며, 개념을 먼저 설명한 뒤 적용 예로 사용합니다.
- 한 장에서 두 사례를 쓰더라도 같은 정의를 두 번 반복하지 않고 입력·상태·위험·증거가 달라지는 지점만 비교합니다.
- 사례가 장의 학습 목표와 직접 연결되지 않으면 추가하지 않습니다.
- 독자가 사례 도메인 지식 때문에 막히지 않도록 새 도메인 용어는 즉시 쉬운 말로 설명하고 판단에 필요하지 않은 세부는 제외합니다.
- 실제 구현 코드보다 사용자 행동, 시스템 경계, 실패 상태, 판단 질문과 검증 증거를 우선합니다.

## 8. 영속 지식과 교체 가능한 도구 예시의 계층

핸드북의 정본은 특정 제품 사용법이 아니라 소프트웨어 시스템을 설계·질문·검토·검증·운영하는 지식입니다. 도구 예시는 독자가 현재 바이브 코딩 환경에 개념을 연결하도록 돕지만 학습 목표와 정의를 대신하지 않습니다.

1. **영속 개념**: 아키텍처, 구성요소와 경계, 프레임워크의 역할과 선택 기준, 데이터 모델, API 계약, 인증과 인가, 개발 생명주기, 요구사항·설계·테스트, Git, 배포·운영, 개발 용어와 판단 질문을 제품 이름 없이 설명합니다.
2. **사례 적용**: 영속 개념을 모임 참가 웹앱과 주가 데이터 분석 대시보드의 사용자 행동·상태·실패·증거에 대응시킵니다.
3. **기준 도구 매핑**: 공식 자료를 확인한 시점의 Supabase를 관리형 백엔드 사례, Vercel을 기본 배포 후보, Codex Sites를 대체 배포 후보로 사용해 같은 책임이 실제 제품에서 어디에 나타나는지 보여 줍니다.
4. **교체 가능한 실습·부록**: 제품 화면, 설정 위치, CLI 명령, 요금·한도와 현재 기능은 확인일·버전·적용 범위를 표시하고 본문 정본과 분리합니다.

### 도구 예시 편집 규칙

- `데이터베이스 = Supabase`, `배포 = Vercel`, `호스팅 = Codex Sites`, `에이전트 = Claude Code 또는 Codex`처럼 제품과 개념을 등치하지 않습니다.
- 프레임워크는 아키텍처보다 먼저 정답처럼 선택하지 않고, 해결할 책임·렌더링 방식·상태·팀 역량·배포 환경·유지 비용으로 선택 근거를 설명합니다.
- 핵심 학습 목표, 한 문장 정의와 완료 기준은 제품 UI 이름이나 버튼 위치에 의존하지 않습니다.
- 기준 도구는 하나의 흐름을 끝까지 연결할 때만 사용하고, 대안 나열은 선택을 바꾸는 조건과 책임 차이가 있을 때로 제한합니다.
- 제품별 보안·권한·런타임·환경 변수·배포·복구 동작은 집필 시점의 공식 자료로 다시 확인하고 `research/source-map.md`에 확인일·적용 범위·일반화 금지선을 기록합니다.
- 도구가 바뀌면 적용 상자와 부록을 교체하되 영속 개념과 사례의 사용자 문제·판단 질문은 유지할 수 있어야 합니다.

## 9. 두 독립 캡스톤의 완료 범위

### 개발 캡스톤

`첫 풀스택 프로젝트`는 모임 참가 웹앱의 문제·주최자와 참가자·요구사항·비목표·아키텍처·상태 모델·API·데이터 관계·인증과 인가·UI 상태·동시성·테스트·Git·배포·운영·AI 작업 인수를 처음부터 끝까지 연결합니다. 공개 조회, 주최자 생성, 참가·취소, 정원·마감과 운영 인수를 수직 조각으로 나눠 처음부터 과설계하지 않는 판단도 보여 줍니다.

### 분석 캡스톤

`데이터 분석가의 대시보드 사례`는 주가 데이터 분석 대시보드의 원천·권리·데이터 계약·품질·재현성·표와 차트·배포·갱신·복구·AI 작업 인수를 처음부터 끝까지 연결합니다. 데이터가 화면에 표시됐다는 사실과 데이터 정의·변환·기준 시점이 타당하다는 사실을 별도 증거로 검증합니다.

두 캡스톤은 같은 개발 생명주기를 공유하지만 하나를 다른 하나의 부록으로 취급하지 않습니다. 각 독자는 관심 사례 하나만 읽어도 완결된 흐름을 얻고, 비교하고 싶은 독자는 공통 체크리스트를 통해 책임 차이를 확인할 수 있어야 합니다.

## 10. 기존 검토 증거와 상태 처리

과거 검토 기록은 당시 정본에 대한 역사적 증거이므로 반도체 표현을 주식 표현으로 소급 수정하지 않습니다. 새 사례 전환은 별도 영향 감사와 새 검토 기록으로 추적합니다.

각 공개 문서는 다음 기준으로 분류합니다.

- **표면 편집**: 도메인 명칭만 바뀌고 요구사항·데이터 계약·기술 주장·실패 상태·테스트·출처·다이어그램이 달라지지 않는 변경입니다. 자체 점검과 자동·렌더링 검증을 기록하고 기존 상태 유지 가능성을 판단합니다.
- **실질 변경**: 요구사항, 입력·출력 필드, 데이터 품질, 인증·인가, 테스트 오라클, 출처와 이용 조건, 비유의 결론 또는 장의 학습 흐름이 달라지는 변경입니다. 해당 문서는 `draft`로 되돌리고 새 독립 검토와 `request:` 증거를 갖춘 뒤 `review` 승격을 다시 판단합니다.
- **캡스톤 전환**: 반도체 분석 대시보드를 주가 데이터 분석 대시보드로 바꾸는 작업은 원천·필드·품질·해석·안전 경계가 달라지므로 실질 변경으로 처리합니다.

현재 `review` 문서를 일괄 강등하지 않습니다. 구현 계획의 첫 단계에서 반도체 사례가 있는 공개 문서마다 표면 편집과 실질 변경을 판정하고, 판정 근거와 필요한 재검토 범위를 하나의 영향 감사 문서에 기록합니다.

## 11. 전환 순서와 작업 경계

후속 구현 계획은 다음 순서를 작은 독립 작업으로 나눕니다.

1. 반도체 사례가 있는 공개 문서·교차 링크·다이어그램·출처·검토 증거를 조사하고 파일별 영향 등급을 기록합니다.
2. 실제 주식 원천을 사용하지 않는 교육용 사례 계약과 조사 브리프를 확정합니다.
3. 기존 북마크 웹앱 초안을 모임 일정·참가 신청 웹앱의 역할·상태·권한·동시성 계약으로 교체하고 현재 기준 장의 깊이와 장 템플릿에 맞게 확장합니다.
4. 주가 데이터 분석 캡스톤을 원천 확인 전 fixture 범위에서 다시 설계하고, 공식 원천 조사 승인을 별도 게이트로 둡니다.
5. Supabase·Vercel·Codex Sites를 현재 기능으로 확정하기 전에 공식 자료 조사 범위와 영속 개념에 대응할 주장 목록을 별도 브리프로 고정합니다.
6. 아직 독립 검토 전인 장부터 새 사례 규칙을 적용하고, 기존 `review` 장은 영향 감사 결과에 따라 필요한 부분만 전환합니다.
7. 학습 경로·사례 인덱스·교차 링크·콘텐츠 지도·프로젝트 문맥을 목표 체계와 동기화합니다.
8. 실질 변경 문서를 다시 독립 검토하고 자동·브라우저 검증 뒤 상태를 재판정합니다.

한 작업 단위에서 두 캡스톤 전체와 모든 핵심 장을 동시에 수정하지 않습니다. 각 커밋은 한 캡스톤의 한 조각 또는 같은 판단 규칙을 공유하는 소수 문서만 포함해야 합니다.

## 12. 수용 기준

- 공개 학습 경로에서 웹앱이 일반 개발의 기본 사례이고 주식 분석이 데이터 분석의 보조 사례라는 역할을 독자가 확인할 수 있습니다.
- 모임 참가 웹앱과 주가 데이터 분석 대시보드가 각각 문제에서 운영 인수까지 독립적으로 완결됩니다.
- 핵심 장은 두 사례를 기계적으로 반복하지 않고 학습 목표에 필요한 차이만 비교합니다.
- 아키텍처·프레임워크 역할·개발 절차·사고법·용어와 방법론을 제품 이름 없이 설명할 수 있고, Supabase·Vercel·Codex Sites는 확인일이 있는 교체 가능한 적용 예로 분리됩니다.
- 검색으로 사례 또는 핵심 장에 바로 들어온 독자가 한 문장 정의·시스템 위치·판단 규칙·관련 용어를 확인할 수 있고, 한국어와 널리 쓰이는 영문 용어·약어가 용어집과 교차 링크로 연결됩니다.
- 반도체 사례는 목표 전환 완료 뒤 현재 공개 학습 문서에서 제거되며, 과거 검토 기록에는 역사적 정본으로 남을 수 있습니다.
- 실제 주식 데이터와 교육용 fixture, 분석 결과와 투자 판단, 데이터 정확성과 웹앱 동작 성공을 명확히 구분합니다.
- 실질 변경된 `review` 문서는 새 독립 검토 전까지 `review` 상태를 유지하지 않습니다.
- 새 출처 주장은 공식·1차 자료의 확인일·적용 범위·한계를 `research/source-map.md`에서 추적할 수 있습니다.
- 콘텐츠 메타데이터·링크·다이어그램 접근성·콘텐츠 지도·정적 빌드와 데스크톱·모바일 렌더링 검증을 통과합니다.

## 15. 후속 결정 게이트

2026-08-07 사용자 승인을 받아 상세 구현 계획을 작성합니다. 구현 계획은 파일별 영향 감사, 모임 참가·주가 분석 캡스톤 확장, 영속 개념과 도구 매핑 분리, 반복 사례 전환과 재검토를 별도 작업으로 나누며, 실제 주식 데이터 원천과 Supabase·Vercel·Codex Sites 공식 조사·네트워크 접근·새 의존성·배포·푸시는 각각 기존 승인 경계를 유지합니다.
