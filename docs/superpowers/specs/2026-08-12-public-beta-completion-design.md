# 바이브 개발 핸드북 공개 베타 완성 설계

- 상태: 사용자 승인 완료
- 승인일: 2026-08-12
- 운영 개정: 2026-08-28 Claude 운영 기록은 역사로 보존하고, 2026-09-05 Codex 두 겹 검토 계약을 앞으로의 M5에 적용
- 목표 릴리스: `v0.1.0-beta.1`
- 적용 범위: 저장소 전체의 콘텐츠·시각 자료·사이트·검증·공개 배포

## 1. 문서 목적

이 문서는 바이브 개발 핸드북을 부분적인 기반 프로젝트에서 실제 공개 베타로 완성하기 위한 상위 완료 계약입니다. 무엇을 완성으로 부를지, 어떤 증거가 있어야 공개할 수 있는지, 장기 작업의 진행률을 어떻게 계산할지, 로컬 작업과 외부 공개의 권한을 어디에서 나눌지를 고정합니다.

세부 파일 순서와 작업 상태는 별도의 마스터 실행 계획이 담당합니다. 이 명세는 실행 중 수시로 바뀌는 체크리스트가 아니라, 계획과 구현이 따라야 하는 안정적인 기준입니다.

## 2. 최상위 목표

비개발자 바이브 코더가 소프트웨어의 구조·용어·개발 절차·개발자의 사고법을 이해하고, AI가 만든 결과를 질문·검토·검증·운영할 수 있도록 돕는 한국어 핸드북을 완성하여 공개 GitHub 저장소와 GitHub Pages에서 공개 베타로 배포하고 실제 공개 URL까지 검증합니다.

완료 범위에는 다음이 포함됩니다.

- 역할별 전체 공개 원고 완성
- 기존 원고를 포함한 콘텐츠 규칙 전수 감사
- 모임 참가 웹앱과 주가 데이터 분석 대시보드 사례의 일관된 적용
- 초보자가 관계·흐름·상태를 이해하는 데 필요한 시각 자료
- 검색·학습 경로·용어집·교차 링크
- 자동 검증·빌드·브라우저 검증
- Codex 두 겹 독립 검토와 지적 재판정(10.2절)
- 프로젝트 소유자 최종 승인
- 공개 GitHub 저장소와 GitHub Issues 피드백 경로
- GitHub Pages 공개 배포와 비로그인 환경의 실제 URL 검증
- `v0.1.0-beta.1` 릴리스 기록

## 3. 독자와 교육 목표

주요 독자는 Claude Code·Codex 등으로 바이브 코딩을 하는 비개발자, 데이터 분석가, PM, 디자이너와 도메인 전문가입니다. 코드를 많이 작성하는 법보다 다음 능력을 먼저 기릅니다.

- 화면을 하나의 결과가 아니라 여러 책임이 연결된 소프트웨어 시스템으로 봅니다.
- 프런트엔드·백엔드·API·데이터베이스·인증·배포·운영의 위치와 관계를 설명합니다.
- 요구사항·설계·작업 계획·테스트·검토를 서로 다른 산출물과 활동으로 구분합니다.
- Git 상태, diff, 로그, HTTP 응답, 권위 있는 데이터 재조회와 브라우저 화면을 서로 다른 증거로 사용합니다.
- AI에게 모호하게 일을 넘기지 않고 목표·비목표·권한·실패 조건·수용 기준·검증 방법을 전달합니다.
- 특정 도구가 바뀌어도 유지되는 구조·원리·판단법을 익힙니다.

## 4. 비목표

공개 베타의 필수 범위에 다음은 포함하지 않습니다.

- 종이책 출판을 전제로 한 전문 교정·교열
- 여러 명의 외부 기술 검토자와 대규모 독자 연구
- 실제 비개발자 참여자를 모집한 사용성 실험
- 맞춤 도메인
- 사용자 계정과 학습 진도 저장
- 서버·데이터베이스·CMS를 사용하는 별도 핸드북 애플리케이션
- 유료 서비스·결제·광고
- 오프라인 PDF·전자책
- 영어판과 다국어판
- 모든 개발 도구의 완전한 사용 설명서

외부 개발자 한 명의 가벼운 검토는 원고 완성 뒤 수행할 수 있는 선택 항목이며 공개 베타 완료의 필수 조건이나 진행률 분모에 포함하지 않습니다. 맞춤 도메인, 퀴즈, 진도 저장, PDF와 다국어는 공개 베타 이후 실제 피드백이 필요성을 뒷받침할 때 별도 명세로 검토합니다.

## 5. 정본 문서 체계

### 5.1 완성 명세

이 문서 `docs/superpowers/specs/2026-08-12-public-beta-completion-design.md`는 다음 기준의 단일 진실 공급원입니다.

- 프로젝트 전체 완료 정의
- 콘텐츠 역할과 품질 기준
- 사례·도구·시각화 정책
- 검토와 `ready` 승격 계약
- 권한·Git·네트워크·배포 경계
- 진척률 계산과 릴리스 게이트
- 버전과 라이선스 정책

### 5.2 마스터 실행 계획

`docs/superpowers/plans/2026-08-12-public-beta-master-plan.md`는 다음 실행 정보를 관리합니다.

- 필수 작업 패키지와 선행 관계
- 파일별 포트폴리오·규칙 감사 결과
- 작업별 대상 파일·수용 기준·검증 명령
- Codex 검토 범위와 결과(Claude/Opus·인증·구독 기록은 명시적으로 역사 전용)
- 상태·결과 커밋·차단 사유·다음 작업
- 진척률 산식의 실제 분자·분모
- 방향 변경 기록

기존 세부 계획의 내용을 다시 복제하지 않고, 세부 계획과 완료 커밋을 연결합니다. 기존 계획의 완료 여부는 파일의 체크 표시만 믿지 않고 Git 객체·검증 기록·현재 공개 콘텐츠를 함께 대조합니다.

### 5.3 실행 상태

작업 상태는 다음 여섯 가지로 통일합니다.

| 상태 | 의미 |
|---|---|
| `pending` | 선행 작업 또는 실행을 기다림 |
| `in_progress` | 담당 작업이 시작됐지만 모든 수용 기준을 통과하지 않음 |
| `blocked` | 명시된 외부 조건·승인·정보가 없어 필수 진전을 낼 수 없음 |
| `completed` | 모든 수용 기준과 필수 검증을 통과하고 결과 커밋이 확인됨 |
| `superseded` | 승인된 다른 작업으로 대체되어 현재 분모에서 제외됨 |
| `optional` | 공개 베타 완료를 막지 않는 선택 작업 |

`.superpowers/sdd`와 `/private/tmp`의 장부는 임시 실행 자료입니다. 저장소 안의 명세·마스터 계획·Git 커밋을 대신하지 않습니다.

### 5.4 변경 기록

방향이 바뀌면 기존 기록을 지우지 않고 마스터 계획에 다음 정보를 덧붙입니다.

- 변경 ID와 날짜
- 변경 전·후 상태
- 변경 이유
- 영향을 받는 문서·작업·완료 기준
- 사용자 승인 여부
- 관련 커밋
- 취소되거나 대체된 작업

새 필수 작업이 추가되어 진척률이 낮아지는 경우에도 같은 기록을 남깁니다.

## 6. 완성 마일스톤

### M0 — 거버넌스와 실행 정본 확정

- 이 명세와 마스터 계획을 승인·커밋합니다.
- 모든 로컬 브랜치·worktree·커밋 계보를 다시 감사합니다.
- 로컬 `main`에만 있는 변경과 최신 작업 스택에만 있는 변경을 비교합니다.
- `main`의 `c362d9c` 변경과 최신 작업 브랜치의 `4acf77f`까지의 유효 변경을 잃지 않습니다.
- 중복 적용·충돌·누락을 확인한 뒤 정상 merge, cherry-pick 또는 표적 수동 통합 중 가장 좁고 추적 가능한 방법을 선택합니다.
- `git reset --hard`, 강제 checkout과 추정에 의한 브랜치 덮어쓰기를 사용하지 않습니다.
- 통합된 기준점에서 장기 브랜치 `codex/public-beta-completion`과 전용 worktree `.worktrees/public-beta-completion`을 공개 베타 작업의 실행 정본으로 지정합니다.
- 루트 저장소와 다른 과거 worktree에서는 동시에 공개 원고를 수정하지 않습니다.

M0 완료 증거는 통합 기준 커밋, 부모 계보, 보존한 양쪽 변경의 diff 대조, 깨끗한 정본 worktree와 마스터 계획의 기준 SHA입니다.

### M1 — 전체 콘텐츠 포트폴리오와 규칙 감사

현재 문서 수는 기준선일 뿐 목표 개수가 아닙니다. 각 공개 문서를 다음 중 하나로 판정합니다.

- 독립 문서로 완성
- 다른 문서와 병합
- 역할 중복으로 제거
- 공개 베타 이후 범위로 제외
- 내부 조사·편집 문서로 이동
- 역사 증거로만 보존

기계 검색과 의미 검토를 함께 수행하고, 판정은 `conform`, `needs_edit`, `needs_rewrite`, `merge`, `remove`, `historical_only` 중 하나로 기록합니다. 공개 콘텐츠의 Critical·Important 규칙 위반과 폐기된 공개 사례 잔존이 모두 0건이어야 M1이 완료됩니다.

### M2 — 필수 기반 계획 완료

기본 순서는 다음과 같습니다.

1. 현재 도구 매핑
2. 학습 경로·검색·목표 Build Track 정합성
3. 기존 `review` 문서의 새 계약 재검토
4. 아키텍처·프레임워크 기반 심화
5. 남은 핵심 장의 독립 검토 준비

계획 간 선행 관계는 마스터 계획 작성 시 현재 Git 상태와 산출물을 다시 감사한 뒤 확정합니다. 과거 문서에 기록된 날짜·개수·상태를 현재 사실로 그대로 복사하지 않습니다.

### M3 — 역할별 전체 원고 완성

모든 공개 문서를 9절의 역할별 기준으로 완성합니다. 미완성 문서는 완성하거나, 병합하거나, 공개 콘텐츠 영역 밖으로 이동합니다. 내비게이션에서만 숨기고 직접 URL로 열리는 파일은 제외로 인정하지 않습니다.

M3의 내용 완성은 독립 검토와 `ready` 승격을 뜻하지 않습니다. M3은 읽을 수 있는 원고·근거·사례·시각 자료 후보가 역할별 수용 기준을 만족하는 단계이고, M5가 독립 검토와 공개 승격을 담당합니다.

### M4 — 시각 자료와 사이트 경험 완성

- 기존 시각 자료를 크기·복잡도·문법·접근성·모바일 가독성 기준으로 전수 감사합니다.
- 필요한 새 시각 자료를 12절의 도구 선택 정책에 따라 작성합니다.
- 학습 경로·홈·섹션 인덱스·용어집·두 캡스톤의 탐색 흐름을 검증합니다.
- 한국어·영문·약어 검색을 확인합니다.
- 대표 데스크톱·모바일·라이트·다크 상태를 검증합니다.
- 키보드 탐색·포커스·대체 텍스트·가로 넘침·콘솔 오류를 확인합니다.

### M5 — 독립 검토와 모든 공개 문서 `ready` 승격

- 10.2절의 Codex 두 겹 독립성 조건을 충족할 때 독립 검토를 실행합니다. M5의 R01~R25는 공개 문서 59개 전체, R26은 분리된 통합 검토이며 표본·작업 단위 검토로 대체하지 않습니다.
- controller가 Codex finding을 현재 원고·공식 근거·프로젝트 규칙에 대조해 재판정합니다.
- Critical·Important 지적을 수정하고 필요한 범위를 재검토합니다.
- 자동·브라우저·시각 자료 검증을 완료합니다.
- 프로젝트 소유자가 고정된 검토 묶음과 기준 SHA를 승인합니다.
- 실제 공개되는 모든 문서를 `ready`로 승격합니다.

### M6 — 공개 저장소와 릴리스 준비

- README·프로젝트 매니페스트·CHANGELOG·버전을 실제 공개 상태와 맞춥니다.
- 콘텐츠·코드 라이선스와 경로별 적용 범위를 추가합니다.
- 기여·피드백 안내와 GitHub Issues 템플릿을 준비합니다.
- 현재 파일과 Git 이력의 비밀정보·개인정보·자산 권리를 감사합니다.
- 임시 장부·브라우저 세션·로컬 경로·비공개 자료가 추적되지 않았는지 확인합니다.
- 최종 release candidate SHA와 공개 승인 묶음을 고정합니다.

### M7 — 실제 공개 배포와 URL 검증

- 사용자가 지정한 GitHub 계정과 저장소에 원격을 구성합니다.
- 별도 외부 쓰기 승인을 받은 뒤 원격 `main`을 갱신합니다.
- 공개 저장소 상태, Actions CI와 Pages 배포 결과를 확인합니다.
- 기본 GitHub Pages URL을 비로그인 환경에서 검증합니다.
- 검증된 동일 SHA에 `v0.1.0-beta.1` 태그와 릴리스 기록을 만듭니다.

실제 공개 URL 검증 전에는 전체 진척률을 100% 또는 공개 베타 완료로 보고하지 않습니다.

### O1 — 외부 개발자 가벼운 검토

전체 원고 완성 뒤 외부 개발자 한 명에게 주요 개념 오류와 위험한 누락을 가볍게 검토받을 수 있습니다. `optional` 상태로 관리하며 수행 여부나 문서 개수는 공개 베타 완료를 막지 않습니다. 실제 피드백이 중요한 결함을 발견하면 중요도에 따라 필수 수정 작업으로 전환할 수 있습니다.

## 7. 콘텐츠 규칙과 소급 감사

### 7.1 규칙 범주

| 규칙 ID | 감사 질문 |
|---|---|
| `CASE` | 승인된 반복 사례와 역할을 사용하며 폐기된 사례가 현재 공개 원고에 남지 않았는가 |
| `DURABLE` | 오래가는 개념·원리·판단법과 날짜가 있는 제품 사용법을 분리했는가 |
| `AUDIENCE` | 비개발자가 코드 문법보다 구조·관계·절차·증거를 이해할 수 있는가 |
| `ANALOGY` | 비유가 맞는 지점과 깨지는 지점을 함께 설명했는가 |
| `EVIDENCE` | 계획·실행·검증·커밋·푸시·공개·배포를 다른 상태로 구분하는가 |
| `SOURCE` | 중요 주장에 공식·1차 출처, 확인일, 적용 범위와 일반화 금지선이 있는가 |
| `TERM` | 약어·용어·방법론을 서로 다른 범주와 뜻으로 구분하는가 |
| `VISUAL` | 시각 자료가 학습 질문에 답하며 복잡도·접근성·화면 검증을 통과하는가 |

새 콘텐츠 규칙은 명시적인 역사 예외가 없으면 기존 공개 원고에도 적용합니다. 미래 원고에만 적용하고 기존 공개 원고를 그대로 두지 않습니다.

### 7.2 폐기된 사례 감사

현재 공개 콘텐츠·frontmatter·대체 텍스트·프롬프트·학습 경로·용어집·교차 링크·Mermaid·SVG 내부 텍스트를 검색합니다. 단순 단어 치환으로 끝내지 않고 다음 의미가 남았는지 확인합니다.

- 이전 사용자와 역할
- 이전 읽기·쓰기 상태
- 이전 API와 데이터 필드
- 이전 데이터 원천·단위·품질 상태
- 이전 실패 조건과 테스트 오라클
- 이전 다이어그램 단계와 설명

현재 작업 기준선에서는 `src/content/docs/start-here/learning-paths.md`의 `공개 반도체 데이터` 한 건이 후속 정렬 대상으로 알려져 있습니다. M1은 최신 정본에서 전체 검색을 다시 실행하며 이 숫자를 고정된 사실로 가정하지 않습니다.

날짜가 있는 과거 검토 보고서·CHANGELOG·역사적 정본에는 당시 반도체 표현이 남을 수 있습니다. 이를 현재 공개 권고로 읽히지 않도록 역사적 범위를 표시하되 과거 증거를 새 사례에 맞게 소급 개작하지 않습니다.

### 7.3 사례 체계

일반 개발의 기본 반복 사례는 `개발 사례: 모임 참가 웹앱`, 데이터 분석의 보조 반복 사례는 `데이터 분석 사례: 주가 데이터 대시보드`입니다.

모임 사례는 사용자 역할, 읽기와 쓰기, 인증·인가, 상태 전이, 정원과 동시 요청, 배포·운영·복구를 설명합니다. 주가 사례는 교육용 fixture, 데이터 원천·권리·계약·결측·재현성·시각화·갱신·복구를 설명합니다.

- 투자 추천·수익 보장·자동 주문은 범위 밖입니다.
- 실제 원천을 채택하기 전에는 가상임을 명시한 교육용 fixture를 사용합니다.
- 실제 시장 원천은 정의·조정 방식·거래일·시간대·이용 조건·재배포 권리를 공식 자료로 확인합니다.
- 사례는 앞선 영속 개념의 정의를 대신하지 않습니다.
- 두 사례를 한 장에 기계적으로 반복하지 않고 위험·상태·증거가 달라지는 경우에만 비교합니다.

### 7.4 영속 지식과 현재 도구 매핑

영속 지식은 제품 이름 없이 설명할 수 있어야 합니다.

- 시스템 경계와 책임
- 클라이언트·서버와 상태의 원본·사본
- API·데이터 계약
- 인증·인가
- 데이터베이스·트랜잭션·복구
- 요구사항·설계·테스트·검토
- Git과 변경 안전성
- 빌드·배포·운영·관찰 가능성
- AI 작업 계약과 증거 기반 완료 인수

Supabase·Vercel·GitHub Pages·Codex Sites·Claude Code·Codex는 날짜가 있는 교체 가능한 도구 매핑으로 다룹니다. `데이터베이스 = Supabase` 또는 `배포 = Vercel`처럼 제품과 개념을 등치하지 않습니다. 제품 기능·계정·요금제·지역·베타 상태는 공식 자료 확인 범위를 벗어나 일반화하지 않습니다.

## 8. 콘텐츠 상태 모델

상태 이름은 `seed`, `draft`, `review`, `ready`를 유지하되, 기존의 사람 검토 의무를 10절의 승인된 검토 체계로 바꿉니다.

| 상태 | 의미 |
|---|---|
| `seed` | 학습 범위와 핵심 질문을 잡은 집필 시드 |
| `draft` | 처음부터 끝까지 읽을 수 있으나 독립 검토 전이거나 실질 변경 뒤 재검토가 필요한 원고 |
| `review` | 자체 점검을 마치고 고정된 입력으로 독립 검토가 진행 중인 원고 |
| `ready` | 역할별 품질·근거·독립 검토·재판정·자동·브라우저·소유자 승인 계약을 모두 통과한 공개 베타 원고 |

공개 베타 빌드에 포함되는 `src/content/docs/` 문서는 모두 `ready`여야 합니다. `seed`, `draft`, `review` 문서가 직접 URL로 접근 가능하면 릴리스 게이트가 실패합니다.

`draft`에서 `review`로 승격할 때는 자체 품질 점검, 대상 원고의 자동 검사와 빌드, 고정된 독립 검토 입력 계약을 먼저 확인하고 `reviewEvidence`에 실제 검토 요청 기록인 `request:`를 남깁니다. 요청만 만들었거나 검토가 실패한 상태는 `ready` 증거가 아니며, 의미 있는 수정으로 입력 SHA가 달라지면 새 요청 또는 명시적인 재검토 계약이 필요합니다.

## 10. 검토와 `ready` 증거

### 10.1 역할 분리

- Codex reviewer: 10.2절의 fresh context·두 겹 분리 조건을 충족한 독립 읽기 전용 검토
- controller: 작성·조사·근거 대조·지적 재판정·반영·검증
- 프로젝트 소유자: 고정된 검토 묶음과 기준 커밋의 최종 승인
- 외부 개발자: 선택적인 가벼운 검토

로컬 체크포인트를 위한 작업 단위 Codex 검토는 M5 fresh reviewer를 대신하지 않습니다. M5 reviewer·controller·소유자 승인을 실제 사람 기술·편집·독자 검토로 바꿔 적지 않습니다.

### 10.2 Codex 두 겹 독립 검토 계약

2026-09-05 사용자 결정은 공개 베타 1 M5 캠페인에 한해 과거 2026-08-28 Claude 운영 개정의 미래 완료 기준을 대체합니다. 과거 Claude 계약·사전 확인·요청·시도·결과 파일은 역사로 보존하며, `blocked`·`not-run`·모델 호출0은 유효 Claude 결과나 PASS가 아닙니다. 이는 Claude 일반 사용이나 다른 캠페인의 과거 기록을 변경하지 않습니다.

- R01~R25는 controller·작성자·이전 대화 이력과 분리된 fresh Codex reviewer가 고정 입력 전체를 읽기 전용으로 검토합니다. R26은 R01~R25 reviewer들과 분리된 fresh Codex reviewer가 공개 문서59개 전체, 행별 결과·재판정·재검토, 감사·source gap을 통합 검토합니다.
- 계획 기본 프로필은 R01~R25 `gpt-6-astra`/`high`, R26 `gpt-6-astra`/`xhigh`입니다. 실제 실행의 모델·reasoning effort를 결과에 기록하며 지정 프로필을 사용할 수 없으면 자동 fallback하지 않고 계약 개정 전까지 해당 행을 보류합니다.
- `Read`로 열거된 고정 입력만 허용합니다. reviewer는 파일·Git·테스트·웹·MCP·플러그인·스킬·외부 상태를 바꾸지 않습니다.
- 입력별·결합 SHA-256, 실제 완독 여부, 실제 모델·reasoning effort, 결과·finding·재판정·재검토를 분리해 기록합니다. 입력 부족·해시 불일치·미완독·미확인 모델/effort·실패/부분 결과는 PASS 증거가 아닙니다.
- 작성·자체 점검·관련 자동 검증을 마친 안정된 원고부터 기존 검토 단위·의존관계를 유지해 위험이 큰 항목을 우선합니다. 핵심·캡스톤·보안·데이터·배포는 개별 또는 기존 소묶음으로, 인덱스·참고편은 기존 의미 묶음으로 검토하고 R26 통합 검토를 유지합니다.
- [Codex 독립 검토 계약](../../project/reviews/public-beta-1/codex-review-contract.md)의 C01~C12와 해당 행의 요청서를 제공합니다. 대상 원고 전체(메타데이터·코드/프롬프트·alt 포함), 필요한 실제 출처 원문·인접 문맥·용어·그림/원본·미해결 finding을 고정 입력으로 제공합니다. controller 요약·자체 PASS가 원문을 대체하지 않습니다.
- 검토 전후 입력 해시를 비교합니다. reviewer는 결과를 응답으로만 반환하고 controller가 입력 완전성·해시·실제 모델/effort·읽기 전용 권한·응답 형식을 확인한 뒤 행렬의 Codex 결과 정본 경로에 저장합니다. 결과는 위치·심각도·근거·최소 수정·재확인 기준 중심으로 받고 불필요한 원문 재출력·전면 재작성을 요청하지 않습니다. 계약 경량화로 필수 기준을 줄이거나 작업 단위 검토를 최종 M5 검토로 계산하지 않습니다.

### 10.2.1 검토 대기와 개발 진행

검토 원장은 기존 `pending`·`in_progress`·`blocked`·`done` 상태를 사용하고 대상·대기 사유·입력 파일/해시·마지막 실행·다음 재개 조건을 기록합니다. 현재 대기 사유는 R01~R26 입력 고정 및 Codex 검토 미실행이며, 지정 모델/effort를 사용할 수 없을 때만 실제 원인을 기록합니다. 구현 상태, 필수 검토 상태, 공개 가능 여부는 별도 필드로 관리하며 `blocked`가 전체 목표 중단이나 완료를 뜻하지 않습니다.

검토가 막혀도 결과에 의존하지 않는 기존 목표 안의 작성·수정·근거 정리·자동 검사·로컬 시각 검증은 계속합니다. 고정 입력을 변경해야 하면 변경 전후 SHA-256과 영향 행을 기록하고 이전 증거를 해당 새 입력의 근거로 무효화한 뒤 필요한 범위만 재검토합니다. 영향 없는 유효 증거는 유지합니다. 필수 검토·미해결 Critical/Important·소유자 승인이 남아 있으면 M5 완료·`ready`·공개 가능으로 표시하지 않습니다.

독립 로컬 작업 단위가 수용 기준, 자동 검증, 필요한 실제 브라우저 또는 출력물 검증, 작성자와 분리된 Codex 작업 검토에서 Critical·Important 0개를 충족하고 다른 미완료 변경과 안전하게 분리되면 관련 파일만 선별해 로컬 체크포인트 커밋할 수 있습니다. 이 커밋은 M5 독립 검토·`ready`·소유자 승인·release candidate·push·배포·공개 가능을 뜻하지 않습니다. 이후 Codex finding이나 입력 변경이 생기면 기존 커밋을 덮어쓰지 않고 영향 파일의 좁은 수정 커밋과 필요한 재검토를 추가합니다.

지정 프로필을 사용할 수 없으면 자동 fallback·대체 제공자·새 목표·새 작업을 만들지 않습니다. 계약 개정 또는 실제 가용성 변경 전까지 해당 행을 `pending`으로 두며, 독립 작업을 소진하면 체크포인트와 필수 잔여 조건만 보고합니다.

### 10.3 지적 처리

controller는 Codex 지적을 `수용`, `부분 수용`, `기각`으로 판정하고 이유와 최소 변경 범위를 기록합니다. Critical·Important는 해결 전 `ready`로 승격하지 않습니다. 의미 변경으로 해결했다면 같은 reviewer의 명시적으로 좁힌 재검토 계약으로 재검토합니다.

표면 편집이 기존 검토 증거를 보존하려면 요구사항·데이터 계약·기술 주장·실패 상태·테스트·출처·다이어그램 의미가 바뀌지 않았다는 diff 기반 증거가 있어야 합니다. 이 조건을 증명하지 못하면 실질 변경으로 분류하고 새 검토를 수행합니다.

### 10.4 필수 `reviewEvidence`

`ready` 문서는 다음 접두사의 추적 가능한 증거를 가집니다.

```yaml
reviewEvidence:
  - "independent: 유효한 Codex 독립 검토 기록 경로(10.2절)"
  - "adjudication: controller 재판정과 반영 기록 경로"
  - "conformance: 콘텐츠 규칙·사례 감사 기록"
  - "sources: 출처·현재성 감사 기록"
  - "automated: 검증 명령·날짜·종료 코드"
  - "browser: 렌더링 검증 기록"
  - "owner: 승인 기록·날짜·기준 커밋"
```

시각 자료가 있는 문서는 다음 증거도 가집니다.

```yaml
  - "visual: 도구 선택·복잡도·접근성·라이트·다크·모바일 검증 기록"
```

실제 외부 사람 검토를 수행했을 때만 `technical:`, `editorial:`, `reader:`를 선택 증거로 사용합니다. 자동 검증기는 접두사와 경로 존재를 확인하고, 검토의 충분성·근거의 타당성·소유자 승인 범위는 release review가 판정합니다.

하나의 소유자 승인 기록이 여러 문서를 명시적으로 나열하고 동일한 release candidate SHA를 가리키면 각 문서가 그 묶음 기록을 참조할 수 있습니다. 소유자가 모든 파일을 줄 단위로 따로 승인할 필요는 없지만 승인 범위와 기준 SHA가 모호해서는 안 됩니다.

## 11. 출처와 최신성

- 표준·제품·프레임워크·GitHub 기능은 공식 문서 또는 1차 자료를 우선합니다.
- 출처별 공식 URL, 확인일, 주장, 적용 문서, 적용 범위와 일반화 금지선을 `research/source-map.md` 또는 연결된 조사 기록에 남깁니다.
- 마케팅 문구와 업계에서 안정적으로 쓰이는 개념을 구분합니다.
- 한 출처의 표현을 길게 복제하지 않고 독자의 학습 흐름에 맞게 재구성합니다.
- 접근 실패·404·인증 실패·429·버전 불일치는 숨기지 않고 현재성 미검증 또는 `blocked`로 기록합니다.
- 이전에 저장된 근거를 현재 확인 결과로 표현하지 않습니다.
- 공식 근거가 필요한 완료 항목을 비공식 블로그로 조용히 대체하지 않습니다.

현재 도구 조사는 공식 자료에 한정한 승인된 읽기 전용 네트워크 범위 안에서 수행합니다. 계정 접근·설정 변경·배포·공개 글 수정은 도구 조사 승인이 허용하지 않습니다.

## 12. 시각 자료 설계와 도구 선택

### 12.1 기본 원칙

- 시각 자료는 장식이 아니라 개념의 관계·흐름·상태를 글보다 명확하게 설명할 때 사용합니다.
- 한 다이어그램은 한 질문에 답합니다.
- 그림 앞에서 무엇을 봐야 하는지, 그림 뒤에서 무엇을 증명하고 무엇을 증명하지 않는지 설명합니다.
- 표나 짧은 문장으로 더 명확하면 다이어그램을 만들지 않습니다.
- 흐름도·아키텍처·시퀀스·상태·ER 등 질문에 맞는 문법을 선택합니다.
- 보통 4~7개 노드를 권장하고 정적 다이어그램은 9개를 기본 상한으로 둡니다.
- 화살표는 12개 이하, 초점 요소는 2개 이하를 권장합니다.
- 9개를 넘으면 개요와 상세로 나누고, 12개를 넘으면 도구 선택 전에 구조를 분할합니다.
- 색만으로 의미를 전달하지 않고 title·desc·대체 텍스트·선 종류·레이블을 사용합니다.
- 확대 없이 모바일에서 핵심 레이블을 읽을 수 있어야 합니다.
- 라이트·다크·데스크톱·모바일에서 잘림·겹침·가로 넘침·선과 화살표 머리 대비를 검증합니다.

### 12.2 기존 자료 감사

현재 알려진 우선 감사 후보는 다음과 같습니다.

- API 흐름 SVG `1200×1640`: 정상 7단계와 실패 6개를 개요와 상세로 분리
- 분석 대시보드 흐름 `760×1200`: 모바일 레이블과 정보 밀도 재검토
- 운영·에이전트 루프 `760×1040`: 세로 길이와 재배치 가능성 검토
- 1200px 폭 가로형 SVG: 전역 overflow뿐 아니라 실제 글자 크기와 내부 스크롤 검증

크기만으로 결함을 확정하지 않습니다. 소비하는 페이지의 실제 렌더와 교육 질문을 함께 봅니다.

### 12.3 도구 라우팅

`diagram-design`을 정적이고 단순한 교육용 다이어그램의 기본 설계 도구로 사용합니다. 해당 스킬의 올바른 다이어그램 문법, 복잡도 제한과 삭제 원칙을 따르되 독립 HTML의 기본 시각 스타일·Google Fonts를 그대로 공개하지 않고 프로젝트 Starlight 팔레트·시스템 폰트·접근 가능한 SVG와 Mermaid 계약에 맞춥니다.

Archify는 8~12개 노드의 복잡한 아키텍처·시퀀스·데이터 흐름·생명주기에서 자동 라우팅·검증·검색·경로 추적이 학습 이해를 실제로 높일 때만 사용합니다. 첫 파일럿 후보는 분할된 API 요청 상세 시퀀스이며 개요는 단순한 정적 그림으로 유지합니다.

공개 기본 산출물은 접근 가능한 정적 SVG입니다. Archify HTML은 별도의 가치·접근성·GitHub Pages·브라우저 승인을 통과한 경우에만 선택하며 애니메이션은 기본적으로 사용하지 않습니다. Mermaid·Archify JSON·SVG를 동시에 영구 정본으로 유지하지 않습니다. Archify JSON을 정본으로 채택하려면 재현 가능한 정적 export와 접근성 검증을 먼저 증명하고 ADR·`PROJECT_CONTEXT.md`를 갱신합니다. 그렇지 않으면 Archify를 임시 설계 보조 도구로만 사용합니다.

2026-08-12 기준 프로젝트 범위의 Archify 2.13.0은 별도 파일럿에서 Node 26.0.0으로 doctor와 showcase 검증을 통과했습니다. 실제 핸드북 작업에서는 프로젝트 권장 Node 22.16.0 호환성을 다시 확인해야 하며 이 과거 통과를 공개 산출물 품질 증거로 사용하지 않습니다.

### 13.1 마스터 계획 승인 뒤 계속할 수 있는 로컬 작업

- 제품·프레임워크·GitHub Pages 최신 동작 확인
- 10.2절의 fresh Codex reviewer·정확한 모델/reasoning effort·읽기 전용 조건을 충족한 Codex 검토
- 검토 결과와 출처 메타데이터의 로컬 저장

### 13.3 별도 승인이 필요한 환경 변경

- Archify 공개 런타임 또는 새 다이어그램 런타임 채택
- 대량 파일 이동·삭제·이름 변경

### 13.4 실행 직전 별도 승인이 필요한 외부 쓰기

- GitHub 원격 저장소 생성·연결·변경

현재 `.github/workflows/deploy.yml`은 `main` 푸시와 수동 실행에서 검증·빌드·Pages 배포를 수행합니다. `main` 푸시 승인을 요청할 때 CI와 Pages 배포가 자동 시작된다는 부작용을 함께 알립니다.

## 14. Git 작업 계약

표준 루프는 `상태 확인 → 목표 고정 → 작은 구현 → 자동 검증 → 독립 검토 → 문맥 갱신 → 선별 커밋`입니다.

각 작업 패키지는 작업 ID, 목표, 비목표, 선행 조건, 대상 파일, 적용 규칙, 시각화 여부, 수용 기준, 자동·브라우저 검증, Codex 검토 수준, 승인 게이트와 결과 커밋을 가집니다. Claude 검토 표기는 2026-09-05 이전의 역사 기록에만 남깁니다.

커밋 전에는 다음을 확인합니다.

1. 허용된 파일만 변경됐습니다.
2. staged·unstaged 변경을 분리했습니다.
3. 관련 수용 기준·검증 명령과 필요한 브라우저/출력물 검증, 작성자와 분리된 Codex 작업 검토가 통과했습니다. M5 Codex 검토 대기 상태의 체크포인트 커밋이면 이를 `implementation verified / M5 Codex review pending`으로 명시하고 M5 독립 검토나 `ready` 승인 충족으로 해석하지 않습니다. 과거 `Claude review pending` 표기는 역사 상태를 보존할 때만 사용합니다.
4. 무관한 미완성 변경을 포함하지 않았습니다.
5. staged diff 전체를 읽었습니다.
6. 되돌릴 수 있는 독립 변경 단위입니다.

원고와 그 원고가 소비하는 다이어그램, 생성되는 `CONTENT_MAP.md`처럼 하나의 수용 기준에 묶인 파일은 같은 작업 단위에 포함할 수 있습니다. 로컬 커밋은 푸시·공개·배포·사용자 승인을 뜻하지 않습니다.

### 15.2 산식

전체 진척률은 다음처럼 계산합니다.

```text
전체 진척률 = Σ(마일스톤 가중치 × 완료된 필수 작업 점수 ÷ 해당 마일스톤의 전체 필수 작업 점수)
```

- `completed` 작업만 배정 점수 전체를 얻습니다.
- `in_progress` 작업은 명시적으로 완료·검증된 하위 수용 기준의 점수만 얻습니다.
- `pending`은 0점입니다.
- `blocked`는 이미 검증된 하위 점수만 보존합니다.
- `superseded`는 승인된 대체 작업이 분모에 들어간 경우 기존 분모에서 제외합니다.
- `optional`은 분자와 분모 모두에서 제외합니다.
- 단순한 문서 개수·본문 문자 수·작업 시작 여부는 점수가 아닙니다.
- 새 필수 작업이 발견되면 분모가 커져 진척률이 내려갈 수 있으며 변경 이유와 승인을 기록합니다.
