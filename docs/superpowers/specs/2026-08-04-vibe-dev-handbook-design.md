# 바이브 개발 핸드북 설계 명세

## 1. 목적

비개발자가 AI 코딩 도구를 단순 명령 실행기로 사용하지 않고, 소프트웨어 개발의 구조·절차·판단·검증 방식을 이해해 개발자와 유사한 문제 해결 루프를 수행하도록 돕는 공개형 학습 자료를 설계합니다. 특정 제품 사용법보다 도구가 바뀌어도 남는 아키텍처·프레임워크 역할·개발 방법론·용어와 사고법을 학습의 정본으로 둡니다.

이 프로젝트는 세 산출물을 동시에 만듭니다.

1. 체계적인 개발 온보딩 교육과정
2. 실전 바이브 코딩 운영 매뉴얼
3. GitHub에서 협업·배포 가능한 문서 사이트

## 2. 독자와 사전 지식

주 독자는 코딩 문법보다 데이터, 제품, 업무 도메인에 익숙한 사람입니다. 터미널과 Git을 처음 볼 수 있으며, PRD·TDD·API 같은 단어는 들어봤지만 서로 어떤 관계인지 모를 수 있습니다.

필수 사전 지식은 파일과 폴더를 열고 웹 브라우저를 사용하는 수준으로 제한합니다. 데이터 분석가는 표·파이프라인·입력과 출력의 비유를 통해 추가 연결점을 얻습니다.

## 3. 학습 성과

독자는 학습 후 다음을 할 수 있어야 합니다.

- 소프트웨어를 화면이 아니라 구성요소·경계·상태·흐름·제약의 시스템으로 설명
- 프런트엔드, 백엔드, API, 데이터베이스, 인증, 배포의 역할 구분
- 아이디어를 요구사항, 설계 선택, 작업 단위, 테스트 증거로 변환
- Git 변경 이력을 읽고 브랜치·커밋·PR·되돌리기의 목적 설명
- 빌드, 테스트, 로그, 배포 확인으로 AI의 완료 주장을 검증
- 컨텍스트, 스펙, 하네스, 반복 루프를 기존 개발 원리 위에서 사용
- 보안·비밀정보·권한·데이터 손실 위험에서 전문가 개입 시점 식별

## 4. 범위와 비범위

### 포함

- 개발자 사고법과 소프트웨어 생명주기
- 웹 기반 풀스택의 보편적 구조
- 요구사항·설계·테스트·협업·배포·운영
- AI 에이전트의 작업 환경, 권한, 컨텍스트, 검증 루프
- 용어 사전, 체크리스트, 템플릿, 사례

### 제외

- 특정 프로그래밍 언어 문법 완전 과정
- 프레임워크별 API 레퍼런스
- 모든 클라우드 제품 비교
- 초기 버전의 로그인·결제·진도 데이터베이스
- 특정 도구 UI에 강하게 종속된 사용 설명서

## 5. 교육 설계

### 5.1 순서

기본 순서는 `시스템 사고 → 실행 환경 → 풀스택 → 요구사항과 설계 → 품질과 협업 → 배포와 운영 → AI 네이티브 개발`입니다.

이 순서는 유행어를 뒤로 미루기 위한 것이 아닙니다. 컨텍스트와 하네스는 에이전트가 어떤 저장소에서 어떤 제약과 증거를 사용해야 하는지 설계하는 활동이므로, 독자가 먼저 저장소·아키텍처·테스트·운영을 알아야 정확히 이해할 수 있습니다.

### 5.2 학습 경로

- Fast Track: 전체 지형과 용어를 빠르게 파악
- Build Track: 소규모 모임 일정·참가 신청 웹앱을 기본 사례로 단계별 개발 흐름을 완성하고, 데이터 분석의 판단 기준이 달라지는 지점에는 공개 주가 데이터 분석 대시보드를 비교
- Deep Track: 설계 대안과 실패 모드를 깊게 학습

반복 사례의 역할, 두 독립 캡스톤, 금융·데이터 안전 경계와 기존 검토 증거의 전환 규칙은 `docs/superpowers/specs/2026-08-07-dual-case-study-system-design.md`를 따릅니다.

### 5.3 두 가지 이용 방식

독자는 `시작하기 → Build Track → 캡스톤` 순서로 처음부터 끝까지 학습할 수 있고, 작업 중 낯선 용어나 판단 문제가 생겼을 때 검색·용어집·교차 링크로 필요한 장만 찾아 읽을 수도 있습니다. 검색으로 바로 들어온 장도 한 문장 정의, 시스템에서의 위치, 판단 규칙과 관련 용어를 통해 앞 장을 모두 읽지 않고 핵심 질문에 답할 수 있어야 하며, 더 깊은 선행 지식이 필요하면 명시적인 링크로 안내합니다.

검색 가능성은 별도 서버 기능이 아니라 정적 빌드에서 생성되는 Starlight Pagefind 인덱스를 기본으로 합니다. 제목은 독자가 실제로 묻는 질문을 드러내고, 한국어 용어와 널리 쓰이는 영문 용어·약어를 첫 등장과 용어집에서 함께 표시하며, 한 파일은 하나의 질문 또는 학습 목표 집합을 담당합니다.

### 5.4 장 템플릿

모든 핵심 장은 필요성, 정의, 비유, 시스템 위치, 실제 신호, 판단 규칙, 실패 모드, 체크리스트, 연습, 관련 용어를 포함합니다. 비유에는 반드시 한계를 적습니다.

## 7. 기술 아키텍처

### 구성요소

- 콘텐츠: `src/content/docs/`의 Markdown/MDX
- 정적 사이트: Astro 7 + Starlight 0.41
- 메타데이터 스키마: Astro Content Collections
- 검색: Starlight 기본 Pagefind
- 시각 자료: 직접 제작 SVG + Mermaid 원본
- 자동 품질: Node 내장 테스트 + 콘텐츠 검증 스크립트
- CI/CD: GitHub Actions
- 호스팅: GitHub Pages

### 경계

콘텐츠 제작은 사이트 코드와 분리합니다. 인터랙티브 기능이 필요해져도 공개 지식 문서는 독립적으로 빌드되고 읽혀야 합니다. 사용자 상태가 필요한 기능은 별도 애플리케이션으로 분리합니다.

핵심 본문은 `영속 개념 → 사례 적용 → 현재 도구 매핑 → 교체 가능한 실습·부록` 순서로 책임을 분리합니다. Supabase·Vercel·Codex Sites·Claude Code·Codex 같은 제품은 공식 자료를 확인한 시점의 적용 예이며, 아키텍처 구성요소나 개발 절차의 정의를 대신하지 않습니다.

## 8. 콘텐츠 상태 모델

- seed: 범위와 핵심 질문을 고정한 집필 시드
- draft: 처음부터 끝까지 읽을 수 있지만 독립 검토 전인 초안
- review: 자체 점검을 마치고 독립적인 기술·편집·독자 검토를 요청한 상태
- ready: 기술·편집·독자 검토, 출처 확인, 자동 검사와 빌드를 통과한 출판 준비 상태

자동 검증은 필수 메타데이터, 미완성 표식, 이미지 대체 텍스트를 검사합니다. 의미 정확성, 비유의 한계, 출처 적절성은 사람의 리뷰가 필요합니다.

상세한 승격 조건과 검토 증거 형식은 `docs/project/content-lifecycle.md`를 단일 진실 공급원으로 사용합니다.

## 9. AI 작업 운영 모델

에이전트는 저장소 파일을 단일 진실 공급원으로 사용합니다. 작업은 상태 확인, 목표 고정, 작은 계획, 구현, 테스트, 독립 검토, 문맥 갱신 순으로 진행합니다.

네트워크, 의존성 설치, 푸시·배포·외부 쓰기, 대량 삭제와 구조 변경은 승인 대상으로 둡니다. 로컬 커밋은 저장소 운영 규칙에 따라 검증을 통과한 독립 작업 단위만 선별하며, 완료 판단은 에이전트의 설명이 아니라 파일 diff, 테스트, 빌드, 수용 기준 증거로 합니다.

## 10. 오류 처리와 복구

- 콘텐츠 검증 실패: 해당 파일과 필드를 구체적으로 출력하고 빌드를 중단
- 빌드 실패: 이전 배포를 유지하고 새 Pages 아티팩트를 배포하지 않음
- 잘못된 대규모 변경: 작은 커밋과 브랜치를 통해 revert 가능하게 유지
- 불확실한 사실: 단정하지 않고 조사 문서에 확인 상태를 기록
- 외부 도구 변경: 공식 문서를 재확인하고 버전·확인일을 기록

## 11. 테스트 전략

- 단위 테스트: frontmatter 파서와 규칙별 오류 검출
- 콘텐츠 검증: 모든 게시 Markdown/MDX 메타데이터와 접근성 기본 규칙
- 빌드 테스트: Starlight 정적 빌드
- 편집 검토: 품질 루브릭과 용어 일관성
- 독자 테스트: 비개발자가 설명을 읽고 시스템 흐름과 판단 기준을 재구성하는지 확인

## 12. 수용 기준

기반 저장소는 다음을 만족해야 합니다.

- 프로젝트 목적·독자·비목표가 문서화됨
- 전체 학습 지도와 대표 장 초안이 존재함
- SDD의 두 뜻과 TDD의 범주가 명확히 구분됨
- 사용자 요청 용어를 포함한 에이전트 출력 용어집이 존재함
- Codex가 후속 작업할 규칙과 계획이 존재함
- 콘텐츠 검증 테스트가 실패→성공 순서로 확인됨
- 의존성 설치 후 사이트를 빌드할 설정과 GitHub Pages 워크플로가 존재함
- 빌드를 실행하지 못한 환경에서는 그 제한을 명확히 보고함

## 13. 위험과 완화

- 범위 과대: 핵심 경로 우선, 나머지는 seed로 관리
- 쉬운 설명의 왜곡: 비유 한계와 기술 감수 필수
- 유행어 중심 회귀: 기본기 선행 정보 구조 고정
- 플랫폼 과설계: 정적 사이트 유지, 서버 요구는 증거 기반 재검토
- 출처 노후화: source map의 확인일과 정기 점검
- AI의 그럴듯한 오류: 독립 검토와 증거 기반 완료 정의
- 제품 설명의 노후화: 영속 개념과 날짜가 있는 도구 매핑·실습을 분리하고 공식 자료 확인 범위를 기록
