## 온라인 공식 출처 감사 — 2026-08-06

| 점검 항목 | 확인 결과 | 판정 |
|---|---|---|
| 후보 출처 접근 | 12개 출처 ID에 해당하는 공식 문서의 현재 URL과 본문을 직접 확인 | 완료 |
| 표준·지침·제품 문서 구분 | OAS·IETF RFC는 규범적 명세, NIST SP 800-63B-4는 미국 연방 디지털 신원 범위의 규범적 지침, OWASP는 실무 보안 지침, PostgreSQL은 제품 문서, MDN은 설명용 보조 자료로 분류 | 완료 |
| API 계약 | OpenAPI 3.2.0의 operation·parameter·request body·response·security requirement 범위를 확인 | 완료, 런타임 준수는 별도 증거 필요 |
| 인증·세션·인가 | NIST와 OWASP에서 정의와 세션 경계를 확인하고 OWASP API Security Top 10에서 객체·기능별 권한 검사를 확인 | 완료, 하나의 보편 구현 순서로 일반화 금지 |
| HTTP 자격 증명과 상태 코드 | RFC 9110의 `Authorization`, `401`, `403` 의미를 확인하고 MDN 흐름 설명으로 연결 | 완료, 상태 코드 하나만으로 내부 실패 원인 확정 금지 |
| 서명과 암호화 | RFC 7515의 JWS와 RFC 7516의 JWE가 제공하는 보장을 구분 | 완료, 특정 JWT 사용 권고로 확대 금지 |
| 트랜잭션·동시성·제약 | PostgreSQL 18의 원자성, 격리 수준·재시도, 제약 조건과 매개변수 분리 동작을 확인 | 완료, 다른 데이터베이스의 동일 동작으로 일반화 금지 |
| 로그 노출 경계 | OWASP Logging Cheat Sheet에서 세션 식별자·접근 토큰·비밀번호·연결 문자열·키·민감 개인정보의 직접 기록 제한을 확인 | 완료, 관할별 법률 판단은 범위 밖 |
| 공개 원고 상태 | 확인된 근거를 아직 독자용 설명·비유·흐름·연습으로 작성하지 않음 | `seed` 유지 |

이번 감사로 핵심 주장 11개에 직접 근거를 연결할 수 있게 됐습니다. 다만 규범적 단어의 효력 범위와 제품 종속 동작이 서로 다르므로, 공개 원고에서는 출처의 문장을 그대로 보편 규칙처럼 옮기지 않고 아래 판정과 한계를 따라 설명합니다.

## 이 장이 답할 한 가지 질문

**사용자의 요청이 백엔드에 도착한 뒤 API 계약, 신원 확인, 권한 판단, 업무 규칙과 데이터 변경을 어떤 순서와 책임으로 통과하는가?**

API, 데이터베이스, 인증·인가는 각각 독립된 큰 주제지만 Phase 1에서는 구현법을 모두 가르치지 않습니다. 비개발자가 AI의 설계를 검토할 때 세 책임을 서로 바꾸어 말하지 않고, 실패한 경계와 확인할 증거를 찾을 수 있는 전체 지도를 만드는 것이 목표입니다.

## 독자 상황

데이터 분석가가 개인 노트북의 반도체 지표 분석을 여러 사용자가 보는 대시보드로 확장한다고 가정합니다. 사용자는 저장한 보고서 이름과 필터를 수정할 수 있지만 다른 사용자의 보고서는 수정하면 안 됩니다. 이 한 흐름에서 독자는 다음 질문을 구분해야 합니다.

- 프런트엔드와 백엔드는 어떤 입력·출력·오류 형식에 합의했나요?
- 서버는 요청을 보낸 사용자가 누구인지 무엇으로 확인하나요?
- 로그인한 사용자가 이 보고서를 수정할 권한이 있는지는 어디에서 판단하나요?
- 보고서와 변경 이력처럼 함께 바뀌어야 하는 데이터는 어떻게 일관성을 지키나요?
- 화면의 성공 메시지는 실제 영속 변경을 어떤 증거로 확인하나요?

## 학습 목표 후보

조사와 집필을 마친 독자는 다음을 할 수 있어야 합니다.

1. API를 백엔드 전체나 단순 URL과 동일시하지 않고 구성요소 사이의 계약과 경계로 설명합니다.
2. 데이터베이스의 영속 상태 관리 책임을 API 처리 책임과 구분합니다.
3. 인증(authentication)과 인가(authorization)를 실제 사용자 행동에서 분리합니다.
4. 요청 식별, 인증, 권한 판단에 필요한 대상 조회, 인가, 입력·업무 규칙 검증, 트랜잭션과 응답의 논리적 책임 순서를 그립니다.
5. 성공·인증 실패·권한 거절·입력 오류·충돌·부분 실패의 증거를 구분합니다.
6. AI가 만든 백엔드를 파일 존재가 아니라 계약, 권한 테스트, 데이터 상태와 로그로 검토합니다.

## Phase 1 포함 범위

### API

- API와 endpoint, backend의 관계
- 요청 입력, 성공 출력, 오류 출력과 권한 조건을 포함하는 계약
- 외부 공개 API와 애플리케이션 내부 API의 공통점과 차이
- HTTP 장과의 연결: HTTP는 메시지 교환 규칙이고 API 계약은 해당 서비스의 업무 의미를 정한다는 경계
- 버전, 호환성과 변경 비용을 판단해야 한다는 최소 개념

### 데이터베이스

- 프로세스가 끝난 뒤에도 남아야 하는 영속 상태
- 스키마, 제약 조건과 데이터 정합성의 역할
- 한 업무 행동에 속한 여러 변경을 함께 성공하거나 함께 실패시키는 트랜잭션 개념
- 사용자 입력은 값으로 전달하고 쿼리나 명령의 구조를 바꾸지 못하게 해야 한다는 검토 원칙
- 트랜잭션이 동시 수정 충돌을 자동으로 해결하지는 않으며 충돌 감지와 사용자 응답이 별도 결정이라는 최소 개념
- 조회 성공과 변경의 실제 commit을 구분하는 증거
- 백업·복구·마이그레이션은 별도 장과 운영 장으로 연결

### 인증과 인가

- 인증: 신원 또는 계정과의 연관성을 확인하는 절차
- 인가: 확인된 주체가 특정 자원에 특정 행동을 할 수 있는지 판단하는 절차
- 로그인 성공이 모든 데이터 접근 권한을 의미하지 않는다는 경계
- 클라이언트의 버튼 숨김과 서버의 권한 검사를 구분
- 세션과 토큰은 인증 상태를 전달하는 수단이며 그 자체가 모든 권한 정책은 아니라는 최소 개념
- 서명은 위조 여부 확인, 암호화는 내용 보호와 관련된 서로 다른 보장이라는 경계
- 오류 응답과 로그에서 비밀정보·개인정보를 노출하지 않는 원칙

## Phase 1 비목표

- 특정 웹 프레임워크의 라우트·ORM·미들웨어 구현 튜토리얼
- SQL 문법, 인덱스 튜닝, 정규화 전체 과정
- ORM별 매개변수 바인딩과 SQL injection 방어 코드 구현 튜토리얼
- JWT와 세션 중 하나를 모든 프로젝트의 정답으로 선정
- OAuth, OpenID Connect, SSO 프로토콜의 상세 구현
- 암호 저장 알고리즘과 키 관리의 구체적 운영 절차
- 특정 데이터베이스 제품 비교와 선정
- 마이크로서비스, API gateway, event-driven architecture 설계
- 개인정보보호 법률의 관할별 해석

이 범위를 넘어서는 내용은 `data-model-schema-migration.md`, `state-cache-queue.md`, `performance-security.md`, `environment-variables-config.md`, `logs-monitoring-backup.md`와 Deep Track으로 연결합니다.

## 한 흐름으로 연결할 예시

예시는 “사용자가 자신이 저장한 반도체 지표 보고서의 이름과 기간을 수정한다”로 고정합니다.

```text
브라우저가 수정 요청 생성
→ API가 요청 형식과 대상 식별
→ 서버가 인증 상태로 사용자 신원 확인
→ 서버가 권한 판단에 필요한 보고서와 소유·공유 관계 조회
→ 서버가 사용자와 보고서의 관계로 수정 권한 판단
→ 입력 형식과 업무 규칙 검증
→ 보고서와 변경 이력을 하나의 데이터 변경 단위로 처리
→ commit 결과에 따라 성공 또는 안전한 오류 응답 생성
→ 프런트엔드가 응답을 화면 상태로 표현
→ 로그와 데이터 조회로 결과 확인
```

이 순서는 **확인해야 할 책임의 논리적 순서**이며 하나의 기술 구성요소나 고정된 코드 위치를 뜻하지 않습니다. 프레임워크의 미들웨어, 서비스 계층, 데이터베이스 쿼리나 행 수준 보안처럼 구현 위치는 달라질 수 있습니다. 대상 조회와 권한 판단이 한 데이터 접근 안에서 함께 수행될 수도 있지만, 어떤 사용자가 어떤 자원에 어떤 행동을 할 수 있는지 검증한다는 책임은 사라지지 않습니다.

## 비유 후보와 한계

회사 건물의 안내 창구·출입 확인·기록실을 한 시스템으로 비유합니다.

- API는 요청 양식과 접수 규칙을 가진 안내 창구에 가깝습니다.
- 인증은 출입증이 누구의 것인지 확인하는 과정에 가깝습니다.
- 인가는 확인된 사람이 특정 방에서 특정 행동을 해도 되는지 판단하는 규칙에 가깝습니다.
- 데이터베이스는 중요한 기록을 정해진 구조와 제약 아래 보존하는 기록실에 가깝습니다.

비유의 한계도 본문에서 함께 설명합니다. 실제 API는 사람처럼 모호한 요청을 알아서 해석하지 않고, 데이터베이스는 단순한 파일 보관함이 아니며 동시 변경·트랜잭션·제약 조건을 처리합니다. 하나의 토큰이 물리적인 출입증처럼 모든 권한 정보를 완전하게 담는 것도 아니고, 실제 시스템에는 캐시·큐·외부 서비스와 여러 데이터 저장소가 추가될 수 있습니다.

## 구분해야 할 용어

| 혼동하기 쉬운 쌍 | 장에서 확인할 경계 |
|---|---|
| API / endpoint | API는 전체 계약과 기능 경계, endpoint는 구체적인 접근 지점인지 확인 |
| API / backend | API는 백엔드가 제공하는 경계 중 하나이며 백엔드 전체와 같은 뜻이 아님 |
| 스키마 / API 계약 | 저장 구조와 외부 입력·출력 계약이 어디에서 같고 달라지는지 확인 |
| 인증 / 인가 | 누구인지 확인하는 절차와 무엇을 할 수 있는지 판단하는 절차 구분 |
| 입력 검증 / 인가 | 값의 형식·범위가 맞는지와 그 사용자가 행동할 권한이 있는지 구분 |
| 입력 값 / 쿼리 구조 | 사용자가 보낸 값을 처리하는 것과 그 값이 데이터 명령의 구조를 바꾸게 두는 것을 구분 |
| 세션 / 토큰 | 서버가 유지하는 인증 상태와 상태를 전달하는 자격 증명의 관계 확인 |
| 서명 / 암호화 | 내용의 위조 여부를 확인하는 보장과 내용을 읽지 못하게 보호하는 보장을 구분 |
| `Authorization` 헤더 / 인가 | 이름이 비슷해도 헤더는 자격 증명을 전달하는 자리이고 행동 허용 판단은 서버가 별도로 수행함을 확인 |
| 요청 성공 / commit | 응답이 성공으로 보이는 것과 영속 변경이 확정된 것을 어떤 증거로 구분하는지 확인 |
| 트랜잭션 / HTTP 요청 | 하나의 요청이 항상 하나의 데이터베이스 트랜잭션과 일치하는지 단정하지 않음 |
| 트랜잭션 / 동시 수정 충돌 | 여러 변경의 원자성을 지키는 것과 두 사용자의 수정이 서로 덮어쓰지 않게 하는 판단을 구분 |
| 인증 오류 / 권한 거절 | 신원을 증명하지 못한 상황과 신원은 알지만 행동이 허용되지 않은 상황 구분 |

## 검증한 주장 목록

| 주장 | 확인한 범위와 집필 판정 | 확인 출처 ID | 잘못 설명했을 때의 위험 |
|---|---|---|---|
| API는 구성요소 사이의 명시적 계약으로 설명할 수 있다 | OpenAPI 3.2.0이 operation별 parameter·request body·response·security requirement를 기술하는 범위를 확인했습니다. 명세의 존재가 실제 구현의 준수나 권한 검사를 증명하지는 않는다고 함께 설명합니다. | `OAS` | API를 단순 URL이나 백엔드 전체로 오해 |
| 인증과 인가는 별도 통제다 | NIST·OWASP의 인증 정의와 OWASP의 권한 판단 지침을 연결해 구분할 수 있습니다. 인증 뒤 인가가 필요한 대표 흐름은 설명하되 모든 시스템의 고정된 코드 실행 순서로 일반화하지 않습니다. | `NIST-ID`, `OWASP-AUTHN`, `OWASP-AUTHZ` | 로그인만 하면 모든 자원 접근을 허용하는 설계 |
| 권한 판단은 신뢰할 수 있는 집행 경계에서 요청 대상별로 수행해야 한다 | OWASP는 deny by default와 매 요청 권한 검증을 권고하고 API1·API5는 객체 ID와 기능별 검사를 요구합니다. “서버 한 파일”이 아니라 우회할 수 없는 서비스·데이터 경계의 책임으로 설명합니다. | `OWASP-AUTHZ`, `OWASP-API` | 다른 사용자의 데이터 조회·수정 |
| 여러 데이터 변경은 업무 원자성이 필요할 수 있다 | PostgreSQL 18은 트랜잭션을 여러 단계를 모두 반영하거나 모두 취소하는 단위로 설명합니다. 한 HTTP 요청과 한 트랜잭션이 항상 일치한다고 쓰지 않습니다. | `PG-TX` | 일부 변경만 반영되어 데이터 불일치 |
| 트랜잭션이 동시 수정 충돌을 자동으로 해결하는 것은 아니다 | PostgreSQL의 격리 수준별 이상 현상·명시적 잠금·직렬화 실패와 애플리케이션 재시도를 확인했습니다. 낙관적·비관적 전략의 구현법은 별도 출처와 설계가 필요하므로 이번 장에서는 충돌 정책이 별도 결정이라는 경계까지만 설명합니다. | `PG-TX` | 먼저 저장한 변경이 조용히 사라짐 |
| 사용자 입력은 값으로 처리되며 쿼리나 명령 구조를 바꿀 수 없어야 한다 | OWASP는 문자열 결합을 피하고 prepared statement와 variable binding을 쓰도록 안내하며 PostgreSQL `PQexecParams`는 명령문과 값을 분리합니다. 특정 ORM의 자동 방어는 주장하지 않습니다. | `OWASP-INJECTION`, `PG-TX` | 입력이 데이터 명령으로 해석되어 조회·변경 범위가 오염됨 |
| 상태 전달 수단과 권한 정책은 같은 것이 아니다 | NIST는 세션을 인증 사건과 연결된 지속 상호작용으로 정의하고 접근 토큰 존재를 가입자 현재성의 증거로 보지 않습니다. OWASP는 세션 ID와 서버의 업무·접근 로직을 분리합니다. 토큰이 claim을 담을 수 있다는 사실과 최종 정책 집행은 별도로 설명합니다. | `OWASP-SESSION`, `NIST-ID` | 토큰 존재만으로 민감 행동 허용 |
| 서명된 토큰의 내용이 자동으로 비밀이 되는 것은 아니다 | RFC 7515는 JWS를 서명 또는 MAC으로 무결성을 보호하는 구조로, RFC 7516은 JWE를 암호화되고 무결성이 보호된 메시지로 정의합니다. JWT 전체를 항상 JWS 또는 JWE라고 단정하지 않고 사용 형식을 확인하게 합니다. | `IETF-JOSE` | 토큰 안에 개인정보·비밀정보를 안전하다고 가정 |
| `Authorization` 헤더와 인가 판단은 같은 것이 아니다 | RFC 9110에서 이 헤더는 자격 증명을 전달하며 `401`과 `403`은 다른 실패 조건을 나타냅니다. 헤더 존재나 이름만으로 애플리케이션의 자원별 권한 검사가 끝났다고 볼 수 없습니다. | `IETF-HTTP-AUTH`, `MDN-HTTP` | 헤더가 있으면 자원 권한 검사도 끝났다고 오해 |
| 오류와 로그는 디버깅 증거이면서 정보 노출 경계다 | OWASP는 일반화된 인증 실패 응답과 권한 실패의 안전한 종료를 권고하고, 로그에서 세션 식별자·접근 토큰·비밀번호·연결 문자열·키·민감 개인정보를 직접 기록하지 않도록 안내합니다. 오류 문구와 내부 로그의 목적을 분리합니다. | `OWASP-AUTHN`, `OWASP-AUTHZ`, `OWASP-LOGGING` | 계정 열거, 토큰·개인정보 노출 |
| 데이터베이스 제약은 애플리케이션 검증과 다른 방어 계층이 될 수 있다 | PostgreSQL 18의 unique·primary key·foreign key 등은 저장소가 거부할 수 있는 무결성 규칙을 제공합니다. “마지막 방어선”이라는 절대 순서 대신 애플리케이션 검증을 보완하는 독립 계층으로 설명합니다. | `PG-TX` | 중복·고아 데이터·경쟁 조건을 화면 검증만으로 방지한다고 오해 |

## 확인한 공식 출처

출처 유형은 근거의 효력과 적용 범위를 구분하기 위한 것입니다. `규범 명세`라고 표시해도 그 요구가 모든 애플리케이션에 직접 적용된다는 뜻은 아니며, `실무 지침`은 유용한 검토 기준이지만 프로토콜 표준과 같은 효력을 갖지 않습니다.

| 출처 ID | 확인한 공식 문서 | 출처 유형 | 직접 뒷받침하는 범위 | 적용 한계 |
|---|---|---|---|---|
| `OAS` | https://spec.openapis.org/oas/v3.2.0.html | OpenAPI Initiative 규범 명세, 3.2.0 | operation의 parameter·request body·response·security requirement와 API 설명 형식 | 명세와 구현의 일치, 런타임 권한 집행은 별도 검증 필요 |
| `OWASP-AUTHN` | https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html | OWASP 실무 보안 지침 | authentication 정의, 일반화된 실패 응답과 재인증 판단 | 특정 프로토콜의 규범 명세가 아니며 제품별 구현은 별도 확인 필요 |
| `OWASP-AUTHZ` | https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html | OWASP 실무 보안 지침 | 최소 권한, deny by default, 매 요청 권한 확인과 테스트 | 권한 모델·집행 위치의 구체 구현을 하나로 정하지 않음 |
| `OWASP-SESSION` | https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html | OWASP 실무 보안 지침 | 세션 ID와 서버 측 의미·업무 로직, 세션 수명과 보호 경계 | 세션 방식을 모든 애플리케이션의 유일한 선택으로 만들지 않음 |
| `OWASP-INJECTION` | https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html | OWASP 실무 보안 지침 | 문자열 결합 위험, prepared statement와 parameterized query 원칙 | ORM·언어·드라이버별 안전한 API는 해당 공식 문서가 추가로 필요 |

| `PG-TX` | https://www.postgresql.org/docs/18/tutorial-transactions.html, https://www.postgresql.org/docs/18/transaction-iso.html, https://www.postgresql.org/docs/18/ddl-constraints.html, https://www.postgresql.org/docs/18/libpq-exec.html | PostgreSQL 18 제품 공식 문서 | 트랜잭션 원자성·commit·rollback, 격리와 직렬화 재시도, 제약 조건, 명령문과 매개변수 분리 | PostgreSQL 18의 구체 동작이며 다른 데이터베이스·드라이버의 동일 동작을 보장하지 않음 |
| `MDN-HTTP` | https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Authentication, https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/401, https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status/403 | MDN 설명용 보조 자료 | HTTP 인증 challenge·credential 흐름과 `401`·`403`을 비개발자에게 연결하는 설명 | 규범적 의미는 RFC 9110을 우선하며 브라우저·서버 구현의 전체 동작을 보증하지 않음 |

제품 선택이나 구현 예제를 추가한다면 해당 제품의 공식 문서가 별도로 필요합니다. 블로그, 마케팅 페이지와 검색 요약은 핵심 정의의 단독 근거로 사용하지 않습니다. PostgreSQL 문서에서 확인한 현재 안정 버전은 2026-08-06 기준 18이며, OpenAPI 명세는 3.2.0, NIST 디지털 신원 지침은 2025년 7월 공개된 Revision 4, OWASP API Security Top 10은 2023 판입니다.

## 집필 전 남은 결정과 금지할 일반화

- API 명세는 계약을 기술하는 도구이지 구현이 계약을 지켰다는 실행 증거가 아닙니다. 공개 원고의 검증 절차에는 실제 요청·응답과 권한 테스트를 별도로 둡니다.
- 권한 집행은 “서버 코드 한 곳”으로 고정하지 않습니다. 프런트엔드에서 우회할 수 없고 신뢰할 수 있는 서비스 또는 데이터 경계에서 매 요청의 주체·대상·행동 관계를 검증해야 한다는 책임으로 설명합니다.
- `401`과 `403`은 유용한 HTTP 구분이지만 보안을 위해 자원의 존재를 감추는 `404` 선택이나 애플리케이션별 오류 계약이 있을 수 있습니다. 상태 코드만 보고 내부 원인을 확정하지 않습니다.
- JWS·JWE는 제공하는 보장을 구분하기 위한 예시입니다. JWT 또는 특정 토큰 형식을 모든 프로젝트의 기본값으로 권하지 않습니다.
- PostgreSQL의 트랜잭션·격리·제약 동작을 관계형 데이터베이스 전체의 세부 동작으로 확대하지 않습니다. 공개 원고에서는 안정된 개념과 제품 예시를 구분합니다.
- prepared statement가 입력 검증·인가·업무 규칙을 대신한다고 설명하지 않습니다. 특정 ORM이 자동으로 안전하다는 주장도 해당 공식 문서 없이는 추가하지 않습니다.
- NIST SP 800-63B-4의 `SHALL`·AAL 요구는 미국 연방 시스템의 디지털 신원 범위입니다. 일반 독자에게는 용어와 위험 판단 근거로 사용하고 보편적인 법적 의무처럼 쓰지 않습니다.
- OWASP Cheat Sheet와 API Security Top 10은 실무 보안 지침과 위험 인식 자료입니다. 규범적 프로토콜 표준이나 완전한 보안 체크리스트로 부르지 않습니다.

## 조사 시 확인 질문

1. 각 출처가 규범적 표준인지, 교육용 설명인지, 보안 실무 지침인지 구분했나요?
2. authentication, authorization, identification, session을 출처마다 같은 뜻으로 쓰는지 확인했나요?
3. `401`, `403`과 오류 본문 설명이 기존 HTTP 장과 충돌하지 않나요?
4. transaction 설명에서 한 요청과 한 트랜잭션이 항상 일치한다고 일반화하지 않았나요?
5. PostgreSQL의 제품 동작을 모든 관계형 데이터베이스의 절대 규칙으로 확장하지 않았나요?
6. 토큰이나 JWT를 세션보다 항상 우월한 선택처럼 설명하지 않았나요?
7. 권한 검사를 프런트엔드 UI 제어로 대체할 수 있다는 오해를 남기지 않았나요?
8. 공개 예시가 실제 자격 증명, 개인정보나 운영 데이터를 요구하지 않나요?
9. 보고서 ID만 바꿔 다른 사용자의 자원에 접근하는 객체 수준 권한 실패를 검토할 수 있나요?
10. 사용자 입력을 쿼리 문자열이나 명령에 직접 이어 붙이는 구현을 위험 신호로 제시했나요?
11. 서명된 토큰의 내용을 암호화된 비밀로 오해하지 않도록 보장 차이를 설명했나요?
12. 트랜잭션이 동시 수정 충돌과 마지막 쓰기 덮어쓰기를 자동으로 해결한다고 일반화하지 않았나요?

## 분량과 위임 기준

공개 원고는 HTTP 참조 장과 비슷한 8,000~12,000자 범위를 목표로 삼되 문자 수 자체를 품질 기준으로 사용하지 않습니다. 12,000자를 크게 넘기면 세 책임을 한 장에 유지할 이유가 약해졌는지 먼저 점검하고, 구현 세부를 관련 장으로 위임합니다.

이 장에서 직접 정의할 핵심은 API 계약, 영속 상태, 인증, 인가, 트랜잭션과 요청 흐름입니다. endpoint, 스키마, 세션, 토큰, 서명·암호화, 동시성은 핵심 흐름을 판단하는 데 필요한 최소 경계만 설명하고 용어집과 관련 장으로 연결합니다. SQL 문법, OAuth 흐름, ORM 사용법, 키 관리, 백업·마이그레이션과 캐시·큐는 이 장에서 구현하지 않습니다.

시각 자료는 보고서 수정 요청이 각 책임을 통과하는 다이어그램 하나를 기본값으로 하며, 장식용 그림을 추가하지 않습니다. 같은 정보를 전달하는 대체 텍스트를 함께 작성합니다.

## 원고 구조 후보

1. 먼저 결론과 왜 이 책임들을 함께 보되 같은 것으로 보면 안 되는가
2. API·데이터베이스·인증·인가의 한 문장 정의와 회사 건물 비유의 한계
3. 보고서 수정 요청이 각 책임을 통과하는 전체 흐름
4. API 계약에서 확인하는 입력·출력·오류·권한 조건
5. 영속 상태, 입력과 쿼리의 경계, 스키마·제약, 트랜잭션과 동시 수정
6. 인증과 인가, 세션과 토큰, 서명과 암호화의 최소 관계
7. 성공·실패·부분 실패의 신호와 개발자 도구·로그·테스트·데이터 증거
8. 판단 규칙, 흔한 실패와 AI에게 요청할 검토 계약
9. 확인 체크리스트와 짧은 연습
10. 관련 용어와 출처

## `seed`에서 `draft`로 올릴 수용 기준

- API, 데이터베이스, 인증과 인가를 각각 정의하고 하나의 요청 흐름에서 연결합니다.
- 회사 건물 비유의 맞는 지점과 깨지는 지점을 명시합니다.
- 보고서 수정 사례에서 인증 실패, 권한 거절, 입력 오류, 충돌, 데이터 변경 실패와 성공을 구분합니다.
- 요청 검증, 권한 판단, 업무 규칙과 영속 변경의 책임 경계를 설명합니다.
- 권한 판단에 필요한 대상 조회를 포함하고, 논리적 책임 순서를 특정 프레임워크의 고정 코드 순서처럼 설명하지 않습니다.
- 사용자 입력을 값으로 처리하는 것과 쿼리 구조를 바꾸게 두는 것을 구분합니다.
- 서명과 암호화, `Authorization` 헤더와 인가 판단을 각각 구분합니다.
- 비개발자가 확인할 수 있는 Network 탭, 안전한 로그, 테스트와 데이터 상태 증거를 제시합니다.
- 전체 요청 흐름 다이어그램과 같은 내용을 전달하는 대체 텍스트를 포함합니다.
- 특정 프레임워크, 데이터베이스, 세션 방식이나 토큰 형식을 보편적 정답으로 제시하지 않습니다.
- 모든 핵심 주장에 직접 확인한 출처 ID와 적용 한계가 연결돼 있습니다.
- 확인한 공식 문서의 URL, 확인일과 적용 범위가 `research/source-map.md`와 일치합니다.
- 관련 용어집과 HTTP·데이터 모델·보안·운영 장의 교차 링크를 검증합니다.
- `npm run check`가 성공합니다.
- 자동 검사만으로 독립 검토가 완료된 것처럼 `review`로 올리지 않습니다.

## 후속 작업 순서

1. 이 브리프의 확인된 주장과 금지할 일반화를 따라 공개 원고를 처음부터 끝까지 읽을 수 있는 `draft`로 작성합니다.
2. 요청 흐름 다이어그램과 동등한 대체 텍스트를 함께 만들고 출처·용어집·인접 장 링크를 연결합니다.
3. 품질 루브릭 자체 점검과 자동 검증을 수행합니다.
4. 독립 AI 기술 검토와 사람 기술 검토를 요청하고 사용한 모델·버전과 검토 기록을 남긴 뒤에만 `review` 승격을 검토합니다.

## 독립 검토 반영 상태 — 2026-08-06

Claude Code 2.1.223의 `claude-opus-5` Max 읽기 전용 검토는 P0 0건·P1 5건·P2 13건·독립 15/18·치명 항목 없음으로 완료됐고, Codex는 실제 원고와 근거에 대조해 P1 수용 4건·부분 수용 1건, P2 수용 10건·부분 수용 2건·기각 1건으로 재판정했습니다. 안전한 AI 계약·허가받은 부정 테스트·일반화된 인증 실패 응답·호환성·용어 첫 등장·스키마와 외부 계약·관찰 주체·응답 유실 다이어그램·PostgreSQL 18 고정 URL과 MDN 보조 자료 범위를 반영했습니다. RFC 7519를 새로 확인하지 않았으므로 공개 원고의 JWT 표현은 이미 확인한 JWS·JWE 범위 안의 “서명된 토큰”으로 좁혔습니다.

최종 공개 원고는 16,212자이며 자체 루브릭 18/18·치명 항목 없음, 독립 검토 `request:`와 자동 검증 증거를 갖춰 `review`로 표시합니다. AI 검토는 사람 `technical:`·`editorial:`·`reader:` 증거가 아니므로 사람 기술·편집 검토와 실제 비개발자 독자 테스트를 별도로 수행해야 합니다.
