# 모임 참가 API·데이터베이스·인증 장 조사 브리프

- 상태: **반복 사례 전환 범위 고정 — 새 독립 검토 전**
- 대상 공개 문서: `src/content/docs/04-backend-data/api-database-auth.md`
- 대상 공개 상태: `draft`
- 기준일: 2026-08-10

이 브리프는 공개 원고가 아니라 모임 참가 사례로 실질 개정하는 장의 주장·근거·일반화 금지선을 고정하는 내부 연구 문서입니다. 2026-08-06에 직접 확인한 OpenAPI 3.2.0·NIST SP 800-63 Revision 4·IETF RFC 7515·7516·9110·OWASP Cheat Sheet와 API Security Top 10 2023·PostgreSQL 18·MDN HTTP의 기존 출처 ID와 적용 범위를 재사용합니다. 이번 전환은 특정 프레임워크·인증 서비스·데이터베이스 제품의 구현법을 추가하지 않으므로 새 제품 출처가 필요하지 않으며, 네트워크 조사를 수행하지 않습니다.

기존 `research/api-database-auth-research-brief.md`와 2026-08-06 검토 기록은 보고서 사례의 역사 정본입니다. 이 파일들을 수정하거나 새 모임 원고의 `reviewEvidence`로 재사용하지 않습니다.

## 이 장이 답할 한 가지 질문

**인증된 참가자의 모임 참가 요청이 API 계약, 자신의 참가 관계에 대한 인가, 중복·모집 상태·정원 업무 규칙과 데이터베이스 트랜잭션을 통과해 어떻게 하나의 확정 결과가 되는가?**

API·endpoint·backend, 인증·인가, 세션·토큰, JWS·JWE, 입력 값·쿼리 구조, 내부 스키마·외부 계약, 트랜잭션·`commit`·`rollback`의 영속 정의는 유지합니다. 사례 필드와 행동만 보고서 수정에서 모임 참가·자기 취소·주최자 전용 이벤트 수정으로 바꾸고, 마지막 한 자리의 동시 요청과 `commit` 뒤 응답 유실을 핵심 판정 사례로 추가합니다.

## 사례 계약

- 비로그인 방문자는 공개 모임을 조회할 수 있지만 참가·취소는 인증된 요청 주체만 수행합니다.
- 참가와 취소의 `participant_id`는 요청 본문을 믿어 정하지 않고 인증된 현재 주체에서 결정합니다.
- 참가자는 자신의 `registrations` 관계만 만들거나 취소할 수 있습니다. 다른 참가자의 식별자를 바꿔 취소하는 행동은 거절해야 합니다.
- 주최자 전용 이벤트 수정은 현재 주체와 `events.host_id`의 소유권 관계를 확인합니다. 자신의 참가 관계에 대한 권한과 주최자의 이벤트 수정 권한은 서로 다른 인가 규칙입니다.
- 새 참가 확정은 `event.status = open`, 활성 참가 중복 없음, 현재 `confirmed` 수가 `capacity`보다 작다는 업무 규칙을 만족해야 합니다.
- 취소 이력을 보존하는 계약에서는 참가 관계를 물리적으로 지우기보다 `registration.status = cancelled` 같은 상태나 별도 이력으로 남길 수 있습니다. 구체적인 저장 구조는 요구사항과 데이터베이스에 맞춰 별도로 결정합니다.
- 이벤트·참가 관계의 일관성, 활성 참가 고유성과 정원 초과 방지는 애플리케이션의 사전 설명만으로 보증하지 않고 데이터베이스 제약·트랜잭션·동시성 설계와 처리 뒤 재조회로 검증합니다.

## 마지막 한 자리 테스트 오라클

가상 모임의 `capacity = 10`, 현재 `confirmed = 9`이고 서로 다른 인증 주체 A·B가 같은 시작 장벽에서 참가 요청을 보낸다고 가정합니다. 두 요청은 모두 트랜잭션 밖의 사전 조회에서 “참가 가능”을 볼 수 있지만, 그 조회는 확정 권한이나 자리 예약이 아닙니다.

검증 오라클은 다음과 같습니다.

- 참가 확정 성공 1건
- 중복·마감·정원 충돌 범주의 안전한 실패 1건
- 최종 활성 `confirmed = 10`
- 최종 `confirmed <= capacity`
- 같은 참가자의 활성 중복 0건
- 실패한 요청의 부분 저장 0건

트랜잭션 격리, 조건부 갱신, 데이터베이스 제약과 유한한 재시도 정책은 가능한 설계 대안입니다. 실제 선택은 사용 데이터베이스의 지원 동작, 격리 의미, 충돌 빈도, 응답 지연과 업무 요구에 맞춰 직접 검증해야 하며 PostgreSQL 18에서 확인한 구체 동작을 다른 데이터베이스에 그대로 일반화하지 않습니다.

## 7단계 다이어그램 계약

이 절은 Task20의 도표 분할 이전 계약을 보존한 역사 기록입니다. 현재는 `api-database-auth-flow.svg`·대응 Mermaid가 정상 책임 순서만, `api-database-auth-sequence.svg`·대응 Mermaid가 마지막 한 자리의 동시 요청과 commit 뒤 응답 유실 복구를 각각 설명합니다. 두 질문을 다시 합치거나 개요에 아래 모든 실패 분기를 넣으라는 현재 지시가 아닙니다. 채택 계보는 `docs/project/public-beta-visual-audit.md`의 PBV-03·PBVA-001과 R04 후속 검토 기록에서 확인합니다. 아래 기존 제목·분기 계약은 당시 내용 그대로 유지합니다.

제목은 Mermaid와 SVG 모두 `모임 참가 요청의 API·인증·인가·데이터베이스 책임 흐름`으로 고정합니다.

1. 요청과 `eventId` 식별
2. API 계약
3. 인증과 요청 주체
4. 이벤트·참가 관계 조회와 인가
5. 중복·모집 상태·정원 업무 규칙
6. `registrations`와 정원 판단 트랜잭션·`commit`
7. 응답·재조회·안전한 로그·동시성 테스트

실패 분기는 형식 오류, 인증 실패, 권한 거절, 중복·마감·정원 충돌, `rollback`·서버 오류, `commit` 뒤 응답 전달 실패를 포함합니다. 정상 흐름 일곱 단계와 실패 분기의 의미는 Mermaid·SVG·본문 대체 텍스트에서 일치해야 합니다.

## 재사용할 출처 ID

| 출처 ID | 확인된 문서·버전 | 이번 적용 범위 | 제한 |
|---|---|---|---|
| `OAS` | OpenAPI Specification 3.2.0 | API operation·요청·응답·보안 요구 설명 | 실행 준수·인가 보증 아님 |
| `OWASP-AUTHN` | OWASP Authentication Cheat Sheet | 인증 정의·일반화된 실패 응답 | 특정 프로토콜 표준 아님 |
| `OWASP-AUTHZ` | OWASP Authorization Cheat Sheet | 기본 거절·최소 권한·매 요청 인가 | 구체 권한 모델·집행 위치 고정 아님 |
| `OWASP-SESSION` | OWASP Session Management Cheat Sheet | 세션 ID·서버 상태·수명·보호 경계 | 세션 방식을 유일한 선택으로 만들지 않음 |
| `OWASP-INJECTION` | OWASP SQL Injection Prevention Cheat Sheet | 쿼리 구조와 입력 값 분리 | 인가·업무 규칙 대체 아님 |
| `OWASP-LOGGING` | OWASP Logging Cheat Sheet | 안전한 진단 로그와 비밀 제외 | 법률·조직 보존 정책 대체 아님 |
| `OWASP-API` | OWASP API Security Top 10 2023 API1·API5 | 객체·기능별 인가 위험 | 완전한 보안 표준 아님 |
| `NIST-ID` | NIST SP 800-63 Revision 4 | 인증·authenticator·session 용어와 위험 판단 | 미국 연방 적용 범위를 보편 의무로 확대하지 않음 |
| `IETF-JOSE` | RFC 7515 JWS·RFC 7516 JWE | 서명·MAC 기반 무결성과 암호화·무결성 구분 | 실제 토큰 형식·키 관리 별도 설계 |
| `IETF-HTTP-AUTH` | RFC 9110 | `Authorization`, `401`, `403`의 규범 의미 | 상태 코드만으로 내부 원인 확정 금지 |
| `PG-TX` | PostgreSQL 18 Transactions·Isolation·Constraints·libpq | 트랜잭션·격리·제약·명령과 값 분리의 제품 예시 | 다른 DB·드라이버 동작 보장 아님 |
| `MDN-HTTP` | MDN HTTP authentication·`401`·`403` | 비개발자용 HTTP 흐름 보조 설명 | 규범 의미는 RFC 9110 우선 |

## 유지할 개념 경계

- API는 백엔드가 제공하는 계약 경계 중 하나이며 endpoint 하나나 백엔드 전체와 같지 않습니다.
- 인증은 요청 주체를 확인하고 인가는 확인된 주체·대상·행동의 허용 여부를 판단합니다.
- 세션과 토큰은 인증 상태를 이어 주거나 전달하는 수단이지 대상별 권한 정책 자체가 아닙니다.
- JWS의 서명·MAC 보호와 JWE의 암호화·무결성 보호는 같은 보장이 아닙니다.
- 사용자 입력은 데이터 명령의 값으로 전달하고 쿼리 구조와 분리하지만, prepared statement가 인가·업무 규칙까지 대신하지는 않습니다.
- 데이터베이스 내부 스키마와 외부 API 계약은 역할이 다르며 내부 필드를 그대로 공개하지 않습니다.
- `commit`은 트랜잭션 변경의 확정이고 `rollback`은 아직 확정되지 않은 변경의 취소이며, 백업 복원과 같지 않습니다.
