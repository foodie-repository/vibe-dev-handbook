# R07 테스트 전략 — 추적 가능한 1차 근거

확인일: 2026-11-15. 대상은 `08-quality/testing-strategy.md` 전체 검토입니다. 과거 source-map의 2026-08-13 확인 기록은 보존합니다. 아래는 관련 절만 읽은 근거이며 표준 전문·제품 실행·새 브라우저 검증이나 전체 사이트 현재성 확인이 아닙니다. 인용은 짧은 원문 식별자이고 설명은 controller의 제한된 요약입니다.

## S01 ISO/IEC/IEEE 29119-1:2022 공개 개요

- URL: https://www.iso.org/standard/81291.html
- 위치: 제목, Abstract, Life cycle / Now. 현재 공개 페이지는 2022판을 Now로 표시하고 시리즈의 일반 개념을 다룬다고 설명합니다.
- 직접 발췌: “This document specifies general concepts in software testing”
- 한계: 이번 추출에는 edition·stage 숫자와 manual/automated·scripted/unscripted 열거가 없습니다. 유료 표준 전문은 읽지 않았으며 과거 edition2·60.60 기록을 새 확인으로 갱신하지 않습니다.

## S02 ISO 시리즈 안내

- URL: https://committee.iso.org/sites/jtc1sc7/home/projects/flagship-standards/isoiecieee-29119-series.html
- 위치: Software and systems engineering — Software testing, 본문 두 번째 문단.
- 직접 발췌: “Static testing, in the form of reviews, is defined in ISO/IEC 20246.”
- 관측: Part2의 조직·관리·동적 테스트 과정, Part3의 과정 산출 문서, Part4의 설계 기법, Part1의 공통 개념을 연결합니다. 현재 본문에는 manual/automated·scripted/unscripted 열거가 없습니다. 원고의 해당 귀속은 reviewer가 실제 제공 근거와 대조해야 합니다. 이 부재가 그 분류 자체의 오류나 표준 전체의 부재를 증명하지는 않습니다.

## S03 IEEE Computer Society SWEBOK 안내

- URL: https://www.computer.org/education/bodies-of-knowledge/software-engineering/resources/
- 위치: About SWEBoK의 25 September 2025 Update, Chapter5 Software Testing 안내.
- 직접 발췌: “it is now identified as SWEBOK v4.0a.”
- 관측: 2025-09-25 소규모 개정으로 v4.0a를 구분하며, 이 날짜는 출판물 갱신일이지 이번 확인일이 아닙니다. 다운로드 폼 제출이나 계정·구독 변경은 하지 않았습니다.

## S04 SWEBOK V4.0a 테스트 장

- URL: https://ieeecs-media.computer.org/media/education/swebok/swebok-v4.pdf
- 위치: 표지 Released Sept 2025, Chapter5 Introduction(5-1~2), 1.2.7 The Oracle Problem(5-4~5), 1.3, 2.1(5-6~7).
- 직접 발췌: “Static techniques complement dynamic testing”; “The oracle cannot always decide”; “Four test stages can be distinguished: unit, integration, system, and acceptance.”
- 관측: 유한한 선택 사례의 실행 결과를 기대 행동과 대조합니다. 입력 외 상태·환경·시점도 사례 조건이며, 정적 기법은 실행 기반 검증을 보완합니다. 오라클은 사람 또는 기계가 판정하고 판단 불가일 수도 있습니다. 수준은 대상·목적에 따라 구분하며 특정 개발 순서나 한 수준의 우월성을 강제하지 않습니다. 통합 검증은 구성요소 상호작용을 봅니다.
- 한계: 전체 책을 완독한 근거가 아닙니다. PDF 텍스트 추출의 하이픈/행 구분은 보존하되 짧은 인용에서 줄바꿈만 합쳤습니다. 테스트의 정확성이 모든 실행 영역의 무결함을 증명한다고 해석하지 않습니다.

## S05 Ham Vocke의 The Practical Test Pyramid

- URL: https://martinfowler.com/articles/practical-test-pyramid.html
- 위치: 2018-02-26 글의 The Test Pyramid, Unit tests/What's a Unit?, Integration Tests, Contract Tests, Exploratory Testing, The Confusion About Testing Terminology.
- 직접 발췌: “Write tests with different granularity”; “The more high-level you get the fewer tests you should have”
- 관측: 작고 빠른 테스트를 넓은 테스트보다 많이 두는 경험적 지침입니다. 층 이름과 통합 범위에는 팀별 차이가 있고 실제 대역/경계를 명시해야 합니다. 소비자·제공자의 인터페이스 합의, 실제 연결과 대역의 차이, 자동화가 놓친 사용성·설계 문제의 탐색을 설명합니다. 고정 비율이나 모든 UI 검사의 E2E 동일시를 뒷받침하지 않습니다.
- 한계: 표준이 아닌 저자의 실무 설명입니다. Java/Spring 예제의 현재 버전·도구 실행은 검증하지 않았으며 외부 그림을 핸드북에 복제하지 않습니다.

## S06 Google Testing Blog — flaky

- URL: https://testing.googleblog.com/2016/05/flaky-tests-at-google-and-how-we.html
- 위치: John Micco, 2016-05-27, 본문 정의 문단과 mitigation/quarantine 목록. 댓글은 근거에서 제외합니다.
- 직접 발췌: “a test that exhibits both a passing and a failing result with the same code.”
- 관측: 동시성·비결정성·외부 코드·인프라 등이 원인이며, 반복 재시도나 격리가 실제 결함을 가릴 수 있습니다. 실패를 무조건 무시하거나 재실행 성공만 남기는 주장을 뒷받침하지 않습니다. 조직 수치는 2016년 사례이지 현재 전체 산업의 비율이 아닙니다. 소유자·기한·해제 조건은 핸드북의 보수적 운영 규칙으로 구분합니다.

## S07 Google Testing Blog — coverage

- URL: https://testing.googleblog.com/2014/07/measuring-coverage-at-google.html
- 위치: 2014-07-14 Introduction, Results의 언어별 수치 한계, Future work.
- 직접 발췌: “don’t necessarily trust that covered code is truly well tested”; “should not be interpreted as guidelines for a particular language”
- 관측: 측정 방식과 도구 한계, 큰 통합/E2E/UI 실행의 측정 누락 가능성을 명시합니다. 조직의 집계 수치로 보편 목표를 정하거나 실행된 줄 비율을 요구·오라클·사용성 충족률로 바꾸지 않습니다. 100% 실행 커버리지가 무결함 보장이라는 근거는 아닙니다.

## 조회·적용 경계

처음 Tavily의 Google 두 URL 추출에는 댓글만 있어 본문 미확인으로 처리했습니다. 같은 결과를 성공으로 계산하지 않고 Exa 읽기에서 본문을 확인했습니다. 나머지 공개 안내와 PDF는 Tavily 추출에서 관련 본문을 확인했습니다. R06에서 해결한 D-01~D-05 연결은 현재 사례 발췌·해시를 재사용하고 사례 전체 R13 검토 완료로 확대하지 않습니다.
