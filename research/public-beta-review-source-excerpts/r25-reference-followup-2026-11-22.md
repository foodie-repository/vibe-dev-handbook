# R25 후속 확인: 방법론과 제품 설명의 직접 근거

확인일은 2026-11-22입니다. 아래 인용은 공식 문서 또는 저자 원문의 반환 본문에서 직접 대조한 짧은 구간입니다. 전체 표준·제품 계정·실행 결과를 검증한 것이 아닙니다. BDD 저자의 옛 주소에서 본문을 얻지 못했고 새 글 주소에서 확인했습니다. 8월 당시 확인일과 실패 기록은 보존합니다.

### Behaviour-Driven Development | Cucumber

[Behaviour-Driven Development | Cucumber](https://cucumber.io/docs/bdd/) · 반환 본문 문자 23–127(0부터, 끝 제외). “collaborative work around concrete, real-world examples that illustrate how we want the system to behave”

BDD는 도구 문법이 아니라 사례를 함께 논의하는 접근이다. Given–When–Then은 예시를 표현하는 한 방식이다.

### Introducing BDD | Dan North & Associates Limited

[Introducing BDD | Dan North & Associates Limited](https://dannorth.net/blog/introducing-bdd/) · 반환 본문 문자 10–55(0부터, 끝 제외). “using the word “behaviour” in place of “test””

원형 자료는 TDD를 행동의 언어로 설명하게 된 배경을 말한다.

### Scrum Guide | Scrum Guides

[Scrum Guide | Scrum Guides](https://scrumguides.org/scrum-guide.html) · 반환 본문 문자 15–101(0부터, 끝 제외). “four formal events for inspection and adaptation within a containing event, the Sprint”

Sprint 안에서 투명성·점검·적응을 구현하는 프레임워크다. 회의 이름만 도입한다고 Scrum이 되지 않는다.

### The Kanban Guide | May 2025 (latest) | Kanban Guides

[The Kanban Guide | May 2025 (latest) | Kanban Guides](https://kanbanguides.org/english/) · 반환 본문 문자 1189–1257(0부터, 끝 제외). “A definition of how WIP will be controlled from started to finished.”

일의 시작과 끝, 진행 중 작업(WIP) 통제 방식을 명시한다. 보드 모양만으로 흐름 개선을 보장하지 않는다.

### What is DevOps? - DevOps Models Explained - Amazon Web Services (AWS)

[What is DevOps? - DevOps Models Explained - Amazon Web Services (AWS)](https://aws.amazon.com/devops/what-is-devops/) · 반환 본문 문자 1448–1558(0부터, 끝 제외). “Developers and operations teams collaborate closely, share many responsibilities, and combine their workflows.”

AWS가 설명하는 협업·공동 책임의 범위다. 모든 팀의 조직도나 도구를 정하는 표준은 아니다.

### A successful Git branching model » nvie.com

[A successful Git branching model » nvie.com](https://nvie.com/posts/a-successful-git-branching-model/) · 반환 본문 문자 564–614(0부터, 끝 제외). “another person is preparing a quick production fix”

릴리스와 긴급 수정이 통합 브랜치와 어떤 관계인지 보여 주는 저자의 브랜치 모델이지 Git의 의무 규칙이 아니다.

### Introduction

[Introduction](https://trunkbaseddevelopment.com/) · 반환 본문 문자 53–130(0부터, 끝 제외). “short-lived feature branches are used for code-review and build checking (CI)”

작은 변경을 주 통합선에 자주 합친다. 수명이 짧은 리뷰 브랜치도 사용할 수 있다.

### Creating and using ChatGPT Sites | OpenAI Help Center

[Creating and using ChatGPT Sites | OpenAI Help Center](https://help.openai.com/en/articles/20001339-creating-and-managing-chatgpt-sites) · 반환 본문 문자 224–308(0부터, 끝 제외). “Restoring an earlier version restores the code, not your database or uploaded files.”

코드 버전 복원은 데이터 복원이 아니다. 같은 도움말의 Take down a Site는 삭제한 사이트의 복원 불가를 설명한다. 도메인은 제공되는 경우 소유권과 DNS 변경 권한이 필요하다. Git 커밋 연결과 Enterprise 전용이라는 현재 조건은 이 발췌가 입증하지 않는다.

### Logs in Studio | Supabase Docs

[Logs in Studio | Supabase Docs](https://supabase.com/docs/guides/monitoring-and-debugging/logs) · 반환 본문 문자 72–137(0부터, 끝 제외). “Use Logs to inspect events across your hosted project's services.”

서비스 이벤트 조회를 확인했다. 프로젝트 생성일에 따라 로그 백엔드가 달라진다는 조건과 플랜별 보존 기간은 이 근거로 확인하지 못했다.

### Choose a permission mode - Claude Code Docs

[Choose a permission mode - Claude Code Docs](https://code.claude.com/docs/en/permission-modes) · 반환 본문 문자 178–299(0부터, 끝 제외). “Except in interactive terminal sessions with bypass permissions available, edits stay blocked until you approve the plan.”

대화형 터미널의 특정 권한 조건과 비대화형 세션이 다르다. 파일·셸 접근에 대한 일반적인 읽기 전용 보장으로 사용하지 않는다. 세부 예외를 임의 설정으로 시험하지 않았다.
